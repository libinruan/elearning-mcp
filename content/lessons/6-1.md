## Summary
A remote MCP server that touches user data needs to know *who* is calling and *what they may do*. MCP does not invent its own scheme: it profiles **OAuth 2.1**. The MCP server is an OAuth **resource server**, the MCP client is an OAuth **client**, and a separate **authorization server** talks to the user and issues tokens. This lesson follows the flow one request at a time: the `401` with `resource_metadata`, Protected Resource Metadata (RFC 9728), authorization server metadata (RFC 8414 / OIDC Discovery), the three ways to register a client, PKCE with `S256`, the `resource` parameter (RFC 8707), `iss` validation (RFC 9207), and scope challenges. The notebook builds a toy authorization server and a protected SDK server on localhost and runs the whole flow, by hand and then with the SDK.

## Lesson
### When authorization applies — and when it does not
Authorization is **OPTIONAL** in MCP, but strongly recommended when a server accesses user-specific data, needs an audit trail of who did what, fronts APIs that require user consent, runs in an enterprise with strict access control, or wants per-user rate limiting.

The spec ties the mechanism to the transport:

- Implementations using an **HTTP-based transport SHOULD** conform to the authorization spec.
- Implementations using **stdio SHOULD NOT** follow it, and instead **retrieve credentials from the environment** (an API key in the server's `env`, or a library embedded in the server). A stdio server is a local process launched by the user; a browser redirect dance buys nothing there.
- Other transports **MUST** follow established security best practices for their protocol.

### The three roles
| Role | OAuth term | Job |
| --- | --- | --- |
| MCP server | **Resource server** | Accepts requests carrying access tokens and validates them. Publishes Protected Resource Metadata. |
| MCP client | **OAuth client** | Discovers the authorization server, obtains tokens on behalf of the user (the resource owner), sends them on every request. |
| Authorization server (AS) | Authorization server | Authenticates the user, asks for consent, issues tokens. Can be co-hosted with the MCP server or separate (Keycloak, Entra ID, Auth0, Okta…). |

The AS's internals are out of scope for MCP. What MCP standardises is how a client that has never seen a server *finds* the right AS and gets a token *bound to that server*.

### The standards it is built from
MCP implements a selected subset of: OAuth 2.1 (draft-ietf-oauth-v2-1-13), Bearer Token Usage (RFC 6750), Authorization Server Metadata (RFC 8414), Dynamic Client Registration (RFC 7591), Resource Indicators (RFC 8707), Protected Resource Metadata (RFC 9728), Authorization Server Issuer Identification (RFC 9207), OAuth Client ID Metadata Documents (draft-ietf-oauth-client-id-metadata-document-00), OpenID Connect Discovery 1.0 and OIDC Dynamic Client Registration. The normative core:

1. Authorization servers **MUST** implement OAuth 2.1 for confidential and public clients.
2. AS and clients **SHOULD** support Client ID Metadata Documents; they **MAY** support Dynamic Client Registration (deprecated).
3. MCP servers **MUST** implement Protected Resource Metadata; clients **MUST** use it to discover the AS.
4. AS **MUST** offer RFC 8414 metadata or OIDC Discovery; clients **MUST** support both.

### The flow, step by step
```text
Client                     MCP server (RS)                 Authorization server
  │ POST /mcp (no token)        │                                │
  │────────────────────────────►│                                │
  │ 401 WWW-Authenticate:       │                                │
  │   Bearer resource_metadata=…, scope="files:read"             │
  │◄────────────────────────────│                                │
  │ GET /.well-known/oauth-protected-resource[/mcp]              │
  │────────────────────────────►│  {resource, authorization_servers, scopes_supported}
  │ GET /.well-known/oauth-authorization-server (or openid-configuration)
  │─────────────────────────────────────────────────────────────►│
  │ register: CIMD URL | pre-registered id | DCR POST /register  │
  │ browser → /authorize?…&code_challenge&resource&state         │
  │ ◄── redirect ?code&state&iss  (validate state + iss)         │
  │ POST /token  code + code_verifier + resource                 │
  │◄───────────────────────────────────── access (+refresh) token│
  │ POST /mcp  Authorization: Bearer …  (every request)          │
```

**1. The challenge.** An unauthenticated request gets `401 Unauthorized` with a `WWW-Authenticate` header. The server **MUST** advertise its metadata either via `resource_metadata` in that header (RFC 9728 §5.1) or at a well-known URI; it **SHOULD** add a `scope` parameter naming the scopes needed.

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         scope="files:read"
```

**2. Protected Resource Metadata (PRM).** Clients **MUST** use the header URL when present, otherwise try, in order, the path-inserted URI (`https://example.com/.well-known/oauth-protected-resource/public/mcp` for an endpoint at `/public/mcp`) and then the root (`/.well-known/oauth-protected-resource`). The document **MUST** contain `authorization_servers` with at least one entry:

```json
{"resource": "https://your-server.com/mcp",
 "authorization_servers": ["https://auth.your-server.com"],
 "scopes_supported": ["mcp:tools", "mcp:resources"]}
```

If several authorization servers are listed, the **client** chooses. Each is independent: credentials and tokens are kept **per AS** and never assumed valid at another.

**3. Authorization server metadata.** MCP uses the default `oauth-authorization-server` suffix. For an issuer with a path (`https://auth.example.com/tenant1`) clients **MUST** try: `/.well-known/oauth-authorization-server/tenant1`, then `/.well-known/openid-configuration/tenant1`, then `/tenant1/.well-known/openid-configuration`. Without a path: `/.well-known/oauth-authorization-server`, then `/.well-known/openid-configuration`. After fetching, the `issuer` in the document **MUST** be identical to the issuer used to build the URL; otherwise the client **MUST NOT** use it (a document at `attacker.example` claiming `"issuer": "https://honest.example"` is rejected).

The metadata also gates PKCE: if `code_challenge_methods_supported` is **absent**, the client **MUST refuse to proceed** — OAuth has no other way to discover PKCE support. OIDC providers serving MCP **MUST** include that field.

**4. Client registration.** A client **MUST** obtain a `client_id`. Priority order for clients supporting all options:

| Priority | Mechanism | When |
| --- | --- | --- |
| 1 | **Pre-registration** | Client already has credentials for this AS (hard-coded, or entered by the user). |
| 2 | **Client ID Metadata Document (CIMD)** | AS advertises `client_id_metadata_document_supported: true`. The `client_id` *is* an HTTPS URL with a path (e.g. `https://app.example.com/oauth/client-metadata.json`) pointing to JSON containing at least `client_id`, `client_name`, `redirect_uris`; the `client_id` inside must equal the URL exactly. The AS fetches it, validates it and checks the request's redirect URI against it. |
| 3 | **Dynamic Client Registration (DCR, RFC 7591)** | AS advertises `registration_endpoint`. **Deprecated in 2026-07-28** in favour of CIMD; kept for backwards compatibility. Clients **MUST** send an appropriate `application_type` — `"native"` for desktop/CLI/localhost apps, `"web"` for remote browser apps — because OIDC defaults to `"web"`, which rejects native-style redirect URIs. |
| 4 | Prompt the user | Nothing else works. |

CIMD fits MCP's normal situation — a client and server with **no prior relationship** — without the AS accumulating thousands of anonymous registrations. **Authorization server binding** (new in 2026-07-28): pre-registered or DCR-obtained credentials **MUST** be keyed by the AS's `issuer`; if PRM later points at a different AS, the client **MUST NOT** reuse them and **MUST** re-register. CIMD client IDs are portable, because any AS resolves the URL on demand.

**5. Authorization request with PKCE.** The client generates a random `code_verifier` and sends `code_challenge = BASE64URL(SHA256(code_verifier))` with `code_challenge_method=S256` (**MUST** use `S256` when technically capable). It adds `state`, the selected `scope`, and the `resource` parameter, then opens the browser. Before redirecting, the client **MUST** record the AS's validated `issuer` alongside the verifier and state.

**6. The callback and `iss` validation (RFC 9207).** The AS redirects back with `code`, `state` and — it **SHOULD** — `iss`. An AS that sends `iss` **MUST** advertise `authorization_response_iss_parameter_supported: true`. Before sending the code anywhere, the client applies:

| `…iss_parameter_supported` | `iss` present? | Action |
| --- | --- | --- |
| `true` | yes | Compare with recorded issuer (simple string comparison) |
| `true` | no | **Reject** |
| false / absent | yes | Compare anyway |
| false / absent | no | Proceed |

No normalisation (case folding, default ports, trailing slashes) is allowed, and on mismatch the client **MUST NOT** act on or display `error`/`error_description`. This defeats **mix-up attacks**, where a malicious AS tricks the client into sending another AS's code to it. The spec expects a future revision to upgrade AS inclusion of `iss` from SHOULD to MUST.

**7. Token request.** `POST` to `token_endpoint` with `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `code_verifier` and `resource`. The AS hashes the verifier and compares — an intercepted code is useless without it.

**8. Calling the server.** Every HTTP request carries `Authorization: Bearer <token>`. Tokens **MUST NOT** go in the query string.

### Resource indicators and the canonical server URI
Clients **MUST** send `resource` (RFC 8707) in **both** the authorization and token requests, **MUST** use the MCP server's **canonical URI**, and **MUST** send it whether or not the AS supports it. The canonical URI is the most specific absolute URI identifying the server: `https://mcp.example.com/mcp`, `https://mcp.example.com`, `https://mcp.example.com:8443`. Invalid: `mcp.example.com` (no scheme), `https://mcp.example.com#fragment`. Prefer no trailing slash; lowercase scheme and host are canonical, but implementations **SHOULD** accept uppercase.

Why it matters: the AS can put the resource in the token's audience (`aud`), so a token minted for your calendar server cannot be replayed at your payroll server.

### What the server must check
- Validate tokens per OAuth 2.1 §5.2, and **validate the audience**: the token **MUST** have been issued specifically for this server (RFC 8707 §2). Invalid or expired → **401**.
- **MUST NOT** accept or transit any other tokens. If the server calls an upstream API, it obtains a *separate* token as an OAuth client of that API — never passing through the one it received (lesson 6.2).
- Clients **MUST NOT** send a server tokens issued by anyone other than that server's AS.

| Status | Meaning |
| --- | --- |
| 401 | Authorization required, or token invalid/expired |
| 403 | Insufficient scope / permissions |
| 400 | Malformed authorization request |

### Scope selection and step-up
Initial scopes, in priority order: (1) the `scope` from the 401's `WWW-Authenticate`; (2) otherwise all of PRM `scopes_supported`; (3) otherwise omit `scope`. Clients **MUST** treat challenged scopes as authoritative for the current operation and **MUST NOT** assume any subset/superset relation to `scopes_supported`, which is meant to be the *minimal* set for basic functionality.

At runtime, a token lacking a permission gets a **scope challenge**:

```http
HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope",
                         scope="files:write",
                         resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource",
                         error_description="File write permission required for this operation"
```

Servers **SHOULD** put *all* scopes needed for the operation in one challenge (no drip-feeding). Clients acting for a user **SHOULD** run the **step-up flow**: compute the **union** of previously requested scopes and the challenged ones (scope accumulation is the *client's* job, so servers stay stateless), re-authorize, retry a limited number of times, and track attempts to avoid loops. Servers **MUST** honour scope hierarchies (a broader scope implying narrower ones).

### Refresh tokens
Clients wanting refresh tokens **MUST** keep them confidential in transit and at rest, **SHOULD** list `refresh_token` in their `grant_types`, **MAY** add `offline_access` to `scope` when the AS's `scopes_supported` includes it, and **MUST NOT** assume one will be issued. MCP servers **SHOULD NOT** put `offline_access` in their challenges or PRM — refresh is a client concern, not a resource requirement. For public clients the AS **MUST** rotate refresh tokens.

### The Keycloak tutorial in brief
The official tutorial runs Keycloak in Docker (`start-dev`, admin/admin, port 8080, never for production), creates an `mcp:tools` client scope (type *Default*, *Include in token scope* on), adds an **Audience mapper** so tokens carry `aud: http://localhost:3000`, relaxes the DCR *Trusted Hosts* policy for testing, and registers a confidential client for the MCP server itself so it can call Keycloak's **token introspection** endpoint. The Python server is an `MCPServer` with `token_verifier=IntrospectionTokenVerifier(...)` and `auth=AuthSettings(issuer_url=..., required_scopes=["mcp:tools"], resource_server_url=...)`; the SDK then publishes PRM, answers 401s with `resource_metadata`, and hands every bearer token to the verifier, which checks `active`, then `aud` against the server URL. VS Code is the test client: it opens the consent page and lists the tools. The tutorial warns that a fixed audience is a test shortcut — in production the audience must follow the `resource` parameter.

### Common pitfalls (from the docs)
- **Don't hand-roll token validation** — use well-tested libraries.
- **Short-lived access tokens**; store cached tokens encrypted with eviction.
- **Always validate** — receiving a token proves nothing. Reject generic audiences like `api`.
- **HTTPS everywhere** except `localhost` during development.
- **Least-privilege scopes**, checked per tool/route on the server.
- **Never log** `Authorization` headers, tokens, codes or secrets.
- **Separate** the server's own client secret from end-user flows.
- **Proper challenges**: on 401 include `Bearer`, `realm`, `resource_metadata`.
- **Lock down DCR** if you keep it: unauthenticated DCR lets anyone register any client.
- **Pin issuer/tenant**: reject tokens from other realms even if signed by the same AS.
- **Generic errors** to clients, detailed reasons with correlation IDs in internal logs.

> **Spec changes in 2026-07-28.** `iss` in authorization responses (SHOULD for AS, MUST-validate for clients, SEP-2468); `application_type` required in DCR (SEP-837); credentials bound to the issuing AS (SEP-2352); DCR **deprecated** in favour of CIMD. Codebases written against 2025-06-18 or 2025-11-25 often still lead with DCR — expect to meet both.

## Key points
- Authorization is optional; HTTP transports **SHOULD** use the OAuth 2.1 profile, **stdio SHOULD NOT** and takes credentials from the environment.
- MCP server = **resource server**, MCP client = **OAuth client**, plus a separate or co-hosted **authorization server**.
- Discovery chain: `401` + `WWW-Authenticate: resource_metadata=…` → **PRM (RFC 9728)** with `authorization_servers` → **AS metadata (RFC 8414 / OIDC Discovery)** whose `issuer` must match exactly.
- Registration priority: **pre-registered → CIMD (HTTPS URL as `client_id`) → DCR (deprecated, needs `application_type`) → ask the user**; non-CIMD credentials are bound to the AS's `issuer`.
- **PKCE with `S256`** is mandatory; no `code_challenge_methods_supported` in AS metadata → refuse to proceed.
- `resource` (RFC 8707) = the server's **canonical URI**, sent in both authorization and token requests; servers **MUST** reject tokens whose audience is not them.
- Validate **`iss`** (RFC 9207) on the callback before redeeming the code — the mix-up defence.
- `403` + `error="insufficient_scope"` + `scope=…` triggers **step-up**; the client re-authorizes with the **union** of old and new scopes.
- Tokens go only in `Authorization: Bearer` on every request — never in the query string, never in logs.

## Pitches
### How does authorization work in MCP?
MCP reuses OAuth 2.1. The MCP server is a resource server; when I call it without a token it answers 401 and points me to its Protected Resource Metadata, which names the authorization server. I fetch that server's metadata, register — ideally with a Client ID Metadata Document — and run the authorization code flow with PKCE, passing the server's canonical URI as the resource parameter. The token I get back is bound to that server, and I send it as a bearer header on every request.

### Why do resource indicators matter so much in MCP?
A user connects one client to many servers, often through the same identity provider. Without audience binding, a token for a harmless notes server would also work against the payroll server, and a malicious server could replay the tokens it receives. The resource parameter tells the authorization server which MCP server the token is for, so it can stamp that into the audience, and each server rejects anything not issued to it. That one check underpins both token theft defence and the ban on token passthrough.

### What changed in MCP authorization in 2026-07-28?
Four things I'd point out. Dynamic Client Registration is now deprecated in favour of Client ID Metadata Documents, where the client ID is an HTTPS URL to the client's own metadata. Clients must validate the RFC 9207 iss parameter on the authorization response, which stops mix-up attacks. Credentials from pre-registration or DCR are now bound to the issuing authorization server and can't be reused if it changes. And DCR requests must carry an application_type so OIDC providers accept localhost redirects.

## Interview
### Walk me through what happens when a client first connects to a protected MCP server.
The client sends its request without a token and gets **401** with `WWW-Authenticate: Bearer resource_metadata="…"` (and ideally `scope="…"`). It fetches the **Protected Resource Metadata** (RFC 9728) — falling back to the path-inserted then root `/.well-known/oauth-protected-resource` if there was no header — and picks an AS from `authorization_servers`. It fetches **AS metadata** via RFC 8414 or OIDC Discovery in the mandated order, checks that `issuer` matches exactly and that `code_challenge_methods_supported` exists. It gets a `client_id` (pre-registered, CIMD, or deprecated DCR), generates PKCE, `state`, and opens `/authorize` with `resource=<canonical URI>` and the selected scopes, recording the expected issuer. On the callback it validates `state` and `iss`, then redeems the code at `/token` with `code_verifier` and `resource`, and retries the MCP request with `Authorization: Bearer`.

### Why does stdio not use OAuth?
The spec says stdio implementations **SHOULD NOT** follow the authorization spec and should retrieve credentials from the environment. A stdio server is a local child process the user launched; it already runs with the user's privileges, so there is no remote resource server to protect and no network boundary for a bearer token to cross. Credentials come from per-server `env` config or a library embedded in the server (which may still run its own browser login to an upstream service). OAuth is designed for remote HTTP servers, where the client must prove to a separate service that the user authorized it.

### What is PKCE protecting against, and why isn't it enough on its own?
PKCE binds the authorization code to the client instance that started the flow: the client keeps a random `code_verifier`, sends only its SHA-256 hash (`S256`) in the authorization request, and must present the verifier to redeem the code. An attacker who intercepts the code — through a malicious app on a localhost port, a log, a referrer — cannot exchange it. It does **not** stop a **mix-up attack**: if a malicious AS tricks the client into sending an honest AS's code to the attacker's token endpoint, the client hands over the verifier too. That is why 2026-07-28 adds RFC 9207 `iss` validation, and why the client must check PKCE support in metadata and refuse otherwise.

### A client gets a 403 with `error="insufficient_scope", scope="files:write"`. What should it do?
Treat the challenged scope as authoritative for this operation, compute the **union** of the scopes it previously requested and `files:write` (otherwise re-authorizing would drop `files:read` and break other tools), run the authorization flow again with that set, and retry the original request. It should cap the retries (a few at most), remember failures so it doesn't loop on a scope the user or AS keeps denying, and treat repeated failure as permanent. A `client_credentials` client acting on its own behalf may instead just abort.

### Gotcha: our server validates the JWT signature and expiry. Is that enough?
No. The token might be perfectly valid — for a *different* resource. MCP servers **MUST** check that the token was issued for them (the `aud` claim or introspection's audience matching the canonical URI), and should pin the expected issuer/tenant, since tokens from another realm of the same AS may share signing keys. Scopes must also be enforced per tool on the server — "the token says `admin`" is not authorization logic. Without the audience check, any token the user ever got from that AS works against you, and a compromised sibling service can replay tokens at you.

### When would you pick CIMD over pre-registration or DCR?
CIMD is the default for the common MCP case: a client (say, an IDE) and a server that have never met. The client hosts one JSON document at a stable HTTPS URL and uses that URL as `client_id`; any AS that advertises `client_id_metadata_document_supported` can verify it, and it is portable across authorization servers. Pre-registration wins when there *is* a relationship — an enterprise app registered with its corporate IdP — and comes first in the priority order. DCR is deprecated: it creates unbounded anonymous registrations and, unless locked down, lets anyone register any client. Keep it only for legacy authorization servers.

## Glossary
- Resource server | 资源服务器 | The OAuth role an MCP server plays: it accepts and validates access tokens on protected requests.
- Authorization server (AS) | 授权服务器 | The service that authenticates the user, obtains consent and issues access tokens.
- Protected Resource Metadata (RFC 9728) | 受保护资源元数据 | A JSON document at `/.well-known/oauth-protected-resource` listing the server's `authorization_servers` and `scopes_supported`.
- Authorization Server Metadata (RFC 8414) | 授权服务器元数据 | The AS's discovery document with `issuer`, endpoints and supported features such as `code_challenge_methods_supported`.
- PKCE (`S256`) | PKCE 授权码证明密钥 | A verifier/challenge pair that makes an intercepted authorization code unusable by anyone but the original client.
- Resource indicator (RFC 8707) | 资源指示符 | The `resource` parameter naming the server's canonical URI so the token is bound to that audience.
- Audience (`aud`) | 受众 | The token claim saying which resource the token was issued for; servers must reject tokens that are not theirs.
- Client ID Metadata Document (CIMD) | 客户端 ID 元数据文档 | A registration method where the `client_id` is an HTTPS URL to the client's own metadata JSON.
- Dynamic Client Registration (DCR) | 动态客户端注册 | RFC 7591 registration via a `registration_endpoint`; deprecated in MCP 2026-07-28.
- Step-up authorization | 递进授权（权限提升） | Re-authorizing with the union of granted and challenged scopes after a `403 insufficient_scope`.

## Notebook
### 1. PKCE by hand
PKCE is just a random secret and its SHA-256 hash. The client sends the **challenge** in the browser redirect (which may leak) and keeps the **verifier** until the back-channel token request.

```python
import base64
import hashlib
import json
import logging
import secrets

logging.getLogger("httpx").setLevel(logging.WARNING)
logging.getLogger("httpx2").setLevel(logging.WARNING)
logging.getLogger("mcp").setLevel(logging.ERROR)


def b64url(raw: bytes) -> str:
    return base64.urlsafe_b64encode(raw).rstrip(b"=").decode()


def make_pkce() -> tuple[str, str]:
    verifier = b64url(secrets.token_bytes(48))              # 64 chars, within the 43..128 allowed
    challenge = b64url(hashlib.sha256(verifier.encode()).digest())
    return verifier, challenge


verifier, challenge = make_pkce()
print("code_verifier :", verifier, f"({len(verifier)} chars, stays on the client)")
print("code_challenge:", challenge, "(goes in the authorization URL)")
print("method        : S256")
# the AS later recomputes the hash from the verifier the client presents:
print("verifies?     :", b64url(hashlib.sha256(verifier.encode()).digest()) == challenge)
```

### 2. A toy authorization server
A real deployment uses Keycloak, Entra ID, Auth0… Here a ~60-line Starlette app plays the AS so you can see every field. It publishes RFC 8414 metadata (with `code_challenge_methods_supported` and `authorization_response_iss_parameter_supported`), auto-approves the user "alice" at `/authorize` (standing in for the login + consent page), enforces exact redirect-URI matching and PKCE at `/token`, and stamps the requested `resource` into the token's `aud`. Tokens are HMAC-signed JWTs — fine for a lesson, **never hand-roll this in production**.

```python
import hmac
import socket
import threading
import time
from urllib.parse import parse_qs, urlencode, urlparse

import uvicorn
from starlette.applications import Starlette
from starlette.responses import JSONResponse, RedirectResponse
from starlette.routing import Route


def free_port() -> int:
    with socket.socket() as s:
        s.bind(("127.0.0.1", 0))
        return s.getsockname()[1]


def serve(app, port):
    server = uvicorn.Server(uvicorn.Config(app, host="127.0.0.1", port=port, log_level="warning"))
    threading.Thread(target=server.run, daemon=True).start()
    while not server.started:
        time.sleep(0.02)
    return server


AS_PORT, MCP_PORT = free_port(), free_port()
ISSUER = f"http://127.0.0.1:{AS_PORT}"
RESOURCE = f"http://127.0.0.1:{MCP_PORT}/mcp"          # the MCP server's canonical URI
SIGNING_KEY = secrets.token_bytes(32)
REDIRECT_URI = "http://127.0.0.1:33418/callback"


def mint_jwt(claims: dict) -> str:
    head = b64url(json.dumps({"alg": "HS256", "typ": "JWT"}).encode())
    body = b64url(json.dumps(claims).encode())
    sig = b64url(hmac.new(SIGNING_KEY, f"{head}.{body}".encode(), hashlib.sha256).digest())
    return f"{head}.{body}.{sig}"


def read_jwt(token: str) -> dict | None:
    """Return the claims if the signature is valid, else None."""
    try:
        head, body, sig = token.split(".")
        good = b64url(hmac.new(SIGNING_KEY, f"{head}.{body}".encode(), hashlib.sha256).digest())
        if not hmac.compare_digest(sig, good):
            return None
        return json.loads(base64.urlsafe_b64decode(body + "=" * (-len(body) % 4)))
    except ValueError:
        return None


CLIENTS = {"notes-cli": {"redirect_uris": [REDIRECT_URI]}}   # pre-registered clients
CODES: dict[str, dict] = {}
REFRESH: dict[str, dict] = {}


async def as_metadata(request):
    return JSONResponse({
        "issuer": ISSUER,
        "authorization_endpoint": f"{ISSUER}/authorize",
        "token_endpoint": f"{ISSUER}/token",
        "response_types_supported": ["code"],
        "grant_types_supported": ["authorization_code", "refresh_token"],
        "code_challenge_methods_supported": ["S256"],
        "token_endpoint_auth_methods_supported": ["none"],
        "scopes_supported": ["notes:read", "notes:write"],
        "authorization_response_iss_parameter_supported": True,
    })


async def authorize(request):
    q = request.query_params
    client = CLIENTS.get(q.get("client_id"))
    if client is None or q.get("redirect_uri") not in client["redirect_uris"]:   # exact match only
        return JSONResponse({"error": "invalid_request", "error_description": "unknown client or redirect_uri"}, 400)
    if q.get("code_challenge_method") != "S256" or not q.get("code_challenge"):
        return JSONResponse({"error": "invalid_request", "error_description": "PKCE S256 required"}, 400)
    # ... a real AS shows a login + consent page here; we auto-approve user "alice" ...
    code = secrets.token_urlsafe(16)
    CODES[code] = {"client_id": q["client_id"], "redirect_uri": q["redirect_uri"], "challenge": q["code_challenge"],
                   "scope": q.get("scope", ""), "resource": q.get("resource"), "sub": "alice"}
    back = {"code": code, "state": q.get("state", ""), "iss": ISSUER}             # RFC 9207 iss
    return RedirectResponse(f"{q['redirect_uri']}?{urlencode(back)}", status_code=302)


def issue_tokens(sub, client_id, scope, resource, ttl=300):
    now = int(time.time())
    access = mint_jwt({"iss": ISSUER, "sub": sub, "aud": resource, "client_id": client_id,
                       "scope": scope, "iat": now, "exp": now + ttl})
    refresh = secrets.token_urlsafe(24)
    REFRESH[refresh] = {"sub": sub, "client_id": client_id, "scope": scope, "resource": resource}
    return {"access_token": access, "token_type": "Bearer", "expires_in": ttl, "refresh_token": refresh, "scope": scope}


async def token(request):
    form = await request.form()
    if form.get("grant_type") == "authorization_code":
        rec = CODES.pop(form.get("code"), None)                                   # codes are single-use
        if rec is None or rec["client_id"] != form.get("client_id") or rec["redirect_uri"] != form.get("redirect_uri"):
            return JSONResponse({"error": "invalid_grant"}, 400)
        if b64url(hashlib.sha256(form.get("code_verifier", "").encode()).digest()) != rec["challenge"]:
            return JSONResponse({"error": "invalid_grant", "error_description": "PKCE verification failed"}, 400)
        if form.get("resource") != rec["resource"]:
            return JSONResponse({"error": "invalid_target"}, 400)
        return JSONResponse(issue_tokens(rec["sub"], rec["client_id"], rec["scope"], rec["resource"]))
    if form.get("grant_type") == "refresh_token":
        rec = REFRESH.pop(form.get("refresh_token"), None)                         # rotation: old one dies
        if rec is None:
            return JSONResponse({"error": "invalid_grant", "error_description": "unknown or reused refresh token"}, 400)
        return JSONResponse(issue_tokens(rec["sub"], rec["client_id"], rec["scope"], rec["resource"]))
    return JSONResponse({"error": "unsupported_grant_type"}, 400)


as_app = Starlette(routes=[Route("/.well-known/oauth-authorization-server", as_metadata),
                           Route("/authorize", authorize),
                           Route("/token", token, methods=["POST"])])
as_server = serve(as_app, AS_PORT)
print("authorization server:", ISSUER)
```

### 3. A protected MCP server with the SDK
The SDK does the resource-server plumbing: given `token_verifier=` and `auth=AuthSettings(...)` it publishes PRM, answers unauthenticated requests with `401` + `resource_metadata`, and — with `validate_token_resource=True` — rejects tokens whose `AccessToken.resource` is not `resource_server_url`. `required_scopes` apply to *every* request, so per-tool scopes need your own check: a small ASGI wrapper reads the 2026-07-28 `Mcp-Method` / `Mcp-Name` headers and answers `403 insufficient_scope` for `delete_note` unless the token has `notes:write`.

```python
from mcp.server import MCPServer
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings


class HmacTokenVerifier:
    """Signature + issuer + expiry. The SDK then compares `resource` (the aud) with resource_server_url."""

    async def verify_token(self, token: str) -> AccessToken | None:
        claims = read_jwt(token)
        if not claims or claims.get("iss") != ISSUER or claims.get("exp", 0) < time.time():
            return None
        return AccessToken(token=token, client_id=claims["client_id"], scopes=claims["scope"].split(),
                           expires_at=claims["exp"], resource=claims["aud"], subject=claims["sub"])


notes_server = MCPServer(
    "notes",
    token_verifier=HmacTokenVerifier(),
    auth=AuthSettings(issuer_url=ISSUER, resource_server_url=RESOURCE,
                      required_scopes=["notes:read"], validate_token_resource=True),
)
NOTES = {"n1": "buy milk", "n2": "renew passport"}


@notes_server.tool()
def list_notes() -> list[str]:
    """List the ids of the user's notes."""
    return sorted(NOTES)


@notes_server.tool()
def delete_note(note_id: str) -> str:
    """Delete one note (needs notes:write)."""
    NOTES.pop(note_id, None)
    return f"deleted {note_id}"


PRM_URL = f"http://127.0.0.1:{MCP_PORT}/.well-known/oauth-protected-resource/mcp"
TOOL_SCOPES = {"delete_note": "notes:write"}
inner_app = notes_server.streamable_http_app()


async def scope_gate(scope, receive, send):
    """Per-tool scope check that emits a spec-shaped 403 challenge."""
    if scope["type"] == "http":
        headers = {k.decode().lower(): v.decode() for k, v in scope["headers"]}
        needed = TOOL_SCOPES.get(headers.get("mcp-name")) if headers.get("mcp-method") == "tools/call" else None
        auth = headers.get("authorization", "")
        if needed and auth.lower().startswith("bearer "):
            claims = read_jwt(auth[7:]) or {}
            if needed not in claims.get("scope", "").split():
                challenge = (f'Bearer error="insufficient_scope", scope="{needed}", '
                             f'resource_metadata="{PRM_URL}", error_description="{needed} required"')
                await send({"type": "http.response.start", "status": 403,
                            "headers": [(b"content-type", b"application/json"),
                                        (b"www-authenticate", challenge.encode())]})
                await send({"type": "http.response.body", "body": b'{"error": "insufficient_scope"}'})
                return
    await inner_app(scope, receive, send)        # lifespan and everything else pass straight through


mcp_server = serve(scope_gate, MCP_PORT)
print("protected MCP server:", RESOURCE)
```

### 5. Steps 2–3 — Protected Resource Metadata, then the AS metadata
Follow the pointer, then build the AS well-known URLs in the order the spec mandates. Two checks the client **must** make: the `issuer` in the document equals the issuer we built the URL from, and PKCE support is advertised.

```python
prm = (await http.get(challenge["resource_metadata"])).json()

def as_metadata_urls(issuer: str) -> list[str]:
    u = urlparse(issuer)
    base, path = f"{u.scheme}://{u.netloc}", u.path.rstrip("/")
    if path:
        return [f"{base}/.well-known/oauth-authorization-server{path}",
                f"{base}/.well-known/openid-configuration{path}",
                f"{base}{path}/.well-known/openid-configuration"]
    return [f"{base}/.well-known/oauth-authorization-server", f"{base}/.well-known/openid-configuration"]
```

### 7. Step 5–6 — authorization request, callback, `state` and `iss`
We play the browser with `httpx` (no redirect following) and read the `Location` header the AS sends back. Scope selection: the 401 had no `scope`, so we take PRM `scopes_supported`. Before using the code we check `state` and apply the RFC 9207 table.

```python
def check_iss(as_meta: dict, recorded_issuer: str, iss: str | None) -> None:
    """The 2026-07-28 Authorization Response Validation table."""
    supported = as_meta.get("authorization_response_iss_parameter_supported") is True
    if iss is not None:
        if iss != recorded_issuer:                 # simple string comparison, no normalisation
            raise ValueError(f"iss mismatch: {iss!r} != {recorded_issuer!r} (possible mix-up attack)")
    elif supported:
        raise ValueError("iss missing although the AS advertises it")


verifier, challenge_s256 = make_pkce()
state = secrets.token_urlsafe(16)
pending = {"verifier": verifier, "state": state, "issuer": asm["issuer"]}      # recorded BEFORE redirecting
scope = challenge.get("scope") or " ".join(prm.get("scopes_supported", []))

auth_url = asm["authorization_endpoint"] + "?" + urlencode({
    "response_type": "code", "client_id": "notes-cli", "redirect_uri": REDIRECT_URI, "state": state,
    "code_challenge": challenge_s256, "code_challenge_method": "S256", "scope": scope, "resource": RESOURCE})
print("authorization URL:\n ", auth_url, "\n")

redirect = await http.get(auth_url)
callback = {k: v[0] for k, v in parse_qs(urlparse(redirect.headers["location"]).query).items()}
print("callback params:", json.dumps(callback, indent=2))

assert callback["state"] == pending["state"], "state mismatch -> discard"
check_iss(asm, pending["issuer"], callback.get("iss"))
print("state and iss OK")
for bad_iss in ["http://evil.example", ISSUER + "/", None]:
    try:
        check_iss(asm, pending["issuer"], bad_iss)
    except ValueError as exc:
        print("rejected:", exc)
```

### 11. Scope challenge and step-up, by hand
Our token only has `notes:read`. Calling `delete_note` gets the runtime **403** with the needed scope. The client re-authorizes with the **union** of old and new scopes and retries.


### 13. Let the SDK do all of it
`mcp.client.auth.OAuthClientProvider` is an `httpx2.Auth` that runs the whole flow on a 401 — PRM discovery with fallbacks, AS metadata with issuer validation, registration, PKCE, `state` + `iss` checks, the token request with `resource` — and the **step-up** on a `403 insufficient_scope`. You supply storage (here: in memory, pre-registered and bound to our issuer) and the two browser hooks. An event hook prints every HTTP exchange.

```python

    def __init__(self):

                                                 token_endpoint_auth_method="none", issuer=ISSUER)

    async def get_tokens(self): return self.tokens
    async def set_tokens(self, tokens): self.tokens = tokens
    async def get_client_info(self): return self.client
    async def set_client_info(self, info): self.client = info


browser = {}
```
