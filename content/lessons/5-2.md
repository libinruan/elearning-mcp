## Summary
A server is only half of an MCP application. The other half is the **host**: the program that connects to servers, shows their tools to a language model, and runs the loop that turns "the model wants to call X" into an actual `tools/call`. This lesson follows the official *Build an MCP client* tutorial in Python. It covers the `Client` lifecycle in an `async with` block, stdio transports, and converting MCP tool definitions to the LLM's tool format. It then goes past the tutorial to a production-shaped **agent loop**: multiple tool rounds until the model stops asking, failed tools passed back as `is_error`, conversation state, timeouts, an iteration guard, and keeping API keys out of your code.

## Lesson
### What a client program does
The official tutorial builds a command-line chatbot that can talk to *any* MCP server. Its "How it works" list is the whole job of a host:

1. The client gets the list of available tools from the server.
2. Your query is sent to the model together with the tool descriptions.
3. The model decides which tools (if any) to use.
4. The client executes the requested tool calls through the server.
5. The results go back to the model.
6. The model writes a natural-language answer.
7. The answer is shown to the user.

MCP standardises steps 1 and 4 (`tools/list` and `tools/call`). Everything else, including which model you use, how you prompt it, how many rounds you allow and what needs user approval, belongs to the host. That is why one server works in Claude Desktop, VS Code and your own 80-line script.

### Setting up: dependencies and secrets
The Python tutorial needs **Python SDK 2.0.0 or higher** and installs three packages: `uv add mcp anthropic python-dotenv`. The model API key lives in a `.env` file (`ANTHROPIC_API_KEY=...`). The tutorial explicitly adds `.env` to `.gitignore`, and `load_dotenv()` loads it at startup. The SDK's `Anthropic()` constructor then reads the key from the environment. Never hard-code a key, never log it, and never pass it to an MCP server, which is a separate trust domain.

### The `Client` and its lifecycle
In SDK 2.x, a single `Client` object is "the single object your program talks to the server through". Listing tools, calling one and reading a resource are all methods on it.

```python
from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="python", args=["weather.py"])   # configuration, not a connection
async with Client(stdio_client(params)) as client:                       # launch + agree a protocol version
    tools = (await client.list_tools()).tools
    result = await client.call_tool("get_forecast", {"latitude": 38.6, "longitude": -90.2})
# leaving the block disconnects and shuts the subprocess down
```

Keep three ideas apart:

- **`StdioServerParameters`** is configuration: `command`, `args`, plus optional `env` and `cwd`. It does not start anything.
- **`stdio_client(params)`** turns it into a **transport** that launches the server as a subprocess and speaks newline-delimited JSON-RPC over its stdin/stdout. `Client` also accepts `StdioServerParameters` directly, a URL string (Streamable HTTP) or an in-process `MCPServer` (handy in tests).
- **`async with Client(...)`** is "the entire connection lifecycle". Entering it starts the transport and agrees on a protocol version. On a 2026-07-28 server that means probing `server/discover`, with a fallback to the legacy `initialize` handshake for older servers. Leaving it disconnects and stops the subprocess. "There is no connect/close pair to call and nothing to clean up afterwards."

The tutorial's server-path helper picks `python` for `.py` and `node` for `.js` and rejects anything else. In your own host, that choice usually comes from a config file such as Claude Desktop's `mcpServers` (lesson 5.5).

### From MCP tools to LLM tools
An MCP `Tool` has `name`, `title`, `description`, `inputSchema`, an optional `outputSchema`, `annotations` and `icons`. Anthropic's Messages API wants `{name, description, input_schema}`. The conversion is one comprehension. The Python SDK exposes snake_case attributes, so it reads `tool.input_schema`:

```python
available_tools = [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                   for t in (await client.list_tools()).tools]
```

Some details matter in production:

- **Pagination.** `tools/list` can return a `nextCursor`. A robust host keeps fetching until there is none.
- **Caching.** In 2026-07-28, list results carry `ttlMs` and `cacheScope`, and servers SHOULD return tools in a **deterministic order**. A stable tool list keeps the LLM's prompt cache warm. The Python `Client` honours `ttlMs` by default.
- **What the model never sees.** `outputSchema`, `annotations` and `icons` are for the host, not the model. Annotations are *hints* from a possibly untrusted server. Use them to decide when to ask the user for confirmation, never as a security guarantee.
- **Names.** Tool names follow the spec's naming rules. With several servers, prefix names with the server (`github__create_issue`) to avoid collisions (lesson 5.4).

Other providers use different shapes for the same data. OpenAI-style APIs want `{"type": "function", "function": {name, description, parameters}}`. MCP is model-agnostic, and the host does the translation.

### The agent loop
The tutorial's `process_query` makes **one** model call, executes any requested tools, and makes **one** follow-up call. That is enough for a demo, but real tasks are multi-step: *find the city code, then fetch its forecast, then compare*. A host therefore loops until the model stops asking for tools:

```python
messages = [{"role": "user", "content": query}]
for _ in range(MAX_ITERATIONS):
    response = llm.messages.create(model=MODEL, max_tokens=16000, tools=available_tools, messages=messages)
    if response.stop_reason != "tool_use":
        break                                                  # end_turn, max_tokens, ...
    messages.append({"role": "assistant", "content": response.content})
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            result = await client.call_tool(block.name, block.input)
            tool_results.append({"type": "tool_result", "tool_use_id": block.id,
                                 "content": text_of(result), "is_error": result.is_error})
    messages.append({"role": "user", "content": tool_results})   # ONE user message with ALL results
```

The rules behind this loop:

- **Append the assistant turn verbatim** (`response.content`, including its `tool_use` blocks) before the results. The API needs to see which call each result answers.
- **Answer every `tool_use` in one user message**, matching ids through `tool_use_id`. The model may request several tools in parallel in one turn.
- **Pass `isError` through as `is_error`.** "A tool that raises does not raise here: it answers with `is_error` set, and passing that flag on lets Claude read the message and try something else." MCP deliberately reports tool execution failures *inside* the result so the model can self-correct.
- **Bound the loop.** A `MAX_ITERATIONS` guard stops a confused model from calling tools forever and burning tokens. When it trips, tell the user instead of failing silently.
- **Read text content carefully.** `result.content` is a list of content blocks (text, image, audio, resource links, embedded resources). The tutorial narrows to `TextContent`. A richer host can forward images as image blocks, or use `structured_content` when it exists.

### Conversation state
"Maintains conversation context" means the `messages` list. Within one query, it grows with every assistant turn and every tool-result turn. Across queries in a chat, the host keeps appending, so "and what about tomorrow?" can be resolved. The MCP connection is **not** where conversation state lives. In 2026-07-28 the protocol is stateless, so each `tools/call` is self-contained. The host owns the history, its truncation or summarisation, and its persistence.

### Error handling, layer by layer
| Layer | What goes wrong | How it surfaces | What the host should do |
| --- | --- | --- | --- |
| Tool execution | bad input, API down, business rule | `CallToolResult` with `isError: true` | Pass it to the model as `is_error` and let it adapt |
| Protocol | unknown method, invalid params, missing capability | JSON-RPC error, raised as `MCPError` | Report it; feed a summary to the model if useful |
| Transport / time | server crashed, hung, slow | `MCPError` such as `Request 'tools/call' timed out`, connection errors | Time out, report, maybe restart the server |
| Model API | rate limit, overload, auth | exceptions from the LLM SDK | Retry with backoff; never retry forever |
| Your chat loop | anything above | an exception in `process_query` | Catch per query so one failure doesn't kill the session |

The tutorial's `chat_loop` wraps each query in `try/except` and prints `Error: ...` while keeping the session alive. It runs `input()` with `asyncio.to_thread` "so the event loop stays free to service the connection while you type". It exits on `quit` or on end-of-file.

**Timeouts.** A hung tool must not hang your host. The tutorial's troubleshooting tip is literal: "`Timeout error`: Consider raising `read_timeout_seconds` on the `Client`." `Client(..., read_timeout_seconds=30)` sets a default for every request, and `call_tool(..., read_timeout_seconds=...)` overrides it per call. Expect the first response to be slow (the tutorial mentions up to 30 seconds), because the server starts, the model thinks and tools run.

### Security in the client
The tutorial's best practices are short: store API keys in `.env`, validate server responses, and be cautious with tool permissions. In practice:

- **Consent before action.** The spec requires hosts to get user consent before invoking tools. Auto-approve read-only tools from trusted servers if you like, but put destructive ones behind a confirmation.
- **Tool results are untrusted input.** A web page or issue body returned by a tool can contain instructions aimed at your model (prompt injection, lesson 6.2). Never let a tool result silently trigger another privileged action.
- **Descriptions and annotations are untrusted** unless the server is trusted.
- **Least privilege for subprocesses.** A stdio server runs with your user's permissions. Pass only the `env` it needs, not your whole environment full of secrets.

### Troubleshooting checklist
`FileNotFoundError` means the server path is wrong, so try an absolute path. On Windows, use forward slashes or escaped backslashes. `Connection refused` means the server isn't running or the URL is wrong. `Tool execution failed` usually means the server is missing environment variables. A timeout means you should raise `read_timeout_seconds` or fix the slow tool.

### What changed from the 2025 SDK
Older tutorials show `ClientSession` plus an `AsyncExitStack`, an explicit `await session.initialize()`, and `stdio_client` yielding read/write streams that you wire up yourself. SDK 2.x collapses this into `Client`. The protocol no longer has an `initialize` handshake in 2026-07-28 (requests carry their version in `_meta`), but `Client` still falls back to it for older servers. You will see both styles in interviews and in existing codebases.

## Key points
- A host's job: list tools → give them to the model → execute the model's tool calls through MCP → return results → repeat → answer.
- `async with Client(...)` is the whole lifecycle. Entering launches/connects and agrees a protocol version, and leaving disconnects and stops the subprocess.
- `StdioServerParameters` is configuration, `stdio_client()` makes the transport, and `Client` opens it. `Client` also takes a URL or an in-process server.
- Convert tools as `{"name", "description", "input_schema": tool.input_schema}`. Keep `outputSchema`, annotations and icons for the host.
- Loop while `stop_reason == "tool_use"`: append the assistant content verbatim, then **one** user message with **all** `tool_result` blocks matched by `tool_use_id`.
- Pass `result.is_error` through as `is_error`. Failing tools return results rather than raising, so the model can recover.
- Always cap iterations, set `read_timeout_seconds`, and catch errors per query so the chat survives.
- The host owns conversation state (the `messages` list). The 2026-07-28 protocol itself is stateless.
- Keep API keys in `.env` (git-ignored), ask consent before tool execution, and treat tool results and descriptions as untrusted.

## Pitches
### How does an MCP client turn an LLM into an agent?
My host connects to each server inside an async context manager and lists its tools. It converts them to the model's tool format and sends them with the user's request. While the model stops with tool use, I append its turn, execute every requested call through MCP, and send back one message of tool results, flagging failures with is_error. The loop ends when the model answers in text or when my iteration cap trips. MCP standardises discovery and invocation, and the loop policy stays mine.

### Why pass tool errors back to the model instead of raising?
Most tool failures are information, not crashes: a wrong ID, a missing permission, a rate limit. MCP reports them inside the result with isError so the model can read the message, fix its arguments or try another tool. In my loop I forward that flag as is_error. Protocol errors and timeouts are different. They mean the plumbing broke, so I surface them to the user or summarise them to the model, and an iteration guard stops endless retries.

### What would you add to the official client tutorial before production?
The tutorial does a single follow-up call, so I'd make it a real loop with a max-iteration guard. I'd add timeouts with read_timeout_seconds, a user-consent gate for destructive tools, pagination and caching of the tool list, and server-prefixed tool names for multiple servers. I'd also treat tool output as untrusted, give subprocess servers a minimal environment, keep keys in git-ignored env files, and add logging and tracing around every model and tool call.

## Interview
### Walk me through the message structure of one tool-use round with the Anthropic API.
The request includes `tools=[{name, description, input_schema}]` and the `messages` history. If the response's `stop_reason` is `"tool_use"`, its `content` holds optional text blocks plus one or more `tool_use` blocks, each with an `id`, `name` and `input`. I append `{"role": "assistant", "content": response.content}` unchanged. Then I call each tool via MCP and append **one** `{"role": "user", "content": [...]}` message holding a `{"type": "tool_result", "tool_use_id": id, "content": text, "is_error": flag}` for **every** `tool_use`. Then I call the API again. Missing a result, splitting results across messages or dropping the assistant turn breaks the pairing and the API rejects the request.

### The official tutorial calls the model at most twice. Why is that insufficient, and what do you change?
Multi-step tasks need chained calls: look up an ID, then fetch details, then act. Each step depends on the previous result, so the number of rounds isn't known in advance. I replace the fixed two calls with a `while stop_reason == "tool_use"` loop bounded by `MAX_ITERATIONS`. On each pass I feed all results back, including errors. When the guard trips, I return a clear "stopped after N steps" message to the user and log the transcript, rather than looping or crashing.

### A tool hangs forever. What happens in your host, and how do you prevent it?
Without a timeout, `await client.call_tool(...)` waits indefinitely and the whole conversation freezes. I set `read_timeout_seconds` on the `Client`, overriding per call for known slow tools. With the Python SDK, a timeout raises `MCPError` ("Request 'tools/call' timed out"). My loop catches it and returns a `tool_result` with `is_error: true` saying the tool timed out, so the model can try something else or tell the user. If the server keeps failing, I restart it or disable it for the session. Long-running work belongs in the Tasks extension (lesson 7.1), not in a blocking call.

### How do you handle conversation state across turns, and where does MCP fit?
The host keeps the `messages` list: user turns, assistant turns with `tool_use`, and tool-result turns. A follow-up question is appended to the same list so the model can resolve references. I trim or summarise old tool results when the context grows, and persist the history if the chat must survive restarts. MCP holds none of this. In 2026-07-28 each request is self-contained, and any cross-call server state is an explicit handle passed as a tool argument.

### What does `async with Client(...)` actually do with a stdio server?
On entry, the transport spawns the subprocess from the `StdioServerParameters` (command, args, env, cwd) and connects to its stdin/stdout. The client then negotiates the protocol. In auto mode it probes `server/discover` and adopts 2026-07-28 when supported, or falls back to the legacy `initialize`/`initialized` handshake for older servers. On exit, it closes the streams. Closing stdin is the stdio shutdown signal, and the process is terminated if it doesn't exit. There's no `close()` to forget, and exceptions inside the block still clean up.

### Gotcha: your agent works with one server but picks the wrong tool after you add a second. Why?
Two servers can expose tools with the same or very similar names (`search`), and the model sees one flat list. Collisions can overwrite each other in a naive name→client map, or the model can confuse descriptions. Fixes: namespace tool names per server (`docs__search`, `tickets__search`) and keep a map back to the right client, sharpen descriptions, and expose fewer tools per request (progressive discovery, lesson 5.4).

## Glossary
- Host | 宿主应用 | The application that owns the LLM, the UI and the agent loop, and creates one MCP client per server.
- Agent loop | 智能体循环 | The host loop that calls the model, executes requested tools through MCP and feeds results back until the model stops asking.
- tool_use block | tool_use 内容块 | A model output block naming a tool, its input and an id that the matching result must reference.
- tool_result block | tool_result 内容块 | A user-message block carrying a tool's output for a given `tool_use_id`, optionally flagged `is_error`.
- is_error | is_error（错误标记） | The flag that tells the model a tool failed; mapped from MCP's `isError`.
- StdioServerParameters | stdio 服务器参数 | Configuration (command, args, env, cwd) describing the subprocess to launch; not a connection.
- Transport | 传输层 | The channel carrying JSON-RPC between client and server, e.g. stdio or Streamable HTTP.
- read_timeout_seconds | 读取超时 | Client-wide or per-call limit on how long to wait for a response before raising a timeout error.
- Iteration guard | 迭代上限保护 | A maximum number of loop rounds that stops runaway tool calling.
- Conversation state | 会话状态 | The host-owned message history that gives the model context across rounds and turns.

## Notebook
### 1. A multi-tool server to drive
Our server exposes three tools that can be chained. `find_city_code` → `get_forecast` → `convert_temperature`. `get_forecast` raises `ToolError` for unknown codes, which is a deliberate, readable failure the model can recover from.

```python
import json
import logging
import os
from types import SimpleNamespace

from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

logging.getLogger("mcp").setLevel(logging.CRITICAL)

CITIES = {"paris": "PAR", "london": "LON", "tokyo": "TYO"}
FORECASTS = {"PAR": {"today": {"celsius": 17, "rain_probability": 80}, "tomorrow": {"celsius": 21, "rain_probability": 10}},
             "LON": {"today": {"celsius": 14, "rain_probability": 95}, "tomorrow": {"celsius": 15, "rain_probability": 60}},
             "TYO": {"today": {"celsius": 26, "rain_probability": 5}, "tomorrow": {"celsius": 24, "rain_probability": 30}}}

weather = MCPServer("weather")


@weather.tool()
def find_city_code(city: str) -> str:
    """Return the 3-letter forecast code for a city name, e.g. 'Paris' -> 'PAR'."""
    try:
        return CITIES[city.strip().lower()]
    except KeyError:
        raise ToolError(f"Unknown city {city!r}. Known: {sorted(CITIES)}")


@weather.tool()
def get_forecast(code: str, day: str = "today") -> dict:
    """Forecast for a city CODE (use find_city_code first) and day ('today' or 'tomorrow')."""
    if code not in FORECASTS:
        raise ToolError(f"Unknown city code {code!r}. Call find_city_code to get a valid code.")
    return {"code": code, "day": day, **FORECASTS[code][day]}


@weather.tool()
def convert_temperature(celsius: float) -> float:
    """Convert Celsius to Fahrenheit."""
    return round(celsius * 9 / 5 + 32, 1)


print("server ready:", weather.name)
```

### 2. Convert MCP tools to the model's tool format
This is the one comprehension from the tutorial, plus pagination. Note what is *not* forwarded: `outputSchema` and annotations stay with the host.

```python
async def list_all_tools(client):
    tools, cursor = [], None
    while True:
        page = await client.list_tools(cursor=cursor)
        tools += page.tools
        cursor = page.next_cursor
        if cursor is None:
            return tools


def to_anthropic(tools):
    return [{"name": t.name, "description": t.description, "input_schema": t.input_schema} for t in tools]


async with Client(weather) as client:
```

### 3. A deterministic "fake LLM" with the same interface as the Anthropic SDK
To run offline, we need something with the Anthropic client's interface: `llm.messages.create(model=..., max_tokens=..., tools=..., messages=...)` returning an object with `stop_reason` and `content` blocks (`type`, `text`, `id`, `name`, `input`). The *policy* reads the conversation (including earlier tool results and `is_error` flags) and decides the next move. That makes the loop's behaviour visible and repeatable. Swapping in the real `anthropic.Anthropic()` later needs **no change to the loop**.

```python
def text_block(text):
    return SimpleNamespace(type="text", text=text)


_ids = iter(range(1, 10_000))
def tool_use(name, args):
    return SimpleNamespace(type="tool_use", id=f"toolu_{next(_ids):03d}", name=name, input=args)


def tool_trace(messages):
    """Pair every tool_use the 'model' made with its tool_result: [{name, input, content, is_error}, ...]."""
    calls = {}
    for m in messages:
        for block in (m["content"] if isinstance(m["content"], list) else []):
            if getattr(block, "type", None) == "tool_use":
                calls[block.id] = {"name": block.name, "input": block.input}
            elif isinstance(block, dict) and block.get("type") == "tool_result":
                calls[block["tool_use_id"]].update(content=block["content"], is_error=block["is_error"])
    return list(calls.values())


class FakeLLM:
    """Mimics anthropic.Anthropic().messages.create with a scripted policy(messages, tool_names) -> blocks."""

    def __init__(self, policy):
        self.policy, self.calls = policy, 0
        self.messages = self                              # so `llm.messages.create(...)` works

    def create(self, *, model, max_tokens, tools, messages):
        self.calls += 1
        blocks = self.policy(messages, {t["name"] for t in tools})
        stop = "tool_use" if any(b.type == "tool_use" for b in blocks) else "end_turn"
        return SimpleNamespace(stop_reason=stop, content=blocks)
```

Now the scripted policy for questions like *"Do I need an umbrella in Paris?"* To show **recovery**, it first *guesses* a code ("PARIS"), sees the `is_error` result, and corrects course. Tool A's output (`PAR`) then feeds tool B.

```python
import re


def umbrella_policy(messages, tool_names):
    question = messages[0]["content"] if isinstance(messages[0]["content"], str) else ""
    city = re.search(r"in (\w+)", question).group(1)
    day = "tomorrow" if "tomorrow" in question else "today"
    trace = tool_trace(messages)
    if not trace:                                                    # round 1: a careless guess
        return [text_block(f"Let me check the forecast for {city}."), tool_use("get_forecast", {"code": city.upper(), "day": day})]
    last = trace[-1]
    if last["is_error"] and last["name"] == "get_forecast":         # recover: read the error, look up the code
        return [text_block("That code was wrong; looking it up."), tool_use("find_city_code", {"city": city})]
    if last["name"] == "find_city_code" and not last["is_error"]:   # chain: A's output becomes B's input
        return [tool_use("get_forecast", {"code": last["content"], "day": day})]
    if last["name"] == "get_forecast":
        f = json.loads(last["content"])
        verdict = "Yes, take an umbrella" if f["rain_probability"] >= 50 else "No umbrella needed"
        return [text_block(f"{verdict}: {f['rain_probability']}% chance of rain in {city} {day}, {f['celsius']}°C.")]
    return [text_block(f"I could not get a forecast: {last['content']}")]


print("policy defined")
```

### 4. The agent loop
This is the standard manual tool-use loop for the Messages API: loop while `stop_reason == "tool_use"`, append the assistant content verbatim, then **one** user message with **all** tool results. It adds an iteration guard and turns transport errors (such as timeouts) into `is_error` results so the model can react.

```python
from mcp.shared.exceptions import MCPError
import mcp_types as types

MODEL = "claude-opus-5-5"


def text_of(result: types.CallToolResult) -> str:
    return "\n".join(b.text for b in result.content if isinstance(b, types.TextContent))


async def run_agent(client, llm, messages, *, max_iterations=6, verbose=True):
    """Run one user turn to completion. Mutates and returns `messages` (the conversation state)."""
    tools = to_anthropic(await list_all_tools(client))
    for step in range(1, max_iterations + 1):
        response = llm.messages.create(model=MODEL, max_tokens=16000, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        for block in response.content:
            if block.type == "text" and verbose:
                print(f"  [{step}] model: {block.text}")
        if response.stop_reason != "tool_use":
            return messages
        tool_results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                result = await client.call_tool(block.name, block.input)
                content, is_error = text_of(result), bool(result.is_error)
            except MCPError as err:                                   # protocol/transport failure, e.g. timeout
                content, is_error = f"MCP error {err.error.code}: {err.error.message}", True
            if verbose:
                flag = "ERROR " if is_error else ""
                print(f"  [{step}] tool  {block.name}({json.dumps(block.input)}) -> {flag}{' '.join(content.split())[:90]}")
            tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": content, "is_error": is_error})
        messages.append({"role": "user", "content": tool_results})
    messages.append({"role": "assistant", "content": [text_block(f"Stopped: reached the {max_iterations}-step limit.")]})
    if verbose:
        print(f"  [guard] stopped after {max_iterations} iterations")
    return messages


def final_text(messages):
    return " ".join(b.text for b in messages[-1]["content"] if getattr(b, "type", None) == "text")


async with Client(weather) as client:
    llm = FakeLLM(umbrella_policy)
    convo = await run_agent(client, llm, [{"role": "user", "content": "Do I need an umbrella in Paris?"}])
    print("\nFINAL:", final_text(convo), f"| model calls: {llm.calls}, messages in history: {len(convo)}")
```

Read the trace. Round 1 fails (`is_error`), round 2 recovers with `find_city_code`, round 3 chains its output `PAR` into `get_forecast`, and round 4 answers. The tutorial's fixed two-call version would have stopped after the failure.

```python
print("...")
```

A follow-up question is appended to the **same** list. That is conversation state across turns. "There" only makes sense because the first question (about Paris) is still in the history. Our scripted policy reads the city from `messages[0]`, while a real model would simply read everything.

```python
def followup_policy(messages, tool_names):
    question = messages[-1]["content"] if isinstance(messages[-1]["content"], str) else None
    if question and "tomorrow" in question:                     # the model resolves "there" from history
        city = re.search(r"in (\w+)", messages[0]["content"]).group(1)
        return [tool_use("find_city_code", {"city": city})]
    last = tool_trace(messages)[-1]
    if last["name"] == "find_city_code":
        return [tool_use("get_forecast", {"code": last["content"], "day": "tomorrow"})]
    f = json.loads(last["content"])
    return [text_block(f"Tomorrow there: {f['rain_probability']}% rain, {f['celsius']}°C.")]


async with Client(weather) as client:
    convo.append({"role": "user", "content": "And tomorrow there?"})
    convo = await run_agent(client, FakeLLM(followup_policy), convo)
    print("FINAL:", final_text(convo), "| history length:", len(convo))
```

### 6. Break it: a model that never stops
A buggy model (or a prompt-injected one) can keep calling tools. The iteration guard is what saves your budget.

```python
def stubborn_policy(messages, tool_names):
    return [tool_use("convert_temperature", {"celsius": len(messages)})]   # always asks for another tool


async with Client(weather) as client:
    llm = FakeLLM(stubborn_policy)
    convo2 = await run_agent(client, llm, [{"role": "user", "content": "Loop forever"}], max_iterations=3)
    print("FINAL:", final_text(convo2), "| model calls:", llm.calls)
```

### 7. The same loop over a real stdio subprocess
Now the server runs as a separate process, as in the tutorial. We use `Client(stdio_client(StdioServerParameters(...)))`, the tutorial's exact form. The server adds a deliberately slow tool. With `read_timeout_seconds=1`, the slow call raises a timeout `MCPError`, the loop turns it into an `is_error` result, and the model falls back to another tool.

```python
import sys
import tempfile
import textwrap
from pathlib import Path

from mcp import StdioServerParameters
from mcp.client.stdio import stdio_client

workdir = Path(tempfile.mkdtemp())
server_file = workdir / "weather_server.py"
server_file.write_text(textwrap.dedent('''
    import time
    from mcp.server import MCPServer
    from mcp.server.mcpserver.exceptions import ToolError

    server = MCPServer("weather-stdio", log_level="CRITICAL")
    CODES = {"paris": "PAR", "london": "LON"}

    @server.tool()
    def find_city_code(city: str) -> str:
        """Return the 3-letter forecast code for a city name."""
        if city.lower() not in CODES:
            raise ToolError(f"Unknown city {city!r}")
        return CODES[city.lower()]

    @server.tool()
    def live_radar(code: str) -> str:
        """High-resolution live radar (slow)."""
        time.sleep(3)
        return f"radar for {code}: heavy rain"

    @server.tool()
    def get_forecast(code: str) -> dict:
        """Forecast for a city CODE."""
        return {"code": code, "rain_probability": {"PAR": 80, "LON": 95}.get(code, 0)}

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))


def radar_policy(messages, tool_names):
    trace = tool_trace(messages)
    if not trace:
        return [tool_use("find_city_code", {"city": "London"})]
    last = trace[-1]
    if last["name"] == "find_city_code":
        return [tool_use("live_radar", {"code": last["content"]})]
    if last["name"] == "live_radar" and last["is_error"]:
        return [text_block("Radar timed out; using the forecast instead."), tool_use("get_forecast", {"code": "LON"})]
    f = json.loads(last["content"])
    return [text_block(f"Yes: {f['rain_probability']}% chance of rain in London (from {last['name']}).")]


params = StdioServerParameters(command=sys.executable, args=[str(server_file)])
async with Client(stdio_client(params), read_timeout_seconds=1.0) as client:
    print("connected over stdio:", client.server_info.name, "| protocol", client.protocol_version)
    print("tools:", [t.name for t in await list_all_tools(client)])
    convo3 = await run_agent(client, FakeLLM(radar_policy), [{"role": "user", "content": "Is it raining in London?"}])
    print("FINAL:", final_text(convo3))
print("subprocess stopped when the async with block exited")
```

### 8. Errors that are *not* tool errors
Calling a tool that doesn't exist or passing invalid arguments still returns a result with `isError: true` in this SDK. An over-long call raises instead. A good host handles all three without crashing the chat.

```python
async with Client(StdioServerParameters(command=sys.executable, args=[str(server_file)])) as client:
    r = await client.call_tool("no_such_tool", {})
    print("unknown tool  -> isError:", r.is_error, "|", text_of(r))
    r = await client.call_tool("find_city_code", {"city": "Atlantis"})
    print("ToolError     -> isError:", r.is_error, "|", text_of(r))
    try:
        await client.call_tool("live_radar", {"code": "PAR"}, read_timeout_seconds=0.5)
    except MCPError as err:
        print("timeout       -> MCPError", err.error.code, err.error.message)
```
