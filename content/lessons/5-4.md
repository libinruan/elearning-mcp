## Summary
The agent loop from lesson 5.2 works beautifully with one server and five tools. Real hosts connect to dozens of servers with hundreds of tools, and two costs explode: the **tool definitions** sent on every model call, and the **intermediate results** that flow back through the model between chained calls. The official client best-practices guide answers with two patterns. **Progressive discovery** controls *when* definitions enter context: a small `search_tools` meta-tool, then inspect, then execute. **Programmatic tool calling** ("code mode") controls *how* tools run: the model writes a script against typed stubs, a sandbox runs it, and only the summary returns. This lesson covers both, plus namespacing, `ttlMs` caching and the prompt-cache trap, and you build a three-server travel host that uses them.

## Lesson
### Why naive multi-server hosts break down
The simplest host does what you built in lesson 5.2 for every server: call `tools/list` on each, concatenate the results, and pass the whole array as `tools` on every model request. The docs are blunt about where this leads: *"when a host has access to dozens of servers exposing hundreds of tools, those definitions alone can consume the majority of the context window before the model has even read the user's message."* Their illustration contrasts ~150,000 tokens of upfront definitions with ~2,000 tokens when only the needed tools are loaded.

Three things go wrong at once:

- **Cost and latency**: definitions are prompt tokens on *every* turn.
- **Quality**: the model must pick the right tool from hundreds of near-duplicates (`contact_update`, `lead_update`, `account_update`…), and selection accuracy drops.
- **Data shuttling**: in a chain such as "read logs → filter → file tickets", every intermediate result passes through the model even when it only needs to be forwarded to the next tool.

The guide's two patterns attack these separately: **progressive discovery** controls *when* tool definitions enter context; **programmatic tool calling** controls *how* tools are invoked. They combine well.

### Aggregating servers: one client each, namespaced names
Before any optimisation, a multi-server host needs correct plumbing. The architecture is unchanged from lesson 1.2: the host creates **one client per server**, and the host — not the servers — decides what flows between them. The docs' travel-planning example shows the payoff: a *Travel* server (flights, hotels), a *Weather* server and a *Calendar/Email* server combine under one `plan-vacation` prompt. The model calls `searchFlights()` and `checkWeather()`, then `bookHotel()`, `createCalendarEvent()` and `sendEmail()`, *"requesting approval from the user where necessary."*

The first problem is **name collisions**. The tools spec says tool-name uniqueness is scoped to a single server:

> **Spec rule.** Clients or proxies that aggregate tools from multiple servers MAY encounter naming collisions (for example, two servers each exposing a `search` tool) and SHOULD implement a disambiguation strategy such as prefixing tool names with a server identifier. The server `name` (from `serverInfo`) is not guaranteed to be unique across servers and SHOULD NOT be relied upon for disambiguation.

So prefix with the host's **own configuration key** (`flights__search`, `hotels__search`), not `serverInfo.name`. Keep the result within the recommended tool-name alphabet — ASCII letters, digits, `_`, `-`, `.`, 1–128 characters — so model APIs accept it, and split the prefix off again to route the call. The guide also recommends **grouping tools by server** when presenting them, so the model can reason about related capabilities.

> **Pitfall.** The Python SDK ships a `ClientSessionGroup` aggregator. Without a `component_name_hook` it refuses duplicate tool names outright, and its hook receives `serverInfo` — exactly the field the spec says not to rely on. Key by your own config name instead.

### Progressive discovery: catalog, inspect, execute
Progressive discovery changes when definitions reach the model, not how the host talks to servers:

- The host still fetches definitions via `tools/list` as normal, but **defers injecting them** into the model's context.
- The host gives the model a lightweight **`search_tools` meta-tool**.
- The host loads full definitions into context **only as needed**.

The guide's reference design has three layers:

| Layer | Meta-tool | Returns |
| --- | --- | --- |
| 1. Catalog | `search_tools({query})` | names + one-line descriptions only |
| 2. Inspect | `get_tool_details({name})` | the full definition (input schema, output schema, docs) of one tool |
| 3. Execute | the tool itself | the real result |

```text
search_tools({query: "update salesforce record"})
  → [{name: "salesforce_updateRecord", description: "Update fields on a Salesforce object"}, …]
get_tool_details({name: "salesforce_updateRecord"})
  → {name, description, inputSchema: {objectType, recordId, data}}
salesforce_updateRecord({...})            # model now knows the exact interface
```

**When to switch.** For a small set of tools, the docs say loading everything is fine. Once definitions take a significant part of the window, switch. Their recommendation: implement a **threshold as a percentage of the context window, for example 1%–5%**. Load definitions, and once the threshold is reached, switch to progressive discovery.

**Search strategies** for the catalog layer:

| Strategy | How | Trade-off |
| --- | --- | --- |
| Keyword | BM25, regex over names and descriptions | simple, effective with descriptive names |
| Embedding | vector similarity over descriptions | handles synonyms and semantics |
| Subagent | a small, fast model picks tools for the task | usually works very well, costs more |
| Hybrid | combine rankings, or pick per query | best of several |

Some providers (the docs name OpenAI and Anthropic) offer **built-in tool search**. Prefer it when available. Build your own when the provider has none or you need specialised retrieval, such as domain ranking or access-control filtering.

**Implementation guidelines** from the guide: offer **multiple detail levels** (name-only, name + description, full schema); **cache definitions host-side** so re-injecting one later needs no new `tools/list` (this cache is separate from what is currently in the model's context); **refresh on `list_changed`** by re-indexing when `notifications/tools/list_changed` arrives; and **group tools by server**.

### Dynamic server management
The same idea applies to whole servers. Instead of connecting every configured server at startup, a host can keep a **registry** of servers with high-level descriptions, **connect only when the model needs one**, and **disconnect** servers that are no longer relevant. The guide's sequence uses model-facing meta-tools such as `search_available_servers("CRM")` → `enable_server("salesforce")`. On enable, the host sends `server/discover` and then `tools/list`, which is the 2026-07-28 flow. An older handshake-era host would send `initialize` here. A general-purpose agent starts with a few always-on servers and grows as needed. Combined with Agent Skills, a skill can declare which servers it needs, and the host connects them only when that skill is invoked.

### Caching: `ttlMs`, `cacheScope` and `list_changed`
New in 2026-07-28: every `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list`, `resources/read` and `server/discover` result with `resultType: "complete"` **MUST** carry `ttlMs` and `cacheScope` (the `CacheableResult` interface, SEP-2549). A 2025-11-25 server had no such fields, so hosts relied on `listChanged` notifications or their own heuristics. The rules a host's definition cache must follow:

- Fresh while `now < t_received + ttlMs`; stale after, so re-fetch on next access. `ttlMs: 0`, an absent field, or a negative value means immediately stale.
- TTL is a **freshness hint, not a polling interval**. Clients SHOULD NOT auto-refetch in the background; any client that does poll MUST use jitter and backoff.
- A relevant **`list_changed` notification invalidates** a cached list immediately, even inside its TTL. In 2026-07-28 the client receives it on a `subscriptions/listen` stream opened with `toolsListChanged: true`.
- `cacheScope: "public"` may be shared across users. `"private"` MUST NOT be shared across authorization contexts, so a different token needs a different cache.
- The cache key is method + result-affecting params. Each paginated page is its own entry.

Related, and also new in this revision: servers **SHOULD return tools in a deterministic order**, precisely so that clients can cache the list and LLM prompt caches keep hitting.

### The prompt-cache trap
Most model providers cache the **prompt prefix, including the `tools` array**. Progressive discovery naturally wants to *add* definitions mid-conversation, and that invalidates the provider cache. The docs warn the miss *"can cost more tokens than the definitions you removed."* Their mitigations:

- **Append** newly discovered definitions after the cache breakpoint rather than re-sorting the `tools` array, **or** route every call through a single stable **`call_tool({name, args})`** meta-tool so the array never changes.
- Treat server disconnection as a **conversation-boundary** operation, not a per-turn one.

### Programmatic tool calling ("code mode")
With direct calling, every invocation is a round trip and *"the full result flows back into the model's context."* In code mode **the model writes code that calls tools**. The code runs in a sandbox, and only the final result returns. The guide's illustration contrasts 100K+ tokens of intermediate results with a ~200-token script and a ~15-token summary.

How it works:

1. **Generate a typed API from MCP schemas.** For each tool the host emits a function from its input schema and, when present, its **`outputSchema`**, which gives precise return types. Without one, use a generic type (the real fix is for the server to provide `outputSchema`). Or, for single-shot calls, a host-brokered `extract(value, ExpectedType)` helper can route to a small model to coerce the value. That costs latency and can hallucinate, so validate the result.
2. **The model writes one script** against those functions, e.g. fetch error logs, deduplicate *inside the sandbox*, file one ticket per unique error, and `console.log` a one-line summary.
3. **The sandbox executes it.** Function calls are intercepted and routed by the **host broker** to the right server as `tools/call`. Data flows between servers without entering the model's context.

```text
┌──────────────────────── MCP Host ────────────────────────┐
│  LLM ──writes code──▶ Sandbox ──function call──▶ MCP Client ──tools/call──▶ Server A
│   ▲                    │  ▲                         │                    └─▶ Server B
│   └──console output────┘  └──────return value───────┘
└──────────────────────────────────────────────────────────┘
```

**Roles.** The *sandbox* has **no direct network access**, and its only exits are the generated stubs. The *host* is the broker: it maps calls to servers, executes them and **holds all credentials**, so generated code never sees a token. The *model* sees only what the sandbox prints or returns.

**Choosing a sandbox.** The guide lists examples, not endorsements: **Deno / `isolated-vm`** (V8 isolates with fine-grained permissions), **Monty** (experimental minimal Python interpreter for AI use, no I/O by default), **pctx** (early-stage TypeScript code-mode library), **Wasmtime** (any language compiled to Wasm, capability-based security). Whatever you choose, the pattern is the same: inject stubs, intercept calls over an in-process or stdio channel so network permission can stay fully denied, and dispatch them as `tools/call`.

### Code mode security and errors
Code mode adds a code-execution surface, and the broker is still the MCP host for spec purposes:

- **Per-call authorization.** Apply the same human-in-the-loop policy to sandbox-originated calls as to direct ones. *Approving the script is not blanket approval for every call it makes.* A host may grant categorical approval ("allow `ticketing_createIssue` for this run"), but the broker must still check each call against that grant.
- **Cross-server data flow.** Results from one server are untrusted input to another, so apply the same input review to brokered calls. *Output truncation alone does not prevent exfiltration.*
- **Network isolation**, **no credential exposure**, **resource limits** (timeouts, memory) and **output filtering** (validate and truncate console output before it reaches the model).

**Errors.** A tool failure arrives as a successful response with `isError: true`, not a transport failure. Generated wrappers should **convert it into a thrown exception** so model code can `try`/`catch`. If an uncaught error ends the script, surface it as the script's result so the model can self-correct. The model is responsible for reporting any partial side effects already committed.

### Combining both patterns
The full design: the model uses discovery meta-tools to find the few tools it needs, loads their schemas, then writes **one** script that calls them all in a single pass. Discovery minimises the token cost of **definitions**, and code mode minimises the token cost of **results**, so the context stays focused on reasoning.

## Key points
- A multi-server host keeps **one client per server** and must **disambiguate tool names**. The spec says prefix with a server identifier, and **not** `serverInfo.name`, which is not guaranteed unique.
- **Progressive discovery** = `tools/list` as usual, but defer injection: a `search_tools` meta-tool, then catalog → inspect (`get_tool_details`) → execute.
- Switch to it with a **threshold of ~1%–5% of the context window**. For a few tools, loading everything is fine.
- Search strategies: **keyword, embedding, subagent, hybrid**. Prefer a provider's built-in tool search when one exists.
- 2026-07-28 list results carry **`ttlMs` + `cacheScope`**. Fresh while `now < t_received + ttlMs`. `list_changed` invalidates immediately. `"private"` caches never cross auth contexts.
- Changing the `tools` array mid-conversation **breaks the provider's prompt cache**. Append after the breakpoint or route through one stable `call_tool` meta-tool. Servers SHOULD return tools in **deterministic order**.
- **Code mode**: the model writes a script against typed stubs generated from input/`outputSchema`, a network-less sandbox runs it, and the host broker dispatches `tools/call` and holds credentials. Only the summary returns.
- Approving a script is **not blanket approval**. The broker authorizes each call, and `isError: true` becomes an exception in generated code.

## Pitches
### How do you scale a host to hundreds of MCP tools?
I stop sending every definition on every turn. Below a threshold of a few percent of the context window I load everything. Above it, I switch to progressive discovery: the model gets a small search_tools meta-tool, inspects the full schema of only the tools it picks, and then calls them. Definitions stay cached host-side, honouring each server's ttlMs and list_changed invalidation. I keep the tools array stable, routing calls through one call_tool meta-tool, so the provider's prompt cache keeps hitting.

### What is code mode and why would you use it?
Code mode, or programmatic tool calling, lets the model write a short script against typed functions generated from the MCP tool schemas, instead of making one tool call per turn. A sandbox with no network runs the script, and every function call goes back through the host, which dispatches the real tools/call and holds the credentials. The big intermediate data, like thousands of log lines, never enters the model's context; only the printed summary does. That means fewer round trips, fewer tokens, and often better results.

### How do you keep code mode safe?
I treat the sandbox as untrusted code execution. It gets no network and no credentials, and runs under timeouts and memory limits in a real isolation runtime like a V8 isolate or Wasm. A filtered Python exec doesn't count. The host broker is still the MCP host, so it applies the same approval policy to every call the script makes. Approving the script doesn't approve the side effects. I also review data crossing between servers and truncate the output before it reaches the model.

## Interview
### Two connected servers both expose a tool called `search`. What do you do?
The spec says tool-name uniqueness is only per server, and aggregating clients SHOULD disambiguate, for example by **prefixing with a server identifier**. I use the host's own configuration key (`flights__search`, `hotels__search`), not `serverInfo.name`, because the spec says that name is not guaranteed unique and SHOULD NOT be used for disambiguation. I keep the prefixed name within the allowed characters (letters, digits, `_`, `-`, `.`) and at most 128 characters, so model APIs accept it. A routing table maps the prefixed name back to *(client, original name)*. I also group tools by server in the catalog so the model sees related capabilities together.

### Walk me through progressive tool discovery. When would you *not* use it?
The host calls `tools/list` as normal but **defers injecting** definitions. The model gets a `search_tools` meta-tool (catalog: names and one-line descriptions), then `get_tool_details` for the full schema of a chosen tool (inspect), then calls it (execute). Retrieval can be keyword, embedding, subagent or hybrid, or the provider's built-in tool search. I would **not** use it when definitions are a small share of the window. The docs suggest switching at a threshold of about 1%–5%. Below that, the extra search round trips cost more than they save, and a model that sees all tools at once can plan better.

### Progressive discovery made our bills go *up*. Why might that happen?
Probably the **provider's prompt cache**. Most providers cache the prompt prefix including the `tools` array. If the host inserts newly discovered definitions, especially re-sorted, every turn changes the prefix and the cache misses. The docs say this miss can cost more than the definitions you removed. Fixes: append new definitions after the cache breakpoint, or keep a fixed `tools` array of meta-tools and execute everything through a stable `call_tool({name, args})`. Also don't disconnect servers mid-conversation; treat that as a conversation-boundary operation. On the server side, deterministic `tools/list` ordering (a 2026-07-28 SHOULD) helps.

### How should a host cache tool lists in 2026-07-28?
Every complete `tools/list` result carries `ttlMs` and `cacheScope`. Record the receive time, and treat the list as fresh while `now < t_received + ttlMs`. When stale, re-fetch **on next access**. TTL is not a polling interval, and any poller MUST add jitter and backoff. `ttlMs` of 0, absent or negative means immediately stale. A `notifications/tools/list_changed`, received on a `subscriptions/listen` stream, invalidates the entry even inside the TTL. `"private"` results may only be reused for the same authorization context. A host may also refresh early, for example after an unexpected "tool not found", and may serve stale data if the re-fetch fails.

### Design a code-mode executor for an agent. What are the components and the security rules?
Three components. The **model** writes a script against typed stubs that the host generated from each tool's input schema and `outputSchema`. The **sandbox** runs it in an isolated runtime (V8 isolate, Wasm, a minimal interpreter) with no network, a timeout and a memory cap. The **host broker** receives each stub call over an in-process or stdio channel, maps it to the right server, sends `tools/call` with credentials the code never sees, and returns the result. Rules: authorize **every** call against the user's grant (approving the script is not blanket approval), treat cross-server data as untrusted, filter and truncate output, and convert `isError: true` into exceptions so scripts can catch them. Return uncaught errors as the result so the model can self-correct.

### Gotcha: "We exec the model's Python with `__builtins__` removed, so it's sandboxed." Agree?
No. Restricting builtins or filtering the AST in the host interpreter is a convenience, not a security boundary. CPython offers many routes back to powerful objects (introspection via dunder attributes, objects you passed in, exceptions and their frames), and nothing limits memory or CPU. The model code also shares the host process, so it shares the credentials. The docs' guidance is a real isolated runtime with no network and only stub channels back to the broker, plus timeouts and memory limits. A toy executor is fine for learning, never for untrusted output in production.

## Glossary
- Progressive discovery | 渐进式（工具）发现 | Deferring tool definitions out of the model's context and loading them on demand through search/inspect meta-tools.
- Meta-tool | 元工具 | A host-provided tool such as `search_tools` or `call_tool` that operates on other tools rather than on the world.
- Tool namespacing | 工具命名空间化 | Prefixing tool names with a server identifier so tools from different servers cannot collide.
- Programmatic tool calling (code mode) | 程序化工具调用（代码模式） | The model writes a script that calls tools through generated stubs; only the script's output returns to context.
- Sandbox | 沙箱 | An isolated runtime with no direct network or credentials that executes model-written code.
- Host broker | 宿主代理（中介） | The host component that intercepts sandbox function calls, authorizes them and dispatches them as `tools/call`.
- `ttlMs` | `ttlMs`（缓存有效期，毫秒） | Server hint for how many milliseconds a cacheable result may be considered fresh.
- `cacheScope` | `cacheScope`（缓存范围） | `"public"` or `"private"`: whether a cached result may be shared across authorization contexts.
- Prompt caching | 提示缓存 | Provider-side reuse of an unchanged prompt prefix (including the `tools` array) to cut cost and latency.
- Dynamic server management | 动态服务器管理 | Connecting servers only when needed and disconnecting them when irrelevant, driven by a registry of server descriptions.

## Notebook
### 1. Three servers, one trip
The travel-planning example from the docs, shrunk to fit a notebook: a **flights** server, a **hotels** server and a **weather** server, all in-process. Two details are deliberate. Both travel servers expose a tool called `search` (tool names are only unique *within* a server), and both report the same `serverInfo.name`, `"travel-api"` (the spec says not to rely on that name to tell servers apart). The flights server also returns a lot of data, which will matter for code mode.

```python
import ast
import asyncio
import hashlib
import json
import logging
import os
import random
import time

from mcp import Client
from mcp.server import MCPServer
from mcp.server.caching import CacheHint
from mcp.server.mcpserver.exceptions import ToolError

logging.getLogger("mcp").setLevel(logging.WARNING)

rng = random.Random(7)
AIRLINES = ["IB", "VY", "UA", "DL", "AA", "BA", "LH", "AF"]
FLIGHTS = [{"id": f"{rng.choice(AIRLINES)}{rng.randint(100, 9999)}", "origin": "NYC", "destination": "BCN",
            "date": "2026-06-15", "depart": f"{rng.randint(6, 22):02d}:{rng.choice(['00', '15', '30', '45'])}",
            "stops": rng.choice([0, 0, 1, 1, 2]), "price": rng.randint(380, 1400),
            "fare_rules": "Non-refundable. Changes allowed for a fee. Seat selection extra."}
           for _ in range(40)]
HOTELS = [{"name": n, "city": "Barcelona", "price": p, "rating": r}
          for n, p, r in [("Casa Gracia", 140, 4.6), ("Hotel Arts", 420, 4.8), ("Generator", 70, 4.1),
                          ("Praktik Rambla", 165, 4.5), ("H10 Metropolitan", 210, 4.4)]]

# One vendor runs both travel servers, so serverInfo.name is the same: "travel-api".
flights = MCPServer("travel-api", cache_hints={"tools/list": CacheHint(ttl_ms=300_000, scope="public")})
hotels = MCPServer("travel-api", cache_hints={"tools/list": CacheHint(ttl_ms=300_000, scope="public")})
weather = MCPServer("weather", cache_hints={"tools/list": CacheHint(ttl_ms=60_000, scope="public")})


@flights.tool()
def search(origin: str, destination: str, date: str) -> list[dict]:
    """Search flights between two airports on a date (YYYY-MM-DD). Returns every matching flight."""
    return [f for f in FLIGHTS if (f["origin"], f["destination"], f["date"]) == (origin, destination, date)]


@hotels.tool(name="search")
def search_hotels(city: str, max_price: int) -> list[dict]:
    """Search hotels in a city with a nightly price at or below max_price (USD)."""
    return [h for h in HOTELS if h["city"] == city and h["price"] <= max_price]


@hotels.tool()
def book(name: str, nights: int) -> str:
    """Book a hotel room for a number of nights. Has side effects: charges the user's card."""
    return f"booked {name} for {nights} nights"


@weather.tool()
def forecast(city: str, date: str) -> str:
    """Daily weather forecast for a city on a date (YYYY-MM-DD)."""
    if city != "Barcelona":
        raise ToolError(f"no forecast data for {city!r}")  # ToolError: the message reaches the client
    return "sunny, 27°C, light sea breeze"


print(len(FLIGHTS), "flights,", len(HOTELS), "hotels; sample flight:", json.dumps(FLIGHTS[0]))
```

### 2. A multi-server host: one client per server, namespaced tools
The host owns one `Client` per server, keyed by **its own configuration name** (`flights`, `hotels`, `weather`), not by `serverInfo.name`. It prefixes every tool with that key (`flights__search`), which keeps names unique across servers and still inside the allowed tool-name characters, and splits the prefix off again to route a call. Clients connect lazily, so a server costs nothing until something needs it (dynamic server management), and `disable()` disconnects it.

The host also keeps its **own tool-definition cache** honouring `ttlMs` (the SDK `Client` has a built-in cache too; we call `list_tools(cache_mode="bypass")` so that every fetch you see here really goes to the server).

```python
SEP = "__"


class Host:
    def __init__(self, registry: dict[str, dict], clock=time.monotonic):
        self.registry = registry          # alias -> {"server": ..., "about": "..."}
        self.clock = clock
        self.clients: dict[str, Client] = {}
        self.owners: dict[str, tuple[asyncio.Task, asyncio.Event]] = {}
        self.cache: dict[str, dict] = {}  # alias -> {"tools", "received", "ttl_ms", "scope"}
        self.list_requests = 0

    async def _own(self, alias: str, ready: asyncio.Event, stop: asyncio.Event) -> None:
        # One long-lived task per connection: it enters and exits the Client in the same task.
        async with Client(self.registry[alias]["server"]) as client:
            self.clients[alias] = client
            ready.set()
            await stop.wait()

    async def enable(self, alias: str) -> Client:
        if alias not in self.clients:
            ready, stop = asyncio.Event(), asyncio.Event()
            task = asyncio.create_task(self._own(alias, ready, stop))
            self.owners[alias] = (task, stop)
            await asyncio.wait([task, asyncio.create_task(ready.wait())], return_when=asyncio.FIRST_COMPLETED)
            if task.done():                # the connection failed before it was ready
                self.owners.pop(alias)
                raise task.exception()
        return self.clients[alias]

    async def disable(self, alias: str) -> None:
        self.cache.pop(alias, None)
        self.clients.pop(alias, None)
        task, stop = self.owners.pop(alias)
        stop.set()
        await task

    async def close(self) -> None:
        for alias in list(self.owners):
            await self.disable(alias)

    async def tools_of(self, alias: str):
        entry = self.cache.get(alias)
        if entry and self.clock() < entry["received"] + entry["ttl_ms"] / 1000:   # now < t_received + ttlMs
            return entry["tools"]
        client = await self.enable(alias)
        result = await client.list_tools(cache_mode="bypass")
        self.list_requests += 1
        self.cache[alias] = {"tools": result.tools, "received": self.clock(),
                             "ttl_ms": max(result.ttl_ms or 0, 0), "scope": result.cache_scope}
        return result.tools

    def on_list_changed(self, alias: str) -> None:
        """notifications/tools/list_changed: stale immediately, even inside the TTL."""
        self.cache.pop(alias, None)

    async def definitions(self, aliases=None) -> list[dict]:
        """Namespaced definitions in the shape a model API expects, grouped by server, stable order."""
        out = []
        for alias in aliases or self.registry:
            for t in await self.tools_of(alias):
                out.append({"name": f"{alias}{SEP}{t.name}", "description": t.description or "",
                            "input_schema": t.input_schema})
        return out

    async def call(self, name: str, arguments: dict):
        alias, sep, tool = name.partition(SEP)
        if not sep or alias not in self.registry:
            raise KeyError(f"unknown tool {name!r}")
        client = await self.enable(alias)
        return await client.call_tool(tool, arguments)


REGISTRY = {
    "flights": {"server": flights, "about": "Flight search across airlines"},
    "hotels": {"server": hotels, "about": "Hotel search and booking"},
    "weather": {"server": weather, "about": "Weather forecasts"},
}
host = Host(REGISTRY)
for d in await host.definitions():
    print(f"{d['name']:<18} {d['description'][:70]}")
print("\nconnected:", sorted(host.clients), "| serverInfo names:",
      [c.server_info.name for c in host.clients.values()])
result = await host.call("hotels__search", {"city": "Barcelona", "max_price": 150})
print("hotels__search ->", result.structured_content)
```

Without the prefix, the host would have two tools named `search` and no way to know which server the model meant. Grouping by server (all `flights__*` together) also helps the model reason about related capabilities.

### 3. What does "load everything" cost?
Every definition you pass in the `tools` array is prompt tokens on **every** model call. We use the rough rule *characters ÷ 4*. Three small servers are cheap, so add a fourth, realistic one: a CRM server with 120 tools, the kind of catalog real SaaS servers ship.

```python
def est_tokens(obj) -> int:
```

### 4. Progressive discovery: catalog → inspect → execute
Instead of 120+ definitions, the model gets three small **meta-tools**. `search_tools` returns names and one-line descriptions (layer 1, catalog), `get_tool_details` returns one full schema (layer 2, inspect), and `call_tool` executes any discovered tool by name (layer 3, execute). Search here is plain keyword scoring; embeddings or a small model would slot into the same function.

```python
META_TOOLS = [
    {"name": "search_tools", "description": "Search all connected MCP tools. Returns names and one-line "
     "descriptions grouped by server. Use detail='names' for just names.",
     "input_schema": {"type": "object", "properties": {"query": {"type": "string"},
                      "detail": {"type": "string", "enum": ["names", "summary"]}}, "required": ["query"]}},
    {"name": "get_tool_details", "description": "Full definition (input schema) of one tool by name.",
     "input_schema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}},
    {"name": "call_tool", "description": "Call a tool found with search_tools, by its full name.",
     "input_schema": {"type": "object", "properties": {"name": {"type": "string"},
                      "arguments": {"type": "object"}}, "required": ["name", "arguments"]}},
]


async def search_tools(query: str, detail: str = "summary", k: int = 5):
    words = {w.strip(".,").lower() for w in query.split()}
    scored = []
    for d in await host.definitions():
        text = (d["name"].replace(SEP, " ").replace("_", " ") + " " + d["description"]).lower()
        score = sum(w in text for w in words)
        if score:
            scored.append((-score, d["name"], d["description"].split(". ")[0]))
    hits = sorted(scored)[:k]
    return [h[1] for h in hits] if detail == "names" else [{"name": n, "description": s} for _, n, s in hits]


async def get_tool_details(name: str):
    return next(d for d in await host.definitions() if d["name"] == name)


async def run_meta_tool(name: str, args: dict):
    if name == "search_tools":
        return await search_tools(**args)
    if name == "get_tool_details":
        return await get_tool_details(**args)
    if name == "call_tool":
        r = await host.call(args["name"], args["arguments"])
        return {"isError": r.is_error, "content": r.structured_content or r.content[0].text}
    raise KeyError(name)


# A scripted "model" that plans a trip using only the three meta-tools.
script = [("search_tools", {"query": "weather forecast city"}),
          ("get_tool_details", {"name": "weather__forecast"}),
          ("call_tool", {"name": "weather__forecast", "arguments": {"city": "Barcelona", "date": "2026-06-15"}})]
context = est_tokens(META_TOOLS)
print(f"meta-tool definitions: ~{context} tokens (vs ~{total} for everything)\n")
for name, args in script:
    out = await run_meta_tool(name, args)
    context += est_tokens(out)
    print(f">>> {name}({json.dumps(args)})\n<<< {json.dumps(out)[:300]}\n")
print(f"context spent on tools after the task: ~{context} tokens ({context / total:.1%} of loading everything)")
```

### 5. Caching: `ttlMs`, `list_changed`, and the prompt-cache trap
Two different caches are in play. The **host-side definition cache** follows the server's `ttlMs` (freshness: `now < t_received + ttlMs`) and is invalidated by `notifications/tools/list_changed`. The **model provider's prompt cache** covers the prefix of the request, including the `tools` array; change that array and the cache misses. We use a fake clock so no one waits five minutes.

```python
class FakeClock:
    def __init__(self):
        self.t = 1000.0

    def __call__(self):
        return self.t


clock = FakeClock()
cached_host = Host({k: REGISTRY[k] for k in ("flights", "weather")}, clock=clock)


async def need_tools(label):
    before = cached_host.list_requests
    await cached_host.definitions()
    hit = cached_host.list_requests == before
    print(f"{label:<46} tools/list sent: {cached_host.list_requests - before}  ({'cache hit' if hit else 'fetched'})")


await need_tools("t=0      first use")
print("          cached:", {a: (e["ttl_ms"], e["scope"]) for a, e in cached_host.cache.items()})
clock.t += 30
await need_tools("t=30s    both fresh")
clock.t += 45
await need_tools("t=75s    weather TTL (60 s) expired")
cached_host.on_list_changed("flights")
await need_tools("list_changed from flights (TTL still fresh)")
await cached_host.close()
```

Now the prompt-cache side. Fingerprint the `tools` array the model sees on each turn under two strategies: injecting discovered definitions into `tools` (re-sorted), versus keeping only the stable meta-tools and routing everything through `call_tool`.

```python
def fingerprint(tools):
    return hashlib.sha256(json.dumps(tools, sort_keys=True).encode()).hexdigest()[:10]


weather_def = await get_tool_details("weather__forecast")
hotel_def = await get_tool_details("hotels__search")
turns_inject = [META_TOOLS, sorted(META_TOOLS + [weather_def], key=lambda d: d["name"]),
                sorted(META_TOOLS + [weather_def, hotel_def], key=lambda d: d["name"])]
turns_stable = [META_TOOLS, META_TOOLS, META_TOOLS]
for i, (a, b) in enumerate(zip(turns_inject, turns_stable), 1):
    print(f"turn {i}: inject+sort tools={fingerprint(a)} | stable call_tool tools={fingerprint(b)}")
print("\nA changed fingerprint means the provider's cached prefix no longer matches -> cache miss.")
print("Fix: append new definitions after the cache breakpoint, or keep the array fixed and use call_tool.")
```

### 6. Code mode: generate a typed API from the schemas
For programmatic tool calling, the host turns each tool's schema into a function signature the model can code against. This short text block is what goes into the prompt instead of the JSON schemas.

```python
PY_TYPES = {"string": "str", "integer": "int", "number": "float", "boolean": "bool", "object": "dict",
            "array": "list"}


def stub_source(d: dict) -> str:
    props, required = d["input_schema"].get("properties", {}), d["input_schema"].get("required", [])
    params = []
    for p, s in props.items():
        t = PY_TYPES.get(s.get("type"), "object")
        params.append(f"{p}: {t}" if p in required else f"{p}: {t} | None = None")
    return f'async def {d["name"]}({", ".join(params)}):\n    """{d["description"]}"""'


travel_defs = await host.definitions(["flights", "hotels", "weather"])
api_text = "\n\n".join(stub_source(d) for d in travel_defs)
print(api_text)
print(f"\n~{est_tokens(api_text)} tokens of API description")
```

### 7. A toy executor and a broker with per-call authorization
The executor runs model-written code with only the generated functions and `print` in scope. Each generated function is a **broker stub**: it checks the run's approval grant, forwards the call to the right server as `tools/call`, and turns `isError: true` into an exception the script can `try`/`except`.

> **This is not a sandbox.** `exec` with a trimmed `__builtins__` and an AST filter is a teaching device; CPython has many escape routes and no memory limit here. A real host runs model code in a separate isolated runtime (a V8 isolate such as Deno or `isolated-vm`, a Wasm runtime such as Wasmtime, a minimal interpreter such as Monty, or a locked-down container/microVM) with **no network**, timeouts and memory limits, and only a message channel back to the broker.

```python
class ScriptToolError(Exception):
    """What a generated stub raises inside the script when the server answers isError: true."""


SAFE_BUILTINS = {n: __builtins__[n] if isinstance(__builtins__, dict) else getattr(__builtins__, n)
                 for n in ["len", "min", "max", "sum", "sorted", "range", "enumerate", "zip", "round",
                           "str", "int", "float", "dict", "list", "set", "any", "all", "Exception"]}


def check_script(code: str) -> None:
    for node in ast.walk(ast.parse(code)):
        if isinstance(node, (ast.Import, ast.ImportFrom, ast.Global, ast.Nonlocal)):
            raise PermissionError(f"line {node.lineno}: imports/globals are not allowed")
        if isinstance(node, ast.Attribute) and node.attr.startswith("_"):
            raise PermissionError(f"line {node.lineno}: private attribute {node.attr!r} is not allowed")
        if isinstance(node, ast.Name) and node.id.startswith("__"):
            raise PermissionError(f"line {node.lineno}: dunder name {node.id!r} is not allowed")


async def run_script(code: str, grant: set[str], timeout: float = 5.0, max_output: int = 1000) -> dict:
    """Run model-written code; return only what it prints (truncated) plus a call log for the host."""
    calls, out = [], []

    def make_stub(name):
        async def stub(**kwargs):
            if name not in grant:                       # per-call authorization, even inside an approved script
                calls.append((name, "DENIED"))
                raise PermissionError(f"{name} is not approved for this run")
            r = await host.call(name, kwargs)
            calls.append((name, "error" if r.is_error else "ok"))
            if r.is_error:
                raise ScriptToolError(r.content[0].text)
            sc = r.structured_content
            return sc["result"] if sc and set(sc) == {"result"} else (sc or r.content[0].text)
        return stub

    try:
        check_script(code)
        env = {"__builtins__": SAFE_BUILTINS, "ToolError": ScriptToolError,
               "print": lambda *a: out.append(" ".join(map(str, a)))}
        env.update({d["name"]: make_stub(d["name"]) for d in travel_defs})
        body = "\n".join("    " + line for line in code.splitlines())
        exec(compile(f"async def _script():\n{body}\n", "<model-code>", "exec"), env)
        await asyncio.wait_for(env["_script"](), timeout)
        status = "ok"
    except Exception as exc:                            # surface uncaught errors so the model can self-correct
        status = f"{type(exc).__name__}: {exc}"
    text = "\n".join(out)
    return {"status": status, "output": text[:max_output] + ("…[truncated]" if len(text) > max_output else ""),
            "calls": calls}


print(await run_script("import os\nprint(os.environ)", grant=set()))
print(await run_script("print(().__class__.__mro__)", grant=set()))
print(await run_script("x = await weather__forecast(city='Paris', date='2026-06-15')", grant={"weather__forecast"}))
print(await run_script('''
try:
    sky = await weather__forecast(city="Paris", date="2026-06-15")
except ToolError as err:
    sky = f"unavailable ({err})"
print("Paris:", sky)
''', grant={"weather__forecast"}))
```

Read the four results: two scripts rejected before running, one uncaught tool error surfaced as the script's result (so the model can self-correct), and one script that handled the `isError` itself with `try`/`except`.

### 8. Direct tool calling vs code mode, side by side
Task: *"Find the cheapest non-stop NYC→BCN flight on 2026-06-15, a hotel under $180, and the weather."* First the direct way: three tool calls, each full result goes back through the model. Then code mode: the model writes one script, the data stays in the executor, one summary line comes back.

```python
TASK_TOOLS = [("flights__search", {"origin": "NYC", "destination": "BCN", "date": "2026-06-15"}),
              ("hotels__search", {"city": "Barcelona", "max_price": 180}),
              ("weather__forecast", {"city": "Barcelona", "date": "2026-06-15"})]

direct_tokens, model_calls = 0, 1                 # the first model call decides to use tools
for name, args in TASK_TOOLS:                     # one tool call per turn, as a cautious model would
    r = await host.call(name, args)
    payload = r.structured_content or r.content[0].text
    direct_tokens += est_tokens(payload)
    model_calls += 1
    print(f"direct: {name:<18} -> ~{est_tokens(payload):>5} tokens into context")
print(f"direct total: {model_calls} model calls, ~{direct_tokens} tokens of tool results in context\n")

MODEL_SCRIPT = '''
flights = await flights__search(origin="NYC", destination="BCN", date="2026-06-15")
nonstop = [f for f in flights if f["stops"] == 0]
best = min(nonstop, key=lambda f: f["price"])
hotels = await hotels__search(city="Barcelona", max_price=180)
hotel = max(hotels, key=lambda h: h["rating"])
sky = await weather__forecast(city="Barcelona", date="2026-06-15")
print(f"{len(flights)} flights checked; cheapest non-stop {best['id']} at {best['depart']} for ${best['price']}; "
      f"best hotel under $180: {hotel['name']} (${hotel['price']}, {hotel['rating']}*); weather: {sky}")
'''
run = await run_script(MODEL_SCRIPT, grant={"flights__search", "hotels__search", "weather__forecast"})
print("code mode broker log:", run["calls"])
print("code mode output    :", run["output"])
print(f"code mode total: 2 model calls, ~{est_tokens(MODEL_SCRIPT) + est_tokens(run['output'])} tokens "
      f"(script + output) in context")
```

Now the security rule from the docs: approving the script is **not** blanket approval. The grant below covers searching but not booking, so the broker refuses the side-effecting call at runtime and the error becomes the script's result.

```python
'''
```
