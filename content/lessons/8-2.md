## Lesson
### Why 2026-07-28 changes production MCP
The 2026-07-28 revision made a remote MCP server "a normal HTTP workload" (the roadmap's words). Every request is self-contained: it carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`, servers MUST NOT rely on earlier requests on the same connection, there is no `initialize` handshake and no `Mcp-Session-Id`, and the standalone GET stream is gone. Server-to-client interactions travel inside results (MRTR), and change notifications flow on a `subscriptions/listen` response stream. In 2025-11-25 a horizontally scaled server needed **sticky sessions** or a shared session store; in 2026-07-28 any replica can answer any request. Expect both models in interviews and in existing codebases.

### Production readiness checklist
**1. Transport and deployment**
- One endpoint, POST only. A modern-only server SHOULD answer GET/DELETE with `405`, ignore `Mcp-Session-Id` and `Last-Event-ID`.
- Put replicas behind a **plain round-robin balancer**, with no affinity. Route or rate-limit on the mirrored headers `Mcp-Method` and `Mcp-Name` (plus `Mcp-Param-*` from `x-mcp-header`) without parsing bodies. Servers MUST reject header/body mismatches with `400` and `-32020`; intermediaries SHOULD only trust mirrored headers when `MCP-Protocol-Version` is a version that requires that validation.
- State that remains must be **explicit and shared**: handles in a database, the MRTR `requestState` key ring shared by every replica (the notebook's section 7), and a shared pub/sub behind `subscriptions/listen` if you serve change notifications from many replicas.
- Proxies: send `X-Accel-Buffering: no` on SSE responses, emit `:` keep-alive comments on long-lived listen streams, and remember that closing a request's SSE stream *is* cancellation on HTTP.
- Validate `Origin` (`403` if invalid) and bind local servers to `127.0.0.1`.

**2. Authentication and authorization**
- A remote server is an **OAuth 2.1 resource server**: `401` with `WWW-Authenticate` → Protected Resource Metadata → authorization server (lesson 6.1).
- Servers **MUST NOT accept tokens not issued for them** (audience), and must not pass client tokens through to downstream APIs. A gateway authenticates to backends with its own credentials, or exchanges tokens (RFC 8693 token exchange is on the roadmap's agent-identity agenda).
- Minimise scopes; step up with a `WWW-Authenticate` `scope="..."` challenge when a privileged tool is first used.
- Enterprise: the **Enterprise-Managed Authorization** extension (`io.modelcontextprotocol/enterprise-managed-authorization`) lets the corporate IdP decide which servers employees may reach — the client exchanges the user's ID token for an **ID-JAG**, then for an access token at the MCP authorization server. Onboarding and revocation happen once, at the IdP.
- Handles are names, not credentials: bind them to the authenticated user.

**3. Secrets**
- Credentials live in the host or gateway, never in the model context or a code-mode sandbox. stdio servers read credentials from the environment.
- Form-mode elicitation MUST NOT collect secrets; use URL mode.
- Keep the `requestState` key ring in a secret manager and rotate it in phases (the Python SDK takes `keys=[new, old]`). Never log tokens; the notebook's test greps the audit log for them.

**4. Rate limiting and quotas**
The tools spec says servers **MUST** rate limit tool invocations. Limit per user or tenant and per tool. At the edge, answer `429` with `Retry-After`. Inside the MCP layer, return a tool execution error that an agent can act on. With several gateway replicas, keep counters in a shared store or the limits multiply.

**5. Observability**
- `_meta` reserves `traceparent`, `tracestate` and `baggage` for **W3C Trace Context / Baggage** (OpenTelemetry has semantic conventions for MCP). Propagate them host → gateway → server so one trace id joins every log. Logging is deprecated as a protocol feature in 2026-07-28: log to stderr for stdio and use OpenTelemetry.
- One **audit record per tool call**: user, tool, outcome, latency, trace id. Distinguish `isError` tool failures from JSON-RPC protocol errors in your metrics.
- `serverInfo` in result `_meta` identifies the server version per response. It is good for debugging, but `clientInfo`/`serverInfo` are self-reported and SHOULD NOT drive security decisions.

**6. Caching**
`server/discover`, the list methods and `resources/read` carry `ttlMs` and `cacheScope`. `public` results may be shared by gateways across users. `private` results MUST NOT be shared across authorization contexts. A list filtered per user is therefore `private` (the notebook's gateway). A `list_changed` notification invalidates a fresh entry, and MRTR retries are never cached. Don't turn TTL into a polling loop; if you must poll, use jitter and backoff. The roadmap plans ETags next.

**7. Versioning and deprecation**
Version negotiation is per request: an unsupported version gets `400` + `-32022` with `data.supported`. Clients that must reach handshake-era servers probe with a modern request and fall back to `initialize` only when the `400` body is not a recognised modern error. Track the deprecated registry. Roots, Sampling and Logging were deprecated in 2026-07-28 (earliest removal: first revision on or after 2027-07-28), as were Dynamic Client Registration (replaced by Client ID Metadata Documents) and the old HTTP+SSE transport. Rename tools by *add → deprecate → remove*, announce changes with `list_changed`, and keep TTLs short around a migration.

**8. Testing**
Unit-test servers in-process (`Client(server)`), contract-test the HTTP surface (the notebook's smoke tests: `401`, `-32020`, `403`, `405`, `-32601`), run agent workflows with a scripted planner (lesson 8.1), and load-test with concurrency. SDK tiers are judged against a conformance suite. Use the Inspector for manual debugging.

**9. Rollout**
Use canaries behind the balancer (statelessness makes them trivial), feature-flag new tools per role, and roll out key rotations in phases. Watch error rate, p95 latency and rate-limit counters, and keep a rollback path that doesn't strand handles or sealed state.

### How to answer an MCP system-design question
Interviewers score structure as much as content. Use six beats and say them out loud: **(1) requirements** — users, scale, latency, the dangerous actions; **(2) architecture** — host, gateway, servers, identity provider; **(3) protocol choices** — transport, primitives, MRTR, caching, extensions; **(4) scaling** — statelessness, caches, hot paths; **(5) security** — authentication, least privilege, injection, audit; **(6) trade-offs** and what you'd do next.

### Worked question A — "Design an enterprise MCP gateway for 5,000 employees and 200 internal tools"
1. **Requirements.** Single sign-on, per-role access, central revocation, audit for compliance, about 200 tools across about 30 teams, p95 overhead under 50 ms, no team able to break another.
2. **Architecture.** Agent hosts (IDE, chat, internal agents) → one **MCP gateway** (stateless replicas behind a load balancer) → team-owned MCP servers. A tool registry (owner, risk tier, schema) feeds the gateway. The corporate IdP issues identities.
3. **Protocol choices.** Streamable HTTP everywhere. Enterprise-Managed Authorization so the IdP decides which servers a user may reach (ID-JAG → access token). The gateway is an OAuth resource server to hosts and a client with its own audience-bound credentials to backends. Namespaced tools. A per-user filtered `tools/list` with `cacheScope: "private"`. MRTR elicitation for high-risk tools.
4. **Scaling.** Gateway replicas are stateless. Cache backend catalogs with `ttlMs` and invalidate on `list_changed`. Pool connections to backends. Rate limits live in a shared store. 200 tools is too many to inject into context, so hosts use progressive discovery (`search_tools`) or the gateway offers it.
5. **Security.** Allowlists per role, re-checked per call. No token passthrough. A W3C trace in `_meta` plus an audit record per call shipped to the SIEM. Risk tiers decide confirmation. Tool descriptions from team servers are reviewed, because annotations are untrusted.
6. **Trade-offs.** A central gateway is a choke point and a blast radius, so make it multi-AZ and keep its logic thin. Per-call re-authorization adds latency, so cache decisions briefly. The alternative is direct host→server connections with IdP policy only, which is simpler but gives weaker audit and rate control.

### Worked question B — "Expose our SaaS product to AI agents via MCP"
1. **Requirements.** Customers' agents (Claude, ChatGPT, IDEs, their own) act on *their* tenant's data. Self-serve onboarding, abuse protection, a stable contract.
2. **Architecture.** A remote MCP server at `https://api.example.com/mcp` in front of the existing public API, deployed like any stateless HTTP service. List it in the MCP Registry.
3. **Protocol choices.** OAuth 2.1 authorization code + PKCE with **Client ID Metadata Documents** (DCR is deprecated). Fine-grained scopes. Tools designed for agents, not 1:1 endpoint wrappers (lesson 4.2): task-level, paginated, truncated, with `outputSchema`. Resources for records. MRTR confirmation for destructive actions. `x-mcp-header` to mirror, say, the region for routing.
4. **Scaling.** Stateless replicas. Handles for multi-step work. `tools/list` is `public` with a long TTL if it's the same for everyone. Per-tenant rate limits and quotas. Tasks extension for long-running exports.
5. **Security.** Audience-bound tokens, no passthrough to internal services, state handles bound to the tenant, output sanitised (tool results flow into someone's model and can carry prompt injection back out), SSRF-safe URL handling, a full audit log.
6. **Trade-offs.** Fewer, richer tools versus API parity. Versioning discipline (add → deprecate → remove) because you cannot upgrade customers' agents. MCP versus a plain REST API: keep both — MCP adds discovery, auth discovery and agent-friendly shapes.

### Worked question C — "Our agent calls 40 tools and is slow and expensive — fix it"
1. **Measure first.** Use traces (`traceparent` per call) to split time into model latency versus tool latency, and tokens into tool definitions versus tool results versus reasoning.
2. **Definitions.** If 40+ schemas take a large share of context, use **progressive discovery**. The client guide suggests switching at a threshold such as 1–5% of the window, via `search_tools` → inspect → execute, or provider-native tool search. Keep the `tools` array stable (or a single `call_tool` meta-tool) so prompt caching keeps hitting.
3. **Results.** Paginate and truncate in servers. Move chains of read → transform → write into **programmatic tool calling** (code mode) in a sandbox, so intermediate data never enters the context. Apply per-call authorization in the broker.
4. **Round trips.** Allow parallel tool calls. Cache `tools/list` per `ttlMs`. Pin the protocol version for known servers to skip the discover probe. Pool HTTP connections.
5. **Model choice.** Route sub-tasks (tool selection, extraction) to a small fast model.
6. **Trade-offs.** Code mode needs a hardened sandbox. Discovery adds a hop and can miss tools. Caching risks staleness, which `list_changed` bounds.

## Key points
- 2026-07-28 MCP is **stateless**: every request carries version and capabilities in `_meta`, so replicas sit behind a **plain round-robin balancer** with no sticky sessions.
- The state that remains must be explicit and shared: **handles** in a database, the **MRTR `requestState` key ring** across replicas, a shared pub/sub for `subscriptions/listen`.
- Gateways route and rate-limit on `Mcp-Method` / `Mcp-Name`. Servers reject header/body mismatches with `400` + `-32020`. GET/DELETE get `405`.
- Remote servers are OAuth resource servers: audience-bound tokens, **no token passthrough**, minimal scopes with step-up. Enterprises add **Enterprise-Managed Authorization** (ID-JAG).
- Propagate **`traceparent` / `tracestate` / `baggage`** in `_meta`, write one audit record per call, and use OpenTelemetry, not the deprecated Logging feature.
- `cacheScope: "private"` results MUST NOT be shared across authorization contexts. A per-user filtered list is private. `list_changed` invalidates.
- Version negotiation is per request (`-32022` with `supported`). Roots, Sampling, Logging and DCR are deprecated in 2026-07-28. Rename tools by add → deprecate → remove.
- Answer design questions in six beats: requirements → architecture → protocol choices → scaling → security → trade-offs.

## Pitches
### MCP vs. function calling vs. agent-to-agent protocols
Function calling is a model API feature: the model asks my code to run a function I declared. MCP standardises where those functions, plus resources and prompts, come from, so any host can use any server across vendors. Agent-to-agent protocols such as A2A address a different boundary: one autonomous agent discovering and delegating a task to another. In practice they compose. An agent uses function calling internally, reaches its tools and data through MCP, and may hand whole tasks to other agents over A2A.

### How does an MCP server scale now that the protocol is stateless?
Since 2026-07-28, every request carries its protocol version and client capabilities in `_meta`, and there is no handshake or session id. So I deploy a remote server like any stateless HTTP service: replicas behind a round-robin load balancer, autoscaling on latency, canaries without sticky sessions. The state that's left is explicit. Handles go in a database, all replicas share the key that seals MRTR request state, and notification fan-out uses shared pub/sub. Caching hints let a gateway answer list requests without touching the servers.

### When would you not use MCP?
When the integration is private to one application and one code path, plain function calling is simpler: no extra process, no protocol surface. I'd also avoid wrapping an existing API one-to-one, because agents need task-level tools, not endpoint mirrors. And for hard real-time or bulk data movement, a direct API or pipeline is better. MCP earns its keep when tools must be reusable across hosts, owned by another team, governed centrally, or offered to customers' agents.

## Interview
### How do MCP, function calling and agent-to-agent protocols like A2A relate?
They sit at different boundaries. **Function calling** is inside one model API: the model emits a structured request to call a function the application declared. **MCP** standardises the boundary between an AI application and external systems: discovery (`tools/list`), invocation (`tools/call`), resources, prompts, transports, authorization and versioning. It is model-agnostic, and the host translates MCP tools into whatever function-calling format its model uses. **Agent-to-agent protocols** (for example A2A, which Google started and later moved to the Linux Foundation) address communication *between* autonomous agents: discovering an agent's capabilities and delegating a whole task, with the remote agent kept opaque. They are complementary, not competitors.

### You're putting an MCP server behind a load balancer. What, if anything, still needs to be shared between replicas?
The protocol state needs nothing shared. Every 2026-07-28 request is self-contained, so round-robin works and there are no sticky sessions or session store. But three things still need care. **Application handles** (drafts, carts, transactions) must live in shared storage keyed by user and handle. The **MRTR `requestState`** is sealed by the server, so every replica must hold the same key ring, or a retry routed to another replica is rejected (the Python SDK's default key is per process). And **`subscriptions/listen`** fan-out needs a shared pub/sub so a change on replica A reaches a listener on replica B. Rate-limit counters need a shared store too.

### What is token passthrough, and why is it forbidden?
Token passthrough is when an MCP server accepts a client's token without checking that it was issued *for this server*, and forwards it to a downstream API. It breaks the audience boundary: tokens issued for other services can be replayed, downstream rate limits and audit see the wrong identity, and a stolen token turns the server into an exfiltration proxy. The rule is that MCP servers **MUST NOT accept tokens that were not explicitly issued for them**. A gateway or proxy authenticates downstream with its own credentials, or obtains a new token for the downstream audience (for example via token exchange). It never forwards the user's token.

### How would you trace one user request from the host, through a gateway, to a backend tool?
Use W3C Trace Context in `_meta`. The host starts a trace and sends `traceparent` (optionally `tracestate` and `baggage`) on each request. The gateway continues the trace with a child span and forwards it to the backend, which does the same. All three log the trace id with their audit records, so one query in the tracing backend shows the whole path and its latency breakdown. One gotcha: the Python SDK already extracts and injects the ambient OpenTelemetry context, so configure a real `TracerProvider` rather than hand-writing span ids. And never put secrets in `baggage`.

### A teammate marks the gateway's `tools/list` response `cacheScope: "public"` with a 10-minute TTL. The list is filtered by the user's role. What's wrong?
`public` means any client, shared gateway or proxy MAY serve the cached response *to any user*. A list filtered per user or role contains user-specific data, so a shared cache could show Ana's restricted list to Ben, or, worse, show an admin's tools to everyone. Per the caching spec, results that vary per user must be `private`, which may be reused only within the same authorization context. Two more points: `cacheScope` is not access control, so the gateway must still re-check permissions on `tools/call`. And a `list_changed` notification should invalidate the entry before the TTL expires.

### When would you advise a team *not* to build an MCP server?
- The integration is used by one application in one code path, so in-process function calling is simpler.
- The job is bulk or streaming data movement, or hard real-time control, where a direct API or data pipeline fits better.
- The plan is to mirror an existing REST API endpoint by endpoint: the effort goes into tool design, not wrapping.
- Nobody can own security: auth, rate limits, audit, and review of tool descriptions.

MCP pays off when tools must work across many hosts and models, be owned and versioned by a different team, be centrally governed (allowlists, audit), or be offered to customers' agents.

## Glossary
- MCP gateway | MCP 网关 | A server that fronts many MCP servers: it authenticates callers, filters and namespaces tools, enforces policy and forwards calls.
- Round-robin load balancing | 轮询负载均衡 | Sending each request to the next replica in turn, which is possible because 2026-07-28 requests are self-contained.
- Token bucket | 令牌桶（限流算法） | A rate-limiting algorithm that allows bursts up to a capacity and refills at a steady rate.
- W3C Trace Context | W3C 链路追踪上下文 | The `traceparent`/`tracestate` format, reserved in MCP `_meta`, that joins spans across services into one trace.
- `cacheScope` | 缓存作用域（`cacheScope`） | `public` results may be shared across users. `private` results only within one authorization context.
- Token passthrough | 令牌透传 | The forbidden anti-pattern of accepting a token not issued for the server and forwarding it downstream.
- Audience validation | 受众校验 | Checking that an access token was issued for this specific resource server before accepting it.
- ID-JAG | 身份断言授权许可（ID-JAG） | The Identity Assertion JWT Authorization Grant an enterprise IdP issues so a client can obtain an MCP access token under central policy.
- Key ring rotation | 密钥环轮换 | Sealing with the newest key while still accepting older keys, so secrets rotate without downtime.
- Canary rollout | 金丝雀发布 | Shifting a small share of traffic to a new version first, and widening only if its metrics stay healthy.

### 2. Two replicas behind a round-robin balancer
A 2026-07-28 server keeps no per-connection state, so a dumb **round-robin** balancer is enough: no sticky sessions, no `Mcp-Session-Id` affinity. The balancer below forwards each POST to the next replica and copies the MCP headers. One client, consecutive calls, different replicas — and nothing breaks.

```python
def round_robin_balancer(upstreams: list[str]) -> Starlette:
    ring, http = itertools.cycle(upstreams), httpx.AsyncClient(trust_env=False)
    hop_by_hop = {"host", "content-length", "connection"}

    async def proxy(request: Request) -> Response:
        upstream = next(ring)
        headers = {k: v for k, v in request.headers.items() if k.lower() not in hop_by_hop}
        r = await http.request(request.method, upstream, content=await request.body(), headers=headers)
        keep = {k: v for k, v in r.headers.items() if k.lower() in ("content-type", "www-authenticate")}
        return Response(r.content, status_code=r.status_code, headers=keep)

    return Starlette(routes=[Route("/mcp", proxy, methods=["POST", "GET", "DELETE"])])

serve(round_robin_balancer(list(KB_REPLICAS.values())), KB_PORT)
```

### 3. The gateway: one front door, policy in the middle
The gateway is itself an MCP server (built on the low-level `Server`, so it can pass backend schemas through unchanged) and an MCP client of each backend. On every request it:

1. **authenticates** the bearer token (SDK `token_verifier` → `401` + `WWW-Authenticate` otherwise);
2. lists only the tools the user's **role allows**, with `cacheScope: "private"` because the list differs per user;
3. re-checks the **allowlist** on `tools/call` and applies a per-user **token-bucket rate limit**;
4. continues the caller's **trace** (`traceparent` in `_meta`) or starts a new one, and sends a child span to the backend;
5. forwards with its **own service token**, never the user's;
6. writes one **structured audit record** (JSON line) per call.

```python
USERS = {   # gateway access tokens -> (user, role); a stand-in for the enterprise IdP
    "tok-ana": ("ana", "support"),
    "tok-ben": ("ben", "sales-admin"),
    "tok-load": ("loadbot", "support"),
}
ROLE_TOOLS = {
    "support": {"kb__search_kb", "crm__lookup_customer"},
    "sales-admin": {"kb__search_kb", "crm__lookup_customer", "crm__update_tier"},
}
RATE = {"default": (5, 5.0), "loadbot": (200, 500.0)}   # (burst capacity, refill tokens per second)
BACKENDS = {"kb": (KB_URL, "svc-gw-kb-1f9c"), "crm": (CRM_URL, "svc-gw-crm-77ab")}
AUDIT_FILE = WORKDIR / "audit.jsonl"
AUDIT: list[dict] = []


class UserTokenVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        if token not in USERS:
            return None
        user, role = USERS[token]
        return AccessToken(token=token, client_id="agent-host", subject=user, scopes=["mcp"],
                           claims={"role": role}, resource=GW_URL)


class TokenBucket:
    def __init__(self, capacity: int, refill_per_s: float):
        self.capacity, self.refill, self.tokens, self.t = capacity, refill_per_s, float(capacity), time.monotonic()

    def take(self) -> float:
        """0.0 if allowed, else seconds until a token is available."""
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.t) * self.refill)
        self.t = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 0.0
        return (1 - self.tokens) / self.refill


BUCKETS: dict[str, TokenBucket] = {}
CATALOG = {"tools": None, "fresh_until": 0.0}


POOLS: dict[str, httpx2.AsyncClient] = {}       # one pooled HTTP client per backend (keep-alive connections)


def backend_client(name: str) -> Client:
    url, service_token = BACKENDS[name]
    if name not in POOLS:                          # created lazily, inside the gateway's event loop
        POOLS[name] = httpx2.AsyncClient(headers={"Authorization": f"Bearer {service_token}"}, trust_env=False,
                                         limits=httpx2.Limits(max_connections=50))
    # mode pins the version: no server/discover probe per call (the gateway already knows its backends).
    # A Client is cheap and stateless here: open one per call; the pooled HTTP client reuses connections.
    return Client(streamable_http_client(url, http_client=POOLS[name]), mode="2026-07-28")


async def backend_catalog() -> dict[str, types.Tool]:
    if CATALOG["tools"] is None or time.monotonic() > CATALOG["fresh_until"]:
        tools, ttl = {}, 3_600_000
        for name in BACKENDS:
            async with backend_client(name) as c:
                listing = await c.list_tools()
            ttl = min(ttl, listing.ttl_ms or 60_000)
            for t in listing.tools:
                tools[f"{name}__{t.name}"] = t.model_copy(update={"name": f"{name}__{t.name}"})
        CATALOG.update(tools=tools, fresh_until=time.monotonic() + ttl / 1000)
    return CATALOG["tools"]


def caller() -> tuple[str, str]:
    token = get_access_token()                      # set by the SDK's bearer-auth middleware
    return token.subject, token.claims["role"]


def child_trace(meta: dict) -> tuple[str, str | None, str]:
    """Continue an incoming W3C traceparent, or start a new trace. Returns (trace_id, parent_span, span)."""
    parts = str(meta.get("traceparent", "")).split("-")
    if len(parts) == 4 and len(parts[1]) == 32 and len(parts[2]) == 16:
        return parts[1], parts[2], secrets.token_hex(8)
    return secrets.token_hex(16), None, secrets.token_hex(8)


def audit(record: dict):
    AUDIT.append(record)
    with AUDIT_FILE.open("a") as f:
        f.write(json.dumps(record) + "\n")


async def gw_list_tools(ctx, params) -> types.ListToolsResult:
    user, role = caller()
    allowed = [t for name, t in (await backend_catalog()).items() if name in ROLE_TOOLS[role]]
    return types.ListToolsResult(tools=allowed, ttl_ms=60_000, cache_scope="private")


async def gw_call_tool(ctx, params) -> types.CallToolResult:
    user, role = caller()
    meta = dict(ctx.meta or {})
    trace_id, parent, span = child_trace(meta)
    record = {"ts": round(time.time(), 3), "user": user, "role": role, "tool": params.name,
              "trace_id": trace_id, "parent_span": parent, "span": span}
    started = time.perf_counter()

    def finish(outcome: str, result: types.CallToolResult) -> types.CallToolResult:
        record.update(outcome=outcome, ms=round((time.perf_counter() - started) * 1000, 1))
        audit(record)
        return result

    catalog = await backend_catalog()
    if params.name not in catalog:
        record.update(outcome="unknown_tool", ms=0.0)
        audit(record)
        raise MCPError(types.INVALID_PARAMS, f"Unknown tool: {params.name}")      # protocol error, per spec
    if params.name not in ROLE_TOOLS[role]:
        return finish("denied", types.CallToolResult(is_error=True, content=[types.TextContent(
            type="text", text=f"Role '{role}' may not call {params.name}.")]))
    wait = BUCKETS.setdefault(user, TokenBucket(*RATE.get(user, RATE["default"]))).take()
    if wait:
        return finish("rate_limited", types.CallToolResult(is_error=True, content=[types.TextContent(
            type="text", text=f"Rate limit exceeded; retry in {wait:.2f}s.")]))
    backend, _, tool = params.name.partition("__")
    # NOTE: the SDK client also injects the *ambient OpenTelemetry context* into outgoing _meta. When the caller
    # sent a traceparent, the SDK server middleware made it ambient, so that value wins over ours (section 4).
    forward_meta = {"traceparent": f"00-{trace_id}-{span}-01", "com.example.gateway/user": user}
    for key in ("tracestate", "baggage"):              # propagate the rest of the W3C context untouched
        if key in meta:
            forward_meta[key] = meta[key]
    async with backend_client(backend) as c:
        result = await c.call_tool(tool, params.arguments or {}, meta=forward_meta)
    record["backend"] = backend
    if isinstance(result.structured_content, dict) and "replica" in result.structured_content:
        record["replica"] = result.structured_content["replica"]
    return finish("tool_error" if result.is_error else "ok", types.CallToolResult(
        content=result.content, structured_content=result.structured_content, is_error=result.is_error))


gateway = Server("mcp-gateway", version="1.4.0", on_list_tools=gw_list_tools, on_call_tool=gw_call_tool)
serve(gateway.streamable_http_app(
    auth=AuthSettings(issuer_url="https://idp.example.com", resource_server_url=GW_URL,
                      validate_token_resource=True, required_scopes=["mcp"]),
    token_verifier=UserTokenVerifier()), GW_PORT)
print("gateway up at", GW_URL)
```

```python
    print(" ", seen)
```

Read the two `traceparent` values the CRM saw. Ben's request carries the gateway's **child span** — the value our gateway put in `_meta`. Ana's carries her host's **original span id**, not the gateway's. Why? The Python SDK has OpenTelemetry built in: its server middleware *extracts* `traceparent` from incoming `_meta` into the ambient context, and its client *injects* the ambient context into outgoing `_meta`, overwriting what you passed. With only the OTel API installed (as here) the tracer is a no-op, so the injected span is the caller's. In production you install the OTel SDK with a `TracerProvider`: then the SDK creates real `SERVER` and `CLIENT` spans and this propagation is exactly what you want. Either way the **trace id** is preserved end to end, and that is what joins the logs.

### 6. Load test: statelessness under concurrency
Two independent agent hosts fire 40 concurrent calls each through the gateway. Because no request depends on a previous one, the balancer spreads them across both kb replicas — and **each client is served by both replicas**. We also compute latency percentiles, the shape of the numbers you'd put on a dashboard. (All eight servers share one Python process here, so the absolute numbers say nothing about real capacity; the distribution and the zero error count are the point.)

```python
LOAD_RESULTS: list[dict] = []


async def agent_host(host_id: str, n_calls: int):
    async with user_client("tok-load") as c:
        async def one(i):
            t0 = time.perf_counter()
```

### 7. The one piece of shared state: MRTR keys across replicas
Statelessness has a catch. `reindex` returns an `InputRequiredResult`; the retry carries a `requestState` that the SDK **seals with a key**. By default each process generates its own key (`RequestStateSecurity.ephemeral()`), so when the round-robin balancer sends the retry to the *other* replica, it cannot open the state. The fix is configuration, not stickiness: give every replica the same key ring.

```python
async def operator_says_yes(ctx, params):
    return types.ElicitResult(action="accept", content={"ok": True})


async def try_reindex(url: str) -> str:
    async with httpx2.AsyncClient(headers={"Authorization": "Bearer svc-gw-kb-1f9c"}, trust_env=False) as http:
        async with Client(streamable_http_client(url, http_client=http),
                          elicitation_callback=operator_says_yes, mode="2026-07-28") as kb:
            try:
                r = await kb.call_tool("reindex", {})
                return r.content[0].text
            except MCPError as exc:
                return f"MCPError {exc.code}: {exc.message}"


print("per-process keys :", await try_reindex(KB_URL))

SHARED_KEYS = [secrets.token_bytes(32)]           # in production: from a secret manager, rotated as a ring
shared = [serve(make_kb(n, request_state_keys=SHARED_KEYS).streamable_http_app(), free_port())
          for n in ("kb-c", "kb-d")]
KB2_PORT = free_port()
```
