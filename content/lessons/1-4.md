## Summary
Three terms get mixed up in almost every agent conversation: **function calling** (also called tool use), **MCP** and **Agent Skills**. They are not competitors — they answer three different questions. Function calling answers *“how does a model ask my code to do something?”* MCP answers *“where do the tools and data come from, and how does any app connect to them?”* Skills answer *“how does the agent know the right procedure for this job?”* This lesson compares them side by side with one analogy (a new employee: hands, badge-and-sockets, playbook), shows how they stack in a single request, and builds all three around the same toy task in the notebook.

## Lesson
### Three questions, three answers
When someone says “we gave the agent a tool”, they could mean three different things. Separate them by the question each one answers:

| Question | Answer | One-liner |
| --- | --- | --- |
| How does the model *ask* for an action? | **Function calling / tool use** | A model-API feature: you describe functions with a JSON Schema, the model replies with a structured call, **your code** runs it. |
| Where do actions and data *come from*, and how does any AI app plug into them? | **MCP** | An open protocol: servers expose tools, resources and prompts; any MCP host discovers and calls them at runtime. |
| How does the agent know *how to do the job well*? | **Agent Skills** | An open format for packaged know-how: a folder with a `SKILL.md` (instructions) plus optional scripts, references and assets, loaded only when relevant. |

A useful slogan: **functions are the hands, MCP is the plug, skills are the playbook.**

### The analogy: a new employee's first day
Imagine hiring a capable new employee (the model inside your agent).

- **Function calling = the employee's ability to act by filling in a request form.** The employee can't touch the systems directly; they fill in a form (“refund order #123, amount 40 €”) and someone executes it. The form's fields are the JSON Schema, the executor is your host code. Without forms, the employee can only talk.
- **MCP = the company's standard badge-and-socket system.** Every department — CRM, payroll, the wiki — exposes its services through the *same* kind of socket, so any employee (or any contractor from another firm: Claude, ChatGPT, VS Code, your own agent) can plug in and see what that department offers, without custom wiring per department. MCP decides *what forms exist and where they're sent*.
- **Skills = the onboarding binder of standard operating procedures.** “How to close a support ticket”, “how to run the quarterly expense review”: step-by-step know-how, checklists and templates. The binder's table of contents is always on the desk (cheap); a chapter is opened only when that task comes up; appendices are pulled only if a step needs them.

The three are useless alone in different ways: the binder without sockets describes work nobody can carry out; sockets without the binder give access but no judgement about procedure; and without the request form the employee can't act at all.

> A second way to remember it — the kitchen. **Function** = pressing a specific appliance button (“oven, 200 °C”). **MCP** = the standard outlet and delivery dock any appliance or supplier plugs into. **Skill** = the recipe card that says which buttons to press, in what order, and why.

### Function calling (tool use): the model-API mechanism
Function calling is a feature of each model provider's API. In the Claude Messages API you pass `tools=[{"name", "description", "input_schema"}]`; when the model wants an action it stops with `stop_reason: "tool_use"` and returns a `tool_use` block with arguments; your code executes it and sends back a `tool_result`. Key properties:

- **Defined in your application.** The function and its schema live in your code; nothing is discoverable by anyone else.
- **Full definitions in every request.** Each tool's name, description and schema is part of the prompt every time — more tools, more tokens.
- **Provider-shaped.** Every vendor's API has its own (similar) format for tool definitions and calls.
- **It never executes anything by itself.** The model only *requests*; your host decides and runs.

### MCP: the connectivity standard
MCP sits one layer out. It doesn't replace function calling — it **feeds** it. A host connects to MCP servers, calls `tools/list`, converts each MCP tool (name, description, `inputSchema`) into the model provider's tool format, and when the model emits a tool call, forwards it as `tools/call` to the right server. What MCP adds on top of plain functions:

- **Location independence and reuse** — the tool lives in a separate process, local (stdio) or remote (Streamable HTTP), written once and usable by any MCP host (lessons 1.1, 2.3).
- **Runtime discovery** — hosts learn what exists at runtime instead of hard-coding it (`server/discover`, `tools/list`).
- **More than actions** — resources (data the *app* attaches) and prompts (workflows the *user* invokes) alongside model-controlled tools (module 3).
- **Production plumbing** — authorization, caching hints, elicitation, versioning and security rules (modules 2, 5 and 6).

From the model's point of view an MCP tool looks *exactly* like any other function definition; the notebook proves this by comparing the two side by side.

### Agent Skills: packaged procedural knowledge
The [Agent Skills specification](https://agentskills.io/specification) defines a skill as a **directory containing a `SKILL.md` file** with YAML frontmatter and Markdown instructions, plus optional `scripts/` (executable code), `references/` (documentation) and `assets/` (templates, resources). The frontmatter requires:

- `name` — 1–64 characters, lowercase letters, digits and hyphens, not starting or ending with a hyphen;
- `description` — 1–1024 characters, saying what the skill does **and when to use it**.

The defining idea is **progressive disclosure**, in three levels:

| Level | What is loaded | When | Typical cost |
| --- | --- | --- | --- |
| 1. Metadata | `name` + `description` of every installed skill | At startup | ~100 tokens per skill |
| 2. Instructions | The full `SKILL.md` body | When the skill is activated | < 5,000 tokens recommended |
| 3. Resources | Files in `scripts/`, `references/`, `assets/` | Only when a step needs them | As needed |

So an agent can have dozens of skills “installed” for the price of their descriptions. The spec also recommends keeping `SKILL.md` under 500 lines and moving detail into reference files. A skill contains **no new capability by itself**: its scripts run through whatever execution tools the agent already has, and its instructions typically tell the agent which tools — often MCP tools — to call in which order.

The MCP docs use skills too: the *Build with Agent Skills* page ships `build-mcp-server`, `build-mcp-app` and `build-mcpb` skills that guide a coding agent through designing an MCP server.

### Side by side
| | Function calling | MCP | Agent Skills |
| --- | --- | --- | --- |
| **What it is** | A model-API feature | An open protocol (JSON-RPC) | An open file format (folder + `SKILL.md`) |
| **Answers** | How the model requests an action | Where tools/data live and how apps connect | How to do a task well |
| **Unit** | One function definition | A server with tools, resources, prompts | A skill directory |
| **Where code runs** | In your host process | In the server process (local or remote) | Scripts run via the agent's own tools; instructions run “in the model's head” |
| **What the model sees** | Full schema every request | Tool list discovered at runtime, then given as function definitions | Metadata always; body on activation; files on demand |
| **Reuse** | One app | Any MCP host | Any agent that supports the format |
| **Typical author** | The app developer | The team that owns the system | Domain experts, ops, the team that owns the workflow |
| **Best for** | A few app-specific actions | Shared, governed access to systems and data | Repeatable multi-step procedures, conventions, checklists |
| **Main risk** | Bugs in your own code | Untrusted servers, over-scoped tokens, injected tool results | Instructions or scripts from an untrusted source steering the agent |

### How they stack in one request
Take “review last week's expense reports and flag violations”:

```text
User ──► Host/agent loop
           │ system prompt: skill catalog (name + description of each skill)   ← Skills level 1
           │ tools: MCP tools from the finance server, as function definitions ← MCP feeds function calling
           ▼
         Model: "this matches skill `expense-review`" ──► host loads SKILL.md  ← Skills level 2
         Model: follows step 2 → tool_use list_reports(week=41)               ← function calling
           host ──► tools/call list_reports on finance MCP server              ← MCP
         Model: step 3 needs the policy table ──► host reads references/policy.md ← Skills level 3
         Model: tool_use flag_report(id=…, reason=…) ──► tools/call …          ← function calling + MCP
         Model: final summary
```

They also meet in the protocol itself: the official **Skills extension** (`io.modelcontextprotocol/skills`, lesson 7.3) lets an MCP server *serve* its skills, so the know-how ships with the service it describes. And **prompts** — MCP's user-invoked templates — overlap with skills in spirit, but a prompt is a single parameterised message the user picks, while a skill is a whole folder of procedure the agent can pick itself and load in stages.

### Choosing in practice
- A handful of actions only your app needs → **plain function calling**.
- Several apps, teams or vendors need the same system, or it needs its own auth, deployment and security boundary → **an MCP server**.
- The agent *has* the tools but keeps doing the job wrong, skipping steps, or needs company conventions → **a skill**.
- A team owns a system *and* the right way to use it → **an MCP server that also serves skills**.

> **Pitfall.** Don't turn every procedure into a giant “workflow tool”, and don't paste every procedure into the system prompt. Procedures that need judgement belong in skills (loaded on demand); capabilities with side effects belong in tools behind consent gates.

## Key points
- **Function calling** = a model-API feature: schema in, structured call out, *your code* executes. It defines how a model requests an action.
- **MCP** = an open protocol for where tools, resources and prompts live and how any host discovers and calls them. MCP tools reach the model *through* function calling.
- **Agent Skills** = an open format for procedural know-how: a directory with `SKILL.md` (frontmatter `name` + `description`) and optional `scripts/`, `references/`, `assets/`.
- Skills use **progressive disclosure**: metadata (~100 tokens) at startup, the body (< 5,000 tokens recommended) on activation, resources only when needed.
- Analogy: **hands (functions), badge-and-sockets (MCP), onboarding binder (skills)**.
- They are complementary: a skill tells the agent *which* MCP tools to call and in what order; MCP supplies them; function calling is how each call is expressed.
- MCP's **Skills extension** (`io.modelcontextprotocol/skills`) lets servers distribute skills alongside their tools.
- Choose by need: app-local actions → functions; shared governed access → MCP; repeatable procedure and judgement → skills.

## Pitches
### MCP vs. Skills vs. function calling in 30 seconds
They solve three different problems and stack together. Function calling is the model API mechanism: I describe a function with a JSON schema, the model asks for it, my code runs it. MCP is the connectivity standard: tools, data and prompts live in servers any host can discover and call, instead of being hard-wired into one app. Skills are packaged know-how — a SKILL.md with instructions and files the agent loads only when a task needs it. Hands, plugs and a playbook.

### When would you write a skill instead of an MCP server?
I write an MCP server when the agent is missing a capability — it needs to reach a system, with its own auth and security boundary, and several apps should share it. I write a skill when the capability already exists but the agent uses it badly: it skips steps, ignores our conventions or needs a checklist. A skill is cheap to add because only its name and description sit in context until it is needed. Often the best answer is both: a server for the actions, a skill for the procedure.

### Isn't MCP just function calling with extra steps?
No — MCP feeds function calling rather than replacing it. Function calling is how one model inside one app requests an action that app defined. MCP standardises where those actions come from: they live in separate servers, are discovered at runtime, carry auth and versioning, and work in any host. It also adds things function calling has no notion of, like resources the app attaches and prompts the user invokes. To the model, an MCP tool looks exactly like any other function.

## Interview
### Compare function calling, MCP and Agent Skills. How do they relate?
They sit at different layers. **Function calling** is the model-API contract: the request carries tool definitions (name, description, JSON Schema); the model returns a structured call; the application executes it. **MCP** is an integration protocol: servers expose tools, resources and prompts; a host discovers them at runtime and converts MCP tools into the provider's function definitions, then routes calls back with `tools/call`. **Agent Skills** are a content format: a `SKILL.md` with frontmatter and instructions, plus optional scripts, references and assets, loaded by progressive disclosure. In one agent: the skill says *what to do and in what order*, MCP supplies *the tools to do it*, and function calling is *how each call is expressed*.

### We have a 12-step incident runbook that uses five tools we already expose over MCP. The agent keeps skipping steps. What do you build?
A **skill**, not another server. The capability exists; what's missing is procedure. I'd write `incident-response/SKILL.md` with a description saying when it applies, numbered steps naming the MCP tools to call, decision points, and a final checklist; long material (escalation matrix, past postmortems) goes in `references/` so it loads only when a step needs it. If the runbook belongs to the team that owns those tools, I'd ship it from their MCP server through the Skills extension so it stays versioned with the tools. I would *not* collapse the 12 steps into one opaque “run_incident” tool, because the steps need judgement and human checkpoints.

### Do skills make MCP unnecessary?
No. A skill has no new capability of its own: its instructions steer the model, and its scripts only run if the agent already has an execution tool such as a shell or code sandbox. Reaching a CRM with OAuth, tenant isolation and audit logging, or offering the same capability to many hosts, is exactly what MCP standardises. Conversely, MCP alone gives access without procedure. They're complementary — which is why MCP has an official Skills extension to serve skills from servers.

### Compare the context-window cost of the three.
Plain function definitions and MCP tools both end up as full schemas in every model request, so cost grows with the number of tools — dozens of servers can mean thousands of tokens before the user says anything. Hosts mitigate that with progressive tool discovery or code mode (lesson 5.4) and benefit from deterministic `tools/list` order for prompt caching. Skills are designed for this: only `name` + `description` (~100 tokens each) are loaded up front, the body when activated, files on demand. That's why procedural detail belongs in skills, not in tool descriptions or the system prompt.

### How do the security risks differ?
**Function calling**: the code is yours, so the risk is your own bugs and what you let the model trigger without approval. **MCP**: servers may be third-party or remote, so tool descriptions and results are untrusted input (prompt injection, tool poisoning, rug pulls), tokens must be audience-bound and least-privilege, and local servers run with your permissions (module 6). **Skills**: a skill is instructions plus possibly executable scripts, so a malicious or tampered skill can steer the agent or run code — install only from trusted sources, review scripts, pin versions, and when skills come over MCP verify integrity digests and get user approval before loading (lesson 7.3).

### Where does an MCP prompt fit compared with a skill?
Both package reusable intent, but they differ in who triggers them and how much they carry. An MCP **prompt** is user-controlled: a single parameterised message template the user picks (often a slash command) via `prompts/get`. A **skill** is usually model-selected from its description, can be activated by the user too, and is a whole directory loaded in stages — instructions, then scripts and references as needed. Use a prompt for a one-shot template a person invokes; use a skill for a multi-step procedure the agent should recognise and follow.

## Glossary
- Function calling (tool use) | 函数调用（工具调用） | A model-API feature where the model returns a structured request to call a function the application described with a JSON Schema.
- Tool definition | 工具定义 | The name, description and input JSON Schema that tell a model what a function does and how to call it.
- Agent Skill | 智能体技能 | A packaged unit of procedural know-how: a directory with a `SKILL.md` and optional scripts, references and assets.
- SKILL.md | SKILL.md（技能说明文件） | The required file of a skill: YAML frontmatter (`name`, `description`) followed by Markdown instructions.
- Frontmatter | 前置元数据 | The YAML block at the top of `SKILL.md` holding the skill's metadata.
- Progressive disclosure | 渐进式披露 | Loading information in stages — metadata first, full instructions on activation, resource files only when needed — to save context.
- Context window | 上下文窗口 | The maximum amount of text (tokens) a model can consider in one request, shared by instructions, tools and conversation.
- Skills extension | 技能扩展 | The official MCP extension `io.modelcontextprotocol/skills` that lets servers expose skills for clients to discover and read.
- Runbook | 运行手册 | A step-by-step operational procedure — a typical candidate for a skill.

## Notebook
### 1. One task, three layers
We'll build the same small job three ways — *“check an expense against company policy”* — so the differences are concrete. First, the **function calling** version: a Python function plus the tool definition you would send in a Claude `tools=[...]` list. Everything lives in this notebook, which stands in for “your app”.

```python
import json

POLICY = {"meals": 60, "hotel": 220, "taxi": 80}          # max EUR per item


def check_expense(category: str, amount: float) -> dict:
    """The business logic: is one expense within policy?"""
    limit = POLICY.get(category)
    if limit is None:
        return {"ok": False, "reason": f"unknown category {category!r}"}
    return {"ok": amount <= limit, "limit": limit, "over_by": max(0, amount - limit)}


# Function calling: YOU write the definition the model sees, by hand, inside your app.
FUNCTION_TOOL = {
    "name": "check_expense",
    "description": "Check one expense against company policy. Returns ok, the limit and how much it is over.",
    "input_schema": {
        "type": "object",
        "properties": {"category": {"type": "string", "enum": sorted(POLICY)},
                       "amount": {"type": "number", "description": "Amount in EUR"}},
        "required": ["category", "amount"],
    },
}

# What the model sends back when it wants the action (shape of a Claude `tool_use` block):
tool_use = {"type": "tool_use", "id": "toolu_01", "name": "check_expense",
            "input": {"category": "hotel", "amount": 260}}

# Your code executes it locally and returns a `tool_result` block:
result = check_expense(**tool_use["input"])
print(json.dumps({"type": "tool_result", "tool_use_id": tool_use["id"], "content": json.dumps(result)}, indent=2))
```

### 2. The same capability as an MCP server
Now the logic moves into an **MCP server**. The host no longer hard-codes the definition: it *discovers* it with `tools/list` and converts it into the model's tool format. Notice the converted definition has exactly the same shape as `FUNCTION_TOOL` — **MCP feeds function calling, it doesn't replace it.**

```python
from typing import Annotated, Literal

from pydantic import Field

from mcp import Client
from mcp.server import MCPServer

finance = MCPServer("finance")


@finance.tool()
def check_expense_tool(
    category: Annotated[Literal["hotel", "meals", "taxi"], Field(description="Expense category")],
    amount: Annotated[float, Field(description="Amount in EUR")],
) -> dict[str, object]:
    """Check one expense against company policy. Returns ok, the limit and how much it is over."""
    return check_expense(category, amount)


@finance.tool()
def list_expenses(employee: str) -> list[dict[str, object]]:
    """List last week's expenses for an employee."""
    return [{"id": 1, "category": "hotel", "amount": 300.0},
            {"id": 2, "category": "meals", "amount": 35.5},
            {"id": 3, "category": "taxi", "amount": 95.0}]


async with Client(finance) as client:
    mcp_tools = (await client.list_tools()).tools

# The host's one-line adapter: MCP tool -> model tool definition
as_model_tools = [{"name": t.name, "description": t.description, "input_schema": t.input_schema} for t in mcp_tools]
print(json.dumps(as_model_tools[0], indent=2))
print("\nsame keys as the hand-written function tool:", as_model_tools[0].keys() == FUNCTION_TOOL.keys())
```

### 3. The know-how as an Agent Skill
The tools say *what can be done*. They don't say *how the company wants an expense review done*: check every item, round to cents, cite the policy, escalate anything more than 25 % over. That procedure goes into a **skill**: a folder with `SKILL.md` and a reference file, written to a temp directory.

```python
import tempfile
import textwrap
from pathlib import Path

skills_root = Path(tempfile.mkdtemp()) / "skills"
skill_dir = skills_root / "expense-review"
(skill_dir / "references").mkdir(parents=True)

(skill_dir / "SKILL.md").write_text(textwrap.dedent("""\
    ---
    name: expense-review
    description: Review an employee's expense report against company policy and flag violations. Use when asked to audit, check or approve expenses.
    ---
    # Expense review

    1. Call `list_expenses` for the employee.
    2. For EVERY item call `check_expense_tool` (never guess limits).
    3. If an item is more than 25% over its limit, mark it ESCALATE; otherwise mark it FLAG.
       The escalation rules are in references/escalation.md - read it only if something must be escalated.
    4. Finish with a table: id, category, amount, verdict.
"""))
(skill_dir / "references" / "escalation.md").write_text(
    "Escalations go to finance-approvals@example.com with the receipt attached, within 2 working days.\n")

for path in sorted(skill_dir.rglob("*")):
    print(path.relative_to(skills_root))
```

### 4. A tiny skill loader with progressive disclosure
A host that supports skills does three things: validate the frontmatter, put **only metadata** in the model's context, and load the body or a reference file **only on demand**. Watch the token estimate (≈ characters ÷ 4) at each level.

```python
import re

NAME_RULE = re.compile(r"^[a-z0-9]([a-z0-9-]{0,62}[a-z0-9])?$")   # 1-64 chars, a-z 0-9 -, no edge hyphens


def parse_skill(skill_md: Path) -> dict:
    text = skill_md.read_text()
    match = re.match(r"---\n(.*?)\n---\n(.*)", text, re.S)
    meta = dict(line.split(": ", 1) for line in match.group(1).splitlines())
    assert NAME_RULE.match(meta["name"]), f"invalid skill name {meta['name']!r}"
    assert 1 <= len(meta["description"]) <= 1024, "description must be 1-1024 characters"
    assert meta["name"] == skill_md.parent.name, "name should match the directory name"
    return {"name": meta["name"], "description": meta["description"], "body": match.group(2), "dir": skill_md.parent}


tokens = lambda s: len(s) // 4
catalog = {s["name"]: s for s in (parse_skill(p) for p in skills_root.glob("*/SKILL.md"))}

level1 = "\n".join(f"- {s['name']}: {s['description']}" for s in catalog.values())
print("LEVEL 1 - always in context (metadata):", tokens(level1), "tokens\n" + level1)
print("\nLEVEL 2 - on activation (SKILL.md body):", tokens(catalog["expense-review"]["body"]), "tokens")
ref = (catalog["expense-review"]["dir"] / "references" / "escalation.md").read_text()
print("LEVEL 3 - only if a step needs it (references/escalation.md):", tokens(ref), "tokens")
print("\nfor comparison, the MCP tool definitions sent with EVERY request:", tokens(json.dumps(as_model_tools)), "tokens")
```

### 5. All three in one agent run
Now an agent loop that uses everything. A scripted stand-in for the model (so it runs offline) reads the skill catalog, activates `expense-review`, follows its steps by emitting `tool_use` calls, and the host executes each one through MCP. The trace labels which layer did each step.

```python
def scripted_model(state: dict) -> dict:
    """A deterministic stand-in for the LLM that follows the skill's procedure step by step."""
    if "skill" not in state:
        return {"action": "activate_skill", "name": "expense-review"}            # chosen from level-1 metadata
    if "expenses" not in state:
        return {"action": "tool_use", "name": "list_expenses", "input": {"employee": "ana"}}
    pending = [e for e in state["expenses"] if e["id"] not in state["checked"]]
    if pending:
        e = pending[0]
        return {"action": "tool_use", "name": "check_expense_tool", "input": {"category": e["category"], "amount": e["amount"]}, "id": e["id"]}
    if any(v["over_by"] > 0.25 * v["limit"] for v in state["checked"].values()) and "escalation" not in state:
        return {"action": "read_skill_file", "path": "references/escalation.md"}
    return {"action": "final"}


state = {"checked": {}}
async with Client(finance) as client:
    while (step := scripted_model(state))["action"] != "final":
        if step["action"] == "activate_skill":
            state["skill"] = catalog[step["name"]]["body"]
            print(f"[SKILLS level 2]  load SKILL.md of {step['name']!r}")
        elif step["action"] == "read_skill_file":
            state["escalation"] = (catalog["expense-review"]["dir"] / step["path"]).read_text()
            print(f"[SKILLS level 3]  read {step['path']}")
        else:
            print(f"[FUNCTION CALL]   model emits tool_use {step['name']}({step['input']})")
            result = await client.call_tool(step["name"], step["input"])
            print(f"[MCP]             host sends tools/call to server 'finance' -> {result.structured_content}")
            if step["name"] == "list_expenses":
                state["expenses"] = result.structured_content["result"]   # lists are wrapped in {"result": ...}
            else:
                state["checked"][step["id"]] = result.structured_content     # a dict return is the object itself

print("\nid | category | amount | verdict")
for e in state["expenses"]:
    v = state["checked"][e["id"]]
    verdict = "OK" if v["ok"] else ("ESCALATE" if v["over_by"] > 0.25 * v["limit"] else "FLAG")
    print(f"{e['id']}  | {e['category']:<8} | {e['amount']:>6.2f} | {verdict}")
```

Read the trace: the **skill** decided the procedure (check every item, read the escalation file only when needed), **function calling** expressed each action, and **MCP** carried each action to the server that owns the logic.

### 6. Optional: the real model chooses
With `ANTHROPIC_API_KEY` set, Claude gets the skill catalog in the system prompt, a `load_skill` function for level 2, and the finance MCP tools — then decides on its own when to load the skill and which tools to call. Without a key the cell explains what would happen.

```python
import os

if os.environ.get("ANTHROPIC_API_KEY"):
    import anthropic

    llm = anthropic.Anthropic()
    load_skill = {"name": "load_skill", "description": "Load the full instructions of a skill by name.",
                  "input_schema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}}
    system = "You can use these skills; call load_skill before following one.\n" + level1
    messages = [{"role": "user", "content": "Please audit ana's expenses from last week."}]
    async with Client(finance) as client:
        for _ in range(12):
            response = llm.messages.create(model="claude-opus-5-5", max_tokens=16000, system=system,
                                           tools=as_model_tools + [load_skill], messages=messages)
            if response.stop_reason != "tool_use":
                break
            messages.append({"role": "assistant", "content": response.content})
            results = []
            for block in response.content:
                if block.type != "tool_use":
                    continue
                if block.name == "load_skill":
                    print("[SKILLS] Claude loaded", block.input)
                    content, is_error = catalog.get(block.input["name"], {}).get("body", "no such skill"), False
                else:
                    print("[MCP]    Claude called", block.name, block.input)
                    r = await client.call_tool(block.name, block.input)
                    content, is_error = json.dumps(r.structured_content), r.is_error
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": content, "is_error": is_error})
            messages.append({"role": "user", "content": results})
```
