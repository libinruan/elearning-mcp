## Summary
**传输层（Transport）**是一种绑定（Binding）。它决定 MCP 消息如何分帧（Framing）和投递、请求元数据如何承载，以及取消和终止如何发出信号。它从不改变消息的含义。本课介绍 2026-07-28 中的两种标准绑定。**stdio** 是在子进程的 stdin/stdout 上以换行分隔的 JSON-RPC，日志写到 stderr，通过关闭 stdin 来关停。**Streamable HTTP（可流式 HTTP 传输）**是每条消息向单一端点（Endpoint）发送一次 POST，以 JSON 或请求作用域内的 SSE 流作答，并把方法、名称和选定的工具参数镜像到经过校验的请求头中。你还会学到安全规则（Origin 校验、仅绑定 localhost）、通过关闭流来取消、已被移除的内容（会话、GET 流、可恢复性）、向后兼容，以及自定义传输。

## Lesson
### 传输层是什么，不是什么
传输层概述说得很精确：*协议语义在每种传输上都完全相同。* 一个绑定（Binding）定义四件事：

1. **分帧（Framing）与投递。** 一条 JSON-RPC 消息如何定界和发送。消息**必须（MUST）**是 UTF-8。
2. **请求元数据（Request Metadata）。** 一切都在消息体的 `_meta` 中。绑定**可以（MAY）**再把字段镜像到信封元数据（如 HTTP 请求头）中。*消息体始终是权威来源*，进行镜像的绑定要规定如何拒绝不一致的情况。
3. **取消（Cancellation）。** 在 stdio 上，客户端发送 `notifications/cancelled`。在 Streamable HTTP 上，客户端关闭该请求的响应流。
4. **终止（Termination）。** 连接或进程如何结束。

每种绑定都**必须（MUST）**把客户端的请求和通知投递给服务器，把服务器的响应和通知投递给客户端。*不存在其他消息方向*：服务器从不发送请求，客户端从不发送响应。

### stdio：本地子进程传输
客户端（Client）把服务器（Server）作为子进程启动，双方通过它的标准流通信：

- 服务器从 **stdin** 读取 JSON-RPC，向 **stdout** 写入 JSON-RPC。
- 每条消息是一个 JSON-RPC 请求、通知或响应，**以换行分隔**，并且**不得（MUST NOT）包含内嵌换行**。请紧凑地序列化。美化打印（pretty-print）的消息会破坏分帧。
- 服务器**不得（MUST NOT）**向 stdout 写入任何不是有效 MCP 消息的内容。客户端**不得（MUST NOT）**向 stdin 写入任何其他内容。
- 服务器**可以（MAY）**向 **stderr** 写入 UTF-8 文本用于任何日志。客户端可以捕获、转发或忽略它，并且**不应（SHOULD NOT）**认为 stderr 有输出就意味着出错。

> **陷阱。** stdio 服务器里一句遗漏的 `print("debug")` 会写到 stdout 并破坏数据流。请用 `print(..., file=sys.stderr)` 或配置为输出到 stderr 的 logger 记日志。这是手写 stdio 服务器的头号 bug。

所有服务器消息共用唯一的 stdout 通道，没有按请求划分的流。服务器写入响应（按 `id` 关联）、属于进行中请求的通知（`notifications/progress`、`notifications/message`），以及属于活跃 `subscriptions/listen` 请求的通知，客户端通过 `_meta` 中的 `io.modelcontextprotocol/subscriptionId` 来关联后者。服务器**不得（MUST NOT）**向 stdout 写入请求。服务器对客户端的需求通过 `InputRequiredResult` 回复（多轮往返请求（MRTR））来传递。由于响应带有 id，客户端可以**流水线（Pipelining）**发送多个请求，并在答复以任意顺序到达时逐一匹配。

**stdio 上的请求元数据**完全内联（在消息体的 `_meta` 中），没有请求头这一层。

**取消：**客户端**必须（MUST）**发送带有该请求 id 的 `notifications/cancelled`。服务器**应当（SHOULD）**尽快停止工作，并且**不得（MUST NOT）**再为该请求发送任何消息。

**关停。** 客户端**应当（SHOULD）**：

1. 关闭服务器的 stdin；
2. 等待进程退出；
3. 如果在合理时间内没有退出，就强制终止它（POSIX：先 `SIGTERM`，再 `SIGKILL`；Windows：`TerminateProcess` 或 Job Objects）。

服务器**应当（SHOULD）**在遇到 EOF 时立即退出。*这是主要的优雅关停信号，也是唯一可移植的信号。* 服务器**可以（MAY）**通过关闭 stdout 并退出来自行关停。如果服务器意外崩溃，客户端**应当（SHOULD）**重启它。进行中的请求会丢失，但可以重试（得益于无状态（Stateless）），`subscriptions/listen` 流则需要重新建立。

**生命周期：**客户端**不应（SHOULD NOT）**把 stdio 进程的生命周期绑定到单个任务、线程或对话上（第 2.2 课）。一个进程可以服务交错进行、互不相关的工作。

### Streamable HTTP：每条消息一次 POST
对于远程服务器（以及许多本地服务器），服务器是一个独立进程，同时服务多个客户端（Client）。它暴露一个**单一的 MCP 端点（MCP Endpoint）**路径（例如 `https://example.com/mcp`），接受 **POST**。

**发送。** 客户端的每条消息都是发往该端点的一次**新的 HTTP POST**：

- `Accept` 请求头**必须（MUST）**同时列出 `application/json` 和 `text/event-stream`。
- 消息体是**单个** JSON-RPC 请求或通知。客户端**不得（MUST NOT）**POST 响应。
- 每次 POST 都必须带上请求元数据头（见下文）。
- 服务器接受的**通知（Notification）**得到 `202 Accepted`，没有消息体。如果无法接受，服务器返回错误状态码。（本修订版没有定义任何通过 HTTP 从客户端发往服务器的通知。`notifications/cancelled` 只用于 stdio。）
- **请求（Request）**得到的要么是 `Content-Type: application/json`（一个 JSON 对象），要么是 `Content-Type: text/event-stream`（一个 SSE 流）。由服务器逐个请求选择，**客户端必须（MUST）两者都支持**。

**接收 SSE 响应。** 在最终响应之前，服务器**可以（MAY）**发送通知，这些通知**必须（MUST）**与发起的请求相关：进度、日志消息。它**不得（MUST NOT）**在流上发送独立的请求。2025-03-26 到 2025-11-25 期间允许这样做，现在由 MRTR 取代。最终响应**应当（SHOULD）**结束该流。打开 SSE 时，服务器**应当（SHOULD）**发送 `X-Accel-Buffering: no`，以免 nginx 之类的代理缓冲事件。长时间存活的流应定期发送 SSE 注释行（`:`）作为保活（keep-alive），客户端必须忽略它们。

```text
POST /mcp  tools/call (progressToken=7)          200 OK  Content-Type: text/event-stream
                                                  event: message
                                                  data: {"method":"notifications/progress",...}
                                                  event: message
                                                  data: {"jsonrpc":"2.0","id":1,"result":{...}}
                                                  (stream closes)
```

**变更通知**（列表变更、资源更新）**不会**走这些按请求划分的流。客户端打开一个长时间存活的 `subscriptions/listen` POST，其响应流只携带它选择订阅的类型（第 3.4 课）。请求作用域内的 `notifications/progress` 和 `notifications/message` 永远不会出现在监听流上。

### 请求元数据头
Streamable HTTP 会**把消息体字段镜像到请求头中**，这样负载均衡器、网关（Gateway）、WAF 和可观测性工具无需解析 JSON 就能路由和检查流量：

| 请求头 | 来源 | 必需场景 |
| --- | --- | --- |
| `MCP-Protocol-Version` | `_meta["io.modelcontextprotocol/protocolVersion"]` | 每次 POST |
| `Mcp-Method` | `method` | 所有请求 |
| `Mcp-Name` | `params.name` 或 `params.uri` | `tools/call`、`prompts/get`、`resources/read` |
| `Mcp-Param-{Name}` | 带有 `x-mcp-header` 注解的工具参数 | `tools/call`，且该值存在时 |

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: execute_sql
Mcp-Param-Region: us-west1
```

**与版本和方法相关的状态码。** 不支持的版本得到 `400` 和 `UnsupportedProtocolVersionError`（`-32022`）。未知方法得到 `404` 和 `-32601`。JSON-RPC 消息体可以把它和旧版服务器的普通 404 区分开。对于**没有** `MCP-Protocol-Version` 请求头的请求，支持 2025-06-18 之前客户端的服务器**可以（MAY）**把它当作 `2025-03-26` 处理。否则按服务器校验规则拒绝。

**`x-mcp-header`。** 服务器**可以（MAY）**在 `inputSchema` 中给某个工具参数加上 `"x-mcp-header": "Region"` 注解。客户端**必须（MUST）**支持它：把该参数镜像到 `Mcp-Param-Region`。约束如下：必须是非空、不区分大小写时唯一的 RFC 9110 token；只能用于 `integer`、`string` 或 `boolean` 属性（绝不能是 `number`；整数需在 JavaScript 安全范围内）；并且只能用于通过一串 `properties` 键*静态可达*的属性（不能经由 `items`、`anyOf`/`oneOf`/`allOf`/`not`、`if`/`then`/`else` 或 `$ref`）。HTTP 客户端**必须（MUST）**从 `tools/list` 中丢弃注解违反这些规则的工具，并**应当（SHOULD）**记录一条警告。

**值编码。** 字符串原样发送，整数用十进制，布尔值用 `true`/`false`。不是安全纯 ASCII 的值（非 ASCII、控制字符、首尾空白），或者本身看起来就像哨兵格式的值，以 `=?base64?{base64 of UTF-8}?=` 的形式发送。`Mcp-Name` 同理。所以 `"Hello, 世界"` 会变成 `=?base64?SGVsbG8sIOS4lueVjA==?=`。请求头*名称*比较时不区分大小写，而方法名之类的*值*区分大小写。

**服务器校验。** 处理消息体的服务器在以下情况下**必须（MUST）**以 **`400 Bad Request` 和 `-32020` HeaderMismatch（请求头不匹配错误）**拒绝请求：

- 缺少必需的标准请求头；
- 请求头的值与消息体不同（在 base64 解码之后比较；整数**应当（SHOULD）**按数值比较，所以 `42.0` 等于 `42`）；
- 值中包含非法字符；
- 带注解参数在消息体中有值，却没有对应的 `Mcp-Param-*` 请求头。

原因在于安全：如果负载均衡器按请求头路由，而服务器按消息体执行，两者就绝不能不一致。客户端因为 `Mcp-Param-*` 收到 `-32020` 时，**应当（SHOULD）**重新获取 `tools/list`（模式（Schema）可能已经变化）并重试。中间件（Intermediary）只需返回一个 HTTP 错误。对镜像请求头执行策略的中间件**应当（SHOULD）**拒绝较旧版本或缺失版本的请求，因为它们没有请求头与消息体的校验，而不是信任它们。

### HTTP 服务器的安全
规范列出了三项要求：

1. 服务器**必须（MUST）在所有传入连接上校验 `Origin` 请求头**，以防止 **DNS 重绑定攻击（DNS Rebinding）**。如果它存在且无效，服务器**必须（MUST）**回复 `403 Forbidden`，可以附带一个不含 id 的 JSON-RPC 错误体。
2. 在本地运行时，服务器**应当（SHOULD）只绑定到 `127.0.0.1`**，而不是 `0.0.0.0`。
3. 服务器**应当（SHOULD）**对所有连接进行认证（Authentication）（OAuth，见模块 6）。

DNS 重绑定的原理：`evil.example` 上的页面让自己的主机名解析到 `127.0.0.1`。浏览器此时认为这是同源的，于是页面的 JavaScript 就能向你的本地 MCP 服务器发 POST 并调用它的工具。把 `Origin`（以及 Python SDK 同样会检查的 `Host`）与白名单比对就能挫败这种攻击，因为重绑定页面的 Origin 和 Host 仍然是 `evil.example`。

### 取消与可恢复性的终结
在 Streamable HTTP 上，**关闭 SSE 响应流就是取消（Cancellation）**。服务器**必须（MUST）**把客户端断开连接视为取消该请求，**应当（SHOULD）**尽快停止工作，并且**不得（MUST NOT）**再为它发送任何消息。由于每个请求都有自己的流，这个信号是明确无歧义的，因此不需要、也不期望 `notifications/cancelled`。

另一面是：2026-07-28 **不支持通过 `Last-Event-ID` 恢复 SSE（可恢复性（Resumability））**。响应流一旦中断，进行中的请求就丢失了，客户端**必须（MUST）**用一个**新的 id** 把它作为新请求重新发出。如果工作耗时长到这会造成困扰，请使用 Tasks 扩展（第 7.1 课），而不是在传输层上耍花招。

### 向后兼容
2026-07-28 修改了 Streamable HTTP：**没有 GET 流端点、没有协议级会话（Session）、SSE 上没有服务器发起的请求、没有可恢复性**。2025-03-26 到 2025-11-25 的修订版有 `Mcp-Session-Id`（以 `DELETE` 结束）、独立的 GET SSE 流和 `Last-Event-ID`。只支持本修订版的服务器**应当（SHOULD）**：

- 对 **GET 或 DELETE** 回复 `405 Method Not Allowed`；
- **忽略** `Mcp-Session-Id`，既不生成也不回显会话 id；
- **忽略** `Last-Event-ID`。

**通过 HTTP 进行时代探测（Era Probe）。** 双时代（Dual-era）客户端先发送一个新版请求。收到 `400` 时检查消息体。若是可识别的新版 JSON-RPC 错误（`-32022`、`-32021`、`-32020`），说明服务器是新版的，客户端修正请求即可。若消息体为空或无法识别，说明是旧版服务器，于是回退到 `initialize`。

**旧的 HTTP+SSE 传输（2024-11-05）**在特性生命周期（Feature Lifecycle）策略下属于**已弃用（Deprecated）**（自 2025-03-26 起弃用）。新实现**不应（SHOULD NOT）**采用它。仍然支持它的客户端先发 POST。收到 `400`、`404` 或 `405` 且*没有*可识别的新版错误体时，它发出一个 GET，期待得到一个首个事件为 `endpoint` 的 SSE 流，如果收到了就使用旧传输。服务器可以在新的 MCP 端点旁边继续托管旧的 SSE 和 POST 端点。

### 自定义传输
实现**可以（MAY）**在任何双向通道上添加传输（Transport）。它们**必须（MUST）**保留 JSON-RPC 格式、消息模式（Message Pattern）和逐请求元数据模型，并**应当（SHOULD）**记录连接建立、分帧和取消的方式。在可靠的字节流（Unix socket、TCP）上，它们**应当（SHOULD）复用 stdio 的分帧方式**，即以换行分隔的 JSON-RPC。只有与进程生命周期相关的部分（启动、stderr、EOF 关停、重启）需要针对具体通道的等价机制。

## Key points
- 传输层（Transport）定义的是**分帧、元数据承载、取消和终止**，从不定义语义。消息是 UTF-8 的 JSON-RPC，消息体中的 `_meta` 是权威来源。
- **stdio（标准输入输出传输）：**在 stdin/stdout 上每行一条紧凑的 JSON 消息，不含内嵌换行，stdout 上不得有其他内容。**日志写到 stderr**，它不是错误信号。
- stdio 关停（Shutdown）：**关闭 stdin → 等待 → SIGTERM/SIGKILL**。服务器在 EOF 时退出。取消用 `notifications/cancelled`。
- **Streamable HTTP（可流式 HTTP 传输）：**单一端点，**每条消息一次 POST**，`Accept: application/json, text/event-stream`。通知得到 `202`。请求得到 JSON **或**请求作用域内的 SSE 流，客户端必须两者都能处理。
- 必需的请求头（Header）：每次 POST 都要有 **`MCP-Protocol-Version`**，每个请求都要有 **`Mcp-Method`**，`tools/call`/`prompts/get`/`resources/read` 要有 **`Mcp-Name`**。`x-mcp-header` 参数会变成 **`Mcp-Param-{Name}`**，不安全的值使用 `=?base64?…?=`。
- 请求头与消息体不一致，或缺少必需请求头 → **`400` + `-32020` HeaderMismatch（请求头不匹配错误）**。版本不受支持 → `400` + `-32022`。未知方法 → `404` + `-32601`。
- 安全：**校验 `Origin`**（无效 → `403`）以防御 DNS 重绑定攻击（DNS Rebinding），本地运行时**绑定到 127.0.0.1**，并进行认证。
- HTTP 上的取消（Cancellation）=**关闭响应流**。**没有可恢复性**：中断的请求要用新的 id 重新发出。
- 2026-07-28 移除了**会话（Session）、GET 流和服务器发起的请求**。GET/DELETE 得到 `405`，`Mcp-Session-Id`/`Last-Event-ID` 被忽略。2024-11-05 的 **HTTP+SSE 传输已被弃用（Deprecated）**。

## Pitches
### stdio 还是 Streamable HTTP，你会选哪个？
这取决于服务器跑在哪里、给谁用。如果是由某个用户的宿主（Host）启动的本地工具，比如文件系统或 git 服务器，我会用 stdio：宿主把它作为子进程拉起来，没有网络暴露面，凭据来自环境变量，关停也只需关闭 stdin。如果是共享的或远程的服务，我会用 Streamable HTTP（可流式 HTTP 传输）：一个端点，每条消息一次 POST，响应是 JSON 或请求作用域内的 SSE 流。它是无状态（Stateless）的，所以放在普通负载均衡器后面就能扩展，前面再加上 OAuth。

### 为什么 Streamable HTTP 要把消息体镜像到请求头里？
这样基础设施不用解析 JSON-RPC 就能做决策。网关（Gateway）可以按 `Mcp-Method` 路由、按 `Mcp-Name` 限流，或者通过工具模式（Schema）里用 `x-mcp-header` 声明的 `Mcp-Param-Region` 请求头，把某个租户固定在某个区域。因为消息体始终是权威来源，服务器必须检查请求头和消息体是否一致，不一致就返回 400 和错误码负 32020 拒绝。否则攻击者就能让网关按一个值路由，而服务器执行的却是另一个值。

### 你会如何保护一个本地 HTTP MCP 服务器？
把它绑定到 127.0.0.1，绝不要绑 0.0.0.0，这样网络上的任何东西都连不到它。然后在每个请求上校验 Origin 请求头，对未知来源返回 403。这能挡住 DNS 重绑定攻击（DNS Rebinding）：恶意网页把自己的主机名指向 localhost，诱使浏览器调用我的工具。检查 Host 请求头也有帮助。另外我仍然会在前面加上认证（Authentication），因为本机上的其他进程和其他用户也能访问 localhost。

## Interview
### 你的 stdio 服务器在 Inspector 里正常，但在宿主里会卡住或崩溃。你首先检查什么？
先检查 **stdout 是否干净**。stdout 上任何不是换行分隔 JSON-RPC 的内容，比如一个 `print()`、某个库的启动横幅或一个进度条，都会破坏数据流（stdio 传输（stdio Transport）），客户端要么解析失败，要么永远等待一个它无法分帧的响应。把所有日志都挪到 **stderr**。接着检查消息是否紧凑（没有内嵌换行）且是 UTF-8。然后检查生命周期：stdin 关闭时服务器会退出吗？如果不会，宿主（Host）就只能 SIGTERM 或 SIGKILL 它。最后要记住，客户端可能只把 stderr 当作参考信息，所以一个只在 stderr 上“报告”错误的服务器，从协议角度看是健康的。

### 说明 Streamable HTTP 服务器什么时候用 JSON 作答，什么时候用 SSE。
由服务器逐个请求选择，客户端必须两种都接受。没有内容需要流式传输的普通请求得到 `application/json`。如果服务器想在结果之前发送与该请求相关的通知，比如进度通知（Progress Notification）（仅当客户端发送了 `progressToken` 时）或日志消息（仅当客户端设置了 `logLevel` 时），它就打开 `text/event-stream`，把这些作为服务器发送事件（SSE）发出，最后以响应结束。它不得在流上发送独立的请求。服务器对客户端的需求放在 `InputRequiredResult` 中。长期存在的变更通知使用单独的 `subscriptions/listen` POST。例如，Python SDK 会推迟决定使用 SSE，直到处理函数真的发出一条通知，所以快速调用得到的是 JSON。

### 一个请求带着 `Mcp-Name: get_weather`，但消息体调用的是 `delete_repo`。服务器必须怎么做？为什么这很重要？
以 **HTTP 400 和 JSON-RPC `-32020` HeaderMismatch（请求头不匹配错误）**拒绝它，不执行任何操作。镜像请求头的存在就是为了让中间件能据此行动：WAF 可能允许 `get_weather` 而拦截 `delete_repo`，或者路由器可能把它发到只读资源池。如果服务器不管请求头、照样执行消息体，攻击者就能把一个被禁止的调用偷偷带过所有基于请求头的控制。`MCP-Protocol-Version`、`Mcp-Method` 以及每个由 `x-mcp-header` 派生的 `Mcp-Param-*` 同样适用，比较在 base64 解码之后进行，整数按数值比较。

### stdio 和 Streamable HTTP 上的取消有什么不同？
在 **stdio** 上只有一个共享通道，没有按请求划分的流，所以客户端**必须**发送带有 `requestId`（以及可选的 `reason`）的 `notifications/cancelled`（取消通知）。在 **Streamable HTTP** 上每个请求都有自己的响应流，所以**关闭它就是取消（Cancellation）**。服务器必须把断开连接视为取消，不会期待任何通知。两种情况下服务器都应停止工作并释放资源，不得再为该请求发送任何内容，并且双方都必须能容忍竞态条件（Race Condition）：结果可能已经在发送途中。

### 在 2026-07-28 中，如果 SSE 连接断开，进行中的请求会怎样？
它会丢失。修订版 2026-07-28 **移除了 SSE 可恢复性（Resumability）**（`Last-Event-ID` 和 SSE 事件 id），服务器把断开视为取消。客户端**必须重新发出**该请求，作为一个**带有新 id 的新请求**。由于协议是无状态（Stateless）的，按这种方式设计是安全的，但这意味着非幂等的工具需要自己的保护措施，比如参数中的幂等键（Idempotency Key）或服务器生成的句柄（Server-minted Handle）。真正长时间运行的工作应该交给 Tasks 扩展，由客户端轮询任务句柄，而不是一直保持流打开。

### 陷阱题：一个旧客户端发送带有 `Mcp-Session-Id` 的 `GET /mcp`。只支持 2026-07-28 的服务器应该如何响应？
对 MCP 端点的 `GET`（以及 `DELETE`）回复 **`405 Method Not Allowed`**。已经不存在独立的 SSE 流了。在 POST 上，`Mcp-Session-Id` 被**忽略**：服务器既不生成也不回显会话（Session）id。`Last-Event-ID` 也会被忽略，因为流不可恢复。如果旧客户端还发送了 `initialize`，只支持新版的服务器应当以一个列出其支持版本的错误拒绝它，因为旧版客户端无法向前兼容升级，而这条消息可能就是用户能看到的全部信息。双时代（Dual-era）服务器则可以改用旧版语义来服务它。

## Glossary
- Transport binding | 传输绑定 | 定义 MCP 消息如何在某个通道上分帧、投递、取消和终止，而不改变其含义。
- stdio transport | 标准输入输出传输 | 客户端把服务器作为子进程启动，并通过 stdin/stdout 交换以换行分隔的 JSON-RPC 的绑定方式。
- Streamable HTTP | 可流式 HTTP 传输 | 客户端的每条消息都是发往单一 MCP 端点的 HTTP POST，并以 JSON 或请求作用域内的 SSE 流作答的绑定方式。
- Server-Sent Events (SSE) | 服务器发送事件 | 一种 `text/event-stream` HTTP 响应格式，用于先投递与请求相关的通知，再投递最终响应。
- MCP endpoint | MCP 端点 | Streamable HTTP 服务器上接受 POST 的唯一 HTTP 路径（例如 `/mcp`）。
- `Mcp-Method` / `Mcp-Name` | `Mcp-Method`／`Mcp-Name` 请求头 | 镜像 JSON-RPC 方法以及工具/提示模板名称或资源 URI 的必需请求头。
- `x-mcp-header` | `x-mcp-header` 参数头注解 | 一种 JSON Schema 注解，使客户端把某个基本类型的工具参数镜像到 `Mcp-Param-{Name}` 请求头中。
- DNS rebinding | DNS 重绑定攻击 | 网页让自己的主机名解析到 localhost，从而使浏览器能够调用本地服务器的攻击；可通过 Origin/Host 校验阻止。
- Resumability (removed) | 可恢复性（已移除） | 2025 年代各版本中通过 `Last-Event-ID` 恢复 SSE 流的能力；在 2026-07-28 中，流中断意味着要重新发出请求。
- HTTP+SSE transport (deprecated) | HTTP+SSE 传输（已弃用） | 2024-11-05 的双端点传输（GET SSE 流加 POST 端点），已被弃用并由 Streamable HTTP 取代。

### 1. 手动实现 stdio 分帧：流水线、stderr 与损坏的帧
一个在工作时把日志写到 **stderr** 的服务器（Server）。我们在一次写入中以流水线方式发送两个请求，观察答复**按 id、乱序**到达，并分别读取 stdout 和 stderr。

```python
import json
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
import time
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "stdio_server.py").write_text(textwrap.dedent('''
    import sys
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("stdio-lab", log_level="ERROR")

    @mcp.tool()
    def add(a: int, b: int) -> int:
        """Add two integers."""
        return a + b

    @mcp.tool()
    async def slow(steps: int, ctx: Context) -> str:
        """Work for a while, reporting progress."""
        for i in range(steps):
            print(f"[server log] slow step {i + 1}/{steps}", file=sys.stderr, flush=True)   # stderr: fine
            await ctx.report_progress(i + 1, steps)
            await anyio.sleep(0.3)
        return "done"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {}}
proc = subprocess.Popen([sys.executable, str(workdir / "stdio_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
stdout_q, stderr_q = queue.Queue(), queue.Queue()
threading.Thread(target=lambda: [stdout_q.put(l) for l in proc.stdout], daemon=True).start()
threading.Thread(target=lambda: [stderr_q.put(l) for l in proc.stderr], daemon=True).start()


def write_lines(*messages):
    data = "".join(json.dumps(m) + "\n" for m in messages)     # compact JSON, one per line
    proc.stdin.write(data)
    proc.stdin.flush()


def read_stdout(timeout=3.0):
    try:
        return json.loads(stdout_q.get(timeout=timeout))
    except queue.Empty:
        return None


write_lines(
    {"jsonrpc": "2.0", "id": "slow-1", "method": "tools/call",
     "params": {"name": "slow", "arguments": {"steps": 3}, "_meta": {**ENVELOPE, "progressToken": "p"}}},
    {"jsonrpc": "2.0", "id": "fast-2", "method": "tools/call",
     "params": {"name": "add", "arguments": {"a": 2, "b": 40}, "_meta": ENVELOPE}},
)
start = time.time()
for _ in range(5):
    msg = read_stdout(timeout=10)
    label = f"response id={msg['id']}" if "id" in msg else f"{msg['method']} {msg['params'].get('progress')}"
    print(f"stdout +{time.time() - start:.2f}s  {label}")
time.sleep(0.1)
while not stderr_q.empty():
    print("stderr          ", stderr_q.get().rstrip())
```

`fast-2` 是第二个写入的，却最先得到答复。客户端（Client）按 `id` 而不是按顺序匹配答复。现在来破坏分帧（Framing）：把同一个请求**美化打印**后发送（带内嵌换行）。

```python
pretty = json.dumps({"jsonrpc": "2.0", "id": 3, "method": "tools/list", "params": {"_meta": ENVELOPE}}, indent=2)
print(f"pretty-printed message spans {pretty.count(chr(10)) + 1} lines")
proc.stdin.write(pretty + "\n")
proc.stdin.flush()
print("reply:", read_stdout(timeout=2))

write_lines({"jsonrpc": "2.0", "id": 4, "method": "tools/list", "params": {"_meta": ENVELOPE}})
print("compact reply has", len(read_stdout()["result"]["tools"]), "tools - the server survived, but request 3 was lost")
```

不带 `indent` 的 `json.dumps` 永远不会输出原始换行：字符串*内部*的换行会被转义为 `\n`，所以任意文本都可以安全地放在一帧里。

### 3. Streamable HTTP：单一端点，原始 POST
在一个线程中于 `127.0.0.1` 上运行 HTTP 服务器。一个小的 ASGI 包装器会**记录每个请求的请求头**，让我们能确切看到客户端（Client）发送了什么。其中一个工具声明了 `x-mcp-header` 参数。

```python
import logging
import socket
from typing import Annotated

import anyio
import httpx
import uvicorn
from pydantic import Field
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

web_server = MCPServer("http-lab")


@web_server.tool()
def run_sql(region: Annotated[str, Field(description="Region to run in", json_schema_extra={"x-mcp-header": "Region"})],
            query: str) -> str:
    """Run a (pretend) SQL query in a region."""
    return f"[{region}] {query} -> 42 rows"


@web_server.tool()
async def slow(steps: int, ctx: Context) -> str:
    """Work for a while, reporting progress."""
    try:
        for i in range(steps):
            await ctx.report_progress(i + 1, steps, f"step {i + 1}")
            await anyio.sleep(0.2)
    except BaseException as exc:            # cancellation arrives as an exception in the handler
        server_events.append(f"slow() interrupted by {type(exc).__name__}")
        raise
    return "done"


for noisy in ("httpx", "httpx2", "mcp", "uvicorn"):
    logging.getLogger(noisy).setLevel(logging.ERROR)

server_events, seen_headers = [], []
mcp_app = web_server.streamable_http_app()          # binds DNS-rebinding protection for 127.0.0.1


async def recorder(scope, receive, send):
    if scope["type"] == "http":
        seen_headers.append({"method": scope["method"],
                             **{k.decode(): v.decode() for k, v in scope["headers"] if k.startswith(b"mcp")}})
    await mcp_app(scope, receive, send)


sock = socket.socket()
sock.bind(("127.0.0.1", 0))
port = sock.getsockname()[1]
sock.close()
uv = uvicorn.Server(uvicorn.Config(recorder, host="127.0.0.1", port=port, log_level="warning", lifespan="on"))
threading.Thread(target=uv.run, daemon=True).start()
while not uv.started:
    time.sleep(0.05)
URL = f"http://127.0.0.1:{port}/mcp"
web = httpx.Client(trust_env=False, timeout=10)

           "MCP-Protocol-Version": "2026-07-28"}


def tools_call(name, arguments, id_=1, meta=ENVELOPE):
    return {"jsonrpc": "2.0", "id": id_, "method": "tools/call",
            "params": {"name": name, "arguments": arguments, "_meta": meta}}


r = web.post(URL, json=tools_call("run_sql", {"region": "us-west1", "query": "select 1"}),
             headers={**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "run_sql", "Mcp-Param-Region": "us-west1"})

print(json.dumps(r.json(), indent=2)[:600])
```

### 4. JSON 还是 SSE？由请求决定
同一个 `slow` 工具（Tool），在没人要求进度时以 JSON 作答，在请求携带 `progressToken`（进度令牌（Progress Token））时以 SSE 流作答。这个 SDK 只有在处理函数真正发出通知时才会切换到 SSE。

```python
def parse_sse(text):
    return [json.loads(line[len("data: "):]) for line in text.splitlines() if line.startswith("data: ")]


h = {**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "slow"}
r = web.post(URL, json=tools_call("slow", {"steps": 2}), headers=h)
print("no progressToken  ->", r.status_code, r.headers["content-type"])

r = web.post(URL, json=tools_call("slow", {"steps": 3}, meta={**ENVELOPE, "progressToken": "tok-1"}), headers=h)
print("with progressToken->", r.status_code, r.headers["content-type"],
      "| X-Accel-Buffering:", r.headers.get("x-accel-buffering"))
for event in parse_sse(r.text):

          event.get("params", {}).get("message", ""))
```

### 5. 请求头校验：把每个请求头都弄错
下面每个请求都恰好错在一处。除了最后两个以外，其他请求都会在任何工具运行**之前**被拒绝。

```python
good_body = tools_call("run_sql", {"region": "us-west1", "query": "select 1"})
base = {**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "run_sql", "Mcp-Param-Region": "us-west1"}
cases = {
    "all correct": base,
    "Mcp-Method lies": {**base, "Mcp-Method": "tools/list"},
    "Mcp-Name lies (WAF bypass attempt)": {**base, "Mcp-Name": "get_weather"},
    "Mcp-Name missing": {k: v for k, v in base.items() if k != "Mcp-Name"},
    "Mcp-Param-Region lies": {**base, "Mcp-Param-Region": "eu-west1"},
    "Mcp-Param-Region missing": {k: v for k, v in base.items() if k != "Mcp-Param-Region"},
    "Accept lacks text/event-stream": {**base, "Accept": "application/json"},
    "header NAMES are case-insensitive": {k.upper(): v for k, v in base.items()},
}
old_body = tools_call("run_sql", {"region": "us-west1", "query": "select 1"},
                      meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": "2025-11-25"})
for label, headers in cases.items():
    r = web.post(URL, json=good_body, headers=headers)
    detail = r.json().get("error", {}) if r.headers.get("content-type", "").startswith("application/json") else {}
    print(f"{label:<36} HTTP {r.status_code}  {detail.get('code', '')} {detail.get('message', '')[:70]}")

r = web.post(URL, json=old_body, headers=base)          # header says 2026-07-28, body says 2025-11-25
print(f"{'body version != header':<36} HTTP {r.status_code}  {r.json()['error']['code']} {r.json()['error']['message'][:70]}")
```

`MCP-Protocol-Version` 检查在受支持版本检查之前运行，所以自相矛盾的客户端收到的是 `-32020`，而不是 `-32022`。有一个特殊之处：这个双时代（Dual-era）SDK 根据请求头来选择*时代*，所以**请求头**中写着旧版本的请求会被交给旧版传输处理（你会在第 8 节看到）。

非 ASCII 值以 base64 哨兵形式传输。SDK 提供了与客户端所用相同的编码器：

```python

    print(f"{value!r:<22} -> Mcp-Param-Region: {encode_header_value(value)}")

r = web.post(URL, json=tools_call("run_sql", {"region": "Zürich", "query": "select 1"}),
             headers={**base, "Mcp-Param-Region": encode_header_value("Zürich")})
```

### 8. 旧客户端与高层 `Client`
先看 2026-07-28 服务器如何对待旧版流量，再看 SDK 的 `Client` 自己会发送什么。

```python
print("GET  /mcp                ->", web.get(URL, headers=HEADERS).status_code, "(no standalone SSE stream any more)")
print("DELETE /mcp              ->", web.delete(URL, headers=HEADERS).status_code, "(no sessions to delete)")
```

```python
    print((await client.call_tool("run_sql", {"region": "Zürich", "query": "select 1"})).content[0].text)
    print((await client.call_tool("slow", {"steps": 2}, progress_callback=on_progress)).content[0].text)
```

2. 在一个 `number` 参数上，或在数组 `items` 内部的某个属性上加 `x-mcp-header`，然后从 `Client(URL)` 调用 `list_tools()`。规范说 HTTP 客户端必须丢弃这样的工具：这个 SDK 会这样做吗？
3. 编写一个函数 `cancel_after(seconds)`，以流式方式发起 `slow` 调用，并在超出时间预算后关闭它。把服务器端的事件与第 2 节的 stdio 取消进行比较。在每种情况下，哪一方知道取消的原因？
4. 用 `web_server.streamable_http_app(json_response=True)` 重新构建 HTTP 应用。进度通知会怎样？为什么部署在会缓冲的代理后面的服务可能仍然会选择这样做？
