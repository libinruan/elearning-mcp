## Summary
2026-07-28 中最大的变化是 MCP 变成了一个**无状态协议（Stateless Protocol）**。不再有 `initialize` 握手，不再有 `Mcp-Session-Id`，也不再有“记得”你是谁的连接。每个请求（Request）都携带自己的协议版本和能力（Capability），所以任何一个服务器实例都能回答它。正是这一点让 MCP 服务器很容易放到负载均衡器后面、以 serverless 方式运行并进行水平扩展（Horizontal Scaling）。本课讲解无状态的各项规则、取代会话的机制（显式的、由服务器生成的**句柄（Server-minted Handle）**，作为工具参数传递）、必须实现的 **`server/discover`** RPC 及其 `DiscoverResult`，以及版本协商（Version Negotiation）如何借助 `UnsupportedProtocolVersionError` 改为逐请求进行。notebook 会运行两个相互独立的服务器进程，在它们之间轮询分发请求，并展示一个照样能正常工作的有状态购物篮。

## Lesson
### 从会话到自包含的请求
在 2025-11-25 及之前，一个 MCP 连接以握手开始。客户端发送 `initialize`（协议版本、能力、客户端信息），服务器回复自己的信息，客户端再用 `notifications/initialized` 确认。此后的一切都依赖于协商好的状态，在 Streamable HTTP 上，服务器还可以把这些状态绑定到一个 `Mcp-Session-Id` 请求头上。2026-07-28 的变更日志移除了所有这些内容：

| 2025-11-25 及更早（旧时代） | 2026-07-28（新时代） |
| --- | --- |
| `initialize` → 结果 → `notifications/initialized` | **没有握手**；每个请求都是自包含的 |
| 每个连接协商一次版本和能力 | **每个**请求的 `_meta` 中都带有 `io.modelcontextprotocol/protocolVersion` 和 `clientCapabilities` |
| `Mcp-Session-Id` 请求头，用 `DELETE` 结束会话 | **没有协议层面的会话** |
| `tools/list` 等可能因连接而异 | 列表类端点**不再因连接而异** |
| `ping` | 已移除 |
| 服务器信息由 `initialize` 返回一次 | `server/discover`（必须实现）以及每个结果 `_meta` 中的 `serverInfo` |
| 跨调用状态隐藏在会话里 | **显式的、由服务器生成的句柄**，作为普通工具参数传递 |

### 无状态的规则
基础协议直接写明：*处理一个请求所需的所有信息都包含在请求本身之中。服务器独立处理每个请求；不应从之前的请求中推断任何状态，即使它们来自同一个连接或同一个流。* 具体来说：

- 服务器（Server）**不得（MUST NOT）**依赖同一连接上之前的请求来建立上下文，例如能力（Capability）、协议版本或客户端身份。每个请求都在 `_meta` 中提供这些信息。
- 服务器**应当（SHOULD）**做好准备，处理与多个任务、线程或对话相关联的请求。
- 服务器**不应（SHOULD NOT）**要求客户端为相关操作复用同一个连接或进程。
- 客户端**不应（SHOULD NOT）**把单个任务、线程或对话作为 stdio 进程的生命周期边界。
- 必须跨请求存在的状态（长时间运行的任务、应用层句柄）**必须（MUST）**通过一个**显式标识符**来引用，由客户端在每个请求中传递。

> **规范规则。** 一个打开的连接，即使是一个 stdio 进程，*也不是一次对话或会话*。客户端可以在同一个传输（Transport）上交错发送互不相关的请求，服务器不得把连接或进程的身份当作对话连续性的替代品。

像 `subscriptions/listen` 这样的长时请求依然是请求/响应。其响应是一条开放的通知流，它的状态**限定于该请求**，而不是底层的连接。如果通道断开，客户端只需重新发出该请求即可。

能力同样是**逐请求**的。同一个客户端可以在一次调用中声明 `{"elicitation": {}}`，在下一次调用中声明 `{}`，服务器必须只根据每个请求自身的声明来判断。如果缺少所需的能力，答复就是 `-32021`（第 2.1 课）。

### 为什么要无状态？运维上的回报
会话是*基础设施*必须保存的状态。有会话时，请求必须到达持有该会话的那个服务器实例。这意味着需要粘性负载均衡，或者在所有实例背后放一个共享的会话存储，此外还需要某种机制来应对实例在会话中途宕机的情况。移除协议状态改变了部署模型：

- **水平扩展（Horizontal Scaling）与负载均衡。** 任何副本都能处理任何请求，所以一个普通的轮询负载均衡器（Round-robin Load Balancing）就能工作。Streamable HTTP 传输还会把方法名和工具名镜像到请求头中（`Mcp-Method`、`Mcp-Name`），让网关无需解析消息体就能路由和限流（第 2.3 课）。
- **Serverless 与自动扩缩容。** 一个只为一次请求而存在的函数就可以是一个完整的 MCP 服务器，因为除了你的应用有意存储的东西之外，没有任何东西需要在两次调用之间保留下来。
- **简单的故障恢复。** 在 stdio 上，如果服务器意外退出，客户端会重启它。*因为协议是无状态的，进行中的请求只是丢失了，可以对新进程重试。* 中断的 HTTP 响应流也是同样处理：用一个新 id 重新发出请求。
- **无需粘性路由的服务器到客户端交互。** 多轮往返请求（MRTR）模式之所以存在，就是为了让征询（Elicitation）和采样（Sampling）*无需跨服务器实例的共享存储层，也无需有状态的负载均衡*就能工作。任何中间状态都以 `requestState` 的形式随请求本身一起传递。
- **可缓存性。** 因为列表结果不再因连接而异，它们可以带上 `ttlMs`/`cacheScope` 并被缓存，当范围为 `public` 时甚至可以被共享的中间层缓存。

代价是请求稍微变大一些（每条消息都带一个信封），以及对那些确实需要状态的服务器来说，设计上的责任更多了。

### 取代会话的机制：服务器生成的句柄
很多工具天生就是有状态的：购物车、一个打开的浏览器页面、一个数据库事务。工具页面给出了非规范性的指导：*由一个创建类工具返回一个显式的句柄，并在后续调用中把该句柄作为参数接收。* 从线路的角度看，句柄（Server-minted Handle）只是结果中的一个字符串，之后又作为一个普通参数出现。协议本身并没有这个概念。

```jsonc
// → tools/call  create_basket {}
// ← structuredContent: {"basket_id": "bsk_a1b2c3"}
// → tools/call  add_item {"basket_id": "bsk_a1b2c3", "sku": "..."}
```

**模型**负责把 `basket_id` 带到后续调用中。**服务器**把购物篮以该键存储在每个实例都能访问的存储中（数据库、Redis、对象存储），并在每次调用时查找它。规范列出了四个设计关注点：

| 关注点 | 指导 |
| --- | --- |
| **授权** | 在需要认证的服务器上，句柄是一个*名称，而不是一项权限*：每次调用都要根据句柄检查调用方的授权。在无需认证的服务器上，句柄就是一个持有者令牌，所以要用足够的熵生成它（例如 UUIDv4），并给它设定有限的生命周期。 |
| **不透明性** | 编码了结构的句柄会招致解析和猜测。使用不透明的 id。 |
| **生命周期** | 句柄的寿命比连接更长，所以要在创建工具的描述中写明保留策略（“购物篮在 24 小时无活动后过期”），让模型能看到。 |
| **过期错误** | 使用过期或未知句柄的调用应当返回一个说明情况的**工具执行错误**（`isError: true`），这样模型可以通过创建一个新句柄来恢复。 |

与隐藏的会话相比，显式句柄还让状态在对话记录中变得可见。用户可以同时操作两个购物篮，另一个客户端（或一个恢复运行的智能体）也可以拿着同一个句柄继续工作。

### `server/discover`：告诉你一切的那一个调用
服务器**必须（MUST）**实现 `server/discover`。除了标准的 `_meta` 之外，它不接受任何参数：

```json
{"jsonrpc": "2.0", "id": "discover-1", "method": "server/discover",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"},
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

```json
{"jsonrpc": "2.0", "id": "discover-1",
 "result": {"resultType": "complete",
            "supportedVersions": ["2026-07-28"],
            "capabilities": {"tools": {}, "resources": {}},
            "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "ExampleServer", "version": "1.0.0"}},
            "instructions": "This server provides weather and resource utilities.",
            "ttlMs": 3600000, "cacheScope": "public"}}
```

**`DiscoverResult` 的字段：**

| 字段 | 是否必需 | 含义 |
| --- | --- | --- |
| `supportedVersions` | 是 | 服务器支持的协议版本。客户端应当从中选择一个用于后续请求。 |
| `capabilities` | 是 | `ServerCapabilities`：`tools`、`resources`（`subscribe`、`listChanged`）、`prompts`、`completions`、`logging`（已弃用）、`extensions`、`experimental` |
| `_meta["io.modelcontextprotocol/serverInfo"]` | SHOULD | `Implementation`：`name`、`version`，可选的 `title`、`description`、`websiteUrl`、`icons`。自行上报：用于展示和调试，绝不能用于行为或安全决策。 |
| `instructions` | 否 | 给 LLM 的关于如何使用该服务器的自然语言指导，例如用于系统提示词。它不应重复工具描述。 |
| `ttlMs`、`cacheScope` | 是 | 缓存提示，类似 HTTP 的 `max-age` 和 `public`/`private`。`0` 表示立即过期。`public` 允许共享的中间层缓存它。 |
| `resultType` | 是 | `"complete"` |

**何时调用它。** 它*对客户端来说是可选的*：客户端可以直接调用任何 RPC，并处理 `UnsupportedProtocolVersionError`。它在两种场景下很有用：

1. **展示服务器信息。** 一次请求就能返回身份、能力和版本。这比为了弄清有哪些东西而分别探测 `tools/list`、`prompts/list` 和 `resources/list` 要好。
2. **stdio 向后兼容探测（Backward-compatibility Probe）。** stdio 没有可以驱动回退的 HTTP 状态码，所以双时代客户端**应当（SHOULD）**先发送 `server/discover`（见下一节）。

由于结果可以缓存，客户端通常对每个服务器只发现一次（或每个 `ttlMs` 一次），而不是每个请求一次。

### 逐请求的版本协商
没有协商握手。*每个请求都携带自己的协议版本，服务器独立地接受或拒绝每个请求。*（在 HTTP 上，版本还会出现在 `MCP-Protocol-Version` 请求头中，且两者必须一致。）如果服务器没有实现所请求的版本，无论该版本是未知的，还是服务器选择不支持的已知版本，它都**必须（MUST）**以 `-32022` 作答：

```json
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32022, "message": "Unsupported protocol version",
           "data": {"supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01"}}}
```

客户端**应当（SHOULD）**从 `supported` 中挑选一个双方都支持的版本并**重试**，如果不存在这样的版本则报告错误。所以版本协商（Version Negotiation）在最坏情况下多花一次往返，而当版本本来就匹配时则没有任何额外开销。

### 与旧时代共存
真实的部署中混杂着**新版**服务器（2026-07-28 及以后，逐请求 `_meta`）、**旧版**服务器（2025-11-25 及更早，`initialize`），以及同时支持两者的**双时代实现（Dual-era Implementation）**。检测方式取决于传输：

- **stdio：** 以你首选的新版本发送 `server/discover` 进行探测。收到 `DiscoverResult` 意味着是新版。收到*可识别的新版错误*（例如 `-32022`）也意味着是新版，所以要用列出的版本重试，**不要**回退。任何其他错误，或者直到超时都没有回应，则意味着是旧版，此时回退到 `initialize`。回退**不得（MUST NOT）**以某一个特定错误码为依据，因为旧版服务器对 `initialize` 之前的未知请求会返回各种各样的错误（`-32601`、`-32602`），或者干脆不回应。
- **Streamable HTTP：** 发送一个新版请求。收到 `400` 时检查消息体。可识别的新版 JSON-RPC 错误意味着是新版（修正请求即可）。消息体为空或无法识别则意味着是旧版，此时回退。

时代是**服务器**的属性，而不是请求的属性。客户端**应当（SHOULD）**按 stdio 进程或 HTTP 源缓存它，并且**可以（MAY）**在重启之间持久保存。双时代服务器根据客户端的开场方式选择行为。带有新版 `_meta` 的请求以无状态方式处理，而 `initialize` 则选择限定于该进程或会话的旧版语义。仅支持新版的服务器**应当（SHOULD）**在对 `initialize` 返回的错误中写明自己支持的版本，因为旧版客户端无法向前升级，而这条消息可能是用户能看到的唯一诊断信息。

> **陷阱。** 仅支持新版的客户端与旧版服务器对话时，可能会悄无声息地出错：有些旧版服务器不检查 `initialize` 是否发生过，会按旧版语义执行 `tools/call` 这类在两个时代含义不明确的方法。先用 `server/discover` 探测，就能把这种情况变成一个确定性的失败。

## Key points
- 2026-07-28 版 MCP 是**无状态（Stateless）**的。每个请求都携带处理它所需的一切，不会从同一连接上较早的请求中推断任何状态。
- **已移除：**`initialize`/`notifications/initialized` 握手、`Mcp-Session-Id` 会话和 `ping`。版本和能力随每个请求的 `_meta` 传递。
- 一个 stdio 进程或 HTTP 连接**不是会话（Session）**。客户端可以交错发送互不相关的请求，能力按请求逐一判断。
- 跨调用状态使用**显式的、由服务器生成的句柄（Server-minted Handle）**，由创建类工具返回，再作为工具参数传回。句柄应当在每次调用时校验授权、保持不透明、写明生命周期，并在过期时以可读的 `isError` 失败。
- 无状态使**轮询负载均衡（Round-robin Load Balancing）、serverless 和水平扩展**成为可能，恢复也很简单：重启并重试。
- 服务器**必须（MUST）**实现 `server/discover`。它返回 `supportedVersions`、`capabilities`、`instructions`、`_meta` 中的 `serverInfo`，以及缓存提示 `ttlMs`/`cacheScope`。
- 调用 `server/discover` 对客户端（Client）来说是**可选的**。它可用于展示服务器信息，也可作为 **stdio 向后兼容探测**。
- 不支持的版本会得到 `-32022`，并附带 `data.supported`/`data.requested`。客户端挑选一个双方都支持的版本重试。可识别的新版错误绝不会触发旧版回退。

## Pitches
### MCP 为什么变成了无状态？
会话让 MCP 服务器很难运维。每个请求都必须到达持有该会话的实例，这意味着要用粘性负载均衡或者共享会话存储，而一个实例崩溃就会打断对话。在 2026-07-28 中，每个请求都在 `_meta` 中携带自己的协议版本和能力（Capability），所以任何副本都能回答它。服务器可以放在普通的负载均衡器后面、以 serverless 方式运行、水平扩展（Horizontal Scaling），出了问题重启再重试就能恢复。应用真正需要的状态则改为显式的句柄。

### 没有会话，怎么在多次工具调用之间保持状态？
我会把状态显式化。一个创建类工具，比如 `create_basket`，返回一个不透明的、高熵的句柄（Server-minted Handle），后续的工具把这个句柄作为普通参数接收。模型负责把它带下去。服务器把数据存在每个实例都能访问的地方，每次调用都检查调用方的授权，在工具描述中写明生命周期，并在句柄过期时返回一个可读的 `isError` 结果，这样模型就能通过创建一个新的句柄来恢复。

### `server/discover` 是做什么用的？
它是能返回服务器全部信息的那一个请求：它支持的协议版本、它的能力（Capability）、`serverInfo` 中的身份，以及可选的给模型的说明，全都附带缓存提示。服务器必须实现它，但客户端不一定要调用它，因为版本不匹配可以在请求过程中直接处理。我用它来展示一个服务器提供了什么，而不必逐个探测列表端点；在 stdio 上，我还用它来探测，以区分新版服务器和旧版服务器。

## Interview
### 在 MCP 2026-07-28 中，“无状态”到底是什么意思？是不是说服务器不能有状态？
它的意思是**协议**不携带状态。服务器不得从较早的请求中推断能力（Capability）、版本或身份，即使它们在同一个连接上，也不得把相关的操作绑定到某个连接或进程。这**并不**意味着服务器是纯函数。服务器可以持有任意多的应用状态（数据库、缓存、购物车），只要每个请求都通过客户端传递的显式标识符**指明**它要操作的状态即可。像 `subscriptions/listen` 这样的长时存在的东西仍然是请求，其状态限定于该请求，而不是连接。

### 一个 2025 时代的服务器保存了一个按会话区分的“当前项目”变量，你会如何迁移它？
这个变量是隐式的会话（Session）状态，一旦请求落到不同的副本上，或者客户端交错进行多个对话，它就会出问题。我会添加 `open_project(...)`（或者复用一个已有的 id），让它返回一个不透明的 `project_id`；把 `project_id` 作为必需参数加到每一个原先使用隐式项目的工具上；并把项目上下文存放到以该 id 为键的共享存储中。每次调用时，我都根据该 id 校验调用方的授权，刷新一个在工具描述中写明的有限 TTL，并在查找失败时返回 `isError: true` 和“未知或已过期的项目，请调用 open_project”。额外的好处是，两个对话现在可以通过同一个连接分别操作两个项目。

### 讲一讲双时代客户端在连接一个未知的 stdio 服务器时会做什么。
它首先以自己首选的新版本发送 `server/discover`。结果有三种。收到 `DiscoverResult` 意味着服务器是新版，客户端从 `supportedVersions` 中挑一个版本继续。收到像 `-32022` 这样可识别的新版错误也意味着是新版，客户端用 `data.supported` 中的版本重试，**不**回退。任何其他错误，或者在超时时间内没有回复，意味着是旧版，客户端回退到 `initialize`。回退不能依赖某一个特定的错误码，因为旧版服务器的表现各不相同。客户端会在该服务器进程的整个生命周期内缓存这个判断结果。这整个过程就是向后兼容探测（Backward-compatibility Probe）。

### 在 `tools/call` 之前必须先调用 `server/discover` 吗？
不必。服务器**必须实现**它，但客户端**可以**调用它。客户端可以立即用自己首选的版本发送 `tools/call`。如果该版本不受支持，服务器会返回列出其版本的 `-32022`，客户端再重试。当你想展示能力（Capability）和身份、用 `instructions` 填充 LLM 系统提示词，或者在 stdio 上探测时代时，就值得调用 discover。它的结果带有 `ttlMs` 和 `cacheScope`，所以你可以缓存它，而不必重复调用。

### 陷阱题：客户端在同一个连接上发送了声明 `elicitation` 的请求 A 和没有声明的请求 B。请求 B 的工具需要征询。会发生什么？
请求 B 会以 `-32021 MissingRequiredClientCapability` 失败，并附带 `data.requiredCapabilities: {"elicitation": ...}`。服务器必须只根据 B 自己的 `_meta` 来判断 B。“客户端刚才还说它支持征询（Elicitation）”恰恰是无状态（Stateless）所禁止的跨请求推断。与此同时，请求 A 会得到一个要求进行征询的 `input_required` 结果。修复要在客户端进行：为每个请求声明它所需的能力，SDK 会在每次调用时自动加盖同一个信封，从而做到这一点。

### `DiscoverResult` 中的哪些字段值得宿主信任？
把 `supportedVersions` 和 `capabilities` 视为服务器的协议契约。它们决定发送哪个版本、调用哪些方法，不过客户端仍然要优雅地处理错误。`instructions` 是有用的模型上下文，但它是服务器编写的文本，所以要像对待任何不可信的提示词内容一样对待它（警惕提示注入（Prompt Injection））。`serverInfo`（名称、版本、图标）是**自行上报、未经验证的**。用它来展示、记录日志和调试，绝不能用它来改变行为或做安全决策。一个自称“official-github”的服务器什么也证明不了。

## Glossary
- Stateless protocol | 无状态协议 | 每个请求都包含处理它所需的全部信息的协议，因此不会从较早的请求中推断任何状态。
- Session (legacy) | 会话（旧版） | 由 `initialize` 建立的、限定于连接的状态，在 HTTP 上还包括 `Mcp-Session-Id`；在 2026-07-28 中已移除。
- `server/discover` | `server/discover`（服务器发现） | 必须实现的 RPC，返回服务器支持的版本、能力、身份、说明和缓存提示。
- `DiscoverResult` | 发现结果（`DiscoverResult`） | `server/discover` 的结果：`supportedVersions`、`capabilities`、`instructions`、`ttlMs`、`cacheScope`，以及 `_meta` 中的 `serverInfo`。
- Server-minted handle | 服务器生成的句柄 | 由创建类工具返回、再作为工具参数传回的不透明标识符，用于引用跨调用的状态。
- Version negotiation | 版本协商 | 逐请求选择协议版本；服务器以 `-32022` 拒绝不支持的版本，并列出可选版本。
- Modern / legacy / dual-era | 新版／旧版／双时代实现 | 分别使用逐请求 `_meta`（2026-07-28 及以后）、`initialize` 握手（2025-11-25 及更早），或两者兼有的实现。
- Backward-compatibility probe | 向后兼容探测 | 在 stdio 上先发送 `server/discover`，以便在回退到 `initialize` 之前区分新版服务器和旧版服务器。
- Horizontal scaling | 水平扩展 | 在负载均衡器后面添加相同的服务器副本；无状态使这无需粘性路由即可实现。

### 1. 手工调用 `server/discover`
我们把一个小型商店服务器（Server）作为子进程启动，并以原始 JSON 行的形式发送 `server/discover`。服务器为发现结果声明了缓存提示，所以你能看到由服务器设置的 `ttlMs` 和 `cacheScope`。

```python
import itertools
import json
import os
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
from pathlib import Path


def show(obj, limit=1200):
    text = json.dumps(obj, indent=2, ensure_ascii=False)
    print(text if len(text) <= limit else text[:limit] + "\n  ...")


workdir = Path(tempfile.mkdtemp())
(workdir / "shop_server.py").write_text(textwrap.dedent('''
    import json, os, secrets, sqlite3, sys, time
    from mcp.server import CacheHint, MCPServer
    from mcp.server.mcpserver.exceptions import ToolError

    INSTANCE = sys.argv[1]                       # which replica am I?
    DB = os.environ["SHOP_DB"]                   # storage shared by every replica
    mcp = MCPServer(f"shop-{INSTANCE}", version="1.0.0",
                    instructions="Create a basket with create_basket, then pass its basket_id to add_item.",
                    cache_hints={"server/discover": CacheHint(ttl_ms=3_600_000, scope="public")})

    _implicit_cart = []                          # per-process memory: the anti-pattern

    def db():
        conn = sqlite3.connect(DB)
        conn.execute("create table if not exists baskets (id text primary key, items text, expires real)")
        return conn

    @mcp.tool()
    def add_to_my_cart(sku: str) -> str:
        """ANTI-PATTERN: add to 'the' cart remembered by this process."""
        _implicit_cart.append(sku)
        return json.dumps({"served_by": INSTANCE, "cart": _implicit_cart})

    @mcp.tool()
    def create_basket() -> str:
        """Create an empty basket and return its basket_id. Baskets expire after 10 minutes of inactivity."""
        basket_id = "bsk_" + secrets.token_urlsafe(12)      # opaque, high entropy
        with db() as conn:
            conn.execute("insert into baskets values (?, ?, ?)", (basket_id, "[]", time.time() + 600))
        return json.dumps({"served_by": INSTANCE, "basket_id": basket_id})

    @mcp.tool()
    def add_item(basket_id: str, sku: str) -> str:
        """Add a product to a basket created by create_basket."""
        with db() as conn:
            row = conn.execute("select items, expires from baskets where id = ?", (basket_id,)).fetchone()
            if row is None or row[1] < time.time():
                raise ToolError(f"Unknown or expired basket {basket_id!r}. Call create_basket to start a new one.")
            items = json.loads(row[0]) + [sku]
            conn.execute("update baskets set items = ?, expires = ? where id = ?",
                         (json.dumps(items), time.time() + 600, basket_id))
        return json.dumps({"served_by": INSTANCE, "basket_id": basket_id, "items": items})

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

ENV = {**os.environ, "SHOP_DB": str(workdir / "shop.sqlite")}
ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "notebook", "version": "0.1"}}


class Replica:
    """One server process we talk to with raw JSON lines."""

    def __init__(self, name):
        self.name = name
        self.proc = subprocess.Popen([sys.executable, str(workdir / "shop_server.py"), name], env=ENV,
                                     stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.DEVNULL,
                                     text=True)
        self.inbox = queue.Queue()
        threading.Thread(target=lambda: [self.inbox.put(l) for l in self.proc.stdout], daemon=True).start()

    def send(self, message: dict, wait=10):
        self.proc.stdin.write(json.dumps(message) + "\n")
        self.proc.stdin.flush()
        return json.loads(self.inbox.get(timeout=wait))

    def rpc(self, id_, method, params=None, meta=ENVELOPE):
        return self.send({"jsonrpc": "2.0", "id": id_, "method": method, "params": {**(params or {}), "_meta": meta}})

    def close(self):
        self.proc.stdin.close()
        return self.proc.wait(timeout=10)


a = Replica("A")
discover = a.rpc("discover-1", "server/discover")
show(discover)
```

```python
d = discover["result"]

print("versions        :", d["supportedVersions"])
print("capabilities    :", sorted(d["capabilities"]))
print("instructions    :", d.get("instructions"))
print(f"cache           : fresh for {d['ttlMs'] / 1000:.0f}s, scope={d['cacheScope']!r} "
      "(public = a shared gateway may cache it)")
```

### 2. 逐请求的版本协商
没有握手：我们直接以一个服务器不认识的版本调用工具，读取 `-32022`，从 `data.supported` 中选出一个双方都支持的版本，然后重试。这就是规范所描述的客户端版本协商（Version Negotiation）逻辑，大约十行代码。

```python
CLIENT_VERSIONS = ["2099-01-01", "2026-07-28"]          # newest first


def call_with_negotiation(replica, method, params, preferred=CLIENT_VERSIONS[0]):
    version, attempt = preferred, 0
    while True:
        attempt += 1
        reply = replica.rpc(100 + attempt, method, params,
                            meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": version})
        if "error" in reply and reply["error"]["code"] == -32022:
            supported = reply["error"]["data"]["supported"]
            print(f"attempt {attempt}: {version} rejected; server supports {supported}")
            mutual = [v for v in CLIENT_VERSIONS if v in supported]
            if not mutual:
                raise RuntimeError("no mutually supported protocol version")
            version = mutual[0]
            continue
        print(f"attempt {attempt}: accepted at {version}")
        return reply


reply = call_with_negotiation(a, "tools/call", {"name": "create_basket", "arguments": {}})
print(reply["result"]["content"][0]["text"])
```

### 3. 任何副本都能作答：两个独立的进程
启动第二个进程 `B`。除了*应用*选择共享的数据库文件之外，它与 `A` 没有任何共享。一个轮询“负载均衡器”（Round-robin Load Balancing）把每个请求发给下一个副本。

```python
b = Replica("B")
balancer = itertools.cycle([a, b])
ids = itertools.count(1000)


def lb_call(tool, arguments):
    replica = next(balancer)
    reply = replica.rpc(next(ids), "tools/call", {"name": tool, "arguments": arguments})
    result = reply["result"]
    return replica.name, result["isError"], result["content"][0]["text"]


for _ in range(2):
    replica = next(balancer)
    info = replica.rpc(next(ids), "server/discover")["result"]["_meta"]["io.modelcontextprotocol/serverInfo"]
    print(f"discover via {replica.name}: {info}")
```

### 4. 把它弄坏：隐式的进程内状态
`add_to_my_cart` 把“那个”购物车保存在进程内存中，就像会话时代的服务器可能把它保存在会话（Session）里一样。在负载均衡器后面，用户的购物车被拆散到了不同的副本上：

```python
for sku in ["apple", "pear", "fig", "kiwi"]:
    name, is_error, text = lb_call("add_to_my_cart", {"sku": sku})
    print(f"via {name}: {text}")
```

没有哪个副本拥有完整的购物车，而协议中也没有任何东西能修复这个问题。服务器从进程推断了连续性，而这正是规范所禁止的。

### 5. 修复它：作为工具参数传递的服务器生成句柄
现在按照规范推荐的方式实现这个有状态的工作流。`create_basket` 生成一个不透明的 id，之后的每次调用都指明它。无论哪个副本处理调用，都能在共享存储中找到这个购物篮。这就是服务器生成的句柄（Server-minted Handle）。

```python
name, _, text = lb_call("create_basket", {})
basket_id = json.loads(text)["basket_id"]
print(f"created by {name}: {basket_id}")

for sku in ["apple", "pear", "fig", "kiwi"]:
    name, is_error, text = lb_call("add_item", {"basket_id": basket_id, "sku": sku})
    print(f"via {name}: {json.loads(text)['items']}")

name, is_error, text = lb_call("add_item", {"basket_id": "bsk_does_not_exist", "sku": "x"})
print(f"\nunknown handle via {name}: isError={is_error} -> {text}")
```

未知句柄的情况是一个**工具执行错误（Tool Execution Error）**（`isError: true`），其消息告诉模型如何恢复，这正是规范中“过期错误”指导所要求的。（在这个 SDK 中，抛出 `ToolError` 可以发送你自己的消息。任何其他异常都会被报告为一条通用的“Error executing tool …”。）

### 6. 能力按请求逐一判断，即使在同一个连接上
在**同一个**进程上发两个请求，一个声明了 `elicitation`，另一个没有。服务器不得把第一次的声明沿用到第二次。这就是能力（Capability）的逐请求判断。

```python
(workdir / "confirm_server.py").write_text(textwrap.dedent('''
    from typing import Annotated
    from pydantic import BaseModel
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Elicit, Resolve

    mcp = MCPServer("confirm")

    class Confirm(BaseModel):
        ok: bool

    def ask(basket_id: str):
        return Elicit(f"Empty basket {basket_id}?", Confirm)

    @mcp.tool()
    def empty_basket(basket_id: str, confirm: Annotated[Confirm, Resolve(ask)]) -> str:
        """Empty a basket after the user confirms."""
        return "emptied" if confirm.ok else "kept"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
confirm = Replica.__new__(Replica)
confirm.name = "confirm"
confirm.proc = subprocess.Popen([sys.executable, str(workdir / "confirm_server.py")], stdin=subprocess.PIPE,
                                stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
confirm.inbox = queue.Queue()
threading.Thread(target=lambda: [confirm.inbox.put(l) for l in confirm.proc.stdout], daemon=True).start()

args = {"name": "empty_basket", "arguments": {"basket_id": basket_id}}
with_cap = confirm.rpc(1, "tools/call", args, meta={**ENVELOPE, "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}})
without = confirm.rpc(2, "tools/call", args)
print("request 1 (declares elicitation):", with_cap["result"]["resultType"])
print("request 2 (declares nothing)    :", without["error"]["code"], without["error"]["message"][:60])
print("                                  ", without["error"]["data"])
```

### 7. 旧时代：在新进程上调用 `initialize`
这个 SDK 是**双时代（Dual-era）**的。如果一个 stdio 进程收到的第一个请求是 2025 风格的 `initialize`，整个进程都会以旧版语义提供服务，在它上面的新版请求会被拒绝。这就是为什么双时代的*客户端*要先用 `server/discover` 探测。

```python
old = Replica("legacy")
show(old.send({"jsonrpc": "2.0", "id": 1, "method": "initialize",
               "params": {"protocolVersion": "2025-11-25", "capabilities": {},
                          "clientInfo": {"name": "old-client", "version": "1.0"}}}), limit=600)
old.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "method": "notifications/initialized"}) + "\n")
old.proc.stdin.flush()
show(old.rpc(2, "server/discover"))
```

### 8. SDK 会替你完成这一切
`Client` 在默认的 `mode="auto"` 下会探测 `server/discover`，采用其结果，并在之后的每个请求上加盖信封（Per-request Envelope）。`mode="legacy"` 则强制使用旧的握手。对比一下：

```python
from mcp import Client, StdioServerParameters

params = StdioServerParameters(command=sys.executable, args=[str(workdir / "shop_server.py"), "C"], env=ENV)
async with Client(params) as client:
    d = client.session.discover_result
    print("auto  :", client.protocol_version, "| discover:", d.supported_versions, d.ttl_ms, d.cache_scope)
    print("        instructions:", client.instructions)
async with Client(params, mode="legacy") as client:
    print("legacy:", client.protocol_version, "| discover result:", client.session.discover_result)

for replica in (a, b, confirm, old):
    replica.close()
```
