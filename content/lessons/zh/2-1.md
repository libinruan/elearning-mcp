## Summary
剥开所有 SDK，MCP 其实只是三种 JSON-RPC 2.0 消息：**请求（Request）**、**响应（Response）**和**通知（Notification）**。2026-07-28 修订版在普通 JSON-RPC 之上增加了几条规则：id 永远不能为 `null`，每个结果都带有 `resultType`，每个请求都在 `params._meta` 中携带一个**信封（Per-request Envelope）**：协议版本、客户端能力（Capability）以及（可选的）客户端身份。本课涵盖消息的结构、`_meta` 键的命名规则与保留键（包括 OpenTelemetry 链路追踪上下文）、错误码分配策略以及 MCP 定义的三个错误码 `-32020`、`-32021` 和 `-32022`、MCP 如何使用 JSON Schema，以及 `icons` 字段。在 notebook 中，你会先构建一个消息校验器，然后从一个真实的服务器上逐一触发每种错误码。

## Lesson
### 三种消息，一种格式
规范说得很直白：*MCP 客户端与服务器之间的所有消息**必须（MUST）**遵循 JSON-RPC 2.0 规范。* JSON-RPC 有三种消息，MCP 对每种都加了几条规则。

| 类型 | 结构 | 在 2026-07-28 中由谁发送 | 是否有回复？ |
| --- | --- | --- | --- |
| **请求** | `jsonrpc`、`id`、`method`、`params?` | 只有**客户端** | 有：恰好一个响应 |
| **响应** | `jsonrpc`、`id`，以及 `result` 或 `error` 二者之一 | 只有**服务器** | 没有 |
| **通知** | `jsonrpc`、`method`、`params?`，**没有 `id`** | 任意一方 | 永远没有：接收方**不得（MUST NOT）**响应 |

“由谁发送”这一列是新增的。早期修订版允许服务器发送自己的请求（`sampling/createMessage`、`elicitation/create`、`roots/list`、`ping`）。在 2026-07-28 中，**服务器不得（MUST NOT）发起 JSON-RPC 请求，客户端也不发送响应**。当服务器需要从客户端获取某些东西时，它会改为返回一种特殊的结果（见下文的 `resultType`）。

**请求规则。**
- 请求（Request）**必须（MUST）**包含一个字符串或整数类型的 `id`。
- *与基础 JSON-RPC 不同*，id **不得（MUST NOT）**为 `null`。
- 该 id **不得（MUST NOT）**与发送方已发出、但尚未收到响应的任何其他请求的 id 相同。id 只需在进行中的请求之间保持唯一，正是这一点让响应（以及取消（Cancellation））能够匹配回正确的请求。

```json
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "add", "arguments": {"a": 2, "b": 3},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

**通知规则。** 通知（Notification）**不得（MUST NOT）**包含 `id`。省略 id 正是让一条消息成为通知的原因。例如 `notifications/progress`、`notifications/message` 和 `notifications/cancelled`。

### 响应与 `resultType`
**结果响应**（Response）**必须（MUST）**带有与其请求相同的 `id` 以及一个 `result` 对象。2026-07-28 新增规定：结果**必须（MUST）**包含一个 `resultType` 字符串，让客户端知道如何解析其余部分：

| `resultType` | 含义 |
| --- | --- |
| `"complete"` | 请求已完成，`result` 中包含最终内容。 |
| `"input_required"` | 服务器需要更多输入（一次征询、一次采样调用、根目录）。`result` 是一个带有 `inputRequests` 的 `InputRequiredResult`；客户端会携带 `inputResponses` 重试原始请求。这就是**多轮往返请求（Multi Round-Trip Request）**模式（第 5.3 课）。 |
| 由扩展定义 | 扩展**可以（MAY）**添加新值，但只能是通过能力声明公布过的值。 |

有两条规则对互操作性很重要。客户端不认识的 `resultType` **必须（MUST）**视为无效。**没有** `resultType` 的结果（来自较早修订版的服务器）**必须（MUST）**视为 `"complete"`。

```json
{"jsonrpc": "2.0", "id": 7,
 "result": {"resultType": "complete",
            "content": [{"type": "text", "text": "5"}], "structuredContent": {"result": 5},
            "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "calc", "version": "1.0.0"}}}}
```

**错误响应**带有一个 `error` 对象，其中包含整数 `code`、一个 `message`（模式中说它**应当（SHOULD）**是一句简洁的话）以及一个任意类型的可选 `data`。它**必须（MUST）**带上请求的 `id`，*除非*因为请求格式错误而无法读取 id。这就是为什么模式中 `JSONRPCErrorResponse.id` 是可选的，也是为什么解析错误会以 `"id": null` 发出。

### 三种消息模式
核心协议把这些消息组合成三种消息模式（Message Pattern），每一种传输（Transport）都要承载全部三种：

1. **请求与响应。** 服务器可以在响应之前发送限定于该请求的通知（进度、日志消息）。
2. **多轮往返请求（MRTR）。** 服务器以 `resultType: "input_required"` 作答，客户端带上所需的输入重试。
3. **订阅与通知。** 一个 `subscriptions/listen` 请求，其响应是一条长期存在的变更通知流。每条通知都带有 `io.modelcontextprotocol/subscriptionId` 标记。

### `_meta` 信封：逐请求的协议字段
由于 2026-07-28 是无状态（Stateless）的（第 2.2 课），不再有 `initialize` 握手来记住版本或能力。**每个请求都在** `params._meta` 中**携带它们**：

| 键 | 类型 | 是否必需 | 用途 |
| --- | --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | string | **是** | 本次请求的协议版本，例如 `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | `ClientCapabilities` | **是** | 客户端*在本次请求中*支持什么；`{}` 表示没有任何可选能力 |
| `io.modelcontextprotocol/clientInfo` | `Implementation` | 否（**应当（SHOULD）**发送） | 客户端名称和版本 |
| `io.modelcontextprotocol/logLevel` | `LoggingLevel` | 否 | 为本次请求开启日志通知（已弃用特性，第 2.4 课） |

> **规范规则。** 缺少必需字段的请求属于格式错误。服务器**必须（MUST）**以 `-32602`（Invalid params）拒绝它，在 HTTP 上状态码**必须（MUST）**为 `400 Bad Request`。

服务器**应当（SHOULD）**在每个结果的 `_meta` 中用 `io.modelcontextprotocol/serverInfo` 标识自己。`clientInfo` 和 `serverInfo` 都是**自行上报、未经验证的**。它们用于展示、日志和调试。实现**不应（SHOULD NOT）**根据它们改变行为，也**不应（SHOULD NOT）**把它们用于安全决策。

服务器**不得（MUST NOT）**依赖客户端在本次请求中没有声明的能力（Capability）。如果它需要某种能力（例如，某个工具必须向一个未声明 `elicitation` 的客户端征询确认），它**必须（MUST）**返回 `-32021` `MissingRequiredClientCapability`，并在 `data.requiredCapabilities` 中列出缺少的能力。在 HTTP 上这同样是 `400`。

### `_meta` 键的命名与保留键
`_meta` 是每个请求、结果和通知上都存在的唯一扩展点，因此规范为它的键规定了格式。一个键由可选的**前缀**加上一个**名称**组成：

- **前缀：** 以点分隔的标签，后接 `/`。每个标签以字母开头、以字母或数字结尾，中间可以是字母、数字或连字符。使用**反向 DNS**（`com.example/`，而不是 `example.com/`）。
- **名称：** 除非为空，否则以字母数字字符开头和结尾，中间可以包含 `-`、`_`、`.` 和字母数字。
- **保留：** 任何**第二个标签**为 `modelcontextprotocol` 或 `mcp` 的前缀都属于保留前缀（Reserved Prefix）。所以 `io.modelcontextprotocol/`、`dev.mcp/`、`org.modelcontextprotocol.api/` 和 `com.mcp.tools/` 都是保留的，但 `com.example.mcp/` 不是（它的第二个标签是 `example`）。

规范保留的键有：`progressToken`、上面四个逐请求字段、`io.modelcontextprotocol/subscriptionId`（用于来自 `subscriptions/listen` 流的通知），以及 `traceparent`、`tracestate` 和 `baggage`。实现**不得（MUST NOT）**对保留键的值做任何假设。官方扩展会在 `io.modelcontextprotocol/` 下添加更多键，第三方则使用自己的厂商前缀。

**OpenTelemetry 链路追踪上下文。** `traceparent`、`tracestate` 和 `baggage` 是前缀规则的一个明确例外。它们保留 W3C 的原始名称，以便与现有工具以及 MCP 的 OpenTelemetry 语义约定兼容，其值**必须（MUST）**遵循 W3C 链路追踪上下文（W3C Trace Context）和 W3C Baggage。传播 `traceparent` 可以让一条分布式链路从宿主的智能体循环出发，穿过 MCP 客户端，一直延伸到服务器的数据库调用。这也是已弃用的协议级日志的推荐替代方案。

```json
"_meta": {"traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01",
          "io.modelcontextprotocol/protocolVersion": "2026-07-28",
          "io.modelcontextprotocol/clientCapabilities": {}}
```

### 错误码与分配策略
对于一般性故障，MCP 复用标准的 JSON-RPC 错误码：

| 错误码 | 名称 | 在 MCP 中的典型原因 |
| --- | --- | --- |
| `-32700` | Parse error | 消息体不是合法的 JSON |
| `-32600` | Invalid request | 不是合法的请求对象（批量消息、被 POST 上来的响应、错误的信封） |
| `-32601` | Method not found | 未知的方法，或者受某项服务器未公布的能力限制的方法（HTTP：`404`） |
| `-32602` | Invalid params | 缺少 `_meta` 字段、未知的工具或提示模板、错误的游标、错误的日志级别、资源不存在 |
| `-32603` | Internal error | 服务器出现意外状况 |

JSON-RPC 把 `-32000` 到 `-32099` 保留给由实现定义的服务器错误。在 2026-07-28 中，MCP 对这个范围进行了**划分**：

| 子范围 | 状态 | 规则 |
| --- | --- | --- |
| `-32000` … `-32019` | 旧版 / 由实现定义 | 新错误码**不得（MUST NOT）**分配在这里，新实现**不应（SHOULD NOT）**使用它们，接收方**不得（MUST NOT）**假设其含义（`-32002` 除外）。 |
| `-32020` … `-32099` | **保留给 MCP 规范** | 只能发出规范定义的错误码，且只能用于其规定的含义。 |

规范定义了三个错误码：

| 错误码 | 名称 | 何时使用 | HTTP 状态码 |
| --- | --- | --- | --- |
| `-32020` | `HeaderMismatch` | Streamable HTTP 请求头（`MCP-Protocol-Version`、`Mcp-Method`、`Mcp-Name`、`Mcp-Param-*`）缺失、格式错误或与消息体不一致 | `400` |
| `-32021` | `MissingRequiredClientCapability` | 请求需要某项未声明的客户端能力；`data.requiredCapabilities` | `400` |
| `-32022` | `UnsupportedProtocolVersion` | 服务器不提供所请求的版本；`data: {supported: [...], requested}` | `400` |

来自早期修订版的错误码仍然保留，**不得（MUST NOT）**再发出。`-32002`（在 2025-11-25 及更早版本中表示资源不存在）已改为 `-32602`，不过客户端**应当（SHOULD）**仍然接受来自旧服务器的 `-32002`。`-32042`（需要 URL 征询，仅限 2025-11-25）已退役。这三个错误码在草案中曾短暂使用 `-32001`/`-32003`/`-32004`，在分配策略确立后才重新编号，所以你可能仍会在较旧的代码中看到旧编号。**纯本地**的错误（例如 SDK 自身的请求超时）没有规范错误码。要把它们明确地暴露出来，以免被误认为是对端发来的错误。你自己应用的错误码**应当（SHOULD）**完全位于 `-32768`…`-32000` 之外。

> **陷阱。** 工具执行失败通常**不是** JSON-RPC 错误。工具执行错误（Tool Execution Error）会以带有 `isError: true` 的正常结果返回，这样模型可以读到错误信息并重试。JSON-RPC 错误是针对协议错误（Protocol Error）的：错误的信封、未知的方法、错误的版本。

### MCP 如何使用 JSON Schema
工具的 `inputSchema`/`outputSchema` 以及征询表单都是 JSON Schema，并遵循以下规则：

- **默认方言：** 没有 `$schema` 的模式（Schema）就是 **JSON Schema 2020-12**。模式**可以（MAY）**声明其他方言（例如 draft-07）。实现**必须（MUST）**支持 2020-12，**应当（SHOULD）**在文档中说明支持的其他方言，并且**必须（MUST）**以返回错误的方式优雅地处理不支持的方言。
- 模式**必须（MUST）**在其声明的或默认的方言下是合法的。在 2026-07-28 中，`inputSchema` 和 `outputSchema` 可以使用任何 2020-12 关键字，`structuredContent` 可以是任意 JSON 值。
- **`$ref` 解析：** 实现**不得（MUST NOT）**自动解引用指向**网络 URI** 的 `$ref`。需要主动开启的获取模式**必须（MUST）**默认关闭，并且**应当（SHOULD）**使用主机白名单（至少拒绝回环、链路本地和私有地址）、超时、大小限制和日志记录。因无法解析外部 `$ref` 而失败的模式**应当（SHOULD）**被拒绝，而不是被当作宽松模式处理。否则，一个工具模式就可能变成服务端请求伪造（SSRF）的探针。
- **组合关键字**（`anyOf`、`oneOf`、`allOf`、`if`/`then`/`else`、`$defs`）**应当（SHOULD）**受到最大深度、子模式数量上限或时间预算的限制，以免恶意模式被用来对你的校验器发动拒绝服务攻击。

### `icons`
`Implementation`（服务器或客户端信息）、`Tool`、`Prompt` 和 `Resource` 都可以带有 `icons`：一个由 `{src, mimeType?, sizes?, theme?}` 组成的数组。`src` 是一个 HTTPS URL 或 `data:` URI，`sizes` 形如 `["48x48"]` 或 `["any"]`，`theme` 为 `"light"` 或 `"dark"`。渲染图标的客户端（Client）**必须（MUST）**支持 `image/png` 和 `image/jpeg`，**应当（SHOULD）**支持 `image/svg+xml` 和 `image/webp`。图标是一个攻击面，因此使用方**必须（MUST）**：

- 把图标元数据和图标字节都视为不可信；
- 只接受 `https:` 或 `data:` URI，拒绝 `javascript:`、`file:`、`ftp:`、`ws:` 以及应用自定义协议，也拒绝重定向到其他源；
- 获取图标时不带 cookie 或凭据；
- 防范超大图片以及内嵌脚本的 SVG；
- 根据魔数（magic bytes）检测真实类型，并使用严格的白名单。

它们还应当检查图标是否来自服务器自己的源。

## Key points
- MCP 消息就是 JSON-RPC 2.0：**请求（Request）**（带 `id`）、**响应（Response）**（`result` 或 `error`，`id` 相同）和**通知（Notification）**（没有 `id`，永远不会被回复）。
- 在 2026-07-28 中，只有**客户端（Client）发送请求**。服务器负责作答，可以发出限定于该请求的通知，并通过 `resultType: "input_required"` 请求输入。
- 请求 id 是字符串或整数，**永远不能是 `null`**，并且在发送方进行中的请求之间唯一。
- 每个结果都带有 `resultType`（`"complete"`、`"input_required"` 或已公布的扩展值）。如果缺失，就视为 `"complete"`。
- 每个请求都携带 `_meta`，其中**必需**包含 `io.modelcontextprotocol/protocolVersion` 和 `io.modelcontextprotocol/clientCapabilities`。缺失时的答复是 `-32602`（HTTP `400`）。`clientInfo`/`serverInfo` 未经验证。
- `_meta` 的键采用反向 DNS 的 `prefix/name` 形式。**第二个标签**为 `modelcontextprotocol` 或 `mcp` 的前缀属于保留前缀（Reserved Prefix）。`traceparent`/`tracestate`/`baggage` 是不带前缀的 OpenTelemetry 例外。
- `-32000…-32019` 是旧版的由实现定义范围，`-32020…-32099` 属于规范：**-32020 HeaderMismatch、-32021 MissingRequiredClientCapability、-32022 UnsupportedProtocolVersion**。
- 工具执行错误（Tool Execution Error）是 `isError: true` 的结果，而不是 JSON-RPC 错误。资源不存在已从 `-32002` 改为 `-32602`。
- JSON Schema 默认为 **2020-12**。永远不要自动获取网络 `$ref`，并限制组合关键字。图标是不可信输入：只允许 `https:`/`data:`，且获取时不带凭据。

## Pitches
### MCP 消息在线路上长什么样？
它就是普通的 JSON-RPC 2.0。客户端发送请求（Request），带有方法、参数和一个非空的 id。服务器用携带同一个 id 的结果或错误来作答，任何一方都可以发送没有 id、发出即不管的通知（Notification）。MCP 额外加的是一个信封：每个请求都在 `params._meta` 中带上自己的协议版本和客户端能力，每个结果都带有 `resultType`，这样客户端就知道它是最终结果，还是服务器需要更多输入。

### 讲讲 MCP 的错误码。
第一层是标准的 JSON-RPC 错误码：解析错误、无效请求、方法不存在、无效参数和内部错误。缺少信封字段或者工具不存在，返回的是 -32602。然后 MCP 对服务器错误范围做了划分。-32000 到 -32019 是旧版的、由实现定义的空间。-32020 往上保留给规范，规范在这里定义了请求头不匹配、缺少必需的客户端能力（Capability）和不支持的协议版本。普通的工具失败根本不算协议错误：它们会作为 `isError` 为 true 的结果返回。

### 为什么 `_meta` 要有键命名规则？
`_meta` 是每条消息上的扩展点（Extension），所以如果没有规则，各厂商和规范之间就会冲突。键的形式是反向 DNS 前缀、一个斜杠，再加上名称。任何第二个标签是 `modelcontextprotocol` 或 `mcp` 的前缀都保留给协议，所以我会把自己的数据放在类似 `com.acme/` 这样的前缀下。唯一有意为之的例外是 OpenTelemetry 的 `traceparent`、`tracestate` 和 `baggage`，它们保留 W3C 名称，这样标准的链路追踪工具就能跨越客户端到服务器这一跳正常工作。

## Interview
### MCP 对普通 JSON-RPC 2.0 做了哪些改动？
- 请求（Request）id **不能为 `null`**，并且必须在发送方进行中的请求之间唯一。
- 每个结果都必须带有 **`resultType`**：`"complete"`、`"input_required"`（多轮往返请求（MRTR））或某个扩展值。缺失则表示 `"complete"`，以保持向后兼容。
- 每个请求在 `params._meta` 中携带一个**逐请求信封（Per-request Envelope）**（协议版本和客户端能力，外加作为 SHOULD 的客户端信息），取代了握手。
- **方向受到限制**：服务器从不发起请求，客户端从不发送响应。
- **不使用批量消息。** Streamable HTTP 的 POST 消息体必须是单个请求或通知，stdio 则每行一条消息。
- 服务器错误范围有一套**分配策略**，`-32020…-32099` 归规范所有。

### 一个请求没有携带 `io.modelcontextprotocol/clientCapabilities`。服务器应该怎么做？为什么不直接假定为 `{}`？
它必须以 `-32602` Invalid params 拒绝该请求，在 HTTP 上还要返回 `400 Bad Request`。规范把缺少任何必需字段的请求称为*格式错误*。如果服务器去猜，它就是在推断客户端从未声明过的状态，而这恰恰是无状态（Stateless）所禁止的。这样做还会掩盖客户端的 bug。一个确实不支持任何可选能力的客户端会显式发送 `{}`。同样的逻辑引出了 `-32021`：如果处理请求需要，比如说，征询（Elicitation），而客户端没有声明它，服务器就返回 `MissingRequiredClientCapability` 并附上 `data.requiredCapabilities`，而不是硬着头皮去尝试。

### 什么时候故障是 JSON-RPC 错误，什么时候是 `isError: true`？
JSON-RPC 错误针对的是**协议层**检测到的问题：无法解析的 JSON、未知的方法、格式错误的参数或信封、不支持的版本、请求头不匹配、缺少能力。模型通常无法修复这些问题，它们交给客户端代码处理。**工具执行错误（Tool Execution Error）**，比如 API 故障、参数值的校验问题或者“没有这个客户”，会作为带有 `isError: true` 和可读错误信息的普通 `CallToolResult` 返回。宿主把它交给模型，让模型能够自我纠正。如果你把这些变成 JSON-RPC 错误，模型就永远看不到它们。

### 你想给每个 MCP 请求附上租户 id 和一条链路追踪。怎么做？
用 `_meta`。链路追踪上下文放在保留的、不带前缀的 `traceparent` 中（可选再加 `tracestate`/`baggage`），使用 W3C 格式。服务器的 OpenTelemetry 插桩会提取它，并把自己的 span 挂在客户端的 span 之下。租户 id 放在**我自己的反向 DNS 前缀**下，例如 `com.acme/tenant`，绝不能放在 `io.modelcontextprotocol/` 或 `dev.mcp/` 之下，因为它们是保留前缀（Reserved Prefix）。两点注意：`_meta` 是由客户端自行声明的，所以放在那里的租户 id 不构成授权（Authorization）（授权来自认证授权层）；另外在 HTTP 上，如果网关需要根据某个值进行路由，这个值应该放在一个工具参数中，并用 `x-mcp-header` 镜像出来（第 2.3 课）。

### 陷阱题：服务器返回错误码 `-32002`。这是什么意思？
在 2026-07-28 中，它本身没有任何含义。`-32000…-32019` 是旧版的由实现定义范围，接收方不得假设其含义，**唯独** `-32002` 例外。这个错误码在 2025-11-25 及更早版本中表示“资源不存在”，客户端**应当（SHOULD）**仍然接受来自旧服务器的这个错误码。新版服务器不得发出它：资源不存在现在是 `-32602`。所以正确的理解是“一个较旧的服务器在告诉我这个资源不存在”。类似地，`-32042`（需要 URL 征询）仅属于 2025-11-25，现已退役。

### 为什么规范禁止自动解引用工具模式中的远程 `$ref`？
工具模式（Schema）来自服务器，而服务器可能不可信。如果客户端的校验器去跟随 `"$ref": "http://169.254.169.254/latest/meta-data"`，恶意服务器就能让宿主去获取内部 URL（服务端请求伪造（SSRF）），泄露模式已被加载这一事实，或者让校验器挂起。所以网络 `$ref` 解析**默认关闭**。需要主动开启的模式应当对主机做白名单，拒绝回环、链路本地和私有地址段，并施加超时和大小限制。无法解析的引用会使模式无效，而不是变成“接受任何东西”。出于同样的原因，组合关键字也要有深度和规模预算。

## Glossary
- JSON-RPC 2.0 | JSON-RPC 2.0 远程过程调用协议 | 所有 MCP 消息使用的轻量级请求/响应/通知消息格式。
- Request | 请求 | 带有方法、参数以及一个非空字符串或整数 id 的消息，期望恰好得到一个响应。
- Notification | 通知 | 没有 id 的单向消息；接收方不得回复。
- `resultType` | 结果类型（`resultType`） | 每个结果上的必需字段，说明如何解析该结果：`"complete"`、`"input_required"` 或某个扩展值。
- `_meta` | 元数据字段（`_meta`） | 请求、结果和通知上的元数据对象，承载逐请求信封、进度令牌、链路追踪上下文和厂商数据。
- Per-request envelope | 逐请求信封 | 每个请求的 `_meta` 中必需的 `io.modelcontextprotocol/protocolVersion` 和 `clientCapabilities` 键（外加可选的 `clientInfo`）。
- Reserved prefix | 保留前缀 | 第二个标签为 `modelcontextprotocol` 或 `mcp` 的 `_meta` 键前缀，保留给协议使用。
- `HeaderMismatch` (-32020) | 请求头不匹配错误 | 当 Streamable HTTP 请求头缺失、格式错误或与请求体不一致时返回的错误。
- `MissingRequiredClientCapability` (-32021) | 缺少必需的客户端能力错误 | 当请求需要某项客户端未声明的能力时返回的错误。
- `UnsupportedProtocolVersion` (-32022) | 不支持的协议版本错误 | 当所请求的版本不受支持时返回的错误，其中列出服务器支持的版本。

### 1. 一个值得信赖的消息分类器
在和服务器对话之前，先把本课的规则写成代码。`inspect_message` 会对一个解码后的 JSON 对象进行分类，并列出它违反的每一条规则。我们会在服务器的真实回复上复用它。

```python
import json


def show(obj, limit=900):
    text = json.dumps(obj, indent=2, ensure_ascii=False)
    print(text if len(text) <= limit else text[:limit] + "\n  ...")


REQUIRED_ENVELOPE = ("io.modelcontextprotocol/protocolVersion", "io.modelcontextprotocol/clientCapabilities")


def inspect_message(msg: dict) -> tuple[str, list[str]]:
    """Return (kind, problems) for one decoded MCP / JSON-RPC message."""
    problems = []
    if msg.get("jsonrpc") != "2.0":
        problems.append('jsonrpc must be exactly "2.0"')
    has_id = "id" in msg
    if "method" in msg:
        kind = "request" if has_id else "notification"
        if has_id:
            rid = msg["id"]
            if rid is None:
                problems.append("request id MUST NOT be null (MCP rule, stricter than JSON-RPC)")
            elif isinstance(rid, bool) or not isinstance(rid, (str, int)):
                problems.append("request id must be a string or an integer")
            meta = (msg.get("params") or {}).get("_meta") or {}
            missing = [k for k in REQUIRED_ENVELOPE if k not in meta]
            if missing:
                problems.append(f"request envelope is missing {missing} -> server answers -32602")
    elif "result" in msg or "error" in msg:
        kind = "response"
        if "result" in msg and "error" in msg:
            problems.append("a response carries result OR error, never both")
        if "result" in msg:
            if msg.get("id") is None:
                problems.append("a result response must echo the request id")
            if "resultType" not in msg["result"]:
                problems.append("result lacks resultType (a client treats it as 'complete')")
        if "error" in msg and not isinstance(msg["error"].get("code"), int):
            problems.append("error.code must be an integer")
    else:
        kind = "invalid"
        problems.append("neither method nor result/error present")
    return kind, problems


ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "notebook", "version": "0.1"}}

samples = {
    "good request": {"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {"_meta": ENVELOPE}},
    "null id": {"jsonrpc": "2.0", "id": None, "method": "tools/list", "params": {"_meta": ENVELOPE}},
    "no envelope": {"jsonrpc": "2.0", "id": "a", "method": "tools/list"},
    "notification": {"jsonrpc": "2.0", "method": "notifications/progress",
                     "params": {"progressToken": "t", "progress": 1}},
    "old-style result": {"jsonrpc": "2.0", "id": 1, "result": {"tools": []}},
    "error": {"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "Method not found"}},
}
for label, msg in samples.items():
    kind, problems = inspect_message(msg)
    print(f"{label:<17} -> {kind:<12} {problems or 'OK'}")
```

### 2. `_meta` 键规则与保留前缀
实现规范中的键语法：一个可选的、以 `/` 结尾的反向 DNS 前缀，后接一个名称。当前缀的*第二个*标签是 `modelcontextprotocol` 或 `mcp` 时，该前缀就是**保留前缀（Reserved Prefix）**。

```python
import re

LABEL = r"[A-Za-z](?:[A-Za-z0-9-]*[A-Za-z0-9])?"
NAME = r"(?:[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)?"
KEY = re.compile(rf"^(?:(?P<prefix>{LABEL}(?:\.{LABEL})*)/)?(?P<name>{NAME})$")
OTEL_KEYS = {"traceparent", "tracestate", "baggage"}


def check_meta_key(key: str) -> str:
    m = KEY.match(key)
    if not m:
        return "INVALID"
    prefix = m.group("prefix")
    if prefix is None:
        return "OpenTelemetry exception (reserved, no prefix)" if key in OTEL_KEYS else "valid, unprefixed"
    labels = prefix.split(".")
    if len(labels) > 1 and labels[1] in ("modelcontextprotocol", "mcp"):
        return "RESERVED for MCP"
    return "valid, vendor prefix"


for key in ["io.modelcontextprotocol/protocolVersion", "dev.mcp/anything", "org.modelcontextprotocol.api/x",
            "com.mcp.tools/y", "com.example.mcp/tenant", "com.acme/tenant", "traceparent", "progressToken",
            "1bad.com/x", "com.acme/-name", "com.acme-/x"]:
    print(f"{key:<42} {check_meta_key(key)}")
```

注意 `com.example.mcp/tenant` **不是**保留的（它的第二个标签是 `example`），而 `com.mcp.tools/y` **是**保留的。

### 3. 一个错误码从何而来？
把分配策略写成代码，这样你一眼就能读懂任何错误码。

```python
MCP_DEFINED = {-32020: "HeaderMismatch", -32021: "MissingRequiredClientCapability",
               -32022: "UnsupportedProtocolVersion"}
JSONRPC_STANDARD = {-32700: "Parse error", -32600: "Invalid request", -32601: "Method not found",
                    -32602: "Invalid params", -32603: "Internal error"}


def explain_code(code: int) -> str:
    if code in JSONRPC_STANDARD:
        return f"JSON-RPC standard: {JSONRPC_STANDARD[code]}"
    if code in MCP_DEFINED:
        return f"MCP spec: {MCP_DEFINED[code]}"
    if -32019 <= code <= -32000:
        extra = " (old 'resource not found' - accept from legacy servers)" if code == -32002 else ""
        return "legacy implementation-defined range: assume nothing" + extra
    if -32099 <= code <= -32020:
        return "reserved for the MCP spec but undefined: a server MUST NOT emit it"
    if -32768 <= code <= -32000:
        return "JSON-RPC reserved range: do not use for app errors"
    return "application-defined (outside the JSON-RPC reserved range)"


for code in [-32700, -32602, -32020, -32021, -32022, -32002, -32001, -32042, -32050, -32500, -1, 4004]:
    print(f"{code:>7}  {explain_code(code)}")
```

### 4. 通过 stdio 从真实服务器触发每一种错误
现在，一个真实的 SDK 服务器（Server）作为子进程运行，我们用原始的 JSON 行与它对话。其中一个工具 `delete` 需要用户确认。它通过一个会发起征询（Elicitation）的解析器来声明这一点，因此服务器需要客户端具备 `elicitation` 能力。

```python
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "lab_server.py").write_text(textwrap.dedent('''
    from typing import Annotated
    from pydantic import BaseModel
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Elicit, Resolve

    mcp = MCPServer("error-lab", version="1.0.0")

    @mcp.tool()
    def add(a: int, b: int) -> int:
        """Add two integers."""
        return a + b

    @mcp.tool()
    def divide(a: float, b: float) -> float:
        """Divide a by b."""
        if b == 0:
            raise ValueError("division by zero")
        return a / b

    class Confirm(BaseModel):
        ok: bool

    def ask(target: str):
        return Elicit(f"Really delete {target}?", Confirm)

    @mcp.tool()
    def delete(target: str, confirm: Annotated[Confirm, Resolve(ask)]) -> str:
        """Delete something after the user confirms."""
        return f"deleted {target}" if confirm.ok else "kept"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "lab_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
inbox = queue.Queue()
threading.Thread(target=lambda: [inbox.put(line) for line in proc.stdout], daemon=True).start()


def send_raw(text: str, wait: float = 5.0):
    """Write one line to the server's stdin and return the next line it writes (or None)."""
    proc.stdin.write(text + "\n")
    proc.stdin.flush()
    try:
        return json.loads(inbox.get(timeout=wait))
    except queue.Empty:
        return None


def rpc(id_, method, params=None, *, meta=ENVELOPE):
    params = dict(params or {})
    if meta is not None:
        params["_meta"] = meta
    return send_raw(json.dumps({"jsonrpc": "2.0", "id": id_, "method": method, "params": params}))


reply = rpc(1, "server/discover")
show(reply)
print("classifier:", inspect_message(reply))
```

现在一次破坏一样东西，并把每个回复都交给两个辅助函数处理：

```python
def report(label, reply):
    if reply is None:
        print(f"{label:<34} -> (no reply)")
    elif "error" in reply:
        err = reply["error"]
        print(f"{label:<34} -> {err['code']} {explain_code(err['code'])}\n{'':<38}message: {err['message'][:90]}")
        if "data" in err:
            print(f"{'':<38}data: {json.dumps(err['data'])}")
    else:
        r = reply["result"]
        print(f"{label:<34} -> result resultType={r.get('resultType')!r} isError={r.get('isError')}")


report("unknown method", rpc(2, "tasks/list"))
report("missing _meta envelope", rpc(3, "tools/list", meta=None))
report("unsupported protocol version", rpc(4, "tools/list",
       meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": "1900-01-01"}))
report("needs undeclared elicitation", rpc(5, "tools/call", {"name": "delete", "arguments": {"target": "prod"}}))
report("tool raises (NOT a protocol error)", rpc(6, "tools/call", {"name": "divide", "arguments": {"a": 1, "b": 0}}))
```

仔细看最后两个。在没有声明 `elicitation` 的情况下调用 `delete` 会得到 **-32021**，`data.requiredCapabilities` 会准确地告诉客户端需要添加什么。抛出异常的工具（Tool）**不是** JSON-RPC 错误：它是一个带有 `isError: true` 的 `complete` 结果，宿主会把它展示给模型。

如果客户端*确实*声明了 elicitation，会发生什么？服务器不能再发送自己的 `elicitation/create` 请求（Request）（在 2026-07-28 中服务器从不发起请求），所以它以 `resultType: "input_required"` 作答：

```python
reply = rpc(7, "tools/call", {"name": "delete", "arguments": {"target": "prod"}},
            meta={**ENVELOPE, "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}})
result = reply["result"]
print("resultType:", result["resultType"])
show(result["inputRequests"])
print("requestState (opaque, echoed back on retry):", result["requestState"][:40], "...")
```

第 5.3 课会完成这次往返。眼下的重点是：`resultType` 告诉客户端如何解析 `result`。

最后是格式错误的 JSON-RPC。规范说，解析错误要以 `id: null` 作答，但这个 SDK 的 stdio 服务器会直接丢弃它无法解析、或者不符合 JSON-RPC 结构的行。**永远不要指望垃圾输入能得到回复。** 一定要使用客户端超时。

                    ("jsonrpc 1.0", json.dumps({"jsonrpc": "1.0", "id": 9, "method": "tools/list",
                                                "params": {"_meta": ENVELOPE}}))]:

### 5. 通过 Streamable HTTP 的同样错误，以及状态码
在 HTTP 上，每个错误还会对应一个 HTTP 状态码：信封、请求头和版本问题对应 `400`，未知方法对应 `404`。这里服务器在 `127.0.0.1` 上的一个后台线程中运行。

                                   log_level="warning"))
threading.Thread(target=uv.run, daemon=True).start()

    data = r.json()

### 6. `_meta` 透传：链路追踪上下文与厂商键
`Client.call_tool(..., meta=...)` 会把你的键合并进 SDK 构建的信封（Per-request Envelope）中。这个工具会原样回显收到的内容，让你看到 W3C 的 `traceparent` 和一个带厂商前缀的租户键与协议字段一起传递。

```python
from mcp import Client
from mcp.server.mcpserver import Context

echo = MCPServer("meta-echo")


@echo.tool()
def show_meta(ctx: Context) -> str:
    """Return the request's _meta exactly as the server received it."""
    return json.dumps(dict(ctx.request_context.meta or {}), indent=2, default=str)


async with Client(echo) as client:
    result = await client.call_tool("show_meta", {}, meta={
        "traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01",
        "com.acme/tenant": "tenant-42",
    })
    print(result.content[0].text)
    print("\nserverInfo in the result's _meta:", result.meta["io.modelcontextprotocol/serverInfo"])
```

SDK 为你填上了 `protocolVersion`、`clientCapabilities` 和 `clientInfo`。在服务器端，SDK 的 OpenTelemetry 中间件会从同一个 `_meta` 中读取 `traceparent`，用来确定其 span 的父级。
