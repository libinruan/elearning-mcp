## Lesson
### 为什么 2026-07-28 改变了生产环境中的 MCP
2026-07-28 修订版让远程 MCP 服务器（Remote Server）变成了“一个普通的 HTTP 工作负载”（路线图原话）。每个请求都是自包含的：它在 `_meta` 中携带 `io.modelcontextprotocol/protocolVersion` 和 `io.modelcontextprotocol/clientCapabilities`，服务器不得（MUST NOT）依赖同一连接上的先前请求，没有 `initialize` 握手，没有 `Mcp-Session-Id`，独立的 GET 流也没有了。服务器到客户端的交互在结果内部传递（MRTR，多轮往返请求），变更通知则在 `subscriptions/listen` 的响应流上流动。在 2025-11-25 中，一个水平扩展的服务器需要**粘性会话（sticky session）**或共享的会话存储；在 2026-07-28 中，任何副本都能应答任何请求。在面试和现有代码库中，这两种模式你都会遇到。

### 生产就绪清单
**1. 传输与部署**
- 一个端点，只用 POST。只支持新版的服务器应当（SHOULD）对 GET/DELETE 返回 `405`，忽略 `Mcp-Session-Id` 和 `Last-Event-ID`。
- 把副本放在一个**普通的轮询负载均衡器（Round-robin Load Balancing）**后面，不做亲和性。基于镜像出来的请求头 `Mcp-Method` 和 `Mcp-Name`（以及来自 `x-mcp-header` 的 `Mcp-Param-*`）做路由或限流，无需解析请求体。服务器必须（MUST）以 `400` 和 `-32020` 拒绝请求头与请求体不一致的请求；中间层只有在 `MCP-Protocol-Version` 是要求这种校验的版本时，才应当（SHOULD）信任镜像请求头。
- 剩下的状态必须**显式且共享**：句柄放在数据库里，MRTR `requestState` 的密钥环由所有副本共享（Notebook 第 7 节），如果你从多个副本提供变更通知，`subscriptions/listen` 背后还要有共享的发布/订阅。
- 代理：在 SSE 响应上发送 `X-Accel-Buffering: no`，在长连接的 listen 流上发送 `:` 保活注释，并记住在 HTTP 上关闭一个请求的 SSE 流*就是*取消。
- 校验 `Origin`（无效则返回 `403`），并把本地服务器绑定到 `127.0.0.1`。

**2. 认证与授权**
- 远程服务器是一个 **OAuth 2.1 资源服务器（Resource Server）**：`401` 加 `WWW-Authenticate` → 受保护资源元数据（Protected Resource Metadata）→ 授权服务器（Authorization Server）（见 6.1 课）。
- 服务器**不得（MUST NOT）接受不是为它签发的令牌**（受众），也不得把客户端令牌透传给下游 API。网关用自己的凭据向后端认证，或者交换令牌（RFC 8693 令牌交换（Token Exchange）已列入路线图中的智能体身份议程）。
- 最小化权限范围；当某个特权工具首次被使用时，用带 `scope="..."` 的 `WWW-Authenticate` 质询进行递进授权（Step-up Authorization）。
- 企业场景：**企业托管授权（Enterprise-Managed Authorization）**扩展（`io.modelcontextprotocol/enterprise-managed-authorization`）让企业身份提供方（IdP）决定员工可以访问哪些服务器——客户端把用户的 ID 令牌换成一个 **ID-JAG**，再在 MCP 授权服务器上换成访问令牌。入职和吊销只需在 IdP 上做一次。
- 句柄是名字，不是凭据：把它们绑定到已认证的用户上。

**3. 机密**
- 凭据存放在宿主或网关中，绝不放进模型上下文或代码模式的沙箱（Sandbox）里。stdio 服务器从环境变量读取凭据。
- 表单模式征询（Form-mode Elicitation）不得（MUST NOT）收集机密；请使用 URL 模式。
- 把 `requestState` 密钥环放在机密管理器中，并分阶段轮换（Python SDK 接受 `keys=[new, old]`）。绝不要记录令牌；Notebook 的测试会在审计日志中搜索它们。

**4. 限流与配额**
工具规范指出，服务器**必须（MUST）**对工具调用进行限流。按用户或租户、按工具限流。在边缘层，返回 `429` 并带上 `Retry-After`。在 MCP 层内部，返回一个智能体可以据此采取行动的工具执行错误（Tool Execution Error）。如果有多个网关副本，要把计数器放在共享存储中，否则限额会成倍放大。

**5. 可观测性**
- `_meta` 为 **W3C Trace Context / Baggage** 保留了 `traceparent`、`tracestate` 和 `baggage`（OpenTelemetry 有针对 MCP 的语义约定）。把它们从宿主 → 网关 → 服务器一路传播下去，让一个 trace id 串起所有日志。在 2026-07-28 中，日志作为协议特性已被弃用（Deprecated Feature）：stdio 下写 stderr，并使用 OpenTelemetry。
- **每次工具调用一条审计记录**：用户、工具、结果、延迟、trace id。在指标中区分 `isError` 工具失败和 JSON-RPC 协议错误。
- 结果 `_meta` 中的 `serverInfo` 标识了每个响应对应的服务器版本。它适合调试，但 `clientInfo`/`serverInfo` 是自我声明的，不应当（SHOULD NOT）用来驱动安全决策。

**6. 缓存**
`server/discover`、各个 list 方法和 `resources/read` 都携带 `ttlMs` 和 `cacheScope`。`public` 结果可以被网关跨用户共享。`private` 结果不得（MUST NOT）跨授权上下文共享。因此按用户过滤的列表是 `private` 的（Notebook 中的网关就是如此）。`list_changed` 通知会让一个仍新鲜的缓存条目失效（Invalidation），而 MRTR 重试永远不会被缓存。不要把 TTL 变成轮询循环；如果必须轮询，就加上抖动和退避。路线图计划下一步引入 ETag。

**7. 版本管理与弃用**
版本协商（Version Negotiation）是逐请求进行的：不受支持的版本会得到 `400` + `-32022`，并带有 `data.supported`。需要访问握手时代服务器的客户端，先用一个新版请求探测，只有当 `400` 的响应体不是一个可识别的新版错误时，才回退到 `initialize`。持续关注弃用登记表。Roots、Sampling 和 Logging 在 2026-07-28 中被弃用（最早移除时间：2027-07-28 当天或之后的第一个修订版），同样被弃用的还有动态客户端注册（Dynamic Client Registration）（由客户端 ID 元数据文档取代）和旧的 HTTP+SSE 传输。重命名工具要遵循*新增 → 弃用 → 移除*，用 `list_changed` 宣布变更，并在迁移前后把 TTL 设短。

**8. 测试**
在进程内对服务器做单元测试（`Client(server)`），对 HTTP 接口做契约测试（Contract Test）（Notebook 的冒烟测试：`401`、`-32020`、`403`、`405`、`-32601`），用脚本化规划器运行智能体工作流（见 8.1 课），并在并发下做压力测试。SDK 分级是依据一致性测试套件来评定的。手动调试使用 Inspector。

**9. 发布**
在负载均衡器后面使用金丝雀发布（Canary Rollout）（无状态让它变得轻而易举），按角色用特性开关上线新工具，分阶段推进密钥轮换。关注错误率、p95 延迟和限流计数器，并保留一条不会让句柄或封装状态失效的回滚路径。

### 如何回答 MCP 系统设计题
面试官对结构的打分和对内容的打分一样多。用六个步骤，并且要大声说出来：**（1）需求**——用户、规模、延迟、危险操作；**（2）架构**——宿主（Host）、网关、服务器、身份提供方（Identity Provider）；**（3）协议选择**——传输、原语（Primitive）、MRTR、缓存、扩展（Extension）；**（4）扩展**——无状态、缓存、热点路径；**（5）安全**——认证、最小权限、注入、审计；**（6）权衡**，以及你下一步会做什么。

### 例题 A——“为 5,000 名员工和 200 个内部工具设计一个企业级 MCP 网关”
1. **需求。** 单点登录、按角色访问、集中吊销、满足合规的审计、约 30 个团队的约 200 个工具、p95 额外开销低于 50 ms，任何团队都不能搞坏另一个团队。
2. **架构。** 智能体宿主（IDE、聊天、内部智能体）→ 一个 **MCP 网关（MCP Gateway）**（负载均衡器后面的无状态副本）→ 各团队自有的 MCP 服务器。一个工具注册表（所有者、风险等级、模式）为网关提供数据。企业 IdP 签发身份。
3. **协议选择。** 全部使用 Streamable HTTP。采用企业托管授权（Enterprise-Managed Authorization），让 IdP 决定用户可以访问哪些服务器（ID-JAG → 访问令牌）。网关对宿主而言是 OAuth 资源服务器，对后端而言是一个持有自己受众绑定凭据的客户端。工具带命名空间。按用户过滤的 `tools/list`，并标记 `cacheScope: "private"`。高风险工具使用 MRTR 征询（Elicitation）。
4. **扩展。** 网关副本是无状态的。按 `ttlMs` 缓存后端工具目录，并在收到 `list_changed` 时失效。对后端连接做连接池。限流计数放在共享存储中。200 个工具太多，无法全部注入上下文，所以宿主使用渐进式发现（Progressive Discovery）（`search_tools`），或者由网关提供这一能力。
5. **安全。** 按角色设置白名单，每次调用时再次检查。不做令牌透传。在 `_meta` 中携带 W3C 链路追踪，外加每次调用一条审计记录，发送到 SIEM。风险等级决定是否需要确认。来自团队服务器的工具描述要经过审查，因为注解是不可信的。
6. **权衡。** 中心网关既是瓶颈也是故障爆炸半径，所以要多可用区部署，并保持其逻辑精简。逐次调用的重新授权会增加延迟，所以要对授权决策做短暂缓存。另一种方案是宿主→服务器直连、只靠 IdP 策略，它更简单，但审计和限流控制更弱。

### 例题 B——“通过 MCP 把我们的 SaaS 产品开放给 AI 智能体”
1. **需求。** 客户的智能体（Claude、ChatGPT、各种 IDE、他们自己的智能体）对*他们自己*租户的数据进行操作。自助式接入、滥用防护、稳定的契约。
2. **架构。** 在现有公共 API 前面放一个位于 `https://api.example.com/mcp` 的远程 MCP 服务器（Remote Server），像任何无状态 HTTP 服务一样部署。把它登记到 MCP 注册中心（MCP Registry）。
3. **协议选择。** OAuth 2.1 授权码 + PKCE，配合**客户端 ID 元数据文档（Client ID Metadata Document）**（DCR 已被弃用）。细粒度的权限范围。为智能体设计工具，而不是一对一地包装端点（见 4.2 课）：任务级、分页、截断、带 `outputSchema`。记录用资源（Resource）表示。破坏性操作用 MRTR 确认。用 `x-mcp-header` 镜像出例如区域这样的参数，用于路由。
4. **扩展。** 无状态副本。多步骤工作使用句柄。如果 `tools/list` 对所有人都一样，就标为 `public` 并设较长的 TTL。按租户限流和配额。长时间运行的导出使用 Tasks 扩展。
5. **安全。** 受众绑定的令牌，不透传给内部服务，状态句柄绑定到租户，输出经过清洗（工具结果会流入别人的模型，可能把提示注入带出去），URL 处理防范 SSRF，完整的审计日志。
6. **权衡。** 更少但更丰富的工具，还是与 API 一一对应。版本管理纪律（新增 → 弃用 → 移除），因为你无法替客户升级他们的智能体。MCP 与普通 REST API 之争：两者都保留——MCP 增加了发现、认证发现和对智能体友好的结构。

### 例题 C——“我们的智能体调用 40 个工具，又慢又贵——修好它”
1. **先测量。** 用链路追踪（每次调用一个 `traceparent`）把时间拆分为模型延迟与工具延迟，把令牌（Token）拆分为工具定义、工具结果和推理三部分。
2. **工具定义。** 如果 40 多个模式（Schema）占用了很大一部分上下文，就使用**渐进式发现（Progressive Discovery）**。客户端指南建议在某个阈值（例如窗口的 1–5%）时切换，方式是 `search_tools` → 查看 → 执行，或者使用模型提供方原生的工具搜索。保持 `tools` 数组稳定（或者只用一个 `call_tool` 元工具），让提示缓存持续命中。
3. **工具结果。** 在服务器中分页和截断。把读取 → 转换 → 写入这样的链条移到沙箱中的**程序化工具调用（Programmatic Tool Calling）**（代码模式）里，让中间数据永远不进入上下文。在代理层执行逐次调用授权。
4. **往返次数。** 允许并行工具调用。按 `ttlMs` 缓存 `tools/list`。对已知服务器固定协议版本以跳过 discover 探测。复用 HTTP 连接池。
5. **模型选择。** 把子任务（工具选择、信息抽取）路由给一个小而快的模型。
6. **权衡。** 代码模式需要一个加固的沙箱。发现机制多了一跳，而且可能漏掉工具。缓存有陈旧的风险，而 `list_changed` 为此设定了边界。

## Key points
- 2026-07-28 的 MCP 是**无状态（Stateless）**的：每个请求都在 `_meta` 中携带版本和能力，因此副本可以放在**普通的轮询负载均衡器**后面，无需粘性会话。
- 剩下的状态必须显式且共享：**句柄（State Handle）**放在数据库中，**MRTR `requestState` 密钥环**跨副本共享，`subscriptions/listen` 使用共享的发布/订阅。
- 网关（MCP Gateway）基于 `Mcp-Method` / `Mcp-Name` 做路由和限流。服务器以 `400` + `-32020` 拒绝请求头与请求体不一致的请求。GET/DELETE 得到 `405`。
- 远程服务器是 OAuth 资源服务器（Resource Server）：受众绑定的令牌、**不做令牌透传**、最小权限范围加递进授权。企业再加上**企业托管授权（Enterprise-Managed Authorization）**（ID-JAG）。
- 在 `_meta` 中传播 **`traceparent` / `tracestate` / `baggage`**（W3C Trace Context），每次调用写一条审计记录，并使用 OpenTelemetry，而不是已弃用的 Logging 特性。
- `cacheScope: "private"`（缓存作用域）的结果不得（MUST NOT）跨授权上下文共享。按用户过滤的列表是 private 的。`list_changed` 会使其失效。
- 版本协商（Version Negotiation）是逐请求进行的（`-32022` 带 `supported`）。Roots、Sampling、Logging 和 DCR 在 2026-07-28 中被弃用。重命名工具要遵循新增 → 弃用 → 移除。
- 用六个步骤回答设计题：需求 → 架构 → 协议选择 → 扩展 → 安全 → 权衡。

## Pitches
### MCP vs. 函数调用 vs. 智能体间协议
函数调用（Function Calling）是模型 API 的一项特性：模型请求我的代码去运行一个我声明过的函数。MCP 标准化的是这些函数——以及资源和提示模板（Prompt）——从哪里来，这样任何宿主都能跨厂商使用任何服务器。像 A2A 这样的智能体间协议处理的是另一条边界：一个自主智能体（Agent）去发现另一个智能体，并把任务委托给它。实践中它们是组合使用的。一个智能体内部用函数调用，通过 MCP 获取它的工具和数据，还可能通过 A2A 把整个任务交给别的智能体。

### 既然协议是无状态的，MCP 服务器现在怎么扩展？
从 2026-07-28 开始，每个请求都在 `_meta` 里带着自己的协议版本和客户端能力，也没有握手和会话 id 了。所以我会像部署任何无状态（Stateless）HTTP 服务一样部署远程服务器：副本放在轮询负载均衡器（Round-robin Load Balancing）后面，按延迟自动扩缩容，不用粘性会话也能做金丝雀发布。剩下的状态都是显式的。句柄放进数据库，所有副本共享那把封装 MRTR 请求状态的密钥，通知的扇出用共享的发布/订阅。缓存提示让网关不碰服务器就能应答 list 请求。

### 什么时候你不会用 MCP？
如果集成只属于一个应用、一条代码路径，直接用函数调用（Function Calling）更简单：不需要额外的进程，也没有协议层面的东西。我也会避免把现有 API 一对一地包装起来，因为智能体需要的是任务级的工具，不是端点的镜像。对于硬实时或大批量数据搬运，直接的 API 或数据管道更合适。当工具必须在多个宿主之间复用、归另一个团队所有、需要集中治理，或者要提供给客户的智能体使用时，MCP 才真正物有所值。

## Interview
### MCP、函数调用和 A2A 这样的智能体间协议是什么关系？
它们位于不同的边界上。**函数调用（Function Calling）**发生在一个模型 API 内部：模型发出一个结构化请求，要调用应用声明过的某个函数。**MCP** 标准化的是 AI 应用与外部系统之间的边界：发现（`tools/list`）、调用（`tools/call`）、资源、提示模板、传输、授权和版本管理。它与模型无关，宿主（Host）会把 MCP 工具翻译成其模型所用的函数调用格式。**智能体间协议**（例如由 Google 发起、后来移交给 Linux 基金会的 A2A）处理的是自主智能体（Agent）*之间*的通信：发现一个智能体的能力并委托一整个任务，远端智能体对调用方保持不透明。它们是互补的，而不是竞争对手。

### 你要把一个 MCP 服务器放到负载均衡器后面。副本之间还需要共享什么吗？
协议状态不需要任何共享。每个 2026-07-28 请求都是自包含的，所以轮询负载均衡（Round-robin Load Balancing）就能工作，不需要粘性会话，也不需要会话存储。但还有三件事需要注意。**应用句柄**（草稿、购物车、事务）必须放在以用户和句柄为键的共享存储中。**MRTR `requestState`** 由服务器封装，所以每个副本都必须持有相同的密钥环，否则被路由到另一个副本的重试会被拒绝（Python SDK 的默认密钥是每进程一把）。而 **`subscriptions/listen`** 的扇出需要共享的发布/订阅，这样副本 A 上的变更才能到达副本 B 上的监听者。限流计数器也需要共享存储。

### 什么是令牌透传？为什么它被禁止？
令牌透传（Token Passthrough）是指 MCP 服务器接受客户端的令牌，却不检查它是不是*为本服务器*签发的，然后把它转发给下游 API。它破坏了受众边界：为其他服务签发的令牌可以被重放，下游的限流和审计看到的是错误的身份，一个被盗的令牌会把服务器变成数据外泄的代理。规则是 MCP 服务器**不得（MUST NOT）接受并非明确为其签发的令牌**。网关或代理用自己的凭据向下游认证，或者为下游受众获取一个新令牌（例如通过令牌交换）。它绝不转发用户的令牌。

### 你会如何追踪一个用户请求从宿主、经过网关、到达后端工具的全过程？
在 `_meta` 中使用 W3C 链路追踪上下文（W3C Trace Context）。宿主开启一条链路，在每个请求上发送 `traceparent`（可选地加上 `tracestate` 和 `baggage`）。网关以一个子 span 延续这条链路并转发给后端，后端也这样做。三者都在各自的审计记录中记下 trace id，这样在链路追踪后端里一次查询就能看到整条路径及其延迟分解。有一个坑：Python SDK 已经会提取和注入环境中的 OpenTelemetry 上下文，所以要配置一个真正的 `TracerProvider`，而不是手写 span id。另外，绝不要把机密放进 `baggage`。

### 一位同事把网关的 `tools/list` 响应标记为 `cacheScope: "public"`，TTL 为 10 分钟。而这个列表是按用户角色过滤的。哪里有问题？
`public` 意味着任何客户端、共享网关或代理都可以（MAY）把缓存的响应提供给*任何用户*。按用户或角色过滤的列表包含特定于用户的数据，所以共享缓存可能把 Ana 受限的列表展示给 Ben，更糟的是，把管理员的工具展示给所有人。按照缓存规范，随用户而变的结果必须是 `private` 的，它只能在同一个授权上下文中复用。还有两点：缓存作用域（`cacheScope`）不是访问控制，网关仍然必须在 `tools/call` 时再次检查权限。另外，`list_changed` 通知应当在 TTL 过期之前就让该条目失效。

### 什么时候你会建议一个团队*不要*构建 MCP 服务器？
- 这个集成只被一个应用的一条代码路径使用，进程内的函数调用（Function Calling）更简单。
- 工作内容是大批量或流式的数据搬运，或者是硬实时控制，直接的 API 或数据管道更合适。
- 计划是按端点逐个镜像现有的 REST API：工夫应该花在工具设计上，而不是包装上。
- 没有人能负责安全：认证、限流、审计，以及对工具描述的审查。

当工具必须在多个宿主和模型之间通用、由另一个团队拥有并做版本管理、需要集中治理（白名单、审计），或者要提供给客户的智能体使用时，MCP 才物有所值。

## Glossary
- MCP gateway | MCP 网关 | 位于众多 MCP 服务器前面的服务器：它认证调用方、过滤工具并加命名空间、执行策略并转发调用。
- Round-robin load balancing | 轮询负载均衡 | 依次把每个请求发给下一个副本，之所以可行，是因为 2026-07-28 的请求是自包含的。
- Token bucket | 令牌桶（限流算法） | 一种限流算法，允许突发流量达到某个容量上限，并以稳定速率补充令牌。
- W3C Trace Context | W3C 链路追踪上下文 | `traceparent`/`tracestate` 格式，在 MCP `_meta` 中被保留，用于把跨服务的 span 串成一条链路。
- `cacheScope` | 缓存作用域（`cacheScope`） | `public` 结果可以跨用户共享。`private` 结果只能在同一个授权上下文中共享。
- Token passthrough | 令牌透传 | 一种被禁止的反模式：接受并非为本服务器签发的令牌，并把它转发给下游。
- Audience validation | 受众校验 | 在接受访问令牌之前，检查它是否是为这个特定的资源服务器签发的。
- ID-JAG | 身份断言授权许可（ID-JAG） | 身份断言 JWT 授权许可（Identity Assertion JWT Authorization Grant），由企业 IdP 签发，使客户端能在集中策略下获取 MCP 访问令牌。
- Key ring rotation | 密钥环轮换 | 用最新的密钥封装，同时仍接受较旧的密钥，从而在不停机的情况下轮换机密。
- Canary rollout | 金丝雀发布 | 先把一小部分流量切到新版本，只有在其指标保持健康时才逐步扩大。

### 2. 轮询负载均衡器后面的两个副本
2026-07-28 服务器不保存任何按连接的状态，所以一个简单的**轮询（Round-robin）**负载均衡器就够了：不需要粘性会话，不需要 `Mcp-Session-Id` 亲和性。下面的负载均衡器把每个 POST 转发给下一个副本，并复制 MCP 请求头。同一个客户端，连续的调用，不同的副本——什么都不会坏。

```python
def round_robin_balancer(upstreams: list[str]) -> Starlette:
    ring, http = itertools.cycle(upstreams), httpx.AsyncClient(trust_env=False)
    hop_by_hop = {"host", "content-length", "connection"}

    async def proxy(request: Request) -> Response:
        upstream = next(ring)
        headers = {k: v for k, v in request.headers.items() if k.lower() not in hop_by_hop}
        r = await http.request(request.method, upstream, content=await request.body(), headers=headers)
        keep = {k: v for k, v in r.headers.items() if k.lower() in ("content-type", "www-authenticate")}
        return Response(r.content, status_code=r.status_code, headers=keep)

    return Starlette(routes=[Route("/mcp", proxy, methods=["POST", "GET", "DELETE"])])
```

### 3. 网关：一个统一入口，策略居中
网关（MCP Gateway）本身是一个 MCP 服务器（基于低层 `Server` 构建，因此可以原封不动地透传后端的模式），同时也是每个后端的 MCP 客户端。在每个请求上，它会：

1. **认证** Bearer 令牌（SDK `token_verifier` → 否则返回 `401` + `WWW-Authenticate`）；
2. 只列出用户**角色允许**的工具，并标记 `cacheScope: "private"`，因为这个列表因用户而异；
3. 在 `tools/call` 时再次检查**白名单**，并应用按用户的**令牌桶限流**；
4. 延续调用方的**链路**（`_meta` 中的 `traceparent`）或开启一条新链路，并向后端发送一个子 span；
5. 用它**自己的服务令牌**转发，绝不使用用户的令牌；
6. 每次调用写一条**结构化审计记录**（一行 JSON）。

```python
USERS = {   # gateway access tokens -> (user, role); a stand-in for the enterprise IdP
    "tok-ana": ("ana", "support"),
    "tok-ben": ("ben", "sales-admin"),
    "tok-load": ("loadbot", "support"),
}
ROLE_TOOLS = {
    "support": {"kb__search_kb", "crm__lookup_customer"},
    "sales-admin": {"kb__search_kb", "crm__lookup_customer", "crm__update_tier"},

RATE = {"default": (5, 5.0), "loadbot": (200, 500.0)}   # (burst capacity, refill tokens per second)
BACKENDS = {"kb": (KB_URL, "svc-gw-kb-1f9c"), "crm": (CRM_URL, "svc-gw-crm-77ab")}
AUDIT_FILE = WORKDIR / "audit.jsonl"
AUDIT: list[dict] = []

    async def verify_token(self, token: str) -> AccessToken | None:
        if token not in USERS:
            return None
        user, role = USERS[token]
        return AccessToken(token=token, client_id="agent-host", subject=user, scopes=["mcp"],
                           claims={"role": role}, resource=GW_URL)


class TokenBucket:
    def __init__(self, capacity: int, refill_per_s: float):
        self.capacity, self.refill, self.tokens, self.t = capacity, refill_per_s, float(capacity), time.monotonic()

    def take(self) -> float:
        """0.0 if allowed, else seconds until a token is available."""
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.t) * self.refill)
        self.t = now
        if self.tokens >= 1:
            self.tokens -= 1
            return 0.0
        return (1 - self.tokens) / self.refill


BUCKETS: dict[str, TokenBucket] = {}
CATALOG = {"tools": None, "fresh_until": 0.0}


POOLS: dict[str, httpx2.AsyncClient] = {}       # one pooled HTTP client per backend (keep-alive connections)


def backend_client(name: str) -> Client:
    url, service_token = BACKENDS[name]
    if name not in POOLS:                          # created lazily, inside the gateway's event loop
        POOLS[name] = httpx2.AsyncClient(headers={"Authorization": f"Bearer {service_token}"}, trust_env=False,
                                         limits=httpx2.Limits(max_connections=50))
    # mode pins the version: no server/discover probe per call (the gateway already knows its backends).
    # A Client is cheap and stateless here: open one per call; the pooled HTTP client reuses connections.
    return Client(streamable_http_client(url, http_client=POOLS[name]), mode="2026-07-28")


async def backend_catalog() -> dict[str, types.Tool]:
    if CATALOG["tools"] is None or time.monotonic() > CATALOG["fresh_until"]:
        tools, ttl = {}, 3_600_000
        for name in BACKENDS:
            async with backend_client(name) as c:
                listing = await c.list_tools()
            ttl = min(ttl, listing.ttl_ms or 60_000)
            for t in listing.tools:
                tools[f"{name}__{t.name}"] = t.model_copy(update={"name": f"{name}__{t.name}"})
        CATALOG.update(tools=tools, fresh_until=time.monotonic() + ttl / 1000)
    return CATALOG["tools"]


def caller() -> tuple[str, str]:
    token = get_access_token()                      # set by the SDK's bearer-auth middleware
    return token.subject, token.claims["role"]


def child_trace(meta: dict) -> tuple[str, str | None, str]:
    """Continue an incoming W3C traceparent, or start a new trace. Returns (trace_id, parent_span, span)."""
    parts = str(meta.get("traceparent", "")).split("-")
    if len(parts) == 4 and len(parts[1]) == 32 and len(parts[2]) == 16:
        return parts[1], parts[2], secrets.token_hex(8)
    return secrets.token_hex(16), None, secrets.token_hex(8)


def audit(record: dict):
    AUDIT.append(record)
    with AUDIT_FILE.open("a") as f:
        f.write(json.dumps(record) + "\n")


async def gw_list_tools(ctx, params) -> types.ListToolsResult:
    user, role = caller()
    allowed = [t for name, t in (await backend_catalog()).items() if name in ROLE_TOOLS[role]]
    return types.ListToolsResult(tools=allowed, ttl_ms=60_000, cache_scope="private")


async def gw_call_tool(ctx, params) -> types.CallToolResult:
    user, role = caller()
    meta = dict(ctx.meta or {})
    trace_id, parent, span = child_trace(meta)
    record = {"ts": round(time.time(), 3), "user": user, "role": role, "tool": params.name,
              "trace_id": trace_id, "parent_span": parent, "span": span}
    started = time.perf_counter()

    def finish(outcome: str, result: types.CallToolResult) -> types.CallToolResult:
        record.update(outcome=outcome, ms=round((time.perf_counter() - started) * 1000, 1))
        audit(record)
        return result

    catalog = await backend_catalog()
    if params.name not in catalog:
        record.update(outcome="unknown_tool", ms=0.0)
        audit(record)
        raise MCPError(types.INVALID_PARAMS, f"Unknown tool: {params.name}")      # protocol error, per spec
    if params.name not in ROLE_TOOLS[role]:
        return finish("denied", types.CallToolResult(is_error=True, content=[types.TextContent(
            type="text", text=f"Role '{role}' may not call {params.name}.")]))
    wait = BUCKETS.setdefault(user, TokenBucket(*RATE.get(user, RATE["default"]))).take()
    if wait:
        return finish("rate_limited", types.CallToolResult(is_error=True, content=[types.TextContent(
            type="text", text=f"Rate limit exceeded; retry in {wait:.2f}s.")]))
    backend, _, tool = params.name.partition("__")
    # NOTE: the SDK client also injects the *ambient OpenTelemetry context* into outgoing _meta. When the caller
    # sent a traceparent, the SDK server middleware made it ambient, so that value wins over ours (section 4).
    forward_meta = {"traceparent": f"00-{trace_id}-{span}-01", "com.example.gateway/user": user}
    for key in ("tracestate", "baggage"):              # propagate the rest of the W3C context untouched
        if key in meta:
            forward_meta[key] = meta[key]
    async with backend_client(backend) as c:
        result = await c.call_tool(tool, params.arguments or {}, meta=forward_meta)
    record["backend"] = backend
    if isinstance(result.structured_content, dict) and "replica" in result.structured_content:
        record["replica"] = result.structured_content["replica"]
    return finish("tool_error" if result.is_error else "ok", types.CallToolResult(
        content=result.content, structured_content=result.structured_content, is_error=result.is_error))


gateway = Server("mcp-gateway", version="1.4.0", on_list_tools=gw_list_tools, on_call_tool=gw_call_tool)
serve(gateway.streamable_http_app(
    auth=AuthSettings(issuer_url="https://idp.example.com", resource_server_url=GW_URL,
                      validate_token_resource=True, required_scopes=["mcp"]),
    token_verifier=UserTokenVerifier()), GW_PORT)
print("gateway up at", GW_URL)
```

看看 CRM 收到的两个 `traceparent` 值。Ben 的请求携带的是网关的**子 span**——也就是我们的网关放进 `_meta` 的那个值。Ana 的请求携带的是她宿主的**原始 span id**，而不是网关的。为什么？Python SDK 内置了 OpenTelemetry：它的服务器中间件会把传入 `_meta` 中的 `traceparent` *提取*到环境上下文中，而它的客户端会把环境上下文*注入*到传出的 `_meta` 中，覆盖你传入的值。只安装了 OTel API 时（如这里），tracer 是空操作，所以注入的 span 就是调用方的那个。在生产环境中，你会安装带 `TracerProvider` 的 OTel SDK：这时 SDK 会创建真正的 `SERVER` 和 `CLIENT` span，而这种传播正是你想要的。无论哪种情况，**trace id** 都会端到端保留下来，而正是它把日志串在一起。

### 6. 压力测试：并发下的无状态
两个独立的智能体宿主各自通过网关发起 40 个并发调用。由于没有任何请求依赖于之前的请求，负载均衡器会把它们分散到两个 kb 副本上——而且**每个客户端都由两个副本共同服务**。我们还计算了延迟百分位数，也就是你会放到仪表盘上的那种数字。（这里所有八个服务器共享一个 Python 进程，所以绝对数值完全说明不了真实容量；重点在于分布和零错误数。）

### 7. 唯一一份共享状态：跨副本的 MRTR 密钥
无状态也有一个陷阱。`reindex` 返回一个 `InputRequiredResult`；重试携带一个 SDK **用密钥封装**的 `requestState`（请求状态）。默认情况下每个进程会生成自己的密钥（`RequestStateSecurity.ephemeral()`），所以当轮询负载均衡器把重试发给*另一个*副本时，它打不开这份状态。解决方法是配置，而不是粘性：给每个副本同一个密钥环。

```python
async def operator_says_yes(ctx, params):
    return types.ElicitResult(action="accept", content={"ok": True})


async def try_reindex(url: str) -> str:
    async with httpx2.AsyncClient(headers={"Authorization": "Bearer svc-gw-kb-1f9c"}, trust_env=False) as http:
        async with Client(streamable_http_client(url, http_client=http),
                          elicitation_callback=operator_says_yes, mode="2026-07-28") as kb:
            try:
                r = await kb.call_tool("reindex", {})
                return r.content[0].text
            except MCPError as exc:
                return f"MCPError {exc.code}: {exc.message}"


print("per-process keys :", await try_reindex(KB_URL))

SHARED_KEYS = [secrets.token_bytes(32)]           # in production: from a secret manager, rotated as a ring
shared = [serve(make_kb(n, request_state_keys=SHARED_KEYS).streamable_http_app(), free_port())
          for n in ("kb-c", "kb-d")]
KB2_PORT = free_port()
serve(round_robin_balancer(shared), KB2_PORT)
SERVICE_TOKENS["svc-gw-kb-1f9c"] = KB_URL          # (same audience: the replicas still verify against KB_URL)
print("shared key ring  :", await try_reindex(f"http://127.0.0.1:{KB2_PORT}/mcp"))
```

### 动手练习
1. **网关端缓存。** `backend_catalog()` 忽略了 `cacheScope`（缓存作用域）。让它遵守这一点：`public` 的后端列表为所有人缓存一份，而 `private` 的按用户作为缓存键（Cache Key）。如果你把一份 `private` 列表跨用户共享，会出什么问题？
2. **HTTP 原生限流。** 把令牌桶移到一个 Starlette 中间件里，在 MCP 层运行*之前*就返回 `429 Too Many Requests` 并带上 `Retry-After`。智能体宿主能得到什么？你又失去了什么（提示：模型不再能看到一条可读的工具错误）？
3. **分布式限流。** 在 `round_robin_balancer` 后面运行两个网关副本。为什么现在每个用户得到的突发额度是原来的两倍？勾勒出修复方案（使用 Redis 这样的共享存储，或者在负载均衡器上限流）。
