## Summary
有时服务器必须先问点什么，才能完成一个请求：“你确定要删除这个仓库吗？”、“用哪个 GitHub 账号？”、“请连接你的日历”。在 2026-07-28 中，这种对话遵循同一种模式：**多轮往返请求（Multi Round-Trip Requests，MRTR）**。服务器*返回*一个带有 `inputRequests` 和不透明 `requestState` 的 `InputRequiredResult`（需输入结果）。客户端收集答案，然后带着 `inputResponses` *重试*原始请求，而任何一个服务器实例都能完成这项工作。本课介绍该模式的确切规则、为什么 `requestState` 必须进行完整性保护，并深入讲解征询（Elicitation）：受限的表单模式（Schema）、用于密钥和第三方 OAuth 的 URL 模式（URL Mode）、accept/decline/cancel 模型，以及 `notifications/elicitation/complete` 被移除的原因。

## Lesson
### 为什么会有 MRTR
在早期修订版中，如果服务器在 `tools/call` 中途需要输入，它会向客户端发送**自己的 JSON-RPC 请求**（`elicitation/create`），并在原始请求保持未结束的状态下*等待*答案。这种设计是有代价的：

- 它需要一条**双向通道**，在用户作答的整个过程中保持打开，这可能长达数分钟。
- 等待中的服务器实例持有**内存中的状态**，因此负载均衡器必须把答案路由回*同一个*实例（粘性会话），而一次重启就会丢失这个问题。
- 它把每个服务器都绑定在 2026-07-28 已经移除的会话机制上。

MRTR（SEP-2322）把这个问题变成了一个普通的**结果**。变更日志说它“取代了以往由服务器发起请求的做法”，模式说明页面也说得很明确：服务器**必须（MUST）**对 `roots/list`、`sampling/createMessage` 和 `elicitation/create` 使用 MRTR，旧模式“不再受支持”，并且“这是一项破坏性变更”。设计目标也写得很清楚：不需要“跨服务器实例的共享存储层”，也不需要“有状态的负载均衡”。

```text
Client                                Server (any instance)
  │ tools/call id:1 {name, arguments}   │
  │────────────────────────────────────▶│ needs input
  │ result id:1 {resultType:"input_required", inputRequests, requestState}
  │◀────────────────────────────────────│ (request 1 is now FINISHED)
  │  …ask user…                          │
  │ tools/call id:2 {name, arguments, inputResponses, requestState}
  │────────────────────────────────────▶│ verify state, continue
  │ result id:2 {resultType:"complete", content…}
  │◀────────────────────────────────────│
```

### 核心类型
- **`resultType`**（结果类型）。2026-07-28 中的每个结果都携带它：普通结果为 `"complete"`，MRTR 中间结果为 `"input_required"`。对于较旧服务器返回的、省略了该字段的结果，客户端**必须（MUST）**将其视为 `"complete"`。
- **`InputRequests`**（输入请求映射）是一个从**服务器分配的字符串键**（在该请求内唯一）到请求对象的映射。每个值**必须（MUST）**是 `ElicitRequest`（`elicitation/create`）、`CreateMessageRequest`（`sampling/createMessage`）或 `ListRootsRequest`（`roots/list`）之一。
- **`InputResponses`**（输入响应映射）是一个使用**相同键**的映射，其值为客户端的结果：`ElicitResult`、`CreateMessageResult` 或 `ListRootsResult`。
- **`InputRequiredResult`**（需输入结果）包含可选的 `inputRequests` 和可选的 `requestState`，后者是一个“只对服务器有意义的不透明字符串”。两者中至少**必须（MUST）**有一个存在。

```json
{"jsonrpc": "2.0", "id": 2, "result": {
  "resultType": "input_required",
  "inputRequests": {"github_login": {"method": "elicitation/create", "params": {
      "mode": "form", "message": "Please provide your GitHub username",
      "requestedSchema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}}}},
  "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."}}
```

重试时会重复原始参数，并加上这两个字段：

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {
  "name": "get_weather", "arguments": {"location": "New York"},
  "inputResponses": {"github_login": {"action": "accept", "content": {"name": "octocat"}}},
  "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."}}
```

### 哪些请求支持它
| 客户端请求 | 是否可以返回 `InputRequiredResult` |
| --- | --- |
| `tools/call` | 是 |
| `prompts/get` | 是 |
| `resources/read` | 是 |
| 其他所有请求（`tools/list`、`server/discover`……） | **不得（MUST NOT）** |

### 服务器端规则
1. 服务器**可以（MAY）**用 `InputRequiredResult` 回答任何受支持的请求。
2. `inputRequests` 的键**必须（MUST）**在该请求内唯一，值**必须（MUST）**是三种请求类型之一。
3. `requestState` 可以使用任意编码：base64 JSON、加密的 JWT、二进制。
4. **`requestState` 是攻击者可控的输入。** 如果它会影响授权（Authorization）、资源访问或业务逻辑，服务器**必须（MUST）**保护其完整性（HMAC 或带关联数据的认证加密（AEAD）），并且**必须（MUST）**拒绝校验失败的状态。*只有*当篡改最多只会导致请求失败时，才可以省略完整性保护。
5. 为防止重放，服务器**应当（SHOULD）**在受保护的载荷中放入并校验：**已认证的主体**、**较短的过期时间**，以及**原始请求的标识符**（方法加上其关键参数的摘要）。这些措施能缩小重放窗口，但不能保证一次性使用。一次性操作**必须（MUST）**在服务器端强制保证这一不变量。
6. 每个 `InputRequiredResult` 都包含 `inputRequests` 和/或 `requestState`。
7. 永远不要发送客户端未声明的输入请求（没有 `elicitation` 能力就意味着不能发送 `elicitation/create`）。
8. 永远不要假定客户端一定会作答或重试。服务器**可以（MAY）**在重试时再次返回 `InputRequiredResult`，持续询问，直到拿到所需的全部信息。

### 客户端规则
1. 如果存在 `inputRequests`，客户端**必须（MUST）**在重试之前构建好响应。如果只有 `requestState`，客户端**可以（MAY）**立即重试。模式中给出的例子是*负载削减（Load Shedding）*，即服务器表示“带着这个状态稍后再来”。
2. **原样**回传 `requestState`。客户端不得检查、解析或修改它，如果服务器没有发送，也不得自行编造一个。
3. 重试时使用**新的 JSON-RPC `id`**。它是一个独立的请求。
4. `inputRequests`/`requestState` **只**适用于对该请求的重试，绝不适用于并行运行的其他请求。

**错误处理。** 服务器**应当（SHOULD）**校验 `inputResponses`。格式错误的数据或内部故障会得到 JSON-RPC 错误。未知的多余键**应当（SHOULD）**被忽略。如果必需的答案*缺失*，服务器**应当（SHOULD）**发送一个新的 `InputRequiredResult` 再次询问，而不是返回错误。当用户拒绝或客户端一侧出现故障时，客户端只需不再重试，因为“服务器并没有在等待响应”。

### 深入理解征询
**能力（Capability）。** 客户端在每个请求的 `_meta` 中声明 `"elicitation": {"form": {}, "url": {}}`。空的 `{}` 表示仅支持表单模式。声明了征询的客户端**必须（MUST）**至少支持一种模式，服务器**不得（MUST NOT）**使用客户端不支持的模式。

**请求参数。** 每个 `elicitation/create` 都有 `mode`（`"form"` 或 `"url"`；省略时表示表单）以及一条人类可读的 `message`。

**表单模式（Form Mode）**额外带有 `requestedSchema`，它被限制为**由基本类型构成的扁平对象**：

| 属性类型 | 允许的关键字 |
| --- | --- |
| 字符串 | `title`、`description`、`minLength`、`maxLength`、`format`（`email`、`uri`、`date`、`date-time`）、`default` |
| 数字 / 整数 | `title`、`description`、`minimum`、`maximum`、`default` |
| 布尔值 | `title`、`description`、`default` |
| 单选枚举 | 带 `enum` 的 `type: "string"`，或用于带标签选项的 `oneOf: [{const, title}]` |
| 多选枚举 | 带 `items.enum` 或 `items.anyOf: [{const, title}]` 的 `type: "array"`，以及 `minItems`、`maxItems` |

嵌套对象和对象数组“有意不予支持，以简化客户端的用户体验”。客户端使用该模式生成表单，**在发送前进行校验**，并预填默认值。

**URL 模式（URL Mode）**额外带有 `url`（一个有效的 URL）。它在 2025-11-25 中引入，并被标记为仍可能变化。当数据“*不得*经过 MCP 客户端”时使用它：API 密钥、付款、**第三方 OAuth**。这里的 `accept` 只表示用户*同意打开该 URL*，并不表示交互已经完成。客户端打开 URL 并重试，服务器（根据 `requestState` 或自己的存储）检查带外步骤是否已经完成。如果尚未完成，它会返回另一个 `InputRequiredResult`。客户端**应当（SHOULD）**为用户提供手动重试或取消的控件。

**响应动作（Elicitation Actions）。** `accept`（表单模式包含 `content`，URL 模式则省略）、`decline`（“拒绝”、“否”）和 `cancel`（关闭了对话框、按下了 Esc、页面加载失败）。服务器**必须（MUST）**处理拒绝、取消和客户端故障。常见做法是在拒绝时提供替代方案，在取消时稍后再问一次。

### 征询的安全
- **敏感数据**：服务器**不得（MUST NOT）**用表单模式索取密码、API 密钥、访问令牌（Token）或支付凭据，并且**必须（MUST）**对它们使用 URL 模式。姓名、邮箱和用户名可以由服务器自行决定是否在表单模式中索取，因为用户始终可以拒绝。
- **客户端界面**：客户端**必须（MUST）**显示是哪个服务器在提问，提供拒绝和取消选项，并允许用户检查和修改表单答案。
- **安全处理 URL（客户端）**：**不得（MUST NOT）**预先获取该 URL 或其元数据，**不得（MUST NOT）**在没有明确同意的情况下打开它，**必须（MUST）**先显示完整的 URL，并且**必须（MUST）**以客户端和 LLM 都无法检查的方式打开它（规范以 iOS 上的 SFSafariViewController 与 WKWebView 作对比）。客户端**应当（SHOULD）**突出显示域名，并对 Punycode 或其他可疑 URL 发出警告。
- **安全处理 URL（服务器）**：**不得（MUST NOT）**在 URL 中放入凭据或个人身份信息，**不得（MUST NOT）**发送预先认证的 URL，**应当（SHOULD）**使用 HTTPS，并且**不应当（SHOULD NOT）**在表单模式字段中放入可点击的 URL。
- **身份**：服务器**必须（MUST）**把征询绑定到客户端和用户身份上。它们绝不能信任用户自己输入的“我是 joe@example.com”。身份来自 MCP 授权（例如 `sub` 声明）。
- **网络钓鱼**：攻击者可以把一个 URL 模式链接转发给受害者，受害者完成 OAuth 流程后，令牌最终会被绑定到*攻击者的*账号上。服务器**必须（MUST）**验证打开该 URL 的人就是触发这次征询的用户。例如，先把用户引导到 `https://mcp.example.com/connect?...`，将其会话 cookie 中的主体与征询中的主体进行比对，确认一致后才重定向到第三方的授权端点。
- **通过 URL 模式进行的第三方 OAuth** 与 MCP 授权是两回事。第三方凭据**不得（MUST NOT）**经过客户端，服务器**不得（MUST NOT）**把客户端的令牌用于上游（令牌透传（Token Passthrough）），服务器要把第三方令牌与用户绑定后存储起来。这使服务器在这些令牌方面变成有状态的。

### 有状态性与被移除的完成通知
得益于 MRTR，征询（Elicitation）“不要求服务器维护状态”，因为 `requestState` 承载了上下文。如果服务器确实存储了状态（例如 OAuth 令牌），它**必须（MUST）**保护这些状态，并以从授权中得出的用户身份作为键。在 2025-11-25 中，URL 模式使用 `elicitationId` 和一条由服务器发送的 `notifications/elicitation/complete` 来表示“浏览器步骤已完成”。这两者都**在 2026-07-28 中被移除**了。无状态协议（Stateless Protocol）没有承载服务器发起信号的通道，客户端现在通过**重试**来获知结果。需要关联的服务器会把自己的标识符放进 `requestState`。

### Python SDK 如何实现 MRTR
- **服务器，声明式**：把工具参数标注为 `Annotated[T, Resolve(fn)]`，其中 `fn` 返回 `Elicit(message, Model)`、`Sample(...)` 或 `ListRoots()`。框架会把这些问题批量放进一个 `InputRequiredResult`，把答案存进 `requestState`，确保每个问题只问一次，并且只在所有问题都解决后才运行工具函数体。在 2025 年代的连接上，它则会发送真正的服务器到客户端请求。
- **服务器，手工实现**：从工具中返回 `types.InputRequiredResult(...)`，并在重试时读取 `ctx.input_responses` / `ctx.request_state`。你必须自己检查 `ctx.client_capabilities`。
- **`requestState` 的保护是自动的**：`MCPServer` 安装了一个 `RequestStateBoundary`，用 **AES-256-GCM** 把传出的状态封装在一个信封里，信封包含过期时间（默认 TTL 为 600 秒）、方法、目标、参数摘要、受众（服务器名称）和主体。它会在你的处理函数运行之前校验传入的状态。校验失败会返回 `-32602 "Invalid or expired requestState"`。默认密钥是临时的（每个进程一个），因此多实例部署需要传入 `RequestStateSecurity(keys=[shared_secret])`。
- **客户端**：`client.call_tool(...)` 会通过你的回调自动运行这个循环（最多 `input_required_max_rounds` 轮，默认 10 轮，对于只有状态的轮次会进行短暂退避）。`client.session.call_tool(..., allow_input_required=True)` 会把原始结果交给你，让你自己驱动循环，例如在重启之间持久化一个待回答的问题。

## Key points
- 多轮往返请求（MRTR）取代了服务器发起的请求：服务器**返回** `{"resultType": "input_required", "inputRequests", "requestState"}`，客户端以一个**新的 JSON-RPC id** 带着 `inputResponses` 和原样回传的 `requestState` **重试**。
- 只有 `tools/call`、`prompts/get` 和 `resources/read` 可以返回 `InputRequiredResult`（需输入结果）。输入请求仅限于 `elicitation/create`、`sampling/createMessage` 和 `roots/list`。
- `inputResponses`（输入响应映射）的键与 `inputRequests` 的键一一对应。`inputRequests`/`requestState` 中始终至少有一个存在，而只有状态的结果意味着“稍后带着它重试”。
- 把 `requestState`（请求状态）视为**攻击者可控的**。在重要场景下使用 HMAC/AEAD，并绑定主体、过期时间和原始请求。一次性使用必须在服务器端强制保证。
- 客户端逐字节回传 `requestState`，从不解析它。服务器对缺失的答案重新询问，而不是返回错误。
- 表单模式（Form Mode）的模式是由基本类型构成的扁平结构（string/number/integer/boolean/枚举）。密钥、付款和第三方 OAuth **必须**使用 URL 模式。
- 征询响应动作（Elicitation Actions）为 `accept` / `decline` / `cancel`。URL 模式中的 `accept` 只表示“用户同意打开该 URL”。
- `notifications/elicitation/complete` 和 `elicitationId` 已被移除。重试会告诉客户端结果，关联信息存放在 `requestState` 中。
- 由于状态随请求一起传递，任何服务器实例都能完成重试，因此不需要粘性路由，也不需要共享的会话存储，这正是水平扩展（Horizontal Scaling）的基础。

## Pitches
### 什么是 MRTR？MCP 为什么采用它？
多轮往返请求（MRTR）是 2026 年的 MCP 服务器在请求中途索取信息的方式。服务器不再自己向客户端发起请求然后干等，而是返回一个“需要输入”的结果，列出它需要什么，再附上一个不透明的状态数据块，原始请求到这里就结束了。客户端去问用户，然后带着答案和这个状态重试同一个调用。因为继续执行所需的一切都随重试一起传过来，任何一个服务器实例都能完成它，不需要粘性会话，也不需要共享的会话存储。

### 为什么 requestState 必须签名或加密？
请求状态（requestState）要经过客户端走一个来回，所以恶意客户端是可以修改它的。如果它里面写着要删除哪个仓库，或者哪个用户批准了一笔付款，那篡改它就等于提权。规范要求把它当作攻击者可控的输入，用 HMAC 或认证加密保护它的完整性，并把它绑定到用户、较短的过期时间和原始请求上，这样它就没法被拿到别处重放。Python SDK 会自动用 AES-GCM 做这件事。

### 你如何为破坏性工具构建一个安全的确认步骤？
我的删除工具在第一次调用时不会真的执行。它会返回一个表单模式的征询（Elicitation），要求用户输入资源名称，而删除目标保存在受保护的请求状态里。重试时，只有在明确的 accept 且输入的名称匹配时我才会执行。decline 和 cancel 会得到一个清楚的“什么都没删”，输错名称则会重新提问。宿主的界面会显示是哪个服务器在提问，所以单靠模型永远没法确认一次删除。

## Interview
### 请描述一个需要用户输入的 `tools/call` 的完整 MRTR 交互过程，包括 id。
客户端以 id 1 发送 `tools/call`。服务器对 id 1 回复 `result: {"resultType": "input_required", "inputRequests": {"confirm": {"method": "elicitation/create", "params": {...}}}, "requestState": "..."}`，请求 1 至此完成。客户端展示表单，然后发送一个**新的**请求 id 2，带有相同的 `name` 和 `arguments`，外加 `inputResponses: {"confirm": {"action": "accept", "content": {...}}}` 以及原样的 `requestState`。服务器校验状态、重建上下文，并以 `resultType: "complete"` 回答 id 2；如果仍然需要别的信息，则返回另一个 `InputRequiredResult`（需输入结果）。每个请求还都携带常规的 `_meta` 逐请求信封（Per-request Envelope），其中包括客户端能力。

### 如果服务器把 `{"repo": "acme/web", "approved": true}` 以普通 base64 形式放进 `requestState`，可能会出什么问题？
客户端可以解码并修改它，例如把仓库改成 `acme/prod`，或者在用户被询问之前就设置 `approved`，而服务器会基于伪造的数据执行操作。规范要求，只要状态会影响授权、资源或业务逻辑，就必须进行完整性保护（HMAC 或带关联数据的认证加密（AEAD）），并拒绝任何校验失败的状态。它还建议绑定主体、较短的 TTL 和原始请求（方法加参数摘要），以阻止跨用户和跨请求的重放。任何只能发生一次的操作（比如付款）都需要在服务器端记录已使用的令牌，因为一个有效的状态在其 TTL 内仍然可能被重放。

### 客户端收到一个只有 `requestState` 的 `InputRequiredResult`。它应该怎么做？
用新的 id 重试原始请求，原样回传该状态，并且不发送 `inputResponses`。规范允许客户端立即重试。模式中给出的例子是*负载削减（Load Shedding）*，即服务器表示“我很忙或者还在处理，带着这个稍后再来”。合理的客户端会在这样的轮次之间稍作退避，并限制总轮数。Python SDK 两者都做了：从 50 ms 到 250 ms 的指数退避，以及默认为 10 的 `input_required_max_rounds`。

### 征询什么时候必须使用 URL 模式？`accept` 在其中又是什么意思？
只要服务器需要密钥或凭据（密码、API 密钥、访问令牌、支付信息），或者需要用户通过 OAuth 授权服务器访问某个*第三方*服务，就必须使用 URL 模式（URL Mode）。在这些情况下，数据绝不能经过 MCP 客户端或 LLM 上下文。在 URL 模式中，`accept` 只表示用户**同意打开该 URL**。真正的交互在浏览器中、在带外进行。重试时，服务器检查自己的记录（通过 `requestState` 和用户身份作为键），然后要么完成，要么再次询问。它还必须验证完成浏览器流程的人就是同一个用户，以挫败把链接转发给受害者的网络钓鱼攻击。

### 为什么移除了 `notifications/elicitation/complete`？
它是一条由服务器发起的消息，用于告诉客户端某次 URL 模式交互已经完成，并通过 `elicitationId` 进行关联。在 2026-07-28 下，已经没有会话或反向通道来承载服务器发起的消息。MRTR 的重试本身就已经把答案告诉了客户端：重试，然后服务器要么完成，要么再次询问。因此这条通知及其 id 被移除了，需要关联的服务器会把自己的 id 编码进 `requestState`（请求状态）。

### 陷阱题：一个手写的工具向一个没有声明任何能力的客户端返回了征询。谁错了？你会如何发现这个问题？
是服务器错了。服务器**不得（MUST NOT）**发送客户端未声明的输入请求。SDK 层面的辅助工具（在 Python 中是 `Resolve(...)` 解析器）会检查这一点，并以 `-32021` MissingRequiredClientCapability（缺少必需客户端能力）失败。手工编写的 `return InputRequiredResult(...)` 绕过了这项检查，因此工具必须自己检查 `ctx.client_capabilities` 并进行回退，例如返回一个工具错误，说明“需要确认；该客户端无法询问用户”。用一个没有能力声明的客户端编写测试，就能发现这个问题。

## Glossary
- Multi Round-Trip Request (MRTR) | 多轮往返请求 | 2026-07-28 中的一种模式：服务器返回一个需要输入的结果，客户端带着所请求的输入重试原始请求。
- InputRequiredResult | 需输入结果 | 一种 `resultType: "input_required"` 的结果，携带 `inputRequests` 和/或 `requestState`。
- inputRequests | 输入请求映射 | 由服务器设定键的映射，包含客户端必须完成的 `elicitation/create`、`sampling/createMessage` 或 `roots/list` 请求。
- inputResponses | 输入响应映射 | 由客户端提供、键与 `inputRequests` 相同的映射，在重试的请求中携带各项结果。
- requestState | 请求状态（不透明令牌） | 由服务器生成、客户端原样回传的不透明字符串；它是攻击者可控的，因此在重要场景下必须进行完整性保护。
- AEAD | 带关联数据的认证加密 | 一种认证加密（例如 AES-GCM），既能保持状态的机密性，又能检测篡改。
- Form-mode elicitation | 表单模式征询 | 在带内收集扁平的、基本类型的、经模式校验的用户输入。
- URL-mode elicitation | URL 模式征询 | 在某个 URL 上进行的带外交互，用于密钥、付款和第三方 OAuth。
- Elicitation actions | 征询响应动作 | `accept`、`decline` 或 `cancel`：用户明确的选择或关闭对话框的操作。
- Load shedding | 负载削减（稍后重试） | 一种只有状态的 `InputRequiredResult`，告诉客户端稍后带着给定的状态重试。

### 1. 带确认关卡的破坏性工具（手工实现 MRTR）
我们显式地编写整个流程，让每个字段都清晰可见。`delete_repository` 在第一次调用时绝不会删除任何东西。它会：

- 检查客户端是否声明了表单模式征询（Form-mode Elicitation）（这是规范中的 MUST；手工编写的代码必须自己做这项检查），
- 返回一个 `InputRequiredResult`，要求用户**输入仓库名称**，
- 在重试时，只有在 `accept` 且名称匹配时才执行操作；输错时重新提问；对 `decline`/`cancel` 进行报告。

`ctx.request_state` 保存着我们上一轮生成的内容。SDK 会在传出时加密它，并在传回时校验它。

```python
import json
import logging

import mcp_types as types
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

logging.getLogger("mcp").setLevel(logging.CRITICAL)


def wire(model) -> str:
    return json.dumps(model.model_dump(by_alias=True, exclude_none=True, mode="json"), indent=2)


REPOS = {"acme/web", "acme/prod", "acme/docs"}
github = MCPServer("github-admin")


def confirm_request(repo: str, note: str = "") -> types.ElicitRequest:
    return types.ElicitRequest(params=types.ElicitRequestFormParams(
        message=f"{note}This permanently deletes {repo}. Type the full repository name to confirm.",
        requested_schema={"type": "object",
                          "properties": {"repo_name": {"type": "string", "title": "Repository name",
                                                       "minLength": 1, "maxLength": 100}},
                          "required": ["repo_name"]}))


@github.tool()
def delete_repository(repo: str, ctx: Context) -> str | types.InputRequiredResult:
    """Permanently delete a repository (asks the user to confirm first)."""
    if repo not in REPOS:
        return f"No such repository: {repo}"
    caps = ctx.client_capabilities
    if caps is None or caps.elicitation is None:
        return "Refused: deletion needs user confirmation, but this client cannot ask the user."

    answer = (ctx.input_responses or {}).get("confirm_delete")
    if answer is None:                                     # round 1, or the client sent nothing
        return types.InputRequiredResult(input_requests={"confirm_delete": confirm_request(repo)},
                                         request_state=json.dumps({"repo": repo, "round": 1}))
    state = json.loads(ctx.request_state)                  # already verified by the SDK
    if answer.action == "decline":
        return f"Not deleted: the user declined deleting {state['repo']}."
    if answer.action == "cancel":
        return "Not deleted: the confirmation was dismissed. Ask again later if needed."
    if (answer.content or {}).get("repo_name") != state["repo"]:
        return types.InputRequiredResult(              # spec: re-ask rather than error
            input_requests={"confirm_delete": confirm_request(repo, "The name did not match. ")},
            request_state=json.dumps({"repo": repo, "round": state["round"] + 1}))
    REPOS.discard(state["repo"])
    return f"Deleted {state['repo']} after {state['round']} confirmation round(s)."


print("tool registered; repos:", sorted(REPOS))
```

### 2. 自动循环：`Client(elicitation_callback=...)`
高层的 `call_tool` 看到 `input_required` 后，会把每个输入请求路由到我们的回调，并带着 `inputResponses` 和 `requestState` 重试，直到结果完成。这就是多轮往返请求（MRTR）的自动驱动。我们脚本化的“用户”会演示四种场景。

```python
answers = []


async def confirm_dialog(context, params):
    print(f"   [dialog from github-admin] {params.message}")
    action, typed = answers.pop(0)
    print(f"   [user] {action} {typed or ''}")
    return types.ElicitResult(action=action, content={"repo_name": typed} if typed else None)


scenarios = {"decline": [("decline", None)],
             "cancel": [("cancel", None)],
             "typo, then correct": [("accept", "acme/wbe"), ("accept", "acme/web")]}

async with Client(github, elicitation_callback=confirm_dialog) as client:
    for label, script in scenarios.items():
        answers[:] = script
        result = await client.call_tool("delete_repository", {"repo": "acme/web"})
        print(f"{label:>20} -> {result.content[0].text}\n")
print("repos now:", sorted(REPOS))
```

### 3. 手动驱动并阅读原始 JSON
`client.session.call_tool(..., allow_input_required=True)` 会返回中间结果，而不是自动解决它。如果要持久化一个待回答的问题（例如一个聊天在等一位去吃午饭的用户），之后再恢复，就是这样做的。然后我们自己构建 `inputResponses`，并带着**原样的** `requestState`（请求状态）重试。

```python
REPOS.add("acme/web")

async with Client(github, elicitation_callback=confirm_dialog) as client:
    first = await client.session.call_tool("delete_repository", {"repo": "acme/docs"}, allow_input_required=True)
    print("ROUND 1 result:\n", wire(first))
    saved_state = first.request_state                      # opaque: store it, never parse it
    key = next(iter(first.input_requests))

    responses = {key: types.ElicitResult(action="accept", content={"repo_name": "acme/docs"})}
    final = await client.session.call_tool("delete_repository", {"repo": "acme/docs"},
                                           input_responses=responses, request_state=saved_state,
                                           allow_input_required=True)
    print("\nROUND 2 result:\n", wire(final))
```

我们生成的 `requestState` 是 `{"repo": "acme/docs", "round": 1}`，但客户端看到的只有一个 `v1.…` 令牌。SDK 的 `RequestStateBoundary` 用 AES-256-GCM 把它连同过期时间、方法、工具名称、参数摘要以及作为受众（Audience）的服务器名称一起封装了起来。

### 4. 制造故障：篡改并重放 `requestState`
把客户端当作攻击者。我们 (a) 翻转令牌中的字符，(b) 在*另一个*仓库上重放一个有效的令牌，(c) 发送服务器从未生成过的状态。每一种都会在我们的处理函数运行之前被拒绝，而且返回相同的错误，让攻击者得不到任何信息。这就是状态句柄劫持（State Handle Hijacking）的防御。

```python
from mcp.shared.exceptions import MCPError

async with Client(github, elicitation_callback=confirm_dialog) as client:
    first = await client.session.call_tool("delete_repository", {"repo": "acme/web"}, allow_input_required=True)
    good = first.request_state
    yes = {"confirm_delete": types.ElicitResult(action="accept", content={"repo_name": "acme/prod"})}
    attacks = {"bit-flipped token": (good[:-6] + ("A" * 6 if not good.endswith("AAAAAA") else "B" * 6), "acme/web"),
               "replayed on another repo": (good, "acme/prod"),
               "forged plaintext state": (json.dumps({"repo": "acme/prod", "round": 1}), "acme/prod")}
    for label, (state, repo) in attacks.items():
        try:
            await client.session.call_tool("delete_repository", {"repo": repo}, input_responses=yes,
                                           request_state=state, allow_input_required=True)
            print(f"{label:>26}: ACCEPTED (bad!)")
        except MCPError as err:
            print(f"{label:>26}: {err.error.code} {err.error.message} {err.error.data}")
print("acme/prod still exists:", "acme/prod" in REPOS)
```

### 5. 线路上：通过 stdio 传输的原始 JSON-RPC
这一次，客户端一侧没有 SDK。注意观察 **id**（先是 1，然后是 2）、`resultType` 的取值，以及状态被逐字节回传。`_meta` 信封在*每个*请求上都声明了 `elicitation: {form: {}}`，这就是逐请求的能力协商（Capability Negotiation）。

### 6. 无状态的横向扩展：实例 A 提问，实例 B 完成
由于状态随请求一起传递，重试可以落到**另一个服务器实例**上，前提是它们共享封装密钥（并且使用相同的名称，因为名称是令牌的受众）。使用默认的每进程临时密钥时，实例 C 会拒绝 A 的令牌。这就是在负载均衡器后面配置 `RequestStateSecurity(keys=[...])` 的运维原因，也是水平扩展（Horizontal Scaling）的关键。较短的 TTL 还能演示过期。

```python
import secrets
import time

from mcp.server.request_state import RequestStateSecurity

SHARED_KEY = secrets.token_hex(32)


def make_instance(label, security):
    srv = MCPServer("transfers", request_state_security=security)

    @srv.tool()
    def transfer(amount: int, ctx: Context) -> str | types.InputRequiredResult:
        """Transfer money after the user approves the amount."""
        answer = (ctx.input_responses or {}).get("approve")
        if answer is None:
            return types.InputRequiredResult(
                input_requests={"approve": types.ElicitRequest(params=types.ElicitRequestFormParams(
                    message=f"Approve transfer of {amount} EUR?",
                    requested_schema={"type": "object", "properties": {"approve": {"type": "boolean"}},
                                      "required": ["approve"]}))},
                request_state=json.dumps({"amount": amount}))
        return f"instance {label}: transferred {json.loads(ctx.request_state)['amount']} EUR"
    return srv


a = make_instance("A", RequestStateSecurity(keys=[SHARED_KEY], ttl=2))
b = make_instance("B", RequestStateSecurity(keys=[SHARED_KEY], ttl=2))
c = make_instance("C", None)                                          # default: ephemeral per-process key
approve = {"approve": types.ElicitResult(action="accept", content={"approve": True})}

async with Client(a, elicitation_callback=confirm_dialog) as ca, Client(b) as cb, Client(c) as cc:
    pending = await ca.session.call_tool("transfer", {"amount": 50}, allow_input_required=True)
    done = await cb.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                      request_state=pending.request_state, allow_input_required=True)
    print("A asked, B finished ->", done.content[0].text)
    try:
        await cc.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                   request_state=pending.request_state, allow_input_required=True)
    except MCPError as err:
        print("A asked, C (own ephemeral key) ->", err.error.message)
    time.sleep(2.2)
    try:
        await cb.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                   request_state=pending.request_state, allow_input_required=True)
    except MCPError as err:
        print("after TTL, B ->", err.error.message)
```

同一个有效令牌在其 TTL *之内*仍然可以在 B 上被重放。真正的转账还需要在服务器端记录“已使用”，因为规范指出，协议层面的措施并不能保证一次性使用。

### 7. URL 模式：连接第三方日历，而密钥从不接触客户端
服务器需要获得某个第三方日历的 OAuth 授权。它发送一个 **URL 模式**征询（URL-mode Elicitation），并把一个流程 id 保存在 `requestState` 中。客户端的回调显示完整的 URL 和域名，征得同意后“打开浏览器”。我们的模拟浏览器通过直接调用服务器的回调端点来完成这个流程。客户端始终只返回 `{"action": "accept"}`。重试时，服务器在**自己的令牌存储**中查找这个流程（正如规范对第三方令牌所说的，这部分是有状态的），然后要么完成，要么再次询问。

```python
import uuid
from urllib.parse import parse_qs, urlparse

calendar = MCPServer("calendar")
PENDING_FLOWS: dict[str, str] = {}      # flow_id -> user (server-side, bound to the authenticated user)
TOKENS: dict[str, str] = {}             # user -> third-party token (never sent to the client)


def oauth_callback(flow_id: str):
    """What the server's https://.../connect route would do after the third-party redirect."""
    user = PENDING_FLOWS.pop(flow_id)
    TOKENS[user] = f"tp-token-{secrets.token_hex(4)}"


@calendar.tool()
def next_meeting(ctx: Context) -> str | types.InputRequiredResult:
    """Return the user's next meeting from their third-party calendar."""
    user = "user-123"                                           # in production: the `sub` from MCP authorization
    if user in TOKENS:
        return f"Next meeting: Design review at 15:00 (fetched with a token the client never saw)"
    if ctx.request_state:                                       # retried, but the browser flow isn't done yet
        flow_id = json.loads(ctx.request_state)["flow"]
    else:
        flow_id = uuid.uuid4().hex[:8]
        PENDING_FLOWS[flow_id] = user
    return types.InputRequiredResult(
        input_requests={"connect": types.ElicitRequest(params=types.ElicitRequestURLParams(
            message="Connect your calendar so I can read your meetings.",
            url=f"https://mcp.example.com/connect?flow={flow_id}"))},
        request_state=json.dumps({"flow": flow_id}))


async def url_consent(context, params):
    if params.mode != "url":
        return types.ElicitResult(action="decline")
    domain = urlparse(params.url).hostname
    print(f"   [consent] calendar server wants to open: {params.url}\n   [consent] domain: {domain} -> user approves")
    flow = parse_qs(urlparse(params.url).query)["flow"][0]
    oauth_callback(flow)                                         # stands in for the user finishing OAuth in a browser
    return types.ElicitResult(action="accept")                   # no content in URL mode

async with Client(calendar, elicitation_callback=url_consent) as client:
    first = await client.session.call_tool("next_meeting", {}, allow_input_required=True)
    print("input request:", wire(first.input_requests["connect"]))
    print("\nauto loop ->", (await client.call_tool("next_meeting", {})).content[0].text)
    print("client-visible data contained a token?", any("tp-token" in json.dumps(v) for v in [wire(first)]))
```

这里没有 `elicitationId`，也没有 `notifications/elicitation/complete`。重试本身*就是*完成信号。

### 8. 声明式的做法：由解析器负责簿记
对于大多数工具，你并不需要手工管理状态。一个 `Resolve(...)` 解析器（Resolver）返回 `Elicit(message, Model)`。SDK 会构建 `InputRequiredResult`，把答案记录在 `requestState` 中以确保每个问题只问一次，检查客户端的能力（缺失时返回 `-32021`），并且只在所有问题都解决后才运行函数体。这里的两个解析器意味着**一轮中有两个输入请求**。

```python
from typing import Annotated

from pydantic import BaseModel, Field

from mcp.server.elicitation import AcceptedElicitation, ElicitationResult
from mcp.server.mcpserver import Elicit, Resolve


class Environment(BaseModel):
    env: str = Field(json_schema_extra={"enum": ["staging", "production"]}, description="Target environment")


class Approval(BaseModel):
    approve: bool = Field(description="Approve this deployment?")


deployer = MCPServer("deployer")


def pick_env() -> Elicit[Environment]:
    return Elicit("Which environment?", Environment)


def approve(service: str) -> Elicit[Approval]:
    return Elicit(f"Deploy {service}? This restarts it.", Approval)


@deployer.tool()
def deploy(service: str,
           target: Annotated[Environment, Resolve(pick_env)],
           ok: Annotated[ElicitationResult[Approval], Resolve(approve)]) -> str:
    """Deploy a service after asking for the environment and an approval."""
    if isinstance(ok, AcceptedElicitation) and ok.data.approve:
        return f"Deployed {service} to {target.env}."
    return f"Deployment of {service} not approved ({ok.action})."


async def deploy_ui(context, params):
    props = params.requested_schema["properties"]
    content = {"env": "staging"} if "env" in props else {"approve": True}
    print(f"   [dialog] {params.message} -> {content}")
    return types.ElicitResult(action="accept", content=content)

async with Client(deployer, elicitation_callback=deploy_ui) as client:
    first = await client.session.call_tool("deploy", {"service": "api"}, allow_input_required=True)
    print("one round, input request keys:", list(first.input_requests))
    print((await client.call_tool("deploy", {"service": "api"})).content[0].text)

async with Client(deployer) as no_ui:
    try:
        await no_ui.call_tool("deploy", {"service": "api"})
    except MCPError as err:
        print("client without elicitation ->", err.error.code, err.error.message[:70])
```
