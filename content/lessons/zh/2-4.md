## Summary
MCP 的每个特性都由三种**消息模式（Message Pattern）**构成：请求/响应、多轮往返请求，以及订阅/通知。在它们之上，是真实系统从第一天起就需要的横切**实用功能（Utilities）**。**取消（Cancellation）**用于停止被放弃的工作：在 stdio 上是 `notifications/cancelled`，在 HTTP 上是客户端关闭流，超时也应触发取消。**进度（Progress）**让长时间运行的请求通过 `progressToken` 和 `notifications/progress` 报告完成了多少。**分页（Pagination）**用不透明游标（Opaque Cursor）拆分大型列表。**日志（Logging）**通过 `io.modelcontextprotocol/logLevel` 逐请求发送结构化日志行。日志在 2026-07-28 中已被**弃用（Deprecated）**，取而代之的是 stderr 和 OpenTelemetry。Notebook 会针对真实服务器逐一演练：进度回调、超时看门狗（Watchdog）、通过 stdio 取消、以每页三个的方式翻阅一个有 7 个工具的服务器，以及选择接收日志。

## Lesson
### 消息模式回顾
模式页面规定了谁可以说什么。*每次交互都由客户端（Client）发起。* 客户端发送请求和通知。服务器（Server）对每个请求回以一个响应，响应之前可以先发送**限定于该请求**的通知。*服务器**不得（MUST NOT）**发起 JSON-RPC 请求，客户端也不发送 JSON-RPC 响应。*

| 模式 | 形态 | 用途 |
| --- | --- | --- |
| **请求与响应** | 请求 → （限定于该请求的通知）→ 结果或错误 | 几乎所有场景；进度和日志消息都搭载在这里 |
| **多轮往返请求（MRTR）** | 请求 → `InputRequiredResult` → 带 `inputResponses` 重试 → 结果 | 无需服务器发起请求即可实现征询、采样和根目录（第 5.3 课） |
| **订阅与通知** | `subscriptions/listen` → `notifications/subscriptions/acknowledged` → 带标签的变更通知 | 列表变更、资源更新（第 3.4 课） |

传输层（Transport）原样承载每种模式，因为模式完全由请求、响应和通知来表达。未来的修订版如果新增一种模式，只需在这个页面上定义它，无需改动传输层。下面介绍的实用功能都位于第一种模式之内。

### 取消
客户端**应当（SHOULD）**取消（Cancellation）它不再需要的请求。在 stdio 上，它发送：

```json
{"jsonrpc": "2.0", "method": "notifications/cancelled",
 "params": {"requestId": "123", "reason": "User requested cancellation"}}
```

`requestId` 是**客户端此前发出的**某个请求的 id，`reason` 是可选的文本，用于记录日志或显示。信号如何传递取决于传输层：

| 传输层 | 取消信号 |
| --- | --- |
| **stdio** | 客户端**必须（MUST）**发送引用该请求 id 的 `notifications/cancelled`（没有按请求划分的流） |
| **Streamable HTTP** | **关闭 SSE 响应流**；服务器**必须（MUST）**把断开连接视为取消，不需要也不期望任何通知 |

**服务器发送取消只有一个用途。** 服务器在拆除 `subscriptions/listen` 订阅流时，**必须（MUST）**发送引用该 `subscriptions/listen` 请求 id 的 `notifications/cancelled`，并且**不得（MUST NOT）**因为其他任何原因发送它。

**行为要求。**

- 取消**必须（MUST）**只引用客户端发出的、并且它认为仍在进行中的请求。
- 收到取消的服务器**应当（SHOULD）**停止处理、释放相关资源，并且不发送响应。
- 如果请求未知、已经完成或不可取消，服务器**可以（MAY）**忽略它。
- 客户端**应当（SHOULD）**忽略此后到达的任何响应。
- *无效的*取消（未知 id、已完成的请求、格式错误的通知）**应当（SHOULD）**被忽略。这让通知保持“发出即不管”（fire-and-forget）。
- 双方都**应当（SHOULD）**记录取消原因，UI **应当（SHOULD）**显示已请求取消。

**竞态是正常的。** 由于网络延迟，取消可能在处理结束之后才到达，甚至在响应已经发出之后。*双方都**必须（MUST）**妥善处理这些竞态条件（Race Condition）。* 实际后果是：取消只是一个停止请求，并不能保证什么都没发生。有副作用的工具仍然需要幂等性（Idempotency）或补偿机制。

**超时（Timeout）。** 实现**应当（SHOULD）**为所有发出的请求设置超时，以防止连接挂起和资源耗尽。超时触发时，发送方**应当（SHOULD）**取消该请求（在 stdio 上发送通知，在 HTTP 上关闭流）并停止等待。SDK **应当（SHOULD）**允许逐请求配置超时。当某个请求收到进度通知时，实现**可以（MAY）**重置超时计时，因为这表明工作正在进行，但无论有无进度，都**应当（SHOULD）**强制执行一个**最大超时**，以约束行为异常的对端。

### 进度
进度（Progress）是按请求选择开启的。想要更新的客户端在请求的 `_meta` 中放入一个 `progressToken`（字符串或整数，**在所有活跃请求中唯一**，由客户端随意选择）：

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "index_repo", "arguments": {}, "_meta": {"progressToken": "abc123", "...": "envelope"}}}
```

随后，服务器**可以（MAY）**发送携带同一令牌（Token）的通知：

```json
{"jsonrpc": "2.0", "method": "notifications/progress",
 "params": {"progressToken": "abc123", "progress": 50, "total": 100, "message": "Reticulating splines..."}}
```

| 字段 | 规则 |
| --- | --- |
| `progressToken` | 来自请求的令牌 |
| `progress` | 每条通知都**必须（MUST）递增**，即使总量未知；可以是浮点数 |
| `total` | 可选；可以是浮点数；未知时省略 |
| `message` | 可选；**应当（SHOULD）**是人类可读的进度信息 |

进度通知**必须（MUST）**只引用操作仍在进行中的活跃请求的令牌，并且在完成后**必须（MUST）**停止。收到令牌的服务器**可以（MAY）**一条都不发，可以选择任意频率，也可以省略 `total`。双方都**应当（SHOULD）**跟踪活跃令牌并进行**限流（Rate Limiting）**，以免消息泛滥。在 Streamable HTTP 上，进度会迫使响应成为 SSE 流，因为这些通知必须在同一请求的流上、在最终结果之前到达。

### 分页
列表操作可能返回很大的结果集，所以 MCP 用**不透明游标（Opaque Cursor）**而不是页码对它们进行分页（Pagination）：

- **游标（Cursor）**是一个表示位置的不透明字符串。**页大小由服务器选择**，客户端**不得（MUST NOT）**假定固定的大小。
- 响应包含当前页；如果还有更多结果，则包含 `nextCursor`。
- 客户端通过发送同一方法、并把 `params.cursor` 设为该值（加上通常的 `_meta` 信封）来继续获取。

```json
{"jsonrpc": "2.0", "id": "123",
 "result": {"resultType": "complete", "resources": ["..."], "nextCursor": "eyJwYWdlIjogM30=",
            "ttlMs": 300000, "cacheScope": "public"}}
```

支持分页的操作是 **`tools/list`、`resources/list`、`resources/templates/list` 和 `prompts/list`**。

| 一方 | 指导 |
| --- | --- |
| 服务器**应当（SHOULD）** | 提供**稳定的游标**，并妥善处理无效游标；无效游标**应当（SHOULD）**产生 `-32602`（Invalid params） |
| 客户端**应当（SHOULD）** | 把**缺失**的 `nextCursor` 视为结束，并同时支持分页和不分页的流程 |
| 客户端**必须（MUST）** | 把游标视为**不透明的**：绝不解析、修改或解释它们；只根据是否提供了非 null 值来做判断。**空字符串是有效游标**，**不得（MUST NOT）**被视为结束。 |

为什么要不透明？这让服务器可以改变策略（偏移量、键集分页、快照 id、签名令牌）而不破坏客户端，也能阻止客户端伪造位置。再结合 2026-07-28 中服务器**应当（SHOULD）**以**确定性顺序**返回 `tools/list` 的规则，稳定的游标让列表结果可以被缓存（`ttlMs`/`cacheScope`），也对 LLM 的提示缓存（Prompt Caching）更友好。

### 日志（已弃用）
> **在 2026-07-28 中弃用（SEP-2577）。** 根据特性生命周期（Feature Lifecycle）策略，日志功能将在规范中至少保留十二个月。新实现**不应（SHOULD NOT）**采用它。现有实现**应当（SHOULD）**迁移：stdio 传输改为**向 `stderr` 写日志**，结构化可观测性则改用 **OpenTelemetry**。

你仍然会在现有服务器和面试中遇到日志（Logging），而且它在 2026-07-28 中的形态展示了一个特性如何变为无状态（Stateless）。发出日志的服务器**必须（MUST）**声明 `logging` 能力（Capability）。级别遵循 syslog（RFC 5424）：`debug`、`info`、`notice`、`warning`、`error`、`critical`、`alert`、`emergency`。

**有什么变化。** 在 2025-11-25 中，客户端调用一次 `logging/setLevel`，会话（Session）就会记住它。在 2026-07-28 中，**`logging/setLevel` 被移除了**，因为已经没有会话来记住它。取而代之的是，级别是**逐请求**的：

- 要接收某个请求的日志，客户端在该请求的 `_meta` 中加入 `io.modelcontextprotocol/logLevel`。
- 对于没有这个字段的请求，服务器**不得（MUST NOT）**发出 `notifications/message`。
- 有这个字段时，服务器**可以（MAY）**在该请求的响应流上、在最终响应**之前**，发送等于或高于该级别的 `notifications/message`。
- `notifications/message` 是**请求作用域内**的。它**不得（MUST NOT）**出现在 `subscriptions/listen` 流或任何其他流上。

```json
{"jsonrpc": "2.0", "method": "notifications/message",
 "params": {"level": "error", "logger": "database",
            "data": {"error": "Connection failed", "details": {"host": "localhost", "port": 5432}}}}
```

`data` 是任何可 JSON 序列化的值，`logger` 是可选的名称。无法识别的 `logLevel` **应当（SHOULD）**以 `-32602` 拒绝，内部错误则用 `-32603`。日志消息**不得（MUST NOT）**包含凭据或密钥、个人身份信息，或任何可能帮助攻击的内部细节。服务器**应当（SHOULD）**限流、校验数据字段、控制日志访问权限，并使用一致的 logger 名称。

**为什么弃用它？** 协议级日志重复了成熟工具早已做得更好的事情。在 stdio 上，stderr 是一个免费、标准、宿主（Host）可以捕获的日志通道。对于远程服务器，OpenTelemetry 提供跨服务关联的追踪、指标和日志，而且 MCP 已经在 `_meta` 中携带 W3C `traceparent`/`tracestate`/`baggage`（第 2.1 课）。移除协议级日志也消除了一个意外把数据泄露进模型上下文的来源。

## Key points
- 三种消息模式（Message Pattern）：**请求/响应**、**MRTR**、**订阅/通知**。每次交互都由客户端发起，服务器从不发起请求。
- 在 **stdio** 上用 `notifications/cancelled {requestId, reason?}` 取消（Cancellation）。在 **Streamable HTTP** 上，**关闭响应流**。服务器**只在**拆除 `subscriptions/listen` 流时才发送 `notifications/cancelled`。
- 收到取消（Cancellation）时，服务器应停止、释放资源并且**不再响应**。未知或已完成的 id 会被忽略，双方都必须容忍“完成之后才取消”的竞态条件（Race Condition）。
- 为每个请求设置**超时（Timeout）**，超时触发时取消，可以在收到进度时重置，但始终要强制一个**最大值**。
- 进度（Progress）通过 `_meta.progressToken`（在活跃请求中唯一）选择开启。`notifications/progress` 携带 `progress`（**严格递增**）、可选的 `total` 和 `message`，并在完成时停止。
- 分页（Pagination）使用**不透明游标**和**由服务器选择的页大小**：结果中有 `nextCursor`，参数中有 `cursor`。缺失 `nextCursor` = 结束，而 `""` 是有效游标。无效游标 → `-32602`。
- 支持分页（Pagination）的方法：`tools/list`、`resources/list`、`resources/templates/list`、`prompts/list`。
- 日志（Logging）已被**弃用**。`logging/setLevel` 已被**移除**，改为逐请求的 `io.modelcontextprotocol/logLevel`，没有级别就意味着没有 `notifications/message`。请改用 **stderr** 或 **OpenTelemetry**。

## Pitches
### MCP 中的取消是如何工作的？
这取决于传输层（Transport）。在 stdio 上，客户端发送一条 `notifications/cancelled` 通知，带上它要放弃的请求的 id，还可以附上原因。在 Streamable HTTP 上，每个请求都有自己的响应流，所以客户端直接关闭它就行，服务器必须把断开连接当作取消。不管哪种方式，服务器都应该停止工作、释放资源，并且不再为这个请求发送任何东西。取消可能和完成发生竞态，所以双方都必须能容忍这种情况。

### 你会如何为一个长时间运行的工具报告进度？
客户端通过在请求的 `_meta` 里放一个 `progressToken`（进度令牌（Progress Token））来选择开启。工具运行期间，服务器发送带有这个令牌的 `notifications/progress`，里面有一个必须持续递增的进度值、一个可选的总量和一条人类可读的消息。在 Python SDK 里，这只需要调用 `ctx.report_progress`。在 HTTP 上，这会把响应变成一个 SSE 流。在客户端，我会把它显示在 UI 上，并用它来延长空闲超时，同时仍然强制一个硬性上限。

### 为什么 MCP 的日志功能被弃用了？你改用什么？
因为它重复了更好的工具。从 2026-07-28 起，客户端只能通过在 `_meta` 里带上 `logLevel`、逐请求地选择接收服务器日志，旧的 `logging/setLevel` 调用已经没了。规范现在说新实现不应该采用它。对于 stdio 服务器，我把日志写到 stderr，宿主（Host）可以捕获它。对于远程服务器，我用 OpenTelemetry，在 `_meta` 中传播追踪上下文，这样一次工具调用就会出现在发起它的智能体（Agent）所在的同一条分布式追踪里。

## Interview
### 为一个调用可能运行数分钟的工具的 MCP 客户端设计超时策略。
每个请求都有超时（Timeout），并且可以按规范要求 SDK 支持的那样逐请求配置。对于长时间运行的工具，我会用一个唯一的 `progressToken` 请求进度，并使用**两个时钟**：一个*空闲*超时（比如 30 秒），每当该令牌的 `notifications/progress` 到达时就重置；以及一个*硬性上限*（比如 10 分钟），进度永远不能延长它。规范明确推荐了这个上限，这样一个无休止发送进度的服务器就无法无限期地占用请求。任何一个触发时，我都会**正确地取消**：在 stdio 上发送带原因的 `notifications/cancelled`，在 HTTP 上关闭流。然后忽略任何迟到的响应，并给出明确的错误。对于确实比一个连接活得更久的工作，我会使用 Tasks 扩展（Extension），而不是一味拉长超时。

### 客户端为请求 42 发送了 `notifications/cancelled`，但服务器早已发出了结果。双方各应怎么做？
不需要做什么特别的事。这正是规范指出的竞态条件（Race Condition）。对于已完成或未知的请求，服务器**可以（MAY）**忽略取消，并且不得报错；无效的取消**应当（SHOULD）**被忽略，以保持通知“发出即不管”。客户端**应当（SHOULD）**忽略在它取消之后到达的响应。如果它已经处理了该响应，也没问题。重要的设计要点是，取消是*建议性的*：如果工具有副作用，这些副作用可能已经发生了。非幂等的工具需要幂等键（Idempotency Key）或补偿手段，UI 应该显示“已请求取消”，而不是“什么都没发生”。

### 为什么客户端必须把分页游标视为不透明的？举一个不这样做会出现的 bug。
因为游标的含义属于服务器。它今天可能是偏移量，明天可能是签名的快照 id。一个经典 bug：客户端看到 `nextCursor: "eyJwYWdlIjogM30="`，把它解码成 `{"page": 3}`，然后自作聪明地“优化”，直接跳到第 7 页。当服务器换成键集分页时，这就会出错；或者当列表在两次调用之间发生变化时，它会漏掉条目。另一个 bug 是把**空字符串**当作“没有更多页了”。规范说 `""` 是有效游标（不透明游标（Opaque Cursor）），只有*缺失*的 `nextCursor` 才表示结束。客户端也不能假定页大小，因为它由服务器选择。

### 在 2025-11-25 和 2026-07-28 之间，日志功能发生了什么变化？
有两点。**机制：**`logging/setLevel`（一个会话范围的设置）被移除了，因为已经没有会话（Session）了。客户端现在通过在 `_meta` 中加入 `io.modelcontextprotocol/logLevel` **逐请求**地选择开启；没有它，服务器**不得**发送 `notifications/message`。这些消息是请求作用域内的，在结果之前通过该请求的响应流发送，绝不出现在 `subscriptions/listen` 流上。**状态：**整个日志（Logging）特性连同根目录（Roots）和采样（Sampling）一起被**弃用**（SEP-2577）。它至少还会保留十二个月，但新实现应当把日志写到 stderr（stdio）或使用 OpenTelemetry。

### 陷阱题：服务器先发送 `progress: 30` 的 `notifications/progress`，然后又发送 `progress: 20`。此外，它还为一个没有 `progressToken` 的请求发送了进度。违反了哪些规则？
两者都是违规。对于同一个令牌，`progress` 在每条通知中都**必须（MUST）递增**，即使 `total` 未知，所以 30 → 20 是无效的（客户端可以丢弃它或把该服务器标记出来）。而且进度通知（Progress Notification）**必须（MUST）**只引用活跃请求中提供过的令牌。没有 `progressToken` 就没有可引用的东西，所以服务器一条都不能发。还有两条相关规则：操作完成后通知**必须停止**，双方都**应当对它们进行限流**。

## Glossary
- Message pattern | 消息模式 | 请求、响应和通知组合的标准方式：请求/响应、多轮往返请求，或订阅/通知。
- Cancellation | 取消 | 放弃一个进行中的请求：在 stdio 上发送 `notifications/cancelled`，在 Streamable HTTP 上关闭响应流。
- `notifications/cancelled` | `notifications/cancelled`（取消通知） | 携带 `requestId` 和可选 `reason` 的通知；服务器只在结束 `subscriptions/listen` 流时发送它。
- Race condition | 竞态条件 | 取消在请求已经完成之后才到达的情况，双方都必须妥善处理。
- Progress token | 进度令牌 | 由客户端选择、放在 `_meta.progressToken` 中、在活跃请求中唯一的字符串或整数，用于让请求开启进度通知。
- `notifications/progress` | `notifications/progress`（进度通知） | 一种服务器通知，携带 `progressToken`、严格递增的 `progress`，以及可选的 `total` 和 `message`。
- Cursor-based pagination | 基于游标的分页 | 把列表结果拆分为由服务器决定大小的页面，并通过不透明的 `nextCursor`/`cursor` 令牌相互链接。
- Opaque cursor | 不透明游标 | 客户端不得解析或修改的分页令牌；只有它是否存在才有意义，`""` 也是有效的。
- `io.modelcontextprotocol/logLevel` | 逐请求日志级别 | 让单个请求开启等于或高于某级别的日志通知的 `_meta` 键；取代了 `logging/setLevel`。
- Deprecated feature | 已弃用特性 | 在规范中至少保留十二个月、但新实现不应采用的特性，例如日志。

### 1. 通过 SDK 观察进度
`ctx.report_progress(progress, total, message)` 会发送 `notifications/progress`（进度通知），但**只有**在请求携带了 `progressToken`（进度令牌（Progress Token））时才会发送。`Client.call_tool(..., progress_callback=...)` 会替你创建令牌，并把通知转给你的回调函数。

```python
import json
import os
import sys
import tempfile
import textwrap
import time
import warnings
from pathlib import Path

import anyio
from mcp import Client, StdioServerParameters
from mcp.server import MCPServer
from mcp.server.mcpserver import Context
from mcp.shared.exceptions import MCPDeprecationWarning, MCPError

indexer = MCPServer("indexer")


@indexer.tool()
async def index_repo(files: int, ctx: Context) -> str:
    """Index a repository, reporting progress per file."""
    for i in range(1, files + 1):
        await anyio.sleep(0.05)
        await ctx.report_progress(i, files, f"indexed file {i}/{files}")
    return f"indexed {files} files"


async def show_progress(progress, total, message):
    bar = "#" * int(20 * progress / total)
    print(f"  [{bar:<20}] {progress:>4.0f}/{total:.0f}  {message}")


async with Client(indexer) as client:
    result = await client.call_tool("index_repo", {"files": 5}, progress_callback=show_progress)
    print(result.content[0].text)
    quiet = await client.call_tool("index_repo", {"files": 5})        # no callback -> no token -> no notifications
    print(quiet.content[0].text, "(no progressToken, so no notifications)")
```

### 2. 线路上的进度，以及一个检查规则的客户端
通过原始 stdio，你可以看到令牌（Token）是如何传递的。我们还让每条通知都经过一个小型校验器，检查规范中的规则：令牌必须已知且处于活跃状态，`progress` 必须严格递增。一个故意写错的工具会让进度倒退。

```python
import queue
import subprocess
import threading

workdir = Path(tempfile.mkdtemp())
(workdir / "progress_server.py").write_text(textwrap.dedent('''
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("progress-lab", log_level="ERROR")

    @mcp.tool()
    async def good(ctx: Context) -> str:
        """Well-behaved progress."""
        for i in (0.25, 0.5, 1.0):
            await ctx.report_progress(i, 1.0, f"{i:.0%}")
        return "ok"

    @mcp.tool()
    async def buggy(ctx: Context) -> str:
        """Progress that goes backwards."""
        for i in (30, 20, 40):
            await ctx.report_progress(i)
        return "ok"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {}}


def start(script, env=None):
    proc = subprocess.Popen([sys.executable, str(workdir / script)], stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                            stderr=subprocess.DEVNULL, text=True, env=env)
    inbox = queue.Queue()
    threading.Thread(target=lambda: [inbox.put(l) for l in proc.stdout], daemon=True).start()
    return proc, inbox


def send(proc, message):
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()


class ProgressTracker:
    def __init__(self):
        self.active = {}                                     # token -> last progress value

    def start(self, token):
        self.active[token] = None

    def check(self, params):
        token, value = params["progressToken"], params["progress"]
        if token not in self.active:
            return "VIOLATION: unknown or finished token"
        last = self.active[token]
        self.active[token] = value
        if last is not None and value <= last:
            return f"VIOLATION: progress went {last} -> {value} (MUST increase)"
        return "ok"

    def finish(self, token):
        self.active.pop(token, None)


proc, inbox = start("progress_server.py")
tracker = ProgressTracker()
for id_, tool in [(1, "good"), (2, "buggy")]:
    token = f"tok-{tool}"
    tracker.start(token)
    send(proc, {"jsonrpc": "2.0", "id": id_, "method": "tools/call",
                "params": {"name": tool, "arguments": {}, "_meta": {**ENVELOPE, "progressToken": token}}})
    while True:
        msg = json.loads(inbox.get(timeout=10))
        if msg.get("method") == "notifications/progress":
            print(f"  {json.dumps(msg['params']):<85} {tracker.check(msg['params'])}")
        else:
            tracker.finish(token)
            print(f"  response id={msg['id']} -> token {token!r} retired\n")
            break
proc.stdin.close()
_ = proc.wait(timeout=10)
```

### 3. 通过 SDK 取消：放弃、超时，以及服务器看到了什么
服务器把事件追加写入一个事件文件，这样我们就能从外部观察它。当调用方的 `anyio` 作用域放弃等待时，SDK 会在 stdio 上发送 `notifications/cancelled`，处理函数随即被中断。`read_timeout_seconds`（读取超时）的效果相同，并会抛出一个错误。

```python
(workdir / "cancel_server.py").write_text(textwrap.dedent('''
    import os
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("cancel-lab", log_level="ERROR")

    def note(text):
        with open(os.environ["EVENTS_FILE"], "a") as f:
            f.write(text + "\\n")

    @mcp.tool()
    async def crunch(seconds: float, ctx: Context) -> str:
        """A long job."""
        note(f"request {ctx.request_id}: started ({seconds}s of work)")
        try:
            await anyio.sleep(seconds)
        except BaseException as exc:
            note(f"request {ctx.request_id}: interrupted by {type(exc).__name__}, resources freed")
            raise
        note(f"request {ctx.request_id}: finished")
        return "crunched"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
events_file = workdir / "events.log"
events_file.write_text("")
env = {**os.environ, "EVENTS_FILE": str(events_file)}
params = StdioServerParameters(command=sys.executable, args=[str(workdir / "cancel_server.py")], env=env)

async with Client(params) as client:
    with anyio.move_on_after(0.5) as scope:                 # the user pressed "stop" after 0.5 s
        await client.call_tool("crunch", {"seconds": 5})
    print("caller gave up:", scope.cancelled_caught)

    try:
        await client.call_tool("crunch", {"seconds": 5}, read_timeout_seconds=0.5)
    except MCPError as err:
        print(f"timeout -> MCPError {err.error.code}: {err.error.message}")

    print((await client.call_tool("crunch", {"seconds": 0.1})).content[0].text)
    await anyio.sleep(0.2)

print("\nserver-side events:")
print(events_file.read_text())
```

超时以错误码 `-32001` 呈现，它来自**旧版、由实现自定义的**范围。规范没有为纯本地错误分配错误码，所以 SDK 只好自己选一个。记住，这个错误是由你自己的客户端（Client）抛出的，而不是服务器发来的。

### 5. 看门狗：由进度重置的空闲超时，再加一个硬性上限
这里实现了规范中关于超时（Timeout）的建议。进度会延长*空闲*截止时间，但硬性上限即使对一个永远在报告进度的请求也会终止它。

```python
forever = MCPServer("forever")


@forever.tool()
async def stream_forever(ctx: Context) -> str:
    """Reports progress endlessly (a misbehaving server)."""
    i = 0
    while True:
        i += 1
        await ctx.report_progress(i, message=f"tick {i}")
        await anyio.sleep(0.2)


async def call_with_watchdog(client, name, args, idle=0.5, hard_max=1.5):
    started = last_progress = time.monotonic()

    async def on_progress(progress, total, message):
        nonlocal last_progress
        last_progress = time.monotonic()

    async with anyio.create_task_group() as tg:
        outcome = {}

        async def run():
            outcome["result"] = (await client.call_tool(name, args, progress_callback=on_progress)).content[0].text
            tg.cancel_scope.cancel()

        tg.start_soon(run)
        while True:
            await anyio.sleep(0.05)
            now = time.monotonic()
            if now - last_progress > idle:
                outcome["error"] = f"idle timeout ({idle}s without progress)"
            elif now - started > hard_max:
                outcome["error"] = f"hard maximum of {hard_max}s reached despite progress"
            if outcome:
                tg.cancel_scope.cancel()             # cancelling the call makes the SDK cancel the request
                break
    return outcome


async with Client(forever) as client:
    print(await call_with_watchdog(client, "stream_forever", {}))
async with Client(indexer) as client:
    print(await call_with_watchdog(client, "index_repo", {"files": 8}, idle=0.5, hard_max=5))
```

### 6. 使用不透明游标的分页
`MCPServer` 会把所有工具放在一页中返回。要实现分页（Pagination），请使用底层的 `Server` 并自己编写 `tools/list` 处理函数。这里的游标是一个客户端不得解释的 base64 数据块（不透明游标（Opaque Cursor）），错误的游标会得到 `-32602`。

```python
import base64

import mcp_types as types
from mcp.server import Server

CATALOG = [types.Tool(name=f"report_{i:02d}", description=f"Report number {i}", input_schema={"type": "object"})
           for i in range(7)]
PAGE_SIZE = 3                                                   # the SERVER decides


def make_cursor(offset: int) -> str:
    return base64.urlsafe_b64encode(json.dumps({"o": offset}).encode()).decode()


async def list_tools(ctx, params: types.PaginatedRequestParams | None) -> types.ListToolsResult:
    offset = 0
    if params is not None and params.cursor is not None:
        try:
            offset = json.loads(base64.urlsafe_b64decode(params.cursor))["o"]
        except Exception:
            raise MCPError(code=types.INVALID_PARAMS, message="Invalid cursor")
    page = CATALOG[offset:offset + PAGE_SIZE]
    more = offset + PAGE_SIZE < len(CATALOG)
    return types.ListToolsResult(tools=page, next_cursor=make_cursor(offset + PAGE_SIZE) if more else None)


pager = Server("pager", on_list_tools=list_tools)

async with Client(pager) as client:
    first = await client.list_tools()
    show = first.model_dump(by_alias=True, exclude_none=True, mode="json")
    print("first page on the wire:", json.dumps({k: v for k, v in show.items() if k != "tools"}),
          "| tools:", [t["name"] for t in show["tools"]])

    everything, cursor, pages = [], None, 0
    while True:                                                  # the loop every client should have
        page = await client.list_tools(cursor=cursor)
        pages += 1
        everything += [t.name for t in page.tools]
        if page.next_cursor is None:                             # only a MISSING cursor ends the loop
            break
        cursor = page.next_cursor
    print(f"collected {len(everything)} tools in {pages} pages:", everything)

    try:
        await client.list_tools(cursor="not-a-real-cursor")
    except MCPError as err:
        print("invalid cursor ->", err.error.code, err.error.message)
```

### 7. 日志：已弃用，但仍在线路上
客户端通过设置 `io.modelcontextprotocol/logLevel`（逐请求日志级别）来**逐请求**选择开启日志（Logging）。SDK 的 `Client(log_level=..., logging_callback=...)` 会在每个请求上加上这个键。没有级别时，服务器必须保持沉默。SDK 用 `MCPDeprecationWarning` 标记了整个特性。

```python
chatty = MCPServer("chatty")


@chatty.tool()
async def migrate(ctx: Context) -> str:
    """Run a migration, logging along the way."""
    await ctx.debug("opening connection pool")
    await ctx.info({"step": "migrate", "tables": 12})
    await ctx.warning("table 'legacy_users' has no primary key")
    return "migrated"


async def print_log(params):
    print(f"   log [{params.level:<7}] {params.data}")


with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always", MCPDeprecationWarning)
    for level in ["debug", "warning", None]:
        print(f"log_level={level!r}:")
        async with Client(chatty, log_level=level, logging_callback=print_log) as client:
            print("  ", (await client.call_tool("migrate", {})).content[0].text)
print("\ndeprecation warnings raised:", sorted({str(w.message) for w in caught}))
```

在原始线路上，级别只是 `_meta` 中的一个键，未知的级别会被拒绝：


### 8. 替代方案：stderr 上的结构化日志
对于 stdio 服务器，迁移路径就是 stderr。这里服务器每行向 stderr 写一个 JSON 对象，宿主（Host）把它与协议流分开捕获。不需要选择开启，也不需要声明能力，而且没有任何内容会进入模型的上下文。

```python
(workdir / "stderr_server.py").write_text(textwrap.dedent('''
    import json, logging, sys, time
    from mcp.server import MCPServer

    class JsonLines(logging.Formatter):
        def format(self, record):
            return json.dumps({"ts": round(time.time(), 3), "level": record.levelname.lower(),
                               "logger": record.name, "msg": record.getMessage()})

    handler = logging.StreamHandler(sys.stderr)          # never stdout on stdio!
    handler.setFormatter(JsonLines())
    log = logging.getLogger("billing")
    log.addHandler(handler)
    log.setLevel(logging.INFO)
    log.propagate = False

    mcp = MCPServer("billing", log_level="ERROR")

    @mcp.tool()
    def charge(cents: int) -> str:
        """Charge a (pretend) card."""
        log.info("charge requested: %d cents", cents)
        if cents > 10_000:
            log.warning("large charge flagged for review")
        return "charged"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
proc = subprocess.Popen([sys.executable, str(workdir / "stderr_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
send(proc, {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
            "params": {"name": "charge", "arguments": {"cents": 25_000}, "_meta": ENVELOPE}})
print("stdout (protocol):", proc.stdout.readline().strip()[:110], "...")
proc.stdin.close()
_ = proc.wait(timeout=10)
print("stderr (logs the host can capture):")
for line in proc.stderr.read().splitlines():
    if line.startswith("{"):
        print("  ", json.loads(line))
```

对于远程服务器，对应的方案是 OpenTelemetry。客户端在 `_meta` 中放入 `traceparent`（第 2.1 课），服务器把 span 和日志导出到你的可观测性后端，并与智能体（Agent）的追踪相关联。
