## Summary
服务器只是 MCP 应用的一半。另一半是**宿主（Host）**：这个程序负责连接服务器、把服务器的工具展示给语言模型，并运行一个循环，把“模型想调用 X”变成一次真正的 `tools/call`。本课沿着官方的 *Build an MCP client* Python 教程展开，内容包括 `async with` 块中的 `Client` 生命周期、stdio 传输（Transport），以及把 MCP 工具定义（Tool Definition）转换为 LLM 的工具格式。随后本课会超越教程，构建一个面向生产环境的**智能体循环（Agent Loop）**：多轮工具调用直到模型不再请求、把失败的工具以 `is_error` 回传、会话状态（Conversation State）、超时、迭代上限保护（Iteration Guard），以及让 API 密钥远离代码。

## Lesson
### 客户端程序要做什么
官方教程构建了一个能与*任意* MCP 服务器对话的命令行聊天机器人。它的“How it works”列表就是宿主（Host）的全部工作：

1. 客户端从服务器获取可用工具列表。
2. 你的查询连同工具描述一起发送给模型。
3. 模型决定使用哪些工具（如果需要的话）。
4. 客户端通过服务器执行所请求的工具调用。
5. 结果返回给模型。
6. 模型写出自然语言的回答。
7. 回答展示给用户。

MCP 标准化的是第 1 步和第 4 步（`tools/list` 和 `tools/call`）。其余的一切，包括使用哪个模型、如何给它写提示词、允许多少轮、哪些操作需要用户审批，都属于宿主。这就是为什么同一个服务器既能在 Claude Desktop、VS Code 中工作，也能在你自己写的 80 行脚本中工作。

### 准备工作：依赖与密钥
Python 教程需要 **Python SDK 2.0.0 或更高版本**，并安装三个包：`uv add mcp anthropic python-dotenv`。模型 API 密钥放在 `.env` 文件中（`ANTHROPIC_API_KEY=...`）。教程明确把 `.env` 加入了 `.gitignore`，并在启动时用 `load_dotenv()` 加载它。随后 SDK 的 `Anthropic()` 构造函数会从环境变量中读取密钥。永远不要硬编码密钥，永远不要把它写进日志，也永远不要把它传给 MCP 服务器，因为服务器属于另一个信任域。

### `Client` 及其生命周期
在 SDK 2.x 中，单个 `Client` 对象是“你的程序与服务器通信所用的唯一对象”。列出工具、调用工具和读取资源都是它的方法。

```python
from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="python", args=["weather.py"])   # configuration, not a connection
async with Client(stdio_client(params)) as client:                       # launch + agree a protocol version
    tools = (await client.list_tools()).tools
    result = await client.call_tool("get_forecast", {"latitude": 38.6, "longitude": -90.2})
# leaving the block disconnects and shuts the subprocess down
```

请把三个概念区分清楚：

- **`StdioServerParameters`**（stdio 服务器参数）是配置：`command`、`args`，以及可选的 `env` 和 `cwd`。它不会启动任何东西。
- **`stdio_client(params)`** 把它变成一个**传输层（Transport）**，以子进程方式启动服务器，并通过其 stdin/stdout 使用按换行分隔的 JSON-RPC 进行通信。`Client` 也可以直接接受 `StdioServerParameters`、一个 URL 字符串（可流式 HTTP（Streamable HTTP）），或者一个进程内的 `MCPServer`（在测试中很方便）。
- **`async with Client(...)`** 就是“整个连接生命周期”。进入该块时会启动传输层并协商协议版本。对于 2026-07-28 服务器，这意味着探测 `server/discover`，对于较旧的服务器则回退到旧版的 `initialize` 握手。离开该块时会断开连接并停止子进程。“没有需要调用的 connect/close 配对，事后也没有任何东西需要清理。”

教程中的服务器路径辅助函数会为 `.py` 选择 `python`，为 `.js` 选择 `node`，其他一律拒绝。在你自己的宿主中，这个选择通常来自配置文件，例如 Claude Desktop 的 `mcpServers`（第 5.5 课）。

### 从 MCP 工具到 LLM 工具
一个 MCP `Tool` 包含 `name`、`title`、`description`、`inputSchema`、可选的 `outputSchema`、`annotations` 和 `icons`。Anthropic 的 Messages API 需要的是 `{name, description, input_schema}`。转换只需一个推导式。Python SDK 暴露的是 snake_case 属性，所以读取的是 `tool.input_schema`：

```python
available_tools = [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                   for t in (await client.list_tools()).tools]
```

有些细节在生产环境中很重要：

- **分页（Pagination）。** `tools/list` 可能返回一个 `nextCursor`。健壮的宿主会一直获取，直到不再有游标为止。
- **缓存（Caching）。** 在 2026-07-28 中，列表结果携带 `ttlMs` 和 `cacheScope`，服务器应当（SHOULD）以**确定性的顺序**返回工具。稳定的工具列表能让 LLM 的提示缓存（Prompt Caching）保持命中。Python `Client` 默认遵循 `ttlMs`。
- **模型永远看不到的东西。** `outputSchema`、`annotations` 和 `icons` 是给宿主用的，不是给模型的。注解（Annotations）是来自可能不受信任的服务器的*提示*。用它们来决定何时请求用户确认，但永远不要把它们当作安全保证。
- **名称。** 工具名称遵循规范的命名规则。存在多个服务器时，给名称加上服务器前缀（`github__create_issue`）以避免冲突（第 5.4 课）。

其他提供商对同样的数据使用不同的结构。OpenAI 风格的 API 需要 `{"type": "function", "function": {name, description, parameters}}`。MCP 与模型无关，由宿主负责转换。

### 智能体循环
教程中的 `process_query` 只调用**一次**模型，执行所请求的工具，然后再进行**一次**后续调用。这对演示来说足够了，但真实任务是多步骤的：*先查出城市代码，再获取它的天气预报，然后进行比较*。因此宿主会一直循环，直到模型不再请求工具为止，这就是智能体循环（Agent Loop）：

```python
messages = [{"role": "user", "content": query}]
for _ in range(MAX_ITERATIONS):
    response = llm.messages.create(model=MODEL, max_tokens=16000, tools=available_tools, messages=messages)
    if response.stop_reason != "tool_use":
        break                                                  # end_turn, max_tokens, ...
    messages.append({"role": "assistant", "content": response.content})
    tool_results = []
    for block in response.content:
        if block.type == "tool_use":
            result = await client.call_tool(block.name, block.input)
            tool_results.append({"type": "tool_result", "tool_use_id": block.id,
                                 "content": text_of(result), "is_error": result.is_error})
    messages.append({"role": "user", "content": tool_results})   # ONE user message with ALL results
```

这个循环背后的规则：

- **原样追加助手轮次**（`response.content`，包括其中的 `tool_use` 块），然后再追加结果。API 需要知道每个结果对应的是哪一次调用。
- **在一条用户消息中回答每一个 `tool_use`**，通过 `tool_use_id` 匹配 id。模型可能在一个轮次中并行请求多个工具。
- **把 `isError` 作为 `is_error` 透传。**“抛出异常的工具在这里不会抛出：它会以设置了 `is_error` 的结果作答，而把这个标志传下去，Claude 就能读到错误信息并尝试别的办法。”MCP 有意把工具执行错误（Tool Execution Error）放在结果*内部*报告，让模型能够自我纠正。
- **给循环设定上限。** `MAX_ITERATIONS` 保护能阻止一个糊涂的模型无休止地调用工具、消耗令牌（Token）。触发上限时，要告知用户，而不是静默失败。
- **仔细读取文本内容。** `result.content` 是一个内容块列表（文本、图像、音频、资源链接、嵌入式资源）。教程只取 `TextContent`。更完善的宿主可以把图像作为图像块转发，或者在存在 `structured_content` 时使用它。

### 会话状态
“维护会话上下文”指的就是 `messages` 列表。在一次查询中，它会随着每个助手轮次和每个工具结果轮次而增长。在一次聊天的多次查询之间，宿主会持续追加内容，因此“那明天呢？”这样的问题也能被理解。会话状态（Conversation State）**并不**存放在 MCP 连接中。在 2026-07-28 中，协议是无状态（Stateless）的，因此每个 `tools/call` 都是自包含的。历史记录、对它的截断或摘要，以及它的持久化，都由宿主负责。

### 逐层的错误处理
| 层 | 出了什么问题 | 如何显现 | 宿主应当怎么做 |
| --- | --- | --- | --- |
| 工具执行 | 输入错误、API 宕机、业务规则 | 带 `isError: true` 的 `CallToolResult` | 以 `is_error` 传给模型，让它调整 |
| 协议 | 未知方法、无效参数、缺少能力 | JSON-RPC 错误，以 `MCPError` 抛出 | 报告它；如有帮助，把摘要提供给模型 |
| 传输 / 时间 | 服务器崩溃、挂起、缓慢 | 诸如 `Request 'tools/call' timed out` 的 `MCPError`、连接错误 | 超时、报告，必要时重启服务器 |
| 模型 API | 限流、过载、认证 | 来自 LLM SDK 的异常 | 带退避地重试；永远不要无限重试 |
| 你的聊天循环 | 以上任何一种 | `process_query` 中的异常 | 按查询捕获，避免一次失败拖垮整个会话 |

教程中的 `chat_loop` 把每次查询都包在 `try/except` 中，打印 `Error: ...`，同时保持会话存活。它用 `asyncio.to_thread` 运行 `input()`，“这样在你打字时，事件循环仍能空出来为连接服务”。它在输入 `quit` 或遇到文件结束符时退出。

**超时。** 挂起的工具不能让你的宿主（Host）也挂起。教程的故障排查提示说得很直白：“`Timeout error`：考虑调高 `Client` 上的 `read_timeout_seconds`。”`Client(..., read_timeout_seconds=30)` 为每个请求设置默认值，`call_tool(..., read_timeout_seconds=...)` 则按调用覆盖它。预计第一次响应会很慢（教程提到最长可达 30 秒），因为服务器要启动、模型要思考、工具要运行。

### 客户端中的安全
教程的最佳实践很简短：把 API 密钥存放在 `.env` 中，校验服务器响应，谨慎对待工具权限。在实践中：

- **行动前先征得同意。** 规范要求宿主在调用工具前获得用户同意。如果愿意，你可以自动批准来自受信任服务器的只读工具，但要把破坏性工具放在确认步骤之后，这就是工具调用审批（Tool Approval）。
- **工具结果是不受信任的输入。** 工具返回的网页或 issue 正文中可能包含针对你的模型的指令（提示注入（Prompt Injection），第 6.2 课）。永远不要让一个工具结果悄无声息地触发另一个特权操作。
- **描述和注解都是不受信任的**，除非服务器本身受信任。
- **子进程的最小权限。** stdio 服务器以你的用户权限运行。只传入它需要的 `env`，而不是把你装满密钥的整个环境都传进去。

### 故障排查清单
`FileNotFoundError` 表示服务器路径错误，可以尝试使用绝对路径。在 Windows 上，请使用正斜杠或转义后的反斜杠。`Connection refused` 表示服务器没有运行，或者 URL 错误。`Tool execution failed` 通常意味着服务器缺少环境变量。出现超时则意味着你应当调高 `read_timeout_seconds`，或者修复那个缓慢的工具。

### 与 2025 年 SDK 相比的变化
较早的教程展示的是 `ClientSession` 加上 `AsyncExitStack`、显式的 `await session.initialize()`，以及 `stdio_client` 产出需要你自己连接的读/写流。SDK 2.x 把这些都合并进了 `Client`。在 2026-07-28 中，协议已经没有 `initialize` 握手（请求在 `_meta` 中携带自己的版本），但 `Client` 仍会为较旧的服务器回退到这个握手。在面试和现有代码库中，这两种风格你都会见到。

## Key points
- 宿主（Host）的工作：列出工具 → 交给模型 → 通过 MCP 执行模型的工具调用 → 返回结果 → 重复 → 作答。
- `async with Client(...)` 就是整个生命周期。进入时启动/连接并协商协议版本，离开时断开连接并停止子进程。
- `StdioServerParameters` 是配置，`stdio_client()` 创建传输层（Transport），`Client` 打开它。`Client` 也可以接受 URL 或进程内服务器。
- 把工具转换为 `{"name", "description", "input_schema": tool.input_schema}`。`outputSchema`、注解（Annotations）和图标留给宿主使用。
- 当 `stop_reason == "tool_use"` 时持续循环：原样追加助手内容，然后追加**一条**用户消息，其中包含通过 `tool_use_id` 匹配的**所有** `tool_result` 块。
- 把 `result.is_error` 作为 `is_error` 透传。失败的工具（Tool）返回结果而不是抛出异常，这样模型才能恢复。
- 始终限制迭代次数、设置 `read_timeout_seconds`，并按查询捕获错误，让聊天得以继续。
- 宿主拥有会话状态（Conversation State）（即 `messages` 列表）。2026-07-28 协议本身是无状态的。
- 把 API 密钥放在 `.env` 中（被 git 忽略），在执行工具前征得同意，并把工具结果和描述视为不受信任的内容，以防提示注入（Prompt Injection）。

## Pitches
### MCP 客户端如何把 LLM 变成智能体？
我的宿主（Host）会在一个异步上下文管理器里连接每个服务器，并列出它的工具。我把这些工具转换成模型的工具格式，和用户的请求一起发出去。只要模型因为要调用工具而停下，我就追加它这一轮的内容，通过 MCP 执行它请求的每一个调用，然后回传一条包含所有工具结果的消息，失败的用 is_error 标出来。当模型用文字作答，或者触发我的迭代上限时，循环就结束。MCP 标准化的是发现和调用，循环策略仍然由我来定，这就是智能体循环（Agent Loop）。

### 为什么要把工具错误回传给模型，而不是直接抛出异常？
大多数工具失败其实是信息，而不是崩溃：ID 写错了、缺少权限、被限流了。MCP 把它们放在结果里，用 isError 标记，这样模型就能读到错误信息，修正参数或者换一个工具，这就是工具执行错误（Tool Execution Error）的设计。在我的循环里，我把这个标志作为 is_error 转发。协议错误和超时就不一样了，它们说明底层管道坏了，所以我会把它们告诉用户，或者总结给模型，同时用迭代上限防止无休止的重试。

### 在投入生产之前，你会给官方客户端教程补充什么？
教程只做一次后续调用，所以我会把它改成一个真正的循环，并加上最大迭代次数保护（Iteration Guard）。我会用 read_timeout_seconds 加上超时，为破坏性工具加上用户同意关卡，对工具列表做分页和缓存，并在多服务器时给工具名加上服务器前缀。我还会把工具输出视为不受信任的内容，只给子进程服务器最小化的环境，把密钥放在被 git 忽略的 env 文件里，并在每次模型调用和工具调用前后加上日志和链路追踪。

## Interview
### 请讲解使用 Anthropic API 时，一轮工具调用的消息结构。
请求中包含 `tools=[{name, description, input_schema}]` 和 `messages` 历史记录。如果响应的 `stop_reason` 是 `"tool_use"`，它的 `content` 中会有可选的文本块，以及一个或多个 `tool_use` 内容块（tool_use Block），每个都带有 `id`、`name` 和 `input`。我把 `{"role": "assistant", "content": response.content}` 原样追加。然后通过 MCP 调用每个工具，并追加**一条** `{"role": "user", "content": [...]}` 消息，其中为**每一个** `tool_use` 放入一个 `{"type": "tool_result", "tool_use_id": id, "content": text, "is_error": flag}`。接着再次调用 API。漏掉某个结果、把结果拆到多条消息中，或者丢掉助手轮次，都会破坏配对关系，API 会拒绝该请求。

### 官方教程最多调用模型两次。为什么这不够？你会怎么改？
多步骤任务需要链式调用：先查一个 ID，再获取详情，然后执行操作。每一步都依赖上一步的结果，所以轮数无法事先确定。我会把固定的两次调用替换为一个 `while stop_reason == "tool_use"` 循环，并用 `MAX_ITERATIONS` 设定上限（迭代上限保护（Iteration Guard））。每一轮我都会把所有结果回传，包括错误。当保护触发时，我会向用户返回一条清晰的“已在 N 步后停止”消息并记录完整对话，而不是继续循环或直接崩溃。

### 某个工具永远挂起。你的宿主会发生什么？你如何防止这种情况？
没有超时的话，`await client.call_tool(...)` 会无限期等待，整个对话都会冻结。我会在 `Client` 上设置 `read_timeout_seconds`（读取超时），并为已知较慢的工具按调用覆盖它。使用 Python SDK 时，超时会抛出 `MCPError`（“Request 'tools/call' timed out”）。我的循环会捕获它，并返回一个 `is_error: true` 的 `tool_result`，说明该工具超时了，这样模型就能尝试别的办法或告知用户。如果服务器持续失败，我会重启它，或者在本次会话中禁用它。长时间运行的工作应当放到任务（Tasks）扩展中（第 7.1 课），而不是放在阻塞调用里。

### 你如何处理跨轮次的会话状态？MCP 在其中处于什么位置？
宿主维护 `messages` 列表：用户轮次、带 `tool_use` 的助手轮次，以及工具结果轮次。后续问题会被追加到同一个列表中，这样模型就能理解其中的指代。当上下文变大时，我会裁剪或总结旧的工具结果；如果聊天需要在重启后继续，我会把历史记录持久化。MCP 不保存其中任何内容。在 2026-07-28 中，每个请求都是自包含的，任何跨调用的服务器状态都是作为工具参数传递的显式句柄（State Handle）。会话状态（Conversation State）完全属于宿主。

### `async with Client(...)` 对一个 stdio 服务器到底做了什么？
进入时，传输层（Transport）根据 `StdioServerParameters`（command、args、env、cwd）派生子进程，并连接到它的 stdin/stdout。然后客户端协商协议。在自动模式下，它会探测 `server/discover`，如果支持就采用 2026-07-28；对于较旧的服务器，则回退到旧版的 `initialize`/`initialized` 握手。退出时，它会关闭这些流。关闭 stdin 就是 stdio 的关闭信号，如果进程没有退出，它会被终止。没有需要记得调用的 `close()`，块内抛出异常时也同样会完成清理。

### 陷阱题：你的智能体在只有一个服务器时工作正常，但加入第二个服务器后却选错了工具。为什么？
两个服务器可能暴露名称相同或非常相似的工具（`search`），而模型看到的是一个扁平的列表。在简单的 名称→客户端 映射中，冲突的名称可能互相覆盖，或者模型可能混淆它们的描述。解决办法：按服务器对工具名进行命名空间化（Tool Namespacing）（`docs__search`、`tickets__search`），并保留一个指回正确客户端的映射；把描述写得更精确；以及每次请求暴露更少的工具（渐进式发现（Progressive Discovery），第 5.4 课）。

## Glossary
- Host | 宿主应用 | 拥有 LLM、用户界面和智能体循环的应用，它为每个服务器创建一个 MCP 客户端。
- Agent loop | 智能体循环 | 宿主中的循环：调用模型、通过 MCP 执行所请求的工具，并把结果回传，直到模型不再请求为止。
- tool_use block | tool_use 内容块 | 模型输出的一种内容块，指明工具名称、输入以及一个 id，对应的结果必须引用该 id。
- tool_result block | tool_result 内容块 | 用户消息中的一种内容块，携带某个 `tool_use_id` 对应的工具输出，可选地标记为 `is_error`。
- is_error | is_error（错误标记） | 告诉模型某个工具失败了的标志；由 MCP 的 `isError` 映射而来。
- StdioServerParameters | stdio 服务器参数 | 描述要启动的子进程的配置（command、args、env、cwd）；它本身不是连接。
- Transport | 传输层 | 在客户端和服务器之间承载 JSON-RPC 的通道，例如 stdio 或可流式 HTTP。
- read_timeout_seconds | 读取超时 | 在整个客户端范围或单次调用上设置的等待响应的时限，超过后抛出超时错误。
- Iteration guard | 迭代上限保护 | 循环轮数的最大值，用于阻止失控的工具调用。
- Conversation state | 会话状态 | 由宿主拥有的消息历史，为模型提供跨轮次和跨对话回合的上下文。

### 1. 一个供驱动的多工具服务器
我们的服务器暴露了三个可以串联的工具（Tool）：`find_city_code` → `get_forecast` → `convert_temperature`。`get_forecast` 在遇到未知代码时会抛出 `ToolError`，这是一种刻意设计的、可读的失败，模型可以从中恢复。

```python
import json
import logging
import os
from types import SimpleNamespace

from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

logging.getLogger("mcp").setLevel(logging.CRITICAL)

CITIES = {"paris": "PAR", "london": "LON", "tokyo": "TYO"}
FORECASTS = {"PAR": {"today": {"celsius": 17, "rain_probability": 80}, "tomorrow": {"celsius": 21, "rain_probability": 10}},
             "LON": {"today": {"celsius": 14, "rain_probability": 95}, "tomorrow": {"celsius": 15, "rain_probability": 60}},
             "TYO": {"today": {"celsius": 26, "rain_probability": 5}, "tomorrow": {"celsius": 24, "rain_probability": 30}}}

weather = MCPServer("weather")


@weather.tool()
def find_city_code(city: str) -> str:
    """Return the 3-letter forecast code for a city name, e.g. 'Paris' -> 'PAR'."""
    try:
        return CITIES[city.strip().lower()]
    except KeyError:
        raise ToolError(f"Unknown city {city!r}. Known: {sorted(CITIES)}")


@weather.tool()
def get_forecast(code: str, day: str = "today") -> dict:
    """Forecast for a city CODE (use find_city_code first) and day ('today' or 'tomorrow')."""
    if code not in FORECASTS:
        raise ToolError(f"Unknown city code {code!r}. Call find_city_code to get a valid code.")
    return {"code": code, "day": day, **FORECASTS[code][day]}


@weather.tool()
def convert_temperature(celsius: float) -> float:
    """Convert Celsius to Fahrenheit."""
    return round(celsius * 9 / 5 + 32, 1)


print("server ready:", weather.name)
```

### 3. 一个与 Anthropic SDK 接口相同的确定性“模拟 LLM”
为了离线运行，我们需要一个与 Anthropic 客户端接口相同的东西：`llm.messages.create(model=..., max_tokens=..., tools=..., messages=...)`，返回一个带有 `stop_reason` 和 `content` 块（`type`、`text`、`id`、`name`、`input`）的对象。*策略*函数读取对话（包括之前的工具结果和 `is_error` 标志），并决定下一步行动，相当于一个脚本化规划器（Scripted Planner）。这让循环的行为变得可见且可重复。之后换成真正的 `anthropic.Anthropic()` 时，**循环无需任何改动**。

```python
def text_block(text):
    return SimpleNamespace(type="text", text=text)


_ids = iter(range(1, 10_000))
def tool_use(name, args):
    return SimpleNamespace(type="tool_use", id=f"toolu_{next(_ids):03d}", name=name, input=args)


def tool_trace(messages):
    """Pair every tool_use the 'model' made with its tool_result: [{name, input, content, is_error}, ...]."""
    calls = {}
    for m in messages:
        for block in (m["content"] if isinstance(m["content"], list) else []):
            if getattr(block, "type", None) == "tool_use":
                calls[block.id] = {"name": block.name, "input": block.input}
            elif isinstance(block, dict) and block.get("type") == "tool_result":
                calls[block["tool_use_id"]].update(content=block["content"], is_error=block["is_error"])
    return list(calls.values())


class FakeLLM:
    """Mimics anthropic.Anthropic().messages.create with a scripted policy(messages, tool_names) -> blocks."""

    def __init__(self, policy):
        self.policy, self.calls = policy, 0
        self.messages = self                              # so `llm.messages.create(...)` works

    def create(self, *, model, max_tokens, tools, messages):
        self.calls += 1
        blocks = self.policy(messages, {t["name"] for t in tools})
        stop = "tool_use" if any(b.type == "tool_use" for b in blocks) else "end_turn"
        return SimpleNamespace(stop_reason=stop, content=blocks)
```

下面是针对 *“Do I need an umbrella in Paris?”* 这类问题的脚本化策略。为了展示**恢复**过程，它首先*猜测*一个代码（“PARIS”），看到 `is_error` 结果后再纠正方向。随后工具 A 的输出（`PAR`）会作为工具 B 的输入。

```python
import re


def umbrella_policy(messages, tool_names):
    question = messages[0]["content"] if isinstance(messages[0]["content"], str) else ""
    city = re.search(r"in (\w+)", question).group(1)
    day = "tomorrow" if "tomorrow" in question else "today"
    trace = tool_trace(messages)
    if not trace:                                                    # round 1: a careless guess
        return [text_block(f"Let me check the forecast for {city}."), tool_use("get_forecast", {"code": city.upper(), "day": day})]
    last = trace[-1]
    if last["is_error"] and last["name"] == "get_forecast":         # recover: read the error, look up the code
        return [text_block("That code was wrong; looking it up."), tool_use("find_city_code", {"city": city})]
    if last["name"] == "find_city_code" and not last["is_error"]:   # chain: A's output becomes B's input
        return [tool_use("get_forecast", {"code": last["content"], "day": day})]
    if last["name"] == "get_forecast":
        f = json.loads(last["content"])
        verdict = "Yes, take an umbrella" if f["rain_probability"] >= 50 else "No umbrella needed"
        return [text_block(f"{verdict}: {f['rain_probability']}% chance of rain in {city} {day}, {f['celsius']}°C.")]
    return [text_block(f"I could not get a forecast: {last['content']}")]


print("policy defined")
```

### 4. 智能体循环
这是 Messages API 标准的手动工具调用循环，即智能体循环（Agent Loop）：当 `stop_reason == "tool_use"` 时持续循环，原样追加助手内容，然后追加**一条**包含**所有**工具结果的用户消息。它还加入了迭代上限保护（Iteration Guard），并把传输错误（例如超时）转换为 `is_error` 结果，让模型能够作出反应。

```python
from mcp.shared.exceptions import MCPError
import mcp_types as types

MODEL = "claude-opus-5-5"


def text_of(result: types.CallToolResult) -> str:
    return "\n".join(b.text for b in result.content if isinstance(b, types.TextContent))


async def run_agent(client, llm, messages, *, max_iterations=6, verbose=True):
    """Run one user turn to completion. Mutates and returns `messages` (the conversation state)."""
    tools = to_anthropic(await list_all_tools(client))
    for step in range(1, max_iterations + 1):
        response = llm.messages.create(model=MODEL, max_tokens=16000, tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": response.content})
        for block in response.content:
            if block.type == "text" and verbose:
                print(f"  [{step}] model: {block.text}")
        if response.stop_reason != "tool_use":
            return messages
        tool_results = []
        for block in response.content:
            if block.type != "tool_use":
                continue
            try:
                result = await client.call_tool(block.name, block.input)
                content, is_error = text_of(result), bool(result.is_error)
            except MCPError as err:                                   # protocol/transport failure, e.g. timeout
                content, is_error = f"MCP error {err.error.code}: {err.error.message}", True
            if verbose:
                flag = "ERROR " if is_error else ""
                print(f"  [{step}] tool  {block.name}({json.dumps(block.input)}) -> {flag}{' '.join(content.split())[:90]}")
            tool_results.append({"type": "tool_result", "tool_use_id": block.id, "content": content, "is_error": is_error})
        messages.append({"role": "user", "content": tool_results})
    messages.append({"role": "assistant", "content": [text_block(f"Stopped: reached the {max_iterations}-step limit.")]})
    if verbose:
        print(f"  [guard] stopped after {max_iterations} iterations")
    return messages


def final_text(messages):
    return " ".join(b.text for b in messages[-1]["content"] if getattr(b, "type", None) == "text")


async with Client(weather) as client:
    llm = FakeLLM(umbrella_policy)
    convo = await run_agent(client, llm, [{"role": "user", "content": "Do I need an umbrella in Paris?"}])
    print("\nFINAL:", final_text(convo), f"| model calls: {llm.calls}, messages in history: {len(convo)}")
```

阅读这段输出轨迹。第 1 轮失败（`is_error`），第 2 轮通过 `find_city_code` 恢复，第 3 轮把它的输出 `PAR` 串联进 `get_forecast`，第 4 轮给出回答。教程中固定两次调用的版本在失败之后就会停下。

### 5. 检查会话状态
`messages` 列表*就是*智能体的记忆，也就是会话状态（Conversation State）。下面以 JSON 形式展示它，可以看到每个 `tool_use` id 与 `tool_result` 的配对。

```python
def jsonable(message):
    content = message["content"]
    if isinstance(content, list):
        content = [vars(b) if isinstance(b, SimpleNamespace) else b for b in content]
    return {"role": message["role"], "content": content}


for m in convo[:4]:
    print(json.dumps(jsonable(m))[:260])
print("...")
```

后续问题会被追加到**同一个**列表中。这就是跨轮次的会话状态。“there（那里）”之所以有意义，只是因为第一个问题（关于巴黎）还在历史记录中。我们的脚本化策略从 `messages[0]` 中读取城市，而真正的模型会直接阅读全部内容。

```python
def followup_policy(messages, tool_names):
    question = messages[-1]["content"] if isinstance(messages[-1]["content"], str) else None
    if question and "tomorrow" in question:                     # the model resolves "there" from history
        city = re.search(r"in (\w+)", messages[0]["content"]).group(1)
        return [tool_use("find_city_code", {"city": city})]
    last = tool_trace(messages)[-1]
    if last["name"] == "find_city_code":
        return [tool_use("get_forecast", {"code": last["content"], "day": "tomorrow"})]
    f = json.loads(last["content"])
    return [text_block(f"Tomorrow there: {f['rain_probability']}% rain, {f['celsius']}°C.")]


async with Client(weather) as client:
    convo.append({"role": "user", "content": "And tomorrow there?"})
    convo = await run_agent(client, FakeLLM(followup_policy), convo)
    print("FINAL:", final_text(convo), "| history length:", len(convo))
```

### 7. 在真实的 stdio 子进程上运行同一个循环
现在服务器作为一个独立进程运行，就像教程中那样。我们使用 `Client(stdio_client(StdioServerParameters(...)))`，这正是教程中的写法，即标准输入输出传输（stdio Transport）。服务器增加了一个刻意设计得很慢的工具。在 `read_timeout_seconds=1` 的设置下，这个慢调用会抛出超时 `MCPError`，循环把它转换为 `is_error` 结果，模型随后改用另一个工具。

```python
import sys
import tempfile
import textwrap
from pathlib import Path

from mcp import StdioServerParameters
from mcp.client.stdio import stdio_client

workdir = Path(tempfile.mkdtemp())
server_file = workdir / "weather_server.py"
server_file.write_text(textwrap.dedent('''
    import time
    from mcp.server import MCPServer
    from mcp.server.mcpserver.exceptions import ToolError

    server = MCPServer("weather-stdio", log_level="CRITICAL")
    CODES = {"paris": "PAR", "london": "LON"}

    @server.tool()
    def find_city_code(city: str) -> str:
        """Return the 3-letter forecast code for a city name."""
        if city.lower() not in CODES:
            raise ToolError(f"Unknown city {city!r}")
        return CODES[city.lower()]

    @server.tool()
    def live_radar(code: str) -> str:
        """High-resolution live radar (slow)."""
        time.sleep(3)
        return f"radar for {code}: heavy rain"

    @server.tool()
    def get_forecast(code: str) -> dict:
        """Forecast for a city CODE."""
        return {"code": code, "rain_probability": {"PAR": 80, "LON": 95}.get(code, 0)}

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))


def radar_policy(messages, tool_names):
    trace = tool_trace(messages)
    if not trace:
        return [tool_use("find_city_code", {"city": "London"})]
    last = trace[-1]
    if last["name"] == "find_city_code":
        return [tool_use("live_radar", {"code": last["content"]})]
    if last["name"] == "live_radar" and last["is_error"]:
        return [text_block("Radar timed out; using the forecast instead."), tool_use("get_forecast", {"code": "LON"})]
    f = json.loads(last["content"])
    return [text_block(f"Yes: {f['rain_probability']}% chance of rain in London (from {last['name']}).")]


params = StdioServerParameters(command=sys.executable, args=[str(server_file)])
async with Client(stdio_client(params), read_timeout_seconds=1.0) as client:
    print("connected over stdio:", client.server_info.name, "| protocol", client.protocol_version)
    print("tools:", [t.name for t in await list_all_tools(client)])
    convo3 = await run_agent(client, FakeLLM(radar_policy), [{"role": "user", "content": "Is it raining in London?"}])
    print("FINAL:", final_text(convo3))
print("subprocess stopped when the async with block exited")
```

### 8. *不是*工具错误的错误
在这个 SDK 中，调用一个不存在的工具或传入无效参数，仍然会返回一个带 `isError: true` 的结果。而超时过长的调用则会抛出异常。一个好的宿主（Host）能处理全部三种情况，而不会让聊天崩溃。

```python
async with Client(StdioServerParameters(command=sys.executable, args=[str(server_file)])) as client:
    r = await client.call_tool("no_such_tool", {})
    print("unknown tool  -> isError:", r.is_error, "|", text_of(r))
    r = await client.call_tool("find_city_code", {"city": "Atlantis"})
    print("ToolError     -> isError:", r.is_error, "|", text_of(r))
    try:
        await client.call_tool("live_radar", {"code": "PAR"}, read_timeout_seconds=0.5)
    except MCPError as err:
        print("timeout       -> MCPError", err.error.code, err.error.message)
```
