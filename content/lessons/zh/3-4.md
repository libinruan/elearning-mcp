## Summary
一个连接了十个服务器的宿主（Host），不可能在每次调用模型之前都重新获取每一份工具列表，但它也不能依据过期的定义行事。2026-07-28 修订版给出了两个互补的答案。**缓存**（拉取）：`server/discover`、各个列表方法以及 `resources/read` 的结果都是可缓存结果（CacheableResult），携带 `ttlMs`——客户端可以把它们视为新鲜的时长——以及 `cacheScope`——共享缓存能否在不同用户之间复用它们。**订阅**（推送）：`subscriptions/listen` 打开一条长期存在的流，服务器只在这条流上发送客户端选择接收的变更通知（Notification），每条都打上 `subscriptionId` 标记。本课详细讲解这两个页面——TTL 语义、缓存键（Cache Key）、分页、作用范围的安全性、确认、多路复用、取消和优雅关闭（Graceful Closure）——以及为什么 `subscriptions/listen` 取代了 HTTP GET 流和 `resources/subscribe`。

## Lesson
### 新鲜度问题
工具、提示模板和资源列表很少变化，但它们*确实*会变：安装了一个插件、授予了一项权限、编辑了一个文件。因此客户端（Client）面临一个权衡。重新获取太频繁，会浪费往返次数（而且对于放在 LLM 提示词里的工具列表来说，还会破坏提示缓存（Prompt Caching））；重新获取太少，模型就会去调用一个已经不存在的工具。MCP 的答案与 HTTP 类似，把服务器给出的**新鲜度提示**与发生变化时的**失效信号**结合起来。缓存页面说得很直白：缓存与变更通知是互补的，两种机制可以共存。

### 哪些结果可缓存
对于以下方法的 `resultType: "complete"` 结果，服务器**必须（MUST）**附带缓存提示：

| 方法 | 典型范围 |
| --- | --- |
| `server/discover` | public |
| `tools/list`、`prompts/list`、`resources/templates/list` | 若对所有用户相同则为 public |
| `resources/list` | public；若按用户过滤则为 private |
| `resources/read` | 通常为 private（用户数据） |

中间态的 `input_required` 结果（多轮往返，第 5.3 课）是**不可**缓存的，也不携带提示。`tools/call`、`prompts/get` 和 `completion/complete` 根本不在此列。在模式（Schema）中，这些结果扩展自可缓存结果（CacheableResult），后者增加了两个必填字段。变更日志记录这是 2026-07-28 版本的新内容（SEP-2549）。

### `ttlMs`：新鲜度提示
`ttlMs` 是一个以毫秒为单位的整数，表示客户端可以（MAY）将结果视为新鲜的时长——语义类似于 HTTP 的 `Cache-Control: max-age`。

| 取值 | 客户端行为 |
| --- | --- |
| `0` | 应当（SHOULD）视为立即过期；可以（MAY）每次都重新获取 |
| 正数 | 应当（SHOULD）在收到后的这么多毫秒内视为新鲜 |
| 缺失 | 应当（SHOULD）假定为 `0`（只有较旧的服务器才会省略它），并使用自己的启发式规则或通知 |
| 负数 | 应当（SHOULD）忽略它并视为 `0`；服务器**必须（MUST）**发送 `>= 0` 的值 |

新鲜度依据本地接收时间计算：当 `now < t_received + ttlMs` 时为新鲜；此后该条目即**过期（Stale）**，客户端应当（SHOULD）在下次访问时重新获取。

有三条规则可以防止常见错误：

- **TTL 不是轮询间隔。** 客户端不应当（SHOULD NOT）在 TTL 到期时安排后台重新获取；它们在*需要数据时*才检查新鲜度。无论如何仍要轮询的实现**必须（MUST）**加入抖动和退避——否则成千上万个 TTL 相同的客户端会同步地蜂拥冲击服务器。
- **TTL 不是保证。** 服务器可以（MAY）在 TTL 到期前改变数据。当客户端有理由相信数据已变时，可以（MAY）提前重新获取——例如某次 `tools/call` 因为工具已不存在或参数已失效而失败。
- **过期的也比没有强。** 如果重新获取失败（网络问题、服务器宕机），客户端可以（MAY）提供过期的响应。

### `cacheScope`：谁可以复用
`cacheScope` 取值为 `"public"` 或 `"private"`，类似于 HTTP 的 `Cache-Control: public` / `private`。

| 取值 | 含义 |
| --- | --- |
| `"public"` | 不含用户特定数据。任何客户端、共享网关或缓存代理都可以（MAY）存储它，并将其提供给**任何**用户。 |
| `"private"` | 包含私有数据。只可以（MAY）在**同一授权上下文**内复用；缓存**不得（MUST NOT）**跨授权上下文共享（不同的访问令牌需要不同的缓存）。 |

public 适合对所有人都相同的工具、提示模板和模板列表；private 适合读取用户数据的 `resources/read`，以及按调用方权限过滤的列表结果。

### 缓存键
一条缓存的响应由缓存键（Cache Key）标识，即**请求方法加上影响结果的参数**——对 `resources/read` 是 `uri`，对分页列表是 `cursor`。对于方法或参数不同的请求，客户端**不得（MUST NOT）**提供缓存的响应。通过携带 `inputResponses` 或 `requestState` 重试而得到的结果**不得（MUST NOT）**缓存：它们依赖于键之外的输入。

### 通知使缓存失效；分页按页缓存
服务器可以只给 TTL 而不提供 `listChanged`（客户端仅依赖 TTL），也可以两者都提供——这时 TTL 避免了两次通知之间不必要的重新获取，而**通知（Notification）就是立即失效（Invalidation）**：在条目新鲜期间收到一条相关通知，会使它立刻过期。

```text
t=0     tools/list  -> {tools, ttlMs: 300000}   cache it, fresh 5 min
t=2m    need tools  -> fresh, serve from cache   (no request)
t=3m    notifications/tools/list_changed         invalidate now
t=3m    need tools  -> stale, tools/list again
```

对于分页列表，**每一页都是可独立缓存的响应**：每页都有自己的 `ttlMs` 和新鲜度计时（服务器可以（MAY）给前面的页更长的 TTL）；过期的页用其游标重新获取。不同页之间没有一致性保证——如果遍历途中数据发生变化，可能出现重复或遗漏——因此需要一致快照的客户端应当（SHOULD）从头重新获取。如果某个游标失效，客户端应当（SHOULD）丢弃所有已缓存的页并重新开始。服务器**必须（MUST）**在一个列表的每一页上使用相同的 `cacheScope`。

### 共享缓存的安全性
一个 `"public"` 结果可以在调用方之间共享，**即使它来自经过认证的端点**：网关可以把用 Alice 的令牌（Token）获取的 `tools/list` 提供给 Bob。因此服务器作者应当让 `cacheScope` 反映每个原语（Primitive）的真实可见性，并且**必须（MUST）**实施逐原语的访问控制，而不是依赖 `cacheScope` 来防止未授权访问。把按用户区分的列表错标为 public，共享缓存就会把它泄露出去；在每次 `tools/call` 和 `resources/read` 时都检查授权（Authorization），这样泄露的列表才不会变成泄露的访问权。

### `subscriptions/listen`：一条选择加入的流
`subscriptions/listen` 打开一条从服务器到客户端的**长期通知流**。与普通请求（Request）不同，它会一直保持打开，持续传递通知，直到被取消。它**取代**了以前的 `resources/subscribe` / `resources/unsubscribe` RPC 以及可流式 HTTP（Streamable HTTP）的 **GET 端点**。

```json
{"jsonrpc": "2.0", "id": 1, "method": "subscriptions/listen",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"},
                      "io.modelcontextprotocol/clientCapabilities": {}},
            "notifications": {"toolsListChanged": true,
                              "resourceSubscriptions": ["file:///project/config.json"]}}}
```

| 过滤字段 | 类型 | 传递的通知 |
| --- | --- | --- |
| `toolsListChanged` | boolean | `notifications/tools/list_changed` |
| `promptsListChanged` | boolean | `notifications/prompts/list_changed` |
| `resourcesListChanged` | boolean | `notifications/resources/list_changed` |
| `resourceSubscriptions` | string[] | 这些 URI 的 `notifications/resources/updated` |

所有字段都是可选的；省略某个字段就表示不订阅它。服务器**不得（MUST NOT）**发送客户端未显式请求的通知类型。

**为什么要改？** 旧模型有三个问题。GET 流只存在于 HTTP 上，所以 stdio 和 HTTP 的行为不一致。它传递的是服务器自己选择推送的任何内容，没有选择加入机制。而 `resources/subscribe` 会在服务器上产生逐会话的状态——这与任何实例都可能处理任何请求的无状态协议（Stateless Protocol）不相容。listen 请求是自包含的（它携带自己的 `_meta` 和过滤器），在两种传输（Transport）上表现完全一致（在 HTTP 上它是一个 POST，其响应就是 SSE 流），而服务器除了这条打开的流本身之外不保存任何东西。`notifications/progress` 和 `notifications/message` 这类请求作用域的通知**不**使用它；它们仍然在所属请求的响应流上传递。

### 确认与 `subscriptionId`
服务器**必须（MUST）**把 `notifications/subscriptions/acknowledged` 作为订阅的**第一条**消息发送，并在 `_meta` 中携带 `io.modelcontextprotocol/subscriptionId`，并且在确认之前不得（MUST NOT）在该订阅上发送任何通知（Notification）。它的 `notifications` 字段反映的是服务器**同意遵从**的子集——不支持的类型会被省略——客户端应当（SHOULD）将其与自己请求的内容比较，并优雅降级（Graceful Degradation）（例如对不支持的列表退回到 TTL 轮询）。

```json
{"jsonrpc": "2.0", "method": "notifications/subscriptions/acknowledged",
 "params": {"_meta": {"io.modelcontextprotocol/subscriptionId": 1},
            "notifications": {"toolsListChanged": true, "resourceSubscriptions": ["file:///project/config.json"]}}}
```

订阅标识（subscriptionId）**就是 `subscriptions/listen` 请求的 JSON-RPC `id`**，流上的每条通知都携带它。客户端可以（MAY）同时持有**多个并发订阅**——一个用于工具变更，另一个用于一组资源——并用这个 ID 进行多路分解。在 stdio 上，所有内容共享同一条通道，客户端**必须（MUST）**用它来关联消息；“确认优先”的顺序是按订阅定义的，因此其他订阅的消息可以（MAY）穿插在它之前。

### 结束订阅
订阅在以下情况下结束：

- **客户端**取消——关闭 SSE 流（HTTP），或发送引用该 listen 请求 id 的 `notifications/cancelled`（stdio）；
- **服务器**将其拆除（例如关机）——它应当（SHOULD）先对原始请求发送一个成功响应 `{"resultType": "complete", "_meta": {"io.modelcontextprotocol/subscriptionId": 1}}`，然后关闭流（**优雅关闭（Graceful Closure）**）；
- **传输层**关闭（HTTP 超时、TCP 断开、进程退出）。

优雅关闭响应告诉客户端，这次结束是有意为之的；没有它的传输层关闭则意味着意外断开，客户端可以（MAY）把它当作重新连接的触发信号。**不会重放**：重新订阅后，要重新获取你所依赖的数据。在 stdio 上，如果连接被终止后又重新建立，客户端**必须（MUST）**重新发送 `subscriptions/listen`——服务器不会跨重连保存任何订阅状态。

### 完整的客户端策略
1. 获取列表并读取资源；按（方法、参数、授权上下文）分别缓存每一项，并附上其 `ttlMs` 和 `cacheScope`。
2. 为你展示的或交给模型的列表、以及你已附加的资源打开 `subscriptions/listen`；检查确认消息。
3. 收到通知时，使匹配的条目失效（`list_changed` → 该列表；`resources/updated` → 该 `uri`），然后在需要时惰性地重新获取。
4. 遇到优雅关闭或断连时，重新 listen 并重新获取；获取出错时，如果可以接受，就提供过期数据。

## Key points
- 可缓存结果（CacheableResult）为 `server/discover`、`tools/list`、`prompts/list`、`resources/list`、`resources/templates/list` 和 `resources/read` 的结果增加了必填的 `ttlMs` 和 `cacheScope`；`input_required` 结果不可缓存。
- `ttlMs` 是类似 `max-age` 的新鲜度提示：`0` 或缺失 = 过期，负数 = 视为 `0`，服务器必须（MUST）发送 `>= 0`；当 `now < t_received + ttlMs` 时为新鲜。
- TTL 不是轮询间隔（轮询必须（MUST）使用抖动和退避），也不是保证；客户端可以（MAY）提前重新获取，也可以（MAY）在出错时提供过期数据。
- 缓存范围（cacheScope）：`public` 可以在用户和网关之间共享；`private` 只能在同一授权上下文内复用。绝不能依赖它做访问控制。
- 缓存键（Cache Key）= 方法 + 影响结果的参数（`uri`、`cursor`）；多轮往返请求（MRTR）的重试结果不得（MUST NOT）缓存；每一页单独缓存，且范围相同。
- 一条相关通知（Notification）会**立即使**新鲜的缓存条目**失效**。
- `subscriptions/listen` 取代了 HTTP GET 流和 `resources/subscribe`；其过滤器（`toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions`）严格采用选择加入方式。
- 确认消息最先到达，并列出被遵从的子集；每条消息都带有订阅标识（subscriptionId）= listen 请求的 JSON-RPC id，从而支持并发订阅。
- 结束方式：客户端取消（关闭 SSE / `notifications/cancelled`）、服务器的优雅关闭响应，或传输层关闭；不会重放——重新 listen 并重新获取。

## Pitches
### MCP 客户端如何在不持续轮询的情况下保持工具列表新鲜？
靠两种机制配合。每个列表结果都带有 ttlMs 和 cacheScope，所以客户端（Client）可以在它新鲜期间直接从缓存提供——在需要时惰性检查，而不是靠轮询。同时，客户端打开一条 subscriptions/listen 流，请求 toolsListChanged；当服务器的工具发生变化时，它会发送一条通知，立即让缓存失效，于是下一次使用时就会重新获取。在没有通知可用时，TTL 给过期程度设了上限；而通知能让变化立刻可见。

### 什么是 cacheScope？为什么它对安全很重要？
缓存范围（cacheScope）说明谁可以复用一条缓存结果。public 表示其中不含任何用户特定的内容，因此共享网关可以把它提供给任何人，即使它是用某人的令牌获取的。private 表示它只能在同一授权上下文内复用。作为服务器作者，我会把按用户区分的列表和资源读取标为 private，并且仍然在每次调用时检查授权，因为规范明确指出 cacheScope 不是一种访问控制机制。

### MCP 为什么用 subscriptions/listen 取代 resources/subscribe 和 GET 流？
因为它们与无状态协议（Stateless Protocol）不契合。GET 流只存在于 HTTP 上，而且推送什么由服务器说了算；resources/subscribe 则会在服务器上按会话存储订阅状态。subscriptions/listen 是一个自包含的单一请求，带有显式的选择加入过滤器，在 stdio 和 HTTP 上表现一致；服务器会确切地确认它将遵从哪些内容，而且每条通知都打上订阅 id 标记，所以客户端可以同时运行多条流。

## Interview
### 服务器在 `tools/list` 上返回了 `ttlMs: 300000`。接下来五分钟里客户端究竟可以做什么？
它可以（MAY）把该列表视为新鲜的，下次需要工具时跳过重新获取——新鲜度依据本地接收时间计算。它**不应**在第五分钟时安排一次重新获取；而是在下次使用时惰性地检查新鲜度。如果怀疑有变化（某次调用因未知工具错误而失败），它可以（MAY）提前重新获取；而一旦收到 `notifications/tools/list_changed`，它必须（MUST）立即把该条目视为过期（Stale）。在 TTL 期间，服务器（Server）端的数据仍可能变化——它只是提示，而不是保证。

### 哪些参数构成缓存键？哪些东西绝不能缓存？
缓存键（Cache Key）是方法加上影响结果的参数：对 `resources/read` 是 `uri`，对列表分页是 `cursor`。对于方法或这些参数不同的请求，绝不能提供缓存的响应。绝不要缓存 `input_required` 中间结果，也不要缓存任何通过携带 `inputResponses`/`requestState` 重试得到的结果——它们依赖于键之外的输入。对于分页，每一页都是独立的条目，有自己的 TTL，所有页共享同一个 `cacheScope`，而游标失效就意味着丢弃所有已缓存的页。

### 你运营着一个带共享缓存的多租户 MCP 网关（MCP Gateway）。可能出什么问题？
某个服务器把按用户区分的结果标成了 `public`——比如一个按用户权限过滤的 `resources/list`——于是网关把 Alice 的列表提供给了 Bob。缓解措施：按授权上下文给私有条目分区（该上下文从经过验证的令牌派生，绝不从请求数据中获取），只有在你信任服务器的标注时，才在租户之间共享 `public` 条目，并依靠服务器在每次 `tools/call`/`resources/read` 时实施访问控制——规范说它们不得（MUST NOT）仅依赖 `cacheScope`。

### 讲一讲 stdio 上一个 `subscriptions/listen` 请求的生命周期。
客户端（Client）发送 id 为 `7` 的 `subscriptions/listen`，并带上过滤器，比如 `toolsListChanged` 和两个资源 URI。服务器首先发送 `notifications/subscriptions/acknowledged`，其中带有 `_meta.subscriptionId: 7` 和被遵从的子集；客户端将其与自己的请求进行比较。之后，变更以带有 `subscriptionId: 7` 标记的 `notifications/tools/list_changed` 或 `notifications/resources/updated` 形式到达，与共享通道上的其他流量交错在一起。客户端通过针对请求 `7` 的 `notifications/cancelled` 来结束它；如果服务器关机，它应当（SHOULD）以一个 `complete` 结果回复请求 `7`（优雅关闭（Graceful Closure））。重连之后，客户端必须（MUST）重新发送 listen 请求。

### 陷阱题：一个耗时很长的 `tools/call` 的进度通知会出现在 listen 流上吗？
不会。`subscriptions/listen` 只承载选择加入的变更通知（Notification）：工具/提示模板/资源列表的变更，以及资源更新。请求作用域的通知——`notifications/progress`、`notifications/message`——继续在其所属请求的响应流上传递（变更日志明确说明了这一点），因此客户端按请求而不是按订阅来关联进度。而且服务器不得（MUST NOT）发送客户端未请求的类型，所以除非某条流的过滤器请求了列表变更，否则连列表变更也不会出现在这条流上。

## Glossary
- CacheableResult | 可缓存结果 | 携带 `ttlMs` 和 `cacheScope` 缓存提示的结果类型。
- ttlMs | 存活时间（毫秒） | 服务器给出的提示，表示一个结果可被视为新鲜的毫秒数。
- cacheScope | 缓存范围 | `public`（可在用户之间共享）或 `private`（仅限同一授权上下文）。
- Cache key | 缓存键 | 用于标识一条缓存响应的请求方法加上影响结果的参数。
- Stale | 过期（陈旧） | 超过其 TTL 或被通知置为失效的缓存条目；下次使用时需重新获取。
- Invalidation | 缓存失效 | 立即将缓存条目标记为过期，例如在收到列表变更通知时。
- subscriptions/listen | 订阅监听请求 | 一个长期存在的请求，其响应流传递选择接收的变更通知。
- Subscription filter | 订阅过滤器 | 用于选择接收哪些变更通知的 `notifications` 对象。
- subscriptionId | 订阅标识 | 流上每条消息 `_meta` 中的键，其值等于 listen 请求的 JSON-RPC id。
- Graceful closure | 优雅关闭 | 服务器通过向 listen 请求发送 `complete` 响应来结束订阅。

### 1. 每个可缓存结果都携带提示

### 2. 服务器端：选择提示
`MCPServer(cache_hints={method: CacheHint(ttl_ms, scope)})` 按方法设置提示。一个中间件统计实际到达服务器（Server）的请求数，这样我们就能看到客户端缓存在起作用。

```python
from mcp.server.caching import CacheHint

hits = Counter()


async def count_requests(ctx, call_next):
    hits[ctx.method] += 1
    return await call_next(ctx)


server = MCPServer("travel", middleware=[count_requests], cache_hints={
    "tools/list": CacheHint(ttl_ms=300_000, scope="public"),       # same for every user, 5 min

inbox = {"messages": 1}


@server.tool()
```

### 3. 客户端：响应缓存与 `cache_mode`
SDK 的 `Client` 默认遵守提示（`cache=CacheConfig()`）。每个可缓存调用都接受 `cache_mode`：`"use"`（新鲜则从缓存提供，否则获取并存储）、`"refresh"`（总是获取，然后存储）、`"bypass"`（忽略缓存）。`Client(..., cache=None)` 会禁用缓存。

```python
async with Client(server) as client:
    hits.clear()
    await client.list_tools()                         # miss -> server
    await client.list_tools()                         # fresh -> served from cache
    await client.list_tools(cache_mode="refresh")     # forced fetch, re-stored
    await client.list_tools(cache_mode="bypass")      # straight to server
    print("with cache:   ", dict(hits))

async with Client(server, cache=None) as client:
    hits.clear()
    await client.list_tools()
    await client.list_tools()
    print("cache=None:   ", {k: v for k, v in hits.items() if k != "server/discover"})
```

### 4. 新鲜度从接收时间开始计算
`CacheConfig(clock=...)` 让我们可以伪造挂钟时间：当 `now < t_received + ttlMs` 时条目是新鲜的，之后就过期（Stale）。

```python
from mcp.client.caching import CacheConfig

fake_now = [1_000.0]  # seconds

async with Client(server, cache=CacheConfig(clock=lambda: fake_now[0])) as client:
    hits.clear()
    for advance_s in [0, 120, 179.9, 0.2]:
        fake_now[0] += advance_s
        before = hits["tools/list"]
        await client.list_tools()
        print(f"t+{fake_now[0] - 1_000:6.1f}s  ->  {'server' if hits['tools/list'] > before else 'cache '}"
              f"   (ttl {300}s)")
```

在 t=0 收到的条目，在 120 s 和 299.9 s 时是新鲜的（`now < 0 + 300 s`），在 300.1 s 时过期，所以那次请求会发往服务器，新的响应开始一轮新的 300 s 计时。新鲜度是**惰性**检查的，在需要数据的那一刻进行：计时期间没有任何东西在后台被重新获取。

### 5. TTL 是提示而非保证——通知会使缓存失效
一个工具修改了收件箱。没有订阅（Subscription）时，客户端会一直提供缓存的（此时已错误的）值，直到 TTL 用完。有了 `subscriptions/listen`，`notifications/resources/updated` 会立即逐出该条目，下一次读取就会发往服务器。

```python
@server.tool()
async def receive_mail(ctx: Context) -> int:
    """Simulate new mail arriving."""
    inbox["messages"] += 1
    await ctx.notify_resource_updated("inbox://me")
    return inbox["messages"]


async with Client(server) as client:
    print("read:", (await client.read_resource("inbox://me")).contents[0].text)
    await client.call_tool("receive_mail", {})
    print("after change, no subscription:", (await client.read_resource("inbox://me")).contents[0].text, "<- stale!")

    async with client.listen(resource_subscriptions=["inbox://me"]) as sub:
        await client.call_tool("receive_mail", {})
        event = await anext(sub)
        hits.clear()
        print("event:", event)
        print("after notification:", (await client.read_resource("inbox://me")).contents[0].text,
              "| reached server:", hits["resources/read"] == 1)
```

### 6. 线路上的 `subscriptions/listen`
深入 SDK 之下，通过 stdio：两个过滤器不同的**并发**订阅、最先到达的确认、`subscriptionId` 标记、选择加入式过滤、通过 `notifications/cancelled` 进行的客户端取消，以及由服务器发起的**优雅关闭（Graceful Closure）**。（`shutdown_streams` 工具调用了 SDK 的一个内部接口，只是为了触发服务器在关机时会做的事情。）

```python
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
import time
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "watch_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    from mcp.server.caching import CacheHint
    from mcp.server.mcpserver import Context

    server = MCPServer("watchable", cache_hints={"tools/list": CacheHint(ttl_ms=300_000, scope="public")})
    config = {"theme": "dark"}

    @server.resource("config://app", mime_type="application/json")
    def app_config() -> str:
        return str(config)

    @server.tool()
    async def set_theme(theme: str, ctx: Context) -> str:
        """Change the theme (updates config://app)."""
        config["theme"] = theme
        await ctx.notify_resource_updated("config://app")
        return "ok"

    @server.tool()
    async def install_plugin(name: str, ctx: Context) -> str:
        """Install a plugin, which adds a tool."""
        server.add_tool(lambda: f"{name} says hi", name=f"{name}_hello", description=f"Greeting from {name}")
        await ctx.notify_tools_changed()
        return "installed"

    @server.tool()
    async def shutdown_streams() -> str:
        """Demo only: end all listen streams gracefully, as on server shutdown."""
        server._lowlevel_server._request_handlers["subscriptions/listen"].handler.close()
        return "closing"

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "watch_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
inbound: queue.Queue = queue.Queue()
threading.Thread(target=lambda: [inbound.put(line) for line in proc.stdout], daemon=True).start()
META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def send(message):
    message.setdefault("params", {})["_meta"] = META
    shown = {k: v for k, v in message.items() if k != "jsonrpc"}
    shown["params"] = {k: v for k, v in message["params"].items() if k != "_meta"}
    print(">>>", json.dumps(shown))
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()


def drain(seconds=0.6):
    deadline = time.time() + seconds
    while (left := deadline - time.time()) > 0:
        try:
            msg = json.loads(inbound.get(timeout=left))
        except queue.Empty:
            break
        if "result" in msg and "tools" in msg["result"]:
            msg["result"] = {k: msg["result"][k] for k in ("ttlMs", "cacheScope")} | {"tools": "[...]"}
        elif "result" in msg:
            msg["result"].get("_meta", {}).pop("io.modelcontextprotocol/serverInfo", None)
            msg["result"] = {k: v for k, v in msg["result"].items()
                             if k in ("resultType", "structuredContent") or (k == "_meta" and v)}
        print("    <<<", json.dumps({k: v for k, v in msg.items() if k != "jsonrpc"}))


send({"jsonrpc": "2.0", "id": 1, "method": "tools/list"}); drain()
send({"jsonrpc": "2.0", "id": "tools-sub", "method": "subscriptions/listen",
      "params": {"notifications": {"toolsListChanged": True}}})
send({"jsonrpc": "2.0", "id": "cfg-sub", "method": "subscriptions/listen",
      "params": {"notifications": {"resourceSubscriptions": ["config://app"]}}}); drain()
print("\n# a resource change reaches only cfg-sub:")
send({"jsonrpc": "2.0", "id": 2, "method": "tools/call", "params": {"name": "set_theme", "arguments": {"theme": "light"}}}); drain()
print("\n# a tool-list change reaches only tools-sub:")
send({"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "install_plugin", "arguments": {"name": "maps"}}}); drain()
print("\n# cancel cfg-sub, then change the resource again: silence")
send({"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": "cfg-sub"}}); drain(0.3)
send({"jsonrpc": "2.0", "id": 4, "method": "tools/call", "params": {"name": "set_theme", "arguments": {"theme": "solarized"}}}); drain()
print("\n# the server shuts its streams down gracefully:")
send({"jsonrpc": "2.0", "id": 5, "method": "tools/call", "params": {"name": "shutdown_streams", "arguments": {}}}); drain()
proc.stdin.close()
_ = proc.wait(timeout=10)
```

仔细阅读：每条确认都先于其订阅上的任何通知；每条流消息都把 listen 请求的 id 作为 `subscriptionId` 携带；最后一条消息是 id 为 `tools-sub` 的**响应**——也就是优雅关闭。

### 7. 用 SDK 做同样的事：`client.listen()`
`client.listen(...)` 发送请求，等待确认（`sub.honored`、`sub.subscription_id`），然后产出带类型的事件。两个订阅可以同时运行；当服务器优雅关闭（Graceful Closure）时，`async for` 循环就会直接结束。

```python
catalogue = MCPServer("catalogue")
prompts_enabled = []


@catalogue.tool()
async def add_feature(name: str, ctx: Context) -> str:
    """Add a prompt and a tool, then tell subscribers."""
    catalogue.add_tool(lambda: name, name=f"{name}_tool", description=f"{name} tool")
    await ctx.notify_tools_changed()
    prompts_enabled.append(name)
    await ctx.notify_prompts_changed()
    return "added"


async with Client(catalogue) as client:
    async with client.listen(tools_list_changed=True) as tools_sub, \
               client.listen(prompts_list_changed=True, resources_list_changed=True) as other_sub:
        print("subscription ids:", tools_sub.subscription_id, other_sub.subscription_id)
        print("honoured:", tools_sub.honored.model_dump(by_alias=True, exclude_none=True),
              other_sub.honored.model_dump(by_alias=True, exclude_none=True))
        await client.call_tool("add_feature", {"name": "maps"})
        print(f"{tools_sub.subscription_id} got:", await anext(tools_sub))
        print(f"{other_sub.subscription_id} got:", await anext(other_sub))

        # graceful closure from the server side (SDK internal, demo only)
        catalogue._lowlevel_server._request_handlers["subscriptions/listen"].handler.close()
        leftovers = [event async for event in tools_sub]
        print("tools_sub ended gracefully; leftover events:", leftovers)
```

### 8. 动手破坏：共享缓存中被错标为 `public` 的结果
一个网关在用户之间共享同一个缓存存储，按授权上下文分区，并选择启用对 `public` 条目的共享（`share_public=True`）。如果服务器把一次*私有*的收件箱读取标为 `public`，Bob 就会拿到 Alice 的邮件，而服务器甚至从未看到他的请求。

```python
from mcp.client.caching import InMemoryResponseCacheStore

mail = {"alice": "Alice: your flight is confirmed", "bob": "Bob: nothing new"}


def make_mail_server(scope):
    srv = MCPServer("mail", middleware=[count_requests],
                    cache_hints={"resources/read": CacheHint(ttl_ms=60_000, scope=scope)})
    current_user = {"name": "alice"}   # stand-in for the authenticated principal

    @srv.resource("mail://inbox")
    def mailbox() -> str:
        return mail[current_user["name"]]

    return srv, current_user


for scope in ["public", "private"]:
    srv, current_user = make_mail_server(scope)
    store = InMemoryResponseCacheStore()   # one shared gateway cache
    hits.clear()
    for user in ["alice", "bob"]:
        current_user["name"] = user
        config = CacheConfig(store=store, partition=user, target_id="mail-server", share_public=True)
        async with Client(srv, cache=config) as client:
            text = (await client.read_resource("mail://inbox")).contents[0].text
            print(f"cacheScope={scope:<7} {user:<5} sees: {text!r}")
    print(f"   server saw {hits['resources/read']} resources/read request(s)\n")
```

使用 `private` 时，每个用户的条目都位于自己的分区中，Bob 的读取会发往服务器。修复应当在**服务器**端进行（把用户数据标为 `private`，并对每个请求实施访问控制）——而网关只应对其信任的服务器启用 `share_public`。
