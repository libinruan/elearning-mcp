## Summary
每个有用的 AI 应用都需要从别处获取上下文（Context）：文件、数据库、日历、工单系统、搜索。在 MCP 出现之前，每个应用都要为每个系统各写一套连接器——这就是一次性胶水代码的 N×M 爆炸。模型上下文协议（Model Context Protocol）是一个开放标准，它把这个问题变成了 N+M：一个系统只需被封装一次，成为 **MCP 服务器（MCP Server）**，任何 **MCP 宿主（MCP Host）**（Claude、ChatGPT、VS Code、Cursor 或你自己的智能体（Agent））都可以通过客户端（Client）使用它。本课将建立起整体的心智模型——USB-C 类比、三种服务器原语（Primitive）、JSON-RPC 的作用、安全原则与设计哲学——最后让一个可运行的客户端与真实服务器对话。

## Lesson
### 问题所在：上下文是瓶颈
语言模型本身只知道它的训练数据和提示词里的内容。一切让 AI 应用变得*有用*的事情——读取你的代码仓库、查询销售数据库、创建日历事件、提交工单——都需要把模型连接到外部系统。每个连接都需要两样东西：一种**向模型提供上下文（Context）**的方式（它可以读取的数据），以及一种**让模型采取行动**的方式（它可以调用的函数）。

在标准出现之前，每个 AI 应用都在私下解决这个问题。一个聊天助手写了自己的 GitHub 集成，一个 IDE 又写了一个，一个内部智能体（Agent）再写第三个。有 *N* 个 AI 应用和 *M* 个外部系统时，整个行业要写将近 **N × M** 个集成，每个都有自己的认证处理、模式（Schema）约定和 bug。更糟的是，为一个应用打造的工具无法被另一个应用复用。

### 解决方案：一个协议，N + M 个集成
官方定义是：*MCP（Model Context Protocol，模型上下文协议）是一个用于把 AI 应用连接到外部系统的开源标准。* 借助 MCP，Claude 或 ChatGPT 这样的应用可以连接到**数据源**（本地文件、数据库）、**工具（Tool）**（搜索引擎、计算器）和**工作流**（专门的提示词）。

文档中的类比是 **AI 应用的 USB-C**：正如 USB-C 让任何设备都能通过一个标准接口插入任何笔记本电脑，MCP 让任何 AI 应用都能通过一个标准协议接入任何外部系统。每个系统只被封装一次，成为 MCP 服务器（MCP Server）；每个应用只实现一次 MCP。集成数量变为 **N + M**。

| | 没有 MCP | 有 MCP |
| --- | --- | --- |
| 5 个 AI 应用 × 20 个系统 | 最多 100 个定制集成 | 5 个客户端 + 20 个服务器 = 25 个组件 |
| 出现一个新系统 | 每个应用都必须添加支持 | 写一个服务器，所有应用都能使用 |
| 出现一个新应用 | 必须重新实现每一个集成 | 实现一次 MCP，继承整个生态 |

规范将**语言服务器协议（Language Server Protocol，LSP）**视为灵感来源：LSP 标准化了编辑器与语言工具之间的通信方式，因此同一个 Python 语言服务器可以同样在 VS Code、Vim 和 JetBrains 中工作。MCP 为 AI 应用及其上下文做了同样的事。

### MCP 让什么成为可能
文档给出了一些具体的例子：

- 一个读取你的 **Google Calendar 和 Notion** 的智能体（Agent），充当个性化助手。
- **Claude Code** 根据 **Figma** 设计稿生成整个 Web 应用。
- 一个连接多个数据库的**企业聊天机器人**，让人们可以在聊天中分析数据。
- 一个在 **Blender 中创建 3D 设计**并把它们发送到 3D 打印机的模型。

谁受益取决于你所处的位置：**开发者**在构建和集成上花的时间更少；**AI 应用**获得了一个由数据源、工具和应用组成的生态；**终端用户**获得能够访问他们的数据、并在需要时代表他们行动的助手。这个生态非常广泛——Claude、ChatGPT、Visual Studio Code、Cursor、MCPJam 等众多产品都支持 MCP——所以你可以*一次构建，处处集成*。

### 参与方：宿主、客户端、服务器
规范定义了三种角色（第 1.2 课会深入讲解）：

- **宿主（Host）**——用户与之交互的 AI 应用（Claude Desktop、IDE、你的智能体）。它拥有 LLM、UI 以及用户的同意权。
- **客户端（Client）**——宿主*内部*的一个连接器。宿主为它连接的**每个服务器创建一个客户端**。
- **服务器（Server）**——提供上下文和能力（Capability）的程序。它可以作为子进程在本地运行，也可以通过 HTTP 远程运行。

```text
┌──────────────── Host (AI application) ────────────────┐
│   LLM  ·  UI  ·  consent                               │
│   ┌──────────┐   ┌──────────┐   ┌──────────┐          │
│   │ Client A │   │ Client B │   │ Client C │          │
│   └────┬─────┘   └────┬─────┘   └────┬─────┘          │
└────────┼──────────────┼──────────────┼────────────────┘
         │ stdio        │ HTTP         │ HTTP
   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
   │ Server:   │  │ Server:   │  │ Server:   │
   │ filesystem│  │ GitHub    │  │ database  │
   └───────────┘  └───────────┘  └───────────┘
```

### 服务器提供什么：工具、资源、提示模板
服务器可以暴露三种**原语（Primitive）**中的任意几种，这种划分是有意为之的——每种原语都有不同的*控制方*：

| 原语 | 它是什么 | 谁决定使用它 | 示例 |
| --- | --- | --- | --- |
| **工具（Tools）** | 模型可以执行的函数 | **模型**（需经用户批准） | `search_flights`, `create_issue` |
| **资源（Resources）** | 供读取的上下文和数据 | **应用** | 一个文件、一个数据库模式、一份日历 |
| **提示模板（Prompts）** | 可复用的模板化消息／工作流 | **用户** | “/summarise-PR”、“规划一次度假” |

在客户端一侧，本修订版中的核心特性是**征询（Elicitation）**：一种让服务器在操作进行中向用户索取更多信息的方式（第 5.3 课）。围绕这些的是一些实用功能——进度、取消、错误报告——以及可选启用的**扩展（Extension）**，例如 Tasks（长时间运行的工作）、Skills over MCP 和 MCP Apps（在对话中渲染的交互式 UI）。

### 它们如何通信：JSON-RPC 2.0，无状态请求
所有 MCP 消息都是 **JSON-RPC 2.0**：请求（Request）带有 `method`、`params` 和 `id`；回复带有相同的 `id`，以及 `result` 或 `error` 之一。在 2026-07-28 修订版中，基础协议被描述为**无状态（Stateless）、自包含的请求**，并采用**逐请求的能力协商（Capability Negotiation）**——每个请求都在 `_meta` 中携带自己的协议版本和客户端能力，因此任何服务器实例都可以响应它，而无需记住会话。（更早的修订版在每个连接开始时会进行 `initialize` 握手；在真实代码中你会同时遇到这两种方式——见第 1.3 课。）

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "add", "arguments": {"a": 2, "b": 40},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

同样的消息通过两种标准传输（Transport）方式传递：**stdio**（宿主将服务器作为子进程启动）和**可流式 HTTP（Streamable HTTP）**（服务器是一个 Web 服务）。把*说什么*与*如何传递*分离开来，就是你接下来要学习的数据层（Data Layer）／传输层（Transport Layer）划分。

### 安全是头等大事
MCP 打开了通向任意数据访问和代码执行的通道，因此规范列出了每个实现者都必须处理的原则——尽管协议本身无法强制执行它们：

1. **用户同意与控制（User Consent and Control）**——用户明确同意数据访问和操作，掌控哪些内容被共享，并获得清晰的 UI 来审查和授权各项活动。
2. **数据隐私（Data Privacy）**——宿主在向服务器暴露用户数据之前必须获得同意，未经同意不得将资源数据传输到其他地方。
3. **工具安全（Tool Safety）**——工具就是任意代码执行。对工具行为的描述和注解（Annotations）**除非服务器可信，否则都不可信**，宿主在调用任何工具之前都必须获得同意。

> **陷阱。** “这个工具说它是只读的”并不是安全保证。一个恶意的或被攻陷的服务器可以随意描述自己。第 6 模块会讲解提示注入（Prompt Injection）、令牌透传（Token Passthrough）、混淆代理人问题（Confused Deputy）等内容。

### MCP 背后的设计哲学
维护者公开了一组设计原则，它们解释了你后面会看到的许多决策。了解这些原则能让你*预测*协议的走向，并在面试中就其展开讨论：

- **趋同优于选择（Convergence over choice）**——一个问题只有一种解决方式；扩展是检验想法的地方，规范是承诺想法的地方。
- **可组合性优于特定性（Composability over specificity）**——保持原语精简（工具、资源、提示模板），用它们来构建特性，而不是添加特例。
- **互操作性优于优化（Interoperability over optimisation）**——特性应当能优雅降级（Graceful Degradation）；能力协商让复杂程度不同的对端可以协同工作。
- **稳定优于速度（Stability over velocity）**——每一项新增都是永久性的；“今天说不，门还开着；说是，门就永远关上了”。
- **能力优于补偿（Capability over compensation）**——避免为绕开模型的暂时性弱点而引入永久性结构。
- **演示优于商议（Demonstration over deliberation）**、**务实优于纯粹（Pragmatism over purity）**、**标准化优于创新（Standardisation over innovation）**——优先采用经过验证、已有实现的模式。

例如，这些原则解释了为什么 2026-07-28 *移除*了一些特性（会话、`ping`、服务器发起的请求）并弃用了另一些（根目录（Roots）、采样（Sampling）、日志（Logging））：更小的接口面，更多的趋同。

### MCP 在智能体应用中的位置
对 AI 工程师来说，MCP 是智能体（Agent）的**集成层**：模型负责规划，宿主（Host）运行循环（调用模型 → 模型请求某个工具 → 宿主通过 MCP 调用该工具 → 结果返回给模型），MCP 服务器提供工具和上下文。MCP **不会**规定你使用哪个模型、如何给它写提示词，或者你的智能体循环（Agent Loop）如何运作。它标准化的是“AI 应用”与“其他一切”之间的边界，这正是它能与任何框架或模型提供商组合使用的原因。

## Key points
- MCP 是一个**用于把 AI 应用连接到外部系统的开放标准**——数据源、工具（Tool）和工作流。类比：AI 的 USB-C。
- 它把 **N × M** 个定制集成变为 **N + M**：把一个系统封装一次成为服务器（Server），每个 MCP 宿主（Host）都能使用它。
- 三种角色：**宿主（Host）**（AI 应用）、**客户端（Client）**（宿主内部每个服务器对应一个连接器）、**服务器（Server）**（提供上下文和能力）。
- 三种服务器原语（Primitive），对应三种控制方：**工具（Tools）**（模型控制）、**资源（Resources）**（应用控制）、**提示模板（Prompts）**（用户控制）。
- 消息格式是 **JSON-RPC 2.0**；在 2026-07-28 中，每个请求（Request）都是**自包含的**，在 `_meta` 中携带其协议版本和客户端能力。
- 两种标准传输（Transport）：用于本地子进程服务器的 **stdio**，以及用于远程服务器的**可流式 HTTP（Streamable HTTP）**。
- 灵感来自**语言服务器协议（Language Server Protocol）**，它为编辑器和语言工具做了同样的事。
- 安全原则——同意、隐私、工具安全（Tool Safety）——对实现者是强制性的；除非服务器可信，否则工具的描述和注解都是**不可信的**。
- 设计原则（趋同、可组合、互操作、稳定……）解释了为什么协议保持精简，并会移除特性。

## Pitches
### 一句话说清什么是 MCP？
MCP，也就是模型上下文协议（Model Context Protocol），是一个把 AI 应用连接到外部世界的开放标准——文件、数据库、SaaS API、内部服务都可以。一个系统只需封装一次，成为暴露工具（Tool）、资源（Resource）和提示模板（Prompt）的 MCP 服务器，任何支持 MCP 的宿主（Host）——Claude、ChatGPT、VS Code、Cursor，或者我自己的智能体——都能通过客户端来使用它。它就像 AI 的 USB-C：一个接口，取代每对设备之间各自定制的线缆。

### 为什么行业需要 MCP？
没有标准的话，每个 AI 应用都要给每个系统各写一套连接器，集成工作量按 N 乘以 M 增长，而且什么都没法复用。MCP 把它变成 N 加 M：为 GitHub 写一个服务器（Server），它就能在每个宿主（Host）里工作；写一个宿主，就能继承整个服务器生态。对工程师来说，这意味着我可以把时间花在智能体的逻辑和打磨好用的工具上，而不是为每个应用重写同样的胶水代码。

### MCP 和函数调用是什么关系？
函数调用（Function Calling）是单个模型 API 让模型请求调用我在代码里定义的函数的方式。MCP 位于它外面一层：它标准化的是这些函数从哪里来。我的宿主（Host）从 MCP 服务器列出工具，把它们的名字和 JSON 模式交给我用的任何模型，当模型请求某个工具时，宿主再通过 MCP 客户端去执行。所以 MCP 是一套与模型无关的管道，为函数调用提供输入，此外它还有函数调用根本没有的资源和提示模板概念。

## Interview
### MCP 解决了什么问题？为什么函数调用没有早就解决它？
函数调用（Function Calling）让一个模型请求调用*某一个应用所定义的*函数。每个应用仍然必须编写和维护自己的集成，于是整个行业在构建 N × M 个无法共享的连接器。MCP 标准化的是 **AI 应用与外部系统之间的边界**：发现（`tools/list`）、调用（`tools/call`）、数据访问（资源（Resource））、可复用的工作流（提示模板（Prompt））、传输（Transport）、授权（Authorization）和版本管理。一个服务器写一次，就能在任何合规的宿主中运行，与模型厂商无关。函数调用仍然是宿主*内部*让模型选择工具的机制；而 MCP 则是宿主获得这个工具的方式。

### 解释宿主、客户端和服务器。为什么每个服务器对应一个客户端？
**宿主（Host）**就是 AI 应用：它拥有模型、UI 和用户同意权。**客户端（Client）**是宿主内部的一个连接器，它与恰好一个**服务器（Server）**保持对话，而服务器负责暴露能力（Capability）。每个服务器对应一个客户端，使每个连接都相互隔离：能力、协议版本、凭据和故障都是按服务器划分的，并且由宿主——而不是服务器——决定数据如何在它们之间流动。除非宿主选择传递，否则文件系统服务器永远看不到 GitHub 服务器返回了什么。

### 谁控制工具、资源和提示模板？这为什么重要？
工具（Tool）是**模型控制（Model-controlled）**的：由 LLM 决定是否调用（宿主负责强制执行用户批准）。资源（Resource）是**应用控制**的：由宿主决定附加哪些上下文，例如用户选中的某个文件。提示模板（Prompt）是**用户控制（User-controlled）**的：由用户显式调用，通常以斜杠命令（Slash Command）的形式出现。这一区分决定了用户体验和安全性：有副作用的操作应当是放在同意关卡之后的工具，由应用整理的只读上下文应当是资源，而由人触发的可复用工作流应当是提示模板。

### MCP 在设计上是安全的吗？
协议定义了一些机制——针对 HTTP 服务器的基于 OAuth 的授权（Authorization）、能力协商（Capability Negotiation）、同意要求——但规范明确指出 **MCP 无法在协议层面强制保证安全**；必须由实现者来保证。宿主在暴露数据或调用工具之前必须获得用户同意，并且除非服务器本身可信，否则必须把工具描述和注解视为不可信。真正的风险在边缘：通过工具结果进行的提示注入（Prompt Injection）、恶意的本地服务器、权限范围过大的令牌（Token）、令牌透传（Token Passthrough）。一个好的回答会点出这些风险以及相应的缓解措施（沙箱（Sandbox）、限定范围的令牌、人在回路（Human in the Loop）审批）。

### MCP “受 LSP 启发”是什么意思？
语言服务器协议（Language Server Protocol，LSP）让一个语言服务器（比如 Rust 的）能在每个编辑器中工作，终结了“编辑器 × 语言”的矩阵。MCP 把同样的做法应用到 AI 上：每个外部系统一个服务器，可以从每个 AI 宿主中使用。它还借鉴了 LSP 的技术形态——JSON-RPC 2.0 消息和能力协商（Capability Negotiation）——使得特性集合不同的对端仍然能够互操作。

### 什么时候你*不会*使用 MCP？
如果某个集成只属于一个应用、只被一条模型调用路径使用，而且永远不会被共享，那么直接在代码里使用普通的函数调用（Function Calling）更简单。当工具应当跨宿主复用、由另一个团队负责、为了隔离而运行在单独的进程中，或者要提供给第三方时，MCP 才会带来回报。当你希望用户把他们自己的系统接入你的智能体时，它也是自然之选。

## Glossary
- Model Context Protocol (MCP) | 模型上下文协议 | 一个用于把 AI 应用连接到外部数据源、工具和工作流的开放标准。
- Host | 宿主（宿主应用） | 用户与之交互的 AI 应用；它拥有模型、UI 和同意权，并为每个服务器创建一个客户端。
- Client | 客户端 | 宿主内部的连接器，与恰好一个 MCP 服务器保持连接。
- Server | 服务器 | 在本地或远程向 MCP 客户端暴露工具、资源和提示模板的程序。
- Tool | 工具 | 由服务器暴露、模型可以决定调用的函数。
- Resource | 资源 | 由 URI 标识、可被应用附加的只读上下文或数据。
- Prompt | 提示模板 | 由用户显式调用的可复用、参数化的消息模板。
- JSON-RPC 2.0 | JSON-RPC 2.0 远程过程调用协议 | 所有 MCP 消息所使用的轻量级请求／响应消息格式。
- Language Server Protocol (LSP) | 语言服务器协议 | 启发了 MCP 设计的编辑器工具标准。
- N×M integration problem | N×M 集成问题 | 当每个 AI 应用都必须分别集成每个系统时，定制连接器数量的爆炸式增长。

## Notebook
### 1. 用数字看 N × M 问题
在编写任何使用 MCP 通信的代码之前，先把这个经济学论证具体化。改一改数字，看看差距如何扩大。

```python
def integrations(apps: int, systems: int) -> tuple[int, int]:
    """Connectors to write without a standard vs. with MCP."""
    return apps * systems, apps + systems


for apps, systems in [(3, 5), (10, 50), (40, 2000)]:
    without, with_mcp = integrations(apps, systems)
    print(f"{apps:>3} apps × {systems:>4} systems -> {without:>6} bespoke connectors | "
          f"{with_mcp:>5} MCP components  ({without / with_mcp:.0f}x less work)")
```

### 2. 第一个服务器：一个工具、一个资源、一个提示模板
官方 Python SDK（`mcp` 2.x）提供了 `MCPServer`。装饰器把普通的 Python 函数变成三种原语（Primitive）：类型注解变成模型看到的 JSON 模式（Schema），文档字符串变成描述。

```python
import json

from mcp import Client
from mcp.server import MCPServer

notes = {"mcp": "MCP is USB-C for AI applications.", "lsp": "LSP inspired MCP's design."}

server = MCPServer("notes")


@server.tool()
def search_notes(query: str) -> list[str]:
    """Return the ids of notes whose text contains the query (case-insensitive)."""
    return [nid for nid, text in notes.items() if query.lower() in text.lower()]


@server.resource("notes://{note_id}")
def read_note(note_id: str) -> str:
    """The full text of one note."""
    return notes[note_id]


@server.prompt()
def explain(topic: str) -> str:
    """Ask the model to explain a topic to a beginner."""
    return f"Explain {topic} to a new AI engineer in three sentences."


print("server defined:", server.name)
```

### 3. 连接客户端，发现服务器提供的内容
`Client(server)` 在进程内建立连接——非常适合学习和测试。客户端（Client）在运行时*发现*能力（Capability）：客户端一侧没有硬编码任何关于工具的信息。

```python
async with Client(server) as client:
    print("protocol version:", client.protocol_version)
    tools = (await client.list_tools()).tools
    templates = (await client.list_resource_templates()).resource_templates
    prompts = (await client.list_prompts()).prompts

    for t in tools:
        print("TOOL     ", t.name, "-", t.description)
        print("          input schema:", json.dumps(t.input_schema))
    for r in templates:
        print("RESOURCE ", r.uri_template, "-", r.description)
    for p in prompts:
        print("PROMPT   ", p.name, "- args:", [a.name for a in p.arguments or []])
```

### 4. 使用全部三种原语
注意三种不同的*控制方*：模型会调用工具（Tool），应用读取资源（Resource），用户挑选提示模板（Prompt）。

```python
async with Client(server) as client:
    hit = await client.call_tool("search_notes", {"query": "usb"})      # model-controlled
    print("tools/call      ->", hit.structured_content, "| isError:", hit.is_error)

    doc = await client.read_resource("notes://mcp")                      # application-controlled
    print("resources/read  ->", doc.contents[0].text)

    msg = await client.get_prompt("explain", {"topic": "MCP"})          # user-controlled
    print("prompts/get     ->", msg.messages[0].content.text)
```

### 5. 一次构建，处处集成
两个完全不同的“宿主（Host）”复用*同一个*服务器，而且两者都不需要事先知道它有哪些工具：一个只列出能力的仪表盘，以及一个通过阅读描述来挑选工具的小型关键词“智能体”。这就是用代码表达的 N + M 论证。

```python
async def dashboard_host(srv):
    async with Client(srv) as c:
        names = [t.name for t in (await c.list_tools()).tools]
        return f"dashboard: server '{c.server_info.name}' offers {names}"


async def keyword_agent_host(srv, request: str):
    async with Client(srv) as c:
        tools = (await c.list_tools()).tools
        # a stand-in for an LLM: pick the tool whose description shares the most words with the request
        score = lambda t: len(set(request.lower().split()) & set(t.description.lower().split()))
        best = max(tools, key=score)
        result = await c.call_tool(best.name, {"query": request.split()[-1]})
        return f"agent: chose {best.name!r} -> {result.structured_content}"


print(await dashboard_host(server))
print(await keyword_agent_host(server, "find the notes that contain lsp"))
```

### 6. 窥探线路：通过 stdio 传输的原始 JSON-RPC
在 SDK 之下，MCP 只不过是 JSON-RPC 消息。这里服务器作为一个真正的子进程运行（即 **stdio** 传输（Transport）），我们通过每行写入一个 JSON 对象来与它对话——客户端一侧完全不用 SDK。每个请求都在 `_meta` 中携带 2026-07-28 的信封。

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "notes_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    server = MCPServer("notes")

    @server.tool()
    def search_notes(query: str) -> list[str]:
        """Return ids of notes containing the query."""
        return [n for n in ["mcp", "lsp"] if query.lower() in n]

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "notes_server.py")],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def rpc(id_, method, params):
    message = {"jsonrpc": "2.0", "id": id_, "method": method, "params": params}
    print(">>>", json.dumps(message))
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    print("<<<", json.dumps(reply, indent=2)[:700], "\n")
    return reply


rpc(1, "server/discover", {"_meta": META})
rpc(2, "tools/call", {"name": "search_notes", "arguments": {"query": "mc"}, "_meta": META})
proc.stdin.close()
exit_code = proc.wait(timeout=10)   # closing stdin is how a stdio client shuts a server down
```

读一读这些回复：返回的是相同的 `id`，`resultType` 为 `"complete"`，服务器在 `_meta` 中表明自己的身份（`io.modelcontextprotocol/serverInfo`）。`structuredContent` 和文本 `content` 携带的是同一个答案——一个给程序用，一个给模型用。
