## Summary
工具（Tool）是让语言模型能够*行动*的原语（Primitive）：查询数据库、调用 API、预订航班。服务器通过 `tools/list` 公布它们——每个工具都有一个名称、一段描述，以及描述其输入（以及可选的输出）的 JSON Schema——客户端则通过 `tools/call` 调用它们。本课完整讲解 2026-07-28 规范中的 Tools 页面：模型控制（Model-controlled）的交互模型，以及为什么必须让人留在回路中；该能力及其 `listChanged` 标志；命名规则；`Tool` 的每个字段；结果可以携带的五种内容类型；由 `outputSchema` 校验的 `structuredContent`；协议错误与 `isError` 结果之间的关键区分；有状态工具的显式句柄；以及双方各自的安全职责。

## Lesson
### 工具在三种原语中的位置
服务器（Server）提供三种构建块，官方的 “Understanding MCP servers” 页面按**由谁控制**来划分每一种原语（Primitive）：

| 原语 | 是什么 | 控制方 | 典型示例 |
| --- | --- | --- | --- |
| **工具（Tools）** | LLM 可以主动调用的函数；可能写入数据库、调用 API、修改文件 | **模型** | 搜索航班、发送消息、创建日历事件 |
| **资源（Resources）** | 被动的、只读的数据源，用作上下文 | **应用** | 文档、知识库、日历 |
| **提示模板（Prompts）** | 预先构建的指令模板 | **用户** | “规划一次度假”“总结我的会议” |

工具是唯一具有*副作用*的原语，这也是它们配备最多安全机制的原因。在文档的旅行示例中，模型调用了 `searchFlights`、`createCalendarEvent` 和 `sendEmail`——后两个会改变外部世界，用户应当看到并批准它们。

### 交互模型：模型控制，人工监督
工具是**模型控制（Model-controlled）**的：大语言模型（LLM）发现它们，并根据上下文和用户的请求决定是否调用。协议并不强制要求任何 UI，但规范给出了一个强烈的警告：出于信任与安全的考虑，**应当（SHOULD）**始终有一个人在回路中（Human in the Loop），能够拒绝某次调用。应用应当（SHOULD）：

- 清楚地表明哪些工具暴露给了模型，
- 每当调用工具时显示清晰的视觉提示，
- 对操作弹出确认提示。

在实践中，宿主（Host）通过以下方式实现这些要求：逐个工具的启用/禁用开关、审批对话框、针对预先批准的安全操作的“始终允许”设置，以及记录每次调用和结果的活动日志。

### 能力与发现：`tools/list`
拥有工具的服务器**必须（MUST）**（在其 `server/discover` 结果中）声明该能力（Capability）：

```json
{"capabilities": {"tools": {"listChanged": true}}}
```

`listChanged` 表示当工具集合发生变化时，服务器会发出通知。声明了 `tools` 的服务器**必须（MUST）**用当前对请求方客户端可用的工具来响应 `tools/list`。该集合可以（MAY）为空，也可以（MAY）随时间变化，但**不得（MUST NOT）按连接而变化，也不得因其他请求的副作用而变化**——2026-07-28 移除了会话（Session），所以不存在可以据以变化的连接状态。它**可以（MAY）**根据请求上的*授权（Authorization）*而变化（例如只返回调用方权限范围（Scope）允许的工具），因为凭据是逐请求的输入。

服务器**应当（SHOULD）**以**确定性顺序**返回工具（2026-07-28 新增）。相同的集合 → 相同的顺序，意味着客户端可以缓存这个列表，而且——不那么显而易见的是——宿主放在 LLM 提示词顶部的工具定义能保持字节级一致，于是模型提供商的**提示缓存（Prompt Caching）**会持续命中。`tools/list` 支持分页（`cursor` / `nextCursor`）和缓存（`ttlMs`、`cacheScope`——第 3.4 课）：

```json
{"jsonrpc": "2.0", "id": 1, "result": {
  "resultType": "complete",
  "tools": [{"name": "get_weather", "title": "Weather Information Provider",
             "description": "Get current weather information for a location",
             "inputSchema": {"type": "object",
                             "properties": {"location": {"type": "string", "description": "City name or zip code"}},
                             "required": ["location"]}}],
  "nextCursor": "next-page-cursor", "ttlMs": 300000, "cacheScope": "public"}}
```

### `Tool` 的结构剖析
| 字段 | 是否必需 | 含义 |
| --- | --- | --- |
| `name` | 是 | 唯一标识符，用于 `tools/call` |
| `title` | 否 | 人类可读的显示名称 |
| `description` | 否（实践中必不可少） | 它做什么——模型正是读这一段来做决定的 |
| `inputSchema` | 是 | 参数的 JSON Schema；**必须（MUST）**是带有 `"type": "object"` 的有效模式对象，绝不能是 `null` |
| `outputSchema` | 否 | `structuredContent` 必须遵循的 JSON Schema |
| `annotations` | 否 | `ToolAnnotations` 行为提示 |
| `icons` | 否 | 供 UI 使用的带尺寸图标（`src`、`mimeType`、`sizes`） |
| `_meta` | 否 | 扩展元数据 |

当没有给出 `$schema` 时，两种模式（Schema）默认都使用 **JSON Schema 2020-12**；服务器可以显式选择另一种方言（例如 draft-07）。对于没有参数的工具（Tool），规范**推荐**使用 `{"type": "object", "additionalProperties": false}`（只接受 `{}`）；`{"type": "object"}` 也可以用，但会接受任意对象。在 2026-07-28 中，两种模式都被放宽为允许*任意* 2020-12 关键字，并新增了客户端在校验时要遵循的 `$ref` 解析规则。

工具显示名称的优先级是 `title`，然后是 `annotations.title`，最后是 `name`。

**`ToolAnnotations`（工具注解）**是关于行为的提示：`title`、`readOnlyHint`（默认 `false`）、`destructiveHint`（默认 `true`，仅在非只读时有意义）、`idempotentHint`（默认 `false`）、`openWorldHint`（默认 `true`——表示与外部实体交互，比如网页搜索，与之相对的是记忆存储这类封闭领域）。它们让宿主可以做出决定，比如对只读查询跳过确认。但是：

> **规范规则。** 除非工具注解来自受信任的服务器，否则客户端**必须（MUST）**把它们视为不可信的，并且绝不应根据来自不受信任服务器的注解来做工具使用方面的决策。

还有两个细节。`inputSchema` 中的属性可以带有 **`x-mcp-header`**，它会把一个基本类型的参数镜像到 `Mcp-Param-{name}` HTTP 请求头中，让负载均衡器和 WAF 无需解析消息体就能路由（2026-07-28 新增；详见第 2.3 课；绝不要用这种方式标记密钥）。另外，如果你在 2025-11-25 的代码里见过工具上的 `execution.taskSupport`：任务（Task）已经离开核心规范，转入 `io.modelcontextprotocol/tasks` 扩展（Extension），2026-07-28 的 `Tool` 模式中没有 `execution` 字段。

### 工具名称
名称**应当（SHOULD）**为 1–128 个字符，区分大小写，只使用 `A-Z a-z 0-9 _ - .`——不能有空格、逗号或其他特殊字符——并且在同一服务器内唯一。有效示例：`getUser`、`DATA_EXPORT_v2`、`admin.tools.list`。唯一性只针对单个服务器：聚合多个服务器的宿主（Host）会遇到两个 `search` 工具（Tool），**应当（SHOULD）**加以区分，例如加上服务器标识符作为前缀。不要用 `serverInfo.name` 来做这件事——它并不保证唯一。

### 调用：`tools/call`
```json
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "New York"}}}
```
结果是一个 `CallToolResult`：`content`（内容块列表）、可选的 `structuredContent`、可选的 `isError`（缺省表示 `false`），再加上 `resultType: "complete"`。（与 2026-07-28 中的每个请求（Request）一样，真实消息还会携带 `_meta` 信封；规范示例为简洁起见省略了它。）

服务器也可以（MAY）改为以 `resultType: "input_required"` 作答——即一个 `InputRequiredResult`，其中的 `inputRequests` 向客户端索要例如一次征询（Elicitation）。随后客户端用一个**新的 JSON-RPC id** 重试 `tools/call`，加上 `inputResponses` 并回传 `requestState`。这种多轮往返请求（Multi Round-Trip Request）模式取代了服务器发起的请求；第 5.3 课会讲到它。

### 结果可以包含什么
**非结构化**内容放在 `content` 中，可以混合多个块：

| `type` | 形态 | 用途 |
| --- | --- | --- |
| `text` | `text` | 最常见的情况 |
| `image` | base64 `data` + `mimeType` | 图表、截图 |
| `audio` | base64 `data` + `mimeType` | 语音、录音 |
| `resource_link` | `uri`、`name`，可选的 `description`、`mimeType` | 指向客户端可以获取或订阅的资源 |
| `resource` | 嵌入的 `resource`，带有 `uri`、`mimeType`、`text` 或 `blob` | 内联资源内容 |

每种内容类型都接受与资源（Resource）相同的可选**注解（Annotations）**——`audience`（`"user"` / `"assistant"`）、`priority`（0–1）、`lastModified`——所以一张图片可以被标记为“给用户看的”（`audience: ["user"]`），并且不进入模型的上下文。工具返回的 `resource_link` 不保证会出现在 `resources/list` 中；嵌入资源的服务器应当（SHOULD）实现 `resources` 能力。

**结构化**内容放在 `structuredContent` 中——任意 JSON 值（对象、数组、字符串、数字、布尔值或 null；2026-07-28 从仅限对象放宽而来）。如果工具声明了 `outputSchema`，服务器**必须（MUST）**返回符合它的结构化结果，客户端**应当（SHOULD）**对其进行校验。为了向后兼容，返回结构化内容的工具应当（SHOULD）同时把序列化后的 JSON 放进一个文本块。注意文档中的澄清：`structuredContent` 是*服务器产出的数据*，与 LLM 的“结构化输出（Structured Output）”无关。

为什么两者都要？文本块是给模型看的；`structuredContent` 加上 `outputSchema` 则是给程序的类型化契约——宿主可以渲染一张表格，代码模式（Code Mode）的智能体（Agent）可以把这个值串联到下一次调用中，而校验能发现偏离了自己声明形态的服务器。

### 两类错误
这是面试中关于工具被问得最多的问题。

1. **协议错误（Protocol Error）**——针对请求本身问题的标准 JSON-RPC 错误：未知工具、未通过 `CallToolRequest` 模式的请求、服务器错误。示例：`{"code": -32602, "message": "Unknown tool: invalid_tool_name"}`。
2. **工具执行错误（Tool Execution Error）**——一个带有 `isError: true` 并在 `content` 中给出解释的普通结果：API 故障、**输入校验错误**（日期格式错误、值超出范围）、业务逻辑错误。

```json
{"resultType": "complete", "isError": true,
 "content": [{"type": "text", "text": "Invalid departure date: must be in the future. Current date is 08/08/2025."}]}
```

原因在于模型。客户端**应当（SHOULD）**把工具执行错误传给 LLM，让它能够**自我纠正并重试**；客户端也可以（MAY）传递协议错误，但那些不太可能有帮助。如果一个工具因为“日期已过去”而抛出 JSON-RPC 错误，大多数宿主只会显示一个笼统的失败，模型永远不会知道该改什么。

> **陷阱。** Python SDK 的 `MCPServer` 甚至会把*未知的工具名称*也报告为 `isError` 结果，而不是 `-32602`；格式错误的参数（例如没有 `name`）则确实会返回 `-32602`。要了解规范中的区分，并测试你的 SDK 实际发送的是什么。

### 列表变更——现在通过 `subscriptions/listen`
当工具集合发生变化时，声明了 `listChanged` 的服务器**应当（SHOULD）**发送 `notifications/tools/list_changed`（通知（Notification））——但在 2026-07-28 中，只发给那些以 `toolsListChanged: true` 打开了 **`subscriptions/listen`** 流的客户端（旧的独立 HTTP GET 流已经没有了；第 3.4 课）。随后客户端重新获取 `tools/list`。

### 有状态工具：显式句柄
没有协议会话，服务器就无法通过连接状态把一次调用和下一次调用联系起来。非规范性的指导是：从一个创建类工具中返回一个**显式句柄（Explicit Handle）**（`create_basket` → `{"basket_id": "bsk_a1b2c3"}`），并在后续调用中把它作为参数接收（`add_item(basket_id, sku)`）。由模型把句柄向后传递。设计规则：句柄是一个*名字*，而不是一种权限——每次调用都要重新检查调用方的授权（对于未经认证的服务器，用真正的熵（比如 UUIDv4）生成它，并限制其有效期）；保持它**不透明**；在创建类工具的描述中说明其**有效期**（“闲置 24 小时后过期”）；并对过期或未知的句柄返回**工具执行错误**，让模型能通过创建新句柄来恢复。第 4.2 课会把它变成设计实践。

### 安全注意事项
服务器**必须（MUST）**校验所有输入、实施访问控制、对调用进行限流，并清理输出。客户端**应当（SHOULD）**对敏感操作提示确认、在调用前把工具输入展示给用户（以发现意外或恶意的数据外泄）、在把结果传给 LLM 之前进行校验、在校验时遵循 `$ref` 解析规则、实现超时，并记录工具使用情况以供审计（Audit）。

## Key points
- 工具（Tool）是**模型控制**的，但规范说应当（SHOULD）始终有一个能够拒绝调用的**人在回路中（Human in the Loop）**。
- 声明 `tools` 能力（Capability）（可选带 `listChanged`）；`tools/list` 不得（MUST NOT）按连接变化，但可以（MAY）按授权变化，并且应当（SHOULD）保持**确定性顺序**，以便客户端缓存和提示缓存。
- `Tool` 有 `name` 和 `inputSchema`（必需，是一个对象模式（Schema），绝不能是 `null`），以及 `title`、`description`、`outputSchema`、`annotations`、`icons`、`_meta`。模式默认使用 JSON Schema 2020-12。
- 名称应当（SHOULD）由 1–128 个 `A-Za-z0-9_-.` 字符组成，区分大小写，在同一服务器内唯一；多服务器宿主（Host）通过加前缀来区分。
- 结果内容类型：`text`、`image`、`audio`、`resource_link`、嵌入式 `resource`（嵌入式资源（Embedded Resource））；全部接受 `audience`/`priority`/`lastModified` 注解。
- 有 `outputSchema` 时，服务器必须（MUST）返回符合它的 `structuredContent`（结构化内容，任意 JSON 值），客户端应当（SHOULD）对其校验；同时为了兼容性，还要把 JSON 作为文本包含进来。
- 未知工具 / 格式错误的请求 → **JSON-RPC 错误（协议错误（Protocol Error））**；API、校验和业务失败 → 模型可以读取并修正的 **`isError: true`** 结果。
- `ToolAnnotations`（工具注解）（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`）除非服务器受信任，否则都是**不可信的提示**。
- 跨调用的状态使用作为参数传递的**显式不透明句柄（State Handle）**；`list_changed` 只会通过 `subscriptions/listen` 流到达。

## Pitches
### 模型实际上是如何使用 MCP 工具的？
宿主（Host）在每个服务器上调用 `tools/list`，拿到每个工具（Tool）的名称、描述和输入的 JSON Schema。它把这些作为函数定义交给模型。当模型决定使用某个工具时，如果需要审批，宿主会先把这次调用展示给用户，然后带着名称和参数发送 `tools/call`，再把返回的内容回传给模型。所以是模型来选择，宿主负责执行和监督，而服务器只是运行函数并描述结果。

### 为什么 MCP 要区分 isError 结果和协议错误？
因为读到工具错误的通常是模型，而模型只能修正它看得到的东西。如果我的工具收到了格式错误的日期，我会返回一个 isError 为 true 的普通结果，附上一条像“请使用 YYYY-MM-DD”这样的消息；宿主把它交给模型，模型就会用正确的方式重试。JSON-RPC 错误（协议错误（Protocol Error））是留给模型修不了的问题的——未知工具、格式错误的请求、崩溃的服务器——宿主通常会把它变成一个笼统的失败。

### 工具注解是什么？我能依赖它们吗？
注解（Tool Annotations）是一些提示，比如 readOnlyHint、destructiveHint、idempotentHint 和 openWorldHint。它们帮助宿主设计好的用户体验——对只读查询跳过确认对话框，在破坏性的删除之前大声警告。但它们是服务器自己报告的，所以规范说，除非服务器本身受信任，否则客户端必须把它们视为不可信的。对于经过审核的服务器，我用它们让审批更顺畅；对于未知的服务器，绝不把它们当作安全边界。

## Interview
### 带我过一遍 MCP 工具定义的各个字段。
`name`（必需，在同一服务器内唯一，由 1–128 个 `A-Za-z0-9_-.` 字符组成），可选的用于显示的 `title`，模型据以选择工具（Tool）的 `description`，`inputSchema`（必需，一个带有 `type: "object"` 的 JSON Schema 对象，默认方言为 2020-12），`structuredContent` 必须遵循的可选 `outputSchema`，可选的 `annotations`（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`、`title`），可选的 `icons`，以及 `_meta`。显示优先级是 `title` → `annotations.title` → `name`。一个出色的回答还会补充：描述和模式（Schema）*就是*模型看到的提示词，所以它们值得像对待任何提示词一样用心打磨。

### 一个工具收到了 `{"date": "31/02/2026"}`。它应该如何失败？为什么？
作为一个**工具执行错误（Tool Execution Error）**：一个带有 `isError: true` 和可操作文本的普通 `CallToolResult`——“Invalid date 31/02/2026: use YYYY-MM-DD and a real calendar date.” 规范之所以把输入校验错误列在执行错误之下，正是为了让客户端应当（SHOULD）把它们传给 LLM，由 LLM 自我纠正并重试。JSON-RPC `-32602` 则保留给请求结构本身的问题——未知工具、与 `CallToolRequest` 不匹配的参数——这些是模型不太可能修好的。

### 什么是 `structuredContent`？什么时候应该加上 `outputSchema`？
`structuredContent`（结构化内容）是一个 JSON 值（自 2026-07-28 起可以是任意类型），为*程序*承载工具的结果：UI、代码模式的智能体（Agent）、下游流水线。当你声明了 `outputSchema`（输出模式）时，服务器必须（MUST）返回符合它的数据，客户端应当（SHOULD）进行校验，这样你就得到了一个类型化的契约，并能及早发现偏离。只要有使用方会解析这个结果，就加上它。同时也要把序列化后的 JSON 保留在一个文本块中，供旧客户端和模型使用。它与 LLM 的“结构化输出”毫无关系。

### 你的宿主连接了三个服务器，每个都暴露了 `search`。你会怎么做？
工具名称只在单个服务器内唯一，规范说进行聚合的客户端应当（SHOULD）实现一种消歧策略，例如加上服务器标识符作为前缀（`github__search`、`jira__search`）（工具命名空间化（Tool Namespacing）），并在调用时映射回去。不要以 `serverInfo.name` 为键——它并不保证唯一；请使用宿主（Host）自己的配置 id。同时让每个服务器的列表保持确定性顺序，这样合并后的工具块对提示缓存（Prompt Caching）依然友好。

### MCP 已经没有会话了。你如何构建一个购物车工具？
使用显式句柄（State Handle）：`create_basket` 返回一个不透明的、高熵的 id（同时放在 `structuredContent` 中），之后的每个工具都把 `basket_id` 作为参数；服务器以这个键存储状态。每次调用都要针对该句柄检查调用方的授权（Authorization），因为句柄是一个名字，而不是一种权限。把保留策略写进创建类工具的描述里，并对过期的句柄返回 `isError` 结果，让模型可以创建一个新的购物篮。

### 陷阱题：`tools/list` 能否向不同的客户端返回不同的工具？
它可以根据请求上出示的**授权（Authorization）**而变化——例如，只返回令牌（Token）权限范围所允许的工具。它**不得（MUST NOT）**按连接变化，也不得因此前请求的副作用而变化（“调用 `enable_admin` 来解锁更多工具”是不行的）。这条规则源自无状态（Stateless）：任何一个服务器实例都必须对同样的请求给出同样的回答。如果你需要按用户区分的列表，就把响应标记为 `cacheScope: "private"`。

## Glossary
- Tool | 工具 | 由服务器暴露、以名称和 JSON Schema 描述、模型可以决定调用的函数。
- Model-controlled | 模型控制 | 一种交互模型，由 LLM（而不是用户或应用）决定何时使用工具。
- Human in the loop | 人在回路（人工监督） | 能够看到并拒绝工具调用的人；规范说应当始终有这样一个人。
- inputSchema / outputSchema | 输入模式 / 输出模式 | 描述工具参数及其结构化结果的 JSON Schema（默认 2020-12）。
- structuredContent | 结构化内容 | 工具结果中供程序使用的 JSON 值，存在 `outputSchema` 时会据其校验。
- isError | 工具执行错误标志 | `CallToolResult` 上的标志，标记一个模型可以读取并据以自我纠正的失败。
- Protocol error | 协议错误 | 针对未知工具、格式错误的请求或服务器故障的 JSON-RPC 错误响应。
- ToolAnnotations | 工具注解 | 不可信的行为提示，例如 `readOnlyHint` 和 `destructiveHint`。
- Resource link | 资源链接 | 指向某个资源 URI 而不是内联其内容的 `resource_link` 内容块。
- State handle | 状态句柄 | 由工具返回、并在后续调用中传回的不透明 id，用于在没有会话的情况下承载状态。

def tiny_png() -> bytes:
    """A valid 1x1 red PNG, built by hand so the notebook needs no image library."""
    chunk = lambda kind, body: (struct.pack(">I", len(body)) + kind + body
                                + struct.pack(">I", zlib.crc32(kind + body) & 0xFFFFFFFF))
    return (b"\x89PNG\r\n\x1a\n" + chunk(b"IHDR", struct.pack(">IIBBBBB", 1, 1, 8, 2, 0, 0, 0))
            + chunk(b"IDAT", zlib.compress(b"\x00\xff\x00\x00")) + chunk(b"IEND", b""))

### 5. 两类错误
四种失败模式。观察哪些变成了 `isError` 结果（工具执行错误（Tool Execution Error），模型可见），以及每条消息向模型透露了多少信息。

```python
@server.tool()

    """Book a flight. date must be YYYY-MM-DD and in the future."""
    if not date[:4].isdigit() or date < "2026-07-28":
        raise ToolError(f"Invalid departure date {date!r}: must be YYYY-MM-DD and in the future.")
    return f"Booked {origin}->{destination} on {date}"


@server.tool()
def flaky_api() -> str:
    """Calls an upstream API that crashes."""
    raise ConnectionError("upstream 10.0.0.7:5432 refused connection (password=hunter2)")


async with Client(server) as client:
    cases = [("business error (ToolError)", "book_flight", {"origin": "NYC", "destination": "BCN", "date": "08/08/2025"}),
             ("unexpected exception", "flaky_api", {}),
             ("arguments fail inputSchema", "book_flight", {"origin": "NYC"}),
             ("unknown tool", "teleport", {})]
    for label, name, args in cases:
        r = await client.call_tool(name, args)
        print(f"{label:<28} isError={r.is_error} -> {r.content[0].text.splitlines()[0][:110]}")
```

注意 SDK 的两个行为。`ToolError` 的消息会到达模型（可据以行动），而意外的异常则变成一个笼统的 “Error executing tool flaky_api”——主机地址和密码之类的内部细节**不会**泄露，这正是“清理工具输出”的要求。另外，这个 SDK 也把未知工具报告为 `isError`，而规范把它列为协议错误。

### 8. 使用显式句柄的有状态工具
没有会话（Session），所以状态保存在一个不透明句柄（State Handle）之下，由模型在调用之间携带。未知的句柄是一个 `isError` 结果，它告诉模型如何恢复。

```python
import uuid

baskets: dict[str, list[str]] = {}
shop = MCPServer("shop")


class BasketRef(BaseModel):
    basket_id: str


@shop.tool()
def create_basket() -> BasketRef:
    """Create an empty basket and return its id. Baskets expire after 24 hours of inactivity."""
    basket_id = f"bsk_{uuid.uuid4().hex[:12]}"
    baskets[basket_id] = []
    return BasketRef(basket_id=basket_id)


@shop.tool()
def add_item(basket_id: str, sku: str) -> list[str]:
    """Add a product to an existing basket; returns the basket contents."""
    if basket_id not in baskets:
        raise ToolError(f"Unknown or expired basket {basket_id!r}. Call create_basket to start a new one.")
    baskets[basket_id].append(sku)
    return baskets[basket_id]


async with Client(shop) as client:
    handle = (await client.call_tool("create_basket", {})).structured_content["basket_id"]
    print("handle:", handle)
    print((await client.call_tool("add_item", {"basket_id": handle, "sku": "TENT-2P"})).structured_content)
    bad = await client.call_tool("add_item", {"basket_id": "bsk_000000000000", "sku": "STOVE"})
    print("isError:", bad.is_error, "->", bad.content[0].text)
```

### 10. 宿主端的审批关卡
协议把用户体验留给宿主（Host），但规范说人应当（SHOULD）能够拒绝调用，并且除非服务器受信任，否则注解是不可信的。下面是一个最小策略：**仅对受信任的服务器**自动批准只读工具，其他情况一律询问（由一个脚本化的“用户”模拟）。

```python
TRUSTED_SERVERS = {"travel"}


def needs_approval(server_name: str, tool: types.Tool) -> bool:
    hints = tool.annotations or types.ToolAnnotations()
    if server_name not in TRUSTED_SERVERS:
        return True                      # never trust hints from unknown servers
    return not hints.read_only_hint      # trusted + read-only -> no dialog


def scripted_user(tool_name: str, args: dict) -> bool:
    print(f"   [dialog] Allow {tool_name}({args})?", "-> DENY" if tool_name.startswith("cancel") else "-> allow")
    return not tool_name.startswith("cancel")


async def host_call(client, server_name, name, args):
    tool = next(t for t in (await client.list_tools()).tools if t.name == name)
    if needs_approval(server_name, tool) and not scripted_user(name, args):
        return f"{name}: denied by user (the model is told the call was refused)"
    text = (await client.call_tool(name, args)).content[0].text
    return f"{name}: " + " ".join(text.split())[:70]


async with Client(server) as client:
    for server_name, name, args in [("travel", "get_weather_data", {"location": "Rome"}),
                                    ("travel", "cancel_booking", {"booking_id": "B-42"}),
                                    ("random-server", "get_weather_data", {"location": "Rome"})]:
        print(f"{server_name}/{name}")
        print("  ", await host_call(client, server_name, name, args))
```
