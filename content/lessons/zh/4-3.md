## Summary
当服务器在 Claude Desktop 里出问题时，你几乎什么都看不到：要么连接器不见了，要么工具静默失败。解决办法是把宿主（Host）从回路中拿掉。官方的 **MCP 检查器（MCP Inspector）** 在一个包里提供了三个客户端（Client）：用于探索的 Web 界面、用于脚本和 CI 的 CLI（带有稳定的退出码（Exit Code）），以及用于终端的 TUI；此外还有实验性的 `mcpdo`，它能保持连接不断开。由于 2026-07-28 改动太多，Inspector 把**协议时代（Protocol Era）**（旧版与新版）作为一项逐服务器的设置。本课介绍这些工具、官方调试指南（stderr 日志、Claude Desktop 日志、工作目录、环境变量、`server/discover` 和 `-32022`），以及一套测试策略：内存内客户端、针对模式的契约测试（Contract Test）、黄金线路测试，以及对一个故意写坏的服务器进行的调试演练。

## Lesson
### 把宿主从回路中拿掉
调试指南列出了三个层次的工具：**MCP 检查器（MCP Inspector）**（“你的第一站”）、**服务器日志**（在 stdio 上把结构化日志写到 stderr，或在任意传输（Transport）上使用 OpenTelemetry），以及**客户端开发者工具**，例如 Claude Desktop 的日志。Inspector 的使用秘诀描述了一个在实践中很好用的循环：

1. **从 CLI 开始。** `--method initialize` 能在一秒左右确认服务器能启动、能连接，并报告了你期望的能力（Capability）。“大多数‘它不工作’的问题最后都出在这里。”
2. **在 Web 客户端中探索。** 由模式驱动的表单、渲染后的结果和 Protocol 标签页并排显示。
3. **测试边界情况。** 无效输入、缺失的提示模板参数、并发调用，以及（对于 HTTP 服务器）**两个协议时代**。“确认那些*错误*和成功一样都是有意为之的。”
4. **用 CLI 固定下来。** 把发现转化为 CI 断言（`--format json | jq -e`，配合 `--stored-auth-only`）。

### 一个包，三个客户端（外加 mcpdo）
`@modelcontextprotocol/inspector` 需要 **Node 22.19.0+**，无需安装，通过 `npx` 运行：

| 客户端 | 调用方式 | 适用于 |
| --- | --- | --- |
| Web | `npx @modelcontextprotocol/inspector [server command]` | 功能最丰富的界面；默认模式 |
| CLI | `npx @modelcontextprotocol/inspector --cli … --method tools/list` | 脚本、CI、编码智能体；每次运行一个请求 |
| TUI | `npx @modelcontextprotocol/inspector --tui …` | 终端和 SSH；需要真实的 TTY |
| `mcpdo` | `npx -p @modelcontextprotocol/inspector mcpdo …` | 实验性；连接一次，运行多条命令 |

它们共享同一个核心：相同的传输、配置文件、磁盘上的 OAuth 状态，以及协议时代协商。有几条启动器规则经常让人栽跟头：

- 这个可执行文件只是一个很薄的启动器，它只负责**模式标志**（`--web`/`--cli`/`--tui`，最多一个，并且只有放在命令行最前面时才会被识别）和 `-h`。
- 其他一切都归具体的客户端处理。用 `-e KEY=VALUE` 和 `--cwd` 传入 stdio 服务器的环境变量和工作目录（Working Directory）。
- **`--` 分隔符**在不同客户端中的切分方式不同。对 Web 和 TUI，`--` 之后的内容传给*你的服务器*。对 CLI，`--` 之前是目标，之后是 Inspector 自己的选项。
- 服务器可以来自位置参数中的命令（stdio）、`--server-url` + `--transport http|sse`，或者一个文件。`--catalog` 是可写的（默认 `~/.mcp-inspector/mcp.json`）。`--config` 是只读的，非常适合指向 `claude_desktop_config.json` 而不改动它。目录文件（Catalog File）中的条目使用熟悉的 `mcpServers` 结构，外加 `protocolEra` 和 `modernLogLevel` 等 Inspector 字段。

> **陷阱。** Inspector 会把密钥（OAuth 令牌、客户端密钥、stdio 的 `env:` 值）存放在操作系统的钥匙串中。在没有钥匙串的机器上（无头 Linux、SSH、容器），它们会被写入 `~/.mcp-inspector/secrets.json`，**除非你提供密钥，否则不加密**。

### 协议时代：legacy、auto、modern
2026-07-28 的改动大到让 Inspector 把协议时代（Protocol Era）作为一等的、逐服务器的设置，与传输方式相互独立：

| 时代 | 连接时 |
| --- | --- |
| `legacy`（**默认**） | 直接发送 `initialize`，不做探测 |
| `auto` | 探测 `server/discover`，只要结果不是新版，就回退到 `initialize` |
| `modern` | 精确锁定 `2026-07-28`；不回退，所以非新版服务器会明确地失败 |

为什么默认是 `legacy`？“调试工具不能自动探测。”`server/discover` 探测在面对静默的旧版 stdio 服务器时会卡住，还会污染你本来要读的报文记录。所以要测试 2026-07-28 的行为，你必须主动选择（`--protocol-era modern`）。官方构建指南要求你在**两个**时代下都运行一次 `tools/list`。两者的差异：

| 特性 | 旧版 | 新版（2026-07-28） |
| --- | --- | --- |
| 日志 | 会话级的 `logging/setLevel` | 逐请求的 `_meta["io.modelcontextprotocol/logLevel"]`；不带标记就没有日志（“silence is correct behavior”） |
| 资源订阅 | `resources/subscribe` | `subscriptions/listen` 流，由 `notifications/subscriptions/acknowledged` 确认 |
| 任务 | `capabilities.tasks`、`tasks/list`、阻塞式 `tasks/result` | `io.modelcontextprotocol/tasks` 扩展，轮询 `tasks/get`，结果内联返回 |
| 服务器→客户端的提问 | `elicitation/create` 请求 | 多轮往返：返回 `input_required` 结果，然后用新 id 重试 |
| 取消 | `notifications/cancelled` | 关闭该请求的 SSE 流（HTTP）；stdio 仍使用 `notifications/cancelled` |
| 会话 | 可选的 `Mcp-Session-Id`，断开时发送 `DELETE` | 无会话；断开纯粹是本地行为 |

在新版连接上，Inspector 还会高亮镜像出来的 `Mcp-Param-*` 请求头（`x-mcp-header`），列出因请求头注解无效而必须被合规客户端**排除**的工具，并以不同方式呈现错误分类。这涵盖了 `-32020`（请求头不匹配）、`-32021`（缺少客户端能力）、`-32022`（不支持的版本，带有 `data.supported`）和 `-32601`（方法不存在），并且即使“Unknown Tool”和“Invalid Parameters”都使用 `-32602`，它也能把两者区分开。

### Web 客户端
该命令会打印一个带有**每次启动生成的 API 令牌（Token）**的 URL。请打开这个 URL，而不是手动输入 `localhost:6274`，因为后端会拉起进程，每个 `/api/*` 调用都需要这个令牌。它默认绑定 `127.0.0.1`，没有 `DANGEROUSLY_BIND_ALL_INTERFACES=true` 就拒绝通配地址绑定。永远不要把它和 `DANGEROUSLY_OMIT_AUTH` 一起使用。标签页根据服务器的能力显示：**Tools**、**Resources**、**Prompts**、**Apps**、**Skills**、**Tasks** 和 **Logs**。三个监视标签页以不同深度展示同一份流量：

- **Protocol**：JSON-RPC 报文记录，请求与响应一一配对，MRTR 轮次被归为一组。
- **Network**：原始的 HTTP 状态码、请求头和消息体（仅 HTTP/SSE）。
- **Console**：stdio 服务器的 **stderr**。“当连接无缘无故失败时”，先来这里看。

**Server Settings** 中包含协议时代、逐请求日志级别、要公布哪些扩展（服务器可能根据这些扩展注册不同的工具）、根目录（Roots）、请求头、超时、OAuth，以及一次一页的分页。

### CLI：脚本、CI 与退出码
每次运行都会连接，发送由 `--method` 指定的单个请求，打印结果然后退出。可用的方法有 `initialize`、`tools/list`、`tools/call`（`--tool-name`、`--tool-arg k=v` 或 `--tool-args-json`）、`resources/list|read|templates/list`、`prompts/list|get`、`logging/setLevel`（仅旧版）、`skills/list|get` 以及目录管理（`servers/*`）。`--tool-arg` 会把每个值按 JSON 解析（`count=1` 发送的是数字），然后把字符串强制转换为模式中的类型。`--tool-args-json` 按原样发送对象。`--format json` 会打印一个干净的 JSON 对象，便于交给 `jq`。

| 退出码 | 含义 |
| --- | --- |
| `0` | 成功 |
| `1` | 用法错误/意外错误 |
| `2` | 该工具没有 MCP 应用（`--app-info`） |
| `3` | 需要认证（401/403） |
| `4` | 服务器不可达 |
| `5` | 工具错误：`isError: true` 或工具不存在 |
| `6` | `--strict` 发现了错误级别的工具模式可移植性问题 |
| `7`/`8`/`9` | 技能 `--verify` 失败 |

只要退出码非零，CLI 就会向 **stderr 写一行 JSON**（`{"error": {"code": "auth_required", "message": …}}`），其中带有稳定的代码，如 `unreachable`、`tool_not_found`、`tool_is_error` 和 `schema_unportable`。返回 `isError: true` 的 `tools/call` 仍会打印其负载，但以 `5` 退出，因此 `&&` 链会停下来。在 CI 中，加上 `--stored-auth-only`（永远不启动交互式 OAuth），并在 `tools/list` 上使用 `--strict`：

```bash
set -euo pipefail
mcp-inspector --cli --config ./ci-servers.json --server my-server \
  --stored-auth-only --method tools/list --format json \
  | jq -e '.result.tools | map(.name) | index("get_weather")' > /dev/null
mcp-inspector --cli --config ./ci-servers.json --server my-server --method tools/list --strict > /dev/null
```

### TUI 与 mcpdo
**TUI** 在终端中提供与 Web 客户端相同的探索功能，标签页一键切换：`t` Tools、`r` Resources、`m` Prompts、`p` Protocol、`o` Console、`n` Network，`c` 连接，`?` 查看帮助。它需要真实的 TTY，所以在 CI 中请使用 CLI。**`mcpdo`** 把命名连接保存在一个后台守护进程（`mcpdod`）中：`mcpdo connect my-server`、`mcpdo @my-server tools/call echo message:=hi`、`mcpdo disconnect my-server`。它适合多步流程（任务、订阅、征询）和编码智能体。在非 TTY 环境下，不带限定的命令会报错，这样脚本就不会作用于“你上次用的那个服务器”。若要隔离一个不可信的 stdio 服务器，可以把它的命令写成一个容器：`mcpdo connect @sandboxed -- docker run -i --rm --network none …`。

### 日志：去哪里看
- **你的服务器。** 在 stdio 上，日志写到 **stderr**，宿主会自动捕获。永远不要写到 stdout。在 HTTP 上，客户端不会捕获 stderr，所以请使用你自己的日志聚合或 **OpenTelemetry**，再配合 curl 或浏览器 DevTools 查看请求和 SSE 流。记录启动步骤、资源访问、工具执行、错误和耗时，并带上请求 id。对凭据和个人数据进行脱敏。
- **协议日志（Protocol Logging）**（`notifications/message`）在 2026-07-28 中已被**弃用**，只会针对携带 `io.modelcontextprotocol/logLevel` 的请求发送。
- **Claude Desktop。** `~/Library/Logs/Claude`（macOS）、`%APPDATA%\Claude\logs`（Windows）、`~/.config/Claude/logs/`（Linux，依据构建指南）。`mcp.log` 记录连接事件。`mcp-server-NAME.log` 保存该服务器的 stderr。运行 `tail -n 20 -F ~/Library/Logs/Claude/mcp*.log`。对于客户端一侧的错误，在 `developer_settings.json` 中设置 `{"allowDevTools": true}` 启用 DevTools，然后按 Cmd-Option-I（Windows 上为 Ctrl+Alt+I）。

### 调试指南中的常见问题
- **工作目录（Working Directory）。** 宿主可能以一个未定义的工作目录启动你的服务器（在 macOS 上是 `/`）。在配置和 `.env` 文件中使用**绝对路径**，并相对于你的代码（而不是 `cwd`）来解析数据文件。
- **环境变量。** stdio 服务器只继承一个有限的、与平台相关的子集。请在服务器条目中添加一个 `env` 映射。
- **启动。** 路径问题（可执行文件不对、文件缺失、权限不足；可以试试使用绝对路径的 `command`）、配置错误（JSON 无效、缺少字段、类型不匹配）以及环境问题。
- **连接问题。** 检查客户端日志，检查进程是否在运行，用 Inspector 单独测试，然后检查协议兼容性。调用 `server/discover` 查看 `supportedVersions`。`UnsupportedProtocolVersionError`（**`-32022`**）会在 `data` 中列出这些版本。如果请求的 `_meta` 中缺少 `io.modelcontextprotocol/protocolVersion` 或 `clientCapabilities`，会得到 **`-32602`**；缺少必需的客户端能力，则会得到 **`-32021`**。
- **让修改生效。** 修改配置*和*服务器代码之后都要重启客户端。对 Claude Desktop 来说，这意味着完全退出。快速迭代时请使用 Inspector。

### 自动化测试：一套实用策略
文档给了你工具；测试金字塔则属于 **[practice]**，而且它与 Python SDK 配合得很好：

1. **内存内单元测试。** `async with Client(server)` 在进程内运行真实的协议处理函数，没有子进程，也不占端口，所以测试快速且结果确定。对 `structured_content`、`is_error` 以及模型将读到的文本做断言。使用 pytest 时，用 `@pytest.mark.anyio` 标记异步测试（anyio 自带这个插件）。
2. **针对定义的契约测试（Contract Test）。** 把规范化后的 `tools/list`（名称、模式、注解）快照保存到一个黄金文件中，出现任何差异就让测试失败。重命名一个参数会破坏所有依赖它的提示词和客户端，所以这类修改应当是有意为之并经过评审的。
3. **黄金线路测试（Golden Test）。** 保存若干有代表性的结果，按线路上的原样导出（`model_dump(by_alias=True, exclude_none=True, mode="json")`）。比较之前先去掉易变字段（id、时间戳、`_meta`）。
4. **传输冒烟测试。** 通过 stdio（以及 HTTP）把真实的入口点启动一次，以捕捉内存内测试看不到的问题：导入时崩溃、stdout 污染、缺少环境变量和路径 bug。
5. **错误路径测试。** 断言错误输入会产生带可操作文本的 `isError: true`，而不是崩溃。
6. **CI 关卡。** 加入 Inspector CLI（`--strict`、退出码），作为针对构建产物的黑盒检查。

Python SDK 的 `mcp dev server.py`（来自 `mcp[cli]`）会在开发期间把你的服务器放在 Inspector 下启动。

## Key points
- **MCP 检查器（MCP Inspector）**是一个 npm 包（Node 22.19.0+），包含基于共享核心的 **Web**、**CLI** 和 **TUI** 客户端，外加用于持久连接的实验性 **`mcpdo`**。
- **协议时代（Protocol Era）**按服务器设置：`legacy`（默认，不探测）、`auto`（探测 `server/discover`，然后回退）和 `modern`（锁定 2026-07-28）。要在**两个**时代下测试服务器。
- CLI 的退出码（Exit Code）是稳定的：`3` 认证、`4` 不可达、`5` 工具错误或工具不存在、`6` `--strict` 模式问题。失败时还会在 stderr 上打印一行 JSON 错误信封。
- Web 客户端：打开打印出来的、带有**每次启动令牌**的 URL。**Protocol** 显示 JSON-RPC，**Network** 显示 HTTP，**Console** 显示 stdio 服务器的 stderr。
- stdio 服务器把日志写到 **stderr**，由宿主（Host）捕获（Claude Desktop：`mcp.log` 加 `mcp-server-NAME.log`）。HTTP 服务器需要自己的日志或 OpenTelemetry。
- 典型故障：相对路径（工作目录（Working Directory）可能是 `/`）、缺少环境变量（继承有限，所以要用 `env`）、配置 JSON 无效，以及 stdout 污染。
- 版本和信封问题表现为 `-32022`（带 `data.supported`）、`-32602`（缺少 `_meta` 字段）和 `-32021`（缺少客户端能力（Capability））。
- 测试金字塔：内存内 `Client(server)` 测试、`tools/list` 的**契约快照**（契约测试（Contract Test））、**黄金线路**结果、一个 stdio 冒烟测试，以及在 CI 中运行的 Inspector CLI。

## Pitches
### 你怎么调试一个 MCP 服务器？
我会先把宿主从回路里拿掉。第一步用 Inspector CLI，跑 method initialize 或者 tools/list，一秒钟就能告诉我服务器能不能启动、它公布了什么，以及用的是哪个协议时代。然后用 Web 版 Inspector 手动调用工具，同时盯着 Protocol 和 Console 标签页。如果只在 Claude Desktop 里出问题，我就去读 mcp.log 和服务器自己的 stderr 日志，并检查绝对路径、环境变量，还有有没有误打到 stdout 的 print。

### 为什么 Inspector 默认使用旧版协议时代？
因为调试工具不应该改变它观察的对象。先探测 server/discover，碰上忽略未知方法的老版 stdio 服务器可能会卡住，还会给我想读的报文记录增加噪音。所以 legacy 就是直接发 initialize，auto 先探测再回退，modern 锁定 2026-07-28，不行就明确报错。实际工作中我会在两个时代下都跑一遍检查，因为真实的客户端两边都有。

### 你怎么自动化测试一个 MCP 服务器？
大部分在进程内完成：Python SDK 的 Client 可以直接连到服务器对象上，所以 pytest 跑的是真实的处理函数，不用端口也不用子进程。我会把 tools/list 做成快照当作契约，因为重命名一个参数就会破坏所有依赖它的客户端和提示词。关键调用我会保留黄金样本结果，并断言错误输入返回的是可操作的 isError 结果。再用一个冒烟测试启动真实的 stdio 入口点，CI 里则用 Inspector CLI 拿到稳定的退出码。

## Interview
### 你的服务器在 Inspector 里能用，在 Claude Desktop 里却不行。区别在哪？
区别在启动环境。Inspector 是从你的 shell 里运行它的，带着你的 `PATH`、你的工作目录和你完整的环境。Claude Desktop 是个 GUI 应用：工作目录（Working Directory）可能是 `/`，只继承一组有限的环境变量，而 `uv`/`node` 可能不在它的 `PATH` 上。所以要检查配置中的每个路径是否都是绝对路径，给出命令的完整路径，通过条目的 `env` 传入所需变量，并相对于 `__file__` 解析数据文件。然后读 `mcp.log`（进程拉起失败了吗？）和 `mcp-server-NAME.log`（stderr 中的 traceback），并记住修改之后需要完全退出再重启。你还可以用 `--config` 以只读方式把 Inspector 指向真实的配置，从而精确复现问题。

### Inspector CLI 的退出码在 CI 中能给你带来什么？
一套稳定的失败分类，而无需抓取文本：`0` 成功、`1` 用法错误或意外错误、`3` 需要认证、`4` 不可达、`5` 工具返回了 `isError: true` 或不存在、`6` `--strict` 发现了错误级别的模式可移植性问题，`7`–`9` 是技能校验失败。每次失败还会向 stderr 写入一个 JSON 错误信封（`code`、`message`，以及可选的 `status`/`url`/`cause`）。流水线可以根据代码分支处理，比如区分“需要认证”和“服务器宕机”。加上 `--stored-auth-only` 后，它永远不会卡在浏览器 OAuth 流程上。

### 新版时代的 Inspector 没显示你服务器的任何日志。是 bug 吗？
不一定。在 2026-07-28 中，协议日志（Protocol Logging）已被弃用，并且是**逐请求**的：除非该请求的 `_meta` 中携带 `io.modelcontextprotocol/logLevel`，否则服务器不得（MUST NOT）发送 `notifications/message`。Inspector 的新版连接默认会打上 `debug` 标记，但如果 **Log Level per Request** 被设为 Off，那么没有日志就是正确的行为。在旧版时代，机制是会话级的 `logging/setLevel`。还要检查服务器做了什么：SDK 2.x 的 `ctx.info()` 只有在客户端选择启用时才会发送。更好的解决办法是把日志写到 stderr（在 Console 标签页可见）或 OpenTelemetry。

### 你会如何为一个 Python MCP 服务器设计测试套件？
大多数测试使用 pytest 配合 anyio，在进程内 `async with Client(server)`，这样速度快而且不需要端口。分层如下：每个工具的行为测试（正常路径，加上断言 `is_error` 和可操作消息的错误路径）；一个**契约测试（Contract Test）**，把规范化后的 `tools/list` 与已提交的黄金文件比较，让模式变更变得显式；对选定结果的**黄金线路测试**，用 `by_alias=True` 导出并去掉易变字段；一个启动真实入口点的 **stdio 冒烟测试**，用来捕捉导入时崩溃、stdout 污染以及环境变量/路径问题；以及在 CI 中带 `--strict` 运行的 Inspector CLI。在 SDK 允许的情况下（`mode="legacy"`），让测试套件在两个协议时代下都跑一遍。

### 客户端报告了 `-32022`。这是什么意思？你怎么处理？
`-32022` 是 `UnsupportedProtocolVersionError`（不支持的协议版本错误）：请求中的 `io.modelcontextprotocol/protocolVersion` 指定了一个服务器不支持的修订版。它的 `data` 中带有 `supported`（以及 `requested` 版本），因此客户端可以用双方都支持的版本重试，或者回退到旧版的 `initialize` 握手。调试时，调用 `server/discover` 并读取 `supportedVersions`，然后检查客户端的 `_meta`。相关的错误码：缺少必需的 `_meta` 字段时为 `-32602`，未声明必需的客户端能力时为 `-32021`。在 HTTP 上，这些错误会伴随 `400` 状态码返回。

```python
%%writefile {server_path}
import json
import logging
import sys
from pathlib import Path
from typing import Annotated, Literal

from pydantic import Field

from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError
from mcp_types import ToolAnnotations

logging.basicConfig(level=logging.INFO, stream=sys.stderr, format="%(levelname)s %(name)s: %(message)s")
log = logging.getLogger("notes")
NOTES: dict[str, str] = json.loads((Path(__file__).parent / "notes.json").read_text())
log.info("loaded %d notes", len(NOTES))

mcp = MCPServer("notes", version="1.2.0")
RO = ToolAnnotations(readOnlyHint=True, openWorldHint=False)


@mcp.tool(annotations=RO)
def notes_search(query: Annotated[str, Field(description="Case-insensitive text to look for")],
                 match: Annotated[Literal["any", "all"], Field(description="Match any or all words")] = "any") -> list[str]:
    """Return the ids of notes whose text matches the query. Read one with notes_get."""
    words = query.lower().split()
    test = any if match == "any" else all
    return sorted(nid for nid, text in NOTES.items() if test(w in text.lower() for w in words))


@mcp.tool(annotations=RO)
def notes_get(note_id: Annotated[str, Field(description="A note id from notes_search")]) -> str:
    """Return the full text of one note."""
    if note_id not in NOTES:
        raise ToolError(f"Unknown note {note_id!r}. Call notes_search to list valid ids.")
    return NOTES[note_id]


@mcp.resource("notes://index")
def index() -> str:
    """All note ids, one per line."""
    return "\n".join(sorted(NOTES))


@mcp.resource("notes://{note_id}")
def note(note_id: str) -> str:
    """One note as a resource."""
    return NOTES[note_id]


@mcp.prompt()
def summarize(note_id: str) -> str:
    """Ask the model to summarise a note."""
    return f"Summarise note {note_id} in one sentence: {NOTES.get(note_id, '')}"


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

### 3. 一个迷你 Inspector
Inspector CLI 会连接、运行一个方法，然后以有意义的退出码（Exit Code）退出。我们的 `inspect_server` 执行“列出所有内容，然后调用每个工具”这一遍检查。它**根据每个 `inputSchema` 构造示例参数**（第一个 enum 值、默认值，或基于类型的占位值），并返回一个 Inspector 风格的退出码：所有调用都成功时为 `0`，任何工具返回 `isError` 时为 `5`。

```python
import time

from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client


def sample_args(schema: dict, overrides: dict | None = None) -> dict:
    samples = {"string": "mcp", "integer": 1, "number": 1.0, "boolean": True, "array": [], "object": {}}
    args = {}
    for name, prop in schema.get("properties", {}).items():
        if name not in schema.get("required", []):
            continue                                    # like a form left at its defaults
        if "enum" in prop:
            args[name] = prop["enum"][0]
        else:
            args[name] = prop.get("default", samples.get(prop.get("type"), "mcp"))
    return args | (overrides or {})


async def inspect_server(target, overrides: dict | None = None) -> int:
    exit_code = 0
    async with Client(target) as c:
        caps = c.server_capabilities.model_dump(exclude_none=True)
        print(f"server: {c.server_info.name} {c.server_info.version} | protocol {c.protocol_version}")
        print("capabilities:", sorted(caps))
        tools = (await c.list_tools()).tools
        print("resources:", [str(r.uri) for r in (await c.list_resources()).resources],
              "| templates:", [t.uri_template for t in (await c.list_resource_templates()).resource_templates],
              "| prompts:", [p.name for p in (await c.list_prompts()).prompts])
        for tool in tools:
            args = sample_args(tool.input_schema, (overrides or {}).get(tool.name))
            started = time.perf_counter()
            r = await c.call_tool(tool.name, args)
            ms = (time.perf_counter() - started) * 1000
            status = "ERROR" if r.is_error else "ok"
            exit_code = 5 if r.is_error else exit_code
            hints = tool.annotations.model_dump(by_alias=True, exclude_none=True) if tool.annotations else {}
            print(f"  {status:5} {tool.name}({json.dumps(args)}) {ms:5.1f} ms  hints={hints}")
            shown = r.structured_content if r.structured_content is not None else r.content[0].text
            print(f"        -> {json.dumps(shown)[:90]}")
    return exit_code


params = StdioServerParameters(command=sys.executable, args=[str(server_path)])
with open(workdir / "notes.stderr.log", "w") as errlog:
    code = await inspect_server(stdio_client(params, errlog=errlog))
print("exit code:", code)
```

`notes_get("mcp")` 碰巧成功了，因为我们的占位字符串恰好是一个真实的 id。试试 `overrides={"notes_get": {"note_id": "nope"}}`，退出码就会变成 `5`，就像工具返回 `isError: true` 时的 `mcp-inspector --cli … --method tools/call` 一样。

### 4. 线路记录器：30 行实现 Protocol 标签页
Inspector 的 Protocol 标签页就是一份 JSON-RPC 消息的报文记录（线路报文记录（Wire Transcript））。我们在客户端和服务器之间放一个很小的 **stdio 代理**，也能得到同样的效果。它原样转发每一行，并把它追加到一个 JSONL 记录中，同时标记出 stdout 上任何不是 JSON 的内容。因为它只是另一条命令，所以能与任何 stdio 客户端配合使用，包括 Claude Desktop（`"command": "python", "args": ["proxy.py", "log.jsonl", "python", "server.py"]`）。

```python
proxy_path = workdir / "wire_proxy.py"
proxy_path.write_text('''
import json, subprocess, sys, threading, time
log_path, *cmd = sys.argv[1:]
child = subprocess.Popen(cmd, stdin=subprocess.PIPE, stdout=subprocess.PIPE)
lock = threading.Lock()

def record(direction, raw):
    text = raw.decode("utf-8", "replace").rstrip("\\n")
    try:
        entry = {"t": time.time(), "dir": direction, "msg": json.loads(text)}
    except json.JSONDecodeError:
        entry = {"t": time.time(), "dir": direction, "invalid": text}
    with lock, open(log_path, "a") as f:
        f.write(json.dumps(entry) + "\\n")

def client_to_server():
    for line in sys.stdin.buffer:
        record("->", line)
        child.stdin.write(line)
        child.stdin.flush()
    child.stdin.close()

threading.Thread(target=client_to_server, daemon=True).start()
for line in child.stdout:
    record("<-", line)
    sys.stdout.buffer.write(line)
    sys.stdout.buffer.flush()
sys.exit(child.wait())
''')


def show_transcript(path: Path, width: int = 150) -> list[dict]:
    entries = [json.loads(l) for l in path.read_text().splitlines()]
    for e in entries:
        if "invalid" in e:
            print(f"{e['dir']} !! NOT JSON-RPC: {e['invalid']!r}")
            continue
        m = e["msg"]
        kind = m.get("method") or ("result" if "result" in m else "error")
        body = m.get("params") or m.get("result") or m.get("error")
        print(f"{e['dir']} id={m.get('id', '-')!s:4} {kind:22} {json.dumps(body)[:width]}")
    return entries


transcript = workdir / "wire.jsonl"
recorded = StdioServerParameters(command=sys.executable,
                                 args=[str(proxy_path), str(transcript), sys.executable, str(server_path)])
with open(workdir / "notes.stderr.log", "w") as errlog:
    async with Client(stdio_client(recorded, errlog=errlog)) as c:
        await c.call_tool("notes_search", {"query": "protocol eras", "match": "all"})
        await c.call_tool("notes_get", {"note_id": "nope"})
entries = show_transcript(transcript)
```

从上到下阅读这份记录：客户端的 `server/discover` 探测，每个请求上的 2026-07-28 `_meta` 信封，SDK 客户端在第一次调用之后发出的一次 `tools/list`（用于获取工具的 `outputSchema` 并校验 `structuredContent`），以及针对未知笔记的 `isError: true` 结果——它是一个*结果*，而不是 JSON-RPC 错误。


### 5. 手动检查协议兼容性
调试指南的连接检查清单最后两项是“verify protocol compatibility”和“check the per-request `_meta` fields”。下面是你应当认得的三种应答：一个正常的 `server/discover`、一个缺少 `_meta` 的请求（`-32602`），以及一个不支持的版本（带 `data.supported` 的 `-32022`）。

```python
import subprocess

proc = subprocess.Popen([sys.executable, str(server_path)], text=True,
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.DEVNULL)
META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0"}}


def rpc(id_, method, params):
    proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": id_, "method": method, "params": params}) + "\n")
    proc.stdin.flush()
    return json.loads(proc.stdout.readline())


ok = rpc(1, "server/discover", {"_meta": META})
print("server/discover ->", {k: ok["result"][k] for k in ("supportedVersions", "capabilities")})
print("missing _meta   ->", rpc(2, "tools/list", {})["error"])
old = dict(META, **{"io.modelcontextprotocol/protocolVersion": "2020-01-01"})
print("bad version     ->", rpc(3, "tools/list", {"_meta": old})["error"])
proc.stdin.close()
_ = proc.wait(timeout=10)
```

### 6. 测试套件：行为测试、契约测试和黄金线路测试
我们在服务器旁边写一个真正的 pytest 风格测试文件。它使用内存内的 `Client(server)` 以求速度，外加一个 stdio 冒烟测试。第一次运行会记录**黄金文件**（工具契约和一个线路格式的结果）。之后的运行都与它们进行比较（黄金样本测试（Golden Test））。如果安装了 `pytest`，就直接运行该文件；否则由一个 15 行的运行器执行同样的测试函数，并 await 其中的异步函数。

```python
print("after renaming a parameter:", await run_tests(tests_path))
golden = workdir / "golden" / "tools_contract.json"
```

### 7. 一步步调试一个坏掉的服务器
这是一个“在我机器上能跑”的服务器：在终端里从它自己的文件夹运行时一切正常。但宿主（Host）启动它的方式不同：脚本使用绝对路径，工作目录（Working Directory）是 `/`，环境变量也极少。我们像宿主那样启动它，像读 `mcp-server-NAME.log` 那样读它的 stderr 日志，每一步修复一个 bug。

```python
broken_path = workdir / "broken_notes.py"
broken_path.write_text('''
import json, os
from mcp.server import MCPServer

NOTES = json.load(open("notes.json"))           # bug 1: relative to the *working directory*
TOKEN = os.environ["NOTES_TOKEN"]               # bug 2: env var the host does not pass
print(f"Loaded {len(NOTES)} notes", flush=True) # bug 3: stdout is the wire

mcp = MCPServer("broken-notes")

@mcp.tool()
def count_notes() -> int:
    """How many notes exist."""
    return len(NOTES)

if __name__ == "__main__":
    mcp.run()
''')


def leaf_error(exc: BaseException) -> BaseException:
    while isinstance(exc, BaseExceptionGroup):
        exc = exc.exceptions[0]
    return exc


async def launch_like_a_host(env: dict | None = None, record_to: Path | None = None) -> None:
    log_path = workdir / "mcp-server-broken-notes.log"
    command = [str(broken_path)]
    if record_to:
        command = [str(proxy_path), str(record_to), sys.executable, str(broken_path)]
    params = StdioServerParameters(command=sys.executable, args=command, cwd="/", env=env)
    try:
        with open(log_path, "w") as errlog:
            async with Client(stdio_client(params, errlog=errlog)) as c:
                r = await c.call_tool("count_notes", {})
                print("CONNECTED: count_notes ->", r.structured_content)
    except Exception as exc:
        print("CLIENT SAW:", repr(leaf_error(exc)))
        tail = log_path.read_text().strip().splitlines()[-1:]
        print("LOG TAIL  :", tail)


print("step 1: launch it like a host would")
await launch_like_a_host()
```

客户端只看到 `Connection closed`，这也是宿主能告诉你的全部信息。**日志**里才有原因：`notes.json` 是在 `/` 中查找的。修复 1：相对于源文件来解析数据。

```python
src = broken_path.read_text()
src = src.replace('json.load(open("notes.json"))',
                  'json.load(open(os.path.join(os.path.dirname(os.path.abspath(__file__)), "notes.json")))')
broken_path.write_text(src)
print("step 2: after fixing the path")
await launch_like_a_host()
```

新的故障，新的日志行：`KeyError: 'NOTES_TOKEN'`。stdio 服务器只继承有限的环境变量，所以要显式传入，这相当于 `claude_desktop_config.json` 中的一个 `"env"` 条目。

```python
print("step 3: pass the environment explicitly, and record the wire")
wire_log = workdir / "broken-wire.jsonl"
await launch_like_a_host(env={"NOTES_TOKEN": "dev-token"}, record_to=wire_log)
_ = show_transcript(wire_log, width=90)
```

它连上了，因为 Python 客户端能容忍那行垃圾内容，但记录器暴露出了 **bug 3**：在第一个响应（Response）之前，stdout 上出现了一行非 JSON 内容。更严格的宿主可能会在这里断开连接。修复 3：把日志写到 stderr。然后确认报文记录是干净的。

```python
broken_path.write_text(broken_path.read_text().replace(
    'print(f"Loaded {len(NOTES)} notes", flush=True)', 'print(f"Loaded {len(NOTES)} notes", file=sys.stderr)')
    .replace("import json, os", "import json, os, sys"))
wire_log.unlink()
print("step 4: after logging to stderr")
await launch_like_a_host(env={"NOTES_TOKEN": "dev-token"}, record_to=wire_log)
bad_lines = [e for e in map(json.loads, wire_log.read_text().splitlines()) if "invalid" in e]
print("non-JSON lines on the wire:", bad_lines)
print("server log:", (workdir / "mcp-server-broken-notes.log").read_text().strip())
```

每个 bug 都只有在**复现宿主的启动条件**并**读对日志**时才会显现出来。把每一次修复都变成一个回归测试：第 6 节的 `test_stdio_smoke` 已经在用 `cwd="/"` 启动了。
