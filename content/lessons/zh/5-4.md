## Summary
第 5.2 课的智能体循环（Agent Loop）在一个服务器、五个工具的情况下运转得很好。但真实的宿主（Host）会连接几十个服务器、上百个工具，这时有两项开销会急剧膨胀：每次调用模型都要发送的**工具定义（Tool Definition）**，以及链式调用之间经由模型往返的**中间结果**。官方的客户端最佳实践指南给出了两种模式来应对。**渐进式发现（Progressive Discovery）**控制定义*何时*进入上下文：先用一个小巧的 `search_tools` 元工具（Meta-tool）搜索，再查看详情，最后执行。**程序化工具调用（Programmatic Tool Calling）**（“代码模式”，Code Mode）控制工具*如何*运行：模型针对带类型的桩函数编写脚本，由沙箱（Sandbox）运行，只有摘要会返回。本课讲解这两种模式，以及命名空间化、`ttlMs` 缓存和提示缓存（Prompt Caching）陷阱，你还将构建一个使用这些技术的三服务器旅行宿主。

## Lesson
### 为什么朴素的多服务器宿主会失效
最简单的宿主（Host）对每个服务器都照搬你在第 5.2 课中的做法：逐个调用 `tools/list`，把结果拼接起来，然后在每次模型请求中把整个数组作为 `tools` 传入。文档对这条路的结局说得毫不客气：*“当宿主可以访问几十个服务器、暴露上百个工具时，仅这些定义就可能在模型读到用户消息之前占掉上下文窗口的大半。”* 文档的示意图对比了两种情形：预先加载全部定义约需 150,000 个令牌（Token），而只加载所需工具时约为 2,000 个令牌。

三个问题会同时出现：

- **成本与延迟**：定义是*每一轮*都要发送的提示词令牌。
- **质量**：模型必须从上百个近乎重复的工具（`contact_update`、`lead_update`、`account_update`……）中挑出正确的那个，选择准确率随之下降。
- **数据搬运**：在“读取日志 → 过滤 → 提交工单”这样的链条中，每个中间结果都要经过模型，即使它只需要被转交给下一个工具。

指南中的两种模式分别解决这些问题：**渐进式发现（Progressive Discovery）**控制工具定义*何时*进入上下文；**程序化工具调用（Programmatic Tool Calling）**控制工具*如何*被调用。两者可以很好地结合。

### 聚合服务器：每个服务器一个客户端，名称加命名空间
在任何优化之前，多服务器宿主（Host）首先需要正确的底层连接。架构与第 1.2 课相同：宿主为**每个服务器创建一个客户端（Client）**，由宿主——而不是服务器——决定它们之间流转什么。文档中的旅行规划示例展示了这样做的好处：一个 *Travel* 服务器（航班、酒店）、一个 *Weather* 服务器和一个 *Calendar/Email* 服务器在同一个 `plan-vacation` 提示模板（Prompt）下协同工作。模型调用 `searchFlights()` 和 `checkWeather()`，然后调用 `bookHotel()`、`createCalendarEvent()` 和 `sendEmail()`，*“必要时请求用户批准。”*

第一个问题是**名称冲突**。工具规范规定，工具名的唯一性仅限于单个服务器之内：

> **规范规则。** 聚合多个服务器工具的客户端或代理可能（MAY）遇到命名冲突（例如两个服务器各自暴露一个 `search` 工具），应当（SHOULD）实现某种消歧策略，例如用服务器标识符作为工具名前缀。服务器的 `name`（来自 `serverInfo`）不保证在各服务器之间唯一，不应当（SHOULD NOT）依赖它来消歧。

因此，应使用宿主**自己的配置键**作为前缀（`flights__search`、`hotels__search`），而不是 `serverInfo.name`。让结果保持在推荐的工具名字符集内——ASCII 字母、数字、`_`、`-`、`.`，长度 1–128 个字符——以便模型 API 接受；路由调用时再把前缀拆掉。指南还建议在展示工具时**按服务器分组**，这样模型能更好地推理相关的能力。

> **陷阱。** Python SDK 自带一个 `ClientSessionGroup` 聚合器。如果没有提供 `component_name_hook`，它会直接拒绝重复的工具名；而它的钩子接收的是 `serverInfo`——恰恰是规范说不要依赖的那个字段。请改用你自己的配置名作为键。

### 渐进式发现：目录、查看、执行
渐进式发现（Progressive Discovery）改变的是定义何时到达模型，而不是宿主（Host）与服务器的通信方式：

- 宿主仍然照常通过 `tools/list` 获取定义，但**推迟将它们注入**模型的上下文。
- 宿主为模型提供一个轻量的 **`search_tools` 元工具（Meta-tool）**。
- 宿主**仅在需要时**才把完整定义加载到上下文中。

指南的参考设计分为三层：

| 层级 | 元工具 | 返回内容 |
| --- | --- | --- |
| 1. 目录 | `search_tools({query})` | 仅名称 + 一行描述 |
| 2. 查看 | `get_tool_details({name})` | 单个工具的完整定义（输入模式、输出模式、文档） |
| 3. 执行 | 工具本身 | 真实结果 |

```text
search_tools({query: "update salesforce record"})
  → [{name: "salesforce_updateRecord", description: "Update fields on a Salesforce object"}, …]
get_tool_details({name: "salesforce_updateRecord"})
  → {name, description, inputSchema: {objectType, recordId, data}}
salesforce_updateRecord({...})            # model now knows the exact interface
```

**何时切换。** 对于少量工具，文档认为全部加载没有问题。一旦定义占据了上下文窗口（Context Window）的相当一部分，就应切换。文档的建议是：**以上下文窗口的百分比设定阈值，例如 1%–5%**。先加载定义，一旦达到阈值，就切换到渐进式发现。

目录层的**搜索策略**：

| 策略 | 做法 | 取舍 |
| --- | --- | --- |
| 关键词 | 对名称和描述使用 BM25、正则 | 简单，名称描述性强时很有效 |
| 嵌入向量 | 基于描述的向量相似度 | 能处理同义词和语义 |
| 子智能体 | 由一个小而快的模型为任务挑选工具 | 通常效果非常好，成本更高 |
| 混合 | 合并排名，或按查询选择策略 | 集多家之长 |

一些模型提供方（文档点名了 OpenAI 和 Anthropic）提供**内置的工具搜索**。有的话优先使用。当提供方没有该功能，或你需要专门的检索方式（例如领域排序或访问控制过滤）时，再自己构建。

指南中的**实现建议**：提供**多个详细程度**（仅名称、名称 + 描述、完整模式）；**在宿主侧缓存定义**，以便之后重新注入时无需再次发送 `tools/list`（这个缓存与模型上下文中当前的内容是两回事）；**收到 `list_changed` 时刷新**，即在 `notifications/tools/list_changed` 到达时重建索引；以及**按服务器对工具分组**。

### 动态服务器管理
同样的思路也适用于整个服务器。动态服务器管理（Dynamic Server Management）指的是：宿主（Host）不必在启动时连接所有已配置的服务器，而是维护一个带有高层描述的服务器**注册中心（Registry）**，**只在模型需要时才连接**某个服务器，并**断开**不再相关的服务器。指南中的流程使用面向模型的元工具（Meta-tool），例如 `search_available_servers("CRM")` → `enable_server("salesforce")`。启用时，宿主发送 `server/discover`，然后发送 `tools/list`，这是 2026-07-28 的流程；较早的握手时代宿主在这里会发送 `initialize`。一个通用智能体（Agent）一开始只带几个常驻服务器，再按需扩展。与智能体技能（Agent Skill）结合时，技能可以声明它需要哪些服务器，宿主只在该技能被调用时才连接它们。

### 缓存：`ttlMs`、`cacheScope` 与 `list_changed`
2026-07-28 新增：每个 `resultType: "complete"` 的 `tools/list`、`prompts/list`、`resources/list`、`resources/templates/list`、`resources/read` 和 `server/discover` 结果都**必须（MUST）**携带 `ttlMs` 和 `cacheScope`（即 `CacheableResult` 接口，SEP-2549）。2025-11-25 的服务器没有这些字段，所以宿主（Host）只能依赖 `listChanged` 通知（Notification）或自己的启发式规则。宿主的定义缓存必须遵循以下规则：

- 当 `now < t_received + ttlMs` 时为新鲜；之后即为过期（Stale），下次访问时重新获取。`ttlMs: 0`、字段缺失或取负值都表示立即过期。
- TTL 是**新鲜度提示，而不是轮询间隔**。客户端不应当（SHOULD NOT）在后台自动重新获取；任何确实要轮询的客户端都必须（MUST）使用抖动（jitter）和退避（backoff）。
- 相关的 **`list_changed` 通知会立即使**缓存的列表**失效（Invalidation）**，即使仍在 TTL 之内。在 2026-07-28 中，客户端是在以 `toolsListChanged: true` 打开的 `subscriptions/listen` 流上收到它的。
- `cacheScope: "public"` 可以在用户之间共享。`"private"` 不得（MUST NOT）跨授权上下文共享，因此换了令牌（Token）就需要另一份缓存。
- 缓存键（Cache Key）是方法 + 会影响结果的参数。分页的每一页都是独立的缓存条目。

与此相关、同样是本修订版新增的一点：服务器**应当（SHOULD）以确定性的顺序返回工具**，正是为了让客户端能够缓存列表，并让 LLM 的提示缓存持续命中。

### 提示缓存陷阱
大多数模型提供方都会缓存**提示词前缀，其中包括 `tools` 数组**，这就是提示缓存（Prompt Caching）。渐进式发现（Progressive Discovery）天然倾向于在对话中途*添加*定义，而这会使提供方的缓存失效。文档警告说，这种未命中*“可能比你删掉的那些定义花费更多令牌。”* 文档给出的缓解措施：

- 把新发现的定义**追加**到缓存断点之后，而不是重新排序 `tools` 数组；**或者**把所有调用都路由到一个稳定的 **`call_tool({name, args})`** 元工具（Meta-tool），让数组永远不变。
- 把断开服务器视为**对话边界**级别的操作，而不是每轮都可以做的操作。

### 程序化工具调用（“代码模式”）
在直接调用方式下，每次调用都是一次往返，而且*“完整的结果会流回模型的上下文。”* 在代码模式（Code Mode）中，**模型编写调用工具的代码**。代码在沙箱（Sandbox）中运行，只有最终结果会返回。指南的示意图对比了 100K+ 令牌的中间结果与一个约 200 令牌的脚本加约 15 令牌的摘要。

工作原理：

1. **从 MCP 模式（Schema）生成带类型的 API。** 对每个工具，宿主根据其输入模式，以及（如果有的话）其 **`outputSchema`** 生成一个函数，后者提供精确的返回类型。如果没有输出模式，就使用通用类型（真正的解决办法是让服务器提供 `outputSchema`）。或者，对于一次性调用，可以由宿主代理一个 `extract(value, ExpectedType)` 辅助函数，把它转给一个小模型来强制转换值。这会增加延迟，也可能产生幻觉，所以要校验结果。
2. **模型编写一个脚本**来调用这些函数，例如：获取错误日志，*在沙箱内*去重，为每个不同的错误提交一张工单，然后用 `console.log` 输出一行摘要。
3. **沙箱执行脚本。** 函数调用被拦截，并由**宿主代理（Host Broker）**以 `tools/call` 的形式路由到正确的服务器。数据在服务器之间流动，而不进入模型的上下文。

```text
┌──────────────────────── MCP Host ────────────────────────┐
│  LLM ──writes code──▶ Sandbox ──function call──▶ MCP Client ──tools/call──▶ Server A
│   ▲                    │  ▲                         │                    └─▶ Server B
│   └──console output────┘  └──────return value───────┘
└──────────────────────────────────────────────────────────┘
```

**角色分工。** *沙箱*（Sandbox）**没有直接的网络访问**，它唯一的出口就是生成的桩函数。*宿主*（Host）是代理：它把调用映射到服务器、执行调用并**持有所有凭据**，因此生成的代码永远看不到令牌（Token）。*模型*只能看到沙箱打印或返回的内容。

**选择沙箱。** 指南列出的是示例，而非推荐：**Deno / `isolated-vm`**（具有细粒度权限的 V8 隔离环境）、**Monty**（面向 AI 用途的实验性极简 Python 解释器，默认无 I/O）、**pctx**（处于早期阶段的 TypeScript 代码模式库）、**Wasmtime**（任何编译为 Wasm 的语言，基于能力的安全模型）。无论选择哪一个，模式都相同：注入桩函数，通过进程内或 stdio 通道拦截调用，使网络权限可以完全保持禁用，再把调用以 `tools/call` 分发出去。

### 代码模式的安全与错误
代码模式（Code Mode）增加了一个代码执行面，而就规范而言，代理方仍然是 MCP 宿主（Host）：

- **逐次调用授权（Authorization）。** 对来自沙箱的调用施加与直接调用相同的人在回路（Human in the Loop）策略。*批准脚本并不等于一揽子批准它发起的每一次调用。* 宿主可以授予类别化的批准（“本次运行允许 `ticketing_createIssue`”），但代理仍必须逐次检查每个调用是否符合该授权。
- **跨服务器数据流。** 一个服务器的结果对另一个服务器而言是不可信的输入，因此要对代理转发的调用施加同样的输入审查。*仅截断输出并不能阻止数据外泄。*
- **网络隔离**、**不暴露凭据**、**资源限制**（超时、内存）以及**输出过滤**（在控制台输出到达模型之前进行校验和截断）。

**错误。** 工具失败是以 `isError: true` 的成功响应（Response）到达的，而不是传输层故障。生成的包装函数应当**将其转换为抛出的异常**，以便模型代码可以 `try`/`catch`。如果未捕获的错误终止了脚本，就把它作为脚本的结果呈现出来，让模型能够自我纠正。模型负责报告任何已经提交的部分副作用。

### 两种模式结合
完整的设计是：模型先用发现类元工具（Meta-tool）找到它需要的少数几个工具，加载它们的模式（Schema），然后编写**一个**脚本，一次性调用所有这些工具。发现机制把**定义**的令牌成本降到最低，代码模式（Code Mode）把**结果**的令牌成本降到最低，于是上下文得以专注于推理。

## Key points
- 多服务器宿主（Host）为**每个服务器保留一个客户端（Client）**，并且必须**对工具名消歧**。规范要求以服务器标识符作为前缀，而**不是** `serverInfo.name`，因为后者不保证唯一。
- **渐进式发现（Progressive Discovery）** = 照常调用 `tools/list`，但推迟注入：提供一个 `search_tools` 元工具（Meta-tool），然后按目录 → 查看（`get_tool_details`）→ 执行的顺序进行。
- 以**约占上下文窗口（Context Window）1%–5% 的阈值**决定是否切换到它。工具不多时，全部加载即可。
- 搜索策略（Search Strategy）：**关键词、嵌入向量、子智能体、混合**。提供方有内置工具搜索时优先使用。
- 2026-07-28 的列表结果携带 **`ttlMs` + `cacheScope`**。当 `now < t_received + ttlMs` 时为新鲜；`list_changed` 会立即使缓存失效（Invalidation）；`"private"` 缓存绝不跨授权上下文使用。
- 在对话中途修改 `tools` 数组会**破坏提供方的提示缓存（Prompt Caching）**。应把新定义追加到断点之后，或通过一个稳定的 `call_tool` 元工具路由。服务器应当（SHOULD）以**确定性顺序**返回工具。
- **代码模式（Code Mode）**：模型针对由输入模式和 `outputSchema` 生成的带类型桩函数编写脚本，由一个无网络的沙箱运行，宿主代理（Host Broker）负责分发 `tools/call` 并持有凭据。只有摘要会返回。
- 批准脚本**不等于一揽子批准**。代理对每次调用分别授权（Authorization），`isError: true` 在生成的代码中会变成异常。

## Pitches
### 如何把一个宿主扩展到上百个 MCP 工具？
我不会在每一轮都发送所有定义。工具定义（Tool Definition）低于上下文窗口几个百分点的阈值时，我就全部加载；超过阈值，我就切换到渐进式发现（Progressive Discovery）：模型拿到一个小小的 search_tools 元工具（Meta-tool），只查看它选中的那些工具的完整模式，然后再调用它们。定义缓存在宿主侧，遵循每个服务器的 ttlMs 和 list_changed 失效机制。我还会保持 tools 数组稳定，通过一个 call_tool 元工具来路由调用，这样提供方的提示缓存（Prompt Caching）就能一直命中。

### 什么是代码模式，为什么要用它？
代码模式（Code Mode），也叫程序化工具调用（Programmatic Tool Calling），就是让模型针对从 MCP 工具模式生成的带类型函数写一段短脚本，而不是每轮只做一次工具调用。脚本在一个没有网络的沙箱（Sandbox）里运行，每个函数调用都会回到宿主，由宿主发出真正的 tools/call 并持有凭据。像成千上万行日志这样的大块中间数据永远不会进入模型的上下文，进去的只有打印出来的摘要。这意味着更少的往返、更少的令牌，结果往往也更好。

### 如何保证代码模式的安全？
我把沙箱（Sandbox）当作不可信代码的执行环境。它没有网络、没有凭据，在真正的隔离运行时里运行，比如 V8 隔离环境或 Wasm，并受超时和内存限制。一个过滤过的 Python exec 不算数。宿主代理（Host Broker）仍然是 MCP 宿主，所以它会对脚本发起的每次调用施加同样的审批策略。批准了脚本并不等于批准了它的副作用。我还会审查在服务器之间传递的数据，并在输出到达模型之前进行截断。

## Interview
### 两个已连接的服务器都暴露了一个名为 `search` 的工具。你怎么处理？
规范规定工具名只在单个服务器内唯一，而进行聚合的客户端（Client）应当（SHOULD）消歧，例如**用服务器标识符作为前缀**。我使用宿主自己的配置键（`flights__search`、`hotels__search`），而不是 `serverInfo.name`，因为规范指出该名称不保证唯一，不应当（SHOULD NOT）用于消歧。我会让加了前缀的名称保持在允许的字符范围内（字母、数字、`_`、`-`、`.`），且不超过 128 个字符，以便模型 API 接受。一张路由表把加了前缀的名称映射回 *(客户端, 原始名称)*。我还会在目录中按服务器对工具分组，让模型把相关能力放在一起看。

### 讲讲渐进式工具发现的流程。什么情况下你*不会*用它？
宿主（Host）照常调用 `tools/list`，但**推迟注入**定义。模型拿到一个 `search_tools` 元工具（Meta-tool）（目录：名称和一行描述），然后用 `get_tool_details` 获取选中工具的完整模式（查看），再调用它（执行）。检索方式可以是关键词、嵌入向量、子智能体或混合，也可以使用提供方内置的工具搜索。当定义只占上下文窗口的一小部分时，我**不会**使用它。文档建议在大约 1%–5% 的阈值处切换。低于这个阈值，额外的搜索往返成本高于节省，而且一次看到所有工具的模型能规划得更好。

### 用了渐进式发现之后，我们的账单反而*上涨*了。可能是什么原因？
很可能是**提供方的提示缓存（Prompt Caching）**。大多数提供方会缓存包括 `tools` 数组在内的提示词前缀。如果宿主插入新发现的定义，尤其是重新排序之后，每一轮的前缀都会变化，缓存就会未命中。文档指出，这种未命中的代价可能超过你删掉的那些定义。解决办法：把新定义追加到缓存断点之后，或者保持一个由元工具组成的固定 `tools` 数组，所有执行都通过稳定的 `call_tool({name, args})` 进行。另外不要在对话中途断开服务器，而应把它视为对话边界级别的操作。在服务器侧，确定性的 `tools/list` 排序（2026-07-28 中的一条 SHOULD）也有帮助。

### 在 2026-07-28 中，宿主应如何缓存工具列表？
每个完整的 `tools/list` 结果都携带 `ttlMs` 和 `cacheScope`。记录接收时间，并在 `now < t_received + ttlMs` 时把列表视为新鲜。过期（Stale）后，**在下次访问时**重新获取。TTL 不是轮询间隔，任何轮询方都必须（MUST）加入抖动和退避。`ttlMs` 为 0、缺失或为负值都表示立即过期。在 `subscriptions/listen` 流上收到的 `notifications/tools/list_changed` 会使该条目失效，即使仍在 TTL 之内。`"private"` 结果只能在同一授权上下文中复用。宿主也可以提前刷新，例如在意外出现“工具未找到”之后；如果重新获取失败，也可以提供过期数据。

### 为一个智能体设计代码模式执行器。有哪些组件，安全规则是什么？
三个组件。**模型**针对宿主根据每个工具的输入模式和 `outputSchema` 生成的带类型桩函数编写脚本。**沙箱（Sandbox）**在隔离的运行时（V8 隔离环境、Wasm、极简解释器）中运行脚本，没有网络，并有超时和内存上限。**宿主代理（Host Broker）**通过进程内或 stdio 通道接收每个桩函数调用，将其映射到正确的服务器，用代码永远看不到的凭据发送 `tools/call`，再返回结果。规则：根据用户的授权对**每一次**调用进行授权（批准脚本不等于一揽子批准），把跨服务器的数据视为不可信，过滤并截断输出，并把 `isError: true` 转换为异常，以便脚本能够捕获。未捕获的错误要作为结果返回，让模型能够自我纠正。

### 陷阱题：“我们在去掉了 `__builtins__` 的环境里 exec 模型生成的 Python，所以它是沙箱化的。”你同意吗？
不同意。在宿主解释器中限制内置函数或过滤 AST 只是一种便利手段，而不是安全边界。CPython 有很多途径可以重新拿到强大的对象（通过双下划线属性进行内省、你传入的对象、异常及其栈帧），而且没有任何东西限制内存或 CPU。模型代码还与宿主共享同一进程，因此也共享凭据。文档的建议是使用真正隔离的运行时，没有网络，只有通往代理的桩函数通道，再加上超时和内存限制。玩具级执行器用来学习没问题，但绝不能在生产环境中用来运行不可信的输出。

## Glossary
- Progressive discovery | 渐进式（工具）发现 | 将工具定义排除在模型上下文之外，通过搜索／查看类元工具按需加载。
- Meta-tool | 元工具 | 由宿主提供的工具，例如 `search_tools` 或 `call_tool`，它作用于其他工具而不是外部世界。
- Tool namespacing | 工具命名空间化 | 用服务器标识符作为工具名前缀，使来自不同服务器的工具不会冲突。
- Programmatic tool calling (code mode) | 程序化工具调用（代码模式） | 模型编写一个通过生成的桩函数调用工具的脚本，只有脚本的输出会返回上下文。
- Sandbox | 沙箱 | 一个没有直接网络访问、也没有凭据的隔离运行时，用于执行模型编写的代码。
- Host broker | 宿主代理（中介） | 宿主中的组件，负责拦截沙箱的函数调用、对其授权，并以 `tools/call` 的形式分发。
- `ttlMs` | `ttlMs`（缓存有效期，毫秒） | 服务器给出的提示，表示一个可缓存结果在多少毫秒内可被视为新鲜。
- `cacheScope` | `cacheScope`（缓存范围） | `"public"` 或 `"private"`：缓存的结果是否可以跨授权上下文共享。
- Prompt caching | 提示缓存 | 提供方对未改变的提示词前缀（包括 `tools` 数组）进行复用，以降低成本和延迟。
- Dynamic server management | 动态服务器管理 | 依据一个服务器描述注册中心，只在需要时连接服务器，并在不再相关时断开连接。

### 2. 多服务器宿主：每个服务器一个客户端，工具加命名空间
宿主（Host）为每个服务器持有一个 `Client`，以**它自己的配置名**（`flights`、`hotels`、`weather`）为键，而不是 `serverInfo.name`。它给每个工具加上该键作为前缀（`flights__search`），这样既能保证名称在各服务器之间唯一，又仍在允许的工具名字符范围内；路由调用时再把前缀拆掉。客户端（Client）是惰性连接的，所以服务器在被需要之前不产生任何开销（动态服务器管理，Dynamic Server Management），而 `disable()` 会断开它。

宿主还维护着**自己的工具定义缓存**，遵循 `ttlMs`（SDK 的 `Client` 也有内置缓存；我们调用 `list_tools(cache_mode="bypass")`，确保你在这里看到的每次获取都真正发往服务器）。

```python
SEP = "__"


class Host:
    def __init__(self, registry: dict[str, dict], clock=time.monotonic):
        self.registry = registry          # alias -> {"server": ..., "about": "..."}
        self.clock = clock
        self.clients: dict[str, Client] = {}
        self.owners: dict[str, tuple[asyncio.Task, asyncio.Event]] = {}
        self.cache: dict[str, dict] = {}  # alias -> {"tools", "received", "ttl_ms", "scope"}
        self.list_requests = 0

    async def _own(self, alias: str, ready: asyncio.Event, stop: asyncio.Event) -> None:
        # One long-lived task per connection: it enters and exits the Client in the same task.
        async with Client(self.registry[alias]["server"]) as client:
            self.clients[alias] = client
            ready.set()
            await stop.wait()

    async def enable(self, alias: str) -> Client:
        if alias not in self.clients:
            ready, stop = asyncio.Event(), asyncio.Event()
            task = asyncio.create_task(self._own(alias, ready, stop))
            self.owners[alias] = (task, stop)
            await asyncio.wait([task, asyncio.create_task(ready.wait())], return_when=asyncio.FIRST_COMPLETED)
            if task.done():                # the connection failed before it was ready
                self.owners.pop(alias)
                raise task.exception()
        return self.clients[alias]

    async def disable(self, alias: str) -> None:
        self.cache.pop(alias, None)
        self.clients.pop(alias, None)
        task, stop = self.owners.pop(alias)
        stop.set()
        await task

    async def close(self) -> None:
        for alias in list(self.owners):
            await self.disable(alias)

    async def tools_of(self, alias: str):
        entry = self.cache.get(alias)
        if entry and self.clock() < entry["received"] + entry["ttl_ms"] / 1000:   # now < t_received + ttlMs
            return entry["tools"]
        client = await self.enable(alias)
        result = await client.list_tools(cache_mode="bypass")
        self.list_requests += 1
        self.cache[alias] = {"tools": result.tools, "received": self.clock(),
                             "ttl_ms": max(result.ttl_ms or 0, 0), "scope": result.cache_scope}
        return result.tools

    def on_list_changed(self, alias: str) -> None:
        """notifications/tools/list_changed: stale immediately, even inside the TTL."""
        self.cache.pop(alias, None)

    async def definitions(self, aliases=None) -> list[dict]:
        """Namespaced definitions in the shape a model API expects, grouped by server, stable order."""
        out = []
        for alias in aliases or self.registry:
            for t in await self.tools_of(alias):
                out.append({"name": f"{alias}{SEP}{t.name}", "description": t.description or "",
                            "input_schema": t.input_schema})
        return out

    async def call(self, name: str, arguments: dict):
        alias, sep, tool = name.partition(SEP)
        if not sep or alias not in self.registry:
            raise KeyError(f"unknown tool {name!r}")
        client = await self.enable(alias)
        return await client.call_tool(tool, arguments)


REGISTRY = {
    "flights": {"server": flights, "about": "Flight search across airlines"},
    "hotels": {"server": hotels, "about": "Hotel search and booking"},
    "weather": {"server": weather, "about": "Weather forecasts"},
}
host = Host(REGISTRY)
for d in await host.definitions():
    print(f"{d['name']:<18} {d['description'][:70]}")
print("\nconnected:", sorted(host.clients), "| serverInfo names:",
      [c.server_info.name for c in host.clients.values()])
result = await host.call("hotels__search", {"city": "Barcelona", "max_price": 150})
print("hotels__search ->", result.structured_content)
```

### 4. 渐进式发现：目录 → 查看 → 执行
模型拿到的不再是 120 多个定义，而是三个小小的**元工具（Meta-tool）**。`search_tools` 返回名称和一行描述（第 1 层，目录），`get_tool_details` 返回单个完整模式（第 2 层，查看），`call_tool` 按名称执行任何已发现的工具（第 3 层，执行）。这里的搜索只是简单的关键词打分；嵌入向量或小模型也可以放进同一个函数中。

```python
META_TOOLS = [
    {"name": "search_tools", "description": "Search all connected MCP tools. Returns names and one-line "
     "descriptions grouped by server. Use detail='names' for just names.",
     "input_schema": {"type": "object", "properties": {"query": {"type": "string"},
                      "detail": {"type": "string", "enum": ["names", "summary"]}}, "required": ["query"]}},
    {"name": "get_tool_details", "description": "Full definition (input schema) of one tool by name.",
     "input_schema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}},
    {"name": "call_tool", "description": "Call a tool found with search_tools, by its full name.",
     "input_schema": {"type": "object", "properties": {"name": {"type": "string"},
                      "arguments": {"type": "object"}}, "required": ["name", "arguments"]}},
]


async def search_tools(query: str, detail: str = "summary", k: int = 5):
    words = {w.strip(".,").lower() for w in query.split()}
    scored = []
    for d in await host.definitions():
        text = (d["name"].replace(SEP, " ").replace("_", " ") + " " + d["description"]).lower()
        score = sum(w in text for w in words)
        if score:
            scored.append((-score, d["name"], d["description"].split(". ")[0]))
    hits = sorted(scored)[:k]
    return [h[1] for h in hits] if detail == "names" else [{"name": n, "description": s} for _, n, s in hits]


async def get_tool_details(name: str):
    return next(d for d in await host.definitions() if d["name"] == name)


async def run_meta_tool(name: str, args: dict):
    if name == "search_tools":
        return await search_tools(**args)
    if name == "get_tool_details":
        return await get_tool_details(**args)
    if name == "call_tool":
        r = await host.call(args["name"], args["arguments"])
        return {"isError": r.is_error, "content": r.structured_content or r.content[0].text}
    raise KeyError(name)


# A scripted "model" that plans a trip using only the three meta-tools.
script = [("search_tools", {"query": "weather forecast city"}),
          ("get_tool_details", {"name": "weather__forecast"}),
          ("call_tool", {"name": "weather__forecast", "arguments": {"city": "Barcelona", "date": "2026-06-15"}})]
context = est_tokens(META_TOOLS)
print(f"meta-tool definitions: ~{context} tokens (vs ~{total} for everything)\n")
for name, args in script:
    out = await run_meta_tool(name, args)
    context += est_tokens(out)
    print(f">>> {name}({json.dumps(args)})\n<<< {json.dumps(out)[:300]}\n")
print(f"context spent on tools after the task: ~{context} tokens ({context / total:.1%} of loading everything)")
```

### 5. 缓存：`ttlMs`、`list_changed` 与提示缓存陷阱
这里涉及两种不同的缓存。**宿主侧定义缓存**遵循服务器的 `ttlMs`（新鲜度：`now < t_received + ttlMs`），并会因 `notifications/tools/list_changed` 而失效（Invalidation）。**模型提供方的提示缓存（Prompt Caching）**覆盖请求的前缀，其中包括 `tools` 数组；一旦修改这个数组，缓存就会未命中。我们使用一个假时钟，免得大家干等五分钟。

```python
class FakeClock:
    def __init__(self):
        self.t = 1000.0

    def __call__(self):
        return self.t


clock = FakeClock()
cached_host = Host({k: REGISTRY[k] for k in ("flights", "weather")}, clock=clock)


async def need_tools(label):
    before = cached_host.list_requests
    await cached_host.definitions()
    hit = cached_host.list_requests == before
    print(f"{label:<46} tools/list sent: {cached_host.list_requests - before}  ({'cache hit' if hit else 'fetched'})")


await need_tools("t=0      first use")
print("          cached:", {a: (e["ttl_ms"], e["scope"]) for a, e in cached_host.cache.items()})
clock.t += 30
await need_tools("t=30s    both fresh")
clock.t += 45
await need_tools("t=75s    weather TTL (60 s) expired")
cached_host.on_list_changed("flights")
await need_tools("list_changed from flights (TTL still fresh)")
await cached_host.close()
```

再看提示缓存（Prompt Caching）这一侧。我们在两种策略下为模型每一轮看到的 `tools` 数组计算指纹：一种是把已发现的定义注入 `tools`（并重新排序），另一种是只保留稳定的元工具（Meta-tool），所有调用都经由 `call_tool` 路由。

```python
def fingerprint(tools):
    return hashlib.sha256(json.dumps(tools, sort_keys=True).encode()).hexdigest()[:10]


weather_def = await get_tool_details("weather__forecast")
hotel_def = await get_tool_details("hotels__search")
turns_inject = [META_TOOLS, sorted(META_TOOLS + [weather_def], key=lambda d: d["name"]),
                sorted(META_TOOLS + [weather_def, hotel_def], key=lambda d: d["name"])]
turns_stable = [META_TOOLS, META_TOOLS, META_TOOLS]
for i, (a, b) in enumerate(zip(turns_inject, turns_stable), 1):
    print(f"turn {i}: inject+sort tools={fingerprint(a)} | stable call_tool tools={fingerprint(b)}")
print("\nA changed fingerprint means the provider's cached prefix no longer matches -> cache miss.")
print("Fix: append new definitions after the cache breakpoint, or keep the array fixed and use call_tool.")
```

### 6. 代码模式：从模式生成带类型的 API
为了实现程序化工具调用（Programmatic Tool Calling），宿主把每个工具的模式（Schema）转换为模型可以据此编码的函数签名。放进提示词里的就是这一小段文本，而不是 JSON 模式。

```python
PY_TYPES = {"string": "str", "integer": "int", "number": "float", "boolean": "bool", "object": "dict",
            "array": "list"}


def stub_source(d: dict) -> str:
    props, required = d["input_schema"].get("properties", {}), d["input_schema"].get("required", [])
    params = []
    for p, s in props.items():
        t = PY_TYPES.get(s.get("type"), "object")
        params.append(f"{p}: {t}" if p in required else f"{p}: {t} | None = None")
    return f'async def {d["name"]}({", ".join(params)}):\n    """{d["description"]}"""'


travel_defs = await host.definitions(["flights", "hotels", "weather"])
api_text = "\n\n".join(stub_source(d) for d in travel_defs)
print(api_text)
print(f"\n~{est_tokens(api_text)} tokens of API description")
```

### 7. 玩具执行器与逐次调用授权的代理
执行器运行模型编写的代码时，作用域中只有生成的函数和 `print`。每个生成的函数都是一个**代理桩函数（Broker Stub）**：它检查本次运行的审批授权，把调用以 `tools/call` 转发给正确的服务器，并把 `isError: true` 转换为脚本可以 `try`/`except` 的异常。

> **这不是沙箱。** 带着精简过的 `__builtins__` 和 AST 过滤器的 `exec` 只是一种教学手段；CPython 有很多逃逸途径，而且这里没有内存限制。真正的宿主会在独立的隔离运行时中运行模型代码（例如 Deno 或 `isolated-vm` 这样的 V8 隔离环境、Wasmtime 这样的 Wasm 运行时、Monty 这样的极简解释器，或是锁定的容器／微虚拟机），**没有网络**，有超时和内存限制，且只有一条通往代理的消息通道。

```python
class ScriptToolError(Exception):
    """What a generated stub raises inside the script when the server answers isError: true."""


SAFE_BUILTINS = {n: __builtins__[n] if isinstance(__builtins__, dict) else getattr(__builtins__, n)
                 for n in ["len", "min", "max", "sum", "sorted", "range", "enumerate", "zip", "round",
                           "str", "int", "float", "dict", "list", "set", "any", "all", "Exception"]}


def check_script(code: str) -> None:
    for node in ast.walk(ast.parse(code)):
        if isinstance(node, (ast.Import, ast.ImportFrom, ast.Global, ast.Nonlocal)):
            raise PermissionError(f"line {node.lineno}: imports/globals are not allowed")
        if isinstance(node, ast.Attribute) and node.attr.startswith("_"):
            raise PermissionError(f"line {node.lineno}: private attribute {node.attr!r} is not allowed")
        if isinstance(node, ast.Name) and node.id.startswith("__"):
            raise PermissionError(f"line {node.lineno}: dunder name {node.id!r} is not allowed")


async def run_script(code: str, grant: set[str], timeout: float = 5.0, max_output: int = 1000) -> dict:
    """Run model-written code; return only what it prints (truncated) plus a call log for the host."""
    calls, out = [], []

    def make_stub(name):
        async def stub(**kwargs):
            if name not in grant:                       # per-call authorization, even inside an approved script
                calls.append((name, "DENIED"))
                raise PermissionError(f"{name} is not approved for this run")
            r = await host.call(name, kwargs)
            calls.append((name, "error" if r.is_error else "ok"))
            if r.is_error:
                raise ScriptToolError(r.content[0].text)
            sc = r.structured_content
            return sc["result"] if sc and set(sc) == {"result"} else (sc or r.content[0].text)
        return stub

    try:
        check_script(code)
        env = {"__builtins__": SAFE_BUILTINS, "ToolError": ScriptToolError,
               "print": lambda *a: out.append(" ".join(map(str, a)))}
        env.update({d["name"]: make_stub(d["name"]) for d in travel_defs})
        body = "\n".join("    " + line for line in code.splitlines())
        exec(compile(f"async def _script():\n{body}\n", "<model-code>", "exec"), env)
        await asyncio.wait_for(env["_script"](), timeout)
        status = "ok"
    except Exception as exc:                            # surface uncaught errors so the model can self-correct
        status = f"{type(exc).__name__}: {exc}"
    text = "\n".join(out)
    return {"status": status, "output": text[:max_output] + ("…[truncated]" if len(text) > max_output else ""),
            "calls": calls}


print(await run_script("import os\nprint(os.environ)", grant=set()))
print(await run_script("print(().__class__.__mro__)", grant=set()))
print(await run_script("x = await weather__forecast(city='Paris', date='2026-06-15')", grant={"weather__forecast"}))
print(await run_script('''
try:
    sky = await weather__forecast(city="Paris", date="2026-06-15")
except ToolError as err:
    sky = f"unavailable ({err})"
print("Paris:", sky)
''', grant={"weather__forecast"}))
```

看看这四个结果：两个脚本在运行前就被拒绝；一个未捕获的工具错误被作为脚本的结果呈现（让模型可以自我纠正）；还有一个脚本用 `try`/`except` 自行处理了 `isError`。

### 8. 直接工具调用与代码模式的对比
任务：*“找出 2026-06-15 从 NYC 到 BCN 最便宜的直飞航班、一家低于 180 美元的酒店，以及当天的天气。”* 先用直接方式：三次工具调用，每个完整结果都要回到模型。再用代码模式（Code Mode）：模型编写一个脚本，数据留在执行器中，只返回一行摘要。

```python
TASK_TOOLS = [("flights__search", {"origin": "NYC", "destination": "BCN", "date": "2026-06-15"}),
              ("hotels__search", {"city": "Barcelona", "max_price": 180}),
              ("weather__forecast", {"city": "Barcelona", "date": "2026-06-15"})]

direct_tokens, model_calls = 0, 1                 # the first model call decides to use tools
for name, args in TASK_TOOLS:                     # one tool call per turn, as a cautious model would
    r = await host.call(name, args)
    payload = r.structured_content or r.content[0].text
    direct_tokens += est_tokens(payload)
    model_calls += 1
    print(f"direct: {name:<18} -> ~{est_tokens(payload):>5} tokens into context")
print(f"direct total: {model_calls} model calls, ~{direct_tokens} tokens of tool results in context\n")

MODEL_SCRIPT = '''
flights = await flights__search(origin="NYC", destination="BCN", date="2026-06-15")
nonstop = [f for f in flights if f["stops"] == 0]
best = min(nonstop, key=lambda f: f["price"])
hotels = await hotels__search(city="Barcelona", max_price=180)
hotel = max(hotels, key=lambda h: h["rating"])
sky = await weather__forecast(city="Barcelona", date="2026-06-15")
print(f"{len(flights)} flights checked; cheapest non-stop {best['id']} at {best['depart']} for ${best['price']}; "
      f"best hotel under $180: {hotel['name']} (${hotel['price']}, {hotel['rating']}*); weather: {sky}")
'''
run = await run_script(MODEL_SCRIPT, grant={"flights__search", "hotels__search", "weather__forecast"})
print("code mode broker log:", run["calls"])
print("code mode output    :", run["output"])
print(f"code mode total: 2 model calls, ~{est_tokens(MODEL_SCRIPT) + est_tokens(run['output'])} tokens "
      f"(script + output) in context")
```

接下来是文档中的安全规则：批准脚本**不等于**一揽子批准。下面的授权涵盖了搜索，但不包括预订，所以代理在运行时拒绝了这个有副作用的调用，该错误成为脚本的结果。

```python
greedy = '''
hotels = await hotels__search(city="Barcelona", max_price=180)
print(await hotels__book(name=hotels[0]["name"], nights=7))
'''
print(json.dumps(await run_script(greedy, grant={"hotels__search"}), indent=2))
```
