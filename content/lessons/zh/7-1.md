## Summary
MCP 的核心规范被刻意保持得很小，而且变化缓慢，因为每一项新增内容都是永久性的。扩展（Extension）就是泄压阀：它们是可选的、单独版本化的新增内容，以 `io.modelcontextprotocol/tasks` 这样的反向 DNS 字符串标识，通过双方能力（Capability）中的 `extensions` 映射进行协商，并且在开发者显式启用之前始终处于禁用状态。本课讲解标识符如何运作、官方扩展与实验性扩展如何治理、协商与优雅降级（Graceful Degradation）如何进行，然后深入剖析最重要的官方扩展：**Tasks**。借助 Tasks，服务器可以用一个持久的任务（Task）句柄来回应一个耗时的 `tools/call`。客户端轮询 `tasks/get`，通过 `tasks/update` 在执行过程中提供输入，并可以用 `tasks/cancel` 取消。在 Notebook 中，你将使用 Python SDK 的扩展 API 构建双方的实现。

## Lesson
### 为什么 MCP 需要扩展
MCP 扩展（Extension）是*对规范的可选补充，定义了核心协议之外的能力*。文档列出了某项特性可能放在核心之外的三个原因：

- **模块化（Modular）**：只有部分部署需要的独立特性，例如另一种认证流程。
- **专门化（Specialized）**：面向某个行业或某种用例的逻辑。
- **实验性（Experimental）**：一个在被考虑纳入核心之前仍在孵化中的想法。

这源自第 1.1 课中的设计原则。*趋同优于选择*和*稳定优于速度*让核心很难改变：“今天说不，门还开着；说是，门就永远关上了”。扩展是在真实实现中检验想法的地方，而规范则是把它们固定下来的地方。你将在本模块中遇到的好几项特性，都是从这里起步或最终落脚于此的。Tasks 在 2026-07-28 中被**移出**了核心。MCP 应用（MCP App）、Skills over MCP 以及授权扩展则从未进入过核心。

### 扩展标识符
每个扩展都有一个唯一的**扩展标识符（Extension Identifier）**，形式为 `{vendor-prefix}/{extension-name}`。标识符遵循与 `_meta` 键相同的语法，但前缀是**必需的**：以点分隔的若干标签，然后是 `/`，再然后是名称。官方扩展使用厂商前缀 `io.modelcontextprotocol`。第三方使用自己拥有的域名的反写形式，类似 Java 包名，因此拥有 `example.com` 的公司会发布 `com.example/my-extension`。这样无需一个集中式的名称注册中心就能避免冲突。

| 扩展 | 标识符 | 仓库 |
| --- | --- | --- |
| MCP 应用（MCP Apps） | `io.modelcontextprotocol/ui` | `ext-apps` |
| Tasks | `io.modelcontextprotocol/tasks` | `ext-tasks` |
| Skills over MCP | `io.modelcontextprotocol/skills` | `ext-skills` |
| OAuth 客户端凭据（OAuth Client Credentials） | `io.modelcontextprotocol/oauth-client-credentials` | `ext-auth` |
| 企业托管授权（Enterprise-Managed Authorization） | `io.modelcontextprotocol/enterprise-managed-authorization` | `ext-auth` |

### 官方扩展与实验性扩展
**官方扩展（Official Extension）**位于 `modelcontextprotocol` GitHub 组织中带有 `ext-` 前缀的仓库里。**实验性扩展（Experimental Extension）**为工作组（Working Group）和兴趣组（Interest Group）提供了一个在撰写正式提案之前进行原型开发的地方。它们位于带有 `experimental-ext-` 前缀的仓库中，例如 `experimental-ext-interceptors`。实验性扩展有三条基本规则：

1. 每个实验性扩展都必须与一个**工作组或兴趣组**相关联。
2. 仓库和已发布的软件包必须在 README 和包名中**清楚地标明其实验性状态**。
3. **核心维护者（Core Maintainer）保留监督权**，可以归档或移除实验性仓库。

**升级（Graduation）**为官方状态需要经过**扩展轨道（Extensions Track）**上的标准规范增强提案（SEP）流程。孵化仓库及其参考实现可以作为证明该扩展切实可行的证据。

### 创建与演进扩展
官方扩展遵循由 SEP-2133 定义的、基于规范增强提案（SEP）的生命周期：

1. **提议（Propose）**：在 MCP 主仓库中开启一个类型为*扩展轨道（Extensions Track）*的 SEP。
2. **实现（Implement）**：在某个官方 SDK 中构建至少一个参考实现。这是 SEP 能够进入评审**之前**的必要条件。
3. **评审（Review）**：核心维护者评审该 SEP，并拥有最终决定权。
4. **发布（Publish）**：一旦获批，就提交 PR，把该扩展添加到它的扩展仓库中。
5. **采用（Adopt）**：之后，其他客户端、服务器和 SDK 就可以实现它。

有两条要求。扩展规范必须使用 **RFC 2119 用语**（必须（MUST）、应当（SHOULD）、可以（MAY）），并且每个扩展都必须有一个关联的工作组或兴趣组。

SDK 的支持是可选的。实现扩展**并不是协议一致性（Protocol Conformance）的必要条件**，SDK 维护者自行决定支持哪些扩展。不过，他们应当说明自己支持哪些。最重要的是，**扩展始终默认禁用，需要开发者显式启用。**

扩展也会独立于核心**各自演进**。它们的维护者无需核心维护者评审即可发布更新。为了保持向后兼容，应在扩展的设置对象中添加能力标志或版本信息，而不是新造一个标识符。如果破坏性变更无法避免，就使用一个新的标识符，例如 `io.modelcontextprotocol/my-extension-v2`。**破坏性变更（Breaking Change）**包括删除或重命名字段、改变字段类型、改变现有行为的语义，以及新增必填字段。

### 协商：`extensions` 能力
修订版 2026-07-28 在 `ClientCapabilities` 和 `ServerCapabilities` 中都新增了一个 `extensions` 字段。它的键是扩展标识符，值是各扩展的设置对象。空对象 `{}` 表示“支持，没有设置”。每个扩展都会定义自己的设置对象的模式（Schema）。

由于协议是无状态的（Stateless），**客户端会在每一个请求中声明它的扩展**，放在 `_meta["io.modelcontextprotocol/clientCapabilities"]` 里。**服务器则在 `server/discover` 结果中公布它的扩展**：

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "New York"},
   "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
             "io.modelcontextprotocol/clientCapabilities": {
               "extensions": {"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}},
             "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"}}}}
```

```json
{"result": {"resultType": "complete", "supportedVersions": ["2026-07-28"],
            "capabilities": {"tools": {}, "extensions": {"io.modelcontextprotocol/ui": {}}}}}
```

只有当**双方**都声明了某个扩展时，该扩展才会对一个请求生效。由于客户端能力是随每个请求传递的，服务器必须检查*本次*请求的声明，而不是更早的某次声明。Tasks 规范对此有明确规定：服务器不得把任务返回给“一个未在其请求中包含该扩展能力的客户端，**无论之前是否声明过**”。

> **规范规则（优雅降级）。** 如果一方支持某个扩展而另一方不支持，支持的一方必须要么**回退到核心行为**，要么在该扩展是强制性的情况下**以适当的错误拒绝该请求**。一个经过 UI 增强的工具仍然应当返回有意义的文本，而一个要求某个认证扩展的服务器则可以拒绝不具备该扩展的客户端。

应使用的错误是 `-32021`（*Missing Required Client Capability*，缺少必需的客户端能力），并在 `data.requiredCapabilities.extensions` 中给出缺失的扩展。请在你的扩展规范中写明回退行为。

**客户端矩阵（Client Matrix）**记录了哪些宿主（Host）实现了哪些官方扩展。MCP 应用得到了广泛支持，包括 Claude、Claude Desktop、VS Code GitHub Copilot、ChatGPT、Cursor 和 Goose。认证类扩展和 Skills 扩展目前只有少数实现，例如 `mcpc` CLI、Archestra.AI，以及 ChatGPT、fast-agent 和检查器（Inspector）中对 Skills 的部分支持。要为某个客户端添加支持，请阅读扩展规范，在 `clientCapabilities.extensions` 中声明它，从 `server/discover` 中读取服务器的 `extensions`，实现各项要求，并提交 PR 来更新矩阵。

### Tasks：为什么不直接阻塞等待？
有些工具调用需要几秒、几分钟甚至几小时：CI 流水线、批处理作业以及人工审批。你可以让请求一直保持打开状态直到工作完成，但任务（Task）解决了阻塞等待无法解决的问题：

- **无需长连接。** 客户端和 HTTP 中间设备都会设置超时，让超过几秒的阻塞等待变得不切实际。
- **崩溃恢复能力。** 任务 ID 是一个**持久句柄（Durable Handle）**，因此重启后的客户端可以用同一个 ID 继续轮询。
- **进度可见性。** 任务带有状态和可选的 `statusMessage`。
- **执行过程中的交互。** 任务可以在 `input_required` 状态下暂停，客户端通过 `tasks/update` 进行回答，既不需要第二条连接，也不需要任何不请自来的服务器到客户端的请求。
- **由服务器主导。** 服务器针对每个请求决定是否创建任务。客户端只需通过能力声明启用一次，然后处理到达的任何一种结果形态即可。

任务适用于长时间运行的操作、人在回路（Human in the Loop）的审批、对已有作业 ID 的外部作业 API 的封装、移动客户端之类不可靠的连接，以及部分进度很重要的批处理。

### 任务是如何创建的
客户端在每个请求的能力中声明 `"io.modelcontextprotocol/tasks": {}`，服务器则在 `server/discover` 中公布同一个键（目前尚未定义任何设置）。如今只有 `tools/call` 支持任务（Task）。实现方应当预期，在未来的修订版中会有更多请求类型支持任务。

支持任务的 `tools/call` 是**多态的（Polymorphic）**：它可能返回普通的 `CallToolResult`，也可能返回 `CreateTaskResult`。两者通过 `resultType` 来区分，该扩展为其增加了一个保留值 `"task"`。`CreateTaskResult` 是 `Result & Task`，因此任务字段直接位于结果之中：

```json
{"jsonrpc": "2.0", "id": 2,
 "result": {"resultType": "task", "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840",
            "status": "working", "statusMessage": "The operation is now in progress.",
            "createdAt": "2025-11-25T10:30:00Z", "lastUpdatedAt": "2025-11-25T10:40:00Z",
            "ttlMs": 60000, "pollIntervalMs": 5000}}
```

| `Task` 字段 | 含义 |
| --- | --- |
| `taskId` | 稳定的、由服务器生成的标识符 |
| `status` | `working`、`input_required`、`completed`、`failed` 或 `cancelled` |
| `statusMessage` | 可选的、人类可读的状态描述；可以展示给用户或模型 |
| `createdAt`、`lastUpdatedAt` | ISO 8601 时间戳 |
| `ttlMs` | 自创建起的存活时间（毫秒），`null` 表示无限；可能会变化 |
| `pollIntervalMs` | 建议的轮询间隔；客户端应当（SHOULD）遵守；可能会变化 |

> **规范规则。** 在任务被**持久地创建**之前，服务器**禁止（MUST NOT）**返回 `CreateTaskResult`，也就是说，针对该 ID 的 `tasks/get` 此时必须已经能够解析成功。在最终一致的存储中，要先等待数据达到一致。这能让客户端免于为一个尚不存在的任务进行投机性轮询。

如果服务器在决定是否创建任务*之前*就需要输入，它应当通过普通的多轮往返请求（MRTR）流程（第 5.3 课）同步解决，然后再返回任务。

### 轮询与生命周期
客户端以 `{"taskId": ...}` 轮询 `tasks/get`。响应是一个 `DetailedTask`，其 `resultType` 为 `"complete"`，因为它是 `tasks/get` 的正常结果。其字段取决于状态：

| 状态 | 额外字段 | 含义 |
| --- | --- | --- |
| `working` | 无 | 仍在运行 |
| `input_required` | `inputRequests` | 服务器需要客户端提供输入后才能继续 |
| `completed` | `result` | 与原始请求本应返回的内容完全相同，例如一个 `CallToolResult` |
| `failed` | `error` | 执行期间发生了 **JSON-RPC 错误** |
| `cancelled` | 无 | 工作已被取消 |

`completed`、`failed` 和 `cancelled` 是**终止状态（Terminal Status）**，因此处于这些状态之一的任务再也不会改变。允许的状态转换是 working ⇄ input_required，以及从这两者中的任意一个转换到某个终止状态。

> **陷阱。** 一个以 `isError: true` 结束的工具，其任务状态是 **`completed`**，而不是 `failed`。`failed` 专门留给 JSON-RPC 协议错误，禁止（MUST NOT）用于工具层面的错误。这与核心规则一致：工具错误应当放在结果里，让模型能够看到。

### 执行过程中的输入：`tasks/update`
当服务器在执行过程中需要某些东西（例如一次确认）时，它会把任务转为 `input_required`。之后的 `tasks/get` 就会带有 `inputRequests`，这是一个由带键的嵌入式请求组成的映射，例如 `{"approve": {"method": "elicitation/create", "params": {...}}}`。客户端用 **`tasks/update`** `{"taskId", "inputResponses": {"approve": {"action": "accept", "content": {...}}}}` 进行回答，服务器则回复一个空的确认（`resultType: "complete"`）。

以下几条规则让这一机制更加稳健：

- `inputRequests` 是一个**时间点快照**：它包含所有尚未处理的请求，并且在得到回答之前每次轮询都会重复出现。客户端应当（SHOULD）**按键去重**，以免向用户重复提问。
- 每个键都必须（MUST）**在任务的整个生命周期内唯一**，且绝不重用。这使服务器能够**忽略针对未知键或已回答键的响应**。
- 确认是**最终一致的**：在确认之后的一小段时间里，`tasks/get` 可能仍然显示 `input_required`。允许只提交部分响应，任务会一直停留在 `input_required`，直到其余响应到达。
- 嵌入式请求保持其正常的**信任模型**。通过任务到达的征询（Elicitation）与直接的 `elicitation/create` 被完全同等对待。任务并不是一个更高信任级别的通道。

> **任务输入与 MRTR 的区别。** 两者看起来相似，但并不相同。MRTR（`InputRequiredResult`）的回答是在**重试原始请求**时带回来的。任务输入则由 `tasks/get` 呈现、由 `tasks/update` 回答，而任务在此期间持续运行。

### 取消与通知
`tasks/cancel {"taskId"}` 表达的是一种**意图**。服务器必须（MUST）以空结果确认它，但取消是**协作式的（Cooperative Cancellation）**。服务器决定是否以及何时停止，如果工作先一步完成，任务仍可能以 `completed` 结束。`notifications/cancelled` **禁止（MUST NOT）**用于任务。取消之后，客户端可以直接忘掉这个任务，无需再次轮询。

轮询是默认方式，但服务器也可以（MAY）推送 `notifications/tasks`。每条通知（Notification）都携带完整的 `DetailedTask`，与 `tasks/get` 将返回的内容完全相同。客户端通过发送带有 `notifications.taskIds` 的 `subscriptions/listen` 来启用通知。`notifications/progress` 和 `notifications/message` 不支持用于任务。

### 错误、路由与安全
| 情形 | 响应 |
| --- | --- |
| 未知或已过期的 `taskId` | `-32602` Invalid params（对 `tasks/get` 是 MUST，对 update/cancel 是 SHOULD） |
| 客户端未声明该扩展，却调用了 `tasks/*` 或订阅任务通知 | 带有 `requiredCapabilities` 的 `-32021` |
| 服务器只能以任务形式处理该请求，但客户端没有声明 Tasks | `-32021` |
| 内部故障 | `-32603` |

在可流式 HTTP（Streamable HTTP）上，客户端在 `tasks/get`、`tasks/update` 和 `tasks/cancel` 中**必须（MUST）**把 `Mcp-Name` 请求头设置为 `params.taskId`。这样，负载均衡器就能把针对某个任务的每一次调用都路由到持有其状态的那个实例上。

在安全方面，任务 ID 可以充当 bearer 令牌（Token），因此**必须（MUST）**以足够的熵生成，使其无法被猜中。每一个任务请求都**必须（MUST）**经过认证（Authentication），并针对任务的所有者进行授权（Authorization）。由于该扩展没有 `tasks/list`，一个调用者再也无法发现另一个调用者的任务。该扩展还保留了 `tasks/` 方法前缀、`notifications/tasks/` 通知前缀以及 `resultType` 值 `"task"`。

### 与 2025-11-25 相比有哪些变化
在 2025-11-25 中，任务（Task）是一项**实验性的核心特性**。修订版 2026-07-28（SEP-2663）把它们移入了官方扩展 `io.modelcontextprotocol/tasks`，并重新进行了设计：

| 2025-11-25（核心，实验性） | 2026-07-28（扩展） |
| --- | --- |
| 客户端按每次调用请求任务（`tools/call` 上的 `task` 参数） | **由服务器主导**：服务器在它选择的任何时候返回句柄，无需按请求启用 |
| 阻塞式的 `tasks/result` 获取结果 | 已移除；轮询 **`tasks/get`**，它会内联返回 `result`/`error` |
| 通过服务器到客户端的请求获取输入 | 新增 **`tasks/update`**，携带 `inputResponses` |
| `tasks/list` | **已移除**（防止跨调用者泄露） |
| `ttl`、`pollInterval` | `ttlMs`、`pollIntervalMs` |

为了向后兼容，一个对外暴露简单的 `call_tool() -> CallToolResult` 的客户端库无需改变其公共 API。它可以在内部驱动轮询循环，只返回最终结果。Notebook 正是要构建这样一个客户端。

## Key points
- 扩展（Extension）是可选的、单独版本化的新增内容，以 `{vendor-prefix}/{name}` 标识。官方扩展使用 `io.modelcontextprotocol/`，第三方使用自己拥有的域名的反写形式（`com.example/...`）。
- 官方扩展位于 `ext-*` 仓库中。实验性扩展（Experimental Extension）位于 `experimental-ext-*` 仓库中，需要一个工作组／兴趣组，必须标明为实验性，并通过**扩展轨道 SEP（Extensions Track SEP）**升级为官方扩展。
- 创建官方扩展需要在**评审之前**于某个官方 SDK 中提供参考实现（Reference Implementation），使用 RFC 2119 用语，并有一个发起小组。SDK 支持是可选的，而且扩展**默认关闭**。
- 协商使用 `extensions` 映射（2026-07-28 新增）。客户端在 `_meta` 的客户端能力（Capability）中**按请求**声明它，服务器在 `server/discover` 中声明它。只有双方都声明时，扩展才会生效。
- 优雅降级（Graceful Degradation）意味着回退到核心行为，或者在扩展是强制性的情况下以 `-32021` 和 `requiredCapabilities` 拒绝。破坏性变更需要一个新的标识符（`...-v2`）。
- 借助 Tasks，服务器以 `CreateTaskResult`（`resultType: "task"`）回应 `tools/call`，前提是*本次*请求声明了 `io.modelcontextprotocol/tasks`。服务器必须在任务被持久创建之后才能响应。
- `tasks/get` 用于轮询（遵守 `pollIntervalMs`），`tasks/update` 用于回答 `inputRequests`，`tasks/cancel` 是协作式的。终止状态（Terminal Status）有 `completed`、`failed` 和 `cancelled`。
- `failed` 仅用于 JSON-RPC 错误。带有 `isError: true` 的工具结果会让任务（Task）处于 `completed` 状态。
- 与 2025-11-25 相比，Tasks 移出了核心，`tasks/result` 和 `tasks/list` 不复存在，`tasks/update` 是新增的，并且由服务器决定何时创建任务（Task）。

## Pitches
### 什么是 MCP 扩展？为什么不直接把它加进规范？
扩展（Extension）是一段可选的、单独版本化的协议内容，带有一个反向 DNS 标识符，比如 io.modelcontextprotocol/tasks。双方都在各自能力里的 extensions 映射中声明它，只有双方都声明了才会启用。MCP 让核心保持精简，因为每一项核心新增都是永久的，所以新想法会先以扩展的形式来尝试：先在实验性仓库里孵化，再通过扩展轨道 SEP 升级。如果对端不支持某个扩展，另一方就回退到核心行为，或者用 -32021 拒绝。

### MCP Tasks 是如何工作的？
当一次工具调用会花很长时间时，服务器可以返回一个任务（Task）句柄，而不是一直阻塞。这个句柄是一个 CreateTaskResult，resultType 是 task，带有任务 ID、TTL 和建议的轮询间隔。客户端不断轮询 tasks/get，直到任务进入 completed、failed 或 cancelled。如果服务器中途需要一次确认，任务就会进入 input_required，带上按键区分的输入请求，客户端再用 tasks/update 来回答。通过 tasks/cancel 取消是协作式的。服务器只会为在本次请求中声明了该扩展的客户端创建任务。

### 2026-07-28 中 Tasks 有哪些变化？
在 2025-11-25 里，任务（Task）还是一项实验性的核心特性：客户端按每次调用申请任务，用阻塞式的 tasks/result 获取结果，还能用 tasks/list 列出所有任务。到了 2026-07-28，它变成了官方的 io.modelcontextprotocol/tasks 扩展。现在任务创建由服务器主导，结果通过轮询 tasks/get 内联返回，执行过程中的输入走新的 tasks/update，而 tasks/list 被去掉了，这也堵上了一个跨调用者的信息泄露口子。

## Interview
### 请讲解在无状态的 2026-07-28 部署中，扩展是如何协商的。
服务器在其 `server/discover` 结果的 `capabilities.extensions` 映射中列出它的扩展（Extension），例如 `{"io.modelcontextprotocol/tasks": {}}`。由于没有会话，客户端会**在每一个请求中**发送自己的 `extensions` 映射，放在 `_meta["io.modelcontextprotocol/clientCapabilities"]` 里。两个映射都以扩展标识符为键、以各扩展的设置对象为值。空对象表示“支持，没有设置”。只有当双方都声明时，扩展才会对一个请求生效，并且服务器必须依据**本次请求**的能力来做决定，而不是更早的某次请求。因此，一个经过负载均衡的服务器集群可以在不共享任何状态的情况下，对同一个客户端的不同请求给出不同的回应。

### 一个服务器有一个经过 UI 增强的工具和一个只能以任务形式运行的工具。对于两个扩展都没有声明的客户端，它们各自会怎么做？
两种情况都遵循概述中要求的优雅降级（Graceful Degradation）。对于 **UI 工具**，扩展只是一种增强，因此服务器回退到核心行为，返回有意义的文本内容（以及 `structuredContent`），任何客户端都能使用。对于**仅限任务的工具**，不存在合理的同步回退方案。Tasks 规范规定，如果服务器不返回 `CreateTaskResult` 就无法处理该请求，它**必须（MUST）**返回 `-32021`（Missing Required Client Capability，缺少必需的客户端能力），并附带 `data.requiredCapabilities.extensions["io.modelcontextprotocol/tasks"] = {}`。这样客户端就能确切地知道需要添加哪项能力。

### 为什么 Tasks 要求在发送响应之前任务必须已经“持久创建”？
响应会把一个 `taskId` 交给客户端，而客户端的下一步就是 `tasks/get`。如果这条记录只存在于某个实例的内存中，或者存在于一个尚未收敛的最终一致存储中，那么第一次轮询可能会返回“任务未找到”（`-32602`）。客户端就不得不去猜测该重试还是放弃。要求在响应之前完成持久化，就消除了投机性轮询。这也正是这个句柄具备崩溃恢复能力的原因：客户端持久保存 ID，重启后继续轮询。

### 一个以任务形式运行的工具遇到了上游 API 的限流。任务应该以 `failed` 还是 `completed` 结束？
这取决于失败是如何呈现的。如果工具把它作为工具结果来报告，例如 `isError: true` 并附带消息 “rate limit exceeded”，那么任务就是 **`completed`**，`result` 中保存的是这个错误结果。`failed` 专门留给执行期间发生的 **JSON-RPC 错误**，例如 `-32603`，此时 `error` 字段保存 JSON-RPC 错误，`statusMessage` 应当对其加以说明。这条规则与核心规范中协议错误（Protocol Error）和工具错误之间的区分一致，并且能保证 `tasks/get` 返回的内容与同步调用本应返回的内容完全相同。

### 你会如何实现一个 Tasks 客户端，让现有代码可以像调用普通的 `call_tool` 那样调用它？
在每个请求中公布 `io.modelcontextprotocol/tasks`。当 `tools/call` 返回 `resultType: "task"` 时，把 `taskId` 持久保存下来，然后进入一个循环：等待 `pollIntervalMs`，调用 `tasks/get` 并把 `Mcp-Name` 请求头设置为任务 ID，遇到终止状态（Terminal Status）就停止。遇到 `input_required` 时，对已经处理过的 `inputRequests` 键进行去重，让每个请求都经过与直接征询（Elicitation）相同的同意界面，然后发送带有 `inputResponses` 的 `tasks/update`。遇到 `completed` 时，把 `result` 作为 `CallToolResult` 返回。遇到 `failed` 时，把 `error` 作为 MCP 错误抛出。把 TTL 到期当作兜底机制。在 Python SDK 中，这就是一个带有针对 `"task"` 的 `ResultClaim` 的 `ClientExtension`。

### 陷阱题：为什么要移除 `tasks/list`？客户端在崩溃后如何找回它的任务？
`tasks/list` 存在跨调用者泄露的风险：一个范围控制不当的实现可能会把一个用户的任务 ID 暴露给另一个用户，而任务 ID 可以充当 bearer 令牌（Token）。在该扩展中根本没有列举功能。客户端需要自己负责**持久保存任务 ID**。规范规定客户端应当（SHOULD）持久地存储它们，以便在重启之后继续轮询。反过来，服务器必须使用高熵的 ID，并针对任务的所有者对每一次 `tasks/*` 调用进行授权（Authorization）。

## Glossary
- Extension | 扩展 | 对 MCP 的一种可选的、单独版本化的补充，以 `{vendor-prefix}/{name}` 字符串标识，并通过能力进行协商。
- Extension identifier | 扩展标识符 | 扩展的反向 DNS 键，例如 `io.modelcontextprotocol/tasks`，遵循 `_meta` 键的规则，且前缀是必需的。
- Experimental extension | 实验性扩展 | 位于 `experimental-ext-*` 仓库中、与某个工作组或兴趣组绑定的孵化中扩展，通过扩展轨道 SEP 升级为官方扩展。
- Graceful degradation | 优雅降级 | 当对端不支持某个扩展时，回退到核心行为，或以 `-32021` 拒绝。
- Task | 任务 | 一个长时间运行请求的持久的、由服务器生成的句柄，带有状态、TTL 和轮询间隔。
- `CreateTaskResult` | 创建任务结果 | 带有 `resultType: "task"` 的多态 `tools/call` 结果，携带初始的 `Task`。
- `tasks/get` | `tasks/get`（任务查询） | 用于轮询的请求，返回任务的当前状态，并在任务终止时返回其 `result` 或 `error`。
- `tasks/update` | `tasks/update`（任务输入更新） | 为任务尚未处理的 `inputRequests` 提交 `inputResponses` 的请求。
- Cooperative cancellation | 协作式取消 | 一种只表达意图的取消；服务器会确认它，但仍可能把工作做完。
- Terminal status | 终止状态 | `completed`、`failed` 或 `cancelled`；一旦进入，任务的状态就再也不会改变。

SDK 用与规范相同的规则来校验扩展标识符（Extension Identifier）：以点分隔的标签、必需的 `/`，然后是名称。试一试合法的和不合法的标识符。

### 2. 在双方声明扩展
`MCPServer(extensions=[...])` 接受 `Extension` 子类。每一个都会以其 `settings()` 返回的字典，公布在 `capabilities.extensions[identifier]` 之下。在客户端一侧，`Client(extensions=[...])` 接受 `ClientExtension` 实例，而 `advertise()` 是只带标识符的简化形式。下面的工具读取**本次请求**的客户端能力（Capability），并进行优雅降级（Graceful Degradation）。

```python
import json

from mcp import Client
from mcp.client.extension import advertise
from mcp.server import MCPServer
from mcp.server.extension import Extension
from mcp.server.mcpserver import Context

ALERTS = "com.example/weather-alerts"


class WeatherAlerts(Extension):
    identifier = ALERTS

    def settings(self):
        return {"version": 1}          # per-extension settings object (schema defined by the extension)


server = MCPServer("weather", extensions=[WeatherAlerts()])


@server.tool()
def forecast(city: str, ctx: Context) -> str:
    """Today's forecast for a city."""
    caps = ctx.client_capabilities
    declared = (caps.extensions or {}) if caps else {}
    text = f"{city}: 18°C, light rain."
    if ALERTS in declared:             # enhanced behaviour only when THIS request declared the extension
        text += " ALERT: wind gusts up to 70 km/h after 18:00."
    return text                        # core fallback is still a meaningful answer


async with Client(server) as plain, Client(server, extensions=[advertise(ALERTS)]) as aware:
    print("server advertises:", json.dumps(plain.server_capabilities.extensions))
    print("plain client ->", (await plain.call_tool("forecast", {"city": "Oslo"})).content[0].text)
    print("aware client ->", (await aware.call_tool("forecast", {"city": "Oslo"})).content[0].text)
```

### 3. 线路层面：基于原始 stdio 的按请求协商
这里把同样的思路作为一个子进程来运行。客户端能力（Capability）位于每个请求的 `_meta` 中，因此同一条连接上连续的两个 `tools/call` 可以协商出不同的结果。

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "alerts_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    from mcp.server.extension import Extension
    from mcp.server.mcpserver import Context

    class WeatherAlerts(Extension):
        identifier = "com.example/weather-alerts"
        def settings(self):
            return {"version": 1}

    server = MCPServer("weather", extensions=[WeatherAlerts()])

    @server.tool()
    def forecast(city: str, ctx: Context) -> str:
        """Today's forecast for a city."""
        caps = ctx.client_capabilities
        extra = " ALERT: gusts after 18:00." if caps and caps.extensions and "com.example/weather-alerts" in caps.extensions else ""
        return f"{city}: 18C, light rain." + extra

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "alerts_server.py")],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)


def meta(extensions=None):
    caps = {"extensions": extensions} if extensions else {}
    return {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": caps,
            "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def rpc(id_, method, params, show=True):
    message = {"jsonrpc": "2.0", "id": id_, "method": method, "params": params}
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    if show:
        print(">>>", json.dumps(message))
        print("<<<", json.dumps(reply)[:400], "\n")
    return reply


disc = rpc(1, "server/discover", {"_meta": meta()}, show=False)
print("server/discover capabilities.extensions =", disc["result"]["capabilities"].get("extensions"), "\n")
rpc(2, "tools/call", {"name": "forecast", "arguments": {"city": "Oslo"}, "_meta": meta()})
rpc(3, "tools/call", {"name": "forecast", "arguments": {"city": "Oslo"},
                      "_meta": meta({"com.example/weather-alerts": {}})})
proc.stdin.close()
exit_code = proc.wait(timeout=10)
```

### 4. 强制性扩展：以 `-32021` 拒绝
当不存在有意义的回退方案时，正确的回答是 *Missing Required Client Capability*（缺少必需的客户端能力）错误。SDK 的辅助函数 `require_client_extension(ctx, identifier)` 会抛出这个错误，并带上 `requiredCapabilities` 载荷。工具处理函数接收的是高层的 `Context`，其 `request_context` 就是该辅助函数所需的底层上下文对象（Context）。

```python
from mcp.server.mcpserver import require_client_extension
from mcp.shared.exceptions import MCPError

strict = MCPServer("strict", extensions=[WeatherAlerts()])


@strict.tool()
def severe_weather_feed(region: str, ctx: Context) -> str:
    """Stream of severe-weather alerts (only meaningful with the alerts extension)."""
    require_client_extension(ctx.request_context, ALERTS)
    return f"{region}: no active alerts"


async with Client(strict) as plain, Client(strict, extensions=[advertise(ALERTS)]) as aware:
    print("aware ->", (await aware.call_tool("severe_weather_feed", {"region": "NO"})).content[0].text)
    try:
        await plain.call_tool("severe_weather_feed", {"region": "NO"})
    except MCPError as err:
        print("plain -> error", err.code, err.message)
        print("         data:", json.dumps(err.data))
```

### 5. Tasks 扩展：线路模型
这里没有安装任何 Tasks 软件包，因此我们在 SDK 的扩展 API 之上自己构建这个扩展（Extension），逐字段遵循 `ext-tasks` 规范。首先是各种数据形态：`Task`、`CreateTaskResult`（`resultType: "task"`）、`DetailedTask`（`tasks/get` 的结果，`resultType: "complete"`），以及请求参数。SDK 的模型会把 snake_case 属性转换为线路上的 camelCase 名称。

```python
import asyncio
import secrets
from datetime import datetime, timezone
from typing import Any, Literal

import mcp_types as types
from mcp_types import Request, RequestParams, Result

TASKS = "io.modelcontextprotocol/tasks"
Status = Literal["working", "input_required", "completed", "failed", "cancelled"]
TERMINAL = {"completed", "failed", "cancelled"}


def now() -> str:
    return datetime.now(timezone.utc).isoformat(timespec="milliseconds").replace("+00:00", "Z")


class Task(Result):
    task_id: str
    status: Status
    status_message: str | None = None
    created_at: str
    last_updated_at: str
    ttl_ms: int | None
    poll_interval_ms: int | None = None


class CreateTaskResult(Task):              # type CreateTaskResult = Result & Task
    result_type: Literal["task"] = "task"


class DetailedTask(Task):                  # type GetTaskResult = Result & DetailedTask
    result_type: Literal["complete"] = "complete"
    input_requests: dict[str, Any] | None = None
    result: dict[str, Any] | None = None
    error: dict[str, Any] | None = None


class TaskIdParams(RequestParams):
    task_id: str


class UpdateTaskParams(TaskIdParams):
    input_responses: dict[str, Any]


def wire(model) -> dict:
    return model.model_dump(by_alias=True, exclude_none=True, mode="json")


print(json.dumps(wire(CreateTaskResult(task_id="t-1", status="working", created_at=now(),
                                       last_updated_at=now(), ttl_ms=60_000, poll_interval_ms=50)), indent=2))
```

### 6. 服务器端：一个拦截 `tools/call` 的 `Extension`
该扩展使用了 SDK 的两个扩展点。**`intercept_tool_call`** 针对每个请求决定是否返回任务（Task）。**`methods()`** 以附加的 `MethodBinding` 形式提供 `tasks/get`、`tasks/update` 和 `tasks/cancel`。工作以后台 `asyncio` 任务的形式运行。它可以在 `input_required` 状态下暂停并等待 `tasks/update`，并按照规范要求的 `completed` / `failed` 划分来记录终止状态（Terminal Status）。

```python
from mcp.server.extension import MethodBinding
from mcp_types import INTERNAL_ERROR, INVALID_PARAMS


class TasksExtension(Extension):
    identifier = TASKS

    def __init__(self, task_tools: dict[str, dict], ttl_ms: int = 60_000, poll_interval_ms: int = 50):
        self.task_tools = task_tools     # tool name -> {"needs_approval": bool, "requires_tasks": bool}
        self.ttl_ms, self.poll_interval_ms = ttl_ms, poll_interval_ms
        self.store: dict[str, dict] = {} # stands in for a durable store (database, Redis, ...)
        self.server: MCPServer | None = None

    # ---- helpers -------------------------------------------------------------------------------
    def _set(self, rec, **changes):
        rec.update(changes, last_updated_at=now())

    def _view(self, rec, model=DetailedTask):
        fields = {k: rec.get(k) for k in ("task_id", "status", "status_message", "created_at",
                                          "last_updated_at", "ttl_ms", "poll_interval_ms")}
        if model is DetailedTask:
            if rec["status"] == "input_required":
                fields["input_requests"] = {k: v for k, v in rec["requests"].items() if k not in rec["answers"]}
            fields["result"], fields["error"] = rec.get("result"), rec.get("error")
        return model(**fields)

    def _lookup(self, ctx, task_id):
        require_client_extension(ctx, TASKS)                    # -32021 for non-declaring clients
        rec = self.store.get(task_id)
        if rec is None:
            raise MCPError(INVALID_PARAMS, "Failed to retrieve task: Task not found")
        return rec

    async def _ask(self, rec, key, params):
        """Pause in input_required until tasks/update answers `key` (keys are never reused)."""
        rec["requests"][key] = {"method": "elicitation/create", "params": params}
        rec["waiters"][key] = asyncio.get_running_loop().create_future()
        self._set(rec, status="input_required", status_message="Waiting for approval")
        answer = await rec["waiters"][key]
        self._set(rec, status="working", status_message="Approval received")
        return answer

    async def _run(self, rec, name, arguments):
        try:
            if self.task_tools[name].get("needs_approval"):
                answer = await self._ask(rec, "approve-1", {
                    "mode": "form", "message": f"Approve {name} with {arguments}?",
                    "requestedSchema": {"type": "object", "properties": {"approve": {"type": "boolean"}},
                                        "required": ["approve"]}})
                if answer.get("action") != "accept" or not (answer.get("content") or {}).get("approve"):
                    self._set(rec, status="completed", status_message="Declined by the user",
                              result={"content": [{"type": "text", "text": "Declined by the user."}],
                                      "isError": True})
                    return
            for step in (1, 2, 3):
                self._set(rec, status_message=f"step {step}/3")
                await asyncio.sleep(0.05)                       # pretend this is minutes of work
            out = await self.server.call_tool(name, arguments)  # run the real tool function
            self._set(rec, status="completed", status_message="Done", result=wire(out))
        except asyncio.CancelledError:
            self._set(rec, status="cancelled", status_message="Cancelled at the client's request")
        except MCPError as exc:                                 # a JSON-RPC error -> failed
            self._set(rec, status="failed", status_message=f"Tool execution failed: {exc.message}",
                      error=exc.error.model_dump(exclude_none=True))
        except Exception as exc:                                # a tool error -> completed + isError
            self._set(rec, status="completed", status_message="Tool reported an error",
                      result={"content": [{"type": "text", "text": str(exc)}], "isError": True})

    # ---- contribution points -------------------------------------------------------------------
    async def intercept_tool_call(self, params, ctx, call_next):
        policy = self.task_tools.get(params.name)
        caps = ctx.session.client_capabilities
        declared = bool(caps and caps.extensions and TASKS in caps.extensions)
        if policy is None:
            return await call_next(ctx)                         # not a long-running tool
        if not declared:
            if policy.get("requires_tasks"):
                require_client_extension(ctx, TASKS)            # cannot serve synchronously -> -32021
            return await call_next(ctx)                         # graceful degradation: block and answer
        task_id = secrets.token_urlsafe(16)                     # unguessable handle
        rec = {"task_id": task_id, "status": "working", "status_message": "Queued",
               "created_at": now(), "last_updated_at": now(), "ttl_ms": self.ttl_ms,
               "poll_interval_ms": self.poll_interval_ms, "requests": {}, "answers": {}, "waiters": {}}
        self.store[task_id] = rec                               # durably created BEFORE we respond
        rec["job"] = asyncio.create_task(self._run(rec, params.name, params.arguments or {}))
        return self._view(rec, CreateTaskResult)

    def methods(self):
        async def get(ctx, params: TaskIdParams):
            return self._view(self._lookup(ctx, params.task_id))

        async def update(ctx, params: UpdateTaskParams):
            rec = self._lookup(ctx, params.task_id)
            for key, response in params.input_responses.items():
                waiter = rec["waiters"].get(key)
                if waiter is None or key in rec["answers"]:     # unknown or already answered: ignore
                    continue
                rec["answers"][key] = response
                waiter.set_result(response)
            return types.EmptyResult(result_type="complete")

        async def cancel(ctx, params: TaskIdParams):
            rec = self._lookup(ctx, params.task_id)
            if rec["status"] not in TERMINAL:
                rec["job"].cancel()                             # cooperative: we choose to honour it
            return types.EmptyResult(result_type="complete")

        return [MethodBinding("tasks/get", TaskIdParams, get),
                MethodBinding("tasks/update", UpdateTaskParams, update),
                MethodBinding("tasks/cancel", TaskIdParams, cancel)]


tasks_ext = TasksExtension({"build_report": {"needs_approval": False, "requires_tasks": False},
                            "deploy": {"needs_approval": True, "requires_tasks": True}})
ops = MCPServer("ops", extensions=[tasks_ext])
tasks_ext.server = ops


@ops.tool()
def build_report(rows: int) -> str:
    """Aggregate `rows` rows of sales data into a report (slow)."""
    if rows > 1_000_000:
        raise MCPError(INTERNAL_ERROR, "Warehouse unavailable")   # protocol-level failure
    if rows < 0:
        raise ValueError("rows must be >= 0")                     # tool-level error
    return f"Report over {rows} rows: revenue up 12%."


@ops.tool()
def deploy(env: str) -> str:
    """Deploy the current build to an environment (needs human approval)."""
    return f"Deployed build 42 to {env}."


print("task-capable tools:", tasks_ext.task_tools)
```

### 7. 客户端：多态结果与轮询循环
声明了 Tasks 的客户端必须能接受*任意一种*结果形态。在 Python SDK 中，`ClientExtension` 通过一个以 `resultType` 为键的 `ResultClaim` 来声明额外的结果形态。借助 `session.call_tool(..., allow_claimed=True)`，我们拿到原始的 `CreateTaskResult`，然后自己驱动 `tasks/get`，并打印每一个线路结果。`name_param = "taskId"` 这一行会让 SDK 在通过 HTTP 运行时设置 `Mcp-Name: <taskId>`，从而支持对任务（Task）的路由。

```python
from mcp.client.extension import ClientExtension, ResultClaim


class GetTaskRequest(Request[TaskIdParams, Literal["tasks/get"]]):
    method: Literal["tasks/get"] = "tasks/get"
    name_param = "taskId"


class UpdateTaskRequest(Request[UpdateTaskParams, Literal["tasks/update"]]):
    method: Literal["tasks/update"] = "tasks/update"
    name_param = "taskId"


class CancelTaskRequest(Request[TaskIdParams, Literal["tasks/cancel"]]):
    method: Literal["tasks/cancel"] = "tasks/cancel"
    name_param = "taskId"


class TasksClient(ClientExtension):
    """Declares io.modelcontextprotocol/tasks and claims resultType "task"."""
    identifier = TASKS

    def __init__(self, answer=None):
        self.answer = answer   # callback used in section 9 to answer input requests

    def claims(self):
        return [ResultClaim(result_type="task", model=CreateTaskResult, resolve=self._resolve)]

    async def _resolve(self, created, cctx):
        raise NotImplementedError   # filled in section 9


async def tasks_get(session, task_id):
    return await session.send_request(GetTaskRequest(params=TaskIdParams(task_id=task_id)), DetailedTask)


async with Client(ops) as legacy, Client(ops, extensions=[TasksClient()]) as modern:
    print("server/discover extensions:", modern.server_capabilities.extensions)
    sync = await legacy.call_tool("build_report", {"rows": 500})          # no Tasks declared
    print("\nclient WITHOUT tasks -> ordinary CallToolResult:", sync.content[0].text)

    created = await modern.session.call_tool("build_report", {"rows": 500}, allow_claimed=True)
    print("\nclient WITH tasks -> tools/call result:")
    print(json.dumps(wire(created), indent=2))
    while True:
        await asyncio.sleep(created.poll_interval_ms / 1000)                # honour pollIntervalMs
        state = await tasks_get(modern.session, created.task_id)
        print("tasks/get ->", state.status, "|", state.status_message)
        if state.status in TERMINAL:
            print(json.dumps(wire(state)["result"], indent=2))
            break
```

### 8. 用 `tasks/update` 提供执行过程中的输入，然后看错误路径
`deploy` 需要审批。轮询直到 `input_required`，读取带键的 `inputRequests`，用 `tasks/update` 回答，再轮询直到完成。然后触发各种错误情况：未声明该扩展的客户端调用仅限任务（Task）的工具（`-32021`）、未知的 `taskId`（`-32602`）、一个 `failed` 的任务（JSON-RPC 错误），以及一个工具结果带有 `isError: true` 的 `completed` 任务。

```python
async def poll(session, task_id, interval=0.05):
    while True:
        state = await tasks_get(session, task_id)
        if state.status in TERMINAL or state.status == "input_required":
            return state
        await asyncio.sleep(interval)


async with Client(ops, extensions=[TasksClient()]) as c:
    created = await c.session.call_tool("deploy", {"env": "staging"}, allow_claimed=True)
    state = await poll(c.session, created.task_id)
    print("status:", state.status)
    print("inputRequests:", json.dumps(state.input_requests, indent=2))

    update = UpdateTaskRequest(params=UpdateTaskParams(
        task_id=created.task_id, input_responses={"approve-1": {"action": "accept", "content": {"approve": True}}}))
    print("\n>>> tasks/update params:", json.dumps(update.params.model_dump(by_alias=True, exclude_none=True)))
    ack = await c.session.send_request(update, types.EmptyResult)
    print("<<< ack:", wire(ack))
    final = await poll(c.session, created.task_id)
    print("final:", final.status, "->", final.result["content"][0]["text"])

    print("\n--- error paths ---")
    for rows in (2_000_000, -5):
        t = await c.session.call_tool("build_report", {"rows": rows}, allow_claimed=True)
        s = await poll(c.session, t.task_id)
        print(f"rows={rows:>9}: status={s.status:<9} error={s.error} isError={s.result and s.result.get('isError')}")
    try:
        await tasks_get(c.session, "no-such-task")
    except MCPError as err:
        print("unknown taskId ->", err.code, err.message)

async with Client(ops) as legacy:
    try:
        await legacy.call_tool("deploy", {"env": "prod"})
    except MCPError as err:
```

### 9. 透明的客户端：隐藏任务的 `call_tool()`
规范中的向后兼容说明指出，客户端可以在内部驱动轮询循环，只返回最终的 `CallToolResult`。现在我们实现 `_resolve`，并传入一个 `answer` 回调，用它代替宿主（Host）的同意界面。已经回答过的键会在多次轮询之间去重。之后，`client.call_tool(...)` 就只是简单地返回结果。最后演示取消（Cancellation）。

```python
async def resolve(self, created, cctx):
    answered, interval = set(), created.poll_interval_ms or 1000
    while True:
        await asyncio.sleep(interval / 1000)
        state = await tasks_get(cctx.session, created.task_id)
        interval = state.poll_interval_ms or interval        # pollIntervalMs MAY change over time
        if state.status == "input_required":
            fresh = {k: v for k, v in (state.input_requests or {}).items() if k not in answered}
            if fresh:
                responses = {k: self.answer(v) for k, v in fresh.items()}
                answered |= set(fresh)
                await cctx.session.send_request(UpdateTaskRequest(params=UpdateTaskParams(
                    task_id=created.task_id, input_responses=responses)), types.EmptyResult)
        elif state.status == "completed":
            return types.CallToolResult.model_validate(state.result)
        elif state.status == "failed":
            raise MCPError(state.error["code"], state.error["message"])
        elif state.status == "cancelled":
            raise RuntimeError("task was cancelled")


TasksClient._resolve = resolve


def approve_everything(request):
    print("   [consent UI] ", request["params"]["message"], "-> approved")
    return {"action": "accept", "content": {"approve": True}}


async with Client(ops, extensions=[TasksClient(answer=approve_everything)]) as c:
    result = await c.call_tool("deploy", {"env": "production"})
    print("call_tool returned a plain CallToolResult:", result.content[0].text)

    created = await c.session.call_tool("build_report", {"rows": 10}, allow_claimed=True)
    await c.session.send_request(CancelTaskRequest(params=TaskIdParams(task_id=created.task_id)), types.EmptyResult)
    print("after tasks/cancel:", (await poll(c.session, created.task_id)).status)
```
