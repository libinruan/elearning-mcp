## Summary
模块 3 讲的是工具（Tool）、资源（Resource）和提示模板（Prompt）*是什么*；本课讲的是如何真正交付一个服务器（Server）。我们沿着官方的“Build an MCP server”教程，用 `uv` 搭建项目，创建一个 `MCPServer`，把两个普通的 Python 函数——`get_alerts` 和 `get_forecast`——变成工具：它们的 JSON Schema 来自类型注解，描述来自文档字符串（docstring）。你会学到那条让最多新手服务器翻车的规则（使用 stdio 时绝不向 stdout 写任何东西），如何让同一份代码分别跑在 stdio 和可流式 HTTP 传输（Streamable HTTP）上，如何用生命周期钩子（Lifespan）只加载一次数据并通过上下文对象（`Context`）访问它，以及如何把服务器接入 Claude Desktop，并在它没有出现时去读日志排查。

## Lesson
### 选择 SDK
所有官方 SDK 都提供相同的核心能力：创建暴露工具（Tool）、资源（Resource）和提示模板（Prompt）的服务器，构建能连接任意服务器的客户端（Client），支持本地与远程传输（Transport），以及类型安全的协议合规。它们的差异在于语言习惯和**分级（Tier）**，分级反映的是功能完整度、协议支持程度和维护承诺：

| Tier | SDKs |
| --- | --- |
| Tier 1 | TypeScript, Python, C#, Go, Rust, Ruby |
| Tier 2 | Java |
| Tier 3 | Swift, PHP, Kotlin |

本课程使用 **Python SDK 2.x**（PyPI 上的 `mcp`）。教程要求 Python 3.10+ 以及 **SDK 2.0.0 或更高版本**。这个版本号很重要：2.x 实现了无状态（Stateless）的 2026-07-28 协议，并把 v1 的 `FastMCP` 改名为 **`MCPServer`**。旧代码里的 `from mcp.server.fastmcp import FastMCP` 现在会抛出 `ModuleNotFoundError`，错误信息会指向迁移指南。

### 用 uv 搭建项目
教程使用 [`uv`](https://docs.astral.sh/uv/) 管理环境和依赖：

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # then restart the terminal
uv init weather && cd weather
uv venv && source .venv/bin/activate
uv add "mcp[cli]"                                 # SDK + the `mcp` dev CLI
touch weather.py
```

`uv run weather.py` 会启动服务器。`[cli]` 这个 extra 会安装一个 `mcp` 命令（`mcp dev`、`mcp run`、`mcp install`）。`mcp dev weather.py` 会在 MCP 检查器（MCP Inspector）下启动你的服务器（见第 4.3 课）。

### MCPServer：由类型注解和文档字符串生成工具
```python
from typing import Any
import httpx2
from mcp.server import MCPServer

mcp = MCPServer("weather")          # the name clients see in serverInfo

@mcp.tool()
async def get_alerts(state: str) -> str:
    """Get weather alerts for a US state.

    Args:
        state: Two-letter US state code (e.g. CA, NY)
    """
    ...
```

文档用一句话概括了这一点：*“MCPServer 类使用 Python 类型注解和文档字符串自动生成工具定义（Tool Definition）。”* 具体对应关系如下：

| 你写的 | 客户端在 `tools/list` 中看到的 |
| --- | --- |
| 函数名 | `name`（可用 `@mcp.tool(name=...)` 覆盖） |
| 文档字符串 | `description` |
| 带类型的参数 | `inputSchema`（一个 JSON Schema 对象，`required` = 没有默认值的参数） |
| 返回值注解 | `outputSchema`；结果中还会带上 `structuredContent`（`str`/`int`/列表会被包装成 `{"result": ...}`；裸 `dict` *不会*生成模式，所以请用 Pydantic 模型、`TypedDict` 或 `dict[str, int]`） |
| 类型为 `Context` 的参数 | 什么也看不到：它是被注入的，从不对外暴露 |
| `@mcp.tool(title=..., annotations=ToolAnnotations(...))` | `title`、`annotations` |

> **陷阱（已在 mcp 2.3.0 中验证）。** Google 风格的 `Args:` 块*不会*被拆分成逐参数的描述。它会原样留在工具的 `description` 里（连缩进一起），所以模型能读到它，但 `inputSchema` 的各个属性拿不到 `description`。若要正确的逐字段文档、取值范围和格式约束，请使用 `Annotated[float, Field(description="Latitude", ge=-90, le=90)]`。这样 Pydantic 会在你的函数运行*之前*校验参数。

`httpx2` 是 SDK 自身依赖的 HTTP 客户端，所以安装 `mcp` 时它已经被一并装好了。异步工具是一等公民：教程里的 `make_nws_request` 使用带 30 秒超时的 `httpx2.AsyncClient`，遇到任何异常都返回 `None`。工具再把它转换成一条友好的字符串（“Unable to fetch alerts or no alerts found.”）。

### 天气示例
教程中的服务器封装了美国国家气象局（NWS）的 API：

- **`get_alerts(state)`** 调用 `/alerts/active/area/{state}`，把每条预警的事件、区域、严重程度、描述和处置建议格式化后，用 `---` 连接起来。
- **`get_forecast(latitude, longitude)`** 需要两跳。`/points/{lat},{lon}` 返回一条网格记录，其中 `properties.forecast` URL 给出各预报时段。它会格式化接下来的 **5** 个时段（名称、温度、风、详细预报）。
- 最后在 `if __name__ == "__main__":` 下调用 `mcp.run(transport="stdio")`。

注意其中的设计取舍：失败以**可读的字符串**返回而不是抛异常，输出被限制在五个时段以内。第 4.2 课会把这两种直觉提炼成一套规范（可操作的 `isError` 结果、截断）。

### 日志：使用 stdio 时绝不写 stdout
教程每个语言标签页的开头都是同一条警告：

> **规范规则（stdio 传输）。** 服务器**不得（MUST NOT）**向其 `stdout` 写入任何不是有效 MCP 消息的内容。它**可以（MAY）**向 `stderr` 写入 UTF-8 日志，并且客户端**不应（SHOULD NOT）**认为 stderr 有输出就意味着出错。

在 stdio 上，stdout *就是* JSON-RPC 通道：每行一条消息。一句随手写的 `print("Processing request")` 会把一行非 JSON 内容放到线路上。取决于客户端的实现，这一行要么被当作解析错误跳过，要么直接导致连接中断。请使用标准的 `logging` 模块（它写到 stderr），每个模块一个 logger（`logging.getLogger(__name__)`）。每种 SDK 都有自己的坑：

| 语言 | ❌ 在 stdio 上 | ✅ 应改用 |
| --- | --- | --- |
| Python | `print()` | `logging`（stderr） |
| TypeScript | `console.log()` | `console.error()` |
| Java | `System.out.println()` | 配置为不输出到 stdout 的 logger |
| C# | `Console.WriteLine()` | 使用 logger；`CreateEmptyApplicationBuilder` |
| Rust | `println!()` | `eprintln!()`、`tracing` |
| Go | `fmt.Println()` | `log.Println()`（stderr） |

**HTTP 服务器**没有这个限制：stdout 不是线路。调试指南还补充说，在那种情况下客户端*不会*捕获 stderr，所以请使用你自己的日志聚合方案或 OpenTelemetry。

> **SDK 细节（已在 mcp 2.3.0 中验证）。** 在 `mcp.run(transport="stdio")` 提供服务期间，Python SDK 2.x 会把协议流挪到一个私有的文件描述符上，并让 fd 1 指向 stderr。因此工具内部一个*已刷新（flushed）*的 `print()` 会落进日志。但这张安全网有漏洞。导入时（`run()` 之前）的 `print()` 会直接写到线路上。仍停留在 Python stdout 缓冲区中的文本会在关闭时被刷出，而那时 fd 1 *已经*恢复，所以它同样会进入协议流。其他 SDK 则完全没有这种保护。不要依赖它。

### 通过协议发送日志已被弃用
2025 时代的服务器还会用 `notifications/message`（在 Python 中是 `ctx.info(...)`）把日志*发给客户端*。**在 2026-07-28 中，Logging 特性已被弃用（SEP-2577）。** 新服务器**不应（SHOULD NOT）**采用它，而应把日志写到 stderr（stdio）或 OpenTelemetry。在仍保留该特性的地方，投递是**逐请求选择启用**的：如果某个请求的 `_meta` 中没有 `io.modelcontextprotocol/logLevel`，服务器**不得（MUST NOT）**为它发出 `notifications/message`。在 2.x SDK 中，`ctx.info()` 会发出 `MCPDeprecationWarning`。只有设置了 `Client(..., log_level="info")` 的客户端才会收到这条消息。

### 运行：stdio 与 Streamable HTTP
| | stdio | Streamable HTTP |
| --- | --- | --- |
| 启动方式 | `mcp.run(transport="stdio")`（默认） | `mcp.run(transport="streamable-http", host=..., port=...)` |
| 由谁启动 | 宿主把它作为子进程拉起 | 由你部署；客户端连接到 `http://host:port/mcp` |
| 默认值 | 不适用 | `127.0.0.1:8000`，路径 `/mcp` |
| 日志 | 只能写 stderr；由宿主捕获 | 写 stdout 没问题；宿主看不到你的日志 |
| 嵌入 | 不适用 | `mcp.streamable_http_app()` 返回一个可挂载的 Starlette ASGI 应用 |

同一份工具代码可以同时服务两者。借助 2.x SDK，两种传输既能应答 2026-07-28 的客户端（`server/discover`，无握手），*也*能应答以 `initialize` 开场的 2025 时代客户端。

### 生命周期钩子：加载一次，处处可用
每次调用都去打开数据库连接池、读取大文件或创建 API 客户端是一种浪费。`MCPServer(name, lifespan=fn)` 接受一个异步上下文管理器：它在启动时运行，yield 出一个状态对象，并在关闭时做清理：

```python
@asynccontextmanager
async def lifespan(server: MCPServer):
    db = await Database.connect()        # startup
    try:
        yield AppState(db=db)            # visible to every handler
    finally:
        await db.disconnect()            # shutdown

mcp = MCPServer("weather", lifespan=lifespan)

@mcp.tool()
async def query(sql: str, ctx: Context) -> str:
    db = ctx.request_context.lifespan_context.db
```

对于 stdio 和 HTTP 应用，它在每个服务器进程中只运行一次；对于进程内的 `Client(mcp)`，则是每个连接运行一次。由于 2026-07-28 **没有协议会话**，生命周期钩子（Lifespan）用于存放*进程级*资源，比如连接池、缓存和客户端。它不是存放逐用户会话状态（Conversation State）的地方；第 4.2 课会展示用显式句柄来处理这类状态。

### Context 对象
添加一个注解为 `Context`（来自 `mcp.server.mcpserver`）的参数，SDK 就会把它注入进来：

| 成员 | 用途 |
| --- | --- |
| `await ctx.report_progress(progress, total, message)` | `notifications/progress`，仅当请求携带了 `progressToken` 时才会发送（当你传入 `progress_callback` 时，Python 客户端会自动加上一个） |
| `await ctx.read_resource(uri)` | 在工具内部读取*本服务器*的某个资源 |
| `ctx.request_context.lifespan_context` | 你的生命周期钩子 yield 出的对象 |
| `ctx.request_id`、`ctx.protocol_version`、`ctx.client_capabilities`、`ctx.headers` | 请求元数据（headers 仅在 HTTP 上可用；应视为不可信输入） |
| `await ctx.elicit(...)` | 向用户征询输入（第 5.3 课，在 2026-07-28 中通过多轮往返请求实现） |
| `ctx.info/debug/warning/error/log` | 已弃用的协议日志（见上文） |

### 连接 Claude Desktop
Claude Desktop 读取 `claude_desktop_config.json`：

| 操作系统 | 路径 |
| --- | --- |
| macOS | `~/Library/Application Support/Claude/claude_desktop_config.json` |
| Linux | `~/.config/Claude/claude_desktop_config.json` |
| Windows | `%APPDATA%\Claude\claude_desktop_config.json` |

```json
{
  "mcpServers": {
    "weather": {
      "command": "uv",
      "args": ["--directory", "/ABSOLUTE/PATH/TO/PARENT/FOLDER/weather", "run", "weather.py"]
    }
  }
}
```

这告诉 Claude Desktop：有一个名为 `weather` 的服务器，用 `uv --directory … run weather.py` 启动它。容易踩坑的细节：

- 路径**必须是绝对路径**。宿主（Host）可能以一个未定义的工作目录（Working Directory）启动你的进程（在 macOS 上是 `/`）。在 Windows 上，JSON 中请使用 `\\` 或 `/`。
- 你可能需要提供 **`uv` 的完整路径**（`which uv` / `where uv`），因为 GUI 应用看不到你 shell 中的 `PATH`。
- stdio 服务器只继承有限的一组环境变量；请通过 `"env": {...}` 键传入密钥和配置。
- 修改之后，要**完全退出** Claude Desktop（Cmd+Q、托盘 → Quit，或在 Linux 上执行 `pkill -f claude-desktop`）。只关闭窗口是不够的。然后在“Add files, connectors, and more”（+）菜单 → **Connectors** 中查看是否有 `weather`。

### 底层发生了什么
当你问“What's the weather in Sacramento?”时：(1) 客户端把你的问题发给 Claude，(2) Claude 读取可用的工具并决定使用哪个，(3) 客户端通过 MCP 服务器执行所选工具，(4) 结果返回给 Claude，(5) Claude 写出自然语言回答，(6) 你看到回答。在协议层面，Claude Desktop 在启动时拉起了你的进程，对它进行发现（2026-07-28 中是 `server/discover`，更早的时代是 `initialize`），获取了 `tools/list`，而第 3 步就是写入你 stdin 的一行 `tools/call`。

### 其他 SDK 概览
教程用八种语言重复实现了这个天气服务器。它们的结构大同小异：

- **TypeScript**：`npm install @modelcontextprotocol/server zod`。在 `createServer()` 工厂函数中用 `server.registerTool(name, {description, inputSchema: z.object(...)}, handler)` 注册工具，然后调用 `serveStdio(createServer)`。`serveStdio` 会同时协商两个协议时代，并为每个实例调用一次工厂函数（包括一次会被丢弃的 `server/discover` 探测），所以它每次都必须返回一个**全新的** `McpServer`。手动接线 `server.connect(new StdioServerTransport())` 仍然能编译，但**只能服务 2025 时代的客户端**。
- **Java（Spring AI）**：使用 `@Tool`/`@ToolParam` 注解，通过 `MethodToolCallbackProvider` 暴露。
- **C#**：`builder.Services.AddMcpServer().WithStdioServerTransport()`，配合 `[McpServerToolType]`/`[McpServerTool]` 特性。
- **Rust（`rmcp`）**：使用 `#[tool_router]` 和 `#[tool]` 宏，通过 `(stdin(), stdout())` 提供服务。
- **Go**：`mcp.NewServer`、`mcp.AddTool`、`server.Run(ctx, &mcp.StdioTransport{})`。
- **Kotlin** 和 **Ruby**（`MCP::Tool` 子类、`MCP::Server::Transports::StdioTransport`）也遵循同样的模式。

### 故障排查
- **日志**：`~/Library/Logs/Claude`（macOS）、`~/.config/Claude/logs/`（Linux）、`%APPDATA%\Claude\logs`（Windows）。`mcp.log` 记录连接与失败情况。`mcp-server-SERVERNAME.log` 保存你服务器的 **stderr**，所以你的 `logging` 输出会落在这里。用 `tail -n 20 -f ~/Library/Logs/Claude/mcp*.log` 实时查看。
- **服务器没有出现**：检查 JSON 语法，使用绝对路径，并完全重启。
- **工具调用静默失败**：查看日志，确认服务器能单独运行（`uv run weather.py`），然后重启。
- **天气 API 报错**：“Failed to retrieve grid point data”意味着坐标不在美国境内、NWS 服务中断或被限流。“No active alerts”不是错误。

## Key points
- `MCPServer`（Python SDK ≥ 2.0，取代了 v1 的 `FastMCP`）根据**类型注解**（inputSchema/outputSchema）和**文档字符串**（description）生成工具定义（Tool Definition）。如需逐参数的描述和约束，请使用 `Annotated[..., Field(...)]`。
- 在 **stdio 上，stdout 就是线路**：绝不要向它 `print()`。用 `logging` 把日志写到 **stderr**。HTTP 服务器可以随意使用 stdout。
- 协议日志（Protocol Logging）（`notifications/message`、`ctx.info`）**在 2026-07-28 中已被弃用**，只有当请求通过 `io.modelcontextprotocol/logLevel` 选择启用时才会投递。
- 同一个服务器既可以用 `mcp.run(transport="stdio")` 运行，也可以用 `mcp.run(transport="streamable-http")`（默认 `127.0.0.1:8000/mcp`）运行，并且 SDK 能应答两个协议时代（Protocol Era）。
- **生命周期钩子（Lifespan）**只加载一次昂贵资源，并通过 `ctx.request_context.lifespan_context` 暴露出来。它不能替代逐用户状态。
- `Context` 为工具提供 `report_progress`、`read_resource`、请求元数据和 `elicit`。它是被注入的，从不出现在模式（Schema）中。
- Claude Desktop 配置：`mcpServers` → `command` + `args`（+ `env`），使用**绝对路径**，可能需要 `uv` 的完整路径，修改后要**完全退出**。
- 从日志入手调试：`mcp.log` 看连接情况，`mcp-server-NAME.log` 看你服务器的 stderr。

## Pitches
### 讲讲你是怎么构建一个 MCP 服务器的
我会从 uv 和官方 Python SDK（2 版或更高）开始。先创建一个 MCPServer，写几个带类型的普通函数，再用装饰器把它们注册成工具：类型注解会变成输入和输出的 JSON Schema，文档字符串和 Field 描述就是模型读到的内容。像数据库连接池这种昂贵的初始化放进生命周期钩子里。本地宿主就跑 stdio，远程的就跑 Streamable HTTP。然后用 Inspector 测一遍，再用绝对路径把它接进 Claude Desktop。

### 为什么 stdio 服务器一 print 就坏？
在 stdio 上，宿主是通过服务器的标准输入和标准输出跟它对话的，每行一条 JSON-RPC 消息。所以 stdout 不是控制台，而是协议通道，规范规定那里只能出现有效的 MCP 消息。一句调试用的 print 会塞进一行不是 JSON 的内容。有的客户端会报个错跳过去，有的直接断开连接。解决办法很无聊但很绝对：用 logging 模块把日志写到 stderr。反正宿主也会把 stderr 收集到每个服务器单独的日志文件里。

### 你怎么在多次工具调用之间共享昂贵的资源？
我用服务器的生命周期钩子，它是一个异步上下文管理器，启动时运行一次，yield 出一个状态对象，关闭时做清理。工具通过注入的 Context，用 request_context.lifespan_context 拿到它。连接池、HTTP 客户端或者加载好的索引放在这里最合适。我不会往里放逐用户的会话状态，因为 2026-07-28 没有协议会话。那种状态我会让工具返回一个显式句柄，之后再作为参数传回来。

## Interview
### Python SDK 是如何把一个函数变成 MCP 工具定义的？
`@mcp.tool()` 会检查这个函数。函数名变成 `name`，文档字符串变成 `description`。参数被编译成一个 Pydantic 模型，其 JSON Schema 就是 `inputSchema`，没有默认值的参数会列在 `required` 中。返回值注解会生成 `outputSchema`，结果会携带 `structuredContent`（基本类型被包装为 `{"result": ...}`）以及一个文本块。类型为 `Context` 的参数会被注入，并从模式（Schema）中排除。需要注意的坑：Google 风格的 `Args:` 段不会被拆分成属性描述（它会留在工具描述里），所以要用 `Annotated[T, Field(description=..., ge=..., pattern=...)]`。参数会在你的代码运行前由 Pydantic 校验，校验失败会以模型可读的 `isError: true` 结果返回。

### 用户说你的服务器在终端里能跑，但在 Claude Desktop 里一直不出现。你怎么排查？
第一，检查配置：JSON 是否合法，是否有 `mcpServers` 条目，项目路径是否为**绝对路径**，由于 GUI 应用没有你 shell 的 `PATH`，可能还需要 `uv`/`node` 的绝对路径，以及是否**完全退出**后重启（关闭窗口不会重新加载）。第二，看日志：`mcp.log` 显示进程拉起或连接是否失败，`mcp-server-weather.log` 显示服务器的 stderr，通常是一段 traceback。典型原因有：相对路径（工作目录（Working Directory）可能是 `/`）、缺少环境变量（stdio 服务器只继承有限的一组，所以要加 `env` 键），以及向 stdout `print()` 破坏了数据流。然后再用 Inspector 在 Claude 之外复现问题。

### 把服务器从 stdio 切换到 Streamable HTTP 时，有什么会变化？
工具代码不变；变的是部署和运维模型。使用 stdio 时，宿主（Host）为每个用户拉起一个进程，stdout 专门留给协议消息，stderr 进入宿主的日志。使用 HTTP 时，你运行的是一个位于 `/mcp` 的长期服务（SDK 默认 `127.0.0.1:8000`）。往 stdout 打日志没问题，但客户端永远看不到你的日志，所以你需要自己的日志聚合或 OpenTelemetry。你还要承担远程服务器（Remote Server）的种种问题：授权（Authorization）（OAuth，模块 6）、Origin 校验与 DNS 重绑定攻击（DNS Rebinding）防护、多副本扩展。由于 2026-07-28 是无状态（Stateless）的，只要你把状态放在显式句柄或共享存储中，任何副本都能应答任何请求。

### 在 2026-07-28 服务器中用 `ctx.info()` 记日志是个好办法吗？
不是。从 2026-07-28 起，协议日志（Protocol Logging）（`notifications/message`）已被**弃用**（SEP-2577）。新实现不应（SHOULD NOT）采用它，而应在 stdio 上写 stderr 或者写到 OpenTelemetry。它的形态也变了：不再有会话级的 `logging/setLevel`。客户端要在 `_meta` 中带上 `io.modelcontextprotocol/logLevel` 来**逐请求**选择启用，否则服务器不得（MUST NOT）发出日志通知。在 SDK 2.x 中，`ctx.info()` 会触发弃用警告，而使用默认客户端时什么都收不到。

### 刁钻题：你的 stdio 服务器在工具里有一句 `print()`，但它照样能工作。为什么？这样可以吗？
Python SDK 2.x 在提供服务期间会部分地保护你。它把真正的协议流挪到一个私有文件描述符上，让 fd 1 指向 stderr，所以处理函数中一个*已刷新*的 `print()` 会落进日志。但这依然是 bug，而且这种保护有漏洞。导入时或 `run()` 之前的 `print()` 会直接写到线路上。未刷新的文本会留在 Python 的 stdout 缓冲区里，并在关闭时、真正的 stdout 恢复之后才被写出，所以它同样会落到协议流上。其他 SDK（TypeScript 的 `console.log`、Go 的 `fmt.Println` 等）则完全没有保护。而且，对消息分帧要求严格的 stdio 客户端可能在遇到第一行非 JSON 内容时就断开连接。请显式地把日志写到 stderr，永远不要依赖这张安全网。

## Glossary
- MCPServer | MCPServer（高层服务器类） | Python SDK 2.x 的高层服务器类（前身为 FastMCP），从带装饰器的函数构建工具、资源和提示模板。
- uv | uv（Python 包与环境管理器） | 官方教程使用的 Python 项目与依赖管理器（`uv init`、`uv add`、`uv run`）。
- Lifespan | 生命周期钩子 | 在服务器启动和关闭时运行的异步上下文管理器，它 yield 出的对象会被所有处理函数共享。
- Context | 上下文对象 | SDK 注入到声明了它的工具中的对象，提供进度报告、资源读取、征询和请求元数据。
- stdout / stderr | 标准输出 / 标准错误 | 在 stdio 上，stdout 只承载 JSON-RPC 消息；stderr 可自由用于日志，宿主可能会捕获这些日志。
- claude_desktop_config.json | Claude Desktop 配置文件 | Claude Desktop 的配置文件；其中的 `mcpServers` 映射为每个服务器命名，并给出启动它所需的 `command`、`args` 和 `env`。
- Streamable HTTP | 可流式 HTTP 传输 | 远程传输方式：服务器是位于某个端点（如 `/mcp`）的 HTTP 服务。
- Progress notification | 进度通知 | `notifications/progress`，当请求携带进度令牌时由 `ctx.report_progress` 发送。
- Protocol logging (deprecated) | 协议日志（已弃用） | 通过 `notifications/message` 投递日志的机制，在 2026-07-28 中已弃用，需通过 `io.modelcontextprotocol/logLevel` 逐请求选择启用。

### 2. 服务器文件
这就是教程里的 `weather.py`，外加三处升级：一个只加载一次数据集的**生命周期钩子（Lifespan）**、`Annotated` 字段描述与取值范围，以及通过上下文对象（`Context`）报告进度。所有日志都写到 **stderr**。`NOISY` 开关会加入两个故意的 `print()` bug，我们会在第 6 节触发它们。

```python
%%writefile {server_path}
"""Offline weather MCP server, shaped like the official tutorial."""
import json
import logging
import os
import sys
from contextlib import asynccontextmanager
from dataclasses import dataclass
from typing import Annotated

from pydantic import Field

from mcp.server import MCPServer
from mcp.server.mcpserver import Context

logging.basicConfig(level=logging.INFO, stream=sys.stderr,           # stderr, never stdout
                    format="%(asctime)s %(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("weather")

if os.environ.get("NOISY"):
    print("Weather server starting...", flush=True)   # BUG on stdio: not a JSON-RPC message


@dataclass
class WeatherData:
    alerts: dict
    points: dict


@asynccontextmanager
async def lifespan(server: MCPServer):
    path = os.environ["WEATHER_DATA"]       # absolute path, set by the host config's "env"
    logger.info("lifespan: loading %s", path)
    with open(path) as f:
        raw = json.load(f)
    yield WeatherData(alerts=raw["alerts"], points=raw["points"])
    logger.info("lifespan: shutting down")


mcp = MCPServer("weather", lifespan=lifespan)


def format_alert(a: dict) -> str:
    return (f"Event: {a.get('event', 'Unknown')}\nArea: {a.get('areaDesc', 'Unknown')}\n"
            f"Severity: {a.get('severity', 'Unknown')}\n"
            f"Description: {a.get('description', 'No description available')}\n"
            f"Instructions: {a.get('instruction', 'No specific instructions provided')}")


@mcp.tool()
async def get_alerts(state: Annotated[str, Field(description="Two-letter US state code, e.g. CA or NY")],
                     ctx: Context) -> str:
    """Get active weather alerts for a US state."""
    if os.environ.get("NOISY"):
        print(f"looking up alerts for {state}")    # BUG: where does this end up? (section 6)
    data: WeatherData = ctx.request_context.lifespan_context
    logger.info("get_alerts state=%s", state)
    features = data.alerts.get(state.upper())
    if features is None:
        return f"Unable to fetch alerts for {state!r}. Use a two-letter US state code such as CA."
    if not features:
        return "No active alerts for this state."
    return "\n---\n".join(format_alert(a) for a in features)


@mcp.tool()
async def get_forecast(latitude: Annotated[float, Field(description="Latitude of the location", ge=-90, le=90)],
                       longitude: Annotated[float, Field(description="Longitude of the location", ge=-180, le=180)],
                       ctx: Context) -> str:
    """Get the weather forecast (next 5 periods) for a US location."""
    data: WeatherData = ctx.request_context.lifespan_context
    await ctx.report_progress(0, 2, "resolving grid point")
    grid = data.points.get(f"{latitude:.2f},{longitude:.2f}")
    if grid is None:
        return "Unable to fetch forecast data for this location (only US locations are supported)."
    await ctx.report_progress(1, 2, "fetching forecast periods")
    periods = [f"{p['name']}:\nTemperature: {p['temperature']}°{p['temperatureUnit']}\n"
               f"Wind: {p['windSpeed']} {p['windDirection']}\nForecast: {p['detailedForecast']}"
               for p in grid["periods"][:5]]                                # only the next 5 periods
    await ctx.report_progress(2, 2, "done")
    return "\n---\n".join(periods)


if __name__ == "__main__":
    if len(sys.argv) == 3 and sys.argv[1] == "http":
        mcp.run(transport="streamable-http", host="127.0.0.1", port=int(sys.argv[2]))
    else:
        mcp.run(transport="stdio")
```

### 6. 弄坏它：stdout 上一句多余的 `print()`
现在设置 `NOISY=1`，手动与服务器对话。服务器写到 stdout 的第一样东西不是 JSON。一个对每一行都执行 `json.loads(line)` 的严格客户端会立刻失败。

```python
import subprocess

META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "strict-client", "version": "0"}}

proc = subprocess.Popen([sys.executable, str(server_path)], text=True,
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                        env={**os.environ, "NOISY": "1", "WEATHER_DATA": str(data_path)})
proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": 1, "method": "tools/call",
                             "params": {"name": "get_alerts", "arguments": {"state": "NY"}, "_meta": META}}) + "\n")
proc.stdin.flush()

for n in range(1, 4):                       # read until the response with id 1 arrives
    line = proc.stdout.readline()
    try:
        msg = json.loads(line)
    except json.JSONDecodeError as exc:
        print(f"line {n}: NOT JSON -> {line.strip()!r}  ({exc.msg}) <- a strict client dies here")
        continue
    print(f"line {n}: valid JSON-RPC, id={msg.get('id')} -> {msg['result']['content'][0]['text']!r}")
    if msg.get("id") == 1:
        break

proc.stdin.close()                          # the client hangs up -> the server shuts down
proc.wait(timeout=10)
late_stdout, stderr_text = proc.stdout.read(), proc.stderr.read()
print("\nwritten to stdout AFTER the last response:", repr(late_stdout))
print("in-tool print found in stderr?", "looking up alerts for NY" in stderr_text)
```

仔细阅读这两个结果：

- **启动时**的 `print()` 在 `mcp.run()` 之前执行，所以它污染了协议通道。
- **工具内**的 `print()`（未刷新）停留在 Python 的 stdout 缓冲区里，并在关闭时被写入了*协议流*。SDK 2.x 在提供服务期间让 fd 1 指向 stderr，但退出时会恢复真正的 stdout，而缓冲区是在那之后才刷新的。给那个 print 加上 `flush=True` 再运行一次：这次它会落到 stderr 中。无论哪种情况，结果都取决于缓冲行为，这正是你在 stdio 上永远不该 print 的原因。
- 启动时的那个 bug 使用了 `flush=True`，以便它能确定性地出现。如果没有它，当 stdout 是管道时，Python 会对 stdout 进行块缓冲，这段多余的文本会在之后某个无法预测的时刻出现，甚至可能出现在一条消息的中间。那就更难调试了。

Python SDK 自带的客户端比较宽容（它会记录一条解析错误并跳过这一行）。其他宿主没有义务这样做。规则不变：在 stdio 上，日志写到 stderr。

### 7. 同一个服务器跑在 Streamable HTTP 上
无需修改代码：用 `http PORT` 参数运行文件，然后连接到 `http://127.0.0.1:PORT/mcp`。我们故意保留了 `NOISY=1`。在 HTTP 上，stdout 只是一个控制台，所以这些 print 是无害的。

```python
import socket
import time

for noisy in ("httpx", "httpx2"):
    logging.getLogger(noisy).setLevel(logging.WARNING)

with socket.socket() as s:
    s.bind(("127.0.0.1", 0))
    port = s.getsockname()[1]

http_log = open(workdir / "http-server.log", "w")
http_proc = subprocess.Popen([sys.executable, str(server_path), "http", str(port)],
                             env={**os.environ, "NOISY": "1", "WEATHER_DATA": str(data_path)},
                             stdout=http_log, stderr=subprocess.STDOUT)
for _ in range(100):                                     # wait until uvicorn accepts connections
    try:
        socket.create_connection(("127.0.0.1", port), timeout=0.2).close()
        break
    except OSError:
        time.sleep(0.1)

try:
    url = f"http://127.0.0.1:{port}/mcp"
    for attempt in range(2):                             # two independent clients, one server process
        async with Client(url) as client:
            r = await client.call_tool("get_alerts", {"state": "CA"})
            print(f"client {attempt + 1}: {client.protocol_version} ->", r.content[0].text.splitlines()[0])
finally:
    http_proc.terminate()
    http_proc.wait(timeout=10)
    http_log.close()

print("\n--- server console (stdout + stderr) ---")
print("\n".join(l for l in (workdir / "http-server.log").read_text().splitlines() if "POST" not in l))
```

### 8. 生成 Claude Desktop 配置
一个小助手函数按照教程推荐的方式（`uv --directory <abs> run weather.py`）写出 `mcpServers` 条目。它还会写出直接调用解释器的变体，并对结果进行**检查（lint）**，找出典型错误：相对路径、GUI 应用可能找不到的裸命令，以及缺失的 `env`。

```python
import shutil


def desktop_entry(server_file: Path, use_uv: bool = True) -> dict:
    env = {"WEATHER_DATA": str(data_path)}
    if use_uv:
        return {"command": shutil.which("uv") or "uv",
                "args": ["--directory", str(server_file.parent), "run", server_file.name], "env": env}
    return {"command": sys.executable, "args": [str(server_file)], "env": env}


def lint_entry(name: str, entry: dict) -> list[str]:
    problems = []
    if not os.path.isabs(entry["command"]):
        problems.append(f"{name}: command {entry['command']!r} is not absolute; GUI hosts may not see your PATH")
    for arg in entry.get("args", []):
        if ("/" in arg or "\\" in arg) and not os.path.isabs(arg):
            problems.append(f"{name}: relative path {arg!r}; the host's working directory may be '/'")
    for key, value in entry.get("env", {}).items():
        if value.endswith(".json") and not os.path.isabs(value):
            problems.append(f"{name}: env {key} is a relative path")
    return problems


config = {"mcpServers": {"weather": desktop_entry(server_path, use_uv=True),
                         "weather-python": desktop_entry(server_path, use_uv=False),
                         "broken": {"command": "uv", "args": ["--directory", "./weather", "run", "weather.py"]}}}
print(json.dumps(config, indent=2))
print("\nlint:")
for name, entry in config["mcpServers"].items():
    print(" ", name, "->", lint_entry(name, entry) or "ok")
print("\nmacOS file: ~/Library/Application Support/Claude/claude_desktop_config.json  (then fully quit Claude)")
```

### 9. 底层原理：六个步骤，配一个脚本化的“Claude”
把教程中“what's happening under the hood”的列表写成代码。一个确定性的模型替身（脚本化规划器（Scripted Planner））根据所公布的描述选择工具；宿主通过 MCP 执行它，并把结果回传。如果设置了 `ANTHROPIC_API_KEY`，第 2 步和第 5 步将由真实模型完成。

### 10. 进度之外的 Context 对象
一个小型配套服务器展示了上下文对象（`Context`）的其余功能。它在工具内部读取自己的一个资源，检查请求元数据，并使用**已弃用的**协议日志（Protocol Logging）。协议日志只会送达通过 `log_level` 选择启用的 2026-07-28 客户端。

```python
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

ctx_demo = MCPServer("ctx-demo")


@ctx_demo.resource("config://units")
def units() -> str:
    return "imperial"


@ctx_demo.tool()
async def describe_request(ctx: Context) -> dict[str, str]:
    """Report what the Context object knows about this request."""
    units_text = list(await ctx.read_resource("config://units"))[0].content
    with warnings.catch_warnings():
        warnings.simplefilter("ignore")
        await ctx.info("describe_request called")          # deprecated notifications/message
    return {"request_id": ctx.request_id, "protocol": ctx.protocol_version or "", "units": units_text}


for level in [None, "info"]:
    received = []

    async def on_log(params):
        received.append(f"[{params.level}] {params.data}")

    async with Client(ctx_demo, logging_callback=on_log, log_level=level) as client:
        r = await client.call_tool("describe_request", {})
        print(f"log_level={level!r:7} -> structured={r.structured_content} | log messages received={received}")
```
