## Summary
一个工具在*你*调用时能正常工作，到了模型调用时仍然可能失败。模型只能看到名称、描述和一个 JSON Schema；你返回的每个 token 它都要付费；而它只能修正你的错误信息解释清楚了的错误。本课把 2026-07-28 Tools 规范中的规范性内容（命名规则、`outputSchema`、`isError`、注解（Annotations）、确定性排序、非规范性的 *Stateful Tools* 指南、安全方面的 MUST 要求）、*Client Best Practices* 中的客户端视角，以及官方智能体技能（Agent Skill）中关于服务器设计的问题，整理成一份实用清单。在 Notebook 中，你会把一套糟糕的工具集和一套良好的工具集放在一起检查，观察一个脚本化的智能体（Agent）只有在错误可操作时才能恢复，对一个超大的结果进行分页，并构建一个基于句柄的工作流。

## Lesson
### 模型就是你的用户
模型对你的工具所知道的一切都来自 `tools/list`：`name`、可选的 `title`、`description`、`inputSchema`、可选的 `outputSchema` 和 `annotations`。宿主（Host）会把这些定义贴进模型的上下文，你返回的每一个结果也会进入那里。所以工具设计就是**为一个无法提问的读者做接口设计**。本课中的每条建议都会打上标签：**[spec]** 表示 2026-07-28 规范（MUST/SHOULD），**[docs]** 表示官方指南，**[practice]** 表示被广泛使用但尚未标准化的通用工程实践。

客户端（Client）一侧说明了这件事为什么重要。*Client Best Practices* [docs] 警告说，简单粗暴的宿主会预先注入所有已连接服务器的定义。当工具有几百个时，仅这些定义就可能消耗 **约 150,000 个 token**，“在模型读到用户消息之前就占据了上下文窗口的大部分”。宿主的应对办法是**渐进式发现（Progressive Discovery）**：用一个 `search_tools` 元工具（Meta-tool）按名称和描述查找工具，*然后*再加载完整的模式。这对服务器作者有两个影响。你的名称和描述必须**便于检索**（关键词、BM25 或向量嵌入），而每一个多余的工具或冗长的模式，都是每一次对话都要付出的成本。

### 命名与命名空间
**[spec]** 工具名称应当（SHOULD）为 1–128 个字符，区分大小写，只使用 `A-Z a-z 0-9 _ - .`，不含空格或逗号。名称应当（SHOULD）在一个服务器内唯一。例如：`getUser`、`DATA_EXPORT_v2`、`admin.tools.list`。唯一性只在单个服务器内成立。聚合多个服务器的客户端会遇到冲突（两个服务器都暴露 `search`），并且应当（SHOULD）消除歧义，例如加上服务器标识作为前缀。规范警告说，`serverInfo.name` **并不**唯一，不应（SHOULD NOT）依赖它来做这件事。

**[practice]** 别让宿主去猜。给工具加上服务前缀（命名空间前缀（Namespacing））（`tickets_search`、`tickets_get`、`tickets_close`），选定一种约定（`service_verb_noun`），避免使用 `do`、`run`、`query` 或 `process` 这类泛泛的动词。一致的前缀还能让你的工具在渐进式发现的目录中归为一组（“Group tools by server” [docs]）。

### 描述就是提示词
**[practice]** 描述要写给一个正在决定*是否*调用以及*如何*调用该工具的模型：

1. 用一句话说明**它做什么**，使用搜索能匹配到的领域词汇。
2. **何时使用它**，以及何时应改用同类的其他工具（“for full details call `tickets_get`”）。
3. **它返回什么以及有何限制**（“at most `limit` summaries, no bodies; use `next_cursor` for more”）。
4. **副作用与生命周期**（“closing is idempotent”；“triage sessions expire after 15 minutes”，规范本身也建议为句柄这样写）。

面向人类的标签放在 `title` 中 [spec]；显示优先级依次为 `title`、`annotations.title`、`name`。描述要精炼。每一条描述都会在包含该工具的每一轮对话中被重新发送。

### 更少、更高层的工具
**[practice，参考 docs]** 把 REST API 按“一个端点一个工具”包装，会产出几十个很薄的工具。模型随后不得不把它们串起来调用，每个中间结果都要流经它的上下文。官方的 `build-mcp-server` 技能（Skill）[docs] 在选择工具设计模式之前，会先问清楚**操作面的大小**（“a handful of operations versus wrapping a large API”）。

| 细粒度工具 | 工作流级工具 |
| --- | --- |
| `get_user`, `list_orders`, `get_order`, `get_invoice` | `customer_order_summary(customer_id, since)` |
| 灵活、可组合、易于实现 | 调用更少、token 更少、走错的弯路更少 |
| 适合代码模式（带 `outputSchema` 的类型化 API） | 适合聊天模型直接调用工具 |

一个合理的默认做法是：围绕**用户意图**设计一小组工具，每个工具在服务器端完成多步工作，只返回下一步决策所需的内容。在确实需要组合的地方保留细粒度工具。

### 有约束力的输入模式
`inputSchema` **必须（MUST）**是一个有效的 JSON Schema 对象（默认 2020-12）[spec]。对于没有参数的工具，规范推荐使用 `{"type": "object", "additionalProperties": false}`。让无效调用难以写出来 [practice]：

- 对封闭集合使用 **`enum`**（`status: "open" | "pending" | "closed"`）。在 Python 中，`Literal[...]` 会变成 `enum`。
- 为常见情况设置**默认值**（`status="open"`、`limit=10`），让最简单的调用就是正确的。
- 通过 `Field(ge=..., le=..., pattern=...)` 设置**取值范围和格式约束**（`limit` 为 1–50，`ticket_id` 匹配 `^T-\d{4}$`）。
- **为每个属性写描述**，包括单位和格式（“ISO date YYYY-MM-DD”）。
- 使用**扁平、明确的参数**，而不是让模型去猜的自由格式 `options: dict`。

SDK 会在你的函数运行*之前*按模式校验参数，所以很多错误根本到不了你的代码。业务规则仍需你自己校验。规范中的 `x-mcp-header` 关键字（把一个基本类型参数镜像到 `Mcp-Param-*` HTTP 头中，以便路由）适用于像区域这样的信息。它不应（SHOULD NOT）用于密钥或个人身份信息（PII），因为请求头对中间节点是可见的 [spec]。

### 输出：structuredContent 与 outputSchema
一个结果包含非结构化的 `content`（文本、图像、音频、`resource_link`、嵌入式资源（Embedded Resource）），以及可选的 `structuredContent`，它可以是任意 JSON 值 [spec]。如果你声明了 `outputSchema`，服务器**必须（MUST）**返回符合它的结构化结果，客户端**应当（SHOULD）**校验这些结果。为了向后兼容，返回结构化内容的工具也应当（SHOULD）在一个文本块中返回序列化后的 JSON。当你返回 Pydantic 模型或 `TypedDict` 时，Python SDK 会自动完成这两件事。

为什么要费这个事？代码模式的宿主 [docs] 会根据 `outputSchema` 生成类型化的函数。没有它，宿主只能退回到 `any`，或者再调用一次模型来提取字段，文档说得很直白：“the real fix is for server authors to provide `outputSchema`”。结构化输出还让你能返回模型可以据此推理的**紧凑**数据（id、计数、标志位），而不是大段文字。注意，`structuredContent` 与 LLM 的“结构化输出（Structured Output）”无关。

### 模型能据此行动的错误
规范区分了两种机制 [spec]：

| | 协议错误 | 工具执行错误 |
| --- | --- | --- |
| 形态 | JSON-RPC `error`（例如 `-32602`） | 带 `isError: true` 的 `result` |
| 适用于 | 未知工具、格式错误的请求、服务器错误 | API 失败、无效输入值、违反业务规则 |
| 模型能看到吗？ | 客户端可以（MAY）转交；不太可能恢复 | 客户端应当（SHOULD）转交，以便模型自我纠正 |

规范中的示例消息就是可以照抄的模板：*“Invalid departure date: must be in the future. Current date is 08/08/2025.”* 它说明了哪里错了，陈述了规则，并给出了修正所需的事实。[practice] 一条好的错误信息会点出参数名，列出有效值或格式并附一个示例，并建议下一步（“call `tickets_search` to find the id”）。永远不要返回堆栈跟踪或光秃秃的 `"error"`。

> **SDK 细节（mcp 2.3.0）。** 对于可预见的失败，抛出 `mcp.server.mcpserver.exceptions.ToolError("…")`：消息会以 `isError: true` 的形式到达模型。**任何其他异常**都会被当作崩溃处理。模型只能看到 `Error executing tool <name>`，traceback 则进入服务器日志，这样虽然避免了密钥泄露到结果中，但也把提示信息藏了起来。参数校验错误会被完整报告。SDK 还会把*未知工具*作为 `isError` 结果返回（`Unknown tool: x`），而规范把它列为协议错误。

### 注解是提示，不是保证
`ToolAnnotations` [spec] 向客户端描述工具行为，客户端可以将其用于用户体验（确认提示、自动批准只读工具）：

| 提示 | 含义 | 默认值 |
| --- | --- | --- |
| `readOnlyHint` | 不修改其所处环境 | `false` |
| `destructiveHint` | 可能执行破坏性更新（仅在非只读时有意义） | `true` |
| `idempotentHint` | 用相同参数重复调用不会产生额外影响（仅在非只读时） | `false` |
| `openWorldHint` | 与开放世界中的外部实体交互（网页搜索），而非封闭领域（记忆存储） | `true` |

默认值是**悲观的**，所以一个没有注解的工具看起来既有破坏性又面向开放世界。请显式且如实地设置它们。除非服务器是可信的，否则客户端**必须（MUST）**把注解视为不可信，并且永远不应根据来自不可信服务器的注解做工具使用决策 [spec]。

### 幂等性与重试
**[practice]** 网络会超时，智能体会重试。设计写操作时要让重试是安全的：

- 让状态转换具有幂等性（Idempotency）。关闭一个已经关闭的工单应当成功并返回“already closed”；这不是错误。
- 对于创建操作，接受一个**幂等键（idempotency key）**（客户端的请求 id），重复请求时返回原来的对象。
- 用 `idempotentHint: true` 声明这一点，并在描述中写明。

### 大结果：分页、截断、摘要
规范层面的分页（`cursor`/`nextCursor`）适用于 `tools/list` 这样的*列举方法*。在工具内部，分页是**你自己的接口** [practice]：一个带合理默认值和上限的 `limit`、一个不透明游标（Opaque Cursor）`cursor`，以及 `total` 或 `has_more`。默认返回摘要，按需返回完整对象；截断时，**要说明已截断，并说明如何获取其余部分**。*Client Best Practices* [docs] 建议宿主在输出到达模型之前进行校验和截断，并指出让大型中间结果流经模型会使上下文成本“成倍累积”。一个因为“客户端会裁剪”而返回 50 KB JSON 的服务器，是在浪费所有人的预算。要去测量：按大约 4 个字符折合 1 个 token 来估算，做预算已经足够。

### 稳定、确定的工具列表
**[spec]** 服务器**应当（SHOULD）**以确定的顺序返回工具，这样客户端可以缓存列表，LLM 的**提示缓存（Prompt Caching）**也能命中。`tools/list` 的集合**不得（MUST NOT）**因连接不同而变化，也不得作为其他请求的副作用而变化，但**可以（MAY）**根据请求所带的授权而变化。当它确实发生变化时，向 `subscriptions/listen` 流发出 `notifications/tools/list_changed`。**[docs]** 大多数提供商会缓存包括 `tools` 数组在内的提示前缀。在对话中途添加、删除或重新排序工具会使缓存失效，而缓存未命中的代价可能比你省下的 token 还多。所以不要用 `set()` 或迭代顺序随机化的哈希表来构建列表，也不要每次请求都重新打乱工具顺序。

### 状态：显式句柄，而非会话
2026-07-28 移除了协议会话（2025 时代的 Streamable HTTP 有 `Mcp-Session-Id`），所以服务器不能依赖逐连接的状态来把一次调用与下一次调用关联起来。规范中非规范性的 **Stateful Tools** 指南是：由一个创建型工具返回一个**显式句柄**（状态句柄（State Handle））（`create_basket` → `{"basket_id": "bsk_a1b2c3"}`），在之后的调用中接收它，并让模型把它一路带下去。设计要点 [spec guidance]：

- **授权**：在需要认证的服务器上，句柄只是一个名字，而不是一种权限凭证，所以每次调用都要检查调用者是否有权使用它。在无需认证的服务器上，它就是一个持有者令牌（bearer token）：要使用高熵值（UUIDv4）并设定有限的生命周期。
- **不透明性**：不要编码会诱使对方去猜测的内部结构。
- **生命周期**：在创建型工具的描述中写明保留策略。
- **过期错误**：未知或已过期的句柄应返回一个说明这一点的工具执行错误，以便模型创建一个新的。

### 安全是设计的一部分
**[spec]** 服务器**必须（MUST）**校验所有工具输入、实施恰当的访问控制、对工具调用限流，并清洗工具输出。客户端应当（SHOULD）对敏感操作进行确认、在调用前展示输入、校验结果、为调用设置超时并记录使用情况。**[practice]** 遵循**最小权限**原则：暴露 `tickets_close`，而不是 `run_sql`。把凭据的权限范围限制在工具所需之内，不要让密钥出现在参数和结果中，并记住你的输出对模型（可能还有其他服务器）而言是不可信输入（提示注入（Prompt Injection），模块 6）。

### 借助智能体技能
官方文档 [docs] 推荐使用 `mcp-server-dev` 插件（`build-mcp-server`、`build-mcp-app`、`build-mcpb`）。它的入口技能（Skill）会在写代码之前先追问你的使用场景：要连接什么、谁会使用、操作面有多大、交互需求（纯文本、征询（Elicitation）还是 UI）以及上游认证方式。然后它会推荐一条部署路径。云 API 默认采用远程 Streamable HTTP；MCP 应用（MCP App）用于添加小组件；MCPB 把本地服务器连同其运行时打包；本地 stdio 用于原型开发。之后，文档建议“iterate on tool descriptions and error handling”，而这正是本课的主题。

## Key points
- 模型只能看到名称、标题、描述和模式（Schema）：要把它们当作**提示词**来写，说明做什么、何时用、返回什么以及有何限制。
- **[spec]** 名称：1–128 个 `A-Za-z0-9_-.` 字符，区分大小写，在单个服务器内唯一。要给它们加上**命名空间前缀（Namespacing）**（`tickets_search`），因为聚合多个服务器的客户端会遇到冲突。
- 优先选择**更少的、意图级的工具**。用 **enum、默认值、取值范围、格式约束和逐属性描述**来约束输入；无参数的工具使用 `additionalProperties: false`。
- 声明 **`outputSchema`** 并返回 `structuredContent`（外加序列化文本）。服务器必须（MUST）符合它，代码模式的宿主会把它转换成类型。
- 可预见的失败应返回**带可操作文本的 `isError: true` 结果**（错在哪、规则、示例、下一步）。在 Python SDK 中要抛出 `ToolError`，因为其他异常会被屏蔽。
- **工具注解（Tool Annotations）**（`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`）的默认值是悲观的，并且是不可信的提示。请显式且如实地设置它们。
- 保持结果精简：**limit + cursor + 摘要**。截断时要说明已截断以及如何获取更多。
- **确定性的工具顺序**能让客户端缓存和 LLM 提示缓存（Prompt Caching）保持命中（规范中的 SHOULD）。
- 2026-07-28 中没有会话：用**显式、不透明、会过期的句柄**（状态句柄（State Handle））承载状态，写明其生命周期，并让过期错误告诉模型去重新创建。

## Pitches
### 什么样的工具让 LLM 用起来顺手？
我设计工具时，会把模型当成一个只能看文档的新同事。名称带命名空间，而且能说明意图，比如 tickets_search。描述写清楚它做什么、什么时候该用它而不是同类的其他工具、以及它返回什么。输入用 enum、默认值和带描述的字段，让错误的调用很难写出来。输出要小，并且是结构化的，配一个输出模式。出了问题时，错误信息会准确说明怎么改这次调用，这样模型就能自己恢复。

### 为什么工具错误应该作为结果返回，而不是抛异常？
MCP 有两条错误通道。协议错误用于请求本身有问题的情况，比如未知方法，模型很少能从中恢复。工具执行错误则作为一个普通结果返回，带 isError true，规范要求客户端把它展示给模型，让模型自我纠正。所以遇到日期格式不对或者工单 id 不存在，我会返回类似“created_after must be YYYY-MM-DD, for example 2026-03-01”这样的文本。在 Python SDK 里，这意味着要抛 ToolError，因为其他异常会被屏蔽掉。

### 没有会话，你怎么保存状态？
2026-07-28 协议移除了会话，所以我没法把状态藏在连接里。取而代之的是，由一个创建型工具返回一个显式句柄，一个不透明的高熵 id，比如 trg_ 后面跟一个 UUID。之后的每次调用都把这个句柄作为参数传进来，服务器去存储里查对应的状态，这在多副本之间也能工作。每次调用我都会校验调用者是否有权使用这个句柄，把它的生命周期写进描述里，句柄过期时，错误信息会告诉模型重新开一个。

## Interview
### 模型总是调用你服务器上错误的工具。你首先看什么？
看工具定义（Tool Definition），因为模型能看到的只有这些。名称是否有区分度、有没有加命名空间，还是存在 `search`/`query`/`do` 这类会和其他服务器冲突的名字？每条描述有没有说明*何时*该用它而不是同类工具，以及它返回什么？有没有功能重叠、应该合并成一个意图级工具的工具？然后检查 token 预算：如果宿主在做渐进式发现（Progressive Discovery），描述里的关键词是否足够丰富，能让工具被找到？最后，看对话记录。如果模型选对了工具但传错了参数，修复点在模式里（enum、默认值、属性描述）以及可操作的错误信息里。

### 什么时候返回 `isError: true`，什么时候返回 JSON-RPC 错误？
JSON-RPC 错误是**协议错误（Protocol Error）**：未知工具、不满足 `CallToolRequest` 模式的请求、服务器内部故障。规范指出模型不太可能从这些错误中恢复，客户端也只是可以（MAY）把它们展示出来。**工具执行错误（Tool Execution Error）**使用带 `isError: true` 的普通结果，用于 API 失败、无效参数值和违反业务规则的情况。客户端应当（SHOULD）把它们交给模型以便自我纠正，所以文本必须是可操作的。需要注意的坑：在 Python SDK 中，只有 `ToolError`（以及参数校验失败）会把消息透传出去。普通的 `ValueError` 会变成不透明的 `Error executing tool X`，而且 SDK 把未知工具报告为 `isError` 结果，这与规范的分类不同。

### 什么是工具注解？客户端能依赖它们吗？
`ToolAnnotations` 包含 `title`、`readOnlyHint`（默认 false）、`destructiveHint`（默认 true，仅在非只读时有意义）、`idempotentHint`（默认 false，条件同上）和 `openWorldHint`（默认 true）。宿主用它们来改善用户体验，例如自动批准只读工具，或在执行破坏性工具前请求确认。但它们只是**提示**。规范规定，除非服务器可信，否则客户端必须（MUST）把它们视为不可信，并且永远不应根据来自不可信服务器的注解做工具使用决策。恶意服务器完全可以把 `delete_everything` 标成只读。作为服务器作者，要显式地设置它们，因为默认值会让每个工具看起来都具有破坏性且面向开放世界。

### 一个工具的自然结果有 10 MB，你怎么处理？
绝不整个返回。返回一页数据：一个默认值适中、有硬性上限的 `limit`，一个不透明游标（Opaque Cursor）`cursor`，一个 `total` 或 `has_more`，以及紧凑的摘要而不是完整记录。为详细信息提供单独的 `get` 工具或 `include_*` 标志。如果必须截断文本，就附上一个明确的标记，说明截掉了多少，以及用哪个调用可以取回其余部分。可以考虑返回一个指向完整内容的 `resource_link`，而不是内联它。声明 `outputSchema`，让代码模式的宿主可以在沙箱中过滤。这一点很重要，因为你返回的每个 token 都是模型在之后每一轮都要付费的上下文，而且宿主本来就被要求进行截断。

### 规范为什么关心 `tools/list` 中工具的*顺序*？
确定性的排序（一条 SHOULD）让客户端可以缓存列表，也让 LLM 的提示缓存（Prompt Caching）能够生效。提供商会缓存包括 `tools` 数组在内的提示前缀，所以如果你的服务器在下一次请求时以不同的顺序返回相同的工具（比如在哈希随机化下由 Python `set` 构建），宿主的提示前缀就会改变，缓存就会未命中。*Client Best Practices* 还补充说，在对话中途改变工具数组的代价可能超过省下的 token。相关规则：列表不得（MUST NOT）因连接不同或作为其他调用的副作用而变化，可以（MAY）因授权不同而变化，真正的变化要通过 `notifications/tools/list_changed` 通知。

### 刁钻题：“我们需要会话，所以按连接来保存状态。”在 2026-07-28 中这有什么问题？
2026-07-28 没有协议会话。请求是自包含的，而且在 Streamable HTTP 上，连续的调用可能落到不同的服务器实例上，所以按连接保存的状态会悄无声息地失效。工具规范还禁止 `tools/list` 因连接不同而变化。被认可的模式是由创建型工具返回一个**显式句柄**（状态句柄（State Handle）），作为参数传回，并保存在共享存储中。然后处理好规范特别指出的细节：每次调用都做授权检查、使用不透明的 id、写明生命周期，以及提供可操作的过期错误。

## Glossary
- Tool definition | 工具定义 | 服务器在 `tools/list` 中公布的 `name`、`title`、`description`、`inputSchema`、`outputSchema` 和 `annotations`。
- Namespacing | 命名空间前缀 | 在工具名称前加上服务标识（例如 `tickets_search`），以避免宿主聚合多个服务器时发生冲突。
- Output schema | 输出模式（outputSchema） | 描述工具 `structuredContent` 的 JSON Schema；服务器必须（MUST）符合它，客户端应当（SHOULD）校验。
- Tool execution error | 工具执行错误 | 一个带 `isError: true` 的结果，其文本能让模型修正自己的调用；与 JSON-RPC 协议错误不同。
- Tool annotations | 工具注解 | 不可信的行为提示：`readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint`（外加 `title`）。
- Idempotency | 幂等性 | 用相同参数重复调用不会产生额外影响的性质，它让重试变得安全。
- Opaque cursor | 不透明游标 | 服务器签发的、表示“下一页”的令牌，客户端不做解析，原样传回。
- State handle | 状态句柄 | 由创建型工具返回、在之后的调用中传回的显式不透明 id，用来取代会话状态。
- Progressive discovery | 渐进式发现 | 一种宿主模式：先检索工具名称和描述，只在需要时才加载完整定义。
- Prompt caching | 提示缓存 | 提供商端对未改变的提示前缀（包括 tools 数组）的复用，确定性的工具顺序可以保住它。

import base64
import hashlib
from typing import Annotated, Literal

from pydantic import BaseModel, Field

from mcp.server.mcpserver.exceptions import ToolError
from mcp_types import ToolAnnotations

Status = Literal["open", "pending", "closed"]
Priority = Literal["low", "normal", "high", "urgent"]


class TicketSummary(BaseModel):
    id: str
    title: str
    status: Status
    priority: Priority
    customer: str
    created: str


class SearchPage(BaseModel):
    items: list[TicketSummary]
    total: int = Field(description="Number of tickets matching the filters")
    next_cursor: str | None = Field(description="Pass back as `cursor` for the next page; null when done")


class TicketDetail(TicketSummary):
    body: str | None = Field(description="Ticket text, truncated to 400 characters unless include_body=True")
    body_truncated: bool


class CloseResult(BaseModel):
    id: str
    status: Status
    changed: bool = Field(description="False if the ticket was already closed (safe to retry)")


def parse_iso_date(value: str, field: str) -> date:
    try:
        return date.fromisoformat(value)
    except ValueError:
        raise ToolError(f"Invalid {field} {value!r}: use an ISO date YYYY-MM-DD, e.g. 2026-03-01.") from None


def make_cursor(offset: int, filters: str) -> str:
    return base64.urlsafe_b64encode(json.dumps({"o": offset, "f": filters}).encode()).decode()


def read_cursor(cursor: str, filters: str) -> int:
    try:
        data = json.loads(base64.urlsafe_b64decode(cursor.encode()))
    except Exception:
        raise ToolError("Invalid cursor: pass back next_cursor exactly as returned, or omit it to start over.") from None
    if data["f"] != filters:
        raise ToolError("This cursor belongs to a search with different filters. Repeat the search without a cursor.")
    return data["o"]


good = MCPServer("helpdesk")
READ_ONLY = ToolAnnotations(readOnlyHint=True, openWorldHint=False)


@good.tool(title="Search tickets", annotations=READ_ONLY)
def tickets_search(
    status: Annotated[Status, Field(description="Ticket status to match")] = "open",
    priority: Annotated[Priority | None, Field(description="Only this priority; omit for any")] = None,
    customer: Annotated[str | None, Field(description="Exact customer name, e.g. Acme")] = None,
    created_after: Annotated[str | None, Field(description="ISO date YYYY-MM-DD; only tickets created on/after it")] = None,
    limit: Annotated[int, Field(ge=1, le=50, description="Page size (1-50)")] = 10,
    cursor: Annotated[str | None, Field(description="next_cursor from a previous page of the same search")] = None,
) -> SearchPage:
    """Search helpdesk tickets by status, priority, customer and creation date.

    Returns at most `limit` short summaries (no ticket text) plus `total` and `next_cursor`.
    Use tickets_get for the full text of one ticket, and tickets_close to close it.
    """
    since = parse_iso_date(created_after, "created_after") if created_after else None
    filters = json.dumps([status, priority, customer, created_after])
    offset = read_cursor(cursor, filters) if cursor else 0
    rows = [t for t in TICKETS.values() if t["status"] == status
            and (priority is None or t["priority"] == priority)
            and (customer is None or t["customer"] == customer)
            and (since is None or date.fromisoformat(t["created"]) >= since)]
    page = rows[offset:offset + limit]
    more = offset + limit < len(rows)
    return SearchPage(items=[TicketSummary(**{k: t[k] for k in TicketSummary.model_fields}) for t in page],
                      total=len(rows), next_cursor=make_cursor(offset + limit, filters) if more else None)


@good.tool(title="Get ticket", annotations=READ_ONLY)
def tickets_get(
    ticket_id: Annotated[str, Field(pattern=r"^T-\d{4}$", description="Ticket id like T-0042")],
    include_body: Annotated[bool, Field(description="Return the full text instead of the first 400 chars")] = False,
) -> TicketDetail:
    """Get one ticket with its text. Find ids with tickets_search."""
    t = TICKETS.get(ticket_id)
    if t is None:
        raise ToolError(f"Ticket {ticket_id} does not exist. Use tickets_search to find valid ids.")
    body = t["body"] if include_body else t["body"][:400]
    return TicketDetail(**{k: t[k] for k in TicketSummary.model_fields}, body=body,
                        body_truncated=len(body) < len(t["body"]))


@good.tool(title="Close ticket",
           annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=False, idempotentHint=True,
                                       openWorldHint=False))
def tickets_close(
    ticket_id: Annotated[str, Field(pattern=r"^T-\d{4}$", description="Ticket id like T-0042")],
    resolution: Annotated[Literal["fixed", "wont_fix", "duplicate"], Field(description="Why it is closed")],
) -> CloseResult:
    """Close a ticket with a resolution. Idempotent: closing a closed ticket succeeds with changed=false."""
    t = TICKETS.get(ticket_id)
    if t is None:
        raise ToolError(f"Ticket {ticket_id} does not exist. Use tickets_search to find valid ids.")
    changed = t["status"] != "closed"
    t["status"], t["resolution"] = "closed", resolution
    return CloseResult(id=ticket_id, status="closed", changed=changed)


print("defined", good.name, "with tools: tickets_search, tickets_get, tickets_close")

### 2. 一个工具定义检查器
一个启发式的检查器（linter）让这些指导原则变得可度量。它只读取客户端能看到的内容，即 `tools/list` 的结果。每条规则都标注了来源：规范规则（`[spec]`）和通用实践（`[practice]`）。

```python
import re

from mcp import Client

NAME_RE = re.compile(r"^[A-Za-z0-9_.\-]{1,128}$")
CLOSED_SET_HINTS = ("status", "priority", "action", "mode", "type", "kind", "resolution", "level")


def lint_tool(tool, prefixes: set[str]) -> list[tuple[int, str]]:
    """Return (penalty, message) pairs for one tool definition."""
    findings = []
    if not NAME_RE.match(tool.name):
        findings.append((15, "[spec] name uses characters outside A-Za-z0-9_-. or is too long"))
    if len(prefixes) > 1 or "_" not in tool.name:
        findings.append((5, "[practice] no shared service prefix (namespace your tools)"))
    if tool.name.split("_")[-1] in {"do", "run", "query", "process", "data", "data2"} or tool.name in {"do", "query"}:
        findings.append((10, "[practice] generic name says nothing about intent"))
    desc = (tool.description or "").strip()
    if len(desc) < 40:
        findings.append((15, f"[practice] description too short ({len(desc)} chars) to tell the model when to use it"))
    props = tool.input_schema.get("properties", {})
    for pname, schema in props.items():
        if "description" not in schema:
            findings.append((4, f"[practice] parameter '{pname}' has no description"))
        typed = any(k in schema for k in ("type", "enum", "anyOf", "$ref", "const"))
        if not typed or (schema.get("type") == "object" and "properties" not in schema) or any(
                s.get("type") == "object" and "properties" not in s for s in schema.get("anyOf", [])):
            findings.append((8, f"[practice] parameter '{pname}' is an untyped/free-form object"))
        is_string = schema.get("type") == "string" or any(s.get("type") == "string" for s in schema.get("anyOf", []))
        has_enum = "enum" in schema or any("enum" in s for s in schema.get("anyOf", []))
        if is_string and not has_enum and any(h in pname.lower() for h in CLOSED_SET_HINTS):
            findings.append((6, f"[practice] '{pname}' looks like a closed set but has no enum"))
    if not tool.output_schema:
        findings.append((10, "[spec/docs] no outputSchema (code-mode hosts can't type the result)"))
    if not tool.annotations or tool.annotations.read_only_hint is None:
        findings.append((8, "[spec] annotations missing: defaults say destructive + open-world"))
    return findings


async def lint_server(server) -> int:
    async with Client(server) as client:
        tools = (await client.list_tools()).tools
        wire = json.dumps([t.model_dump(by_alias=True, exclude_none=True, mode="json") for t in tools])
    prefixes = {t.name.split("_")[0] for t in tools}
    total = 0
    print(f"== {server.name}: {len(tools)} tools, ~{len(wire) // 4} tokens of definitions")
    for t in tools:
        findings = lint_tool(t, prefixes)
        score = max(0, 100 - sum(p for p, _ in findings))
        total += score
        print(f"  {t.name:16} score {score:3}")
        for _, msg in findings:
            print(f"      - {msg}")
    return total // len(tools)


print("average bad :", await lint_server(bad))
print()
print("average good:", await lint_server(good))
```

良好的工具集在定义上花费的 token *更多*。这是正确的取舍：几百个 token 的精确模式（Schema）能省下整个白白浪费的往返。你必须避免的，是把 token 花在*结果*上（第 4 节）。

### 3. 让智能体能够恢复的错误
真实的模型会阅读错误文本并再次尝试。这个脚本化的智能体（Agent）代替了模型：它只能修正消息中解释清楚了的问题。它会三种修复：被告知格式时重新格式化日期，列出有效值时选择最接近的有效值，否则就放弃。

```python
import difflib


def repair(args: dict, error: str) -> dict | None:
    """Return corrected arguments, or None if the error gives nothing to act on."""
    fixed = json.loads(json.dumps(args))
    flat = fixed.get("opts", fixed)
    if "YYYY-MM-DD" in error:
        for key, value in flat.items():
            if isinstance(value, str) and re.fullmatch(r"\d\d/\d\d/\d{4}", value):
                m, d, y = value.split("/")
                flat[key] = f"{y}-{m}-{d}"
                return fixed
    choices = re.findall(r"'([a-z_]+)'", error.split("Input should be", 1)[-1]) if "Input should be" in error else []
    if choices:
        for key, value in flat.items():
            if isinstance(value, str) and value not in choices:
                close = difflib.get_close_matches(value.lower(), choices, n=1)
                if close:
                    flat[key] = close[0]
                    return fixed
    return None


async def agent(server, tool: str, args: dict, max_tries: int = 4):
    async with Client(server) as client:
        for attempt in range(1, max_tries + 1):
            r = await client.call_tool(tool, args)
            if not r.is_error:
                summary = r.structured_content or {}
                total = summary.get("total", f"{len(json.loads(r.content[0].text))} rows")
                print(f"  try {attempt}: OK   {json.dumps(args)} -> total={total}")
                return
            message = r.content[0].text.replace("\n", " ")[:150]
            print(f"  try {attempt}: ERR  {json.dumps(args)}\n           model reads: {message!r}")
            args = repair(args, r.content[0].text)
            if args is None:
                print("           nothing actionable in that message -> agent gives up")
                return


print("bad server (ValueError -> masked by the SDK):")
await agent(bad, "query", {"q": "", "opts": {"status": "Open", "since": "03/01/2026"}})
print("\ngood server (enum + ToolError with format and example):")
await agent(good, "tickets_search", {"status": "Open", "created_after": "03/01/2026"})
```

在糟糕的服务器上发生了两件事。模型从未得知*哪里*错了，因为 SDK 隐藏了普通异常。而且即使是原始消息（“bad status Open”）也没有列出有效值。在良好的服务器上，enum 在函数运行前就被校验，日期错误中带有格式和示例。

### 4. 大结果：token 预算、分页、截断
糟糕的 `query` 会返回每一个匹配的工单及其正文。良好的搜索则返回一页摘要，外加 `total` 和一个不透明游标（Opaque Cursor）。按大约 4 个字符折合 1 个 token 的粗略估算比较它们的大小，然后用游标遍历所有页面。

### 5. 幂等的写操作经得起重试

### 6. 确定性的顺序让缓存保持命中
SDK 按注册顺序列出工具。只有*你的*注册顺序是确定的，它才是确定的。这里有一个服务器通过遍历一个 `set` 来注册工具，这是一个经典错误。Python 在每个进程中对字符串哈希进行随机化，所以两个“副本”（两个 `PYTHONHASHSEED` 不同的进程）会公布不同的顺序。不同的 `tools` 数组意味着不同的提示前缀，提供商的提示缓存（Prompt Caching）就会未命中。

```python
import subprocess
import sys
import textwrap

SNIPPET = textwrap.dedent('''
    import anyio, hashlib, json, sys
    from mcp import Client
    from mcp.server import MCPServer
    names = {"tickets_search", "tickets_get", "tickets_close", "tickets_assign", "tickets_comment"}
    srv = MCPServer("helpdesk")
    for name in (sorted(names) if sys.argv[1] == "sorted" else names):
        srv.add_tool(lambda: "ok", name=name, description=f"{name} tool")
    async def main():
        async with Client(srv) as c:
            tools = [t.model_dump(by_alias=True, exclude_none=True, mode="json") for t in (await c.list_tools()).tools]
        print(hashlib.sha256(json.dumps(tools).encode()).hexdigest()[:12], [t["name"] for t in tools])
    anyio.run(main)
''')

for mode in ("set", "sorted"):
    print(f"registration from a {mode}:")
    for seed in ("1", "2"):
        out = subprocess.run([sys.executable, "-c", SNIPPET, mode], capture_output=True, text=True,
                             env={"PYTHONHASHSEED": seed, "PATH": ""}).stdout.strip()
        print(f"  replica with PYTHONHASHSEED={seed}: {out}")
```

### 7. 没有会话的状态：显式句柄
一个分诊工作流跨越多次调用。`triage_start` 不把队列藏在连接里，而是返回一个不透明的高熵句柄（状态句柄（State Handle）），其生命周期**写在它的描述中**。之后的每次调用都把它传回来。我们使用两个*独立的*客户端连接，以表明没有任何东西依赖于连接。然后我们让句柄过期，观察错误信息如何告诉智能体进行恢复。

```python
import time
import uuid

TRIAGE: dict[str, dict] = {}          # in production: a shared store (Redis, DB) so any replica can serve
TTL_SECONDS = 15 * 60
clock = {"skew": 0.0}                 # lets the notebook fast-forward time


def now() -> float:
    return time.time() + clock["skew"]


@good.tool(title="Start triage", annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=False,
                                                             idempotentHint=False, openWorldHint=False))
def triage_start(priority: Annotated[Priority, Field(description="Queue to triage")] = "urgent") -> dict[str, str | int]:
    """Start a triage session over open tickets of one priority.

    Returns a triage_id to pass to triage_next. Sessions expire after 15 minutes of inactivity;
    if a triage_id is rejected as expired, call triage_start again.
    """
    queue = [t["id"] for t in TICKETS.values() if t["status"] == "open" and t["priority"] == priority]
    triage_id = f"trg_{uuid.uuid4().hex}"
    TRIAGE[triage_id] = {"queue": queue, "pos": 0, "touched": now()}
    return {"triage_id": triage_id, "queued": len(queue)}


@good.tool(title="Next ticket in triage", annotations=READ_ONLY)
def triage_next(triage_id: Annotated[str, Field(description="Handle returned by triage_start")]) -> dict[str, str | int]:
    """Return the next ticket id in a triage session and how many remain."""
    state = TRIAGE.get(triage_id)
    if state is None or now() - state["touched"] > TTL_SECONDS:
        TRIAGE.pop(triage_id, None)
        raise ToolError(f"Triage session {triage_id[:12]}... is unknown or expired (sessions last 15 minutes). "
                        "Call triage_start to begin a new one.")
    state["touched"] = now()
    if state["pos"] >= len(state["queue"]):
        return {"ticket_id": "", "remaining": 0}
    tid = state["queue"][state["pos"]]
    state["pos"] += 1
    return {"ticket_id": tid, "remaining": len(state["queue"]) - state["pos"]}


async with Client(good) as conn_a:
    started = (await conn_a.call_tool("triage_start", {"priority": "urgent"})).structured_content
    print("connection A: triage_start ->", started)
handle = started["triage_id"]

async with Client(good) as conn_b:                     # a different connection (or replica)
    for _ in range(2):
        print("connection B: triage_next ->", (await conn_b.call_tool("triage_next", {"triage_id": handle})).structured_content)

    clock["skew"] += 16 * 60                           # 16 minutes pass
    expired = await conn_b.call_tool("triage_next", {"triage_id": handle})
    print("\nafter 16 min ->", expired.is_error, expired.content[0].text)
    if "triage_start" in expired.content[0].text:      # the agent follows the instruction in the error
        fresh = (await conn_b.call_tool("triage_start", {"priority": "urgent"})).structured_content
        print("agent recovers: new handle", fresh["triage_id"][:12] + "...", "| queued", fresh["queued"])
```
