## Summary
MCP 以日期作为版本号，而从 `2025-11-25` 到 `2026-07-28` 的跨越是它历史上最大的一次：`initialize` 握手、会话（Session）、`ping` 和服务器发起的请求都被移除；现在每个请求都携带自己的版本和能力（Capability）；`server/discover` 和 `subscriptions/listen` 是新增的；根目录（Roots）、采样（Sampling）和日志（Logging）被弃用。真实的代码库和面试官都会把两个世界混在一起，所以本课就是你的地图。你将学习修订版和特性状态如何运作（有效 → 已弃用 → 已移除，最短十二个月），版本如何在每个请求上协商、并在收到 `-32022` 后重试，“双时代（Dual-era）”客户端如何探测服务器并回退，完整的兼容性矩阵——然后是对变更日志的逐行梳理。

## Lesson
### 基于日期的修订版
MCP 版本是 `YYYY-MM-DD` 形式的字符串。这个日期标记的是**最后一次做出向后不兼容变更的时间**——当协议获得向后兼容的更新时，版本号*不会*递增。所以“2026-07-28”指代的是一份兼容性契约，而不是每次编辑的发布日期。

规范的每个修订版（Protocol Revision）都处于三种状态之一：

| 修订版状态 | 含义 |
| --- | --- |
| **草案（Draft）** | 进行中，尚不可用。 |
| **当前（Current）** | 可供使用的版本；仍可能接收向后兼容的变更。 |
| **最终（Final）** | 已成为过去，已完成；不会再变化。 |

**当前**修订版是 `2026-07-28`。你在实际中会遇到的修订版有 `2024-11-05`、`2025-03-26`、`2025-06-18`、`2025-11-25`（全部为最终状态，全部基于握手）以及 `2026-07-28`。

> **陷阱。** 修订版日期恰好可以按字典序排序，但要把版本视为一个**枚举集合**，而不是数字。Python SDK 维护了一个显式的有序注册表（`KNOWN_PROTOCOL_VERSIONS`），正是为了让 `"zzz"` 这样的未知字符串永远不会比 `"2025-11-25"` “更新”。

### 新版、旧版与双时代
版本规范定义了三个你应当精确使用的术语：

- **新版（Modern）**——以**逐请求元数据**传达版本、身份和能力的版本（`2026-07-28` 及以后）。
- **旧版（Legacy）**——通过 **`initialize` 握手**建立会话的版本（`2025-11-25` 及更早）。
- **双时代（Dual-era）**——同时支持两者的实现。

### 协商：在每个请求上进行，没有握手
*不存在协商握手。* 每个请求都在 `_meta["io.modelcontextprotocol/protocolVersion"]` 中声明自己的版本（在可流式 HTTP（Streamable HTTP）上，还会放在 `MCP-Protocol-Version` 请求头中），并且**服务器独立地接受或拒绝每个请求**。客户端和服务器**可以（MAY）**同时支持多个版本。

如果服务器没有实现所请求的版本——它不认识这个版本，或者认识但有意不支持——它**必须（MUST）**回复 `UnsupportedProtocolVersionError`：

```json
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32022, "message": "Unsupported protocol version",
           "data": {"supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01"}}}
```

客户端**应当（SHOULD）**从 `data.supported` 中挑选一个双方都支持的版本并**重试**；如果不存在这样的版本，则报告错误。

服务器**必须（MUST）**实现 `server/discover`，它在一次调用中返回 `supportedVersions`、`capabilities` 和身份信息。客户端**可以（MAY）**先调用它来预先选定版本——但并不要求这样做：*客户端可以直接调用任何 RPC，并处理 `UnsupportedProtocolVersionError`*。

```text
Client                                  Server
  │ tools/call  _meta.protocolVersion=X   │
  │──────────────────────────────────────►│  supports X?  yes → result
  │◄──────────────────────────────────────│               no  → -32022 {supported:[…]}
  │ (on -32022) pick mutual Y, retry      │
  │──────────────────────────────────────►│
```

### 扩展协商
可选的**扩展（Extension）**通过能力而不是版本来协商。`ClientCapabilities` 和 `ServerCapabilities` 都有一个 `extensions` 字段：一个从**扩展标识符（Extension Identifier）**到各扩展**设置对象**的映射。标识符**必须（MUST）**遵循 `_meta` 键的命名规则，带有强制前缀——例如 `io.modelcontextprotocol/ui`（MCP Apps）或 `io.modelcontextprotocol/tasks`（Tasks）。空对象 `{}` 表示“支持，没有设置”。

```json
{"capabilities": {"tools": {}, "extensions": {"io.modelcontextprotocol/tasks": {}}}}
```

如果只有一方支持某个扩展，支持的一方**必须（MUST）**要么回退到核心协议的行为，要么用适当的错误拒绝该请求；扩展**应当（SHOULD）**在文档中说明其回退方式。协议正是这样在不提升核心版本的情况下成长的（第 7 模块）。

### 与基于初始化的版本的向后兼容
服务器**可以（MAY）**同时实现两个时代。必须与两类服务器通信的客户端，会用特定于传输层（Transport）的规则来检测服务器所处的时代：

**stdio——用 `server/discover` 进行探测。** 双时代客户端**应当（SHOULD）**在发送任何其他内容之前，先发送 `server/discover`（在 `_meta` 中带上它首选的新版版本）。有三种结果：

1. 收到 `DiscoverResult` → 服务器是新版的；从 `supportedVersions` 中挑选一个版本。
2. 收到一个**可识别的新版错误**，例如 `UnsupportedProtocolVersionError` → 服务器是新版的，只是不支持该版本；使用它的 `supported` 列表。**不要**回退到 `initialize`。
3. 任何其他错误，或在合理的超时时间内没有响应 → **旧版**；回退到 `initialize`。

回退**绝不能（MUST NOT）**以某个特定错误码为依据：旧版服务器对 `initialize` 之前的未知请求的回应是由实现定义的错误（通常是 `-32601` 或 `-32602`），或者根本不回应。即使是只支持新版的客户端，也**推荐（RECOMMENDED）**进行探测：有些旧版服务器会愉快地按旧版语义处理一个时代不明确的 `tools/call`，而探测能把这种情况变成确定性的失败。

**可流式 HTTP——尝试一个新版请求，检查 400 响应。** 新版服务器在 `UnsupportedProtocolVersionError`、`MissingRequiredClientCapabilityError` 和请求头校验失败时也会使用 `400 Bad Request`，所以收到 `400` 时，客户端**应当（SHOULD）**读取响应体：一个可识别的新版 JSON-RPC 错误意味着“新版——修正请求”；空的或无法识别的响应体意味着“旧版——回退到 `initialize`”（并可能进一步回退到已弃用的 HTTP+SSE 传输）。

时代是**服务器的属性，而不是请求的属性**：客户端**应当（SHOULD）**在服务器进程（stdio）或源（HTTP）的生命周期内缓存它，并**可以（MAY）**跨重启持久化，如果之后这个假设失效再重新探测。只支持新版的服务器在对 `initialize` 返回任何错误时，**应当（SHOULD）**写明自己支持的版本，因为旧版客户端**没有向前升级机制**——这条错误消息可能是用户能看到的唯一诊断信息。

**双时代服务器**根据客户端的开场方式来选择行为：携带新版 `_meta` 的请求以无状态（Stateless）方式处理；`initialize` 请求则选择旧版语义，其作用范围是该 stdio 进程或 HTTP 会话。它**可以（MAY）**在同一个端点上同时服务两个时代。

### 兼容性矩阵

| 客户端 | 服务器 | 结果 |
| --- | --- | --- |
| 新版 | 新版 | **可行。** `server/discover` 可选；不匹配时表现为 `-32022`，客户端重试。 |
| 新版 | 旧版 | **失败。** 服务器可能返回由实现定义的错误、保持沉默，甚至按旧版语义处理一个时代不明确的方法。在 stdio 上，先发送 `server/discover` 以确定性地失败，然后展示一条可操作的错误信息。 |
| 双时代 | 新版 | **可行。** stdio 探测返回 `DiscoverResult`（或 `-32022`）；在 HTTP 上，第一个新版请求要么成功，要么返回一个新版错误。客户端保持新版模式。 |
| 双时代 | 旧版 | **可行。** stdio 探测得到非新版错误或超时 → `initialize`。HTTP：`4xx` 且没有新版错误响应体 → `initialize`（可能再回退到 HTTP+SSE）。 |
| 旧版 | 新版 | **失败。** stdio：`initialize` 被拒绝（未知方法、缺少 `_meta`）。HTTP：缺少必需的请求头 → `400`。没有向前升级机制。 |
| 旧版 | 双时代 | **可行。** 服务器响应 `initialize`，并提供协商出的旧版修订版。 |
| 旧版 | 旧版 | 按该旧版修订版运作。 |

实践上的结论是：**服务器端必须在一段时间内保持双时代**（旧客户端无法自行升级），而**客户端应当是双时代的**，这样它们仍然能够连到大量长尾的 2025 服务器。笔记本会用真实的进程重现每一行。

### 特性生命周期：有效、已弃用、已移除
与修订版相互独立，各个*特性*（消息、能力、传输、模式类型、规范性行为）都有一个由 **SEP-2596** 定义的生命周期，即特性生命周期（Feature Lifecycle）：

| 特性状态 | 含义 | 对实现者的期望 |
| --- | --- | --- |
| **有效（Active）** | 当前修订版的一部分。 | 按其规范性要求实现。 |
| **已弃用（Deprecated）** | 仍在规范中，已计划移除；迁移路径已有文档。 | 新的实现**不应采用**它；已有实现**应当在**最早移除时间之前**完成迁移**。 |
| **已移除（Removed）** | 已从 `draft` 中删除；在下一个当前修订版中不存在；在它最后出现的那个最终修订版中仍有文档。 | 以该修订版为目标的实现不得依赖它。 |

值得记住的规则：

- 弃用需要一份**规范增强提案（SEP）**，说明理由（已被取代；存在无法修复的安全／隐私／互操作风险；采用率可忽略而维护成本高；或核心维护者的其他理由），以及一条**迁移路径**（任何替代方案都必须在同一个修订版中处于有效状态）。
- **最短弃用窗口期（Deprecation Window）为十二个月**，从首次将该特性标记为已弃用的**修订版发布之时**开始计算——而不是从 SEP 获批之时。该特性的**最早移除时间**是窗口期结束当天或之后、作为当前版本发布的第一个修订版。实际移除由核心维护者决定，可能会晚得多。
- **加急移除**：对于正在发生的安全风险（已发布安全公告或已在野外被利用，且无法原地修复），核心维护者可以缩短窗口期——但绝不能短于**九十天**。
- 已弃用的特性可以通过一个取而代之的 SEP **恢复**为有效状态；之后若再次弃用，计时将重新开始。
- 弃用会留下标记：`schema.ts` 中的 `@deprecated`、正文中的说明、变更日志中的一条“Deprecated”条目，以及**弃用注册表**中的一行。
- **Tier 1 SDK** 必须在下一个版本中用该语言的原生机制把相应 API 标记为已弃用，并应当发出运行时警告（Python：`DeprecationWarning`）。从规范中移除**并不**强制 SDK 放弃某个特性；这遵循各 SDK 自己的支持策略。

| 特性 | 弃用于 | 迁移路径 | 最早移除时间 |
| --- | --- | --- | --- |
| 根目录（Roots） | `2026-07-28`（SEP-2577） | 通过工具参数、资源 URI 或服务器配置传递目录／文件 | 2027-07-28 当天或之后的第一个修订版 |
| 采样（Sampling） | `2026-07-28`（SEP-2577） | 直接集成 LLM 提供商的 API | 2027-07-28 当天或之后的第一个修订版 |

### 有哪些变化：2025-11-25 → 2026-07-28
**重大变更**

| # | 变更 | 旧（2025-11-25） | 新（2026-07-28） |
| --- | --- | --- | --- |
| 1 | 移除会话（SEP-2567） | `Mcp-Session-Id` 请求头；列表可以因连接而异 | 没有协议会话；列表端点不因连接而异；跨调用的状态使用**作为工具参数传递的服务器生成句柄（Server-minted Handle）** |
| 2 | 无状态协议（SEP-2575） | `initialize` / `notifications/initialized` 握手 | 每个请求都在 `_meta` 中携带 `io.modelcontextprotocol/protocolVersion` + `clientCapabilities`；客户端应当（SHOULD）发送 `clientInfo`，服务器应当（SHOULD）在每个结果的 `_meta` 中返回 `serverInfo`；不匹配 → `UnsupportedProtocolVersionError` |
| 3 | `server/discover`（SEP-2575） | 能力从 `initialize` 中一次性获知 | 服务器必须（MUST）实现它；客户端可以（MAY）先调用它，或把它用作 stdio 兼容性探测 |
| 4 | `subscriptions/listen`（SEP-2575） | HTTP `GET` 流，`resources/subscribe` / `resources/unsubscribe` | 一个长连接的 POST 响应流；选择加入 `toolsListChanged`、`promptsListChanged`、`resourcesListChanged`、`resourceSubscriptions`；确认 + `subscriptionId` 标记。`notifications/progress` 和 `notifications/message` 仍留在各自请求自己的流上 |
| 5 | 移除项（SEP-2575） | `ping`、`logging/setLevel`、`notifications/roots/list_changed` | 已移除。日志级别通过 `_meta` 中的 `io.modelcontextprotocol/logLevel` 逐请求设置；对于没有该字段的请求，服务器绝不能（MUST NOT）发出 `notifications/message` |
| 6 | 任务（Tasks）→ 扩展（SEP-2663） | 实验性的核心任务，阻塞式 `tasks/result`，`tasks/list` | 扩展 `io.modelcontextprotocol/tasks`：用 `tasks/get` 轮询，通过 `tasks/update` 输入，没有 `tasks/list`；服务器可以主动返回任务句柄 |
| 7 | 多轮往返请求（SEP-2322） | 服务器发起的 `roots/list`、`sampling/createMessage`、`elicitation/create` 请求 | 服务器返回带有 `inputRequests` 的 `InputRequiredResult`；客户端带着 `inputResponses` 重试原始请求 |
| 8 | 处处都有 `resultType`（SEP-2322） | 没有这个字段 | 必需：`"complete"` 或 `"input_required"`；来自旧服务器、不带该字段的结果必须（MUST）被视为 `"complete"` |
| 9 | 不再支持 SSE 可恢复性（SEP-2575） | `Last-Event-ID`、SSE 事件 ID、重新投递 | 流中断会丢失进行中的请求；客户端必须（MUST）用一个**新的请求 ID** 重新发出它 |

本修订版中**被弃用**的：根目录、采样、日志（SEP-2577）；HTTP+SSE 被重新归类；`includeContext` 的 `"thisServer"`/`"allServers"` 被重新归类；动态客户端注册被弃用，改用客户端 ID 元数据文档。**其他**：`schema.json` 现在把 `minimum`/`maximum`/`default` 的类型定为 `number`。**治理／流程**：特性生命周期策略（SEP-2596），以及基于 PR、文件放在 `seps/` 中的 SEP 工作流（SEP-1850）。

> **面试技巧。** 如果被问到“MCP 最近有什么变化？”，先讲*主题*，而不是罗列清单：**MCP 变成了无状态的**。会话、握手、`ping`、SSE 可恢复性和服务器发起的请求，都是为了维护连接状态而存在的；移除它们之后，负载均衡器后面的任何副本都能处理任何请求。`server/discover`、逐请求的 `_meta`、多轮往返请求（MRTR）、`subscriptions/listen` 和 `ttlMs` 缓存，就是取代原先状态所承担职责的那些部件。

## Key points
- 版本是 `YYYY-MM-DD` 字符串，标记**最后一次向后不兼容的变更**；兼容的更新不会提升版本号。修订版（Protocol Revision）分为**草案／当前／最终**；当前版本是 `2026-07-28`。
- **没有握手**：每个请求都在 `_meta` 中携带 `io.modelcontextprotocol/protocolVersion`（在 HTTP 上还有 `MCP-Protocol-Version`）；服务器逐个请求地接受或拒绝。
- 不支持的版本 → **`-32022` `UnsupportedProtocolVersionError`**，带有 `data.supported` 和 `data.requested`；客户端挑选一个双方共同支持的版本并重试。
- `server/discover` **对服务器是强制的，对客户端是可选的**。
- 扩展（Extension）通过能力中的 `extensions` 映射进行协商；如果一方不支持，就回退到核心行为或拒绝请求。
- 双时代（Dual-era）stdio 客户端用 `server/discover` 进行探测，并在遇到**任何非新版错误或超时**时回退到 `initialize`——绝不以某一个错误码为依据；在 HTTP 上则检查 `400` 的响应体。按服务器缓存其时代。
- 特性状态为**有效 → 已弃用 → 已移除**；弃用窗口期（Deprecation Window）从弃用它的修订版发布时起 ≥ **12 个月**（加急的安全移除为 ≥ **90 天**）。
- 2026-07-28 中被弃用的：**根目录、采样、日志、动态客户端注册**；更早已被弃用的：HTTP+SSE、`includeContext` 的 `thisServer`/`allServers`。
- 2026-07-28 中被移除的：**会话、`initialize`、`ping`、`logging/setLevel`、`resources/subscribe`、SSE 可恢复性、服务器发起的请求、核心任务**。

## Pitches
### MCP 2026-07-28 有哪些变化？
最核心的一点是 MCP 变成了无状态协议（Stateless Protocol）。在 2025 版里，客户端用 initialize 握手打开一个会话，服务器会记住它的版本和能力。现在每个请求都在元数据里携带自己的协议版本和客户端能力，服务器提供一个 server/discover 调用，而会话、ping 和可恢复的 SSE 流都没有了。服务器不再向客户端发送请求；它们返回一个“需要输入”的结果，由客户端重试。变更通知改为通过 subscriptions/listen 传递，根目录、采样和日志则被弃用了。

### 现在的 MCP 版本协商是怎么运作的？
没有握手。每个请求都在下划线 meta 字段里声明自己的版本，在 HTTP 上还会放进一个请求头。如果服务器不支持这个版本，它会返回错误码负 32022，并附上它支持的版本列表，客户端再用双方都支持的最佳版本重试。客户端也可以提前调用 server/discover，一次性了解支持的版本和能力。对于老服务器，双时代（Dual-era）客户端会先用 discover 进行探测，如果回复不是一个可识别的新版错误，就回退到 initialize 握手。

### MCP 是如何弃用特性的？
特性会经历有效、已弃用、已移除三个阶段。要弃用某个东西，需要一份写明理由和迁移路径的规范增强提案（SEP），之后这个特性至少还会在规范里保留十二个月，从弃用它的那个修订版发布时开始算——只有在存在正在被利用的安全漏洞时，才会缩短到九十天。有一个公开的注册表列出所有即将退场的东西。Tier 1 SDK 必须把相应 API 标记为已弃用，并且应当在运行时发出警告，所以实际上我会在任何东西坏掉之前很久，就在自己的代码里看到弃用警告。

## Interview
### MCP 为什么移除了 `initialize` 握手？它的每项职责分别由什么取代？
握手会产生按连接划分的状态：协商出的版本、双方的能力和身份，在整个会话期间保持。这让水平扩展（Horizontal Scaling）变得别扭（需要粘性会话、会话存储），也让重连变得复杂。在 2026-07-28 中，每项职责都被迁移了：**版本** → 每个请求 `_meta` 中的 `io.modelcontextprotocol/protocolVersion`，若不支持则用 `-32022` 拒绝；**客户端能力** → 每个请求上的 `io.modelcontextprotocol/clientCapabilities`；**身份** → 请求中的 `clientInfo` 和结果 `_meta` 中的 `serverInfo`；**服务器能力和版本** → `server/discover`，可通过 `ttlMs`/`cacheScope` 缓存。结果是：任何服务器实例都能独立处理任何请求。

### 客户端从服务器收到了错误 `-32022`。它应该做什么——又*不*应该做什么？
`-32022` 是 `UnsupportedProtocolVersionError`；`data.supported` 列出服务器支持的版本，`data.requested` 回显所发送的版本。客户端**应当（SHOULD）**把 `supported` 与自己支持的版本取交集，挑选双方都支持的最佳版本并**重试**该请求；如果没有交集，就报告一个清晰的错误。它**不应**回退到旧版的 `initialize` 握手：一个可识别的新版错误证明了服务器是新版的。对于未知的值，它也不应通过简单的字符串比较来比较版本——应当使用它实际实现的版本集合。

### 你维护着一个很受欢迎的 stdio MCP 服务器，新旧客户端都在用。你会如何迁移？
把它做成**双时代实现（Dual-era Implementation）**：如果第一条消息是 `initialize`，就为该进程提供旧版语义；如果它携带新版 `_meta`，就以无状态方式处理。实现 `server/discover`，添加 `resultType`、`ttlMs`/`cacheScope`，并在结果的 `_meta` 中加入 `serverInfo`。在新版路径上，把所有服务器发起的请求替换为多轮往返请求（MRTR）（`InputRequiredResult` + 重试）。不再依赖按连接划分的状态——改用作为工具参数传递的显式句柄。把日志转移到 `stderr`。保留旧版支持，直到遥测数据表明旧客户端已经消失；如果你最终要放弃它，务必让 `initialize` 的错误**写明你支持的版本**，因为旧版客户端无法向前升级。

### 双时代客户端如何判断一个 stdio 服务器是新版还是旧版？为什么不直接检查 `-32601`？
它首先带着自己首选的新版版本发送 `server/discover`。收到 `DiscoverResult` 或一个可识别的新版错误（比如 `-32022`）意味着是新版。任何其他错误或超时都意味着是旧版 → 发送 `initialize`。规范明确禁止以 `-32601` 为依据：旧版服务器对 `initialize` 之前的请求的回应是由实现定义的错误（`-32601`、`-32602`、`-32600`……），或者根本不回应。之后客户端应当为该服务器进程**缓存**这个判断结果。即使是只支持新版的客户端也应当进行这种时代探测（Era Probe），因为有些旧版服务器会毫无怨言地执行一个时代不明确的 `tools/call`。

### 采样已被弃用。我还能用它吗？它什么时候会消失？
能——已弃用意味着它仍是规范的一部分，并且完全可用；新的实现**不应采用**它，已有的实现**应当迁移**（直接集成 LLM 提供商的 API）。它在 `2026-07-28` 中由 SEP-2577 弃用，最短窗口期为十二个月，所以它的**最早移除时间**是 2027-07-28 当天或之后作为当前版本发布的第一个修订版——而且移除由核心维护者决定，可能会更晚。SDK 可以根据自己的策略，在规范移除之后继续支持它。与之对比的是 `ping`，它在 2026-07-28 中被直接**移除**了。

### 陷阱题：“只要能处理 `-32022`，新版客户端就能与任何 MCP 服务器通信。”对吗？
不对。`-32022` 只在面对版本不同的**新版**服务器时才有用。面对**旧版**服务器时，只支持新版的客户端会失败：服务器可能返回任意错误、永远不回应，或者——更糟——按旧版语义处理一个像 `tools/call` 这样时代不明确的请求。这就是为什么规范推荐即使是只支持新版的客户端也要用 `server/discover` 进行探测（以获得确定性的失败），也是为什么生产环境的客户端应当是**双时代（Dual-era）**的：在 stdio 上回退到 `initialize`，在 HTTP 上检查 `400` 的响应体之后再回退。

## Glossary
- Protocol revision | 协议修订版 | 规范的一个带日期的版本（`YYYY-MM-DD`），标记最后一次向后不兼容的变更；状态为草案、当前或最终。
- Modern / legacy era | 新时代 / 旧时代协议 | 使用逐请求元数据的版本（`2026-07-28` 及以后），与使用 `initialize` 握手的版本（`2025-11-25` 及更早）相对。
- Dual-era implementation | 双时代实现 | 同时支持新版和旧版版本的客户端或服务器。
- `UnsupportedProtocolVersionError` | 不支持的协议版本错误 | 当请求的版本未被实现时返回的错误 `-32022`；`data.supported` 列出可选的版本。
- `server/discover` | `server/discover`（服务器发现） | 服务器必须实现的 RPC，返回所支持的版本、能力和身份；客户端可以选择是否调用。
- Extension negotiation | 扩展协商 | 在能力的 `extensions` 映射中声明可选扩展，以带前缀的标识符作为键。
- Era probe | 时代探测 | 双时代客户端最初发送的 `server/discover`，用于在新版请求与旧版 `initialize` 回退之间做出选择。
- Feature lifecycle | 特性生命周期 | 规范特性依据 SEP-2596 所经历的有效 → 已弃用 → 已移除各个状态。
- Deprecation window | 弃用窗口期 | 特性在可被移除之前保持已弃用状态的最短时间（≥ 12 个月，加急时 ≥ 90 天）。
- SEP (Specification Enhancement Proposal) | 规范增强提案 | 变更、弃用或恢复规范特性所必需的正式提案流程。

### 1. 版本字符串和一个协商函数
版本是一个枚举集合。客户端和服务器各自支持其中的某个子集；客户端想要的是双方共有的最新版本。顺序来自一个显式的注册表，而不是字符串比较。这就是版本协商（Version Negotiation）的核心。

```python
import json

KNOWN_VERSIONS = ["2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25", "2026-07-28"]  # oldest -> newest
MODERN = {"2026-07-28"}   # per-request _meta era; everything older uses the initialize handshake


def choose_version(client_supports, server_supports, known=KNOWN_VERSIONS):
    """Newest version both sides support, or None. Unknown strings are ignored, never 'newer'."""
    mutual = [v for v in known if v in client_supports and v in server_supports]
    return mutual[-1] if mutual else None


cases = {
    "both modern":               (["2026-07-28", "2025-11-25"], ["2026-07-28"]),
    "server still on 2025":      (["2026-07-28", "2025-11-25"], ["2025-06-18", "2025-11-25"]),
    "no overlap":                (["2026-07-28"], ["2025-03-26"]),
    "server claims 'zzz'":       (["2026-07-28"], ["zzz", "2026-07-28"]),
}
for label, (client, server) in cases.items():
    picked = choose_version(client, server)
    era = "-" if picked is None else ("modern" if picked in MODERN else "legacy handshake")
    print(f"{label:<22} -> {picked}  ({era})")
```

### 2. 本笔记本后续要用到的三个服务器
我们需要每个时代各一个服务器。SDK 的 `MCPServer` 是**双时代（Dual-era）**的。另外两个是很小的手写 JSON-RPC 循环：一个只懂 `initialize` 的**旧版**服务器（就像任何一个还没升级的 2025 服务器），以及一个**只支持新版**的服务器，它会按照规范的建议，用写明其版本的 `-32022` 拒绝 `initialize`。一个小小的**线路监听（wiretap）**脚本位于客户端和服务器之间，记录双向的每一行。

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())

(workdir / "dual_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    server = MCPServer("weather", version="2.3.0")

    @server.tool()
    def weather_current(location: str) -> str:
        """Get current weather for a location."""
        return f"{location}: 20 degrees (dual-era SDK server)"

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

(workdir / "legacy_server.py").write_text(textwrap.dedent('''
    """A 2025-11-25-era server: initialize handshake or nothing."""
    import json, sys
    initialized = False
    def reply(id_, result=None, error=None):
        print(json.dumps({"jsonrpc": "2.0", "id": id_, **({"error": error} if error else {"result": result})}), flush=True)
    for line in sys.stdin:
        msg = json.loads(line); method, id_ = msg.get("method"), msg.get("id")
        if method == "initialize":
            reply(id_, {"protocolVersion": "2025-11-25", "capabilities": {"tools": {}},
                        "serverInfo": {"name": "old-weather", "version": "0.9.0"}})
        elif method == "notifications/initialized":
            initialized = True
        elif not initialized:
            reply(id_, error={"code": -32600, "message": "Server not initialized"})
        elif method == "tools/list":
            reply(id_, {"tools": [{"name": "weather_current", "description": "Current weather",
                                   "inputSchema": {"type": "object", "properties": {"location": {"type": "string"}}}}]})
        elif method == "tools/call":
            reply(id_, {"content": [{"type": "text", "text": "Sunny (legacy 2025 server)"}]})
        elif method == "ping":
            reply(id_, {})
        elif id_ is not None:
            reply(id_, error={"code": -32601, "message": f"Method not found: {method}"})
'''))

(workdir / "modern_only_server.py").write_text(textwrap.dedent('''
    """A server that speaks 2026-07-28 and nothing else."""
    import json, sys
    SUPPORTED = ["2026-07-28"]
    INFO = {"io.modelcontextprotocol/serverInfo": {"name": "new-weather", "version": "3.0.0"}}
    def send(msg): print(json.dumps({"jsonrpc": "2.0", **msg}), flush=True)
    for line in sys.stdin:
        msg = json.loads(line); method, id_ = msg.get("method"), msg.get("id")
        if id_ is None:
            continue
        if method == "initialize":   # spec: name supported versions; legacy clients cannot fall forward
            send({"id": id_, "error": {"code": -32022, "message": "This server only speaks 2026-07-28",
                  "data": {"supported": SUPPORTED, "requested": msg["params"].get("protocolVersion")}}})
            continue
        version = msg.get("params", {}).get("_meta", {}).get("io.modelcontextprotocol/protocolVersion")
        if version is None:
            send({"id": id_, "error": {"code": -32602, "message": "missing _meta protocolVersion"}})
        elif version not in SUPPORTED:
            send({"id": id_, "error": {"code": -32022, "message": "Unsupported protocol version",
                  "data": {"supported": SUPPORTED, "requested": version}}})
        elif method == "server/discover":
            send({"id": id_, "result": {"resultType": "complete", "supportedVersions": SUPPORTED,
                  "capabilities": {"tools": {}}, "ttlMs": 60000, "cacheScope": "public", "_meta": INFO}})
        elif method == "tools/list":
            send({"id": id_, "result": {"resultType": "complete", "ttlMs": 60000, "cacheScope": "public", "_meta": INFO,
                  "tools": [{"name": "weather_current", "description": "Current weather",
                             "inputSchema": {"type": "object", "properties": {"location": {"type": "string"}}}}]}})
        elif method == "tools/call":
            send({"id": id_, "result": {"resultType": "complete", "_meta": INFO,
                  "content": [{"type": "text", "text": "Sunny (modern-only server)"}]}})
        else:
            send({"id": id_, "error": {"code": -32601, "message": f"Method not found: {method}"}})
'''))

(workdir / "wiretap.py").write_text(textwrap.dedent('''
    """Usage: python wiretap.py LOGFILE server.py -- relays stdio and logs each line."""
    import subprocess, sys, threading
    log_path, target = sys.argv[1], sys.argv[2:]
    child = subprocess.Popen([sys.executable, *target], stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
    lock = threading.Lock()
    def record(prefix, line):
        with lock, open(log_path, "a") as f:
            f.write(prefix + " " + line.rstrip("\\n") + "\\n")
    def pump():
        for line in child.stdout:
            record("<<<", line); sys.stdout.write(line); sys.stdout.flush()
    t = threading.Thread(target=pump, daemon=True); t.start()
    for line in sys.stdin:
        record(">>>", line); child.stdin.write(line); child.stdin.flush()
    child.stdin.close(); child.wait(); t.join(timeout=2)
'''))

SERVERS = {"dual-era": workdir / "dual_server.py",
           "legacy": workdir / "legacy_server.py",
           "modern-only": workdir / "modern_only_server.py"}
print("written:", sorted(p.name for p in workdir.iterdir()))
```

### 3. 手动进行逐请求协商：`-32022` 与重试
一个未来的客户端偏好一个（假想的）更新修订版 `2027-03-01`，同时也支持 `2026-07-28`。它不做任何发现就直接发送请求，从错误中读取 `data.supported`，进行协商，然后重试——这正是版本规范中描述的流程。

```python
CLIENT_SUPPORTS = ["2027-03-01", "2026-07-28"]   # newest first; 2027-03-01 is made up for the demo


def envelope(version):
    return {"io.modelcontextprotocol/protocolVersion": version,
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "future-client", "version": "1.0"}}


proc = subprocess.Popen([sys.executable, str(SERVERS["dual-era"])],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)


def rpc(message):
    print(">>>", json.dumps(message)[:200])
    proc.stdin.write(json.dumps(message) + "\n"); proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    print("<<<", json.dumps(reply)[:300], "\n")
    return reply


def call_with_negotiation(request_id, method, params):
    version = CLIENT_SUPPORTS[0]
    for attempt in range(2):
        reply = rpc({"jsonrpc": "2.0", "id": request_id + attempt, "method": method,
                     "params": {**params, "_meta": envelope(version)}})
        error = reply.get("error")
        if not error or error["code"] != -32022:
            return version, reply
        mutual = [v for v in CLIENT_SUPPORTS if v in error["data"]["supported"]]
        if not mutual:
            raise RuntimeError(f"no common version: server supports {error['data']['supported']}")
        version = mutual[0]
        print(f"... server rejected {error['data']['requested']}, retrying with {version}\n")
    raise RuntimeError("negotiation did not converge")


version, reply = call_with_negotiation(1, "tools/call", {"name": "weather_current", "arguments": {"location": "Oslo"}})
print("negotiated:", version, "| result:", reply["result"]["content"][0]["text"])
proc.stdin.close()
exit_code = proc.wait(timeout=10)
```

注意这里没有握手：*同一个* `tools/call` 只是换了一个 `_meta` 版本和一个新的 `id`，被重新发送了一次。

### 4. SDK 的两种连接模式在线路上的样子
`Client(..., mode="legacy")` 强制使用 2025 的 `initialize` 握手；默认的 `mode="auto"` 则用 `server/discover` 进行探测，只有当回复不能证明服务器是新版时才回退。同一个双时代（Dual-era）服务器，两段截然不同的对话。

```python
import os

from mcp import Client, StdioServerParameters


def tapped(server_key, log_name):
    log = workdir / log_name
    log.unlink(missing_ok=True)
    return log, StdioServerParameters(command=sys.executable, args=[str(workdir / "wiretap.py"), str(log), str(SERVERS[server_key])])


def print_wire(log, width=260):
    for line in log.read_text().splitlines():
        print(line[:width])


for mode in ["legacy", "auto"]:
    log, params = tapped("dual-era", f"wire_{mode}.log")
    async with Client(params, mode=mode) as client:
        result = await client.call_tool("weather_current", {"location": "Paris"})
        print(f"===== mode={mode!r}: negotiated {client.protocol_version}, "
              f"tools.listChanged={client.server_capabilities.tools.list_changed}")
    print_wire(log)
    print()
```

把两份日志并排读一读：**legacy** 先发送 `initialize`，然后是 `notifications/initialized`，然后是不带 `_meta` 的裸请求，结果中没有 `resultType`。**auto** 先发送 `server/discover`，之后的每个请求都携带完整的信封；结果中带有 `resultType`、`ttlMs`/`cacheScope` 和 `serverInfo`。（SDK 还会在 `tools/call` 之后发出一个 `tools/list`，用来校验工具的输出模式（Output Schema）——阅读日志时知道这一点会很有用。）

### 5. 自动模式对上旧版服务器：探测与回退
现在把 `mode="auto"` 指向旧版服务器。探测得到了一个非新版错误（`-32600 Server not initialized`），于是客户端回退到 `initialize`——事先没有被告知任何关于这个服务器的信息。旧版结果中没有 `resultType`；客户端按规范要求把它视为 `"complete"`。这就是时代探测（Era Probe）的完整过程。

```python
log, params = tapped("legacy", "wire_auto_vs_legacy.log")
async with Client(params) as client:   # mode="auto" is the default
    result = await client.call_tool("weather_current", {"location": "Paris"})
    print("negotiated:", client.protocol_version, "| server:", client.server_info.name)
    print("result:", result.content[0].text, "| resultType seen by the app:", result.result_type)
print()
print_wire(log)
```

### 6. 实时运行的兼容性矩阵
客户端模式与服务器时代的每一种组合。`mode="2026-07-28"` 固定使用一个新版版本而不进行探测——即 SDK 中的“只支持新版的客户端”。

```python
async def attempt(mode, server_key):
    params = StdioServerParameters(command=sys.executable, args=[str(SERVERS[server_key])])
    try:
        async with Client(params, mode=mode, read_timeout_seconds=5) as client:
            result = await client.call_tool("weather_current", {"location": "Paris"})
            return f"works ({client.protocol_version})"
    except Exception as exc:
        while isinstance(exc, BaseExceptionGroup):   # unwrap anyio task-group wrappers
            exc = exc.exceptions[0]
        return f"FAILS: {str(exc)[:55]}"


modes = {"legacy": "legacy client", "auto": "dual-era client", "2026-07-28": "modern-only client"}
for mode, label in modes.items():
    for server_key in SERVERS:
        outcome = await attempt(mode, server_key)
        print(f"{label:<19} x {server_key + ' server':<19} -> {outcome}")
    print()
```

与规范中的矩阵对比一下：旧版 × 只支持新版会失败（而我们的服务器在错误中写明了支持的版本——这是旧版客户端唯一能展示的诊断信息）；只支持新版 × 旧版会失败；双时代（Dual-era）客户端在所有情况下都能工作。

### 7. SDK 中的弃用与移除
Tier 1 SDK 必须标记已弃用或已移除的 API，并且应当在运行时发出警告。`ping` 在 2026-07-28 中被**移除**：SDK 仍然为旧版连接提供 `send_ping`，会用一条警告标记它，而新版服务器则回答 `-32601 Method not found`。这体现了特性生命周期（Feature Lifecycle）在 SDK 中的落地。

```python
import warnings

for mode in ["legacy", "auto"]:
    params = StdioServerParameters(command=sys.executable, args=[str(SERVERS["dual-era"])])
    async with Client(params, mode=mode) as client:
        with warnings.catch_warnings(record=True) as caught:
            warnings.simplefilter("always")
            try:
                await client.send_ping()
                outcome = "pong (empty result)"
            except Exception as exc:
                outcome = f"error: {exc}"
        print(f"mode={mode:<7} protocol={client.protocol_version}  ping -> {outcome}")
        for w in caught:
            print(f"   {w.category.__name__}: {w.message}")
```

### 8. 针对 2025 时代流量的迁移检查器
工程师们会继承旧代码和旧日志。把变更日志和弃用注册表编码成数据，然后扫描第 4 节捕获的旧版线路日志（再加上几段额外的片段），找出任何在 2026-07-28 中被移除或弃用的内容。

### 9. 已弃用的特性什么时候可以消失？
弃用窗口期（Deprecation Window）从弃用它的修订版**发布**时开始计算；最早移除时间是窗口期结束当天或之后作为当前版本发布的第一个修订版。下面 2026-07-28 之后的发布日期是为了练习而**虚构**的。

```python
from datetime import date


def add_months(d, months):
    y, m = divmod(d.month - 1 + months, 12)
    return date(d.year + y, m + 1, min(d.day, 28))


def earliest_removal(deprecated_in, releases, months=12, days=None):
    """First release on/after the window ends. `days` models an expedited (security) window, min 90."""
    if days is not None:
        assert days >= 90, "expedited removal still needs at least ninety days"
        window_end = date.fromordinal(deprecated_in.toordinal() + days)
    else:
        assert months >= 12, "the standard window is at least twelve months"
        window_end = add_months(deprecated_in, months)
    return window_end, next((r for r in sorted(releases) if r >= window_end), None)


hypothetical_releases = [date(2026, 12, 15), date(2027, 6, 30), date(2027, 11, 18), date(2028, 5, 2)]
deprecated = date(2026, 7, 28)   # Roots, Sampling, Logging, DCR
for label, kwargs in [("standard 12 months", {}), ("SEP asks for 18 months", {"months": 18}),
                      ("expedited, 120 days", {"days": 120})]:
    end, release = earliest_removal(deprecated, hypothetical_releases, **kwargs)
    print(f"{label:<24} window ends {end} -> earliest removal in revision released {release}")
```

注意 12 个月的情况落在了 2027-11-18，而不是 2027-07-28：移除只会*在某次发布中*发生，而 2027-06-30 那次发布来得太早了。
