## Summary
The biggest change in 2026-07-28 is that MCP became a **stateless protocol**. There is no `initialize` handshake, no `Mcp-Session-Id` and no connection that "remembers" who you are. Every request carries its own protocol version and capabilities, so any server instance can answer it. That is what makes MCP servers easy to put behind load balancers, run serverless and scale horizontally. This lesson explains the statelessness rules, what replaced sessions (explicit, server-minted **handles** passed as tool arguments), the mandatory **`server/discover`** RPC and its `DiscoverResult`, and how version negotiation now happens per request with `UnsupportedProtocolVersionError`. The notebook runs two independent server processes, round-robins requests between them, and shows a stateful shopping basket that works anyway.

## Lesson
### From sessions to self-contained requests
Up to 2025-11-25, an MCP connection began with a handshake. The client sent `initialize` (protocol version, capabilities, client info), the server replied with its own, and the client confirmed with `notifications/initialized`. Everything after that leaned on the negotiated state, and on Streamable HTTP the server could pin it to an `Mcp-Session-Id` header. The changelog for 2026-07-28 removes all of that:

| 2025-11-25 and earlier (legacy era) | 2026-07-28 (modern era) |
| --- | --- |
| `initialize` → result → `notifications/initialized` | **no handshake**; each request is self-contained |
| version and capabilities negotiated once per connection | `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` in **every** request's `_meta` |
| `Mcp-Session-Id` header, `DELETE` to end a session | **no protocol-level sessions** |
| `tools/list` etc. could vary per connection | list endpoints **no longer vary per connection** |
| `ping` | removed |
| server info returned once by `initialize` | `server/discover` (mandatory to implement) and `serverInfo` in every result's `_meta` |
| cross-call state hidden in the session | **explicit, server-minted handles** passed as ordinary tool arguments |

### The statelessness rules
The base protocol states it directly: *all the information needed to process a request is contained in the request itself. A server processes each request independently; no state should be inferred from previous requests, even those on the same connection or stream.* Concretely:

- Servers **MUST NOT** rely on prior requests over the same connection to establish context such as capabilities, protocol version or client identity. Every request supplies these in `_meta`.
- Servers **SHOULD** be prepared to handle requests associated with multiple tasks, threads or conversations.
- Servers **SHOULD NOT** require a client to reuse the same connection or process for related operations.
- Clients **SHOULD NOT** use an individual task, thread or conversation as the lifetime boundary for the stdio process.
- State that must span requests (long-running tasks, application-level handles) **MUST** be referenced by an **explicit identifier** that the client passes on each request.

> **Spec rule.** An open connection, even a stdio process, *is not a conversation or session*. Clients may interleave unrelated requests on the same transport, and a server must not treat connection or process identity as a proxy for conversation continuity.

Long-lived requests such as `subscriptions/listen` stay request/response. The response is an open stream of notifications, and its state is **scoped to the request**, not to the connection underneath. If the channel drops, the client simply re-issues the request.

Capabilities are also **per request**. The same client can declare `{"elicitation": {}}` on one call and `{}` on the next, and the server must judge each request only by what that request declares. If a needed capability is absent, the answer is `-32021` (lesson 2.1).

### Why stateless? The operational payoff
A session is state the *infrastructure* has to preserve. With sessions, a request had to reach the server instance holding that session. That meant sticky load balancing, or a shared session store behind every instance, plus some way to recover when an instance died mid-session. Removing protocol state changes the deployment model:

- **Horizontal scaling and load balancing.** Any replica can serve any request, so a plain round-robin balancer works. The Streamable HTTP transport also mirrors the method and tool name into headers (`Mcp-Method`, `Mcp-Name`) so gateways can route and rate-limit without parsing bodies (lesson 2.3).
- **Serverless and autoscaling.** A function that lives for one request can be a complete MCP server, because nothing has to survive between invocations except what your application stores on purpose.
- **Simple failure recovery.** On stdio, if the server exits unexpectedly the client restarts it. *Because the protocol is stateless, in-flight requests are simply lost and can be retried against the fresh process.* A broken HTTP response stream is handled the same way: re-issue the request with a new id.
- **Server-to-client interactions without sticky routing.** The MRTR pattern exists so that elicitation and sampling work *without requiring a shared storage layer across server instances or stateful load balancing*. Any intermediate state rides in the request itself as `requestState`.
- **Cacheability.** Because list results no longer vary per connection, they can carry `ttlMs`/`cacheScope` and be cached, even by shared intermediaries when the scope is `public`.

The trade-off is a slightly bigger request (an envelope on every message) and more design responsibility for servers that really do need state.

### What replaced sessions: server-minted handles
Plenty of tools are inherently stateful: a shopping cart, an open browser page, a database transaction. The tools page gives non-normative guidance. *Return an explicit handle from a creation tool and accept that handle as an argument on subsequent calls.* From the wire's perspective a handle is just a string in a result and an ordinary argument later. The protocol has no concept of it.

```jsonc
// → tools/call  create_basket {}
// ← structuredContent: {"basket_id": "bsk_a1b2c3"}
// → tools/call  add_item {"basket_id": "bsk_a1b2c3", "sku": "..."}
```

The **model** is responsible for carrying `basket_id` forward. The **server** stores the basket under that key in storage every instance can reach (a database, Redis, object storage) and looks it up on each call. The spec lists four design concerns:

| Concern | Guidance |
| --- | --- |
| **Authorization** | On authenticated servers a handle is a *name, not a capability*: check the caller's authorization against the handle on every call. On unauthenticated servers the handle is a bearer token, so generate it with enough entropy (e.g. UUIDv4) and give it a bounded lifetime. |
| **Opacity** | Handles that encode structure invite parsing and guessing. Use opaque ids. |
| **Lifetime** | Handles outlive connections, so state the retention policy in the creation tool's description ("baskets expire after 24 hours of inactivity"), where the model can see it. |
| **Expiry errors** | A call with an expired or unknown handle should return a **tool execution error** (`isError: true`) that says so, so the model can recover by creating a new one. |

Compared with a hidden session, explicit handles also make state visible in the conversation transcript. A user can work with two baskets at once, and a different client (or a resumed agent) can carry on with the same handle.

### `server/discover`: the one call that tells you everything
Servers **MUST** implement `server/discover`. It takes no parameters beyond the standard `_meta`:

```json
{"jsonrpc": "2.0", "id": "discover-1", "method": "server/discover",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"},
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

```json
{"jsonrpc": "2.0", "id": "discover-1",
 "result": {"resultType": "complete",
            "supportedVersions": ["2026-07-28"],
            "capabilities": {"tools": {}, "resources": {}},
            "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "ExampleServer", "version": "1.0.0"}},
            "instructions": "This server provides weather and resource utilities.",
            "ttlMs": 3600000, "cacheScope": "public"}}
```

**`DiscoverResult` fields:**

| Field | Required | Meaning |
| --- | --- | --- |
| `supportedVersions` | yes | Protocol versions the server supports. The client should choose one for subsequent requests. |
| `capabilities` | yes | `ServerCapabilities`: `tools`, `resources` (`subscribe`, `listChanged`), `prompts`, `completions`, `logging` (deprecated), `extensions`, `experimental` |
| `_meta["io.modelcontextprotocol/serverInfo"]` | SHOULD | `Implementation`: `name`, `version`, optional `title`, `description`, `websiteUrl`, `icons`. Self-reported: use it for display and debugging, never for behaviour or security decisions. |
| `instructions` | no | Natural-language guidance for the LLM on using this server, e.g. for a system prompt. It should not duplicate tool descriptions. |
| `ttlMs`, `cacheScope` | yes | Caching hints, like HTTP `max-age` and `public`/`private`. `0` means immediately stale. `public` lets shared intermediaries cache it. |
| `resultType` | yes | `"complete"` |

**When to call it.** It is *optional for clients*: a client may invoke any RPC directly and handle `UnsupportedProtocolVersionError`. It is useful in two scenarios:

1. **Presenting server information.** One request returns identity, capabilities and versions. That beats probing `tools/list`, `prompts/list` and `resources/list` separately just to find out what exists.
2. **The stdio backward-compatibility probe.** stdio has no HTTP status codes to drive fallback, so a dual-era client **SHOULD** send `server/discover` first (next section).

Because the result is cacheable, a client typically discovers once per server (or per `ttlMs`), not per request.

### Version negotiation, per request
There is no negotiation handshake. *Every request carries its protocol version, and the server accepts or rejects each request independently.* (On HTTP the version is also in the `MCP-Protocol-Version` header, which must match.) If the server does not implement the requested version, whether it is unknown or a known version the server chose not to support, it **MUST** answer with `-32022`:

```json
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32022, "message": "Unsupported protocol version",
           "data": {"supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01"}}}
```

The client **SHOULD** pick a mutually supported version from `supported` and **retry**, or surface an error if none exists. So negotiation costs one extra round trip in the worst case and none when versions already match.

### Living with the legacy era
Real deployments mix **modern** servers (2026-07-28+, per-request `_meta`), **legacy** servers (2025-11-25 and earlier, `initialize`), and **dual-era** implementations that speak both. Detection is transport-specific:

- **stdio:** probe with `server/discover` at your preferred modern version. A `DiscoverResult` means modern. A *recognised modern error* such as `-32022` also means modern, so retry with a listed version and do **not** fall back. Any other error, or silence until a timeout, means legacy, so fall back to `initialize`. The fallback **MUST NOT** be keyed to one specific code, because legacy servers answer unknown pre-`initialize` requests with assorted errors (`-32601`, `-32602`) or not at all.
- **Streamable HTTP:** send a modern request. On `400`, inspect the body. A recognised modern JSON-RPC error means modern (fix the request). An empty or unrecognised body means legacy, so fall back.

The era is a property of the **server**, not of a request. Clients **SHOULD** cache it per stdio process or HTTP origin, and **MAY** persist it across restarts. A dual-era server picks its behaviour from how the client opens. A request with modern `_meta` is served statelessly, while `initialize` selects legacy semantics scoped to that process or session. Modern-only servers **SHOULD** name their supported versions in the error they return to `initialize`, because legacy clients cannot fall forward and that message may be the only diagnostic a user sees.

> **Pitfall.** A modern-only client talking to a legacy server can be silently wrong: some legacy servers do not check that `initialize` happened and will run an era-ambiguous method like `tools/call` under legacy semantics. Probing with `server/discover` first turns that into a deterministic failure.

## Key points
- 2026-07-28 MCP is **stateless**. Each request carries everything needed to process it, and no state is inferred from earlier requests on the same connection.
- **Removed:** the `initialize`/`notifications/initialized` handshake, `Mcp-Session-Id` sessions and `ping`. Version and capabilities travel in every request's `_meta`.
- A stdio process or HTTP connection **is not a session**. Clients may interleave unrelated requests, and capabilities are judged per request.
- Cross-call state uses **explicit, server-minted handles** returned by a creation tool and passed back as tool arguments. They should be authorized per call, opaque, have a stated lifetime, and fail with a readable `isError` on expiry.
- Statelessness enables **round-robin load balancing, serverless and horizontal scaling**, and simple recovery: restart and retry.
- Servers **MUST** implement `server/discover`. It returns `supportedVersions`, `capabilities`, `instructions`, `serverInfo` in `_meta`, and the cache hints `ttlMs`/`cacheScope`.
- Calling `server/discover` is **optional** for clients. It is useful for showing server info and as the **stdio backward-compatibility probe**.
- An unsupported version gets `-32022` with `data.supported`/`data.requested`. The client picks a mutual version and retries. A recognised modern error never triggers a legacy fallback.

## Pitches
### Why did MCP become stateless?
Sessions made MCP servers hard to operate. Every request had to reach the instance holding the session, which meant sticky load balancing or a shared session store, and a crashed instance broke conversations. In 2026-07-28 each request carries its protocol version and capabilities in `_meta`, so any replica can answer it. Servers can sit behind a plain load balancer, run serverless, scale horizontally, and recover by restarting and retrying. State the application genuinely needs becomes explicit handles instead.

### How do you keep state across tool calls without sessions?
I make the state explicit. A creation tool, say `create_basket`, returns an opaque, high-entropy handle, and later tools take that handle as an ordinary argument. The model carries it forward. The server stores the data in something every instance can reach, checks the caller's authorization on each call, documents the lifetime in the tool description, and returns a readable `isError` result when the handle has expired, so the model can recover by creating a new one.

### What is `server/discover` for?
It's the one request that returns everything about a server: the protocol versions it supports, its capabilities, its identity in `serverInfo`, and optional instructions for the model, all with cache hints. Servers must implement it, but clients don't have to call it, because version mismatches can be handled inline. I use it to show what a server offers without probing every list endpoint, and on stdio as the probe that tells a modern server from a legacy one.

## Interview
### What exactly does "stateless" mean in MCP 2026-07-28? Does it mean the server can't have state?
It means the **protocol** carries no state. A server must not infer capabilities, version or identity from earlier requests, even on the same connection, and must not tie related operations to a connection or process. It does **not** mean servers are pure functions. Servers can hold all the application state they like (databases, caches, carts), as long as each request **names** the state it touches through an explicit identifier the client passes. Long-lived things like `subscriptions/listen` are still requests, and their state is scoped to that request, not to the connection.

### How would you migrate a 2025-era server that kept a per-session "current project" variable?
That variable is implicit session state, and it breaks as soon as requests land on different replicas or a client interleaves conversations. I would add `open_project(...)` (or reuse an existing id) that returns an opaque `project_id`, add `project_id` as a required parameter to every tool that used the implicit project, and store project context in shared storage keyed by that id. On each call I authorize the caller against the id, refresh a bounded TTL that the tool description states, and return `isError: true` with "unknown or expired project, call open_project" when lookup fails. A bonus is that two conversations can now work on two projects through the same connection.

### Walk through what a dual-era client does when connecting to an unknown stdio server.
It sends `server/discover` first, at its preferred modern version. There are three outcomes. A `DiscoverResult` means the server is modern, so the client picks a version from `supportedVersions` and continues. A recognised modern error like `-32022` also means modern, so the client retries with a version from `data.supported` and does **not** fall back. Any other error, or no reply within a timeout, means legacy, so the client falls back to `initialize`. The fallback must not depend on one specific code, since legacy servers vary. The client caches the verdict for the life of that server process.

### Is calling `server/discover` mandatory before `tools/call`?
No. Servers **must implement** it, but clients **may** call it. A client can send `tools/call` immediately with its preferred version. If that version is not supported, the server returns `-32022` listing its versions, and the client retries. Discover is worth calling when you want to display capabilities and identity, populate an LLM system prompt with `instructions`, or probe the era on stdio. Its result carries `ttlMs` and `cacheScope`, so you can cache it rather than repeat it.

### Gotcha: a client sends request A declaring `elicitation` and request B without it, on the same connection. Request B's tool needs elicitation. What happens?
Request B fails with `-32021 MissingRequiredClientCapability` and `data.requiredCapabilities: {"elicitation": ...}`. The server must judge B only by B's own `_meta`. "The client said it supports elicitation a moment ago" is exactly the cross-request inference statelessness forbids. Request A, meanwhile, would get an `input_required` result asking for the elicitation. The fix is client-side: declare the capabilities each request needs, which SDKs do automatically by stamping the same envelope on every call.

### What fields in `DiscoverResult` should a host trust?
Treat `supportedVersions` and `capabilities` as the server's protocol contract. They decide which version to send and which methods to call, though the client still handles errors gracefully. `instructions` is useful model context, but it is server-authored text, so treat it like any untrusted prompt content. `serverInfo` (name, version, icons) is **self-reported and unverified**. Use it for display, logging and debugging, never to change behaviour or to make security decisions. A server calling itself "official-github" proves nothing.

## Glossary
- Stateless protocol | 无状态协议 | A protocol where every request contains all the information needed to process it, so no state is inferred from earlier requests.
- Session (legacy) | 会话（旧版） | Connection-scoped state established by `initialize` and, on HTTP, `Mcp-Session-Id`; removed in 2026-07-28.
- `server/discover` | `server/discover`（服务器发现） | The mandatory RPC that returns a server's supported versions, capabilities, identity, instructions and cache hints.
- `DiscoverResult` | 发现结果（`DiscoverResult`） | The result of `server/discover`: `supportedVersions`, `capabilities`, `instructions`, `ttlMs`, `cacheScope` and `serverInfo` in `_meta`.
- Server-minted handle | 服务器生成的句柄 | An opaque identifier returned by a creation tool and passed back as a tool argument to reference cross-call state.
- Version negotiation | 版本协商 | Choosing a protocol version per request; the server rejects an unsupported one with `-32022` listing alternatives.
- Modern / legacy / dual-era | 新版／旧版／双时代实现 | Implementations that use per-request `_meta` (2026-07-28+), the `initialize` handshake (2025-11-25 and earlier), or both.
- Backward-compatibility probe | 向后兼容探测 | Sending `server/discover` first on stdio to tell a modern server from a legacy one before falling back to `initialize`.
- Horizontal scaling | 水平扩展 | Adding identical server replicas behind a load balancer, which statelessness makes possible without sticky routing.

## Notebook
### 1. Call `server/discover` by hand
We start a small shop server as a subprocess and send `server/discover` as a raw JSON line. The server declares cache hints for discovery, so you can see `ttlMs` and `cacheScope` set by the server.

```python
import itertools
import json
import os
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
from pathlib import Path


def show(obj, limit=1200):
    text = json.dumps(obj, indent=2, ensure_ascii=False)
    print(text if len(text) <= limit else text[:limit] + "\n  ...")


workdir = Path(tempfile.mkdtemp())
(workdir / "shop_server.py").write_text(textwrap.dedent('''
    import json, os, secrets, sqlite3, sys, time
    from mcp.server import CacheHint, MCPServer
    from mcp.server.mcpserver.exceptions import ToolError

    INSTANCE = sys.argv[1]                       # which replica am I?
    DB = os.environ["SHOP_DB"]                   # storage shared by every replica
    mcp = MCPServer(f"shop-{INSTANCE}", version="1.0.0",
                    instructions="Create a basket with create_basket, then pass its basket_id to add_item.",
                    cache_hints={"server/discover": CacheHint(ttl_ms=3_600_000, scope="public")})

    _implicit_cart = []                          # per-process memory: the anti-pattern

    def db():
        conn = sqlite3.connect(DB)
        conn.execute("create table if not exists baskets (id text primary key, items text, expires real)")
        return conn

    @mcp.tool()
    def add_to_my_cart(sku: str) -> str:
        """ANTI-PATTERN: add to 'the' cart remembered by this process."""
        _implicit_cart.append(sku)
        return json.dumps({"served_by": INSTANCE, "cart": _implicit_cart})

    @mcp.tool()
    def create_basket() -> str:
        """Create an empty basket and return its basket_id. Baskets expire after 10 minutes of inactivity."""
        basket_id = "bsk_" + secrets.token_urlsafe(12)      # opaque, high entropy
        with db() as conn:
            conn.execute("insert into baskets values (?, ?, ?)", (basket_id, "[]", time.time() + 600))
        return json.dumps({"served_by": INSTANCE, "basket_id": basket_id})

    @mcp.tool()
    def add_item(basket_id: str, sku: str) -> str:
        """Add a product to a basket created by create_basket."""
        with db() as conn:
            row = conn.execute("select items, expires from baskets where id = ?", (basket_id,)).fetchone()
            if row is None or row[1] < time.time():
                raise ToolError(f"Unknown or expired basket {basket_id!r}. Call create_basket to start a new one.")
            items = json.loads(row[0]) + [sku]
            conn.execute("update baskets set items = ?, expires = ? where id = ?",
                         (json.dumps(items), time.time() + 600, basket_id))
        return json.dumps({"served_by": INSTANCE, "basket_id": basket_id, "items": items})

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

ENV = {**os.environ, "SHOP_DB": str(workdir / "shop.sqlite")}
ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "notebook", "version": "0.1"}}


class Replica:
    """One server process we talk to with raw JSON lines."""

    def __init__(self, name):
        self.name = name
        self.proc = subprocess.Popen([sys.executable, str(workdir / "shop_server.py"), name], env=ENV,
                                     stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.DEVNULL,
                                     text=True)
        self.inbox = queue.Queue()
        threading.Thread(target=lambda: [self.inbox.put(l) for l in self.proc.stdout], daemon=True).start()

    def send(self, message: dict, wait=10):
        self.proc.stdin.write(json.dumps(message) + "\n")
        self.proc.stdin.flush()
        return json.loads(self.inbox.get(timeout=wait))

    def rpc(self, id_, method, params=None, meta=ENVELOPE):
        return self.send({"jsonrpc": "2.0", "id": id_, "method": method, "params": {**(params or {}), "_meta": meta}})

    def close(self):
        self.proc.stdin.close()
        return self.proc.wait(timeout=10)


a = Replica("A")
discover = a.rpc("discover-1", "server/discover")
show(discover)
```

Pull the `DiscoverResult` apart the way a host would:

```python
d = discover["result"]
print("server          :", d["_meta"]["io.modelcontextprotocol/serverInfo"])
print("versions        :", d["supportedVersions"])
print("capabilities    :", sorted(d["capabilities"]))
print("instructions    :", d.get("instructions"))
print(f"cache           : fresh for {d['ttlMs'] / 1000:.0f}s, scope={d['cacheScope']!r} "
      "(public = a shared gateway may cache it)")
```

### 2. Per-request version negotiation
No handshake: we call a tool directly at a version the server does not know, read `-32022`, choose a mutual version from `data.supported`, and retry. This is the client logic the spec describes, in about ten lines.

```python
CLIENT_VERSIONS = ["2099-01-01", "2026-07-28"]          # newest first


def call_with_negotiation(replica, method, params, preferred=CLIENT_VERSIONS[0]):
    version, attempt = preferred, 0
    while True:
        attempt += 1
        reply = replica.rpc(100 + attempt, method, params,
                            meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": version})
        if "error" in reply and reply["error"]["code"] == -32022:
            supported = reply["error"]["data"]["supported"]
            print(f"attempt {attempt}: {version} rejected; server supports {supported}")
            mutual = [v for v in CLIENT_VERSIONS if v in supported]
            if not mutual:
                raise RuntimeError("no mutually supported protocol version")
            version = mutual[0]
            continue
        print(f"attempt {attempt}: accepted at {version}")
        return reply


reply = call_with_negotiation(a, "tools/call", {"name": "create_basket", "arguments": {}})
print(reply["result"]["content"][0]["text"])
```

### 3. Any replica can answer: two independent processes
Start a second process, `B`. It shares nothing with `A` except the database file the *application* chose to share. A round-robin "load balancer" sends each request to the next replica.

```python
b = Replica("B")
balancer = itertools.cycle([a, b])
ids = itertools.count(1000)


def lb_call(tool, arguments):
    replica = next(balancer)
    reply = replica.rpc(next(ids), "tools/call", {"name": tool, "arguments": arguments})
    result = reply["result"]
    return replica.name, result["isError"], result["content"][0]["text"]


for _ in range(2):
    replica = next(balancer)
    info = replica.rpc(next(ids), "server/discover")["result"]["_meta"]["io.modelcontextprotocol/serverInfo"]
    print(f"discover via {replica.name}: {info}")
```

### 4. Break it: implicit per-process state
`add_to_my_cart` keeps "the" cart in process memory, the way a session-era server might have kept it in a session. Behind a load balancer, the user's cart is split across replicas:

```python
for sku in ["apple", "pear", "fig", "kiwi"]:
    name, is_error, text = lb_call("add_to_my_cart", {"sku": sku})
    print(f"via {name}: {text}")
```

Neither replica has the full cart, and nothing in the protocol can fix that. The server inferred continuity from the process, which the spec forbids.

### 5. Fix it: a server-minted handle passed as a tool argument
Now the stateful workflow the way the spec recommends. `create_basket` mints an opaque id, and every later call names it. Whichever replica serves a call, it finds the basket in shared storage.

```python
name, _, text = lb_call("create_basket", {})
basket_id = json.loads(text)["basket_id"]
print(f"created by {name}: {basket_id}")

for sku in ["apple", "pear", "fig", "kiwi"]:
    name, is_error, text = lb_call("add_item", {"basket_id": basket_id, "sku": sku})
    print(f"via {name}: {json.loads(text)['items']}")

name, is_error, text = lb_call("add_item", {"basket_id": "bsk_does_not_exist", "sku": "x"})
print(f"\nunknown handle via {name}: isError={is_error} -> {text}")
```

The unknown-handle case is a **tool execution error** (`isError: true`) with a message that tells the model how to recover, exactly what the spec's "expiry errors" guidance asks for. (In this SDK, raise `ToolError` to send your own message. Any other exception is reported as a generic "Error executing tool …".)

### 6. Capabilities are judged per request, even on one connection
Two requests on the **same** process, one declaring `elicitation` and one not. The server must not carry the first declaration over to the second.

```python
(workdir / "confirm_server.py").write_text(textwrap.dedent('''
    from typing import Annotated
    from pydantic import BaseModel
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Elicit, Resolve

    mcp = MCPServer("confirm")

    class Confirm(BaseModel):
        ok: bool

    def ask(basket_id: str):
        return Elicit(f"Empty basket {basket_id}?", Confirm)

    @mcp.tool()
    def empty_basket(basket_id: str, confirm: Annotated[Confirm, Resolve(ask)]) -> str:
        """Empty a basket after the user confirms."""
        return "emptied" if confirm.ok else "kept"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
confirm = Replica.__new__(Replica)
confirm.name = "confirm"
confirm.proc = subprocess.Popen([sys.executable, str(workdir / "confirm_server.py")], stdin=subprocess.PIPE,
                                stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
confirm.inbox = queue.Queue()
threading.Thread(target=lambda: [confirm.inbox.put(l) for l in confirm.proc.stdout], daemon=True).start()

args = {"name": "empty_basket", "arguments": {"basket_id": basket_id}}
with_cap = confirm.rpc(1, "tools/call", args, meta={**ENVELOPE, "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}})
without = confirm.rpc(2, "tools/call", args)
print("request 1 (declares elicitation):", with_cap["result"]["resultType"])
print("request 2 (declares nothing)    :", without["error"]["code"], without["error"]["message"][:60])
print("                                  ", without["error"]["data"])
```

### 7. The legacy era: `initialize` on a fresh process
This SDK is **dual-era**. If the first request a stdio process sees is a 2025-style `initialize`, the whole process is served with legacy semantics, and a modern request on it is refused. That is why a dual-era *client* probes with `server/discover` first.

```python
old = Replica("legacy")
show(old.send({"jsonrpc": "2.0", "id": 1, "method": "initialize",
               "params": {"protocolVersion": "2025-11-25", "capabilities": {},
                          "clientInfo": {"name": "old-client", "version": "1.0"}}}), limit=600)
old.proc.stdin.write(json.dumps({"jsonrpc": "2.0", "method": "notifications/initialized"}) + "\n")
old.proc.stdin.flush()
show(old.rpc(2, "server/discover"))
```

### 8. The SDK does all of this for you
`Client` in its default `mode="auto"` probes `server/discover`, adopts the result, and stamps the envelope on every later request. `mode="legacy"` forces the old handshake. Compare:

```python
from mcp import Client, StdioServerParameters

params = StdioServerParameters(command=sys.executable, args=[str(workdir / "shop_server.py"), "C"], env=ENV)
async with Client(params) as client:
    d = client.session.discover_result
    print("auto  :", client.protocol_version, "| discover:", d.supported_versions, d.ttl_ms, d.cache_scope)
    print("        instructions:", client.instructions)
async with Client(params, mode="legacy") as client:
    print("legacy:", client.protocol_version, "| discover result:", client.session.discover_result)

for replica in (a, b, confirm, old):
    replica.close()
```
