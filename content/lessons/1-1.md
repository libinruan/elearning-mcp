## Summary
Every useful AI application needs context from somewhere else: files, databases, calendars, ticketing systems, search. Before MCP, each application wrote its own connector for each system — an N×M explosion of one-off glue code. The Model Context Protocol is an open standard that turns that into N+M: a system is wrapped once as an **MCP server**, and any **MCP host** (Claude, ChatGPT, VS Code, Cursor, your own agent) can use it through a client. This lesson builds the mental model — the USB-C analogy, the three server primitives, the role of JSON-RPC, the security principles and the design philosophy — and ends with a working client talking to a real server.

## Lesson
### The problem: context is the bottleneck
A language model on its own only knows its training data and what is in the prompt. Everything that makes an AI application *useful* — reading your repository, querying the sales database, creating a calendar event, filing a ticket — requires connecting the model to external systems. Two things are needed for each connection: a way to **give the model context** (data it can read) and a way to **let it act** (functions it can call).

Before a standard existed, every AI application solved this privately. A chat assistant wrote its own GitHub integration, an IDE wrote another, an internal agent a third. With *N* AI applications and *M* external systems, the industry wrote close to **N × M** integrations, each with its own auth handling, schema conventions and bugs. Worse, a tool built for one application could not be reused by another.

### The answer: one protocol, N + M integrations
The official definition: *MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems.* Using MCP, applications such as Claude or ChatGPT connect to **data sources** (local files, databases), **tools** (search engines, calculators) and **workflows** (specialised prompts).

The docs' analogy is **USB-C for AI applications**: just as USB-C lets any device plug into any laptop through one standard port, MCP lets any AI application plug into any external system through one standard protocol. Each system is wrapped once as an MCP server; each application implements MCP once. Integrations become **N + M**.

| | Without MCP | With MCP |
| --- | --- | --- |
| 5 AI apps × 20 systems | up to 100 bespoke integrations | 5 clients + 20 servers = 25 components |
| A new system appears | every app must add support | write one server, every app can use it |
| A new app appears | must re-implement every integration | implement MCP once, inherit the ecosystem |

The spec credits the **Language Server Protocol (LSP)** as inspiration: LSP standardised how editors talk to language tooling, so one Python language server works in VS Code, Vim and JetBrains alike. MCP does the same for AI applications and their context.

### What MCP enables
The docs give concrete examples of what becomes possible:

- An agent that reads your **Google Calendar and Notion** and acts as a personalised assistant.
- **Claude Code** generating an entire web app from a **Figma** design.
- An **enterprise chatbot** connected to several databases so people can analyse data in chat.
- A model that creates **3D designs in Blender** and sends them to a 3D printer.

Who benefits depends on where you sit: **developers** spend less time building and integrating; **AI applications** gain an ecosystem of data sources, tools and apps; **end users** get assistants that can access their data and act for them when needed. The ecosystem is broad — Claude, ChatGPT, Visual Studio Code, Cursor, MCPJam and many more speak MCP — so you *build once and integrate everywhere*.

### The participants: host, client, server
The specification names three roles (lesson 1.2 goes deeper):

- **Host** — the AI application the user interacts with (Claude Desktop, an IDE, your agent). It owns the LLM, the UI and the user's consent.
- **Client** — a connector *inside* the host. The host creates **one client per server** it connects to.
- **Server** — a program that provides context and capabilities. It can run locally as a subprocess or remotely over HTTP.

```text
┌──────────────── Host (AI application) ────────────────┐
│   LLM  ·  UI  ·  consent                               │
│   ┌──────────┐   ┌──────────┐   ┌──────────┐          │
│   │ Client A │   │ Client B │   │ Client C │          │
│   └────┬─────┘   └────┬─────┘   └────┬─────┘          │
└────────┼──────────────┼──────────────┼────────────────┘
         │ stdio        │ HTTP         │ HTTP
   ┌─────▼─────┐  ┌─────▼─────┐  ┌─────▼─────┐
   │ Server:   │  │ Server:   │  │ Server:   │
   │ filesystem│  │ GitHub    │  │ database  │
   └───────────┘  └───────────┘  └───────────┘
```

### What servers offer: tools, resources, prompts
Servers expose any of three **primitives**, and the split is deliberate — each has a different *controller*:

| Primitive | What it is | Who decides to use it | Example |
| --- | --- | --- | --- |
| **Tools** | Functions the model can execute | The **model** (with user approval) | `search_flights`, `create_issue` |
| **Resources** | Context and data to read | The **application** | a file, a DB schema, a calendar |
| **Prompts** | Reusable templated messages / workflows | The **user** | “/summarise-PR”, “plan a vacation” |

On the client side, the core feature in this revision is **elicitation**: a way for a server to ask the user for more information mid-operation (lesson 5.3). Around these sit utilities — progress, cancellation, error reporting — and opt-in **extensions** such as Tasks (long-running work), Skills over MCP and MCP Apps (interactive UI rendered in the conversation).

### How they talk: JSON-RPC 2.0, stateless requests
All MCP messages are **JSON-RPC 2.0**: a request has a `method`, `params` and an `id`; the reply carries the same `id` with either a `result` or an `error`. In the 2026-07-28 revision the base protocol is described as **stateless, self-contained requests** with **per-request capability negotiation** — every request carries its protocol version and the client's capabilities in `_meta`, so any server instance can answer it without remembering a session. (Earlier revisions started each connection with an `initialize` handshake; you will meet both in real code — lesson 1.3.)

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "add", "arguments": {"a": 2, "b": 40},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

The same messages travel over two standard transports: **stdio** (the host launches the server as a subprocess) and **Streamable HTTP** (the server is a web service). That separation of *what is said* from *how it is carried* is the data-layer / transport-layer split you will study next.

### Security is a first-class concern
MCP opens paths to arbitrary data access and code execution, so the spec states principles every implementer must address — even though the protocol cannot enforce them itself:

1. **User consent and control** — users explicitly consent to data access and operations, keep control of what is shared, and get clear UIs to review and authorise activity.
2. **Data privacy** — hosts obtain consent before exposing user data to servers and must not transmit resource data elsewhere without consent.
3. **Tool safety** — tools are arbitrary code execution. Descriptions and annotations of tool behaviour are **untrusted unless the server is trusted**, and hosts must obtain consent before invoking any tool.

> **Pitfall.** “The tool says it is read-only” is not a security guarantee. A malicious or compromised server can describe itself however it wants. Module 6 covers prompt injection, token passthrough, the confused deputy and more.

### The design philosophy behind MCP
The maintainers publish design principles that explain many decisions you will see later. Knowing them lets you *predict* the protocol and argue about it in an interview:

- **Convergence over choice** — one way to solve a problem; extensions are where ideas are tested, the spec is where they are committed.
- **Composability over specificity** — keep the primitives small (tools, resources, prompts) and build features from them rather than adding special cases.
- **Interoperability over optimisation** — features should degrade gracefully; capability negotiation lets peers of different sophistication work together.
- **Stability over velocity** — every addition is permanent; “no today leaves the door open, yes closes it forever”.
- **Capability over compensation** — avoid permanent structure to work around temporary model weaknesses.
- **Demonstration over deliberation**, **pragmatism over purity**, **standardisation over innovation** — prefer proven, implemented patterns.

These principles explain, for example, why 2026-07-28 *removed* features (sessions, `ping`, server-initiated requests) and deprecated others (Roots, Sampling, Logging): less surface, more convergence.

### Where MCP fits in an agentic application
For an AI engineer, MCP is the **integration layer** of an agent: the model plans, the host runs the loop (call model → model asks for a tool → host calls the tool through MCP → result goes back to the model), and MCP servers supply the tools and context. MCP does **not** prescribe which model you use, how you prompt it, or how your agent loop works. It standardises the boundary between “the AI application” and “everything else”, which is exactly why it composes with any framework or model provider.

## Key points
- MCP is an **open standard for connecting AI applications to external systems** — data sources, tools and workflows. Analogy: USB-C for AI.
- It turns **N × M** bespoke integrations into **N + M**: wrap a system once as a server, and every MCP host can use it.
- Three roles: **host** (the AI app), **client** (one connector per server, inside the host), **server** (provides context and capabilities).
- Three server primitives with three controllers: **tools** (model-controlled), **resources** (application-controlled), **prompts** (user-controlled).
- Messages are **JSON-RPC 2.0**; in 2026-07-28 every request is **self-contained**, carrying its protocol version and client capabilities in `_meta`.
- Two standard transports: **stdio** for local subprocess servers and **Streamable HTTP** for remote ones.
- Inspired by the **Language Server Protocol**, which did the same for editors and language tooling.
- Security principles — consent, privacy, tool safety — are mandatory for implementers; tool descriptions and annotations are **untrusted** unless the server is trusted.
- Design principles (convergence, composability, interoperability, stability…) explain why the protocol stays small and removes features.

## Pitches
### What is MCP, in one breath?
MCP, the Model Context Protocol, is an open standard for connecting AI applications to the outside world — files, databases, SaaS APIs, internal services. A system is wrapped once as an MCP server that exposes tools, resources and prompts, and any MCP-capable host — Claude, ChatGPT, VS Code, Cursor or my own agent — can use it through a client. It is like USB-C for AI: one port instead of a custom cable for every pair of devices.

### Why does the industry need MCP?
Without a standard, every AI application builds its own connector to every system, so integration work grows as N times M and nothing is reusable. MCP makes it N plus M: build one server for GitHub and it works in every host; build one host and it inherits the whole ecosystem of servers. For an engineer that means I spend my time on the agent's logic and on good tools, not on rewriting the same glue code for each application.

### How does MCP relate to function calling?
Function calling is how a single model API lets the model request a function I defined in my code. MCP sits one layer out: it standardises where those functions come from. My host lists tools from MCP servers, hands their names and JSON schemas to whatever model I use, and when the model asks for one, the host executes it through the MCP client. So MCP is model-agnostic plumbing that feeds function calling, plus resources and prompts that function calling has no notion of.

## Interview
### What problem does MCP solve, and why didn't function calling already solve it?
Function calling lets one model request functions *that one application defined*. Every application still had to write and maintain its own integrations, so the industry was building N × M connectors that could not be shared. MCP standardises the **boundary between AI applications and external systems**: discovery (`tools/list`), invocation (`tools/call`), data access (resources), reusable workflows (prompts), transports, authorization and versioning. A server written once works in any compliant host, regardless of model vendor. Function calling remains the mechanism *inside* the host by which the model chooses a tool; MCP is how the host got that tool.

### Explain host, client and server. Why one client per server?
The **host** is the AI application: it owns the model, the UI and user consent. A **client** is a connector inside the host that maintains the conversation with exactly one **server**, which exposes capabilities. One client per server keeps each connection isolated: capabilities, protocol version, credentials and failures are per server, and the host — not the servers — decides what data flows between them. A filesystem server never sees what the GitHub server returned unless the host chooses to pass it.

### Who controls tools, resources and prompts — and why does it matter?
Tools are **model-controlled**: the LLM decides to call them (with the host enforcing user approval). Resources are **application-controlled**: the host decides what context to attach, for example a file the user selected. Prompts are **user-controlled**: the user explicitly invokes them, often as slash commands. The distinction drives UX and safety: an action with side effects should be a tool behind a consent gate, read-only context the app curates should be a resource, and a reusable workflow a person triggers should be a prompt.

### Is MCP secure by design?
The protocol defines mechanisms — OAuth-based authorization for HTTP servers, capability negotiation, consent requirements — but the spec is explicit that **MCP cannot enforce security at the protocol level**; implementers must. Hosts must obtain user consent before exposing data or invoking tools, and must treat tool descriptions and annotations as untrusted unless the server itself is trusted. The real risks are at the edges: prompt injection through tool results, malicious local servers, over-scoped tokens, token passthrough. A good answer names those and the mitigations (sandboxing, scoped tokens, human-in-the-loop approval).

### What does it mean that MCP is "inspired by LSP"?
The Language Server Protocol let one language server (say, for Rust) work in every editor, ending the editors × languages matrix. MCP applies the same move to AI: one server per external system, usable from every AI host. It also borrowed LSP's technical shape — JSON-RPC 2.0 messages and capability negotiation — so peers with different feature sets can still interoperate.

### When would you *not* use MCP?
If the integration is private to one application, used by one model call path, and will never be shared, plain function calling inside your code is simpler. MCP pays off when tools should be reusable across hosts, owned by a different team, run in a separate process for isolation, or offered to third parties. It is also the natural choice when you want users to plug their own systems into your agent.

## Glossary
- Model Context Protocol (MCP) | 模型上下文协议 | An open standard for connecting AI applications to external data sources, tools and workflows.
- Host | 宿主（宿主应用） | The AI application the user interacts with; it owns the model, the UI and consent, and creates one client per server.
- Client | 客户端 | A connector inside the host that maintains the connection to exactly one MCP server.
- Server | 服务器 | A program that exposes tools, resources and prompts to MCP clients, locally or remotely.
- Tool | 工具 | A function exposed by a server that the model can decide to call.
- Resource | 资源 | Read-only context or data identified by a URI that the application can attach.
- Prompt | 提示模板 | A reusable, parameterised message template that a user explicitly invokes.
- JSON-RPC 2.0 | JSON-RPC 2.0 远程过程调用协议 | The lightweight request/response message format all MCP messages use.
- Language Server Protocol (LSP) | 语言服务器协议 | The editor-tooling standard that inspired MCP's design.
- N×M integration problem | N×M 集成问题 | The explosion of bespoke connectors when every AI app must integrate every system separately.

### 1. The N × M problem in numbers
Before any code that talks MCP, make the economic argument concrete. Change the numbers and watch the gap grow.

```python
def integrations(apps: int, systems: int) -> tuple[int, int]:
    """Connectors to write without a standard vs. with MCP."""
    return apps * systems, apps + systems


for apps, systems in [(3, 5), (10, 50), (40, 2000)]:
    without, with_mcp = integrations(apps, systems)
    print(f"{apps:>3} apps × {systems:>4} systems -> {without:>6} bespoke connectors | "
          f"{with_mcp:>5} MCP components  ({without / with_mcp:.0f}x less work)")
```

### 2. A first server: one tool, one resource, one prompt
The official Python SDK (`mcp` 2.x) gives you `MCPServer`. Decorators turn ordinary Python functions into the three primitives: type hints become the JSON Schema the model sees, docstrings become descriptions.

```python
import json

from mcp import Client
from mcp.server import MCPServer

notes = {"mcp": "MCP is USB-C for AI applications.", "lsp": "LSP inspired MCP's design."}

server = MCPServer("notes")


@server.tool()
def search_notes(query: str) -> list[str]:
    """Return the ids of notes whose text contains the query (case-insensitive)."""
    return [nid for nid, text in notes.items() if query.lower() in text.lower()]


@server.resource("notes://{note_id}")
def read_note(note_id: str) -> str:
    """The full text of one note."""
    return notes[note_id]


@server.prompt()
def explain(topic: str) -> str:
    """Ask the model to explain a topic to a beginner."""
    return f"Explain {topic} to a new AI engineer in three sentences."


print("server defined:", server.name)
```

### 3. Connect a client and discover what the server offers
`Client(server)` connects in-process — perfect for learning and tests. The client *discovers* capabilities at runtime: nothing about the tools is hard-coded on the client side.

```python
async with Client(server) as client:
    print("protocol version:", client.protocol_version)
    tools = (await client.list_tools()).tools
    templates = (await client.list_resource_templates()).resource_templates
    prompts = (await client.list_prompts()).prompts

    for t in tools:
        print("TOOL     ", t.name, "-", t.description)
        print("          input schema:", json.dumps(t.input_schema))
    for r in templates:
        print("RESOURCE ", r.uri_template, "-", r.description)
    for p in prompts:
        print("PROMPT   ", p.name, "- args:", [a.name for a in p.arguments or []])
```

### 4. Use all three primitives
Notice the three different *controllers*: the model would call the tool, the application reads the resource, the user picks the prompt.

```python
async with Client(server) as client:
    hit = await client.call_tool("search_notes", {"query": "usb"})      # model-controlled
    print("tools/call      ->", hit.structured_content, "| isError:", hit.is_error)

    doc = await client.read_resource("notes://mcp")                      # application-controlled
    print("resources/read  ->", doc.contents[0].text)

    msg = await client.get_prompt("explain", {"topic": "MCP"})          # user-controlled
    print("prompts/get     ->", msg.messages[0].content.text)
```

### 5. Build once, integrate everywhere
Two completely different “hosts” reuse the *same* server without either knowing its tools in advance: a dashboard that just lists capabilities, and a tiny keyword “agent” that picks a tool by reading descriptions. This is the N + M argument in code.

```python
async def dashboard_host(srv):
    async with Client(srv) as c:
        names = [t.name for t in (await c.list_tools()).tools]
        return f"dashboard: server '{c.server_info.name}' offers {names}"


async def keyword_agent_host(srv, request: str):
    async with Client(srv) as c:
        tools = (await c.list_tools()).tools
        # a stand-in for an LLM: pick the tool whose description shares the most words with the request
        score = lambda t: len(set(request.lower().split()) & set(t.description.lower().split()))
        best = max(tools, key=score)
        result = await c.call_tool(best.name, {"query": request.split()[-1]})
        return f"agent: chose {best.name!r} -> {result.structured_content}"


print(await dashboard_host(server))
print(await keyword_agent_host(server, "find the notes that contain lsp"))
```

### 6. Peek at the wire: raw JSON-RPC over stdio
Under the SDK, MCP is just JSON-RPC messages. Here the server runs as a real subprocess (the **stdio** transport) and we speak to it by writing one JSON object per line — no SDK on the client side. Every request carries the 2026-07-28 envelope in `_meta`.

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "notes_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    server = MCPServer("notes")

    @server.tool()
    def search_notes(query: str) -> list[str]:
        """Return ids of notes containing the query."""
        return [n for n in ["mcp", "lsp"] if query.lower() in n]

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "notes_server.py")],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)
META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def rpc(id_, method, params):
    message = {"jsonrpc": "2.0", "id": id_, "method": method, "params": params}
    print(">>>", json.dumps(message))
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    print("<<<", json.dumps(reply, indent=2)[:700], "\n")
    return reply


rpc(1, "server/discover", {"_meta": META})
rpc(2, "tools/call", {"name": "search_notes", "arguments": {"query": "mc"}, "_meta": META})
proc.stdin.close()
exit_code = proc.wait(timeout=10)   # closing stdin is how a stdio client shuts a server down
```

Read the replies: the same `id` comes back, `resultType` is `"complete"`, and the server identifies itself in `_meta` (`io.modelcontextprotocol/serverInfo`). The `structuredContent` and the text `content` carry the same answer — one for programs, one for the model.

### 7. Optional: let a real model choose the tool
If `ANTHROPIC_API_KEY` is set, Claude receives the MCP tool's name, description and schema — exactly what the server advertised — and decides whether to call it. Otherwise the cell explains what would happen.

```python
import os

if os.environ.get("ANTHROPIC_API_KEY"):
    import anthropic

    llm = anthropic.Anthropic()
    async with Client(server) as client:
        tools = [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                 for t in (await client.list_tools()).tools]
        response = llm.messages.create(
            model="claude-opus-5-5", max_tokens=16000, tools=tools,
            messages=[{"role": "user", "content": "Which of my notes mention LSP?"}])
        for block in response.content:
            if block.type == "tool_use":
                result = await client.call_tool(block.name, block.input)
                print(f"Claude called {block.name}({block.input}) -> {result.structured_content}")
            elif block.type == "text":
                print("Claude:", block.text)
else:
    print("skipped: set ANTHROPIC_API_KEY to watch Claude pick `search_notes` from the MCP tool list.")
```
