## Summary
A tool that works when *you* call it can still fail when a model calls it. The model only sees a name, a description and a JSON Schema, it pays for every token you return, and it can only fix mistakes your error messages explain. This lesson turns the normative bits of the 2026-07-28 Tools spec (naming rules, `outputSchema`, `isError`, annotations, deterministic ordering, the non-normative *Stateful Tools* guidance, security MUSTs), the client-side view from *Client Best Practices* and the server-design questions of the official agent skills into a practical checklist. In the notebook you lint a bad and a good tool set side by side, watch a scripted agent recover only when the errors are actionable, paginate a huge result, and build a handle-based workflow.

## Lesson
### The model is your user
Everything a model knows about your tool comes from `tools/list`: `name`, optional `title`, `description`, `inputSchema`, optional `outputSchema` and `annotations`. The host pastes those definitions into the model's context, and every result you return goes there too. So tool design is **interface design for a reader that cannot ask questions**. Throughout this lesson each piece of advice is tagged: **[spec]** is the 2026-07-28 specification (MUST/SHOULD), **[docs]** is the official guides, and **[practice]** is general engineering practice that is widely used but not standardised.

The client side shows why this matters. *Client Best Practices* [docs] warns that naive hosts inject every connected server's definitions up front. With hundreds of tools those definitions alone can consume **~150,000 tokens**, "the majority of the context window before the model has even read the user's message". Hosts respond with **progressive discovery**: a `search_tools` meta-tool that finds tools by name and description, *then* loads full schemas. Two consequences for server authors follow. Your names and descriptions must be **searchable** (keyword, BM25 or embeddings), and every unnecessary tool or verbose schema is a cost paid by every conversation.

### Naming and namespacing
**[spec]** Tool names SHOULD be 1–128 characters, case-sensitive, and use only `A-Z a-z 0-9 _ - .`, with no spaces or commas. They SHOULD be unique within a server. Examples: `getUser`, `DATA_EXPORT_v2`, `admin.tools.list`. Uniqueness is only per server. Clients that aggregate servers will see collisions (two servers each exposing `search`) and SHOULD disambiguate, for example by prefixing a server identifier. The spec warns that `serverInfo.name` is **not** unique and SHOULD NOT be relied upon for that.

**[practice]** Don't make the host guess. Prefix tools with your service (`tickets_search`, `tickets_get`, `tickets_close`), pick one convention (`service_verb_noun`), and avoid generic verbs like `do`, `run`, `query` or `process`. A consistent prefix also groups your tools in a progressive-discovery catalog ("Group tools by server" [docs]).

### Descriptions are prompts
**[practice]** Write the description for a model deciding *whether* and *how* to call the tool:

1. **What it does** in one sentence, in domain words a search will match.
2. **When to use it**, and when to use a sibling instead ("for full details call `tickets_get`").
3. **What it returns and its limits** ("at most `limit` summaries, no bodies; use `next_cursor` for more").
4. **Side effects and lifetime** ("closing is idempotent"; "triage sessions expire after 15 minutes", which the spec itself recommends for handles).

Put human-facing labels in `title` [spec]; display precedence is `title`, then `annotations.title`, then `name`. Keep descriptions tight. Each one is re-sent on every turn that includes the tool.

### Fewer, higher-level tools
**[practice, informed by docs]** Wrapping a REST API one endpoint per tool produces dozens of thin tools. The model then has to chain them, and every intermediate result flows through its context. The official `build-mcp-server` skill [docs] asks about **action surface size** ("a handful of operations versus wrapping a large API") before it picks a tool-design pattern.

| Granular tools | Workflow-level tools |
| --- | --- |
| `get_user`, `list_orders`, `get_order`, `get_invoice` | `customer_order_summary(customer_id, since)` |
| Flexible, composable, easy to implement | Fewer calls, fewer tokens, fewer wrong turns |
| Good for code mode (typed APIs with `outputSchema`) | Good for direct tool calling by chat models |

A reasonable default is a small set of tools shaped around **user intents**, each doing the multi-step work server-side and returning only what the next decision needs. Keep granular tools where composition is genuinely needed.

### Input schemas that constrain
`inputSchema` **MUST** be a valid JSON Schema object (2020-12 by default) [spec]. For a tool with no parameters, the spec recommends `{"type": "object", "additionalProperties": false}`. Make invalid calls hard to write [practice]:

- **`enum`** for closed sets (`status: "open" | "pending" | "closed"`). In Python, `Literal[...]` becomes an `enum`.
- **defaults** for the common case (`status="open"`, `limit=10`), so the simplest call is correct.
- **ranges and patterns** (`limit` 1–50, `ticket_id` matching `^T-\d{4}$`) via `Field(ge=..., le=..., pattern=...)`.
- **a description on every property**, including units and formats ("ISO date YYYY-MM-DD").
- **flat, explicit parameters** rather than a free-form `options: dict` that the model must guess.

The SDK validates arguments against the schema *before* your function runs, so many mistakes never reach your code. You still validate business rules yourself. The spec's `x-mcp-header` keyword (mirroring a primitive argument into an `Mcp-Param-*` HTTP header for routing) is useful for things like region. It SHOULD NOT be used on secrets or PII, because headers are visible to intermediaries [spec].

### Outputs: structuredContent and outputSchema
A result has unstructured `content` (text, image, audio, `resource_link`, embedded resource) and optionally `structuredContent`, any JSON value [spec]. If you declare an `outputSchema`, servers **MUST** return structured results that conform and clients **SHOULD** validate them. For backwards compatibility, a tool returning structured content SHOULD also return the serialized JSON in a text block. The Python SDK does both automatically when you return a Pydantic model or `TypedDict`.

Why bother? Code-mode hosts [docs] generate typed functions from `outputSchema`. Without one they fall back to `any` or to a second model call to extract fields, and the docs say plainly "the real fix is for server authors to provide `outputSchema`". Structured output also lets you return **compact** data the model can reason over (ids, counts, flags) instead of prose. Note that `structuredContent` is unrelated to LLM "structured outputs".

### Errors the model can act on
The spec separates two mechanisms [spec]:

| | Protocol error | Tool execution error |
| --- | --- | --- |
| Shape | JSON-RPC `error` (e.g. `-32602`) | `result` with `isError: true` |
| For | unknown tool, malformed request, server errors | API failures, invalid input values, business-rule violations |
| Seen by the model? | clients MAY pass it on; recovery unlikely | clients SHOULD pass it on so the model can self-correct |

The spec's example message is the template to copy: *"Invalid departure date: must be in the future. Current date is 08/08/2025."* It says what was wrong, states the rule, and gives the fact needed to fix it. [practice] A good error names the argument, lists the valid values or format with an example, and suggests the next step ("call `tickets_search` to find the id"). Never return a stack trace or a bare `"error"`.

> **SDK detail (mcp 2.3.0).** Raise `mcp.server.mcpserver.exceptions.ToolError("…")` for anticipated failures: the message reaches the model as `isError: true`. **Any other exception** is treated as a crash. The model sees only `Error executing tool <name>`, and the traceback goes to the server log, which keeps secrets out of results but also hides the hint. Argument-validation errors are reported in full. The SDK also returns an *unknown tool* as an `isError` result (`Unknown tool: x`), where the spec lists it as a protocol error.

### Annotations are hints, not guarantees
`ToolAnnotations` [spec] describe behaviour to clients, which may use them for UX (confirmation prompts, auto-approval of read-only tools):

| Hint | Meaning | Default |
| --- | --- | --- |
| `readOnlyHint` | does not modify its environment | `false` |
| `destructiveHint` | may perform destructive updates (only meaningful if not read-only) | `true` |
| `idempotentHint` | repeating with the same arguments has no additional effect (only if not read-only) | `false` |
| `openWorldHint` | interacts with an open world of external entities (web search) vs a closed domain (a memory store) | `true` |

The defaults are **pessimistic**, so an unannotated tool looks destructive and open-world. Set them explicitly and honestly. Clients **MUST** treat annotations as untrusted unless the server is trusted, and should never make tool-use decisions based on annotations from untrusted servers [spec].

### Idempotency and retries
**[practice]** Networks time out and agents retry. Design writes so a retry is safe:

- Make state transitions idempotent. Closing an already-closed ticket succeeds with "already closed"; it is not an error.
- For creates, accept an **idempotency key** (the client's request id) and return the original object on a repeat.
- Advertise it with `idempotentHint: true`, and say it in the description.

### Big results: paginate, truncate, summarise
Spec-level pagination (`cursor`/`nextCursor`) covers *list methods* like `tools/list`. Inside a tool, paging is **your own interface** [practice]: a `limit` with a sane default and maximum, an opaque `cursor`, and a `total` or `has_more`. Return summaries by default and full objects on request, and when you truncate, **say so and say how to get the rest**. *Client Best Practices* [docs] recommends hosts validate and truncate output before it reaches the model, and notes that passing large intermediate results through the model "compounds" context cost. A server that returns 50 KB of JSON because "the client can trim it" is wasting everyone's budget. Measure: roughly 4 characters per token is a good enough estimate for budgeting.

### Stable, deterministic tool lists
**[spec]** Servers **SHOULD** return tools in a deterministic order, so clients can cache the list and LLM **prompt caches** hit. The `tools/list` set **MUST NOT** vary per connection or as a side effect of other requests, but **MAY** vary by the authorization on the request. When it really changes, emit `notifications/tools/list_changed` to `subscriptions/listen` streams. **[docs]** Most providers cache the prompt prefix including the `tools` array. Adding, removing or re-sorting tools mid-conversation invalidates that cache, and the miss can cost more than the tokens you saved. So don't build your list from a `set()` or a hash map with randomised iteration, and don't reshuffle tools per request.

### State: explicit handles, not sessions
2026-07-28 removed protocol sessions (2025-era Streamable HTTP had `Mcp-Session-Id`), so a server cannot rely on per-connection state to relate one call to the next. The spec's non-normative **Stateful Tools** guidance: return an **explicit handle** from a creation tool (`create_basket` → `{"basket_id": "bsk_a1b2c3"}`), accept it on later calls, and let the model carry it forward. Design points [spec guidance]:

- **Authorization**: on authenticated servers a handle is a name, not a capability, so check the caller against it on every call. On unauthenticated servers it is a bearer token: use high entropy (UUIDv4) and a bounded lifetime.
- **Opacity**: don't encode internal structure that invites guessing.
- **Lifetime**: state the retention policy in the creation tool's description.
- **Expiry errors**: an unknown or expired handle returns a tool execution error that says so, so the model can create a new one.

### Security is part of the design
**[spec]** Servers **MUST** validate all tool inputs, implement proper access controls, rate-limit tool invocations and sanitize tool outputs. Clients SHOULD confirm sensitive operations, show inputs before calling, validate results, time out calls and log usage. **[practice]** Apply **least privilege**: expose `tickets_close`, not `run_sql`. Scope credentials to what the tools need, keep secrets out of arguments and results, and remember that your output is untrusted input to the model and possibly to other servers (prompt injection, module 6).

### Getting help from agent skills
The official docs [docs] point to the `mcp-server-dev` plugin (`build-mcp-server`, `build-mcp-app`, `build-mcpb`). Its entry skill interrogates your use case before writing code: what it connects to, who will use it, the action-surface size, interaction needs (plain text, elicitation or UI) and upstream auth. It then recommends a deployment path. Remote Streamable HTTP is the default for cloud APIs; MCP Apps add widgets; MCPB bundles a local server with its runtime; local stdio is for prototyping. Afterwards the docs say to "iterate on tool descriptions and error handling", which is what this lesson is about.

## Key points
- The model sees only name, title, description and schemas: write them as **prompts** that say what, when, returns and limits.
- **[spec]** Names: 1–128 chars of `A-Za-z0-9_-.`, case-sensitive, unique per server. **Namespace** them (`tickets_search`), because aggregating clients see collisions.
- Prefer **fewer, intent-level tools**. Constrain inputs with **enums, defaults, ranges, patterns and per-property descriptions**; no-arg tools use `additionalProperties: false`.
- Declare an **`outputSchema`** and return `structuredContent` (plus serialized text). Servers MUST conform to it, and code-mode hosts turn it into types.
- Anticipated failures are **`isError: true` results with actionable text** (what, rule, example, next step). In the Python SDK, raise `ToolError`, because other exceptions are masked.
- **Annotations** (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) default pessimistically and are untrusted hints. Set them explicitly and honestly.
- Keep results small: **limit + cursor + summaries**. When truncating, say so and how to get more.
- **Deterministic tool order** keeps client caches and LLM prompt caches warm (spec SHOULD).
- No sessions in 2026-07-28: carry state in **explicit, opaque, expiring handles** whose lifetime is documented and whose expiry error tells the model to recreate them.

## Pitches
### What makes a tool easy for an LLM to use?
I design tools as if the model were a new colleague who can only read the docs. The name is namespaced and says the intent, like tickets_search. The description says what it does, when to use it instead of its siblings, and what it returns. Inputs use enums, defaults and described fields so wrong calls are hard to write. Outputs are small and structured with an output schema. And when something goes wrong, the error says exactly how to fix the call, so the model can recover on its own.

### Why should tool errors be results, not exceptions?
MCP has two error channels. Protocol errors are for broken requests, like an unknown method, and the model rarely recovers from those. Tool execution errors come back as a normal result with isError true, and the spec tells clients to show them to the model so it can self-correct. So for a bad date or an unknown ticket id, I return text like "created_after must be YYYY-MM-DD, for example 2026-03-01". In the Python SDK that means raising ToolError, because other exceptions are masked.

### How do you keep state without sessions?
The 2026-07-28 protocol removed sessions, so I can't hide state in the connection. Instead, a creation tool returns an explicit handle, an opaque high-entropy id like trg_ followed by a UUID. Every later call takes that handle as an argument and the server looks the state up in its store, which also works across replicas. I authorize the caller against the handle on every call, write its lifetime into the description, and when it has expired the error tells the model to start a new one.

## Interview
### A model keeps calling the wrong tool on your server. What do you look at first?
The definitions, because that is all the model sees. Are the names distinct and namespaced, or are there `search`/`query`/`do` style names that collide with other servers? Does each description say *when* to use it versus its siblings and what it returns? Are there overlapping tools that should be merged into one intent-level tool? Then check the token budget: if the host is doing progressive discovery, are the descriptions keyword-rich enough to be found? Finally, look at transcripts. If the model picks the right tool but passes bad arguments, the fix is in the schema (enums, defaults, property descriptions) and in actionable error messages.

### When would you return `isError: true` versus a JSON-RPC error?
JSON-RPC errors are **protocol errors**: unknown tool, a request that doesn't satisfy the `CallToolRequest` schema, internal server failures. The spec notes models are unlikely to recover from these, and clients only MAY show them. **Tool execution errors** use a normal result with `isError: true` for API failures, invalid argument values and business-rule violations. Clients SHOULD feed them to the model for self-correction, so the text must be actionable. Gotcha: in the Python SDK only `ToolError` (and argument-validation failures) pass their message through. A plain `ValueError` becomes the opaque `Error executing tool X`, and the SDK reports unknown tools as `isError` results, unlike the spec's classification.

### What are tool annotations, and can a client rely on them?
`ToolAnnotations` carries `title`, `readOnlyHint` (default false), `destructiveHint` (default true, meaningful only when not read-only), `idempotentHint` (default false, same condition) and `openWorldHint` (default true). Hosts use them for UX, such as auto-approving read-only tools or asking for confirmation before destructive ones. But they are **hints**. The spec says clients MUST treat them as untrusted unless the server is trusted, and should never base tool-use decisions on annotations from untrusted servers. A malicious server can label `delete_everything` read-only. As a server author, set them explicitly, because the defaults make every tool look destructive and open-world.

### How do you handle a tool whose natural result is 10 MB?
Never return it whole. Return a page: a `limit` with a modest default and hard maximum, an opaque `cursor`, a `total` or `has_more`, and compact summaries rather than full records. Offer a separate `get` tool or an `include_*` flag for details. If you must truncate text, append an explicit marker saying how much was cut and which call retrieves the rest. Consider returning a `resource_link` to the full artifact instead of inlining it. Declare an `outputSchema` so code-mode hosts can filter in a sandbox. This matters because every token you return is context the model pays for on every later turn, and hosts are told to truncate anyway.

### Why does the spec care about the *order* of tools in `tools/list`?
Deterministic ordering (a SHOULD) lets clients cache the list and lets LLM prompt caching work. Providers cache the prompt prefix, including the `tools` array, so if your server returns the same tools in a different order on the next request (say, built from a Python `set` under hash randomisation), the host's prompt prefix changes and the cache misses. *Client Best Practices* adds that changing the tools array mid-conversation can cost more than the tokens saved. Related rules: the list MUST NOT vary per connection or as a side effect of other calls, MAY vary by authorization, and real changes are announced with `notifications/tools/list_changed`.

### Tricky: "We need sessions, so we'll key state on the connection." What's wrong with that in 2026-07-28?
2026-07-28 has no protocol session. Requests are self-contained, and over Streamable HTTP consecutive calls may hit different server instances, so connection-keyed state silently breaks. The tools spec also forbids `tools/list` from varying per connection. The sanctioned pattern is an **explicit handle** returned by a creation tool and passed back as an argument, stored in a shared store. Then handle the details the spec calls out: authorization on every call, opaque ids, a documented lifetime and an actionable expiry error.

## Glossary
- Tool definition | 工具定义 | The `name`, `title`, `description`, `inputSchema`, `outputSchema` and `annotations` a server advertises in `tools/list`.
- Namespacing | 命名空间前缀 | Prefixing tool names with a service identifier (e.g. `tickets_search`) to avoid collisions when hosts aggregate servers.
- Output schema | 输出模式（outputSchema） | A JSON Schema for a tool's `structuredContent`; servers MUST conform and clients SHOULD validate.
- Tool execution error | 工具执行错误 | A result with `isError: true` whose text lets the model correct its call; distinct from a JSON-RPC protocol error.
- Tool annotations | 工具注解 | Untrusted behavioural hints: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` (plus `title`).
- Idempotency | 幂等性 | The property that repeating a call with the same arguments has no additional effect, making retries safe.
- Opaque cursor | 不透明游标 | A server-issued token for "the next page" that clients pass back without interpreting.
- State handle | 状态句柄 | An explicit, opaque id returned by a creation tool and passed back on later calls, replacing session state.
- Progressive discovery | 渐进式发现 | A host pattern that searches tool names and descriptions first and loads full definitions only when needed.
- Prompt caching | 提示缓存 | Provider-side reuse of an unchanged prompt prefix (including the tools array), which deterministic tool order preserves.

```python
from mcp.server import MCPServer

bad = MCPServer("helpdesk-bad")


@bad.tool()
def query(q: str, opts: dict | None = None) -> str:
    """Query."""
    opts = opts or {}
    rows = [t for t in TICKETS.values() if q.lower() in t["title"].lower()]
    if "status" in opts:
        if opts["status"] not in ("open", "pending", "closed"):
            raise ValueError(f"bad status {opts['status']}")
        rows = [t for t in rows if t["status"] == opts["status"]]
    if "since" in opts:
        since = date.fromisoformat(opts["since"])          # raises ValueError on 03/01/2026
        rows = [t for t in rows if date.fromisoformat(t["created"]) >= since]
    return json.dumps(rows)                                    # everything, bodies included


@bad.tool()
def do(action: str, id: str) -> str:
    if action not in ("close", "reopen"):
        raise ValueError("bad action")
    if TICKETS[id]["status"] == "closed" and action == "close":
        raise ValueError("already closed")                     # retries blow up
    TICKETS[id]["status"] = "closed" if action == "close" else "open"
    return "ok"


@bad.tool()
def getTicketData2(x: str) -> dict:
    """Gets data."""
    return TICKETS[x]


print("defined", bad.name, "with tools: query, do, getTicketData2")
```

```python
import base64
import hashlib
from typing import Annotated, Literal

from pydantic import BaseModel, Field

from mcp.server.mcpserver.exceptions import ToolError
from mcp_types import ToolAnnotations

Status = Literal["open", "pending", "closed"]
Priority = Literal["low", "normal", "high", "urgent"]


class TicketSummary(BaseModel):
    id: str
    title: str
    status: Status
    priority: Priority
    customer: str
    created: str


class SearchPage(BaseModel):
    items: list[TicketSummary]
    total: int = Field(description="Number of tickets matching the filters")
    next_cursor: str | None = Field(description="Pass back as `cursor` for the next page; null when done")


class TicketDetail(TicketSummary):
    body: str | None = Field(description="Ticket text, truncated to 400 characters unless include_body=True")
    body_truncated: bool


class CloseResult(BaseModel):
    id: str
    status: Status
    changed: bool = Field(description="False if the ticket was already closed (safe to retry)")


def parse_iso_date(value: str, field: str) -> date:
    try:
        return date.fromisoformat(value)
    except ValueError:
        raise ToolError(f"Invalid {field} {value!r}: use an ISO date YYYY-MM-DD, e.g. 2026-03-01.") from None


def make_cursor(offset: int, filters: str) -> str:
    return base64.urlsafe_b64encode(json.dumps({"o": offset, "f": filters}).encode()).decode()


def read_cursor(cursor: str, filters: str) -> int:
    try:
        data = json.loads(base64.urlsafe_b64decode(cursor.encode()))
    except Exception:
        raise ToolError("Invalid cursor: pass back next_cursor exactly as returned, or omit it to start over.") from None
    if data["f"] != filters:
        raise ToolError("This cursor belongs to a search with different filters. Repeat the search without a cursor.")
    return data["o"]


good = MCPServer("helpdesk")
READ_ONLY = ToolAnnotations(readOnlyHint=True, openWorldHint=False)


@good.tool(title="Search tickets", annotations=READ_ONLY)
def tickets_search(
    status: Annotated[Status, Field(description="Ticket status to match")] = "open",
    priority: Annotated[Priority | None, Field(description="Only this priority; omit for any")] = None,
    customer: Annotated[str | None, Field(description="Exact customer name, e.g. Acme")] = None,
    created_after: Annotated[str | None, Field(description="ISO date YYYY-MM-DD; only tickets created on/after it")] = None,
    limit: Annotated[int, Field(ge=1, le=50, description="Page size (1-50)")] = 10,
    cursor: Annotated[str | None, Field(description="next_cursor from a previous page of the same search")] = None,
) -> SearchPage:
    """Search helpdesk tickets by status, priority, customer and creation date.

    Returns at most `limit` short summaries (no ticket text) plus `total` and `next_cursor`.
    Use tickets_get for the full text of one ticket, and tickets_close to close it.
    """
    since = parse_iso_date(created_after, "created_after") if created_after else None
    filters = json.dumps([status, priority, customer, created_after])
    offset = read_cursor(cursor, filters) if cursor else 0
    rows = [t for t in TICKETS.values() if t["status"] == status
            and (priority is None or t["priority"] == priority)
            and (customer is None or t["customer"] == customer)
            and (since is None or date.fromisoformat(t["created"]) >= since)]
    page = rows[offset:offset + limit]
    more = offset + limit < len(rows)
    return SearchPage(items=[TicketSummary(**{k: t[k] for k in TicketSummary.model_fields}) for t in page],
                      total=len(rows), next_cursor=make_cursor(offset + limit, filters) if more else None)


@good.tool(title="Get ticket", annotations=READ_ONLY)
def tickets_get(
    ticket_id: Annotated[str, Field(pattern=r"^T-\d{4}$", description="Ticket id like T-0042")],
    include_body: Annotated[bool, Field(description="Return the full text instead of the first 400 chars")] = False,
) -> TicketDetail:
    """Get one ticket with its text. Find ids with tickets_search."""
    t = TICKETS.get(ticket_id)
    if t is None:
        raise ToolError(f"Ticket {ticket_id} does not exist. Use tickets_search to find valid ids.")
    body = t["body"] if include_body else t["body"][:400]
    return TicketDetail(**{k: t[k] for k in TicketSummary.model_fields}, body=body,
                        body_truncated=len(body) < len(t["body"]))


@good.tool(title="Close ticket",
           annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=False, idempotentHint=True,
                                       openWorldHint=False))
def tickets_close(
    ticket_id: Annotated[str, Field(pattern=r"^T-\d{4}$", description="Ticket id like T-0042")],
    resolution: Annotated[Literal["fixed", "wont_fix", "duplicate"], Field(description="Why it is closed")],
) -> CloseResult:
    """Close a ticket with a resolution. Idempotent: closing a closed ticket succeeds with changed=false."""
    t = TICKETS.get(ticket_id)
    if t is None:
        raise ToolError(f"Ticket {ticket_id} does not exist. Use tickets_search to find valid ids.")
    changed = t["status"] != "closed"
    t["status"], t["resolution"] = "closed", resolution
    return CloseResult(id=ticket_id, status="closed", changed=changed)


print("defined", good.name, "with tools: tickets_search, tickets_get, tickets_close")
```

### 2. A tool-definition linter
A heuristic linter makes the guidance measurable. It only reads what a client sees, the `tools/list` result. Each rule is labelled with its source: spec rules (`[spec]`) and general practice (`[practice]`).

```python
import re

from mcp import Client

NAME_RE = re.compile(r"^[A-Za-z0-9_.\-]{1,128}$")
CLOSED_SET_HINTS = ("status", "priority", "action", "mode", "type", "kind", "resolution", "level")


def lint_tool(tool, prefixes: set[str]) -> list[tuple[int, str]]:
    """Return (penalty, message) pairs for one tool definition."""
    findings = []
    if not NAME_RE.match(tool.name):
        findings.append((15, "[spec] name uses characters outside A-Za-z0-9_-. or is too long"))
    if len(prefixes) > 1 or "_" not in tool.name:
        findings.append((5, "[practice] no shared service prefix (namespace your tools)"))
    if tool.name.split("_")[-1] in {"do", "run", "query", "process", "data", "data2"} or tool.name in {"do", "query"}:
        findings.append((10, "[practice] generic name says nothing about intent"))
    desc = (tool.description or "").strip()
    if len(desc) < 40:
        findings.append((15, f"[practice] description too short ({len(desc)} chars) to tell the model when to use it"))
    props = tool.input_schema.get("properties", {})
    for pname, schema in props.items():
        if "description" not in schema:
            findings.append((4, f"[practice] parameter '{pname}' has no description"))
        typed = any(k in schema for k in ("type", "enum", "anyOf", "$ref", "const"))
        if not typed or (schema.get("type") == "object" and "properties" not in schema) or any(
                s.get("type") == "object" and "properties" not in s for s in schema.get("anyOf", [])):
            findings.append((8, f"[practice] parameter '{pname}' is an untyped/free-form object"))
        is_string = schema.get("type") == "string" or any(s.get("type") == "string" for s in schema.get("anyOf", []))
        has_enum = "enum" in schema or any("enum" in s for s in schema.get("anyOf", []))
        if is_string and not has_enum and any(h in pname.lower() for h in CLOSED_SET_HINTS):
            findings.append((6, f"[practice] '{pname}' looks like a closed set but has no enum"))
    if not tool.output_schema:
        findings.append((10, "[spec/docs] no outputSchema (code-mode hosts can't type the result)"))
    if not tool.annotations or tool.annotations.read_only_hint is None:
        findings.append((8, "[spec] annotations missing: defaults say destructive + open-world"))
    return findings


async def lint_server(server) -> int:
    async with Client(server) as client:
        tools = (await client.list_tools()).tools
        wire = json.dumps([t.model_dump(by_alias=True, exclude_none=True, mode="json") for t in tools])
    prefixes = {t.name.split("_")[0] for t in tools}
    total = 0
    print(f"== {server.name}: {len(tools)} tools, ~{len(wire) // 4} tokens of definitions")
    for t in tools:
        findings = lint_tool(t, prefixes)
        score = max(0, 100 - sum(p for p, _ in findings))
        total += score
        print(f"  {t.name:16} score {score:3}")
        for _, msg in findings:
            print(f"      - {msg}")
    return total // len(tools)


print("average bad :", await lint_server(bad))
print()
print("average good:", await lint_server(good))
```

The good set costs *more* tokens of definitions. That is the right trade: a few hundred tokens of precise schema save whole wasted round-trips. What you must avoid is spending tokens on *results* (section 4).

### 3. Errors that let an agent recover
A real model reads the error text and tries again. This scripted agent stands in for it: it can only fix what the message explains. It knows three repairs: reformat a date when told the format, pick the closest valid value when the valid values are listed, and stop otherwise.

```python
import difflib


def repair(args: dict, error: str) -> dict | None:
    """Return corrected arguments, or None if the error gives nothing to act on."""
    fixed = json.loads(json.dumps(args))
    flat = fixed.get("opts", fixed)
    if "YYYY-MM-DD" in error:
        for key, value in flat.items():
            if isinstance(value, str) and re.fullmatch(r"\d\d/\d\d/\d{4}", value):
                m, d, y = value.split("/")
                flat[key] = f"{y}-{m}-{d}"
                return fixed
    choices = re.findall(r"'([a-z_]+)'", error.split("Input should be", 1)[-1]) if "Input should be" in error else []
    if choices:
        for key, value in flat.items():
            if isinstance(value, str) and value not in choices:
                close = difflib.get_close_matches(value.lower(), choices, n=1)
                if close:
                    flat[key] = close[0]
                    return fixed
    return None


async def agent(server, tool: str, args: dict, max_tries: int = 4):
    async with Client(server) as client:
        for attempt in range(1, max_tries + 1):
            r = await client.call_tool(tool, args)
            if not r.is_error:
                summary = r.structured_content or {}
                total = summary.get("total", f"{len(json.loads(r.content[0].text))} rows")
                print(f"  try {attempt}: OK   {json.dumps(args)} -> total={total}")
                return
            message = r.content[0].text.replace("\n", " ")[:150]
            print(f"  try {attempt}: ERR  {json.dumps(args)}\n           model reads: {message!r}")
            args = repair(args, r.content[0].text)
            if args is None:
                print("           nothing actionable in that message -> agent gives up")
                return


print("bad server (ValueError -> masked by the SDK):")
await agent(bad, "query", {"q": "", "opts": {"status": "Open", "since": "03/01/2026"}})
print("\ngood server (enum + ToolError with format and example):")
await agent(good, "tickets_search", {"status": "Open", "created_after": "03/01/2026"})
```

Two things happened on the bad server. The model never learned *what* was wrong, because the SDK hides plain exceptions. And even the original message ("bad status Open") would not have listed the valid values. On the good server the enum is validated before the function runs, and the date error carries the format and an example.

### 6. Deterministic order keeps caches warm
The SDK lists tools in registration order. That is deterministic only if *your* registration order is. Here a server registers tools by iterating a `set`, a classic mistake. Python randomises string hashing per process, so two "replicas" (two processes with different `PYTHONHASHSEED`) advertise different orders. A different `tools` array means a different prompt prefix, and the provider's prompt cache misses.

```python
import subprocess
import sys
import textwrap

SNIPPET = textwrap.dedent('''
    import anyio, hashlib, json, sys
    from mcp import Client
    from mcp.server import MCPServer
    names = {"tickets_search", "tickets_get", "tickets_close", "tickets_assign", "tickets_comment"}
    srv = MCPServer("helpdesk")
    for name in (sorted(names) if sys.argv[1] == "sorted" else names):
        srv.add_tool(lambda: "ok", name=name, description=f"{name} tool")
    async def main():
        async with Client(srv) as c:
            tools = [t.model_dump(by_alias=True, exclude_none=True, mode="json") for t in (await c.list_tools()).tools]
        print(hashlib.sha256(json.dumps(tools).encode()).hexdigest()[:12], [t["name"] for t in tools])
    anyio.run(main)
''')

for mode in ("set", "sorted"):
    print(f"registration from a {mode}:")
    for seed in ("1", "2"):
        out = subprocess.run([sys.executable, "-c", SNIPPET, mode], capture_output=True, text=True,
                             env={"PYTHONHASHSEED": seed, "PATH": ""}).stdout.strip()
        print(f"  replica with PYTHONHASHSEED={seed}: {out}")
```

### 7. State without sessions: explicit handles
A triage workflow spans several calls. Instead of hiding the queue in the connection, `triage_start` returns an opaque, high-entropy handle with a lifetime **stated in its description**. Every later call passes it back. We use two *separate* client connections to show that nothing depends on the connection. Then we let the handle expire and watch the error tell the agent how to recover.

```python
import time
import uuid

TRIAGE: dict[str, dict] = {}          # in production: a shared store (Redis, DB) so any replica can serve
TTL_SECONDS = 15 * 60
clock = {"skew": 0.0}                 # lets the notebook fast-forward time


def now() -> float:
    return time.time() + clock["skew"]


@good.tool(title="Start triage", annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=False,
                                                             idempotentHint=False, openWorldHint=False))
def triage_start(priority: Annotated[Priority, Field(description="Queue to triage")] = "urgent") -> dict[str, str | int]:
    """Start a triage session over open tickets of one priority.

    Returns a triage_id to pass to triage_next. Sessions expire after 15 minutes of inactivity;
    if a triage_id is rejected as expired, call triage_start again.
    """
    queue = [t["id"] for t in TICKETS.values() if t["status"] == "open" and t["priority"] == priority]
    triage_id = f"trg_{uuid.uuid4().hex}"
    TRIAGE[triage_id] = {"queue": queue, "pos": 0, "touched": now()}
    return {"triage_id": triage_id, "queued": len(queue)}


@good.tool(title="Next ticket in triage", annotations=READ_ONLY)
def triage_next(triage_id: Annotated[str, Field(description="Handle returned by triage_start")]) -> dict[str, str | int]:
    """Return the next ticket id in a triage session and how many remain."""
    state = TRIAGE.get(triage_id)
    if state is None or now() - state["touched"] > TTL_SECONDS:
        TRIAGE.pop(triage_id, None)
        raise ToolError(f"Triage session {triage_id[:12]}... is unknown or expired (sessions last 15 minutes). "
                        "Call triage_start to begin a new one.")
    state["touched"] = now()
    if state["pos"] >= len(state["queue"]):
        return {"ticket_id": "", "remaining": 0}
    tid = state["queue"][state["pos"]]
    state["pos"] += 1
    return {"ticket_id": tid, "remaining": len(state["queue"]) - state["pos"]}


async with Client(good) as conn_a:
    started = (await conn_a.call_tool("triage_start", {"priority": "urgent"})).structured_content
    print("connection A: triage_start ->", started)
handle = started["triage_id"]

async with Client(good) as conn_b:                     # a different connection (or replica)
    for _ in range(2):
        print("connection B: triage_next ->", (await conn_b.call_tool("triage_next", {"triage_id": handle})).structured_content)

    clock["skew"] += 16 * 60                           # 16 minutes pass
    expired = await conn_b.call_tool("triage_next", {"triage_id": handle})
    print("\nafter 16 min ->", expired.is_error, expired.content[0].text)
    if "triage_start" in expired.content[0].text:      # the agent follows the instruction in the error
        fresh = (await conn_b.call_tool("triage_start", {"priority": "urgent"})).structured_content
        print("agent recovers: new handle", fresh["triage_id"][:12] + "...", "| queued", fresh["queued"])
```
