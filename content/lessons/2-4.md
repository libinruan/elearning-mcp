## Summary
Every MCP feature is built from three **message patterns**: request/response, multi round-trip requests, and subscribe/notify. On top of them sit cross-cutting **utilities** that real systems need on day one. **Cancellation** stops abandoned work. On stdio that is `notifications/cancelled`, on HTTP the client closes the stream, and timeouts should trigger it. **Progress** lets a long request report how far it has got through `progressToken` and `notifications/progress`. **Pagination** splits large lists with opaque cursors. **Logging** sends structured log lines per request through `io.modelcontextprotocol/logLevel`. Logging is **deprecated** in 2026-07-28, in favour of stderr and OpenTelemetry. The notebook exercises each one against real servers: progress callbacks, a timeout watchdog, cancelling over stdio, paging a 7-tool server three at a time, and opting in to logs.

## Lesson
### The message patterns, recapped
The patterns page fixes who may say what. *Every interaction begins with the client.* The client sends requests and notifications. The server answers each request with a response, optionally preceded by notifications **scoped to that request**. *Servers **MUST NOT** initiate JSON-RPC requests, and clients do not send JSON-RPC responses.*

| Pattern | Shape | Used for |
| --- | --- | --- |
| **Request and response** | request → (scoped notifications) → result or error | almost everything; progress and log messages ride here |
| **Multi round-trip requests (MRTR)** | request → `InputRequiredResult` → retry with `inputResponses` → result | elicitation, sampling and roots without server-initiated requests (lesson 5.3) |
| **Subscribe and notify** | `subscriptions/listen` → `notifications/subscriptions/acknowledged` → tagged change notifications | list changes, resource updates (lesson 3.4) |

Transports carry every pattern unchanged, because patterns are expressed purely as requests, responses and notifications. A future revision that adds a pattern defines it on this page and needs no transport changes. The utilities below all live inside the first pattern.

### Cancellation
A client **SHOULD** cancel a request it no longer needs. On stdio it sends:

```json
{"jsonrpc": "2.0", "method": "notifications/cancelled",
 "params": {"requestId": "123", "reason": "User requested cancellation"}}
```

`requestId` is the id of a request **the client previously issued**, and `reason` is optional text to log or display. How the signal travels depends on the transport:

| Transport | Cancellation signal |
| --- | --- |
| **stdio** | the client **MUST** send `notifications/cancelled` referencing the request id (there is no per-request stream) |
| **Streamable HTTP** | **closing the SSE response stream**; the server **MUST** treat the disconnect as cancellation, and no notification is required or expected |

**Server-sent cancellation exists for one purpose only.** A server **MUST** send `notifications/cancelled` referencing a `subscriptions/listen` request id when it tears down that subscription stream, and **MUST NOT** send it for anything else.

**Behaviour requirements.**

- Cancellations **MUST** only reference requests that the client issued and believes are still in progress.
- A server receiving one **SHOULD** stop processing, free associated resources, and not send a response.
- A server **MAY** ignore it if the request is unknown, already completed, or not cancellable.
- The client **SHOULD** ignore any response that arrives afterwards.
- *Invalid* cancellations (unknown ids, completed requests, malformed notifications) **SHOULD** be ignored. That keeps notifications fire-and-forget.
- Both sides **SHOULD** log cancellation reasons, and UIs **SHOULD** show that cancellation was requested.

**Races are normal.** Network latency means a cancellation may arrive after processing finished, even after the response was sent. *Both parties **MUST** handle these race conditions gracefully.* Practical consequence: a cancel is a request to stop, not a guarantee that nothing happened. Side-effecting tools still need idempotency or compensation.

**Timeouts.** Implementations **SHOULD** set timeouts on all sent requests, to prevent hung connections and resource exhaustion. When a timeout fires, the sender **SHOULD** cancel the request (send the notification on stdio, close the stream on HTTP) and stop waiting. SDKs **SHOULD** allow per-request timeout configuration. Implementations **MAY** reset the timeout clock when a progress notification arrives for the request, since that shows work is happening, but **SHOULD** still enforce a **maximum timeout** regardless of progress, to limit a misbehaving peer.

### Progress
Progress is opt-in, per request. A client that wants updates puts a `progressToken` (string or integer, **unique across all active requests**, chosen however the client likes) in the request's `_meta`:

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "index_repo", "arguments": {}, "_meta": {"progressToken": "abc123", "...": "envelope"}}}
```

The server **MAY** then send notifications carrying the same token:

```json
{"jsonrpc": "2.0", "method": "notifications/progress",
 "params": {"progressToken": "abc123", "progress": 50, "total": 100, "message": "Reticulating splines..."}}
```

| Field | Rule |
| --- | --- |
| `progressToken` | the token from the request |
| `progress` | **MUST increase** with each notification, even if the total is unknown; may be a float |
| `total` | optional; may be a float; omit it if unknown |
| `message` | optional; **SHOULD** be human-readable progress information |

Progress notifications **MUST** only reference tokens from an active request whose operation is still in progress, and they **MUST** stop after completion. A server receiving a token **MAY** send none at all, may choose any frequency, and may omit `total`. Both sides **SHOULD** track active tokens and **rate-limit** to avoid flooding. On Streamable HTTP, progress forces the response to be an SSE stream, because the notifications must arrive before the final result on the same request's stream.

### Pagination
List operations can return large result sets, so MCP paginates them with an **opaque cursor**, not page numbers:

- The **cursor** is an opaque string representing a position. The **page size is chosen by the server**, and clients **MUST NOT** assume a fixed size.
- A response includes the current page and, if more results exist, `nextCursor`.
- The client continues by sending the same method with `params.cursor` set to that value (plus the usual `_meta` envelope).

```json
{"jsonrpc": "2.0", "id": "123",
 "result": {"resultType": "complete", "resources": ["..."], "nextCursor": "eyJwYWdlIjogM30=",
            "ttlMs": 300000, "cacheScope": "public"}}
```

Paginated operations are **`tools/list`, `resources/list`, `resources/templates/list` and `prompts/list`**.

| Side | Guidance |
| --- | --- |
| Servers **SHOULD** | provide **stable cursors** and handle invalid cursors gracefully; an invalid cursor **SHOULD** produce `-32602` (Invalid params) |
| Clients **SHOULD** | treat a **missing** `nextCursor` as the end, and support both paginated and non-paginated flows |
| Clients **MUST** | treat cursors as **opaque**: never parse, modify or interpret them; decide only on whether a non-null value was provided. An **empty string is a valid cursor** and **MUST NOT** be treated as the end. |

Why opaque? It lets the server change its strategy (offsets, keyset pagination, snapshot ids, signed tokens) without breaking clients, and it stops clients from fabricating positions. Combined with the 2026-07-28 rule that servers **SHOULD** return `tools/list` in a **deterministic order**, stable cursors make list results cacheable (`ttlMs`/`cacheScope`) and friendlier to LLM prompt caches.

### Logging (deprecated)
> **Deprecated in 2026-07-28 (SEP-2577).** Logging stays in the spec for at least twelve months under the feature-lifecycle policy. New implementations **SHOULD NOT** adopt it. Existing ones **SHOULD** migrate to **logging to `stderr`** for stdio transports, or to **OpenTelemetry** for structured observability.

You will still meet it in existing servers and interviews, and its 2026-07-28 form shows how a feature becomes stateless. A server that emits logs **MUST** declare the `logging` capability. Levels follow syslog (RFC 5424): `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert`, `emergency`.

**What changed.** In 2025-11-25 a client called `logging/setLevel` once and the session remembered it. In 2026-07-28 **`logging/setLevel` is removed**, because there is no session to remember it. The level is **per request** instead:

- To receive logs for a request, the client includes `io.modelcontextprotocol/logLevel` in that request's `_meta`.
- The server **MUST NOT** emit `notifications/message` for a request without this field.
- With the field present, the server **MAY** send `notifications/message` at or above that level, on that request's response stream, **before** the final response.
- `notifications/message` is **request-scoped**. It **MUST NOT** go on a `subscriptions/listen` stream or any other stream.

```json
{"jsonrpc": "2.0", "method": "notifications/message",
 "params": {"level": "error", "logger": "database",
            "data": {"error": "Connection failed", "details": {"host": "localhost", "port": 5432}}}}
```

`data` is any JSON-serialisable value and `logger` an optional name. An unrecognised `logLevel` **SHOULD** be rejected with `-32602`, and internal errors with `-32603`. Log messages **MUST NOT** contain credentials or secrets, personal identifying information, or internal details that could aid attacks. Servers **SHOULD** rate-limit, validate data fields, control access to logs, and use consistent logger names.

**Why deprecate it?** Protocol-level logging duplicated what mature tooling already does better. On stdio, stderr is a free, standard log channel that the host can capture. For remote servers, OpenTelemetry gives traces, metrics and logs correlated across services, and MCP already carries W3C `traceparent`/`tracestate`/`baggage` in `_meta` (lesson 2.1). Removing protocol-level logging also removes a source of accidental data leaks into the model's context.

## Key points
- Three patterns: **request/response**, **MRTR**, **subscribe/notify**. Every interaction starts with the client, and servers never initiate requests.
- Cancel with `notifications/cancelled {requestId, reason?}` on **stdio**. On **Streamable HTTP**, **close the response stream**. Servers send `notifications/cancelled` **only** to tear down a `subscriptions/listen` stream.
- On cancellation the server should stop, free resources and **not respond**. Unknown or completed ids are ignored, and both sides must tolerate the cancel-after-completion race.
- Set **timeouts** on every request, cancel when they fire, optionally reset on progress, but always enforce a **maximum**.
- Progress is opt-in through `_meta.progressToken` (unique among active requests). `notifications/progress` carries `progress` (**strictly increasing**), optional `total` and `message`, and stops at completion.
- Pagination uses **opaque cursors** and **server-chosen page sizes**: `nextCursor` in results, `cursor` in params. Missing `nextCursor` = end, while `""` is a valid cursor. Invalid cursor → `-32602`.
- Paginated methods: `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list`.
- Logging is **deprecated**. `logging/setLevel` was **removed** in favour of per-request `io.modelcontextprotocol/logLevel`, with no level meaning no `notifications/message`. Use **stderr** or **OpenTelemetry** instead.

## Pitches
### How does cancellation work in MCP?
It depends on the transport. On stdio, the client sends a `notifications/cancelled` notification with the id of the request it's abandoning and optionally a reason. On Streamable HTTP each request has its own response stream, so the client just closes it, and the server must treat the disconnect as a cancel. Either way the server should stop work, free resources and send nothing more for that request. Cancels can race with completion, so both sides have to tolerate that.

### How would you report progress for a long-running tool?
The client opts in by putting a `progressToken` in the request's `_meta`. While the tool runs, the server sends `notifications/progress` with that token, a progress value that must keep increasing, an optional total and a human-readable message. In the Python SDK that's just `ctx.report_progress`. On HTTP it turns the response into an SSE stream. On the client I'd show it in the UI and use it to extend my idle timeout, while still enforcing a hard maximum.

### Why is MCP logging deprecated, and what do you use instead?
It duplicated better tools. Since 2026-07-28 a client could only get server logs by opting in per request with a `logLevel` in `_meta`, and the old `logging/setLevel` call is gone. The spec now says new implementations shouldn't adopt it. For stdio servers I log to stderr, which the host can capture. For remote servers I use OpenTelemetry, with trace context propagated in `_meta`, so a tool call shows up in the same distributed trace as the agent that made it.

## Interview
### Design the timeout policy for an MCP client calling a tool that may run for minutes.
Every request gets a timeout, configurable per request as the spec asks SDKs to allow. For long tools I request progress with a unique `progressToken` and use **two clocks**: an *idle* timeout (say 30 s) that resets whenever a `notifications/progress` for that token arrives, and a *hard maximum* (say 10 min) that progress never extends. The spec explicitly recommends that maximum, so a server that emits progress forever cannot hold the request open indefinitely. When either fires, I **cancel properly**: `notifications/cancelled` with a reason on stdio, closing the stream on HTTP. Then I ignore any late response and surface a clear error. For work that really outlives a connection, I'd use the Tasks extension instead of stretching timeouts.

### A client sends `notifications/cancelled` for request 42, but the server had already sent the result. What should each side do?
Nothing special. This is the race the spec calls out. The server **MAY** ignore cancellations for completed or unknown requests and must not error, and invalid cancellations **SHOULD** be ignored to keep notifications fire-and-forget. The client **SHOULD** ignore a response that arrives after it cancelled. If it already processed the response, fine. The important design point is that cancellation is *advisory*: if the tool had side effects, they may have happened. Non-idempotent tools need idempotency keys or a way to compensate, and the UI should say "cancellation requested", not "nothing happened".

### Why must clients treat pagination cursors as opaque? Give a bug that happens if they don't.
Because the cursor's meaning belongs to the server. It might be an offset today and a signed snapshot id tomorrow. A classic bug: a client sees `nextCursor: "eyJwYWdlIjogM30="`, decodes it to `{"page": 3}`, and "optimises" by jumping straight to page 7. That breaks when the server switches to keyset pagination, or skips items when the list changes between calls. Another bug is treating an **empty string** as "no more pages". The spec says `""` is a valid cursor, and only a *missing* `nextCursor` means the end. Clients also must not assume a page size, because the server chooses it.

### What changed about logging between 2025-11-25 and 2026-07-28?
Two things. **Mechanism:** `logging/setLevel` (a session-wide setting) was removed, because there are no sessions any more. A client now opts in **per request** with `io.modelcontextprotocol/logLevel` in `_meta`, and without it the server **must not** send `notifications/message`. Those messages are request-scoped, sent on that request's response stream before the result, never on a `subscriptions/listen` stream. **Status:** the whole Logging feature is **deprecated** (SEP-2577) along with Roots and Sampling. It remains for at least twelve months, but new implementations should log to stderr (stdio) or use OpenTelemetry.

### Gotcha: a server sends `notifications/progress` with `progress: 30` and then `progress: 20`. Also, it sends progress for a request that had no `progressToken`. Which rules are broken?
Both are violations. `progress` **MUST increase** with every notification for a token, even when `total` is unknown, so 30 → 20 is invalid (a client may drop it or flag the server). And progress notifications **MUST** only reference a token that was provided in an active request. With no `progressToken` there is nothing to reference, so the server must not send any. Two related rules: notifications **must stop** after the operation completes, and both sides **should rate-limit** them.

## Glossary
- Message pattern | 消息模式 | A standard way requests, responses and notifications combine: request/response, multi round-trip requests, or subscribe/notify.
- Cancellation | 取消 | Abandoning an in-flight request: `notifications/cancelled` on stdio, closing the response stream on Streamable HTTP.
- `notifications/cancelled` | `notifications/cancelled`（取消通知） | The notification carrying `requestId` and an optional `reason`; servers send it only to end a `subscriptions/listen` stream.
- Race condition | 竞态条件 | A cancellation arriving after the request already completed, which both sides must handle gracefully.
- Progress token | 进度令牌 | A client-chosen string or integer in `_meta.progressToken`, unique among active requests, that opts a request into progress notifications.
- `notifications/progress` | `notifications/progress`（进度通知） | A server notification with `progressToken`, a strictly increasing `progress`, and optional `total` and `message`.
- Cursor-based pagination | 基于游标的分页 | Splitting list results into server-sized pages linked by opaque `nextCursor`/`cursor` tokens.
- Opaque cursor | 不透明游标 | A pagination token clients must not parse or modify; only its presence matters, and `""` is valid.
- `io.modelcontextprotocol/logLevel` | 逐请求日志级别 | The `_meta` key that opts one request into log notifications at or above a level; replaces `logging/setLevel`.
- Deprecated feature | 已弃用特性 | A feature that remains in the spec for at least twelve months but that new implementations should not adopt, like Logging.

## Notebook
### 1. Progress, seen through the SDK
`ctx.report_progress(progress, total, message)` sends `notifications/progress`, but **only** if the request carried a `progressToken`. `Client.call_tool(..., progress_callback=...)` creates the token for you and routes the notifications to your callback.

```python
import json
import os
import sys
import tempfile
import textwrap
import time
import warnings
from pathlib import Path

import anyio
from mcp import Client, StdioServerParameters
from mcp.server import MCPServer
from mcp.server.mcpserver import Context
from mcp.shared.exceptions import MCPDeprecationWarning, MCPError

indexer = MCPServer("indexer")


@indexer.tool()
async def index_repo(files: int, ctx: Context) -> str:
    """Index a repository, reporting progress per file."""
    for i in range(1, files + 1):
        await anyio.sleep(0.05)
        await ctx.report_progress(i, files, f"indexed file {i}/{files}")
    return f"indexed {files} files"


async def show_progress(progress, total, message):
    bar = "#" * int(20 * progress / total)
    print(f"  [{bar:<20}] {progress:>4.0f}/{total:.0f}  {message}")


async with Client(indexer) as client:
    result = await client.call_tool("index_repo", {"files": 5}, progress_callback=show_progress)
    print(result.content[0].text)
    quiet = await client.call_tool("index_repo", {"files": 5})        # no callback -> no token -> no notifications
    print(quiet.content[0].text, "(no progressToken, so no notifications)")
```

### 2. Progress on the wire, and a client that checks the rules
Over raw stdio you can see the token travel. We also run every notification through a small validator for the spec's rules: the token must be known and active, and `progress` must strictly increase. A deliberately buggy tool goes backwards.

```python
import queue
import subprocess
import threading

workdir = Path(tempfile.mkdtemp())
(workdir / "progress_server.py").write_text(textwrap.dedent('''
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("progress-lab", log_level="ERROR")

    @mcp.tool()
    async def good(ctx: Context) -> str:
        """Well-behaved progress."""
        for i in (0.25, 0.5, 1.0):
            await ctx.report_progress(i, 1.0, f"{i:.0%}")
        return "ok"

    @mcp.tool()
    async def buggy(ctx: Context) -> str:
        """Progress that goes backwards."""
        for i in (30, 20, 40):
            await ctx.report_progress(i)
        return "ok"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {}}


def start(script, env=None):
    proc = subprocess.Popen([sys.executable, str(workdir / script)], stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                            stderr=subprocess.DEVNULL, text=True, env=env)
    inbox = queue.Queue()
    threading.Thread(target=lambda: [inbox.put(l) for l in proc.stdout], daemon=True).start()
    return proc, inbox


def send(proc, message):
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()


class ProgressTracker:
    def __init__(self):
        self.active = {}                                     # token -> last progress value

    def start(self, token):
        self.active[token] = None

    def check(self, params):
        token, value = params["progressToken"], params["progress"]
        if token not in self.active:
            return "VIOLATION: unknown or finished token"
        last = self.active[token]
        self.active[token] = value
        if last is not None and value <= last:
            return f"VIOLATION: progress went {last} -> {value} (MUST increase)"
        return "ok"

    def finish(self, token):
        self.active.pop(token, None)


proc, inbox = start("progress_server.py")
tracker = ProgressTracker()
for id_, tool in [(1, "good"), (2, "buggy")]:
    token = f"tok-{tool}"
    tracker.start(token)
    send(proc, {"jsonrpc": "2.0", "id": id_, "method": "tools/call",
                "params": {"name": tool, "arguments": {}, "_meta": {**ENVELOPE, "progressToken": token}}})
    while True:
        msg = json.loads(inbox.get(timeout=10))
        if msg.get("method") == "notifications/progress":
            print(f"  {json.dumps(msg['params']):<85} {tracker.check(msg['params'])}")
        else:
            tracker.finish(token)
            print(f"  response id={msg['id']} -> token {token!r} retired\n")
            break
proc.stdin.close()
_ = proc.wait(timeout=10)
```

### 3. Cancellation from the SDK: give up, time out, and what the server sees
The server appends to an events file so we can watch it from outside. When the caller's `anyio` scope gives up, the SDK sends `notifications/cancelled` on stdio and the handler is interrupted. `read_timeout_seconds` does the same and raises an error.

```python
(workdir / "cancel_server.py").write_text(textwrap.dedent('''
    import os
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("cancel-lab", log_level="ERROR")

    def note(text):
        with open(os.environ["EVENTS_FILE"], "a") as f:
            f.write(text + "\\n")

    @mcp.tool()
    async def crunch(seconds: float, ctx: Context) -> str:
        """A long job."""
        note(f"request {ctx.request_id}: started ({seconds}s of work)")
        try:
            await anyio.sleep(seconds)
        except BaseException as exc:
            note(f"request {ctx.request_id}: interrupted by {type(exc).__name__}, resources freed")
            raise
        note(f"request {ctx.request_id}: finished")
        return "crunched"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
events_file = workdir / "events.log"
events_file.write_text("")
env = {**os.environ, "EVENTS_FILE": str(events_file)}
params = StdioServerParameters(command=sys.executable, args=[str(workdir / "cancel_server.py")], env=env)

async with Client(params) as client:
    with anyio.move_on_after(0.5) as scope:                 # the user pressed "stop" after 0.5 s
        await client.call_tool("crunch", {"seconds": 5})
    print("caller gave up:", scope.cancelled_caught)

    try:
        await client.call_tool("crunch", {"seconds": 5}, read_timeout_seconds=0.5)
    except MCPError as err:
        print(f"timeout -> MCPError {err.error.code}: {err.error.message}")

    print((await client.call_tool("crunch", {"seconds": 0.1})).content[0].text)
    await anyio.sleep(0.2)

print("\nserver-side events:")
print(events_file.read_text())
```

The timeout surfaces as code `-32001`, from the **legacy implementation-defined** range. The spec assigns no code to purely local errors, so the SDK has to pick one. Remember that it was raised by your own client, not sent by the server.

### 4. Cancellation by hand, including the races
Raw stdio again. We cancel a running request, then send two *invalid* cancellations (an already-finished id and an unknown id). The spec says the server should silently ignore those, and the connection keeps working.

```python
proc, inbox = start("cancel_server.py", env=env)


def next_message(timeout=2.0):
    try:
        return json.loads(inbox.get(timeout=timeout))
    except queue.Empty:
        return None


send(proc, {"jsonrpc": "2.0", "id": "job-1", "method": "tools/call",
            "params": {"name": "crunch", "arguments": {"seconds": 10}, "_meta": ENVELOPE}})
time.sleep(1.0)                                              # let it start (process start-up + work)
send(proc, {"jsonrpc": "2.0", "method": "notifications/cancelled",
            "params": {"requestId": "job-1", "reason": "user pressed stop"}})
print("reply to job-1 after cancel:", next_message())

send(proc, {"jsonrpc": "2.0", "id": "job-2", "method": "tools/call",
            "params": {"name": "crunch", "arguments": {"seconds": 0.05}, "_meta": ENVELOPE}})
print("job-2:", next_message(5)["result"]["content"][0]["text"])
send(proc, {"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": "job-2"}})   # too late
send(proc, {"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": "never-sent"}})
print("after two invalid cancels:", next_message(1.0), "(silently ignored)")

send(proc, {"jsonrpc": "2.0", "id": "job-3", "method": "tools/call",
            "params": {"name": "crunch", "arguments": {"seconds": 0.05}, "_meta": ENVELOPE}})
print("job-3 still works:", next_message(5)["result"]["content"][0]["text"])
proc.stdin.close()
_ = proc.wait(timeout=10)
print("\nserver-side events:\n" + "\n".join(l for l in events_file.read_text().splitlines() if "job-" in l))
```

### 5. A watchdog: idle timeout reset by progress, plus a hard maximum
This implements the spec's timeout advice. Progress extends the *idle* deadline, but a hard cap ends even a request that reports progress forever.

```python
forever = MCPServer("forever")


@forever.tool()
async def stream_forever(ctx: Context) -> str:
    """Reports progress endlessly (a misbehaving server)."""
    i = 0
    while True:
        i += 1
        await ctx.report_progress(i, message=f"tick {i}")
        await anyio.sleep(0.2)


async def call_with_watchdog(client, name, args, idle=0.5, hard_max=1.5):
    started = last_progress = time.monotonic()

    async def on_progress(progress, total, message):
        nonlocal last_progress
        last_progress = time.monotonic()

    async with anyio.create_task_group() as tg:
        outcome = {}

        async def run():
            outcome["result"] = (await client.call_tool(name, args, progress_callback=on_progress)).content[0].text
            tg.cancel_scope.cancel()

        tg.start_soon(run)
        while True:
            await anyio.sleep(0.05)
            now = time.monotonic()
            if now - last_progress > idle:
                outcome["error"] = f"idle timeout ({idle}s without progress)"
            elif now - started > hard_max:
                outcome["error"] = f"hard maximum of {hard_max}s reached despite progress"
            if outcome:
                tg.cancel_scope.cancel()             # cancelling the call makes the SDK cancel the request
                break
    return outcome


async with Client(forever) as client:
    print(await call_with_watchdog(client, "stream_forever", {}))
async with Client(indexer) as client:
    print(await call_with_watchdog(client, "index_repo", {"files": 8}, idle=0.5, hard_max=5))
```

### 6. Pagination with opaque cursors
`MCPServer` returns every tool in one page. To paginate, use the low-level `Server` and write the `tools/list` handler yourself. The cursor here is a base64 blob the client must not interpret, and a bad cursor gets `-32602`.

```python
import base64

import mcp_types as types
from mcp.server import Server

CATALOG = [types.Tool(name=f"report_{i:02d}", description=f"Report number {i}", input_schema={"type": "object"})
           for i in range(7)]
PAGE_SIZE = 3                                                   # the SERVER decides


def make_cursor(offset: int) -> str:
    return base64.urlsafe_b64encode(json.dumps({"o": offset}).encode()).decode()


async def list_tools(ctx, params: types.PaginatedRequestParams | None) -> types.ListToolsResult:
    offset = 0
    if params is not None and params.cursor is not None:
        try:
            offset = json.loads(base64.urlsafe_b64decode(params.cursor))["o"]
        except Exception:
            raise MCPError(code=types.INVALID_PARAMS, message="Invalid cursor")
    page = CATALOG[offset:offset + PAGE_SIZE]
    more = offset + PAGE_SIZE < len(CATALOG)
    return types.ListToolsResult(tools=page, next_cursor=make_cursor(offset + PAGE_SIZE) if more else None)


pager = Server("pager", on_list_tools=list_tools)

async with Client(pager) as client:
    first = await client.list_tools()
    show = first.model_dump(by_alias=True, exclude_none=True, mode="json")
    print("first page on the wire:", json.dumps({k: v for k, v in show.items() if k != "tools"}),
          "| tools:", [t["name"] for t in show["tools"]])

    everything, cursor, pages = [], None, 0
    while True:                                                  # the loop every client should have
        page = await client.list_tools(cursor=cursor)
        pages += 1
        everything += [t.name for t in page.tools]
        if page.next_cursor is None:                             # only a MISSING cursor ends the loop
            break
        cursor = page.next_cursor
    print(f"collected {len(everything)} tools in {pages} pages:", everything)

    try:
        await client.list_tools(cursor="not-a-real-cursor")
    except MCPError as err:
        print("invalid cursor ->", err.error.code, err.error.message)
```

### 7. Logging, deprecated but still on the wire
A client opts in **per request** by setting `io.modelcontextprotocol/logLevel`. The SDK's `Client(log_level=..., logging_callback=...)` stamps that key on every request. With no level, the server must stay silent. The SDK marks the whole feature with `MCPDeprecationWarning`.

```python
chatty = MCPServer("chatty")


@chatty.tool()
async def migrate(ctx: Context) -> str:
    """Run a migration, logging along the way."""
    await ctx.debug("opening connection pool")
    await ctx.info({"step": "migrate", "tables": 12})
    await ctx.warning("table 'legacy_users' has no primary key")
    return "migrated"


async def print_log(params):
    print(f"   log [{params.level:<7}] {params.data}")


with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter("always", MCPDeprecationWarning)
    for level in ["debug", "warning", None]:
        print(f"log_level={level!r}:")
        async with Client(chatty, log_level=level, logging_callback=print_log) as client:
            print("  ", (await client.call_tool("migrate", {})).content[0].text)
print("\ndeprecation warnings raised:", sorted({str(w.message) for w in caught}))
```

On the raw wire, the level is just a `_meta` key, and an unknown level is rejected:

```python
(workdir / "log_server.py").write_text(textwrap.dedent('''
    import warnings
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context
    warnings.simplefilter("ignore")
    mcp = MCPServer("log-lab", log_level="ERROR")

    @mcp.tool()
    async def migrate(ctx: Context) -> str:
        """Run a migration."""
        await ctx.info("migration started")
        return "migrated"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
proc, inbox = start("log_server.py")
for id_, level in [(1, "info"), (2, "loud")]:
    send(proc, {"jsonrpc": "2.0", "id": id_, "method": "tools/call",
                "params": {"name": "migrate", "arguments": {},
                           "_meta": {**ENVELOPE, "io.modelcontextprotocol/logLevel": level}}})
    while True:
        msg = json.loads(inbox.get(timeout=10))
        print(f"logLevel={level!r}:", json.dumps(msg)[:150])
        if "id" in msg:
            break
send(proc, {"jsonrpc": "2.0", "id": 3, "method": "server/discover", "params": {"_meta": ENVELOPE}})
caps = json.loads(inbox.get(timeout=10))["result"]["capabilities"]
print("\ndeclared capabilities:", sorted(caps), "(the spec says log emitters MUST declare 'logging')")
proc.stdin.close()
_ = proc.wait(timeout=10)
```

Notice the last line: this SDK version emits `notifications/message` but does not advertise the `logging` capability in `server/discover`. Treat capability lists as hints and handle what actually arrives.

### 8. The replacement: structured logs on stderr
For stdio servers, the migration path is simply stderr. Here the server writes one JSON object per line to stderr, and the host captures it separately from the protocol stream. No opt-in or capability is needed, and nothing reaches the model's context.

```python
(workdir / "stderr_server.py").write_text(textwrap.dedent('''
    import json, logging, sys, time
    from mcp.server import MCPServer

    class JsonLines(logging.Formatter):
        def format(self, record):
            return json.dumps({"ts": round(time.time(), 3), "level": record.levelname.lower(),
                               "logger": record.name, "msg": record.getMessage()})

    handler = logging.StreamHandler(sys.stderr)          # never stdout on stdio!
    handler.setFormatter(JsonLines())
    log = logging.getLogger("billing")
    log.addHandler(handler)
    log.setLevel(logging.INFO)
    log.propagate = False

    mcp = MCPServer("billing", log_level="ERROR")

    @mcp.tool()
    def charge(cents: int) -> str:
        """Charge a (pretend) card."""
        log.info("charge requested: %d cents", cents)
        if cents > 10_000:
            log.warning("large charge flagged for review")
        return "charged"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))
proc = subprocess.Popen([sys.executable, str(workdir / "stderr_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
send(proc, {"jsonrpc": "2.0", "id": 1, "method": "tools/call",
            "params": {"name": "charge", "arguments": {"cents": 25_000}, "_meta": ENVELOPE}})
print("stdout (protocol):", proc.stdout.readline().strip()[:110], "...")
proc.stdin.close()
_ = proc.wait(timeout=10)
print("stderr (logs the host can capture):")
for line in proc.stderr.read().splitlines():
    if line.startswith("{"):
        print("  ", json.loads(line))
```

For remote servers, the equivalent is OpenTelemetry. The client puts `traceparent` in `_meta` (lesson 2.1), and the server exports spans and logs to your observability backend, correlated with the agent's trace.
