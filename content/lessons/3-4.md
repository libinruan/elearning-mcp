## Summary
A host connected to ten servers cannot re-fetch every tool list before every model call, yet it must not act on stale definitions either. The 2026-07-28 revision gives two complementary answers. **Caching** (pull): results of `server/discover`, the list methods and `resources/read` are `CacheableResult`s carrying `ttlMs` — how long the client may consider them fresh — and `cacheScope` — whether a shared cache may reuse them across users. **Subscriptions** (push): `subscriptions/listen` opens one long-lived stream on which the server sends only the change notifications the client opted into, each tagged with a `subscriptionId`. This lesson covers both pages in detail — TTL semantics, cache keys, pagination, scope security, acknowledgment, multiplexing, cancellation and graceful closure — and why `subscriptions/listen` replaced the HTTP GET stream and `resources/subscribe`.

## Lesson
### The freshness problem
Tool, prompt and resource lists change rarely, but they *do* change: a plugin is installed, a permission is granted, a file is edited. Clients therefore face a trade-off. Re-fetch too often and you waste round trips (and, for tool lists in an LLM prompt, break prompt caching); re-fetch too rarely and the model calls a tool that no longer exists. MCP's answer, like HTTP's, combines a **freshness hint** from the server with an **invalidation signal** when something changes. The caching page states it plainly: caching is complementary to change notifications, and both mechanisms can coexist.

### Which results are cacheable
Servers **MUST** include caching hints on `resultType: "complete"` results of:

| Method | Typical scope |
| --- | --- |
| `server/discover` | public |
| `tools/list`, `prompts/list`, `resources/templates/list` | public if identical for all users |
| `resources/list` | public, or private if filtered per user |
| `resources/read` | often private (user data) |

Interim `input_required` results (multi round-trip, lesson 5.3) are **not** cacheable and carry no hints. `tools/call`, `prompts/get` and `completion/complete` are not in the list at all. In the schema these results extend `CacheableResult`, which adds two required fields. The changelog records this as new in 2026-07-28 (SEP-2549).

### `ttlMs`: a freshness hint
`ttlMs` is an integer number of milliseconds for which the client MAY consider the result fresh — semantics analogous to HTTP `Cache-Control: max-age`.

| Value | Client behaviour |
| --- | --- |
| `0` | SHOULD treat as immediately stale; MAY re-fetch every time |
| positive | SHOULD treat as fresh for that many ms after receipt |
| absent | SHOULD assume `0` (only older servers omit it) and use its own heuristics or notifications |
| negative | SHOULD ignore it and treat as `0`; servers **MUST** send `>= 0` |

Freshness is computed from the local receive time: fresh while `now < t_received + ttlMs`; after that the entry is **stale** and the client SHOULD re-fetch on next access.

Three rules prevent common mistakes:

- **TTL is not a polling interval.** Clients SHOULD NOT schedule background re-fetches when TTLs expire; they check freshness *when they need the data*. Implementations that poll anyway **MUST** apply jitter and backoff — otherwise thousands of clients with the same TTL stampede the server in sync.
- **TTL is not a guarantee.** The server MAY change the data before the TTL expires. Clients MAY re-fetch early when they have reason to believe it changed — e.g. a `tools/call` fails because the tool no longer exists or the parameters are now invalid.
- **Stale is better than nothing.** Clients MAY serve stale responses if re-fetching fails (network issue, server down).

### `cacheScope`: who may reuse it
`cacheScope` is `"public"` or `"private"`, analogous to HTTP `Cache-Control: public` / `private`.

| Value | Meaning |
| --- | --- |
| `"public"` | No user-specific data. Any client, shared gateway or caching proxy MAY store it and serve it to **any** user. |
| `"private"` | Contains private data. MAY be reused only within the **same authorization context**; caches **MUST NOT** be shared across authorization contexts (a different access token needs a different cache). |

Public fits tool, prompt and template lists that are identical for everyone; private fits `resources/read` of user data and list results filtered by the caller's permissions.

### The cache key
A cached response is identified by the **request method plus the parameters that affect the result** — the `uri` for `resources/read`, the `cursor` for a paginated list. Clients **MUST NOT** serve a cached response for a request whose method or parameters differ. Results produced by retrying with `inputResponses` or `requestState` **MUST NOT** be cached: they depend on inputs outside the key.

### Notifications invalidate; pagination caches per page
A server may give a TTL without `listChanged` (clients rely on TTL alone), or both — then the TTL avoids needless re-fetches between notifications and the **notification is an immediate invalidation**: a relevant notification received while an entry is fresh makes it stale at once.

```text
t=0     tools/list  -> {tools, ttlMs: 300000}   cache it, fresh 5 min
t=2m    need tools  -> fresh, serve from cache   (no request)
t=3m    notifications/tools/list_changed         invalidate now
t=3m    need tools  -> stale, tools/list again
```

For paginated lists, **each page is an independently cacheable response**: each has its own `ttlMs` and freshness clock (servers MAY give early pages longer TTLs); an expired page is re-fetched with its cursor. There is no cross-page consistency guarantee — duplicates or gaps can appear if data changes mid-walk — so clients needing a consistent snapshot SHOULD re-fetch from the beginning. If a cursor becomes invalid, clients SHOULD discard all cached pages and restart. Servers **MUST** use the same `cacheScope` on every page of a list.

### Security of shared caches
A `"public"` result may be shared between callers **even if it came from an authenticated endpoint**: a gateway can serve the `tools/list` it fetched with Alice's token to Bob. So server authors should make `cacheScope` reflect the real visibility of each primitive, and **MUST** apply per-primitive access controls rather than relying on `cacheScope` to prevent unauthorised access. Mislabel a per-user list as public and a shared cache will leak it; check authorization on every `tools/call` and `resources/read` so that a leaked list does not become leaked access.

### `subscriptions/listen`: one opt-in stream
`subscriptions/listen` opens a **long-lived notification stream** from server to client. Unlike ordinary requests, it stays open, delivering notifications until cancelled. It **replaces** the former `resources/subscribe` / `resources/unsubscribe` RPCs and the Streamable HTTP **GET endpoint**.

```json
{"jsonrpc": "2.0", "id": 1, "method": "subscriptions/listen",
 "params": {"_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"},
                      "io.modelcontextprotocol/clientCapabilities": {}},
            "notifications": {"toolsListChanged": true,
                              "resourceSubscriptions": ["file:///project/config.json"]}}}
```

| Filter field | Type | Delivers |
| --- | --- | --- |
| `toolsListChanged` | boolean | `notifications/tools/list_changed` |
| `promptsListChanged` | boolean | `notifications/prompts/list_changed` |
| `resourcesListChanged` | boolean | `notifications/resources/list_changed` |
| `resourceSubscriptions` | string[] | `notifications/resources/updated` for those URIs |

All fields are optional; omitting one means not subscribing. The server **MUST NOT** send notification types the client has not explicitly requested.

**Why the change?** The old model had three problems. The GET stream was HTTP-only, so stdio and HTTP behaved differently. It delivered whatever the server chose to push, with no opt-in. And `resources/subscribe` created per-session server state — incompatible with a stateless protocol where any instance may serve any request. A listen request is self-contained (it carries its own `_meta` and filter), works identically on both transports (over HTTP it is a POST whose response is the SSE stream), and the server holds nothing beyond the open stream itself. Request-scoped notifications such as `notifications/progress` and `notifications/message` do **not** use it; they still flow on the response stream of the request they belong to.

### Acknowledgment and `subscriptionId`
The server **MUST** send `notifications/subscriptions/acknowledged` as the **first** message of the subscription, carrying `io.modelcontextprotocol/subscriptionId` in `_meta`, and MUST NOT send any notification on it before the ack. Its `notifications` field reflects the subset the server **agreed to honour** — unsupported types are omitted — and the client SHOULD compare it with what it asked for and degrade gracefully (e.g. fall back to TTL polling for an unsupported list).

```json
{"jsonrpc": "2.0", "method": "notifications/subscriptions/acknowledged",
 "params": {"_meta": {"io.modelcontextprotocol/subscriptionId": 1},
            "notifications": {"toolsListChanged": true, "resourceSubscriptions": ["file:///project/config.json"]}}}
```

The subscription ID **is the JSON-RPC `id` of the `subscriptions/listen` request**, and every notification on the stream carries it. A client MAY hold **several concurrent subscriptions** — one for tool changes, another for a set of resources — and uses the ID to demultiplex. On stdio, where everything shares one channel, clients **MUST** use it to correlate; the "ack first" ordering is defined per subscription, so another subscription's messages MAY be interleaved before it.

### Ending a subscription
A subscription ends when:

- the **client** cancels — closes the SSE stream (HTTP) or sends `notifications/cancelled` referencing the listen request's id (stdio);
- the **server** tears it down (e.g. shutdown) — it SHOULD first send a successful response to the original request, `{"resultType": "complete", "_meta": {"io.modelcontextprotocol/subscriptionId": 1}}`, then close the stream (**graceful closure**);
- the **transport** closes (HTTP timeout, TCP drop, process exit).

A graceful-closure response tells the client the end was deliberate; a transport close without it signals an unexpected disconnect, which the client MAY treat as a trigger to reconnect. There is **no replay**: after re-subscribing, refetch what you depend on. On stdio, if the connection is terminated and re-established, the client **MUST** re-send `subscriptions/listen` — the server holds no subscription state across reconnections.

### A complete client strategy
1. Fetch lists and reads; cache each per (method, params, authorization context) with its `ttlMs` and `cacheScope`.
2. Open `subscriptions/listen` for the lists you display or hand to a model, plus the resources you have attached; check the ack.
3. On a notification, invalidate the matching entries (`list_changed` → that list; `resources/updated` → that `uri`), then re-fetch lazily when needed.
4. On graceful closure or a drop, re-listen and refetch; on fetch errors, serve stale if acceptable.

## Key points
- `CacheableResult` adds required `ttlMs` and `cacheScope` to results of `server/discover`, `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` and `resources/read`; `input_required` results are not cacheable.
- `ttlMs` is a freshness hint like `max-age`: `0` or absent = stale, negative = treat as `0`, servers MUST send `>= 0`; fresh while `now < t_received + ttlMs`.
- TTL is not a polling interval (polling MUST use jitter and backoff) and not a guarantee; clients MAY re-fetch early and MAY serve stale on errors.
- `cacheScope`: `public` may be shared across users and gateways; `private` only within the same authorization context. Never rely on it for access control.
- Cache key = method + result-affecting params (`uri`, `cursor`); MRTR retries MUST NOT be cached; each page caches separately with the same scope.
- A relevant notification **immediately invalidates** a fresh cached entry.
- `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe`; the filter (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`) is strictly opt-in.
- The ack comes first and lists the honoured subset; every message is tagged with `subscriptionId` = the listen request's JSON-RPC id, enabling concurrent subscriptions.
- Ends by client cancel (close SSE / `notifications/cancelled`), server graceful-closure response, or transport close; no replay — re-listen and refetch.

## Pitches
### How do MCP clients keep tool lists fresh without constant polling?
Two mechanisms working together. Every list result carries ttlMs and cacheScope, so the client can serve it from cache while it's fresh — checked lazily when needed, not by polling. And the client opens a subscriptions/listen stream asking for toolsListChanged; when the server's tools change it sends a notification that immediately invalidates the cache, so the next use re-fetches. TTL bounds staleness when notifications aren't available, notifications make changes visible right away.

### What is cacheScope and why does it matter for security?
cacheScope says who may reuse a cached result. Public means it contains nothing user-specific, so a shared gateway can serve it to anyone, even if it was fetched with someone's token. Private means it can only be reused within the same authorization context. As a server author I mark per-user lists and resource reads private, and I still check authorization on every call, because the spec is explicit that cacheScope is not an access-control mechanism.

### Why did MCP replace resources/subscribe and the GET stream with subscriptions/listen?
Because they didn't fit a stateless protocol. The GET stream only existed on HTTP and pushed whatever the server chose, and resources/subscribe stored subscription state on the server per session. subscriptions/listen is a single self-contained request with an explicit opt-in filter, it works the same on stdio and HTTP, the server acknowledges exactly what it will honour, and every notification is tagged with a subscription id so a client can run several streams at once.

## Interview
### A server returns `ttlMs: 300000` on `tools/list`. What exactly may the client do for the next five minutes?
It MAY treat the list as fresh and skip re-fetching when it next needs tools — freshness is computed from the local receive time. It should **not** schedule a refetch at minute five; it checks freshness lazily on next use. It MAY re-fetch earlier if it suspects a change (a call fails with an unknown-tool error) and MUST treat the entry as stale immediately on `notifications/tools/list_changed`. The data can still change server-side within the TTL — it's a hint, not a guarantee.

### Which parameters form the cache key, and what must never be cached?
Method plus the parameters that affect the result: `uri` for `resources/read`, `cursor` for list pages. A response must never be served for a request with a different method or such parameters. Never cache `input_required` interim results or anything obtained by retrying with `inputResponses`/`requestState` — those depend on inputs outside the key. With pagination, each page is its own entry with its own TTL, all pages share one `cacheScope`, and an invalid cursor means discarding every cached page.

### You run a multi-tenant MCP gateway with a shared cache. What can go wrong?
A server labels a per-user result `public` — say a `resources/list` filtered by the user's permissions — and the gateway serves Alice's list to Bob. Mitigations: partition private entries by authorization context (derived from the verified token, never from request data), only share `public` entries across tenants when you trust the server's labelling, and rely on servers enforcing access control on every `tools/call`/`resources/read` — the spec says they MUST NOT rely on `cacheScope` alone.

### Walk through the lifecycle of a `subscriptions/listen` request on stdio.
The client sends `subscriptions/listen` with id `7` and a filter, say `toolsListChanged` and two resource URIs. The server first sends `notifications/subscriptions/acknowledged` with `_meta.subscriptionId: 7` and the honoured subset; the client compares it to its request. Changes then arrive as `notifications/tools/list_changed` or `notifications/resources/updated` tagged with `subscriptionId: 7`, interleaved with other traffic on the shared channel. The client ends it with `notifications/cancelled` for request `7`; if the server shuts down it SHOULD reply to request `7` with a `complete` result (graceful closure). After a reconnect the client MUST re-send the listen request.

### Gotcha: do progress notifications for a long `tools/call` arrive on the listen stream?
No. `subscriptions/listen` carries only the opted-in change notifications: tools/prompts/resources list changes and resource updates. Request-scoped notifications — `notifications/progress`, `notifications/message` — keep flowing on the response stream of the request they relate to (the changelog states this explicitly), so a client correlates progress by the request, not by a subscription. And the server MUST NOT send a type the client didn't request, so even list changes don't appear on a stream unless its filter asked for them.

## Glossary
- CacheableResult | 可缓存结果 | A result type carrying the `ttlMs` and `cacheScope` caching hints.
- ttlMs | 存活时间（毫秒） | Server hint for how many milliseconds a result may be considered fresh.
- cacheScope | 缓存范围 | `public` (shareable across users) or `private` (same authorization context only).
- Cache key | 缓存键 | Request method plus result-affecting parameters that identify a cached response.
- Stale | 过期（陈旧） | A cached entry past its TTL or invalidated by a notification; re-fetch on next use.
- Invalidation | 缓存失效 | Marking a cached entry stale immediately, e.g. on a list-changed notification.
- subscriptions/listen | 订阅监听请求 | A long-lived request whose response stream delivers opted-in change notifications.
- Subscription filter | 订阅过滤器 | The `notifications` object selecting which change notifications to receive.
- subscriptionId | 订阅标识 | `_meta` key on every stream message equal to the listen request's JSON-RPC id.
- Graceful closure | 优雅关闭 | Server ending a subscription by sending a `complete` response to the listen request.

### 1. Every cacheable result carries hints
By default `MCPServer` marks results `ttlMs: 0` (immediately stale) and `cacheScope: "private"` — the safest choice. Check every cacheable method, including the `server/discover` result the client fetched while connecting, and confirm `tools/call` carries no hints.

### 2. Server side: choosing hints
`MCPServer(cache_hints={method: CacheHint(ttl_ms, scope)})` sets hints per method. A middleware counts how many requests actually reach the server, so we can see the client cache work.

```python
from mcp.server.caching import CacheHint

hits = Counter()


async def count_requests(ctx, call_next):
    hits[ctx.method] += 1
    return await call_next(ctx)


server = MCPServer("travel", middleware=[count_requests], cache_hints={
    "tools/list": CacheHint(ttl_ms=300_000, scope="public"),       # same for every user, 5 min
    "resources/read": CacheHint(ttl_ms=60_000, scope="private"),    # user data, 1 min
})
inbox = {"messages": 1}


@server.tool()
def search_flights(origin: str, destination: str) -> list[str]:
    """Search flights between two airports."""
    return [f"{origin}->{destination} 08:15", f"{origin}->{destination} 17:40"]


@server.resource("inbox://me", mime_type="application/json")
def my_inbox() -> str:
    return json.dumps(inbox)


async with Client(server) as client:
    t = await client.list_tools()
    r = await client.read_resource("inbox://me")
    print("tools/list    ", t.ttl_ms, t.cache_scope)
    print("resources/read", r.ttl_ms, r.cache_scope)
```

### 3. Client side: the response cache and `cache_mode`
The SDK `Client` honours hints by default (`cache=CacheConfig()`). Each cacheable call takes `cache_mode`: `"use"` (serve if fresh, else fetch and store), `"refresh"` (always fetch, then store), `"bypass"` (ignore the cache). `Client(..., cache=None)` disables it.

```python
async with Client(server) as client:
    hits.clear()
    await client.list_tools()                         # miss -> server
    await client.list_tools()                         # fresh -> served from cache
    await client.list_tools(cache_mode="refresh")     # forced fetch, re-stored
    await client.list_tools(cache_mode="bypass")      # straight to server
    print("with cache:   ", dict(hits))

async with Client(server, cache=None) as client:
    hits.clear()
    await client.list_tools()
    await client.list_tools()
    print("cache=None:   ", {k: v for k, v in hits.items() if k != "server/discover"})
```

### 4. Freshness is measured from receive time
`CacheConfig(clock=...)` lets us fake the wall clock: the entry is fresh while `now < t_received + ttlMs`, then stale.

```python
from mcp.client.caching import CacheConfig

fake_now = [1_000.0]  # seconds

async with Client(server, cache=CacheConfig(clock=lambda: fake_now[0])) as client:
    hits.clear()
    for advance_s in [0, 120, 179.9, 0.2]:
        fake_now[0] += advance_s
        before = hits["tools/list"]
        await client.list_tools()
        print(f"t+{fake_now[0] - 1_000:6.1f}s  ->  {'server' if hits['tools/list'] > before else 'cache '}"
              f"   (ttl {300}s)")
```

The entry received at t=0 is fresh at 120 s and at 299.9 s (`now < 0 + 300 s`) and stale at 300.1 s, so that request goes to the server and the new response starts a fresh 300 s clock. Freshness is checked **lazily**, at the moment the data is needed: nothing was re-fetched in the background while the clock ran.

### 5. TTL is a hint, not a guarantee — notifications invalidate
A tool changes the inbox. Without a subscription the client keeps serving the cached (now wrong) value until the TTL runs out. With `subscriptions/listen`, the `notifications/resources/updated` evicts the entry immediately and the next read goes to the server.

```python
@server.tool()
async def receive_mail(ctx: Context) -> int:
    """Simulate new mail arriving."""
    inbox["messages"] += 1
    await ctx.notify_resource_updated("inbox://me")
    return inbox["messages"]


async with Client(server) as client:
    print("read:", (await client.read_resource("inbox://me")).contents[0].text)
    await client.call_tool("receive_mail", {})
    print("after change, no subscription:", (await client.read_resource("inbox://me")).contents[0].text, "<- stale!")

    async with client.listen(resource_subscriptions=["inbox://me"]) as sub:
        await client.call_tool("receive_mail", {})
        event = await anext(sub)
        hits.clear()
        print("event:", event)
        print("after notification:", (await client.read_resource("inbox://me")).contents[0].text,
              "| reached server:", hits["resources/read"] == 1)
```

### 6. `subscriptions/listen` on the wire
Below the SDK, over stdio: two **concurrent** subscriptions with different filters, the ack that comes first, `subscriptionId` tagging, opt-in filtering, client cancellation with `notifications/cancelled`, and a server-initiated **graceful closure**. (The `shutdown_streams` tool reaches into an SDK internal just to trigger what a server does on shutdown.)

```python
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
import time
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "watch_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    from mcp.server.caching import CacheHint
    from mcp.server.mcpserver import Context

    server = MCPServer("watchable", cache_hints={"tools/list": CacheHint(ttl_ms=300_000, scope="public")})
    config = {"theme": "dark"}

    @server.resource("config://app", mime_type="application/json")
    def app_config() -> str:
        return str(config)

    @server.tool()
    async def set_theme(theme: str, ctx: Context) -> str:
        """Change the theme (updates config://app)."""
        config["theme"] = theme
        await ctx.notify_resource_updated("config://app")
        return "ok"

    @server.tool()
    async def install_plugin(name: str, ctx: Context) -> str:
        """Install a plugin, which adds a tool."""
        server.add_tool(lambda: f"{name} says hi", name=f"{name}_hello", description=f"Greeting from {name}")
        await ctx.notify_tools_changed()
        return "installed"

    @server.tool()
    async def shutdown_streams() -> str:
        """Demo only: end all listen streams gracefully, as on server shutdown."""
        server._lowlevel_server._request_handlers["subscriptions/listen"].handler.close()
        return "closing"

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "watch_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
inbound: queue.Queue = queue.Queue()
threading.Thread(target=lambda: [inbound.put(line) for line in proc.stdout], daemon=True).start()
META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def send(message):
    message.setdefault("params", {})["_meta"] = META
    shown = {k: v for k, v in message.items() if k != "jsonrpc"}
    shown["params"] = {k: v for k, v in message["params"].items() if k != "_meta"}
    print(">>>", json.dumps(shown))
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()


def drain(seconds=0.6):
    deadline = time.time() + seconds
    while (left := deadline - time.time()) > 0:
        try:
            msg = json.loads(inbound.get(timeout=left))
        except queue.Empty:
            break
        if "result" in msg and "tools" in msg["result"]:
            msg["result"] = {k: msg["result"][k] for k in ("ttlMs", "cacheScope")} | {"tools": "[...]"}
        elif "result" in msg:
            msg["result"].get("_meta", {}).pop("io.modelcontextprotocol/serverInfo", None)
            msg["result"] = {k: v for k, v in msg["result"].items()
                             if k in ("resultType", "structuredContent") or (k == "_meta" and v)}
        print("    <<<", json.dumps({k: v for k, v in msg.items() if k != "jsonrpc"}))


send({"jsonrpc": "2.0", "id": 1, "method": "tools/list"}); drain()
send({"jsonrpc": "2.0", "id": "tools-sub", "method": "subscriptions/listen",
      "params": {"notifications": {"toolsListChanged": True}}})
send({"jsonrpc": "2.0", "id": "cfg-sub", "method": "subscriptions/listen",
      "params": {"notifications": {"resourceSubscriptions": ["config://app"]}}}); drain()
print("\n# a resource change reaches only cfg-sub:")
send({"jsonrpc": "2.0", "id": 2, "method": "tools/call", "params": {"name": "set_theme", "arguments": {"theme": "light"}}}); drain()
print("\n# a tool-list change reaches only tools-sub:")
send({"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {"name": "install_plugin", "arguments": {"name": "maps"}}}); drain()
print("\n# cancel cfg-sub, then change the resource again: silence")
send({"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": "cfg-sub"}}); drain(0.3)
send({"jsonrpc": "2.0", "id": 4, "method": "tools/call", "params": {"name": "set_theme", "arguments": {"theme": "solarized"}}}); drain()
print("\n# the server shuts its streams down gracefully:")
send({"jsonrpc": "2.0", "id": 5, "method": "tools/call", "params": {"name": "shutdown_streams", "arguments": {}}}); drain()
proc.stdin.close()
_ = proc.wait(timeout=10)
```

Read it closely: each ack precedes any notification on its subscription; every stream message carries the listen request's id as `subscriptionId`; the final message is a **response** with id `tools-sub` — the graceful closure.

### 7. The same with the SDK: `client.listen()`
`client.listen(...)` sends the request, waits for the ack (`sub.honored`, `sub.subscription_id`), and yields typed events. Two subscriptions can run at once; when the server closes gracefully the `async for` loop simply ends.

```python
catalogue = MCPServer("catalogue")
prompts_enabled = []


@catalogue.tool()
async def add_feature(name: str, ctx: Context) -> str:
    """Add a prompt and a tool, then tell subscribers."""
    catalogue.add_tool(lambda: name, name=f"{name}_tool", description=f"{name} tool")
    await ctx.notify_tools_changed()
    prompts_enabled.append(name)
    await ctx.notify_prompts_changed()
    return "added"


async with Client(catalogue) as client:
    async with client.listen(tools_list_changed=True) as tools_sub, \
               client.listen(prompts_list_changed=True, resources_list_changed=True) as other_sub:
        print("subscription ids:", tools_sub.subscription_id, other_sub.subscription_id)
        print("honoured:", tools_sub.honored.model_dump(by_alias=True, exclude_none=True),
              other_sub.honored.model_dump(by_alias=True, exclude_none=True))
        await client.call_tool("add_feature", {"name": "maps"})
        print(f"{tools_sub.subscription_id} got:", await anext(tools_sub))
        print(f"{other_sub.subscription_id} got:", await anext(other_sub))

        # graceful closure from the server side (SDK internal, demo only)
        catalogue._lowlevel_server._request_handlers["subscriptions/listen"].handler.close()
        leftovers = [event async for event in tools_sub]
        print("tools_sub ended gracefully; leftover events:", leftovers)
```

### 8. Break it: a mislabelled `public` result in a shared cache
A gateway shares one cache store between users, partitioned by authorization context, and opts in to sharing `public` entries (`share_public=True`). If the server labels a *private* inbox read as `public`, Bob is served Alice's mail without the server ever seeing his request.

```python
from mcp.client.caching import InMemoryResponseCacheStore

mail = {"alice": "Alice: your flight is confirmed", "bob": "Bob: nothing new"}


def make_mail_server(scope):
    srv = MCPServer("mail", middleware=[count_requests],
                    cache_hints={"resources/read": CacheHint(ttl_ms=60_000, scope=scope)})
    current_user = {"name": "alice"}   # stand-in for the authenticated principal

    @srv.resource("mail://inbox")
    def mailbox() -> str:
        return mail[current_user["name"]]

    return srv, current_user


for scope in ["public", "private"]:
    srv, current_user = make_mail_server(scope)
    store = InMemoryResponseCacheStore()   # one shared gateway cache
    hits.clear()
    for user in ["alice", "bob"]:
        current_user["name"] = user
        config = CacheConfig(store=store, partition=user, target_id="mail-server", share_public=True)
        async with Client(srv, cache=config) as client:
            text = (await client.read_resource("mail://inbox")).contents[0].text
            print(f"cacheScope={scope:<7} {user:<5} sees: {text!r}")
    print(f"   server saw {hits['resources/read']} resources/read request(s)\n")
```

With `private`, each user's entry lives in its own partition and Bob's read goes to the server. The fix belongs on the **server** (label user data `private`, enforce access on every request) — and gateways should only enable `share_public` for servers they trust.
