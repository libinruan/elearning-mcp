## Summary
Two families of official extensions extend what MCP can deliver and who can connect. **Skills over MCP** (`io.modelcontextprotocol/skills`) lets a server publish Agent Skills, which are folders of workflow instructions (`SKILL.md`) plus supporting files. Clients discover them with `skills/list` and `skills/get` and fetch the files with plain `resources/read`. Every file carries a SHA-256 digest and size, so the host verifies exactly what it loads and ties user approval to that manifest. The **authorization extensions** cover cases the core OAuth flow doesn't handle well. **OAuth Client Credentials** serves machine-to-machine callers with no user present, preferably using signed JWT assertions. **Enterprise-Managed Authorization** lets a company's identity provider decide which MCP servers employees may use, through an ID-JAG token. In the notebook you build a skills server and a verifying host, then run real SDK auth providers against a mock authorization server.

## Lesson
### Agent Skills, and why serve them over MCP
An **Agent Skill** is a directory containing a `SKILL.md` file and optional supporting files, as defined by the Agent Skills specification (agentskills.io). `SKILL.md` **MUST** begin with YAML frontmatter that includes at least `name` and `description`, and the last segment of its parent directory **MUST** equal `name`. Skills package reusable workflows that combine several tools or need reference material, such as a code-review checklist or a document-processing procedure.

Serving skills over MCP **keeps the instructions next to the service they describe**. The team that owns the server owns the workflow too. Clients can browse available workflows by metadata and load the instructions and files **only when needed**, which saves context. The extension defines **discovery and retrieval only**. The host decides how skills are presented: the model can pick one by name and description, or the user can select one explicitly.

> **Spec rule.** Reading `SKILL.md` with `resources/read` does **not** activate a skill. To load it, the host sends the read through its skill-loading path, which verifies the content and applies any required user approval before anything reaches the model's context.

### Declaring the extension
A server that supports Skills **MUST** declare both the `resources` capability and the extension in `server/discover`:

```json
{"capabilities": {"resources": {},
                  "extensions": {"io.modelcontextprotocol/skills": {"directoryRead": true}}}}
```

The server **MUST** implement `skills/list` and `skills/get`. Skill files are served through ordinary `resources/read`. The optional `directoryRead` setting (default `false`) advertises `resources/directory/read`. Clients send `skills/list` and `skills/get` only after they have seen the declaration. As with any 2026-07-28 request, every call carries the `_meta` envelope.

### `skills/list` and `skills/get`
`skills/list` supports pagination (`cursor` / `nextCursor`) and caching. Its result **MUST** carry `resultType: "complete"`, `ttlMs` and `cacheScope`:

```json
{"resultType": "complete", "ttlMs": 300000, "cacheScope": "public",
 "skills": [{"uri": "skill://code-review/SKILL.md",
             "frontmatter": {"name": "code-review", "description": "Review code using the team's checklist."},
             "resources": [
               {"uri": "skill://code-review/SKILL.md",
                "digest": "sha256:d2489d6c182e8df9c178563ff9f2eac7998a0c1bb1278c52a7fd5306e4259160", "size": 149},
               {"uri": "skill://code-review/references/checklist.md",
                "digest": "sha256:dbab2de7bf7db9cc95cb6ce681c3690b26184db39f75b958a0287ca6d9e24e20", "size": 65}]}]}
```

| Entry field | Meaning |
| --- | --- |
| `uri` | Resource URI of the skill's `SKILL.md` |
| `frontmatter` | **All** YAML frontmatter fields, unchanged |
| `resources` | The complete **file manifest** (URI, SHA-256 `digest`, byte `size` for `SKILL.md` and every supporting file), or `"dynamic"` for generated content |

Each listed entry is complete, so `skills/get` is not needed for more metadata. A manifest is never split across pages. The cache fields describe freshness and sharing. They say nothing about **integrity**, which is the job of digests.

`skills/get {"uri": ...}` returns one entry under `result.skill` (plus `resultType`, `ttlMs`, `cacheScope`). Use it when the URI comes from a user, another skill or server instructions, or to refresh an entry. Servers MAY return partial or empty listings, but they **MUST** answer `skills/get` for every skill they serve, and hosts **MUST** support loading a skill by URI even if it was never listed. An unknown URI returns `-32602`.

**Identity** is the pair *(originating server, skill URI)*. Names are labels and are not guaranteed unique, so hosts **MUST** keep both server identity and URI in registries, approvals and caches. Servers SHOULD use the `skill://` scheme but MAY use another. Hosts **MUST NOT** decide something is a skill from its URI scheme alone.

### Reading content and directories
The host fetches `SKILL.md`, and later each supporting file, with `resources/read`, always from the **same server**. Relative references are resolved against the skill's root, so `references/checklist.md` becomes `skill://code-review/references/checklist.md`. Hosts **MUST NOT retrieve files ahead of need**: not on connection, listing or approval. Approval binds to the manifest, so files don't need to be downloaded in order to approve.

`resources/directory/read {"uri": "skill://code-review/references"}` lists the direct children of a directory. Directory URIs have no trailing slash, subdirectories have `mimeType: "inode/directory"`, and results paginate. Clients **MUST NOT** call it unless the server declared `directoryRead: true`. For a manifest skill the host can answer from the manifest. A live directory listing **never extends the retained manifest**: a newly listed file needs an entry refresh and fresh approval before it counts as part of the skill.

### Integrity and verification
While a skill is in use, at least until its `SKILL.md` leaves the model's context, the host keeps the entry it loaded. For manifest skills the host **MUST**:

1. **restrict reads** to URIs in the retained manifest;
2. **verify each file's raw byte size and SHA-256 digest** before using it;
3. **parse the `SKILL.md` frontmatter and compare it field by field** with the entry's `frontmatter`.

Content that fails verification **MUST NOT** be used. To recover from stale metadata, refresh the entry with `skills/get`. Persisted approval **MUST bind to the full set of file URIs and digests**. A changed, added or removed file **revokes** the approval, and the host must ask again. Verified content SHOULD be cached on demand. A disk cache must either be immutable and protected from the model, its tools and other users, or be re-verified on every access. Cached files must stay out of filesystem skill-discovery paths and keep their MCP origin across restarts.

> **Pitfall.** A digest proves that the bytes match the server's manifest. It does **not** prove the content is trustworthy. Skills that use `"resources": "dynamic"` have no stable digests. Hosts MAY decline them, must still verify frontmatter, and must not treat a past approval as covering future content.

Servers **MUST** serve valid skills, preserve all frontmatter, compute manifests **from the bytes actually served**, and support direct lookup. They SHOULD NOT exceed **512 files or 16 MiB per skill**, and hosts must support skills up to those limits.

**Host security duties.** Skills with the same name must not silently replace each other. Loaded content is tagged with its originating server, and reads stay bound to that server. A cross-server read needs explicit per-call approval naming both servers. Skill content is **untrusted input**, so host-side code execution and grants such as `allowed-tools` require explicit per-skill approval. A nested skill needs fresh consent, because reading its `SKILL.md` as a supporting file does not activate it.

| Condition | Handling |
| --- | --- |
| Unknown skill or file, invalid directory URI | JSON-RPC `-32602` |
| Internal server failure | `-32603` |
| Digest, size, frontmatter or manifest mismatch | Host-side: reject the content, refresh the entry (not a protocol error) |

### Why authorization extensions?
Core MCP authorization (lesson 6.1) handles the common case: **a user with a browser** grants a client delegated access to a server through OAuth. Two real deployments don't fit that model:

- **Machine-to-machine.** Background services, CI pipelines and daemons have nobody present to click "Allow".
- **Enterprise.** The company's identity provider (IdP) should enforce policy centrally. Having every employee authorize every server individually adds friction and **bypasses existing security controls**.

The `ext-auth` repository answers each with an extension. Both are opt-in, both need explicit client support, and both use the standard `extensions` negotiation.

### OAuth Client Credentials (`io.modelcontextprotocol/oauth-client-credentials`)
The client authenticates **as itself**, with application credentials rather than a user's delegated grant, and the authorization server (AS) issues a token with no redirect and no user interaction. The extension builds on OAuth 2.1, RFC 8414 (AS metadata), RFC 9728 (protected resource metadata) and **RFC 7523** (JWT client authentication). It applies to HTTP transports. Credentials are **pre-registered out of band**, so Dynamic Client Registration is not used.

The flow starts like core MCP auth. The client gets a `401` with `WWW-Authenticate` pointing to the protected resource metadata, reads it to find the AS, and fetches the AS metadata. Then it calls the token endpoint with one of two client authentication methods:

```http
POST /token HTTP/1.1
Host: auth.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_assertion_type=urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
&client_assertion=eyJhbGciOiJSUzI1NiIsImtpZCI6IjIyIn0.eyJpc3Mi...
&resource=https%3A%2F%2Fmcp.example.com
&scope=mcp%3Aread
```

- **JWT authentication (RECOMMENDED)**, RFC 7523 §2.2, also called `private_key_jwt`. The client signs a short-lived JWT with its **private key**, and the AS verifies it with the registered **public key**. Typical claims are `iss` and `sub` (both the client ID), `aud`, `exp` and `iat`, plus a `jti` for replay protection. `client_id` is left out of the body because the `sub` claim identifies the client.
- **Client secret** (OAuth 2.1 §2.4.1): `grant_type=client_credentials&client_id=...&client_secret=...`.

> **Doc note.** The overview page's diagram labels the JWT flow `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` and says `aud` is the token endpoint URL. The normative ext-auth spec and the Python SDK both use `grant_type=client_credentials` plus `client_assertion`, which is RFC 7523 §2.2 *client authentication*. The `jwt-bearer` *grant* (§2.1) belongs to Enterprise-Managed Authorization. The SDK sets `aud` to the **AS issuer identifier**, following the RFC 7523 update. Check what your authorization server expects.

The AS metadata **MUST** list `"private_key_jwt"` or `"client_secret_basic"` in `token_endpoint_auth_methods_supported`, and must include `token_endpoint_auth_signing_alg_values_supported` when it supports JWT authentication.

> **Pitfall: secrets are long-lived.** A leaked client secret lets an attacker authenticate silently as your service until someone rotates it. Keep secrets in a secrets manager, rotate them regularly and after any suspected compromise, scope them minimally, and **prefer JWT assertions**: they are short-lived, and the signing key never leaves the client.

Clients declare the extension, obtain a token before connecting, send `Authorization: Bearer <token>`, and refresh before expiry, because these tokens tend to be short-lived. Servers validate the token's signature and claims on every request (usually against the AS's JWKS), check scopes, and SHOULD advertise the extension in `server/discover` so clients can discover it. In the Python SDK, `ClientCredentialsOAuthProvider` (secret) and `PrivateKeyJWTOAuthProvider` with `SignedJWTParameters(...).create_assertion_provider()` (JWT) are `httpx2.Auth` objects that handle discovery, token acquisition and refresh. The keyword is `scope=`, although the docs' example passes `scopes=`. Also pass `issuer=`, because omitting it is deprecated.

### Enterprise-Managed Authorization (`io.modelcontextprotocol/enterprise-managed-authorization`)
In consumer MCP, each user authorizes each server, which works well for individuals. In a company it causes problems: employees shouldn't have to understand each server's auth, security teams can't enforce consistent policy, onboarding means dozens of consent screens, and offboarding means revoking access service by service. This extension (originally **SEP-990**) makes the **enterprise IdP** (Okta, Azure AD, corporate SSO) the authority on which MCP servers each employee may use.

The key artifact is the **Identity Assertion JWT Authorization Grant (ID-JAG)**:

```text
1. SSO:   user signs in to the MCP client through the enterprise IdP -> client keeps the ID Token (or SAML assertion)
2. Leg 1: client -> IdP token endpoint (RFC 8693 token exchange)
          grant_type=urn:ietf:params:oauth:grant-type:token-exchange
          requested_token_type=urn:ietf:params:oauth:token-type:id-jag
          audience=<MCP authorization server issuer>   resource=<MCP server id>
          subject_token=<ID Token>  subject_token_type=urn:ietf:params:oauth:token-type:id_token
          IdP evaluates policy -> returns the ID-JAG (JWT with typ "oauth-id-jag+jwt")
3. Leg 2: client -> MCP authorization server token endpoint
          grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer   assertion=<ID-JAG>
          AS validates the ID-JAG -> access token audience-restricted to the MCP server
4. Client calls the MCP server with the Bearer token
```

The ID-JAG's claims include `iss` (the IdP), `sub`, an optional `email`, `aud` (the MCP AS issuer), `resource` (the MCP server), `client_id`, `scope`, `exp`, `iat` and `jti`. The flow gives four properties: **centralized policy**, **single sign-on** (no per-server consent prompts), **policy enforcement before any token is issued** (an unauthorized employee's client never gets one), and **centralized revocation** at the IdP.

Each party has duties. The **client** supports SSO, keeps the identity assertion, requests and exchanges ID-JAGs, and does **not** redirect the user to the MCP AS's authorization endpoint. Admins configure IdP endpoints at the organization level, and the client handles scope errors gracefully. The **MCP server** declares the extension in its authorization metadata and can optionally publish a resource descriptor to IdP admin consoles. The **MCP AS** validates ID-JAGs against the IdP's JWKS (signature, audience, issuer, expiry), maps claims to permissions, and links accounts by `sub` first, falling back to `email` for accounts created before enterprise auth. Clients detect support through `urn:ietf:params:oauth:grant-profile:id-jag` in the AS metadata field `authorization_grant_profiles_supported`. In the Python SDK, `IdentityAssertionOAuthProvider` performs leg 2. Leg 1 is deployment-specific and comes from your `assertion_provider` callback.

### Choosing the right mechanism
| Scenario | Use |
| --- | --- |
| Background service, daemon, CI/CD pipeline, server-to-server integration | OAuth Client Credentials |
| Employees reaching MCP servers at work; organization-wide access policy | Enterprise-Managed Authorization |
| A person interactively authorizing a client | Core MCP authorization, no extension |

The roadmap's *Agent Identity* area (lesson 7.4) builds on this foundation with workload identity federation, ID-JAG and RFC 8693 token exchange, because agents increasingly act with their own identity or on behalf of an absent user.

## Key points
- Skills over MCP (`io.modelcontextprotocol/skills`): a skill is a directory with `SKILL.md` (YAML frontmatter with `name` and `description`, parent directory equals `name`) plus supporting files. Servers must also declare `resources`.
- Methods are `skills/list` (paginated and cacheable), `skills/get` (MUST work for every served skill, `-32602` if unknown), and plain `resources/read` for file content. The optional `resources/directory/read` requires `directoryRead: true`.
- Each entry has `uri`, the unchanged `frontmatter`, and a `resources` manifest (URI, `sha256:` digest, byte size per file) or `"dynamic"`. Skill identity is server plus URI, never the name alone.
- Hosts MUST read only manifest URIs, verify size, SHA-256 and frontmatter before use, never prefetch, bind approval to the full URI and digest set, and re-approve after any change. A digest proves consistency, not trust.
- Reading `SKILL.md` does not activate a skill. Skill content is untrusted, and `allowed-tools` and code execution need explicit per-skill approval.
- OAuth Client Credentials is for machine-to-machine access with no user. It uses JWT client authentication (RFC 7523 `private_key_jwt`, RECOMMENDED) or a client secret, with pre-registered credentials and no DCR.
- The JWT assertion's claims are `iss` = `sub` = client ID, plus `aud`, `exp`, `iat` and `jti`. It is sent as `client_assertion` with `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`.
- Enterprise-Managed Authorization: the IdP enforces policy and issues an **ID-JAG** through RFC 8693 token exchange. The client presents it to the MCP AS with the `jwt-bearer` grant and receives an access token audience-restricted to the MCP server.
- Choose client credentials for daemons and CI, enterprise-managed for employees, and core OAuth for an interactive user.

## Pitches
### What does the Skills extension add to MCP?
It lets a server ship workflow knowledge, not just tools. A skill is a folder with a SKILL.md and supporting files. The server lists skills with their frontmatter and a manifest of every file's SHA-256 digest and size, and the host fetches files with ordinary resources/read only when they're needed. Before loading anything into the model's context, the host checks size, digest and frontmatter, and ties user approval to that exact manifest, so any change to the skill means asking the user again.

### When would you use the OAuth client credentials extension?
I'd use it whenever no human is around to approve access: a nightly job, a CI pipeline, or one backend calling another's MCP server. The service is pre-registered with the authorization server and authenticates as itself, ideally by signing a short-lived JWT with its private key, the RFC 7523 private_key_jwt method, rather than sending a long-lived secret. It receives an ordinary bearer token, and the MCP server validates it and checks scopes exactly as it would for any other token.

### How does enterprise-managed authorization work?
The company's identity provider becomes the gatekeeper. An employee signs in to the MCP client once with corporate SSO. When the client needs a given MCP server, it exchanges the ID token at the IdP for an ID-JAG, a signed grant scoped to that server's authorization server. The IdP applies policy at this step. The client then trades the ID-JAG for an access token. Nobody clicks through per-server consent screens, and IT can grant or revoke access centrally.

## Interview
### A host loads a skill, and an hour later the server updates `references/checklist.md`. What must the host do?
The retained manifest no longer matches what the server serves. The next read of the checklist yields bytes whose SHA-256 or size disagree with the manifest digest, so the host **must reject** that content and refresh the entry with `skills/get`. The refreshed manifest has a different digest set. Persisted approval is bound to the complete set of URIs and digests, so it is **revoked**, and the host must obtain user approval again before loading or executing anything. The host must also never quietly start using the new file just because it appeared in a listing or a directory read.

### Why does the Skills spec forbid prefetching files and forbid identifying skills by URI scheme?
Prefetching would pull untrusted content into the host before the user has approved anything, and it wastes bandwidth and context for skills that are never used. Approval binds to the manifest's digests, so the bytes are not needed to approve. Scheme-based detection is forbidden because `skill://` is only a SHOULD. Servers may use other schemes, and a malicious server could label any resource `skill://` to have it treated as instructions. A resource counts as a skill only when it comes from `skills/list` or `skills/get` and is keyed by server identity plus URI.

### How would you build and send a `private_key_jwt` client assertion?
Generate a key pair and register the public key with the authorization server. For each token request, build a JWT with `iss` and `sub` set to the client ID, `aud` set to the AS, a short `exp` (minutes), `iat`, and a unique `jti`. Sign it with an algorithm the AS lists in `token_endpoint_auth_signing_alg_values_supported` (for example RS256 or ES256). POST it form-encoded as `grant_type=client_credentials`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion=<jwt>`, plus `resource` and `scope`. The AS verifies the signature, the claims, expiry and that the `jti` hasn't been seen before. The private key never leaves the client.

### Client secret or JWT assertion: what are the trade-offs?
A **client secret** is simple, but it is a long-lived bearer credential sent on every token request. If it leaks, an attacker can authenticate silently until someone rotates it. A **JWT assertion** is short-lived and single-use (`jti`). It proves possession of a private key that never goes over the wire, so a captured assertion is worth little. Its costs are key management and an AS that supports `private_key_jwt`. The extension marks JWT as RECOMMENDED. With a secret, use a secrets manager, rotation and minimal scopes.

### Your company wants employees to use internal MCP servers through Claude with no per-server consent, and IT must be able to cut access instantly. What do you propose?
Enterprise-Managed Authorization. Employees sign in to the client through the corporate IdP. For each MCP server the client performs an RFC 8693 token exchange at the IdP, with `requested_token_type=urn:ietf:params:oauth:token-type:id-jag`, `audience` set to the MCP AS issuer and `resource` set to the server. The IdP evaluates group and role policy and issues an ID-JAG. The client presents it with the `jwt-bearer` grant to the MCP AS, which validates it against the IdP's keys and issues a token audience-restricted to that server. Revocation happens at the IdP, so no further ID-JAGs are issued, and short token lifetimes mean access ends quickly everywhere.

### Gotcha: a server lists skill `code-review` and so does another server. What could go wrong, and what does the spec require?
Names are labels, not identities. Without care, the second skill could **shadow** the first, so the model loads a different server's instructions under a trusted name. Hosts **MUST** prevent same-name skills from silently replacing each other. They must key registries, approvals and caches by *(server identity, URI)*, tag loaded content with its origin, and bind file reads to the originating server. Cross-server reads need explicit per-call approval that names both servers.

## Glossary
- Agent Skill | 智能体技能 | A directory with a `SKILL.md` (YAML frontmatter plus instructions) and supporting files that teaches an agent a workflow.
- `SKILL.md` | `SKILL.md`（技能说明文件） | The entry file of a skill; it must start with frontmatter containing `name` and `description`.
- Skill manifest | 技能文件清单 | The `resources` list in a skill entry: each file's URI, SHA-256 digest and byte size.
- Digest verification | 摘要校验 | Checking a file's raw byte size and SHA-256 against the manifest before using it.
- `skills/list` / `skills/get` | `skills/list` / `skills/get`（技能列举/获取） | Extension methods that return skill entries (frontmatter plus manifest), paginated or by URI.
- Client credentials grant | 客户端凭据授权 | The OAuth flow where an application authenticates as itself and receives a token without a user.
- JWT bearer client assertion | JWT 客户端断言（private_key_jwt） | A short-lived JWT signed with the client's private key and used instead of a secret to authenticate (RFC 7523 §2.2).
- Identity provider (IdP) | 身份提供方 | The enterprise system (Okta, Azure AD, …) that authenticates employees and enforces access policy.
- ID-JAG | 身份断言 JWT 授权许可（ID-JAG） | Identity Assertion JWT Authorization Grant: an IdP-signed JWT the client exchanges for an MCP access token.
- Token exchange (RFC 8693) | 令牌交换 | The OAuth grant the client uses to trade its ID token for an ID-JAG at the IdP.

## Notebook
### 1. A Skills server built on the SDK's extension API
The Python SDK has no built-in Skills extension, so we write one. It declares `io.modelcontextprotocol/skills` with `directoryRead`, serves files as resources, and binds `skills/list`, `skills/get` and `resources/directory/read`. The manifest is **computed from the bytes served**, as the spec requires. The files are exactly the docs' example, so the digests should match the documentation character for character.

```python
import hashlib
import json
import logging
from typing import Any, Literal

import yaml

from mcp import Client
from mcp.server import MCPServer
from mcp.server.extension import Extension, MethodBinding, ResourceBinding
from mcp.server.mcpserver.resources import FunctionResource
from mcp.shared.exceptions import MCPError
from mcp_types import INVALID_PARAMS, PaginatedRequestParams, Request, RequestParams, Result

logging.getLogger("mcp").setLevel(logging.ERROR)
SKILLS = "io.modelcontextprotocol/skills"
FILES = {
    "skill://code-review/SKILL.md":
        "---\nname: code-review\ndescription: Review code using the team's checklist.\n---\n\n"
        "# Code review\n\nRead `references/checklist.md`, then review the diff.\n",
    "skill://code-review/references/checklist.md":
        "# Review checklist\n\nCheck correctness, tests, and compatibility.\n",
}


def sha256_digest(data: bytes) -> str:
    return "sha256:" + hashlib.sha256(data).hexdigest()


def frontmatter_of(text: str) -> dict:
    assert text.startswith("---\n"), "SKILL.md MUST begin with YAML frontmatter"
    return yaml.safe_load(text.split("---\n", 2)[1])


class SkillsListResult(Result):
    result_type: Literal["complete"] = "complete"
    skills: list[dict[str, Any]]
    next_cursor: str | None = None
    ttl_ms: int
    cache_scope: str


class SkillGetParams(RequestParams):
    uri: str


class SkillGetResult(Result):
    result_type: Literal["complete"] = "complete"
    skill: dict[str, Any]
    ttl_ms: int
    cache_scope: str


class DirectoryReadParams(RequestParams):
    uri: str
    cursor: str | None = None


class DirectoryReadResult(Result):
    result_type: Literal["complete"] = "complete"
    resources: list[dict[str, Any]]
    next_cursor: str | None = None


class SkillsExtension(Extension):
    identifier = SKILLS

    def __init__(self, files: dict[str, str]):
        self.files = files                                       # uri -> served text

    def settings(self):
        return {"directoryRead": True}

    def entry(self, skill_md_uri: str) -> dict:
        root = skill_md_uri.rsplit("/", 1)[0]
        manifest = [{"uri": u, "digest": sha256_digest(t.encode()), "size": len(t.encode())}
                    for u, t in sorted(self.files.items()) if u.startswith(root + "/")]
        return {"uri": skill_md_uri, "frontmatter": frontmatter_of(self.files[skill_md_uri]), "resources": manifest}

    def resources(self):   # FunctionResource reads the CURRENT bytes on every resources/read
        return [ResourceBinding(FunctionResource(uri=u, name=u.rsplit("/", 1)[1], mime_type="text/markdown",
                                                 fn=lambda u=u: self.files[u]))
                for u in self.files]

    def methods(self):
        async def list_skills(ctx, params: PaginatedRequestParams):
            entries = [self.entry(u) for u in self.files if u.endswith("/SKILL.md")]
            return SkillsListResult(skills=entries, ttl_ms=300_000, cache_scope="public")

        async def get_skill(ctx, params: SkillGetParams):
            if params.uri not in self.files or not params.uri.endswith("/SKILL.md"):
                raise MCPError(INVALID_PARAMS, f"Unknown skill: {params.uri}")
            return SkillGetResult(skill=self.entry(params.uri), ttl_ms=300_000, cache_scope="public")

        async def read_directory(ctx, params: DirectoryReadParams):
            prefix = params.uri + "/"
            children = {}
            for u in self.files:
                if u.startswith(prefix):
                    head, _, rest = u[len(prefix):].partition("/")
                    children[prefix + head] = ("inode/directory" if rest else "text/markdown", head)
            if not children:
                raise MCPError(INVALID_PARAMS, f"Invalid directory URI: {params.uri}")
            return DirectoryReadResult(resources=[{"uri": u, "name": n, "mimeType": m}
                                                  for u, (m, n) in sorted(children.items())])

        return [MethodBinding("skills/list", PaginatedRequestParams, list_skills),
                MethodBinding("skills/get", SkillGetParams, get_skill),
```

### 3. A verifying host: approve the manifest, then load on demand
The host keeps the entry, asks for approval **bound to the URI and digest set**, and only then reads `SKILL.md`. It verifies size, SHA-256 and frontmatter, resolves the relative reference inside the retained manifest, and refuses anything outside it.

```python
from posixpath import normpath


class SkillLoadError(Exception):
    pass


class SkillHost:
    def __init__(self, client, server_label):
        self.client, self.server = client, server_label
        self.approvals: set[tuple] = set()           # persisted approvals: (server, uri, frozenset of (uri, digest))

    @staticmethod
    def approval_key(server, entry):
        return (server, entry["uri"], frozenset((f["uri"], f["digest"]) for f in entry["resources"]))

    def approve(self, entry, user_says_yes=True):
        files = [f["uri"] for f in entry["resources"]]
        print(f"   [consent] load skill {entry['frontmatter']['name']!r} from {self.server} ({len(files)} files)?",
              "yes" if user_says_yes else "no")
        if user_says_yes:
            self.approvals.add(self.approval_key(self.server, entry))

    async def read_verified(self, entry, uri):
        manifest = {f["uri"]: f for f in entry["resources"]}
        if uri not in manifest:                                       # MUST restrict reads to the manifest
            raise SkillLoadError(f"{uri} is not in the retained manifest")
        data = (await self.client.read_resource(uri)).contents[0].text.encode()
        if len(data) != manifest[uri]["size"] or sha256_digest(data) != manifest[uri]["digest"]:
            raise SkillLoadError(f"{uri}: size/digest mismatch -> reject and refresh with skills/get")
        return data.decode()

    async def load(self, entry):
        if self.approval_key(self.server, entry) not in self.approvals:
            raise SkillLoadError("no approval for this exact manifest")
        text = await self.read_verified(entry, entry["uri"])
        if frontmatter_of(text) != entry["frontmatter"]:              # field-by-field comparison
            raise SkillLoadError("frontmatter differs from the entry")
        name = entry["frontmatter"]["name"]
        if entry["uri"].rsplit("/", 2)[-2] != name:
            raise SkillLoadError("parent directory must equal `name`")
        return f"<skill name={name!r} origin={self.server!r}>\n{text}</skill>"

    async def read_reference(self, entry, relative):
        root = entry["uri"].rsplit("/", 1)[0]
        target = root + "/" + normpath(relative)
        return await self.read_verified(entry, target)


async with Client(server) as client:
```

### 5. Client credentials, part 1: a `private_key_jwt` assertion by hand
The docs recommend asymmetric JWT assertions over secrets. `cryptography` and `PyJWT` are installed, so we generate an RSA key, sign an assertion and decode its parts with the standard library to see exactly what is sent. Then the authorization server verifies it with the **public** key. In this notebook the authorization server is a few lines of Python.

```python
import base64
import time
import uuid
from urllib.parse import parse_qs, urlencode

import jwt
from cryptography.hazmat.primitives import serialization
from cryptography.hazmat.primitives.asymmetric import rsa

AS_ISSUER, MCP_RESOURCE, CLIENT_ID = "https://auth.example.com", "https://mcp.example.com/mcp", "nightly-report-bot"
client_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
client_private_pem = client_key.private_bytes(serialization.Encoding.PEM, serialization.PrivateFormat.PKCS8,
                                              serialization.NoEncryption()).decode()
REGISTERED_KEYS = {CLIENT_ID: client_key.public_key()}       # what the AS stored at (out-of-band) registration


def b64url_json(segment: str) -> dict:
    return json.loads(base64.urlsafe_b64decode(segment + "=" * (-len(segment) % 4)))


now = int(time.time())
assertion = jwt.encode({"iss": CLIENT_ID, "sub": CLIENT_ID, "aud": AS_ISSUER, "iat": now, "exp": now + 300,
                        "jti": str(uuid.uuid4())}, client_private_pem, algorithm="RS256")
header, payload, signature = assertion.split(".")
print("JOSE header:", b64url_json(header))
print("claims:     ", b64url_json(payload))
print("signature:  ", signature[:24], "...", f"({len(signature)} chars)")

body = urlencode({"grant_type": "client_credentials",
                  "client_assertion_type": "urn:ietf:params:oauth:client-assertion-type:jwt-bearer",
```

### 6. Client credentials, part 2: the real SDK provider against a mock authorization server
Now the SDK's `PrivateKeyJWTOAuthProvider` performs the whole flow: `401` → protected resource metadata → AS metadata → token request → retry with `Bearer`. An `httpx2.MockTransport` plays the MCP server and the AS, and the AS **really validates** the assertion: signature, `iss`/`sub`, `aud`, expiry and `jti` replay. Nothing leaves the process.

```python
import httpx2

from mcp.client.auth.extensions.client_credentials import (ClientCredentialsOAuthProvider,
                                                           PrivateKeyJWTOAuthProvider, SignedJWTParameters)

logging.getLogger("httpx2").setLevel(logging.WARNING)
AS_PRIVATE = rsa.generate_private_key(public_exponent=65537, key_size=2048)
seen_jti, wire_log = set(), []
AS_METADATA = {"issuer": AS_ISSUER, "token_endpoint": AS_ISSUER + "/token",
               "authorization_endpoint": AS_ISSUER + "/authorize", "response_types_supported": ["code"],
               "grant_types_supported": ["client_credentials"],
               "token_endpoint_auth_methods_supported": ["private_key_jwt", "client_secret_basic"],
               "token_endpoint_auth_signing_alg_values_supported": ["RS256", "ES256"]}
SECRETS = {"legacy-cron": "s3cr3t"}


def token_endpoint(form: dict, headers) -> httpx2.Response:
    if form.get("grant_type") != "client_credentials":
        return httpx2.Response(400, json={"error": "unsupported_grant_type"})
    if "client_assertion" in form:                          # private_key_jwt (RFC 7523 section 2.2)
        unverified = jwt.decode(form["client_assertion"], options={"verify_signature": False})
        client_id = unverified["sub"]
        try:
            claims = jwt.decode(form["client_assertion"], REGISTERED_KEYS[client_id], algorithms=["RS256", "ES256"],
                                audience=AS_ISSUER, issuer=client_id, options={"require": ["exp", "iat", "jti"]})
        except (KeyError, jwt.PyJWTError) as exc:
            return httpx2.Response(401, json={"error": "invalid_client", "error_description": str(exc)})
        if claims["jti"] in seen_jti:
            return httpx2.Response(401, json={"error": "invalid_client", "error_description": "assertion replayed"})
        seen_jti.add(claims["jti"])
    else:                                                   # client secret (basic or post)
        basic = headers.get("authorization", "")
        if basic.startswith("Basic "):
            client_id, _, secret = base64.b64decode(basic[6:]).decode().partition(":")
        else:
            client_id, secret = form.get("client_id"), form.get("client_secret")
        if SECRETS.get(client_id) != secret:
            return httpx2.Response(401, json={"error": "invalid_client"})
    token = jwt.encode({"iss": AS_ISSUER, "sub": client_id, "aud": form.get("resource", MCP_RESOURCE),
                        "scope": form.get("scope", ""), "exp": int(time.time()) + 300}, AS_PRIVATE, algorithm="RS256")
    return httpx2.Response(200, json={"access_token": token, "token_type": "Bearer", "expires_in": 300,
                                      "scope": form.get("scope", "")})


def mcp_endpoint(headers) -> httpx2.Response:
    auth = headers.get("authorization", "")
    try:
        claims = jwt.decode(auth.removeprefix("Bearer "), AS_PRIVATE.public_key(), algorithms=["RS256"],
                            audience=MCP_RESOURCE, issuer=AS_ISSUER)
    except jwt.PyJWTError:
        return httpx2.Response(401, headers={"WWW-Authenticate":
            'Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp"'})
    if "mcp:read" not in claims["scope"].split():
        return httpx2.Response(403, headers={"WWW-Authenticate": 'Bearer error="insufficient_scope", scope="mcp:read"'})
    return httpx2.Response(200, json={"hello": claims["sub"], "scope": claims["scope"]})


def router(request: httpx2.Request) -> httpx2.Response:
    body = request.content.decode()
    wire_log.append(f"{request.method} {request.url}" + (f"\n      {body[:160]}..." if body else ""))
    path = request.url.path
    if path.startswith("/.well-known/oauth-protected-resource"):
        return httpx2.Response(200, json={"resource": MCP_RESOURCE, "authorization_servers": [AS_ISSUER],
                                          "scopes_supported": ["mcp:read"]})
    if path.startswith("/.well-known/oauth-authorization-server") or path.startswith("/.well-known/openid-configuration"):
        return httpx2.Response(200, json=AS_METADATA)
    if path == "/token":
        return token_endpoint({k: v[0] for k, v in parse_qs(body).items()}, request.headers)
    if path == "/mcp":
        return mcp_endpoint(request.headers)
    return httpx2.Response(404)


class MemoryStorage:
    def __init__(self):
        self.tokens = self.client_info = None

    async def get_tokens(self):
        return self.tokens

    async def set_tokens(self, tokens):
        self.tokens = tokens

    async def get_client_info(self):
        return self.client_info

    async def set_client_info(self, info):
        self.client_info = info


jwt_provider = PrivateKeyJWTOAuthProvider(
    server_url=MCP_RESOURCE, storage=MemoryStorage(), client_id=CLIENT_ID, scope="mcp:read", issuer=AS_ISSUER,
    assertion_provider=SignedJWTParameters(issuer=CLIENT_ID, subject=CLIENT_ID,
                                           signing_key=client_private_pem).create_assertion_provider())
async with httpx2.AsyncClient(transport=httpx2.MockTransport(router), auth=jwt_provider) as http:
    response = await http.post(MCP_RESOURCE, json={})
print("private_key_jwt ->", response.status_code, response.json())
print("\n".join("  " + line for line in wire_log))

wire_log.clear()
secret_provider = ClientCredentialsOAuthProvider(server_url=MCP_RESOURCE, storage=MemoryStorage(), client_id="legacy-cron",
                                                 client_secret="s3cr3t", scope="mcp:read", issuer=AS_ISSUER)
async with httpx2.AsyncClient(transport=httpx2.MockTransport(router), auth=secret_provider) as http:
    response = await http.post(MCP_RESOURCE, json={})
token_call = next(l for l in wire_log if "/token" in l)
print("\nclient_secret_basic ->", response.status_code, response.json(), "\n  token call:", token_call.replace("\n", " "))
```

### 7. Enterprise-managed authorization: mint and exchange an ID-JAG
We play the **IdP** for leg 1. It checks policy and signs an ID-JAG with `typ: oauth-id-jag+jwt`, `aud` set to the MCP AS issuer and `resource` set to the MCP server. The SDK's `IdentityAssertionOAuthProvider` performs leg 2, the `jwt-bearer` grant, and the AS validates the ID-JAG against the IdP's public key before issuing an audience-restricted token.

```python
from mcp.client.auth.extensions.identity_assertion import IdentityAssertionOAuthProvider

IDP_ISSUER = "https://acme.idp.example"
IDP_KEY = rsa.generate_private_key(public_exponent=65537, key_size=2048)
POLICY = {"alice@acme.example": {MCP_RESOURCE}, "bob@acme.example": set()}   # who may reach which MCP server
AS_METADATA["authorization_grant_profiles_supported"] = ["urn:ietf:params:oauth:grant-profile:id-jag"]
AS_METADATA["grant_types_supported"].append("urn:ietf:params:oauth:grant-type:jwt-bearer")
MCP_CLIENTS = {"chat-client": "client-secret-at-mcp-as"}


def idp_token_exchange(user: str, audience: str, resource: str) -> str:
    """Leg 1 (RFC 8693): the IdP evaluates policy, then issues an ID-JAG."""
    if resource not in POLICY.get(user, set()):
        raise PermissionError(f"IdP policy denies {user} -> {resource}")
    now = int(time.time())
    return jwt.encode({"jti": uuid.uuid4().hex, "iss": IDP_ISSUER, "sub": "U019488227", "email": user,
                       "aud": audience, "resource": resource, "client_id": "chat-client",
                       "exp": now + 300, "iat": now, "scope": "mcp:read"},
                      IDP_KEY, algorithm="RS256", headers={"typ": "oauth-id-jag+jwt"})


def as_jwt_bearer(form: dict) -> httpx2.Response:
    """Leg 2: the MCP authorization server validates the ID-JAG."""
    if MCP_CLIENTS.get(form.get("client_id")) != form.get("client_secret"):
        return httpx2.Response(401, json={"error": "invalid_client"})
    try:
        if jwt.get_unverified_header(form["assertion"]).get("typ") != "oauth-id-jag+jwt":
            raise jwt.InvalidTokenError("not an ID-JAG")
        grant = jwt.decode(form["assertion"], IDP_KEY.public_key(), algorithms=["RS256"],
                           audience=AS_ISSUER, issuer=IDP_ISSUER)
    except jwt.PyJWTError as exc:
        return httpx2.Response(400, json={"error": "invalid_grant", "error_description": str(exc)})
    if grant["client_id"] != form["client_id"]:
        return httpx2.Response(400, json={"error": "invalid_grant", "error_description": "client mismatch"})
    token = jwt.encode({"iss": AS_ISSUER, "sub": grant["sub"], "aud": grant["resource"],   # audience-restricted
                        "scope": grant["scope"], "exp": int(time.time()) + 300}, AS_PRIVATE, algorithm="RS256")
    return httpx2.Response(200, json={"access_token": token, "token_type": "Bearer", "expires_in": 300,
                                      "scope": grant["scope"]})


def enterprise_router(request: httpx2.Request) -> httpx2.Response:
    if request.url.path == "/token":
        form = {k: v[0] for k, v in parse_qs(request.content.decode()).items()}
        print("  leg 2 token request: grant_type =", form["grant_type"], "| params:", sorted(form))
        return as_jwt_bearer(form)
    return router(request)


for user in ("alice@acme.example", "bob@acme.example"):
    async def fetch_id_jag(audience: str, resource: str, user=user) -> str:
        jag = idp_token_exchange(user, audience, resource)
        print(f"  leg 1: IdP issued ID-JAG typ={jwt.get_unverified_header(jag)['typ']} claims=",
              {k: v for k, v in jwt.decode(jag, options={"verify_signature": False}).items() if k in ("aud", "resource", "email")})
        return jag

    provider = IdentityAssertionOAuthProvider(server_url=MCP_RESOURCE, storage=MemoryStorage(), client_id="chat-client",
                                              client_secret="client-secret-at-mcp-as", issuer=AS_ISSUER,
                                              assertion_provider=fetch_id_jag, scope="mcp:read")
    print(user)
    try:
        async with httpx2.AsyncClient(transport=httpx2.MockTransport(enterprise_router), auth=provider) as http:
            r = await http.post(MCP_RESOURCE, json={})
        print("  MCP server ->", r.status_code, r.json())
    except PermissionError as exc:
        print("  blocked at the IdP:", exc)
```
