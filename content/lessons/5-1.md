## Summary
Servers are not the only side with something to offer. A client can give a server three things in return: **elicitation** (ask the user for information), **roots** (tell the server which directories matter) and **sampling** (borrow the host's LLM). In 2026-07-28 two big things changed. First, a server can no longer send its own requests to the client. All three features now travel through the **Multi Round-Trip Request** pattern: the server returns an `InputRequiredResult` and the client retries the call with the answers. Second, **Roots and Sampling are deprecated** (SEP-2577), which leaves elicitation as the core client feature. This lesson covers what each feature does, its user-interaction and security model, the capability rules, and the migrations you should use instead.

## Lesson
### Clients give as well as take
A **host** (Claude Desktop, an IDE, your agent) creates one **client** per server. Most of the time the client *consumes* what the server offers: tools, resources, prompts. The spec also defines **client features**, which let a server ask the client for something while it is handling a request:

| Feature | What the server gets | Example from the docs | Status in 2026-07-28 |
| --- | --- | --- | --- |
| **Elicitation** | Information *from the user*, structured by a schema or collected out of band via a URL | A travel server asks for seat preference and a final "confirm $3,000 booking" | **Active**, the core client feature |
| **Roots** | The list of `file://` directories the client considers in scope | `file:///Users/agent/travel-planning` | **Deprecated** (SEP-2577) |
| **Sampling** | An LLM completion produced by the *host's* model | "Analyse these 47 flights and recommend the best one" | **Deprecated** (SEP-2577) |

All three put the **client in control**. The user sees who is asking and why, and can say no. The server never touches the user's UI, the filesystem picker or the model API key directly.

### How client features travel now: MRTR
Before 2026-07-28 a server sent JSON-RPC *requests* of its own (`elicitation/create`, `roots/list`, `sampling/createMessage`) back to the client while the client's request was still open. That needs a long-lived bidirectional channel and sticky state, which is exactly what the stateless revision removed. The changelog says it directly: the **Multi Round-Trip Requests (MRTR)** pattern (SEP-2322) *replaces* server-initiated requests. Servers **MUST** use it, and the old pattern "is no longer supported. This is a breaking change."

```text
client                                     server
  │ tools/call {name, arguments}  (id 1)     │
  │─────────────────────────────────────────▶│  needs user input / roots / an LLM answer
  │◀─────────────────────────────────────────│  result: {resultType: "input_required",
  │                                          │           inputRequests: {key: {method, params}},
  │  ask user / list dirs / call LLM         │           requestState: "opaque"}
  │ tools/call {..., inputResponses, requestState}  (id 2)
  │─────────────────────────────────────────▶│  rebuilds context from requestState
  │◀─────────────────────────────────────────│  result: {resultType: "complete", ...}
```

The three request types are now **values inside `InputRequiredResult.inputRequests`** rather than messages on the wire. Only `tools/call`, `prompts/get` and `resources/read` may return an `InputRequiredResult`. Lesson 5.3 covers the mechanics in depth: `requestState` integrity, retries, and error handling.

Capabilities still gate everything, and they are declared **per request** in `_meta.io.modelcontextprotocol/clientCapabilities`:

```json
{"_meta": {"io.modelcontextprotocol/clientCapabilities": {
  "elicitation": {"form": {}, "url": {}},
  "roots": {},
  "sampling": {"tools": {}}
}}}
```

> **Spec rule.** Servers **MUST NOT** put an input request in `inputRequests` that the client has not declared support for. If a client sends no `elicitation` capability, it gets no `elicitation/create`. If it has `sampling` without `sampling.tools`, it gets no tool-enabled sampling. An empty `"elicitation": {}` means form mode only, for backwards compatibility.

### Elicitation: asking the user, mid-operation
Elicitation lets a server *pause and ask* instead of failing or demanding every argument up front. There are two modes:

- **Form mode** (`mode: "form"`, or omitted): the request carries a `message` and a `requestedSchema`. The client renders a form, validates the input and returns it. The data **is visible to the client**. The schema is a deliberately **restricted JSON Schema**: a flat object whose properties are only string (with `format` `email`, `uri`, `date` or `date-time`), number/integer, boolean, or single/multi-select enums. Nested objects and arrays of objects are not allowed, so any client can render the form.
- **URL mode** (`mode: "url"`, plus `url`): the client shows the URL and, with consent, opens it. The interaction (entering an API key, an OAuth consent, a payment) happens **out of band** and never passes through the client or the LLM context.

The user answers with one of three **actions**: `accept` (with `content` in form mode), `decline` (an explicit no) or `cancel` (dismissed without choosing). Servers must handle all three.

The **user-interaction model** sets the rules. Clients **MUST** make clear *which server* is asking, offer clear decline and cancel options, let users review and edit form answers before sending, and for URL mode show the full URL and domain and get consent before navigating. Servers **MUST NOT** use form mode for passwords, API keys, access tokens or payment credentials. Those **MUST** go through URL mode.

### Roots: advisory filesystem scope (deprecated)
A root is `{ "uri": "file:///home/user/projects/myproject", "name": "My Project" }`. The `uri` **MUST** be a `file://` URI. A server asks for them with a `roots/list` input request, and the client answers with `{"roots": [...]}`. Hosts usually derive roots automatically from the folder or workspace the user opened, and sometimes let users add or exclude directories by hand.

The key word is **advisory**. The docs call roots "a coordination mechanism … not a security boundary": servers "SHOULD respect root boundaries", not "MUST enforce" them, because the client cannot control code running in the server. Real enforcement belongs to the OS: file permissions, sandboxing, containers (lesson 6.3). Security rules still apply. Clients **MUST** expose only roots with appropriate permissions, validate root URIs against path traversal and implement access controls, and they **SHOULD** ask for consent before exposing roots. Servers **SHOULD** validate every path against the provided roots.

What changed in 2026-07-28: `notifications/roots/list_changed` was **removed** along with the other removed notifications, so a server sees the updated list the next time it asks. Roots as a whole are **deprecated**. New implementations **SHOULD NOT** adopt them. The migration is to *pass directories or files via tool parameters, resource URIs, or server configuration*. A `directory` argument is explicit, visible in the tool-call approval UI, and works the same in every host.

### Sampling: borrowing the host's model (deprecated)
Sampling let a server request an LLM completion "with no server API keys necessary". The client owns model access, choice and permissions. The `sampling/createMessage` params are:

- `messages` (`role` `user` or `assistant`, with text, image or audio content) and a **required** `maxTokens`, which the client **MUST** respect.
- `modelPreferences`. Servers can't name a model reliably, because the client may use a different provider. Instead they send `hints` (substrings such as `"claude"`, tried in order, which the client **MAY** map to an equivalent from another provider) and three 0–1 priorities: `costPriority`, `speedPriority` and `intelligencePriority`. The client always makes the final choice.
- `systemPrompt`, `temperature`, `stopSequences`, `metadata`: all things the client **MAY** modify or ignore.
- `includeContext`: `"none"` (the default), or `"thisServer"`/`"allServers"`. The last two are **deprecated** (SEP-2596) and **SHOULD NOT** be used unless the client declares `sampling.context`.

The result is `{role: "assistant", content, model, stopReason}`, with stop reasons `endTurn`, `stopSequence`, `maxTokens` or `toolUse`.

**Sampling with tools.** A server can include `tools` and `toolChoice` (`{mode: "auto" | "required" | "none"}`) so the host's model can call tools that are *scoped to that sampling request*. They don't have to be tools the server exposes. Clients **MUST** declare `sampling.tools`, and servers **MUST NOT** send tool-enabled requests otherwise. Under MRTR this becomes a loop across retries. The model answers with `tool_use` blocks (`stopReason: "toolUse"`), the server runs the tools and sends a new sampling request with history plus `tool_result` blocks, and this repeats until `endTurn`. Two constraints apply. A user message containing tool results **MUST** contain *only* tool results, and every `tool_use` id **MUST** be matched by a `tool_result` with the same `toolUseId`. Both sides **SHOULD** cap iterations, for example with `toolChoice: {mode: "none"}` on the last round.

**Interaction model.** There **SHOULD** always be a human in the loop who can deny sampling requests. The user should be able to review and edit the prompt *before* it is sent, and see the generation *before* it goes back to the server. Clients **SHOULD** rate-limit requests, and both sides **MUST** handle sensitive data appropriately.

**Why deprecate it?** The spec records the decision (SEP-2577) and the migration rather than a long rationale. The engineering trade-offs are easy to see, though. Sampling puts the host's model, budget and conversation trust at the disposal of any connected server, so a server can craft prompts that run on the user's model. Doing it safely needs approval UI at both ends of every call. It also needs a nested model call in the middle of a tool call, which fits poorly with a stateless protocol. The migration is simple: **integrate directly with an LLM provider API** from the server, with the server's own key and its own cost accounting.

### Deprecation, precisely
Under the feature lifecycle policy (SEP-2596), a *Deprecated* feature "remains part of the specification but is scheduled for removal". It stays fully functional for **at least twelve months**, and its earliest removal is the *first revision released on or after 2027-07-28*. Your clients and servers will still meet roots and sampling in the wild, especially from 2025-era SDKs, so you need to recognise them, support them during the window when your users need them, and steer new designs away from them.

| Deprecated | Use instead |
| --- | --- |
| Roots | A tool parameter (`directory: str`), a resource URI, or server configuration (an allowlist of directories given at launch) |
| Sampling | A direct call to an LLM provider API inside the server |
| `includeContext: "thisServer"/"allServers"` | Omit it or use `"none"` |
| Logging (server feature) | `stderr` for stdio; OpenTelemetry for observability |

> **Pitfall.** "We'll use roots to stop the server reading `~/.ssh`." Roots don't stop anything. They are hints to well-behaved servers. A sandbox, container or OS user stops a malicious one.

### Removed from elicitation in 2026-07-28
The `2025-11-25` revision added `notifications/elicitation/complete` and an `elicitationId` so a server could tell the client that a URL-mode interaction had finished. Both were **removed**. Under MRTR the client learns the outcome by **retrying** the original request. A server that needs to correlate a URL interaction across retries puts its own identifier into `requestState`. Lesson 5.3 builds this.

## Key points
- Client features let a server ask the client for something mid-request: **elicitation** (user input), **roots** (directories in scope), **sampling** (an LLM completion).
- In 2026-07-28 they all travel as **input requests inside `InputRequiredResult.inputRequests`** (MRTR, SEP-2322). Server-initiated requests are gone, which is a breaking change.
- Only `tools/call`, `prompts/get` and `resources/read` may return an `InputRequiredResult`, and servers **MUST NOT** send input requests the client hasn't declared in `clientCapabilities`.
- Elicitation has **form mode** (restricted flat JSON Schema, data visible to the client) and **URL mode** (out of band, for secrets, OAuth and payments). Responses are `accept`/`decline`/`cancel`.
- Never request passwords, API keys, tokens or payment credentials with form mode. Use URL mode.
- **Roots** are advisory `file://` boundaries, not a security control. They are deprecated, so pass directories as tool parameters, resource URIs or server config instead.
- **Sampling** uses `modelPreferences` (hints plus cost/speed/intelligence priorities), a required `maxTokens`, optional `tools`/`toolChoice` gated by `sampling.tools`, and human review. It is deprecated, so call LLM provider APIs directly.
- Deprecated features keep working for **at least 12 months**, with earliest removal in the first revision on or after **2027-07-28**. `includeContext` values other than `"none"` are deprecated too.
- `notifications/elicitation/complete`, `elicitationId` and `notifications/roots/list_changed` were **removed**.

## Pitches
### What are MCP client features?
Besides consuming tools, resources and prompts, an MCP client can serve the server. Elicitation lets a server ask the user for structured input or send them to a URL for something sensitive. Roots told the server which folders were in scope. Sampling let the server borrow the host's model. In the 2026-07-28 revision these travel inside an input-required result that the client answers by retrying the call, and roots and sampling are deprecated, so elicitation is the one I design around.

### Why were roots and sampling deprecated?
Both had awkward trust properties. Roots looked like a security boundary but were only advisory, so people relied on them for the wrong thing. Passing a directory as a tool argument or as server configuration is explicit and visible to the user. Sampling let any server spend the host's model budget with prompts it crafted, which needs heavy human review to be safe. A server that needs an LLM can simply call a provider API itself. Both still work for at least a year.

### How does elicitation stay safe?
The client stays in control. It must show which server is asking and why, let the user review and edit answers, and always offer decline and cancel. Form mode is restricted to flat, primitive fields and must never be used for passwords, API keys or payment details. Those go through URL mode, where the user enters them on the provider's own page and the data never passes through the client or the model's context.

## Interview
### Walk me through how a server asks the user a question in MCP 2026-07-28.
The server receives a `tools/call` and realises it needs input. Instead of sending its own `elicitation/create` request, which is no longer allowed, it **returns** a result with `resultType: "input_required"`, an `inputRequests` map such as `{"confirm": {"method": "elicitation/create", "params": {"mode": "form", "message": ..., "requestedSchema": ...}}}`, and optionally an opaque `requestState`. The client shows the form, collects `accept`/`decline`/`cancel`, and **retries** the same `tools/call` with a new JSON-RPC id, `inputResponses: {"confirm": {...}}` and the echoed `requestState`. The server rebuilds its context and completes. It only does this if the client declared `elicitation` (and the right mode) in that request's capabilities.

### What is the difference between form-mode and URL-mode elicitation, and when must you use URL mode?
Form mode collects structured data **in band**. The client renders a flat schema of primitives and enums, and the answers pass through the client. URL mode sends the user to a URL **out of band**. The client only learns whether the user consented (`accept` has no content), and the actual data goes straight to the target site. Servers **MUST** use URL mode for sensitive information: passwords, API keys, access tokens, payment credentials, and third-party OAuth where the MCP server acts as an OAuth client. URL mode is not for authorising the client to the MCP server itself. That is MCP authorization.

### A teammate proposes using roots to restrict a third-party filesystem server to the project folder. What do you say?
Roots are **advisory**. The spec says servers *SHOULD* respect them, because the client cannot control server code, so a buggy or malicious server can ignore them. They are also **deprecated** in 2026-07-28. For scope, I'd pass the directory explicitly (a tool parameter or the server's launch configuration, e.g. an allowlist argument) and have the server validate every path after resolving symlinks and `..`. For *security* I'd enforce at the OS level: run the server in a container or sandbox with only that folder mounted, or under a restricted user.

### How do modelPreferences work, and why not just send a model name?
The server and client may use different providers, so a model name might mean nothing to the client. `modelPreferences` combines advisory `hints` (substrings evaluated in order, which the client **MAY** map to an equivalent from another provider, e.g. a "sonnet"-class hint to a Gemini model) with normalised `costPriority`, `speedPriority` and `intelligencePriority` in 0–1. The client makes the final selection. It is a way to state requirements without coupling to a vendor. The whole feature is deprecated now, though.

### Gotcha: a server sends a tool-enabled sampling request and the client errors. What are the likely causes?
First, the client may not have declared `sampling.tools`. Servers **MUST NOT** send `tools`/`toolChoice` without it (the Python SDK refuses with `-32021` MissingRequiredClientCapability). Second, the message history may break the balance rules: every assistant `tool_use` must be followed by a user message made *only* of `tool_result` blocks with matching `toolUseId`s, with no text mixed in. Third, the loop may have hit an iteration cap. Long term, the right fix is to migrate off sampling and call the provider directly.

### Your server used sampling to summarise documents. How do you migrate it?
Replace the `sampling/createMessage` input request with a direct call to an LLM provider from the server, using the server's own API key from its environment or secret store, with its own model choice, `max_tokens`, rate limits and cost tracking. Keep the human-in-the-loop property where it matters by moving consent to the *tool call* (the host asks before invoking the tool) or by eliciting confirmation before an expensive or sensitive step. During the deprecation window I could keep the sampling path behind a capability check for older hosts, but new deployments shouldn't depend on it.

## Glossary
- Client features | 客户端特性 | Capabilities a client offers to servers (elicitation, roots, sampling), requested mid-operation via input requests.
- Elicitation | 征询（信息征询） | A server's request for information from the user, via a schema-driven form or an out-of-band URL.
- Form mode | 表单模式 | Elicitation that collects flat, primitive, schema-validated data through the client.
- URL mode | URL 模式 | Elicitation that sends the user to an external URL so sensitive data never passes through the client or LLM.
- Roots | 根目录 | Deprecated, advisory list of `file://` directories the client considers in scope for a server.
- Sampling | 采样 | Deprecated feature letting a server request an LLM completion from the host's model via `sampling/createMessage`.
- Model preferences | 模型偏好 | Hints plus cost/speed/intelligence priorities a server sends so the client can pick a suitable model.
- InputRequiredResult | 需输入结果（InputRequiredResult） | A result with `resultType: "input_required"` carrying `inputRequests` and/or `requestState`; the client answers by retrying.
- Deprecated feature | 已弃用特性 | A feature still in the spec and working, but scheduled for removal no earlier than 12 months later.
- MissingRequiredClientCapability | 缺少必需客户端能力（-32021） | The error a server returns when a request needs a capability the client did not declare.

## Notebook
### 1. Setup: what a client declares depends on its callbacks
In the Python SDK, you declare a client feature by **passing a callback**. `Client(elicitation_callback=...)` advertises `elicitation: {form, url}`, `list_roots_callback=` advertises `roots`, and `sampling_callback=` advertises `sampling`. The server sees these in the request's `_meta.io.modelcontextprotocol/clientCapabilities`. Let's prove it with a tool that echoes what it received.

```python
import json
import logging
import warnings

import mcp_types as types
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

logging.getLogger("mcp").setLevel(logging.CRITICAL)    # keep the SDK's own server-side logs quiet
warnings.filterwarnings("ignore", message=".*deprecated.*")


def wire(model) -> str:
    """A pydantic MCP object exactly as it travels on the wire."""
    return json.dumps(model.model_dump(by_alias=True, exclude_none=True, mode="json"), indent=2)


probe = MCPServer("capability-probe")


@probe.tool()
def my_capabilities(ctx: Context) -> str:
    """Return the client capabilities declared on this request."""
    caps = ctx.client_capabilities
    return json.dumps(caps.model_dump(by_alias=True, exclude_none=True) if caps else {})


async def noop(*args):          # placeholder callbacks: we only care about what gets declared
    return types.ErrorData(code=-1, message="unused")

async with Client(probe) as plain:
    print("no callbacks      ->", (await plain.call_tool("my_capabilities", {})).content[0].text)

async with Client(probe, elicitation_callback=noop, list_roots_callback=noop, sampling_callback=noop) as rich:
    print("all three         ->", (await rich.call_tool("my_capabilities", {})).content[0].text)
```

### 2. Elicitation: a travel server asks for booking details
This is the docs' Barcelona example. In `MCPServer`, the idiomatic 2026 way to ask a question is a **resolver**: a function that returns `Elicit(message, Schema)`. You attach it to a tool parameter with `Annotated[..., Resolve(fn)]`. The framework turns the question into an `InputRequiredResult`, and when the client retries with the answer it injects the result and runs the tool body. Annotating the parameter as `ElicitationResult[Schema]` gives you all three outcomes to branch on.

The Pydantic model is rendered as a **restricted flat schema**: a boolean, a string enum (`Literal`) and a boolean with a default. A nested model would be rejected.

```python
from typing import Annotated, Literal

from pydantic import BaseModel, Field

from mcp.server.elicitation import AcceptedElicitation, ElicitationResult
from mcp.server.mcpserver import Elicit, Resolve


class BookingDetails(BaseModel):
    confirmBooking: bool = Field(description="Confirm the booking (Flights + Hotel = $3,000)")
    seatPreference: Literal["window", "aisle", "no preference"] = Field(description="Preferred seat type")
    travelInsurance: bool = Field(default=False, description="Add travel insurance ($150)")


travel = MCPServer("travel")


def ask_booking_details(destination: str) -> Elicit[BookingDetails]:
    return Elicit(f"Please confirm your {destination} vacation booking details:", BookingDetails)


@travel.tool()
def book_trip(destination: str,
              details: Annotated[ElicitationResult[BookingDetails], Resolve(ask_booking_details)]) -> str:
    """Book a vacation package after the user confirms the details."""
    if isinstance(details, AcceptedElicitation):
        d = details.data
        if not d.confirmBooking:
            return "User reviewed the form but did not confirm. Nothing booked."
        extra = " + insurance" if d.travelInsurance else ""
        return f"Booked {destination}: {d.seatPreference} seat{extra}."
    return f"Booking not made: user chose '{details.action}'."


async with Client(travel) as c:
    tool = (await c.list_tools()).tools[0]
    print("book_trip input schema (what the LLM fills):", json.dumps(tool.input_schema))
```

Now the **client side**. A real host would render a form. Our scripted "user" prints what a UI would show (which server is asking, the message, the fields) and then answers. We run it three times to see `accept`, `decline` and `cancel`.

```python
script = []          # the scripted user's next answers


async def form_ui(context, params: types.ElicitRequestFormParams):
    """Stand-in for a host's elicitation dialog."""
    print(f"  ┌ [travel server] asks: {params.message}")
    for name, prop in params.requested_schema["properties"].items():
        choices = prop.get("enum")
        print(f"  │  {name:<16} {prop['type']:<8} {choices or ''} default={prop.get('default', '-')}")
    action, content = script.pop(0)
    print(f"  └ user -> {action} {content or ''}")
    return types.ElicitResult(action=action, content=content)


script[:] = [("accept", {"confirmBooking": True, "seatPreference": "window", "travelInsurance": True}),
             ("decline", None),
             ("cancel", None)]

async with Client(travel, elicitation_callback=form_ui) as client:
    for _ in range(3):
        result = await client.call_tool("book_trip", {"destination": "Barcelona"})
        print("tool result:", result.content[0].text, "\n")
```

### 3. Look under the hood: the input request on the wire
`client.call_tool` hid the round trip. `client.session.call_tool(..., allow_input_required=True)` returns the raw interim result instead, which here is the `InputRequiredResult` with the `elicitation/create` request *inside* it. Lesson 5.3 drives this loop by hand. For now, look at the shape.

```python
async with Client(travel, elicitation_callback=form_ui) as client:
    interim = await client.session.call_tool("book_trip", {"destination": "Barcelona"}, allow_input_required=True)
    print(type(interim).__name__)
    text = wire(interim)
    print(text[:1400] + ("\n  ..." if len(text) > 1400 else ""))
```

Notice `resultType: "input_required"`, the server-chosen key in `inputRequests`, and a `requestState` the SDK has **encrypted**. The client must echo it back untouched.

### 4. Break it: no capability, no question
A server **MUST NOT** send an input request the client didn't declare. Connect *without* an `elicitation_callback` and the SDK refuses with the spec's `-32021` MissingRequiredClientCapability error, naming what is missing.

```python
from mcp.shared.exceptions import MCPError

async with Client(travel) as client:          # no elicitation_callback -> no elicitation capability
    try:
        await client.call_tool("book_trip", {"destination": "Barcelona"})
    except MCPError as err:
        print("code:", err.error.code)
        print("message:", err.error.message)
        print("data:", err.error.data)
```

### 5. Sampling (deprecated): the server borrows the host's model
Sampling still works during the deprecation window. A resolver returns `Sample(...)` with messages, a required `max_tokens` and `model_preferences`. The client's `sampling_callback` is where a host would show the prompt for approval, **pick a model** from the hints and priorities, call its LLM and show the answer for review. Our fake host has three models and does the hint matching the spec describes (substring, in order, then priorities).

```python
from mcp.server.mcpserver import Sample

flights = MCPServer("flights")
FLIGHTS = "IB3101 07:10 €180 direct | VY1307 06:30 €95 1 stop | BA478 21:40 €70 red-eye"


def analyse(preferences: str) -> Sample:
    return Sample(
        [types.SamplingMessage(role="user", content=types.TextContent(
            type="text", text=f"Recommend the best flight.\n{FLIGHTS}\nUser preferences: {preferences}"))],
        max_tokens=200,
        system_prompt="You are a travel expert.",
        model_preferences=types.ModelPreferences(
            hints=[types.ModelHint(name="sonnet"), types.ModelHint(name="claude")],
            cost_priority=0.3, speed_priority=0.2, intelligence_priority=0.9),
    )


@flights.tool()
def find_best_flight(preferences: str,
                     advice: Annotated[types.CreateMessageResult, Resolve(analyse)]) -> str:
    """Recommend a flight using the client's LLM (deprecated sampling)."""
    return f"[{advice.model}] {advice.content.text}"


HOST_MODELS = {"claude-opus-5-5": {"intelligence": 0.95, "speed": 0.4, "cost": 0.2},
               "claude-haiku-fast": {"intelligence": 0.6, "speed": 0.95, "cost": 0.9},
               "gemini-pro": {"intelligence": 0.9, "speed": 0.6, "cost": 0.5}}


def choose_model(prefs: types.ModelPreferences | None) -> str:
    for hint in (prefs.hints or []) if prefs else []:
        matches = [m for m in HOST_MODELS if hint.name and hint.name in m]
        if matches:
            return matches[0]
    p = prefs or types.ModelPreferences()
    score = lambda m: ((p.intelligence_priority or 0) * HOST_MODELS[m]["intelligence"] +
                       (p.speed_priority or 0) * HOST_MODELS[m]["speed"] +
                       (p.cost_priority or 0) * HOST_MODELS[m]["cost"])
    return max(HOST_MODELS, key=score)


async def host_llm(context, params: types.CreateMessageRequestParams):
    model = choose_model(params.model_preferences)
    print(f"  [host] approve sampling? prompt={params.messages[0].content.text.splitlines()[0]!r} "
          f"maxTokens={params.max_tokens} -> approved, using {model}")
    reply = "VY1307: morning departure, one stop, cheapest option that fits."   # a deterministic 'LLM'
    return types.CreateMessageResult(role="assistant", model=model, stop_reason="endTurn",
                                     content=types.TextContent(type="text", text=reply[: params.max_tokens * 4]))


async with Client(flights, sampling_callback=host_llm) as client:
    interim = await client.session.call_tool("find_best_flight", {"preferences": "morning, max 1 stop"},
                                              allow_input_required=True)
    request = next(iter(interim.input_requests.values()))
    print("input request on the wire:\n", wire(request)[:900])
    final = await client.call_tool("find_best_flight", {"preferences": "morning, max 1 stop"})
    print("\nfinal:", final.content[0].text)
```

There are no "sonnet" models in our host, so the first hint misses and `"claude"` matches. That is exactly the advisory, substring-based behaviour the spec describes.

### 6. Same server, old protocol: legacy mode uses server-initiated requests
With `mode="legacy"`, the client speaks 2025-11-25 and the SDK sends `sampling/createMessage` as a real **server-to-client request** in the middle of the call, which is the pre-MRTR way. The resolver code doesn't change. The old imperative helpers like `ctx.elicit(...)` only work in that legacy era, though. On a 2026-07-28 connection there is no back-channel, and they fail.

```python
legacy_demo = MCPServer("legacy-demo")


class Answer(BaseModel):
    name: str


@legacy_demo.tool()
async def ask_name_old_style(ctx: Context) -> str:
    """Ask for a name the pre-2026 way (server-initiated elicitation/create)."""
    result = await ctx.elicit("What is your name?", Answer)
    return f"{result.action}: {getattr(result, 'data', None)}"


async def name_ui(context, params):
    return types.ElicitResult(action="accept", content={"name": "Ada"})

async with Client(flights, mode="legacy", sampling_callback=host_llm) as old:
    print("legacy era", old.protocol_version, "->", (await old.call_tool(
        "find_best_flight", {"preferences": "cheap"})).content[0].text)

for mode in ["legacy", "auto"]:
    async with Client(legacy_demo, mode=mode, elicitation_callback=name_ui) as c:
        try:
            r = await c.call_tool("ask_name_old_style", {})
            print(f"{c.protocol_version}: ctx.elicit ->", r.content[0].text)
        except Exception as err:
            print(f"{c.protocol_version}: ctx.elicit -> {type(err).__name__}: {err}")
```

This is the migration lesson in code: **write new servers with resolvers or explicit `InputRequiredResult`s** (lesson 5.3), not with server-initiated calls.

### 7. Sampling with tools (also deprecated): needs `sampling.tools`
A server can give the host's model a set of tools scoped to the request. Without the `sampling.tools` capability, the SDK refuses to send such a request. With it, the callback receives `tools` and `toolChoice`, and the model can answer with `tool_use` blocks and `stopReason: "toolUse"`.

```python
weather = MCPServer("weather")
GET_WEATHER = types.Tool(name="get_weather", description="Get current weather for a city",
                         input_schema={"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]})


def plan(question: str) -> Sample:
    return Sample([types.SamplingMessage(role="user", content=types.TextContent(type="text", text=question))],
                  max_tokens=300, tools=[GET_WEATHER], tool_choice=types.ToolChoice(mode="auto"))


@weather.tool()
def compare_weather(question: str,
                    step: Annotated[types.CreateMessageResultWithTools, Resolve(plan)]) -> str:
    """Let the client's model decide which weather lookups to make."""
    return json.dumps(step.model_dump(by_alias=True, exclude_none=True, mode="json"))


async def tool_llm(context, params):
    print("  [host] tools offered:", [t.name for t in params.tools or []], "| toolChoice:", params.tool_choice.mode)
    return types.CreateMessageResultWithTools(
        role="assistant", model="claude-opus-5-5", stop_reason="toolUse",
        content=[types.ToolUseContent(type="tool_use", id="call_1", name="get_weather", input={"city": "Paris"}),
                 types.ToolUseContent(type="tool_use", id="call_2", name="get_weather", input={"city": "London"})])

async with Client(weather, sampling_callback=tool_llm) as c:          # sampling, but not sampling.tools
    try:
        await c.call_tool("compare_weather", {"question": "Paris or London?"})
    except MCPError as err:
        print("without sampling.tools ->", err.error.code, err.error.message)

tools_cap = types.SamplingCapability(tools=types.SamplingToolsCapability())
async with Client(weather, sampling_callback=tool_llm, sampling_capabilities=tools_cap) as c:
    out = await c.call_tool("compare_weather", {"question": "Paris or London?"})
    print("with sampling.tools    ->", out.content[0].text)
```

In a full loop the server would now run `get_weather` twice and send a *new* sampling request whose history ends with a user message of **only** `tool_result` blocks (`toolUseId` `call_1` and `call_2`), repeating until `endTurn`.

### 8. Roots (deprecated), and the recommended replacement
First the deprecated way. A `ListRoots()` resolver makes the server ask the client for its `file://` roots. Then the **migration**: the server takes its allowed directories from **configuration** at launch, and the tool takes the directory as a **parameter**. It validates every path by resolving it (which defeats `..` and symlinks) and checking it stays inside an allowed directory.

```python
import tempfile
from pathlib import Path

from mcp.server.mcpserver import ListRoots
from mcp.server.mcpserver.exceptions import ToolError

workspace = Path(tempfile.mkdtemp())
(workspace / "itineraries").mkdir()
(workspace / "itineraries" / "barcelona.md").write_text("Day 1: Sagrada Familia")
(workspace / "secrets.txt").write_text("do not leak")

# --- deprecated: roots via an input request ---
roots_server = MCPServer("roots-demo")


def fetch_roots() -> ListRoots:
    return ListRoots()


@roots_server.tool()
def list_workspace(roots: Annotated[types.ListRootsResult, Resolve(fetch_roots)]) -> list[str]:
    """List files under the client's roots (deprecated mechanism)."""
    files = []
    for root in roots.roots:
        base = Path(str(root.uri).removeprefix("file://"))
        files += [str(p.relative_to(base)) for p in sorted(base.rglob("*")) if p.is_file()]
    return files


async def my_roots(context):
    return types.ListRootsResult(roots=[types.Root(uri=f"file://{workspace / 'itineraries'}", name="Itineraries")])

async with Client(roots_server, list_roots_callback=my_roots) as c:
    print("roots-based listing:", (await c.call_tool("list_workspace", {})).structured_content)

# --- recommended: server configuration + explicit tool parameter ---
ALLOWED_DIRS = [(workspace / "itineraries").resolve()]       # e.g. from argv/env when the host launches the server
files_server = MCPServer("files")


@files_server.tool()
def read_text_file(directory: str, filename: str) -> str:
    """Read a text file from a directory the server is configured to allow."""
    target = (Path(directory) / filename).resolve()
    if not any(target.is_relative_to(allowed) for allowed in ALLOWED_DIRS):
        raise ToolError(f"{filename!r} resolves outside the allowed directories")
    return target.read_text()


async with Client(files_server) as c:
    ok = await c.call_tool("read_text_file", {"directory": str(workspace / "itineraries"), "filename": "barcelona.md"})
    print("allowed  :", ok.is_error, ok.content[0].text)
    bad = await c.call_tool("read_text_file", {"directory": str(workspace / "itineraries"), "filename": "../secrets.txt"})
    print("traversal:", bad.is_error, bad.content[0].text)
```

The traversal attempt fails *inside the server* and comes back as `isError: true` with a reason the model can read. We raise `ToolError` on purpose: `MCPServer` hides the message of any *unexpected* exception (a plain `ValueError` would reach the client only as "Error executing tool read_text_file"). Also note that the directory now appears in the **tool call** itself, so the host's approval UI shows the user exactly which folder the model wants to touch.

### 9. Optional: migrate sampling to a direct provider call
The replacement for sampling is ordinary code: the server calls an LLM API with *its own* key. When `ANTHROPIC_API_KEY` is set, this tool asks Claude directly. Otherwise it uses a deterministic fallback so the notebook still runs.

```python
import os

direct = MCPServer("flights-direct")


@direct.tool()
def recommend_flight(preferences: str) -> str:
    """Recommend a flight by calling the LLM provider directly (no sampling)."""
    prompt = f"Recommend the best flight in one sentence.\n{FLIGHTS}\nUser preferences: {preferences}"
    if os.environ.get("ANTHROPIC_API_KEY"):
        import anthropic
        response = anthropic.Anthropic().messages.create(
            model="claude-opus-5-5", max_tokens=16000, messages=[{"role": "user", "content": prompt}])
        return "".join(b.text for b in response.content if b.type == "text")
    return "(offline fallback) VY1307 — morning, one stop, cheapest that fits."


async with Client(direct) as c:   # note: no sampling_callback, no sampling capability needed
    print((await c.call_tool("recommend_flight", {"preferences": "morning, max 1 stop"})).content[0].text)
```
