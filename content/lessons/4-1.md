## Summary
Module 3 taught what tools, resources and prompts *are*; this lesson is about shipping one. Following the official "Build an MCP server" tutorial, you set up a project with `uv`, create an `MCPServer`, and turn two plain Python functions — `get_alerts` and `get_forecast` — into tools whose JSON Schemas come from type hints and whose descriptions come from docstrings. You learn the one rule that breaks more first servers than any other (never write to stdout on stdio), how to run the same code over stdio or Streamable HTTP, how to load data once with a lifespan and reach it through the `Context` object, and how to wire the server into Claude Desktop and read its logs when it doesn't show up.

## Lesson
### Choosing an SDK
The official SDKs all offer the same core: create servers that expose tools, resources and prompts, build clients that connect to any server, local and remote transports, and type-safe protocol compliance. They differ in idiom and in **tier**, which reflects feature completeness, protocol support and maintenance commitment:

| Tier | SDKs |
| --- | --- |
| Tier 1 | TypeScript, Python, C#, Go, Rust, Ruby |
| Tier 2 | Java |
| Tier 3 | Swift, PHP, Kotlin |

This course uses the **Python SDK 2.x** (`mcp` on PyPI). The tutorial requires Python 3.10+ and **SDK 2.0.0 or higher**. That version matters: 2.x implements the stateless 2026-07-28 protocol and renamed v1's `FastMCP` to **`MCPServer`**. Old code doing `from mcp.server.fastmcp import FastMCP` now fails with a `ModuleNotFoundError` that points at the migration guide.

### Project setup with uv
The tutorial uses [`uv`](https://docs.astral.sh/uv/) for environments and dependencies:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh   # then restart the terminal
uv init weather && cd weather
uv venv && source .venv/bin/activate
uv add "mcp[cli]"                                 # SDK + the `mcp` dev CLI
touch weather.py
```

`uv run weather.py` starts the server. The `[cli]` extra installs an `mcp` command (`mcp dev`, `mcp run`, `mcp install`). `mcp dev weather.py` launches your server under the MCP Inspector (lesson 4.3).

### MCPServer: tools from type hints and docstrings
```python
from typing import Any
import httpx2
from mcp.server import MCPServer

mcp = MCPServer("weather")          # the name clients see in serverInfo

@mcp.tool()
async def get_alerts(state: str) -> str:
    """Get weather alerts for a US state.

    Args:
        state: Two-letter US state code (e.g. CA, NY)
    """
    ...
```

The docs put it in one sentence: *"The MCPServer class uses Python type hints and docstrings to automatically generate tool definitions."* In detail:

| You write | Clients see in `tools/list` |
| --- | --- |
| function name | `name` (override with `@mcp.tool(name=...)`) |
| docstring | `description` |
| typed parameters | `inputSchema` (a JSON Schema object, `required` = params without defaults) |
| return annotation | `outputSchema`; results also carry `structuredContent` (`str`/`int`/lists are wrapped as `{"result": ...}`; a bare `dict` gives *no* schema, so use a Pydantic model, `TypedDict` or `dict[str, int]`) |
| a parameter typed `Context` | nothing: it is injected, never exposed |
| `@mcp.tool(title=..., annotations=ToolAnnotations(...))` | `title`, `annotations` |

> **Pitfall (verified in mcp 2.3.0).** The Google-style `Args:` block is *not* split into per-parameter descriptions. It stays inside the tool `description` (indentation included), so the model reads it but the `inputSchema` properties get no `description`. For proper per-field docs, ranges and patterns, use `Annotated[float, Field(description="Latitude", ge=-90, le=90)]`. Pydantic then validates arguments *before* your function runs.

`httpx2` is the HTTP client the SDK itself depends on, so installing `mcp` already brought it in. Async tools are first-class: the tutorial's `make_nws_request` uses `httpx2.AsyncClient` with a 30 s timeout and returns `None` on any exception. The tools turn that into a friendly string ("Unable to fetch alerts or no alerts found.").

### The weather example
The tutorial server wraps the US National Weather Service API:

- **`get_alerts(state)`** calls `/alerts/active/area/{state}` and formats each alert's event, area, severity, description and instructions, joined by `---`.
- **`get_forecast(latitude, longitude)`** takes two hops. `/points/{lat},{lon}` returns a grid record whose `properties.forecast` URL gives the periods. It formats the next **5** periods (name, temperature, wind, detailed forecast).
- Finally `mcp.run(transport="stdio")` under `if __name__ == "__main__":`.

Notice the design choices: failures come back as **readable strings** rather than exceptions, and output is capped at five periods. Lesson 4.2 turns both instincts into a discipline (actionable `isError` results, truncation).

### Logging: never write to stdout on stdio
Every language tab of the tutorial opens with the same warning:

> **Spec rule (stdio transport).** The server **MUST NOT** write anything to its `stdout` that is not a valid MCP message. It **MAY** write UTF-8 to `stderr` for logging, and the client **SHOULD NOT** assume stderr output means an error.

On stdio, stdout *is* the JSON-RPC channel: one message per line. A stray `print("Processing request")` puts a non-JSON line on the wire. Depending on the client, that line is skipped with a parse error, or the connection breaks. Use the standard `logging` module, which writes to stderr, with one logger per module (`logging.getLogger(__name__)`). Every SDK has its own trap:

| Language | ❌ on stdio | ✅ instead |
| --- | --- | --- |
| Python | `print()` | `logging` (stderr) |
| TypeScript | `console.log()` | `console.error()` |
| Java | `System.out.println()` | a logger configured off stdout |
| C# | `Console.WriteLine()` | a logger; `CreateEmptyApplicationBuilder` |
| Rust | `println!()` | `eprintln!()`, `tracing` |
| Go | `fmt.Println()` | `log.Println()` (stderr) |

**HTTP servers** have no such constraint: stdout is not the wire. The debugging guide adds that stderr is *not* captured by the client there, so use your own log aggregation or OpenTelemetry.

> **SDK detail (verified in mcp 2.3.0).** While `mcp.run(transport="stdio")` is serving, Python SDK 2.x moves the protocol stream to a private file descriptor and points fd 1 at stderr. So a *flushed* `print()` inside a tool lands in the log. That safety net has holes. A `print()` at import time, before `run()`, goes straight onto the wire. Text still sitting in Python's stdout buffer gets flushed at shutdown, *after* fd 1 is restored, so it also ends up on the protocol stream. Other SDKs offer no protection at all. Don't rely on it.

### Logging over the protocol is deprecated
2025-era servers also sent logs *to the client* with `notifications/message` (in Python, `ctx.info(...)`). **In 2026-07-28 the Logging feature is deprecated (SEP-2577).** New servers **SHOULD NOT** adopt it and should log to stderr (stdio) or OpenTelemetry. Where it remains, delivery is **per-request opt-in**: the server **MUST NOT** emit `notifications/message` for a request whose `_meta` lacks `io.modelcontextprotocol/logLevel`. In the 2.x SDK, `ctx.info()` emits an `MCPDeprecationWarning`. A client only receives the message if it set `Client(..., log_level="info")`.

### Running it: stdio vs Streamable HTTP
| | stdio | Streamable HTTP |
| --- | --- | --- |
| Start | `mcp.run(transport="stdio")` (the default) | `mcp.run(transport="streamable-http", host=..., port=...)` |
| Who launches it | the host spawns it as a subprocess | you deploy it; clients connect to `http://host:port/mcp` |
| Defaults | n/a | `127.0.0.1:8000`, path `/mcp` |
| Logging | stderr only; the host captures it | stdout is fine; the host does not see your logs |
| Embedding | n/a | `mcp.streamable_http_app()` returns a Starlette ASGI app you can mount |

The same tool code serves both. With the 2.x SDK, both transports answer 2026-07-28 clients (`server/discover`, no handshake) *and* 2025-era clients that open with `initialize`.

### Lifespan: load once, use everywhere
Opening a database pool, reading a large file or creating an API client per call is wasteful. `MCPServer(name, lifespan=fn)` takes an async context manager that runs at startup, yields a state object, and cleans up at shutdown:

```python
@asynccontextmanager
async def lifespan(server: MCPServer):
    db = await Database.connect()        # startup
    try:
        yield AppState(db=db)            # visible to every handler
    finally:
        await db.disconnect()            # shutdown

mcp = MCPServer("weather", lifespan=lifespan)

@mcp.tool()
async def query(sql: str, ctx: Context) -> str:
    db = ctx.request_context.lifespan_context.db
```

It runs once per server process for stdio and for the HTTP app, and once per connection with an in-process `Client(mcp)`. Because 2026-07-28 has **no protocol session**, the lifespan is for *process* resources such as pools, caches and clients. It is not a place for per-user conversation state; lesson 4.2 shows explicit handles for that.

### The Context object
Add a parameter annotated `Context` (from `mcp.server.mcpserver`) and the SDK injects it:

| Member | Use |
| --- | --- |
| `await ctx.report_progress(progress, total, message)` | `notifications/progress`, sent only if the request carried a `progressToken` (the Python client adds one when you pass `progress_callback`) |
| `await ctx.read_resource(uri)` | read one of *this server's* resources from inside a tool |
| `ctx.request_context.lifespan_context` | the object your lifespan yielded |
| `ctx.request_id`, `ctx.protocol_version`, `ctx.client_capabilities`, `ctx.headers` | request metadata (headers only on HTTP; treat them as untrusted input) |
| `await ctx.elicit(...)` | ask the user for input (lesson 5.3, via multi round-trip requests in 2026-07-28) |
| `ctx.info/debug/warning/error/log` | deprecated protocol logging (see above) |

### Connecting Claude Desktop
Claude Desktop reads `claude_desktop_config.json`:

| OS | Path |
| --- | --- |
| macOS | `~/Library/Application Support/Claude/claude_desktop_config.json` |
| Linux | `~/.config/Claude/claude_desktop_config.json` |
| Windows | `%APPDATA%\Claude\claude_desktop_config.json` |

```json
{
  "mcpServers": {
    "weather": {
      "command": "uv",
      "args": ["--directory", "/ABSOLUTE/PATH/TO/PARENT/FOLDER/weather", "run", "weather.py"]
    }
  }
}
```

This tells Claude Desktop that there is a server named `weather` and to launch it with `uv --directory … run weather.py`. The details that bite:

- Paths **must be absolute**. The host may start your process with an undefined working directory (`/` on macOS). On Windows, use `\\` or `/` in JSON.
- You may need the **full path to `uv`** (`which uv` / `where uv`), because GUI apps do not see your shell's `PATH`.
- Stdio servers inherit only a limited set of environment variables; pass secrets and settings via an `"env": {...}` key.
- After editing, **fully quit** Claude Desktop (Cmd+Q, tray → Quit, or `pkill -f claude-desktop` on Linux). Closing the window is not enough. Then check the "Add files, connectors, and more" (+) menu → **Connectors** for `weather`.

### What happens under the hood
When you ask "What's the weather in Sacramento?": (1) the client sends your question to Claude, (2) Claude reads the available tools and decides which to use, (3) the client executes the chosen tool through the MCP server, (4) the result goes back to Claude, (5) Claude writes a natural-language answer, (6) you see it. At the protocol level, Claude Desktop spawned your process at startup, discovered it (`server/discover` in 2026-07-28, `initialize` in older eras), fetched `tools/list`, and step 3 is a `tools/call` written as one line to your stdin.

### Other SDKs at a glance
The tutorial repeats the weather server in eight languages. The shapes rhyme:

- **TypeScript**: `npm install @modelcontextprotocol/server zod`. Register tools with `server.registerTool(name, {description, inputSchema: z.object(...)}, handler)` inside a `createServer()` factory, then `serveStdio(createServer)`. `serveStdio` negotiates both eras and calls the factory per instance (including a discarded `server/discover` probe), so it must return a **fresh** `McpServer` each time. Hand-wiring `server.connect(new StdioServerTransport())` still compiles but **only serves 2025-era clients**.
- **Java (Spring AI)**: `@Tool`/`@ToolParam` annotations, exposed via `MethodToolCallbackProvider`.
- **C#**: `builder.Services.AddMcpServer().WithStdioServerTransport()`, with `[McpServerToolType]`/`[McpServerTool]` attributes.
- **Rust (`rmcp`)**: `#[tool_router]` and `#[tool]` macros, served over `(stdin(), stdout())`.
- **Go**: `mcp.NewServer`, `mcp.AddTool`, `server.Run(ctx, &mcp.StdioTransport{})`.
- **Kotlin** and **Ruby** (`MCP::Tool` subclasses, `MCP::Server::Transports::StdioTransport`) follow suit.

### Troubleshooting
- **Logs**: `~/Library/Logs/Claude` (macOS), `~/.config/Claude/logs/` (Linux), `%APPDATA%\Claude\logs` (Windows). `mcp.log` covers connections and failures. `mcp-server-SERVERNAME.log` holds your server's **stderr**, so your `logging` output lands there. Watch them with `tail -n 20 -f ~/Library/Logs/Claude/mcp*.log`.
- **Server not showing up**: check the JSON syntax, use absolute paths, and fully restart.
- **Tool calls failing silently**: read the logs, check that the server runs on its own (`uv run weather.py`), then restart.
- **Weather API errors**: "Failed to retrieve grid point data" means non-US coordinates, an NWS outage or rate limiting. "No active alerts" is not an error.

## Key points
- `MCPServer` (Python SDK ≥ 2.0, which replaced v1's `FastMCP`) generates tool definitions from **type hints** (inputSchema/outputSchema) and **docstrings** (description). For per-parameter descriptions and constraints, use `Annotated[..., Field(...)]`.
- On **stdio, stdout is the wire**: never `print()` to it. Log to **stderr** with `logging`. HTTP servers may use stdout freely.
- Protocol logging (`notifications/message`, `ctx.info`) is **deprecated in 2026-07-28** and only delivered when a request opts in with `io.modelcontextprotocol/logLevel`.
- The same server runs with `mcp.run(transport="stdio")` or `mcp.run(transport="streamable-http")` (default `127.0.0.1:8000/mcp`), and the SDK answers both protocol eras.
- A **lifespan** loads expensive resources once and exposes them as `ctx.request_context.lifespan_context`. It is not a substitute for per-user state.
- `Context` gives tools `report_progress`, `read_resource`, request metadata and `elicit`. It is injected and never appears in the schema.
- Claude Desktop config: `mcpServers` → `command` + `args` (+ `env`), **absolute paths**, maybe the full path to `uv`, and a **full quit** after edits.
- Debug from the logs: `mcp.log` for connections, `mcp-server-NAME.log` for your server's stderr.

## Pitches
### Walk me through building an MCP server
I start with uv and the official Python SDK, version 2 or later. I create an MCPServer, write plain typed functions, and decorate them as tools: type hints become the input and output JSON Schemas, docstrings and Field descriptions become what the model reads. Expensive setup like a database pool goes in a lifespan. I run it over stdio for local hosts or Streamable HTTP for remote ones. Then I test it with the Inspector and wire it into Claude Desktop with absolute paths.

### Why do stdio servers break when you print?
Over stdio the host talks to my server through its standard input and output, one JSON-RPC message per line. So stdout is not a console; it's the protocol channel, and the spec says nothing but valid MCP messages may go there. A debug print injects a line that isn't JSON. Some clients skip it with an error, others drop the connection. The fix is boring and absolute: log to stderr with the logging module. The host captures stderr into a per-server log file anyway.

### How do you share expensive resources across tool calls?
I use the server's lifespan, an async context manager that runs once at startup, yields a state object and cleans up at shutdown. Tools reach it through the injected Context as request_context.lifespan_context. That's the right home for connection pools, HTTP clients or a loaded index. What I don't put there is per-user conversation state, because 2026-07-28 has no protocol session. For that I return an explicit handle from a tool and accept it back as an argument.

## Interview
### How does the Python SDK turn a function into an MCP tool definition?
`@mcp.tool()` inspects the function. The name becomes `name`, and the docstring becomes `description`. The parameters are compiled into a Pydantic model whose JSON Schema is the `inputSchema`, with params without defaults listed in `required`. The return annotation produces an `outputSchema`, and results carry `structuredContent` (primitives wrapped as `{"result": ...}`) plus a text block. A parameter typed `Context` is injected and excluded from the schema. Gotchas: a Google-style `Args:` section is not split into property descriptions (it stays in the tool description), so use `Annotated[T, Field(description=..., ge=..., pattern=...)]`. Arguments are validated by Pydantic before your code runs, and a failure comes back as an `isError: true` result the model can read.

### A user says your server works from the terminal but never appears in Claude Desktop. How do you debug it?
First, the config: valid JSON, a `mcpServers` entry, an **absolute** path to the project, possibly the absolute path to `uv`/`node` since GUI apps lack your shell `PATH`, and a **full quit** and restart (closing the window doesn't reload). Second, the logs: `mcp.log` shows whether the spawn or connection failed, and `mcp-server-weather.log` shows the server's stderr, usually a traceback. The classic causes are a relative path (the working directory may be `/`), a missing environment variable (stdio servers inherit only a limited set, so add an `env` key), and a `print()` to stdout corrupting the stream. Then reproduce outside Claude with the Inspector.

### What changes when you switch a server from stdio to Streamable HTTP?
The tool code doesn't change; the deployment and operational model do. With stdio the host spawns one process per user, stdout is reserved for protocol messages and stderr goes into the host's logs. With HTTP you run a long-lived service at `/mcp` (SDK default `127.0.0.1:8000`). Stdout logging is fine, but the client never sees your logs, so you need your own aggregation or OpenTelemetry. You also take on remote-server concerns: authorization (OAuth, module 6), Origin and DNS-rebinding protection, scaling across replicas. Because 2026-07-28 is stateless, any replica can answer any request as long as you keep state in explicit handles or shared stores.

### Is `ctx.info()` a good way to log from a 2026-07-28 server?
No. Protocol logging (`notifications/message`) is **deprecated** as of 2026-07-28 (SEP-2577). New implementations SHOULD NOT adopt it and should log to stderr on stdio or to OpenTelemetry. It also changed shape: there is no session-wide `logging/setLevel` any more. A client opts in **per request** with `io.modelcontextprotocol/logLevel` in `_meta`, and the server MUST NOT emit log notifications otherwise. In SDK 2.x, `ctx.info()` raises a deprecation warning, and with the default client nothing arrives at all.

### Tricky: your stdio server has a `print()` inside a tool and it still works. Why, and is it fine?
Python SDK 2.x partly protects you while it is serving. It moves the real protocol stream to a private file descriptor and points fd 1 at stderr, so a *flushed* `print()` inside a handler ends up in the log. It is still a bug, and the protection has holes. A `print()` at import time or before `run()` goes straight onto the wire. Unflushed text stays in Python's stdout buffer and is written out at shutdown, after the real stdout has been restored, so it lands on the protocol stream too. Other SDKs (TypeScript `console.log`, Go `fmt.Println`, …) give no protection at all. And a stdio client that is strict about framing may drop the connection on the first non-JSON line. Log to stderr explicitly and never depend on this safety net.

## Glossary
- MCPServer | MCPServer（高层服务器类） | The Python SDK 2.x high-level server class (formerly FastMCP) that builds tools, resources and prompts from decorated functions.
- uv | uv（Python 包与环境管理器） | The Python project and dependency manager the official tutorial uses (`uv init`, `uv add`, `uv run`).
- Lifespan | 生命周期钩子 | An async context manager run at server startup and shutdown whose yielded object is shared with every handler.
- Context | 上下文对象 | The object the SDK injects into tools that request it, offering progress, resource reads, elicitation and request metadata.
- stdout / stderr | 标准输出 / 标准错误 | On stdio, stdout carries only JSON-RPC messages; stderr is free for logs that the host may capture.
- claude_desktop_config.json | Claude Desktop 配置文件 | Claude Desktop's config file; its `mcpServers` map names each server with the `command`, `args` and `env` to launch it.
- Streamable HTTP | 可流式 HTTP 传输 | The remote transport: the server is an HTTP service at an endpoint such as `/mcp`.
- Progress notification | 进度通知 | `notifications/progress`, sent by `ctx.report_progress` when the request carried a progress token.
- Protocol logging (deprecated) | 协议日志（已弃用） | `notifications/message` log delivery, deprecated in 2026-07-28 and opt-in per request via `io.modelcontextprotocol/logLevel`.

### 2. The server file
This is the tutorial's `weather.py` with three upgrades: a **lifespan** that loads the dataset once, `Annotated` field descriptions and ranges, and `Context` progress reporting. All logging goes to **stderr**. The `NOISY` switch adds two deliberate `print()` bugs that we trigger in section 6.

```python
%%writefile {server_path}
"""Offline weather MCP server, shaped like the official tutorial."""
import json
import logging
import os
import sys
from contextlib import asynccontextmanager
from dataclasses import dataclass
from typing import Annotated

from pydantic import Field

from mcp.server import MCPServer
from mcp.server.mcpserver import Context

logging.basicConfig(level=logging.INFO, stream=sys.stderr,           # stderr, never stdout
                    format="%(asctime)s %(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("weather")

if os.environ.get("NOISY"):
    print("Weather server starting...", flush=True)   # BUG on stdio: not a JSON-RPC message


@dataclass
class WeatherData:
    alerts: dict
    points: dict


@asynccontextmanager
async def lifespan(server: MCPServer):
    path = os.environ["WEATHER_DATA"]       # absolute path, set by the host config's "env"
    logger.info("lifespan: loading %s", path)
    with open(path) as f:
        raw = json.load(f)
    yield WeatherData(alerts=raw["alerts"], points=raw["points"])
    logger.info("lifespan: shutting down")


mcp = MCPServer("weather", lifespan=lifespan)


def format_alert(a: dict) -> str:
    return (f"Event: {a.get('event', 'Unknown')}\nArea: {a.get('areaDesc', 'Unknown')}\n"
            f"Severity: {a.get('severity', 'Unknown')}\n"
            f"Description: {a.get('description', 'No description available')}\n"
            f"Instructions: {a.get('instruction', 'No specific instructions provided')}")


@mcp.tool()
async def get_alerts(state: Annotated[str, Field(description="Two-letter US state code, e.g. CA or NY")],
                     ctx: Context) -> str:
    """Get active weather alerts for a US state."""
    if os.environ.get("NOISY"):
        print(f"looking up alerts for {state}")    # BUG: where does this end up? (section 6)
    data: WeatherData = ctx.request_context.lifespan_context
    logger.info("get_alerts state=%s", state)
    features = data.alerts.get(state.upper())
    if features is None:
        return f"Unable to fetch alerts for {state!r}. Use a two-letter US state code such as CA."
    if not features:
        return "No active alerts for this state."
    return "\n---\n".join(format_alert(a) for a in features)


@mcp.tool()
async def get_forecast(latitude: Annotated[float, Field(description="Latitude of the location", ge=-90, le=90)],
                       longitude: Annotated[float, Field(description="Longitude of the location", ge=-180, le=180)],
                       ctx: Context) -> str:
    """Get the weather forecast (next 5 periods) for a US location."""
    data: WeatherData = ctx.request_context.lifespan_context
    await ctx.report_progress(0, 2, "resolving grid point")
    grid = data.points.get(f"{latitude:.2f},{longitude:.2f}")
    if grid is None:
        return "Unable to fetch forecast data for this location (only US locations are supported)."
    await ctx.report_progress(1, 2, "fetching forecast periods")
    periods = [f"{p['name']}:\nTemperature: {p['temperature']}°{p['temperatureUnit']}\n"
               f"Wind: {p['windSpeed']} {p['windDirection']}\nForecast: {p['detailedForecast']}"
               for p in grid["periods"][:5]]                                # only the next 5 periods
    await ctx.report_progress(2, 2, "done")
    return "\n---\n".join(periods)


if __name__ == "__main__":
    if len(sys.argv) == 3 and sys.argv[1] == "http":
```

### 6. Break it: a stray `print()` on stdout
Now set `NOISY=1` and talk to the server by hand. The first thing the server writes to stdout is not JSON. A strict client that does `json.loads(line)` on every line fails immediately.

```python
import subprocess

META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "strict-client", "version": "0"}}

proc = subprocess.Popen([sys.executable, str(server_path)], text=True,
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.PIPE,
                        env={**os.environ, "NOISY": "1", "WEATHER_DATA": str(data_path)})
proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": 1, "method": "tools/call",
                             "params": {"name": "get_alerts", "arguments": {"state": "NY"}, "_meta": META}}) + "\n")
proc.stdin.flush()

for n in range(1, 4):                       # read until the response with id 1 arrives
    line = proc.stdout.readline()
    try:
        msg = json.loads(line)
    except json.JSONDecodeError as exc:
        print(f"line {n}: NOT JSON -> {line.strip()!r}  ({exc.msg}) <- a strict client dies here")
        continue
    print(f"line {n}: valid JSON-RPC, id={msg.get('id')} -> {msg['result']['content'][0]['text']!r}")
    if msg.get("id") == 1:
        break

proc.stdin.close()                          # the client hangs up -> the server shuts down
proc.wait(timeout=10)
late_stdout, stderr_text = proc.stdout.read(), proc.stderr.read()
print("\nwritten to stdout AFTER the last response:", repr(late_stdout))
print("in-tool print found in stderr?", "looking up alerts for NY" in stderr_text)
```

Read both results carefully:

- The **startup** `print()` ran before `mcp.run()`, so it polluted the protocol channel.
- The **in-tool** `print()` (not flushed) sat in Python's stdout buffer and was written to the *protocol stream* at shutdown. SDK 2.x points fd 1 at stderr while serving, but it restores the real stdout on exit, and the buffer is flushed after that. Add `flush=True` to that print and re-run: it lands in stderr instead. Either way the result depends on buffering, which is exactly why you never print on stdio.
- The bug uses `flush=True` so it shows up deterministically. Without it, Python block-buffers stdout when stdout is a pipe, and the stray text appears at some unpredictable later moment, possibly in the middle of a message. That is even harder to debug.

The Python SDK's own client is lenient (it logs a parse error and skips the line). Other hosts are not obliged to be. The rule stays: on stdio, log to stderr.

### 8. Generate the Claude Desktop config
A small helper writes the `mcpServers` entry the way the tutorial recommends (`uv --directory <abs> run weather.py`). It also writes the direct-interpreter variant, and **lints** the result for the classic mistakes: relative paths, a bare command a GUI app may not find, and missing `env`.

```python
import shutil


def desktop_entry(server_file: Path, use_uv: bool = True) -> dict:
    env = {"WEATHER_DATA": str(data_path)}
    if use_uv:
        return {"command": shutil.which("uv") or "uv",
                "args": ["--directory", str(server_file.parent), "run", server_file.name], "env": env}
    return {"command": sys.executable, "args": [str(server_file)], "env": env}


def lint_entry(name: str, entry: dict) -> list[str]:
    problems = []
    if not os.path.isabs(entry["command"]):
        problems.append(f"{name}: command {entry['command']!r} is not absolute; GUI hosts may not see your PATH")
    for arg in entry.get("args", []):
        if ("/" in arg or "\\" in arg) and not os.path.isabs(arg):
            problems.append(f"{name}: relative path {arg!r}; the host's working directory may be '/'")
    for key, value in entry.get("env", {}).items():
        if value.endswith(".json") and not os.path.isabs(value):
            problems.append(f"{name}: env {key} is a relative path")
    return problems


config = {"mcpServers": {"weather": desktop_entry(server_path, use_uv=True),
                         "weather-python": desktop_entry(server_path, use_uv=False),
                         "broken": {"command": "uv", "args": ["--directory", "./weather", "run", "weather.py"]}}}
print(json.dumps(config, indent=2))
print("\nlint:")
for name, entry in config["mcpServers"].items():
    print(" ", name, "->", lint_entry(name, entry) or "ok")
print("\nmacOS file: ~/Library/Application Support/Claude/claude_desktop_config.json  (then fully quit Claude)")
```

### 9. Under the hood: the six steps, with a scripted "Claude"

```python
async def fake_model(question: str, tools) -> dict:
    """Step 2: choose a tool by reading names/descriptions (a stand-in for the LLM)."""
    q = question.lower()
    if "alert" in q:
        state = [w.strip("?.") for w in question.split() if w.strip("?.").isupper() and len(w.strip("?.")) == 2][0]
        return {"name": "get_alerts", "arguments": {"state": state}}
    return {"name": "get_forecast", "arguments": {"latitude": 38.58, "longitude": -121.49}}


question = "Are there any weather alerts in TX?"
async with Client(weather.mcp) as client:
    tools = (await client.list_tools()).tools
    print("1. host sends the question + tool list to the model:", question)
    choice = await fake_model(question, tools)
    print("2. model chooses:", choice)
    result = await client.call_tool(choice["name"], choice["arguments"])
    print("3. host executes it through MCP -> isError:", result.is_error)
    print("4. result goes back to the model:", result.content[0].text.count("Event:"), "alerts")
    events = [l.split(": ", 1)[1] for l in result.content[0].text.splitlines() if l.startswith("Event:")]
    print("5./6. answer shown to the user: Texas has", len(events), "active alerts:", ", ".join(events))

    import anthropic

    llm = anthropic.Anthropic()
    async with Client(weather.mcp) as client:
        tool_defs = [{"name": t.name, "description": t.description, "input_schema": t.input_schema}
                     for t in (await client.list_tools()).tools]
        messages = [{"role": "user", "content": "What's the weather in Sacramento (38.58, -121.49)?"}]
        response = llm.messages.create(model="claude-opus-5-5", max_tokens=16000, tools=tool_defs, messages=messages)
        while response.stop_reason == "tool_use":
            messages.append({"role": "assistant", "content": response.content})
            results = []
            for block in response.content:
                if block.type == "tool_use":
                    r = await client.call_tool(block.name, block.input)
                    results.append({"type": "tool_result", "tool_use_id": block.id,
                                    "content": r.content[0].text, "is_error": bool(r.is_error)})
            messages.append({"role": "user", "content": results})
            response = llm.messages.create(model="claude-opus-5-5", max_tokens=16000, tools=tool_defs, messages=messages)
        print("\nClaude:", "".join(b.text for b in response.content if b.type == "text"))
else:
    print("\n(skipped real model: set ANTHROPIC_API_KEY to let Claude do steps 2 and 5)")
```

### 10. The Context object beyond progress
A small companion server shows the rest of `Context`. It reads one of its own resources from inside a tool, inspects request metadata, and uses the **deprecated** protocol logging. Protocol logging only reaches a 2026-07-28 client that opted in with `log_level`.

```python
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

ctx_demo = MCPServer("ctx-demo")


@ctx_demo.resource("config://units")
def units() -> str:
    return "imperial"


@ctx_demo.tool()
async def describe_request(ctx: Context) -> dict[str, str]:
    """Report what the Context object knows about this request."""
    units_text = list(await ctx.read_resource("config://units"))[0].content
    with warnings.catch_warnings():
        warnings.simplefilter("ignore")
        await ctx.info("describe_request called")          # deprecated notifications/message
    return {"request_id": ctx.request_id, "protocol": ctx.protocol_version or "", "units": units_text}


for level in [None, "info"]:
    received = []

    async def on_log(params):
        received.append(f"[{params.level}] {params.data}")

    async with Client(ctx_demo, logging_callback=on_log, log_level=level) as client:
        r = await client.call_tool("describe_request", {})
        print(f"log_level={level!r:7} -> structured={r.structured_content} | log messages received={received}")
```
