## Summary
The core MCP specification is deliberately small, and it changes slowly because every addition is permanent. Extensions are the pressure valve: optional, separately versioned additions identified by a reverse-DNS string such as `io.modelcontextprotocol/tasks`, negotiated through an `extensions` map in each side's capabilities, and always disabled until a developer opts in. This lesson explains how identifiers work, how official and experimental extensions are governed, how negotiation and graceful degradation work, and then digs into the most important official extension: **Tasks**. With Tasks, a server answers a slow `tools/call` with a durable task handle. The client polls `tasks/get`, supplies mid-flight input through `tasks/update` and can cancel with `tasks/cancel`. In the notebook you build both sides with the Python SDK's extension API.

## Lesson
### Why MCP has extensions
MCP extensions are *optional additions to the specification that define capabilities beyond the core protocol*. The docs name three reasons a feature might live outside the core:

- **Modular**: a distinct feature that only some deployments need, such as an alternative authentication flow.
- **Specialized**: logic for one industry or use case.
- **Experimental**: an idea being incubated before it is considered for the core.

This follows from the design principles in lesson 1.1. *Convergence over choice* and *stability over velocity* make the core hard to change: "no today leaves the door open, yes closes it forever". Extensions are where ideas get tested in real implementations, while the spec is where they get committed. Several features you will meet in this module started or ended up here. Tasks was moved **out** of the core in 2026-07-28. MCP Apps, Skills over MCP and the authorization extensions were never core.

### Extension identifiers
Every extension has a unique **extension identifier** of the form `{vendor-prefix}/{extension-name}`. Identifiers follow the same grammar as `_meta` keys but with a **mandatory** prefix: dot-separated labels, then `/`, then a name. Official extensions use the vendor prefix `io.modelcontextprotocol`. A third party uses a reversed domain it owns, Java-package style, so a company owning `example.com` publishes `com.example/my-extension`. This avoids collisions without needing a central registry of names.

| Extension | Identifier | Repository |
| --- | --- | --- |
| MCP Apps | `io.modelcontextprotocol/ui` | `ext-apps` |
| Tasks | `io.modelcontextprotocol/tasks` | `ext-tasks` |
| Skills over MCP | `io.modelcontextprotocol/skills` | `ext-skills` |
| OAuth Client Credentials | `io.modelcontextprotocol/oauth-client-credentials` | `ext-auth` |
| Enterprise-Managed Authorization | `io.modelcontextprotocol/enterprise-managed-authorization` | `ext-auth` |

### Official and experimental extensions
**Official extensions** live in the `modelcontextprotocol` GitHub organization in repositories with the `ext-` prefix. **Experimental extensions** give Working Groups and Interest Groups a place to prototype before writing a formal proposal. They live in repositories with the `experimental-ext-` prefix, for example `experimental-ext-interceptors`. Experimental extensions have three ground rules:

1. Every experimental extension must be associated with a **Working Group or Interest Group**.
2. Repositories and published packages must **clearly indicate their experimental status**, in the README and in the package name.
3. **Core Maintainers keep oversight** and can archive or remove experimental repositories.

**Graduation** to official status goes through the standard SEP process on the **Extensions Track**. The incubation repository and its reference implementations serve as evidence that the extension is practical.

### Creating and evolving an extension
Official extensions follow a SEP-based lifecycle defined by SEP-2133:

1. **Propose**: open a SEP of type *Extensions Track* in the main MCP repository.
2. **Implement**: build at least one reference implementation in an official SDK. This is required **before** the SEP can be reviewed.
3. **Review**: Core Maintainers review the SEP and have final authority.
4. **Publish**: once approved, open a PR to add the extension to its extension repository.
5. **Adopt**: other clients, servers and SDKs can then implement it.

There are two requirements. Extension specifications must use **RFC 2119 language** (MUST, SHOULD, MAY), and every extension must have an associated working or interest group.

SDK support is optional. Implementing extensions is **not required for protocol conformance**, and SDK maintainers decide for themselves which extensions to support. They should, however, document which ones they support. Above all, **extensions are always disabled by default and require explicit opt-in from the developer.**

Extensions also **evolve independently** of the core. Their maintainers ship updates without Core Maintainer review. To keep changes backward compatible, add capability flags or versioning inside the extension's settings object rather than minting a new identifier. If a breaking change cannot be avoided, use a new identifier such as `io.modelcontextprotocol/my-extension-v2`. A **breaking change** includes removing or renaming fields, changing field types, altering the semantics of existing behaviour, and adding new required fields.

### Negotiation: the `extensions` capability
Revision 2026-07-28 added an `extensions` field to both `ClientCapabilities` and `ServerCapabilities`. Its keys are extension identifiers and its values are per-extension settings objects. An empty object `{}` means "supported, no settings". Each extension defines the schema of its own settings.

Because the protocol is stateless, the **client declares its extensions on every request**, inside `_meta["io.modelcontextprotocol/clientCapabilities"]`. The **server advertises its extensions in the `server/discover` result**:

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "New York"},
   "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
             "io.modelcontextprotocol/clientCapabilities": {
               "extensions": {"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}},
             "io.modelcontextprotocol/clientInfo": {"name": "ExampleClient", "version": "1.0.0"}}}}
```

```json
{"result": {"resultType": "complete", "supportedVersions": ["2026-07-28"],
            "capabilities": {"tools": {}, "extensions": {"io.modelcontextprotocol/ui": {}}}}}
```

An extension is active for a request only if **both** sides declare it. Because client capabilities travel per request, a server must check *this* request's declaration and not an earlier one. The Tasks spec puts this explicitly: a server must not return a task "to a client that did not include the extension capability on its request, **regardless of prior declarations**."

> **Spec rule (graceful degradation).** If one side supports an extension and the other does not, the supporting side must either **fall back to core behaviour** or, if the extension is mandatory, **reject the request with an appropriate error**. A UI-enhanced tool should still return meaningful text, while a server that requires an authentication extension can refuse clients that lack it.

The error to use is `-32021` (*Missing Required Client Capability*), with the missing extension in `data.requiredCapabilities.extensions`. Document the fallback behaviour in your extension's specification.

The **client matrix** tracks which hosts implement which official extension. MCP Apps is widely supported, including Claude, Claude Desktop, VS Code GitHub Copilot, ChatGPT, Cursor and Goose. The auth and Skills extensions have only a few implementations so far, such as the `mcpc` CLI, Archestra.AI, and partial Skills support in ChatGPT, fast-agent and the Inspector. To add support to a client, read the extension spec, declare it in `clientCapabilities.extensions`, read the server's `extensions` from `server/discover`, implement the requirements, and send a PR to update the matrix.

### Tasks: why not just block?
Some tool calls take seconds, minutes or hours: CI pipelines, batch jobs and human approvals. You could keep the request open until the work finishes, but Tasks solve problems that blocking cannot:

- **No long-lived connections.** Clients and HTTP intermediaries impose timeouts that make blocking impractical beyond a few seconds.
- **Crash resilience.** A task ID is a **durable handle**, so a client that restarts can resume polling with the same ID.
- **Progress visibility.** Tasks carry a status and an optional `statusMessage`.
- **Mid-flight interaction.** A task can pause in `input_required`, and the client answers through `tasks/update` without a second connection or any unsolicited server-to-client request.
- **Server-directed.** The server decides per request whether to create a task. The client opts in once through the capability and handles whichever result shape arrives.

Tasks fit long-running operations, human-in-the-loop approvals, wrappers around external job APIs that already have job IDs, unreliable connections such as mobile clients, and batch processing where partial progress matters.

### How a task is created
The client declares `"io.modelcontextprotocol/tasks": {}` in its per-request capabilities, and the server advertises the same key in `server/discover` (no settings are defined yet). Only `tools/call` supports tasks today. Implementations should expect more request types to support them in future revisions.

A task-capable `tools/call` is **polymorphic**: it may return an ordinary `CallToolResult` or a `CreateTaskResult`. The two are distinguished by `resultType`, which the extension extends with a reserved value, `"task"`. A `CreateTaskResult` is `Result & Task`, so the task fields sit directly in the result:

```json
{"jsonrpc": "2.0", "id": 2,
 "result": {"resultType": "task", "taskId": "786512e2-9e0d-44bd-8f29-789f320fe840",
            "status": "working", "statusMessage": "The operation is now in progress.",
            "createdAt": "2025-11-25T10:30:00Z", "lastUpdatedAt": "2025-11-25T10:40:00Z",
            "ttlMs": 60000, "pollIntervalMs": 5000}}
```

| `Task` field | Meaning |
| --- | --- |
| `taskId` | Stable, server-generated identifier |
| `status` | `working`, `input_required`, `completed`, `failed` or `cancelled` |
| `statusMessage` | Optional human-readable state; may be shown to the user or model |
| `createdAt`, `lastUpdatedAt` | ISO 8601 timestamps |
| `ttlMs` | Lifetime from creation in ms, `null` for unlimited; may change |
| `pollIntervalMs` | Suggested polling interval; clients SHOULD honour it; may change |

> **Spec rule.** A server **MUST NOT** return `CreateTaskResult` until the task is **durably created**, meaning a `tasks/get` for that ID would already resolve. In an eventually consistent store, wait for consistency first. This spares clients from polling speculatively for a task that does not exist yet.

If a server needs input *before* it can decide to create a task, it should resolve that synchronously with the ordinary MRTR flow (lesson 5.3) and only then return the task.

### Polling and the lifecycle
The client polls `tasks/get` with `{"taskId": ...}`. The response is a `DetailedTask` whose `resultType` is `"complete"`, because it is the normal result of `tasks/get`. Its fields depend on the status:

| Status | Extra field | Meaning |
| --- | --- | --- |
| `working` | none | Still running |
| `input_required` | `inputRequests` | The server needs input from the client before continuing |
| `completed` | `result` | Exactly what the original request would have returned, e.g. a `CallToolResult` |
| `failed` | `error` | A **JSON-RPC error** occurred during execution |
| `cancelled` | none | The work was cancelled |

`completed`, `failed` and `cancelled` are **terminal**, so a task in one of those states never changes again. The allowed transitions are working ⇄ input_required, and from either of those to a terminal state.

> **Pitfall.** A tool that finishes with `isError: true` is **`completed`**, not `failed`. `failed` is reserved for JSON-RPC protocol errors and MUST NOT be used for tool-level errors. This mirrors the core rule that tool errors belong in the result, where the model can see them.

### Mid-flight input: `tasks/update`
When the server needs something during execution, such as a confirmation, it moves the task to `input_required`. The next `tasks/get` then carries `inputRequests`, a map of keyed embedded requests like `{"approve": {"method": "elicitation/create", "params": {...}}}`. The client answers with **`tasks/update`** `{"taskId", "inputResponses": {"approve": {"action": "accept", "content": {...}}}}`, and the server replies with an empty acknowledgement (`resultType: "complete"`).

Several rules make this robust:

- `inputRequests` is a **point-in-time snapshot**: it contains all outstanding requests and repeats on every poll until they are answered. Clients SHOULD **deduplicate by key** so the user is not asked twice.
- Each key MUST be **unique over the task's lifetime** and is never reused. That lets servers **ignore responses for unknown or already-answered keys**.
- The acknowledgement is **eventually consistent**: `tasks/get` may still show `input_required` for a moment after it. A partial set of responses is allowed, and the task stays in `input_required` until the rest arrive.
- Embedded requests keep their normal **trust model**. An elicitation that arrives through a task is treated exactly like a direct `elicitation/create`. A task is not a higher-trust channel.

> **Task input vs MRTR.** The two look alike but differ. MRTR (`InputRequiredResult`) answers come back on a **retry of the original request**. Task input is surfaced by `tasks/get` and answered by `tasks/update`, while the task keeps running.

### Cancellation and notifications
`tasks/cancel {"taskId"}` signals **intent**. The server MUST acknowledge it with an empty result, but cancellation is **cooperative**. The server decides whether and when to stop, and the task may still end `completed` if the work finished first. `notifications/cancelled` **MUST NOT** be used for tasks. After cancelling, a client may forget the task without polling again.

Polling is the default, but servers MAY also push `notifications/tasks`. Each notification carries the full `DetailedTask`, exactly what `tasks/get` would return. Clients opt in by sending `subscriptions/listen` with `notifications.taskIds`. `notifications/progress` and `notifications/message` are not supported on tasks.

### Errors, routing and security
| Situation | Response |
| --- | --- |
| Unknown or expired `taskId` | `-32602` Invalid params (MUST for `tasks/get`, SHOULD for update/cancel) |
| Client did not declare the extension but calls `tasks/*` or subscribes to task notifications | `-32021` with `requiredCapabilities` |
| Server can only serve the request as a task, but the client did not declare Tasks | `-32021` |
| Internal failure | `-32603` |

Over Streamable HTTP, the client **MUST** set the `Mcp-Name` header to `params.taskId` on `tasks/get`, `tasks/update` and `tasks/cancel`. Load balancers can then route every call for a task to the instance that holds its state.

On security, task IDs can act as bearer tokens, so they **MUST** be generated with enough entropy to be unguessable. Every task request **MUST** be authenticated and authorized against the task's owner. Because the extension has no `tasks/list`, one caller can no longer discover another caller's tasks. The extension also reserves the `tasks/` method prefix, the `notifications/tasks/` notification prefix and the `resultType` value `"task"`.

### What changed from 2025-11-25
In 2025-11-25, tasks were an **experimental core feature**. Revision 2026-07-28 (SEP-2663) moved them into the official extension `io.modelcontextprotocol/tasks` and redesigned them:

| 2025-11-25 (core, experimental) | 2026-07-28 (extension) |
| --- | --- |
| Client requested a task per call (a `task` param on `tools/call`) | **Server-directed**: the server returns a handle whenever it chooses, with no per-request opt-in |
| Blocking `tasks/result` fetched the outcome | Removed; poll **`tasks/get`**, which inlines `result`/`error` |
| Input via server-to-client requests | New **`tasks/update`** with `inputResponses` |
| `tasks/list` | **Removed** (prevents cross-caller leaks) |
| `ttl`, `pollInterval` | `ttlMs`, `pollIntervalMs` |

For backward compatibility, a client library that exposes a plain `call_tool() -> CallToolResult` does not need to change its public API. It can drive the polling loop internally and return only the final result. The notebook builds exactly that.

## Key points
- Extensions are optional, separately versioned additions identified as `{vendor-prefix}/{name}`. Official ones use `io.modelcontextprotocol/`, and third parties use a reversed domain they own (`com.example/...`).
- Official extensions live in `ext-*` repos. Experimental ones live in `experimental-ext-*` repos, need a WG/IG, must be labelled experimental, and graduate via an **Extensions Track SEP**.
- Creating an official extension requires a reference implementation in an official SDK **before review**, RFC 2119 language and a sponsoring group. SDK support is optional, and extensions are **off by default**.
- Negotiation uses the `extensions` map (new in 2026-07-28). Clients declare it **per request** in `_meta` client capabilities, and servers declare it in `server/discover`. An extension is active only when both sides declare it.
- Graceful degradation means falling back to core behaviour, or rejecting with `-32021` and `requiredCapabilities` when the extension is mandatory. A breaking change needs a new identifier (`...-v2`).
- With Tasks, a server answers `tools/call` with `CreateTaskResult` (`resultType: "task"`), and only if *this* request declared `io.modelcontextprotocol/tasks`. The task must be durably created before the server responds.
- `tasks/get` polls (honour `pollIntervalMs`), `tasks/update` answers `inputRequests`, and `tasks/cancel` is cooperative. Terminal states are `completed`, `failed` and `cancelled`.
- `failed` is only for JSON-RPC errors. A tool result with `isError: true` makes the task `completed`.
- Compared with 2025-11-25, Tasks moved out of the core, `tasks/result` and `tasks/list` are gone, `tasks/update` is new, and the server decides when to create a task.

## Pitches
### What is an MCP extension and why not just add it to the spec?
An extension is an optional, separately versioned piece of protocol with a reverse-DNS identifier such as io.modelcontextprotocol/tasks. Both sides declare it in an extensions map in their capabilities, and it only switches on when both do. MCP keeps its core small because every core addition is permanent, so new ideas are tried as extensions first: incubated in experimental repos, then promoted through an Extensions Track SEP. If a peer doesn't support an extension, the other side falls back to core behaviour or rejects with -32021.

### How do MCP Tasks work?
When a tool call will take a long time, the server can return a task handle instead of blocking. That's a CreateTaskResult with resultType task, a task ID, a TTL and a suggested poll interval. The client polls tasks/get until the task reaches completed, failed or cancelled. If the server needs a confirmation midway, the task moves to input_required with keyed input requests, and the client answers with tasks/update. Cancellation through tasks/cancel is cooperative. The server only creates tasks for clients that declared the extension on that request.

### What changed about Tasks in 2026-07-28?
In 2025-11-25, tasks were an experimental core feature: the client asked for a task per call, fetched the outcome with a blocking tasks/result, and could enumerate tasks with tasks/list. In 2026-07-28 they became the official io.modelcontextprotocol/tasks extension. Task creation is now server-directed, results come back inline from polling tasks/get, mid-flight input goes through the new tasks/update, and tasks/list is gone, which also closes a cross-caller information leak.

## Interview
### Walk me through how an extension is negotiated in a stateless 2026-07-28 deployment.
The server lists its extensions in the `capabilities.extensions` map of its `server/discover` result, for example `{"io.modelcontextprotocol/tasks": {}}`. There is no session, so the client sends its own `extensions` map **in every request**, inside `_meta["io.modelcontextprotocol/clientCapabilities"]`. Both maps use extension identifiers as keys and per-extension settings objects as values. An empty object means "supported, no settings". An extension is in effect for a request only if both sides declare it, and the server must decide from **this request's** capabilities rather than an earlier one. A load-balanced fleet can therefore answer the same client differently from request to request without any shared state.

### A server has a UI-enhanced tool and a tool that only works as a task. What does each do for a client that declares neither extension?
Both cases follow graceful degradation, which the overview requires. For the **UI tool**, the extension is an enhancement, so the server falls back to core behaviour and returns meaningful text content (and `structuredContent`), which any client can use. For the **task-only tool**, there is no sensible synchronous fallback. The Tasks spec says that if the server cannot serve the request without returning `CreateTaskResult`, it **MUST** return `-32021` (Missing Required Client Capability) with `data.requiredCapabilities.extensions["io.modelcontextprotocol/tasks"] = {}`. The client then knows exactly which capability to add.

### Why does Tasks require the task to be "durably created" before the response is sent?
The response hands the client a `taskId`, and the client's next step is `tasks/get`. If the record existed only in memory on one instance, or in an eventually consistent store that has not converged, that first poll could come back "task not found" (`-32602`). The client would then have to guess whether to retry or give up. Requiring durability before responding removes speculative polling. It is also what makes the handle crash resilient: the client persists the ID, restarts, and resumes polling.

### A tool running as a task hits a rate limit from its upstream API. Should the task end `failed` or `completed`?
It depends on how the failure surfaces. If the tool reports it as a tool result, for example `isError: true` with the message "rate limit exceeded", then the task is **`completed`** and `result` holds that error result. `failed` is reserved for **JSON-RPC errors** during execution, such as `-32603`, and then the `error` field holds the JSON-RPC error and `statusMessage` should explain it. The rule mirrors the core distinction between protocol errors and tool errors, and it keeps `tasks/get` returning exactly what the synchronous call would have returned.

### How would you implement a Tasks client that existing code can call as a normal `call_tool`?
Advertise `io.modelcontextprotocol/tasks` in every request. When `tools/call` returns `resultType: "task"`, persist the `taskId` durably and enter a loop: wait `pollIntervalMs`, call `tasks/get` with the `Mcp-Name` header set to the task ID, and stop on a terminal state. On `input_required`, deduplicate the `inputRequests` keys you have already handled, route each request through the same consent UI as a direct elicitation, and send `tasks/update` with `inputResponses`. On `completed`, return `result` as the `CallToolResult`. On `failed`, raise `error` as an MCP error. Treat elapsed TTL as a backstop. In the Python SDK, this is a `ClientExtension` with a `ResultClaim` for `"task"`.

### Gotcha: why was `tasks/list` removed, and how does a client find its tasks after a crash?
`tasks/list` was a cross-caller leak risk: a poorly scoped implementation could reveal one user's task IDs to another, and task IDs can act as bearer tokens. In the extension there is no listing at all. The client is responsible for **persisting task IDs** itself. The spec says clients SHOULD store them durably so polling can resume after a restart. The server, in turn, must use high-entropy IDs and authorize every `tasks/*` call against the task's owner.

## Glossary
- Extension | 扩展 | An optional, separately versioned addition to MCP, identified by a `{vendor-prefix}/{name}` string and negotiated through capabilities.
- Extension identifier | 扩展标识符 | The reverse-DNS key of an extension, e.g. `io.modelcontextprotocol/tasks`, following `_meta` key rules with a mandatory prefix.
- Experimental extension | 实验性扩展 | An incubating extension in an `experimental-ext-*` repo, tied to a WG/IG, that graduates via an Extensions Track SEP.
- Graceful degradation | 优雅降级 | Falling back to core behaviour, or rejecting with `-32021`, when the peer does not support an extension.
- Task | 任务 | A durable, server-generated handle for a long-running request, with a status, TTL and poll interval.
- `CreateTaskResult` | 创建任务结果 | The polymorphic `tools/call` result with `resultType: "task"` that carries the seed `Task`.
- `tasks/get` | `tasks/get`（任务查询） | The polling request that returns the task's current state and, when terminal, its `result` or `error`.
- `tasks/update` | `tasks/update`（任务输入更新） | The request that delivers `inputResponses` for a task's outstanding `inputRequests`.
- Cooperative cancellation | 协作式取消 | Cancellation that signals intent; the server acknowledges it but may still finish the work.
- Terminal status | 终止状态 | `completed`, `failed` or `cancelled`; once reached, a task's state never changes.

### 1. Extension identifiers: the grammar
The SDK validates identifiers with the same rule the spec gives: dot-separated labels, a mandatory `/`, then a name. Try the good and the bad ones.

```python
from mcp.shared.extension import validate_extension_identifier

candidates = ["io.modelcontextprotocol/tasks", "com.example/weather-alerts",
              "io.modelcontextprotocol/my-extension-v2",
              "tasks",                 # no vendor prefix
              "example.com/x",         # fine grammatically, but use the REVERSED domain you own
              "com.example/",          # empty name
              "-bad.prefix/thing"]     # label must start with a letter
for ident in candidates:
    try:
        validate_extension_identifier(ident, owner="demo")
        print(f"valid    {ident}")
    except TypeError as exc:
        print(f"INVALID  {ident!r}")
```

The grammar cannot tell `example.com/x` from `com.example/x`. Using the *reversed* domain is a convention that the docs ask you to follow, not something a parser can check.

### 2. Declare an extension on both sides
`MCPServer(extensions=[...])` takes `Extension` subclasses. Each one is advertised under `capabilities.extensions[identifier]` with the dict its `settings()` returns. On the client side, `Client(extensions=[...])` takes `ClientExtension` instances, and `advertise()` is the identifier-only form. The tool below reads **this request's** client capabilities and degrades gracefully.

```python
import json

from mcp import Client
from mcp.client.extension import advertise
from mcp.server import MCPServer
from mcp.server.extension import Extension
from mcp.server.mcpserver import Context

ALERTS = "com.example/weather-alerts"


class WeatherAlerts(Extension):
    identifier = ALERTS

    def settings(self):
        return {"version": 1}          # per-extension settings object (schema defined by the extension)


server = MCPServer("weather", extensions=[WeatherAlerts()])


@server.tool()
def forecast(city: str, ctx: Context) -> str:
    """Today's forecast for a city."""
    caps = ctx.client_capabilities
    declared = (caps.extensions or {}) if caps else {}
    text = f"{city}: 18°C, light rain."
    if ALERTS in declared:             # enhanced behaviour only when THIS request declared the extension
        text += " ALERT: wind gusts up to 70 km/h after 18:00."
    return text                        # core fallback is still a meaningful answer


async with Client(server) as plain, Client(server, extensions=[advertise(ALERTS)]) as aware:
    print("server advertises:", json.dumps(plain.server_capabilities.extensions))
    print("plain client ->", (await plain.call_tool("forecast", {"city": "Oslo"})).content[0].text)
    print("aware client ->", (await aware.call_tool("forecast", {"city": "Oslo"})).content[0].text)
```

### 3. On the wire: per-request negotiation over raw stdio
Here the same idea runs as a subprocess. The client capabilities sit in each request's `_meta`, so two consecutive `tools/call`s on one connection can negotiate differently.

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "alerts_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    from mcp.server.extension import Extension
    from mcp.server.mcpserver import Context

    class WeatherAlerts(Extension):
        identifier = "com.example/weather-alerts"
        def settings(self):
            return {"version": 1}

    server = MCPServer("weather", extensions=[WeatherAlerts()])

    @server.tool()
    def forecast(city: str, ctx: Context) -> str:
        """Today's forecast for a city."""
        caps = ctx.client_capabilities
        extra = " ALERT: gusts after 18:00." if caps and caps.extensions and "com.example/weather-alerts" in caps.extensions else ""
        return f"{city}: 18C, light rain." + extra

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "alerts_server.py")],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)


def meta(extensions=None):
    caps = {"extensions": extensions} if extensions else {}
    return {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": caps,
            "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}


def rpc(id_, method, params, show=True):
    message = {"jsonrpc": "2.0", "id": id_, "method": method, "params": params}
    proc.stdin.write(json.dumps(message) + "\n")
    proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    if show:
        print(">>>", json.dumps(message))
        print("<<<", json.dumps(reply)[:400], "\n")
    return reply


disc = rpc(1, "server/discover", {"_meta": meta()}, show=False)
print("server/discover capabilities.extensions =", disc["result"]["capabilities"].get("extensions"), "\n")
rpc(2, "tools/call", {"name": "forecast", "arguments": {"city": "Oslo"}, "_meta": meta()})
```

### 4. Mandatory extensions: rejecting with `-32021`
When there is no meaningful fallback, the right answer is the *Missing Required Client Capability* error. The SDK helper `require_client_extension(ctx, identifier)` raises it with the `requiredCapabilities` payload. Tool handlers receive the high-level `Context`, whose `request_context` is the low-level context that the helper expects.

```python
from mcp.server.mcpserver import require_client_extension
from mcp.shared.exceptions import MCPError

strict = MCPServer("strict", extensions=[WeatherAlerts()])


@strict.tool()
def severe_weather_feed(region: str, ctx: Context) -> str:
    """Stream of severe-weather alerts (only meaningful with the alerts extension)."""
    require_client_extension(ctx.request_context, ALERTS)
    return f"{region}: no active alerts"


async with Client(strict) as plain, Client(strict, extensions=[advertise(ALERTS)]) as aware:
    print("aware ->", (await aware.call_tool("severe_weather_feed", {"region": "NO"})).content[0].text)
    try:
        await plain.call_tool("severe_weather_feed", {"region": "NO"})
    except MCPError as err:
        print("plain -> error", err.code, err.message)
        print("         data:", json.dumps(err.data))
```

### 5. The Tasks extension: wire models
No Tasks package is installed, so we build the extension ourselves on the SDK's extension API, following the `ext-tasks` specification field for field. First come the shapes: `Task`, `CreateTaskResult` (`resultType: "task"`), `DetailedTask` (the `tasks/get` result, `resultType: "complete"`), and the request params. The SDK's models turn snake_case attributes into the camelCase wire names.

```python
import asyncio
import secrets
from datetime import datetime, timezone
from typing import Any, Literal

import mcp_types as types
from mcp_types import Request, RequestParams, Result

TASKS = "io.modelcontextprotocol/tasks"
Status = Literal["working", "input_required", "completed", "failed", "cancelled"]
TERMINAL = {"completed", "failed", "cancelled"}


def now() -> str:
    return datetime.now(timezone.utc).isoformat(timespec="milliseconds").replace("+00:00", "Z")


class Task(Result):
    task_id: str
    status: Status
    status_message: str | None = None
    created_at: str
    last_updated_at: str
    ttl_ms: int | None
    poll_interval_ms: int | None = None


class CreateTaskResult(Task):              # type CreateTaskResult = Result & Task
    result_type: Literal["task"] = "task"


class DetailedTask(Task):                  # type GetTaskResult = Result & DetailedTask
    result_type: Literal["complete"] = "complete"
    input_requests: dict[str, Any] | None = None
    result: dict[str, Any] | None = None
    error: dict[str, Any] | None = None


class TaskIdParams(RequestParams):
    task_id: str


class UpdateTaskParams(TaskIdParams):
    input_responses: dict[str, Any]


def wire(model) -> dict:
    return model.model_dump(by_alias=True, exclude_none=True, mode="json")


print(json.dumps(wire(CreateTaskResult(task_id="t-1", status="working", created_at=now(),
                                       last_updated_at=now(), ttl_ms=60_000, poll_interval_ms=50)), indent=2))
```

### 6. The server side: an `Extension` that intercepts `tools/call`
The extension uses two SDK contribution points. **`intercept_tool_call`** decides, per request, whether to return a task. **`methods()`** serves `tasks/get`, `tasks/update` and `tasks/cancel` as additive `MethodBinding`s. The work runs as a background `asyncio` task. It can pause in `input_required` and wait for `tasks/update`, and it records a terminal state with the same `completed` / `failed` split the spec requires.

```python
from mcp.server.extension import MethodBinding
from mcp_types import INTERNAL_ERROR, INVALID_PARAMS


class TasksExtension(Extension):
    identifier = TASKS

    def __init__(self, task_tools: dict[str, dict], ttl_ms: int = 60_000, poll_interval_ms: int = 50):
        self.task_tools = task_tools     # tool name -> {"needs_approval": bool, "requires_tasks": bool}
        self.ttl_ms, self.poll_interval_ms = ttl_ms, poll_interval_ms
        self.store: dict[str, dict] = {} # stands in for a durable store (database, Redis, ...)
        self.server: MCPServer | None = None

    # ---- helpers -------------------------------------------------------------------------------
    def _set(self, rec, **changes):
        rec.update(changes, last_updated_at=now())

    def _view(self, rec, model=DetailedTask):
        fields = {k: rec.get(k) for k in ("task_id", "status", "status_message", "created_at",
                                          "last_updated_at", "ttl_ms", "poll_interval_ms")}
        if model is DetailedTask:
            if rec["status"] == "input_required":
                fields["input_requests"] = {k: v for k, v in rec["requests"].items() if k not in rec["answers"]}
            fields["result"], fields["error"] = rec.get("result"), rec.get("error")
        return model(**fields)

    def _lookup(self, ctx, task_id):
        require_client_extension(ctx, TASKS)                    # -32021 for non-declaring clients
        rec = self.store.get(task_id)
        if rec is None:
            raise MCPError(INVALID_PARAMS, "Failed to retrieve task: Task not found")
        return rec

    async def _ask(self, rec, key, params):
        """Pause in input_required until tasks/update answers `key` (keys are never reused)."""
        rec["requests"][key] = {"method": "elicitation/create", "params": params}
        rec["waiters"][key] = asyncio.get_running_loop().create_future()
        self._set(rec, status="input_required", status_message="Waiting for approval")
        answer = await rec["waiters"][key]
        self._set(rec, status="working", status_message="Approval received")
        return answer

    async def _run(self, rec, name, arguments):
        try:
            if self.task_tools[name].get("needs_approval"):
                answer = await self._ask(rec, "approve-1", {
                    "mode": "form", "message": f"Approve {name} with {arguments}?",
                    "requestedSchema": {"type": "object", "properties": {"approve": {"type": "boolean"}},
                                        "required": ["approve"]}})
                if answer.get("action") != "accept" or not (answer.get("content") or {}).get("approve"):
                    self._set(rec, status="completed", status_message="Declined by the user",
                              result={"content": [{"type": "text", "text": "Declined by the user."}],
                                      "isError": True})
                    return
            for step in (1, 2, 3):
                self._set(rec, status_message=f"step {step}/3")
                await asyncio.sleep(0.05)                       # pretend this is minutes of work
            out = await self.server.call_tool(name, arguments)  # run the real tool function
            self._set(rec, status="completed", status_message="Done", result=wire(out))
        except asyncio.CancelledError:
            self._set(rec, status="cancelled", status_message="Cancelled at the client's request")
        except MCPError as exc:                                 # a JSON-RPC error -> failed
            self._set(rec, status="failed", status_message=f"Tool execution failed: {exc.message}",
                      error=exc.error.model_dump(exclude_none=True))
        except Exception as exc:                                # a tool error -> completed + isError
            self._set(rec, status="completed", status_message="Tool reported an error",
                      result={"content": [{"type": "text", "text": str(exc)}], "isError": True})

    # ---- contribution points -------------------------------------------------------------------
    async def intercept_tool_call(self, params, ctx, call_next):
        policy = self.task_tools.get(params.name)
        caps = ctx.session.client_capabilities
        declared = bool(caps and caps.extensions and TASKS in caps.extensions)
        if policy is None:
            return await call_next(ctx)                         # not a long-running tool
        if not declared:
            if policy.get("requires_tasks"):
                require_client_extension(ctx, TASKS)            # cannot serve synchronously -> -32021
            return await call_next(ctx)                         # graceful degradation: block and answer
        task_id = secrets.token_urlsafe(16)                     # unguessable handle
        rec = {"task_id": task_id, "status": "working", "status_message": "Queued",
               "created_at": now(), "last_updated_at": now(), "ttl_ms": self.ttl_ms,
               "poll_interval_ms": self.poll_interval_ms, "requests": {}, "answers": {}, "waiters": {}}
        self.store[task_id] = rec                               # durably created BEFORE we respond
        rec["job"] = asyncio.create_task(self._run(rec, params.name, params.arguments or {}))
        return self._view(rec, CreateTaskResult)

    def methods(self):
        async def get(ctx, params: TaskIdParams):
            return self._view(self._lookup(ctx, params.task_id))

        async def update(ctx, params: UpdateTaskParams):
            rec = self._lookup(ctx, params.task_id)
            for key, response in params.input_responses.items():
                waiter = rec["waiters"].get(key)
                if waiter is None or key in rec["answers"]:     # unknown or already answered: ignore
                    continue
                rec["answers"][key] = response
                waiter.set_result(response)
            return types.EmptyResult(result_type="complete")

        async def cancel(ctx, params: TaskIdParams):
            rec = self._lookup(ctx, params.task_id)
            if rec["status"] not in TERMINAL:
                rec["job"].cancel()                             # cooperative: we choose to honour it
            return types.EmptyResult(result_type="complete")

        return [MethodBinding("tasks/get", TaskIdParams, get),
                MethodBinding("tasks/update", UpdateTaskParams, update),
                MethodBinding("tasks/cancel", TaskIdParams, cancel)]


tasks_ext = TasksExtension({"build_report": {"needs_approval": False, "requires_tasks": False},
                            "deploy": {"needs_approval": True, "requires_tasks": True}})
ops = MCPServer("ops", extensions=[tasks_ext])
tasks_ext.server = ops


@ops.tool()
def build_report(rows: int) -> str:
    """Aggregate `rows` rows of sales data into a report (slow)."""
    if rows > 1_000_000:
        raise MCPError(INTERNAL_ERROR, "Warehouse unavailable")   # protocol-level failure
    if rows < 0:
        raise ValueError("rows must be >= 0")                     # tool-level error
    return f"Report over {rows} rows: revenue up 12%."


@ops.tool()
def deploy(env: str) -> str:
    """Deploy the current build to an environment (needs human approval)."""
    return f"Deployed build 42 to {env}."


print("task-capable tools:", tasks_ext.task_tools)
```

### 7. The client side: polymorphic results and the polling loop
A client that declares Tasks must accept *either* result shape. In the Python SDK, a `ClientExtension` declares the extra shape with a `ResultClaim` keyed by `resultType`. With `session.call_tool(..., allow_claimed=True)` we receive the raw `CreateTaskResult` and then drive `tasks/get` ourselves, printing each wire result. The `name_param = "taskId"` line makes the SDK set `Mcp-Name: <taskId>` when this runs over HTTP.

```python
from mcp.client.extension import ClientExtension, ResultClaim


class GetTaskRequest(Request[TaskIdParams, Literal["tasks/get"]]):
    method: Literal["tasks/get"] = "tasks/get"
    name_param = "taskId"


class UpdateTaskRequest(Request[UpdateTaskParams, Literal["tasks/update"]]):
    method: Literal["tasks/update"] = "tasks/update"
    name_param = "taskId"


class CancelTaskRequest(Request[TaskIdParams, Literal["tasks/cancel"]]):
    method: Literal["tasks/cancel"] = "tasks/cancel"
    name_param = "taskId"


class TasksClient(ClientExtension):
    """Declares io.modelcontextprotocol/tasks and claims resultType "task"."""
    identifier = TASKS

    def __init__(self, answer=None):
        self.answer = answer   # callback used in section 9 to answer input requests

    def claims(self):
        return [ResultClaim(result_type="task", model=CreateTaskResult, resolve=self._resolve)]

    async def _resolve(self, created, cctx):
        raise NotImplementedError   # filled in section 9


async def tasks_get(session, task_id):
    return await session.send_request(GetTaskRequest(params=TaskIdParams(task_id=task_id)), DetailedTask)


async with Client(ops) as legacy, Client(ops, extensions=[TasksClient()]) as modern:
    print("server/discover extensions:", modern.server_capabilities.extensions)
    sync = await legacy.call_tool("build_report", {"rows": 500})          # no Tasks declared
    print("\nclient WITHOUT tasks -> ordinary CallToolResult:", sync.content[0].text)

    created = await modern.session.call_tool("build_report", {"rows": 500}, allow_claimed=True)
    print("\nclient WITH tasks -> tools/call result:")
    print(json.dumps(wire(created), indent=2))
    while True:
        await asyncio.sleep(created.poll_interval_ms / 1000)                # honour pollIntervalMs
        state = await tasks_get(modern.session, created.task_id)
        print("tasks/get ->", state.status, "|", state.status_message)
        if state.status in TERMINAL:
            print(json.dumps(wire(state)["result"], indent=2))
            break
```

### 8. Mid-flight input with `tasks/update`, then the error paths
`deploy` needs approval. Poll until `input_required`, read the keyed `inputRequests`, answer with `tasks/update`, and poll to completion. Then hit the error cases: a client without the extension calling a task-only tool (`-32021`), an unknown `taskId` (`-32602`), a `failed` task (JSON-RPC error) and a `completed` task whose tool result has `isError: true`.

```python
async def poll(session, task_id, interval=0.05):
    while True:
        state = await tasks_get(session, task_id)
        if state.status in TERMINAL or state.status == "input_required":
            return state
        await asyncio.sleep(interval)


async with Client(ops, extensions=[TasksClient()]) as c:
    created = await c.session.call_tool("deploy", {"env": "staging"}, allow_claimed=True)
    state = await poll(c.session, created.task_id)
    print("status:", state.status)
    print("inputRequests:", json.dumps(state.input_requests, indent=2))

    update = UpdateTaskRequest(params=UpdateTaskParams(
        task_id=created.task_id, input_responses={"approve-1": {"action": "accept", "content": {"approve": True}}}))
    print("\n>>> tasks/update params:", json.dumps(update.params.model_dump(by_alias=True, exclude_none=True)))
    ack = await c.session.send_request(update, types.EmptyResult)
    print("<<< ack:", wire(ack))
    final = await poll(c.session, created.task_id)
    print("final:", final.status, "->", final.result["content"][0]["text"])

    print("\n--- error paths ---")
    for rows in (2_000_000, -5):
        t = await c.session.call_tool("build_report", {"rows": rows}, allow_claimed=True)
        s = await poll(c.session, t.task_id)
        print(f"rows={rows:>9}: status={s.status:<9} error={s.error} isError={s.result and s.result.get('isError')}")
    try:
        await tasks_get(c.session, "no-such-task")
    except MCPError as err:
        print("unknown taskId ->", err.code, err.message)

async with Client(ops) as legacy:
    try:
        await legacy.call_tool("deploy", {"env": "prod"})
    except MCPError as err:
        print("deploy without Tasks ->", err.code, json.dumps(err.data))
    try:
        await tasks_get(legacy.session, "anything")
    except MCPError as err:
        print("tasks/get without Tasks ->", err.code)
```

### 9. A transparent client: `call_tool()` that hides the task
The spec's backward-compatibility note says a client can drive the polling loop internally and return only the final `CallToolResult`. We now implement `_resolve` and pass an `answer` callback, which stands in for the host's consent UI. Keys already answered are deduplicated across polls. After that, `client.call_tool(...)` simply returns the result. Cancellation is shown last.

```python
async def resolve(self, created, cctx):
    answered, interval = set(), created.poll_interval_ms or 1000
    while True:
        await asyncio.sleep(interval / 1000)
        state = await tasks_get(cctx.session, created.task_id)
        interval = state.poll_interval_ms or interval        # pollIntervalMs MAY change over time
        if state.status == "input_required":
            fresh = {k: v for k, v in (state.input_requests or {}).items() if k not in answered}
            if fresh:
                responses = {k: self.answer(v) for k, v in fresh.items()}
                answered |= set(fresh)
                await cctx.session.send_request(UpdateTaskRequest(params=UpdateTaskParams(
                    task_id=created.task_id, input_responses=responses)), types.EmptyResult)
        elif state.status == "completed":
            return types.CallToolResult.model_validate(state.result)
        elif state.status == "failed":
            raise MCPError(state.error["code"], state.error["message"])
        elif state.status == "cancelled":
            raise RuntimeError("task was cancelled")


TasksClient._resolve = resolve


def approve_everything(request):
    print("   [consent UI] ", request["params"]["message"], "-> approved")
    return {"action": "accept", "content": {"approve": True}}


async with Client(ops, extensions=[TasksClient(answer=approve_everything)]) as c:
    result = await c.call_tool("deploy", {"env": "production"})
    print("call_tool returned a plain CallToolResult:", result.content[0].text)

    created = await c.session.call_tool("build_report", {"rows": 10}, allow_claimed=True)
    await c.session.send_request(CancelTaskRequest(params=TaskIdParams(task_id=created.task_id)), types.EmptyResult)
    print("after tasks/cancel:", (await poll(c.session, created.task_id)).status)
```
