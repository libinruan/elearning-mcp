## Summary
Sometimes a server cannot finish a request without asking something first: "are you sure you want to delete this repository?", "which GitHub account?", "please connect your calendar". In 2026-07-28 that conversation follows one pattern, **Multi Round-Trip Requests (MRTR)**. The server *returns* an `InputRequiredResult` with `inputRequests` and an opaque `requestState`. The client gathers the answers and *retries* the original request with `inputResponses`, and any server instance can finish the job. This lesson covers the pattern's exact rules, why `requestState` must be integrity-protected, and elicitation in depth: restricted form schemas, URL mode for secrets and third-party OAuth, the accept/decline/cancel model, and why `notifications/elicitation/complete` was removed.

## Lesson
### Why MRTR exists
In earlier revisions, a server that needed input in the middle of a `tools/call` sent its **own JSON-RPC request** (`elicitation/create`) to the client and *waited* for the answer while the original request stayed open. That design has costs:

- It needs a **bidirectional channel** that stays open for as long as the user takes to answer, which may be minutes.
- The waiting server instance holds **in-memory state**, so a load balancer must route the answer back to the *same* instance (sticky sessions), and a restart loses the question.
- It ties every server to session machinery that 2026-07-28 removed.

MRTR (SEP-2322) turns the question into an ordinary **result**. The changelog says it "replaces the previous approach of sending server-initiated requests", and the pattern page is explicit: servers **MUST** use MRTR for `roots/list`, `sampling/createMessage` and `elicitation/create`, the old pattern "is no longer supported", and "this is a breaking change". The design goal is stated too: no "shared storage layer across server instances" and no "stateful load balancing".

```text
Client                                Server (any instance)
  │ tools/call id:1 {name, arguments}   │
  │────────────────────────────────────▶│ needs input
  │ result id:1 {resultType:"input_required", inputRequests, requestState}
  │◀────────────────────────────────────│ (request 1 is now FINISHED)
  │  …ask user…                          │
  │ tools/call id:2 {name, arguments, inputResponses, requestState}
  │────────────────────────────────────▶│ verify state, continue
  │ result id:2 {resultType:"complete", content…}
  │◀────────────────────────────────────│
```

### The core types
- **`resultType`**. Every result in 2026-07-28 carries it: `"complete"` for ordinary results, `"input_required"` for MRTR interim results. Clients **MUST** treat results from older servers that omit it as `"complete"`.
- **`InputRequests`** is a map from **server-assigned string keys** (unique within the request) to request objects. Each value **MUST** be one of `ElicitRequest` (`elicitation/create`), `CreateMessageRequest` (`sampling/createMessage`) or `ListRootsRequest` (`roots/list`).
- **`InputResponses`** is a map with the **same keys**, whose values are the client's results: `ElicitResult`, `CreateMessageResult` or `ListRootsResult`.
- **`InputRequiredResult`** has optional `inputRequests` and optional `requestState`, an "opaque string meaningful only to the server". At least one of the two **MUST** be present.

```json
{"jsonrpc": "2.0", "id": 2, "result": {
  "resultType": "input_required",
  "inputRequests": {"github_login": {"method": "elicitation/create", "params": {
      "mode": "form", "message": "Please provide your GitHub username",
      "requestedSchema": {"type": "object", "properties": {"name": {"type": "string"}}, "required": ["name"]}}}},
  "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."}}
```

The retry repeats the original params and adds the two fields:

```json
{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {
  "name": "get_weather", "arguments": {"location": "New York"},
  "inputResponses": {"github_login": {"action": "accept", "content": {"name": "octocat"}}},
  "requestState": "eyJsb2NhdGlvbiI6Ik5ldyBZb3JrIn0..."}}
```

### Which requests support it
| Client request | May return `InputRequiredResult` |
| --- | --- |
| `tools/call` | Yes |
| `prompts/get` | Yes |
| `resources/read` | Yes |
| everything else (`tools/list`, `server/discover`, …) | **MUST NOT** |

### The rules, server side
1. A server **MAY** answer any supported request with an `InputRequiredResult`.
2. `inputRequests` keys **MUST** be unique within the request, and values **MUST** be one of the three request types.
3. `requestState` can use any encoding: base64 JSON, an encrypted JWT, binary.
4. **`requestState` is attacker-controlled input.** If it influences authorization, resource access or business logic, the server **MUST** protect its integrity (HMAC or AEAD) and **MUST** reject state that fails verification. Integrity protection may be skipped *only* when tampering can cause nothing worse than a failed request.
5. Against replay, servers **SHOULD** put inside the protected payload, and verify: the **authenticated principal**, a **short expiry**, and an **identifier of the originating request** (method plus a digest of its salient parameters). These limit the replay window but don't guarantee single use. One-time operations **MUST** enforce that invariant server-side.
6. Every `InputRequiredResult` includes `inputRequests` and/or `requestState`.
7. Never send an input request the client hasn't declared (no `elicitation` capability means no `elicitation/create`).
8. Never assume the client will answer or retry. A server **MAY** return `InputRequiredResult` again on a retry to keep asking until it has what it needs.

### The rules, client side
1. If `inputRequests` is present, the client **MUST** build the responses before retrying. If only `requestState` is present, it **MAY** retry immediately. The schema's example is *load shedding*, where the server says "come back with this state".
2. Echo `requestState` **exactly**. The client must not inspect, parse or modify it, and must not invent one if none was sent.
3. Use a **new JSON-RPC `id`** for the retry. It is an independent request.
4. `inputRequests`/`requestState` apply **only** to the retry of that request, never to other requests running in parallel.

**Error handling.** Servers **SHOULD** validate `inputResponses`. Malformed data or internal failures get a JSON-RPC error. Unknown extra keys **SHOULD** be ignored. If required answers are *missing*, the server **SHOULD** send a new `InputRequiredResult` asking again rather than an error. When the user declines or something fails on the client side, the client simply doesn't retry, because "the server is not waiting for a response".

### Elicitation in depth
**Capabilities.** The client declares `"elicitation": {"form": {}, "url": {}}` in each request's `_meta`. An empty `{}` means form mode only. A client declaring elicitation **MUST** support at least one mode, and servers **MUST NOT** use a mode the client lacks.

**Request parameters.** Every `elicitation/create` has `mode` (`"form"` or `"url"`; if omitted, it means form) and a human-readable `message`.

**Form mode** adds `requestedSchema`, which is restricted to a **flat object of primitives**:

| Property type | Allowed keywords |
| --- | --- |
| string | `title`, `description`, `minLength`, `maxLength`, `format` (`email`, `uri`, `date`, `date-time`), `default` |
| number / integer | `title`, `description`, `minimum`, `maximum`, `default` |
| boolean | `title`, `description`, `default` |
| single-select enum | `type: "string"` with `enum`, or `oneOf: [{const, title}]` for labelled options |
| multi-select enum | `type: "array"` with `items.enum` or `items.anyOf: [{const, title}]`, `minItems`, `maxItems` |

Nested objects and arrays of objects are "intentionally not supported to simplify client user experience". Clients use the schema to generate the form, **validate before sending** and pre-fill defaults.

**URL mode** adds `url` (a valid URL). It was introduced in 2025-11-25 and is marked as still able to change. Use it when data "must *not* pass through the MCP client": API keys, payments, **third-party OAuth**. `accept` here means only that the user *consented to open the URL*, not that the interaction is finished. The client opens the URL, retries, and the server checks (from `requestState` or its own store) whether the out-of-band step has completed. If it hasn't, it returns another `InputRequiredResult`. Clients **SHOULD** give the user manual controls to retry or cancel.

**Response actions.** `accept` (form mode includes `content`, URL mode omits it), `decline` ("Reject", "No") and `cancel` (closed the dialog, pressed Escape, page failed to load). Servers **MUST** handle decline, cancel and client failures. A typical approach is to offer alternatives on decline and to ask again later on cancel.

### Elicitation security
- **Sensitive data**: servers **MUST NOT** use form mode for passwords, API keys, access tokens or payment credentials, and **MUST** use URL mode for them. Names, emails and usernames are allowed in form mode, at the server's discretion, because the user can always decline.
- **Client UI**: clients **MUST** show which server is asking, offer decline and cancel, and let users review and edit form answers.
- **Safe URL handling (clients)**: **MUST NOT** pre-fetch the URL or its metadata, **MUST NOT** open it without explicit consent, **MUST** show the full URL first, and **MUST** open it in a way the client and LLM can't inspect (the spec contrasts SFSafariViewController with WKWebView on iOS). Clients **SHOULD** highlight the domain and warn on Punycode or other suspicious URLs.
- **Safe URL handling (servers)**: **MUST NOT** put credentials or PII in the URL, **MUST NOT** send pre-authenticated URLs, **SHOULD** use HTTPS, and **SHOULD NOT** put clickable URLs in form-mode fields.
- **Identity**: servers **MUST** bind elicitations to the client and user identity. They must never trust "I am joe@example.com" typed by a user. Identity comes from MCP authorization (for example, the `sub` claim).
- **Phishing**: an attacker can forward a URL-mode link to a victim, who completes the OAuth flow, and the tokens end up bound to the *attacker's* account. The server **MUST** verify that the person opening the URL is the user who triggered the elicitation. For example, send users to `https://mcp.example.com/connect?...` first, check their session cookie's subject against the elicitation's, and only then redirect to the third-party authorize endpoint.
- **Third-party OAuth via URL mode** is separate from MCP authorization. The third-party credentials **MUST NOT** pass through the client, the server **MUST NOT** reuse the client's token upstream (token passthrough), and the server stores the third-party tokens bound to the user. This makes the server stateful for those tokens.

### Statefulness and the removed completion notification
Elicitation "does not require that the server maintain state" thanks to MRTR, because `requestState` carries the context. If a server does store state (such as OAuth tokens), it **MUST** protect it and key it to a user identity derived from authorization. In 2025-11-25, URL mode used an `elicitationId` and a server-sent `notifications/elicitation/complete` to say "the browser step finished". Both were **removed in 2026-07-28**. A stateless protocol has no channel for a server-initiated signal, and the client now learns the outcome by **retrying**. A server that needs correlation puts its own identifier into `requestState`.

### How the Python SDK implements MRTR
- **Server, declarative**: annotate a tool parameter `Annotated[T, Resolve(fn)]`, where `fn` returns `Elicit(message, Model)`, `Sample(...)` or `ListRoots()`. The framework batches the questions into one `InputRequiredResult`, stores answers in `requestState` so each question is asked once, and runs the tool body only when everything is resolved. On a 2025-era connection it sends real server-to-client requests instead.
- **Server, hand-rolled**: return `types.InputRequiredResult(...)` from the tool and read `ctx.input_responses` / `ctx.request_state` on the retry. You must check `ctx.client_capabilities` yourself.
- **`requestState` protection is automatic**: `MCPServer` installs a `RequestStateBoundary` that seals outgoing state with **AES-256-GCM** inside an envelope of expiry (default TTL 600 s), method, target, an arguments digest, audience (the server name) and principal. It verifies inbound state before your handler runs. Failures return `-32602 "Invalid or expired requestState"`. The default key is ephemeral (per process), so multi-instance deployments pass `RequestStateSecurity(keys=[shared_secret])`.
- **Client**: `client.call_tool(...)` runs the loop automatically through your callbacks (up to `input_required_max_rounds`, default 10, with a short backoff for state-only rounds). `client.session.call_tool(..., allow_input_required=True)` hands you the raw result so you can drive the loop yourself, for example to persist a pending question across a restart.

## Key points
- MRTR replaces server-initiated requests: the server **returns** `{"resultType": "input_required", "inputRequests", "requestState"}` and the client **retries** with `inputResponses` + echoed `requestState` under a **new JSON-RPC id**.
- Only `tools/call`, `prompts/get` and `resources/read` may return `InputRequiredResult`. Input requests are limited to `elicitation/create`, `sampling/createMessage` and `roots/list`.
- `inputResponses` keys mirror `inputRequests` keys. At least one of `inputRequests`/`requestState` is always present, and a state-only result means "retry later with this".
- Treat `requestState` as **attacker-controlled**. Use HMAC/AEAD when it matters, and bind principal, expiry and originating request. Single use must be enforced server-side.
- Clients echo `requestState` byte-for-byte and never parse it. Servers re-ask for missing answers instead of erroring.
- Form-mode schemas are flat primitives (string/number/integer/boolean/enums). Secrets, payments and third-party OAuth **must** use URL mode.
- Actions are `accept` / `decline` / `cancel`. URL-mode `accept` means only "user consented to open the URL".
- `notifications/elicitation/complete` and `elicitationId` were removed. The retry tells the client the outcome, and correlation lives in `requestState`.
- Because state travels with the request, any server instance can finish the retry, so there is no sticky routing or shared session store.

## Pitches
### What is MRTR and why did MCP adopt it?
Multi round-trip requests are how a 2026 MCP server asks for something mid-request. Instead of opening its own request to the client and waiting, the server returns an input-required result listing what it needs plus an opaque state blob, and the original request ends there. The client asks the user, then retries the same call with the answers and the state. Because everything needed to continue travels with the retry, any server instance can complete it, with no sticky sessions and no shared session store.

### Why must requestState be signed or encrypted?
The state makes a round trip through the client, so a malicious client can edit it. If it says which repository to delete or which user approved a payment, tampering becomes privilege escalation. The spec says to treat it as attacker-controlled, protect its integrity with an HMAC or authenticated encryption, and bind it to the user, a short expiry and the original request so it can't be replayed elsewhere. The Python SDK does this automatically with AES-GCM.

### How do you build a safe confirmation step for a destructive tool?
My delete tool doesn't act on the first call. It returns an elicitation in form mode asking the user to type the resource name, with the target kept in protected request state. On retry I act only on an explicit accept where the typed name matches. Decline and cancel lead to a clear "nothing deleted", and a typo leads to a fresh question. The host's UI shows which server is asking, so the model alone can never confirm a deletion.

## Interview
### Describe the full MRTR exchange for a `tools/call` that needs user input, including ids.
The client sends `tools/call` with id 1. The server replies to id 1 with `result: {"resultType": "input_required", "inputRequests": {"confirm": {"method": "elicitation/create", "params": {...}}}, "requestState": "..."}`, and request 1 is complete. The client shows the form and sends a **new** request, id 2, with the same `name` and `arguments` plus `inputResponses: {"confirm": {"action": "accept", "content": {...}}}` and the exact `requestState`. The server verifies the state, rebuilds its context and answers id 2 with `resultType: "complete"`, or with another `InputRequiredResult` if it still needs something. Every request also carries the usual `_meta` envelope, including client capabilities.

### What could go wrong if a server put `{"repo": "acme/web", "approved": true}` in plain base64 `requestState`?
The client could decode and edit it, for example changing the repo to `acme/prod` or setting `approved` before the user was ever asked, and the server would act on forged data. The spec requires integrity protection (HMAC or AEAD) whenever state influences authorization, resources or business logic, and rejection of anything that fails verification. It also recommends binding the principal, a short TTL and the originating request (method plus parameter digest) to stop cross-user and cross-request replay. Anything that must happen once, like a payment, needs a server-side used-token record, because a valid state can still be replayed within its TTL.

### The client receives an `InputRequiredResult` with only `requestState`. What should it do?
Retry the original request, with a new id, echoing the state and sending no `inputResponses`. The spec allows the client to retry immediately. The schema's example is *load shedding*, where the server says "I'm busy or still working, come back with this". A sensible client backs off a little between such rounds and caps the total number of rounds. The Python SDK does both: exponential backoff from 50 ms to 250 ms and `input_required_max_rounds`, default 10.

### When must elicitation use URL mode, and what does `accept` mean there?
Whenever the server needs secrets or credentials (passwords, API keys, access tokens, payment details), or needs the user to authorise the server with a *third-party* service through OAuth. In those cases the data must never transit the MCP client or the LLM context. In URL mode, `accept` only means the user **consented to open the URL**. The real interaction happens in the browser, out of band. On the retry the server checks its own records (keyed through `requestState` and the user's identity) and either completes or asks again. It must also verify that whoever completes the browser flow is the same user, to defeat the phishing attack where a link is forwarded to a victim.

### Why was `notifications/elicitation/complete` removed?
It was a server-initiated message telling the client that a URL-mode interaction had finished, correlated by `elicitationId`. Under 2026-07-28 there is no session or back-channel to carry server-initiated messages. The MRTR retry already gives the client the answer: retry, and the server either completes or asks again. So the notification and its id were removed, and servers that need correlation encode their own id in `requestState`.

### Gotcha: a hand-written tool returns an elicitation to a client that declared no capabilities. Who is wrong, and how would you catch it?
The server is wrong. Servers **MUST NOT** send input requests the client hasn't declared. SDK-level helpers (in Python, `Resolve(...)` resolvers) check this and fail with `-32021` MissingRequiredClientCapability. A hand-rolled `return InputRequiredResult(...)` bypasses that check, so the tool must inspect `ctx.client_capabilities` itself and fall back, for example by returning a tool error that says "confirmation required; this client can't ask the user". A test with a capability-less client catches it.

## Glossary
- Multi Round-Trip Request (MRTR) | 多轮往返请求 | The 2026-07-28 pattern where a server returns an input-required result and the client retries the original request with the requested input.
- InputRequiredResult | 需输入结果 | A result with `resultType: "input_required"` carrying `inputRequests` and/or `requestState`.
- inputRequests | 输入请求映射 | Server-keyed map of `elicitation/create`, `sampling/createMessage` or `roots/list` requests the client must fulfil.
- inputResponses | 输入响应映射 | Client-supplied map, keyed like `inputRequests`, carrying the results on the retried request.
- requestState | 请求状态（不透明令牌） | Opaque server-minted string the client echoes unchanged; attacker-controlled, so it must be integrity-protected when it matters.
- AEAD | 带关联数据的认证加密 | Authenticated encryption (e.g. AES-GCM) that keeps state confidential and detects tampering.
- Form-mode elicitation | 表单模式征询 | In-band collection of flat, primitive, schema-validated user input.
- URL-mode elicitation | URL 模式征询 | Out-of-band interaction at a URL, used for secrets, payments and third-party OAuth.
- Elicitation actions | 征询响应动作 | `accept`, `decline` or `cancel`: the user's explicit choice or dismissal.
- Load shedding | 负载削减（稍后重试） | A state-only `InputRequiredResult` telling the client to retry later with the given state.

## Notebook
### 1. A destructive tool with a confirmation gate (hand-rolled MRTR)
We write the flow explicitly so every field is visible. `delete_repository` never deletes on the first call. It:

- checks the client declared form elicitation (spec MUST; hand-rolled code must do this itself),
- returns an `InputRequiredResult` asking the user to **type the repository name**,
- on retry, acts only on `accept` with a matching name, re-asks on a typo, and reports `decline`/`cancel`.

`ctx.request_state` holds what we minted last round. The SDK encrypts it on the way out and verifies it on the way back.

```python
import json
import logging

import mcp_types as types
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

logging.getLogger("mcp").setLevel(logging.CRITICAL)


def wire(model) -> str:
    return json.dumps(model.model_dump(by_alias=True, exclude_none=True, mode="json"), indent=2)


REPOS = {"acme/web", "acme/prod", "acme/docs"}
github = MCPServer("github-admin")


def confirm_request(repo: str, note: str = "") -> types.ElicitRequest:
    return types.ElicitRequest(params=types.ElicitRequestFormParams(
        message=f"{note}This permanently deletes {repo}. Type the full repository name to confirm.",
        requested_schema={"type": "object",
                          "properties": {"repo_name": {"type": "string", "title": "Repository name",
                                                       "minLength": 1, "maxLength": 100}},
                          "required": ["repo_name"]}))


@github.tool()
def delete_repository(repo: str, ctx: Context) -> str | types.InputRequiredResult:
    """Permanently delete a repository (asks the user to confirm first)."""
    if repo not in REPOS:
        return f"No such repository: {repo}"
    caps = ctx.client_capabilities
    if caps is None or caps.elicitation is None:
        return "Refused: deletion needs user confirmation, but this client cannot ask the user."

    answer = (ctx.input_responses or {}).get("confirm_delete")
    if answer is None:                                     # round 1, or the client sent nothing
        return types.InputRequiredResult(input_requests={"confirm_delete": confirm_request(repo)},
                                         request_state=json.dumps({"repo": repo, "round": 1}))
    state = json.loads(ctx.request_state)                  # already verified by the SDK
    if answer.action == "decline":
        return f"Not deleted: the user declined deleting {state['repo']}."
    if answer.action == "cancel":
        return "Not deleted: the confirmation was dismissed. Ask again later if needed."
    if (answer.content or {}).get("repo_name") != state["repo"]:
        return types.InputRequiredResult(              # spec: re-ask rather than error
            input_requests={"confirm_delete": confirm_request(repo, "The name did not match. ")},
            request_state=json.dumps({"repo": repo, "round": state["round"] + 1}))
    REPOS.discard(state["repo"])
    return f"Deleted {state['repo']} after {state['round']} confirmation round(s)."


print("tool registered; repos:", sorted(REPOS))
```

### 2. The automatic loop: `Client(elicitation_callback=...)`
The high-level `call_tool` sees `input_required`, routes each input request to our callback, and retries with `inputResponses` + `requestState` until the result is complete. Our scripted "user" plays four scenarios.

```python
answers = []


async def confirm_dialog(context, params):
    print(f"   [dialog from github-admin] {params.message}")
    action, typed = answers.pop(0)
    print(f"   [user] {action} {typed or ''}")
    return types.ElicitResult(action=action, content={"repo_name": typed} if typed else None)


scenarios = {"decline": [("decline", None)],
             "cancel": [("cancel", None)],
             "typo, then correct": [("accept", "acme/wbe"), ("accept", "acme/web")]}

async with Client(github, elicitation_callback=confirm_dialog) as client:
    for label, script in scenarios.items():
        answers[:] = script
        result = await client.call_tool("delete_repository", {"repo": "acme/web"})
        print(f"{label:>20} -> {result.content[0].text}\n")
print("repos now:", sorted(REPOS))
```

### 3. Drive it manually and read the raw JSON
`client.session.call_tool(..., allow_input_required=True)` returns the interim result instead of resolving it. This is how you'd persist a pending question (for example, a chat waiting for a user who went to lunch) and resume later. We then build `inputResponses` ourselves and retry with the **exact** `requestState`.

```python
REPOS.add("acme/web")

async with Client(github, elicitation_callback=confirm_dialog) as client:
    first = await client.session.call_tool("delete_repository", {"repo": "acme/docs"}, allow_input_required=True)
    print("ROUND 1 result:\n", wire(first))
    saved_state = first.request_state                      # opaque: store it, never parse it
    key = next(iter(first.input_requests))

    responses = {key: types.ElicitResult(action="accept", content={"repo_name": "acme/docs"})}
    final = await client.session.call_tool("delete_repository", {"repo": "acme/docs"},
                                           input_responses=responses, request_state=saved_state,
                                           allow_input_required=True)
    print("\nROUND 2 result:\n", wire(final))
```

The `requestState` we minted was `{"repo": "acme/docs", "round": 1}`, but the client only ever sees a `v1.…` token. The SDK's `RequestStateBoundary` sealed it with AES-256-GCM together with an expiry, the method, the tool name, an arguments digest and the server's name as audience.

### 4. Break it: tamper with and replay `requestState`
Treat the client as an attacker. We (a) flip characters in the token, (b) replay a valid token on a *different* repository, and (c) send state the server never minted. Each one is rejected before our handler runs, with the same error so the attacker learns nothing.

```python
from mcp.shared.exceptions import MCPError

async with Client(github, elicitation_callback=confirm_dialog) as client:
    first = await client.session.call_tool("delete_repository", {"repo": "acme/web"}, allow_input_required=True)
    good = first.request_state
    yes = {"confirm_delete": types.ElicitResult(action="accept", content={"repo_name": "acme/prod"})}
    attacks = {"bit-flipped token": (good[:-6] + ("A" * 6 if not good.endswith("AAAAAA") else "B" * 6), "acme/web"),
               "replayed on another repo": (good, "acme/prod"),
               "forged plaintext state": (json.dumps({"repo": "acme/prod", "round": 1}), "acme/prod")}
    for label, (state, repo) in attacks.items():
        try:
            await client.session.call_tool("delete_repository", {"repo": repo}, input_responses=yes,
                                           request_state=state, allow_input_required=True)
            print(f"{label:>26}: ACCEPTED (bad!)")
        except MCPError as err:
            print(f"{label:>26}: {err.error.code} {err.error.message} {err.error.data}")
print("acme/prod still exists:", "acme/prod" in REPOS)
```

### 5. On the wire: raw JSON-RPC over stdio
Now there's no SDK on the client side. Watch the **ids** (1 then 2), the `resultType` values, and the state being echoed byte-for-byte. The `_meta` envelope declares `elicitation: {form: {}}` on *every* request, which is per-request capability negotiation.

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "confirm_server.py").write_text(textwrap.dedent('''
    import json
    import mcp_types as types
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context
```

### 6. Stateless scale-out: instance A asks, instance B finishes
Because the state travels with the request, the retry can land on a **different server instance**, provided they share the sealing key (and the same name, which is the token's audience). With the default per-process ephemeral key, instance C rejects A's token. This is the operational reason to configure `RequestStateSecurity(keys=[...])` behind a load balancer. A short TTL shows expiry too.

```python
import secrets
import time

from mcp.server.request_state import RequestStateSecurity

SHARED_KEY = secrets.token_hex(32)


def make_instance(label, security):
    srv = MCPServer("transfers", request_state_security=security)

    @srv.tool()
    def transfer(amount: int, ctx: Context) -> str | types.InputRequiredResult:
        """Transfer money after the user approves the amount."""
        answer = (ctx.input_responses or {}).get("approve")
        if answer is None:
            return types.InputRequiredResult(
                input_requests={"approve": types.ElicitRequest(params=types.ElicitRequestFormParams(
                    message=f"Approve transfer of {amount} EUR?",
                    requested_schema={"type": "object", "properties": {"approve": {"type": "boolean"}},
                                      "required": ["approve"]}))},
                request_state=json.dumps({"amount": amount}))
        return f"instance {label}: transferred {json.loads(ctx.request_state)['amount']} EUR"
    return srv


a = make_instance("A", RequestStateSecurity(keys=[SHARED_KEY], ttl=2))
b = make_instance("B", RequestStateSecurity(keys=[SHARED_KEY], ttl=2))
c = make_instance("C", None)                                          # default: ephemeral per-process key
approve = {"approve": types.ElicitResult(action="accept", content={"approve": True})}

async with Client(a, elicitation_callback=confirm_dialog) as ca, Client(b) as cb, Client(c) as cc:
    pending = await ca.session.call_tool("transfer", {"amount": 50}, allow_input_required=True)
    done = await cb.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                      request_state=pending.request_state, allow_input_required=True)
    print("A asked, B finished ->", done.content[0].text)
    try:
        await cc.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                   request_state=pending.request_state, allow_input_required=True)
    except MCPError as err:
        print("A asked, C (own ephemeral key) ->", err.error.message)
    time.sleep(2.2)
    try:
        await cb.session.call_tool("transfer", {"amount": 50}, input_responses=approve,
                                   request_state=pending.request_state, allow_input_required=True)
    except MCPError as err:
        print("after TTL, B ->", err.error.message)
```

The same valid token could be replayed on B *within* its TTL. A real transfer also needs a server-side "already used" record, since the spec says the protocol's measures don't guarantee single use.

### 7. URL mode: connect a third-party calendar without the secret touching the client
The server needs an OAuth grant for a third-party calendar. It sends a **URL-mode** elicitation and keeps a flow id in `requestState`. The client's callback shows the full URL and domain, gets consent and "opens a browser". Our fake browser completes the flow by calling the server's callback endpoint directly. The client only ever returns `{"action": "accept"}`. On retry, the server looks up the flow in **its own token store** (stateful, as the spec says for third-party tokens) and either finishes or asks again.

```python
import uuid
from urllib.parse import parse_qs, urlparse

calendar = MCPServer("calendar")
PENDING_FLOWS: dict[str, str] = {}      # flow_id -> user (server-side, bound to the authenticated user)
TOKENS: dict[str, str] = {}             # user -> third-party token (never sent to the client)


def oauth_callback(flow_id: str):
    """What the server's https://.../connect route would do after the third-party redirect."""
    user = PENDING_FLOWS.pop(flow_id)
    TOKENS[user] = f"tp-token-{secrets.token_hex(4)}"


@calendar.tool()
def next_meeting(ctx: Context) -> str | types.InputRequiredResult:
    """Return the user's next meeting from their third-party calendar."""
    user = "user-123"                                           # in production: the `sub` from MCP authorization
    if user in TOKENS:
        return f"Next meeting: Design review at 15:00 (fetched with a token the client never saw)"
    if ctx.request_state:                                       # retried, but the browser flow isn't done yet
        flow_id = json.loads(ctx.request_state)["flow"]
    else:
        flow_id = uuid.uuid4().hex[:8]
        PENDING_FLOWS[flow_id] = user
    return types.InputRequiredResult(
        input_requests={"connect": types.ElicitRequest(params=types.ElicitRequestURLParams(
            message="Connect your calendar so I can read your meetings.",
            url=f"https://mcp.example.com/connect?flow={flow_id}"))},
        request_state=json.dumps({"flow": flow_id}))


async def url_consent(context, params):
    if params.mode != "url":
        return types.ElicitResult(action="decline")
    domain = urlparse(params.url).hostname
    print(f"   [consent] calendar server wants to open: {params.url}\n   [consent] domain: {domain} -> user approves")
    flow = parse_qs(urlparse(params.url).query)["flow"][0]
    oauth_callback(flow)                                         # stands in for the user finishing OAuth in a browser
    return types.ElicitResult(action="accept")                   # no content in URL mode

async with Client(calendar, elicitation_callback=url_consent) as client:
    first = await client.session.call_tool("next_meeting", {}, allow_input_required=True)
    print("input request:", wire(first.input_requests["connect"]))
    print("\nauto loop ->", (await client.call_tool("next_meeting", {})).content[0].text)
    print("client-visible data contained a token?", any("tp-token" in json.dumps(v) for v in [wire(first)]))
```

There's no `elicitationId` and no `notifications/elicitation/complete`. The retry *is* the completion signal.

### 8. The declarative way: resolvers do the bookkeeping
For most tools you don't need hand-rolled state. A `Resolve(...)` resolver returns `Elicit(message, Model)`. The SDK builds the `InputRequiredResult`, records the answer in `requestState` so each question is asked only once, checks the client's capability (`-32021` if missing) and runs the body only when everything is resolved. Two resolvers here mean **two input requests in one round**.

```python
from typing import Annotated

from pydantic import BaseModel, Field

from mcp.server.elicitation import AcceptedElicitation, ElicitationResult
from mcp.server.mcpserver import Elicit, Resolve


class Environment(BaseModel):
    env: str = Field(json_schema_extra={"enum": ["staging", "production"]}, description="Target environment")


class Approval(BaseModel):
    approve: bool = Field(description="Approve this deployment?")


deployer = MCPServer("deployer")


def pick_env() -> Elicit[Environment]:
    return Elicit("Which environment?", Environment)


def approve(service: str) -> Elicit[Approval]:
    return Elicit(f"Deploy {service}? This restarts it.", Approval)


@deployer.tool()
def deploy(service: str,
           target: Annotated[Environment, Resolve(pick_env)],
           ok: Annotated[ElicitationResult[Approval], Resolve(approve)]) -> str:
    """Deploy a service after asking for the environment and an approval."""
    if isinstance(ok, AcceptedElicitation) and ok.data.approve:
        return f"Deployed {service} to {target.env}."
    return f"Deployment of {service} not approved ({ok.action})."


async def deploy_ui(context, params):
    props = params.requested_schema["properties"]
    content = {"env": "staging"} if "env" in props else {"approve": True}
    print(f"   [dialog] {params.message} -> {content}")
    return types.ElicitResult(action="accept", content=content)

async with Client(deployer, elicitation_callback=deploy_ui) as client:
    first = await client.session.call_tool("deploy", {"service": "api"}, allow_input_required=True)
    print("one round, input request keys:", list(first.input_requests))
    print((await client.call_tool("deploy", {"service": "api"})).content[0].text)

async with Client(deployer) as no_ui:
    try:
        await no_ui.call_tool("deploy", {"service": "api"})
    except MCPError as err:
        print("client without elicitation ->", err.error.code, err.error.message[:70])
```
