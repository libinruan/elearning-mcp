## Summary
MCP is versioned by date, and the jump from `2025-11-25` to `2026-07-28` is the biggest in its history: the `initialize` handshake, sessions, `ping` and server-initiated requests are gone; every request now carries its own version and capabilities; `server/discover` and `subscriptions/listen` are new; Roots, Sampling and Logging are deprecated. Real codebases and interviewers will mix both worlds, so this lesson is your map. You will learn how revisions and feature states work (Active → Deprecated → Removed, with a twelve-month floor), how a version is negotiated on every request and retried after `-32022`, how "dual-era" clients probe a server and fall back, the full compatibility matrix — and then a line-by-line digest of the changelog.

## Lesson
### Date-based revisions
MCP versions are strings of the form `YYYY-MM-DD`. The date marks **the last time backwards-incompatible changes were made** — the version is *not* incremented when the protocol gains backwards-compatible updates. So "2026-07-28" names a compatibility contract, not a release date of every edit.

Each revision of the specification is in one of three states:

| Revision state | Meaning |
| --- | --- |
| **Draft** | In progress, not ready for consumption. |
| **Current** | The version ready for use; may still receive backwards-compatible changes. |
| **Final** | Past, complete; will not change. |

The **Current** revision is `2026-07-28`. The revisions you will meet in the wild are `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` (all Final, all handshake-based) and `2026-07-28`.

> **Pitfall.** Revision dates happen to sort lexicographically, but treat versions as an **enumerated set**, not numbers. The Python SDK keeps an explicit ordered registry (`KNOWN_PROTOCOL_VERSIONS`) precisely so that an unknown string like `"zzz"` is never "newer" than `"2025-11-25"`.

### Modern, legacy and dual-era
The versioning spec defines three terms you should use precisely:

- **Modern** — versions that convey version, identity and capabilities as **per-request metadata** (`2026-07-28` and later).
- **Legacy** — versions that establish a session with an **`initialize` handshake** (`2025-11-25` and earlier).
- **Dual-era** — an implementation that supports both.

### Negotiation: on every request, no handshake
*There is no negotiation handshake.* Every request declares its version in `_meta["io.modelcontextprotocol/protocolVersion"]` (on Streamable HTTP, also in the `MCP-Protocol-Version` header), and **the server accepts or rejects each request independently**. Clients and servers **MAY** support several versions at once.

If the server does not implement the requested version — unknown to it, or known but deliberately unsupported — it **MUST** reply with `UnsupportedProtocolVersionError`:

```json
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32022, "message": "Unsupported protocol version",
           "data": {"supported": ["2026-07-28", "2025-11-25"], "requested": "1900-01-01"}}}
```

The client **SHOULD** pick a mutually supported version from `data.supported` and **retry**, or surface an error if none exists.

Servers **MUST** implement `server/discover`, which returns `supportedVersions`, `capabilities` and identity in one call. Clients **MAY** call it first to choose a version up front — but are not required to: *a client is free to invoke any RPC inline and handle `UnsupportedProtocolVersionError`*.

```text
Client                                  Server
  │ tools/call  _meta.protocolVersion=X   │
  │──────────────────────────────────────►│  supports X?  yes → result
  │◄──────────────────────────────────────│               no  → -32022 {supported:[…]}
  │ (on -32022) pick mutual Y, retry      │
  │──────────────────────────────────────►│
```

### Extension negotiation
Optional **extensions** are negotiated through capabilities, not versions. Both `ClientCapabilities` and `ServerCapabilities` have an `extensions` field: a map from **extension identifier** to a per-extension **settings object**. Identifiers **MUST** follow the `_meta` key naming rules, with a mandatory prefix — e.g. `io.modelcontextprotocol/ui` (MCP Apps) or `io.modelcontextprotocol/tasks` (Tasks). An empty object `{}` means "supported, no settings".

```json
{"capabilities": {"tools": {}, "extensions": {"io.modelcontextprotocol/tasks": {}}}}
```

If only one party supports an extension, the supporting party **MUST** either revert to core-protocol behaviour or reject the request with an appropriate error; extensions **SHOULD** document their fallback. This is how the protocol grows without bumping the core version (module 7).

### Backward compatibility with initialization-based versions
A server **MAY** implement both eras. A client that must talk to both kinds of server detects the era with transport-specific rules:

**stdio — probe with `server/discover`.** A dual-era client **SHOULD** send `server/discover` (with its preferred modern version in `_meta`) before anything else. Three outcomes:

1. A `DiscoverResult` → the server is modern; pick a version from `supportedVersions`.
2. A **recognized modern error** such as `UnsupportedProtocolVersionError` → the server is modern but not at that version; use its `supported` list. **Do not** fall back to `initialize`.
3. Any other error, or no response within a reasonable timeout → **legacy**; fall back to `initialize`.

The fallback **MUST NOT** be keyed to one error code: legacy servers answer unknown pre-`initialize` requests with implementation-defined errors (commonly `-32601` or `-32602`) or not at all. Even a modern-only client is **RECOMMENDED** to probe: some legacy servers would happily process an era-ambiguous `tools/call` under legacy semantics, and the probe turns that into a deterministic failure.

**Streamable HTTP — try a modern request, inspect the 400.** Modern servers also use `400 Bad Request` for `UnsupportedProtocolVersionError`, `MissingRequiredClientCapabilityError` and header-validation failures, so on a `400` the client **SHOULD** read the body: a recognized modern JSON-RPC error means "modern — fix the request"; an empty or unrecognized body means "legacy — fall back to `initialize`" (and possibly further to the deprecated HTTP+SSE transport).

The era is **a property of the server, not of a request**: clients **SHOULD** cache it for the lifetime of the server process (stdio) or origin (HTTP) and **MAY** persist it across restarts, re-probing if the assumption later fails. A modern-only server **SHOULD** name its supported versions in any error it returns to `initialize`, because legacy clients have **no fall-forward mechanism** — that error message may be the only diagnostic the user ever sees.

A **dual-era server** picks behaviour from how the client opens: a request carrying modern `_meta` is served statelessly; an `initialize` request selects legacy semantics scoped to the stdio process or HTTP session. It **MAY** serve both eras concurrently on the same endpoint.

### The compatibility matrix

| Client | Server | Outcome |
| --- | --- | --- |
| Modern | Modern | **Works.** `server/discover` optional; mismatches surface as `-32022` and the client retries. |
| Modern | Legacy | **Fails.** The server may return an implementation-defined error, stay silent, or even process an era-ambiguous method under legacy semantics. On stdio, send `server/discover` first to fail deterministically, then show an actionable error. |
| Dual-era | Modern | **Works.** stdio probe returns `DiscoverResult` (or `-32022`); on HTTP the first modern request succeeds or returns a modern error. Client stays modern. |
| Dual-era | Legacy | **Works.** stdio probe gets a non-modern error or times out → `initialize`. HTTP: `4xx` without a modern error body → `initialize` (maybe HTTP+SSE). |
| Legacy | Modern | **Fails.** stdio: `initialize` is rejected (unknown method, missing `_meta`). HTTP: missing required headers → `400`. No fall-forward. |
| Legacy | Dual-era | **Works.** Server answers `initialize` and serves the negotiated legacy revision. |
| Legacy | Legacy | Works per that legacy revision. |

The practical lesson: **the server side must be dual-era for a while** (old clients cannot upgrade themselves), and **clients should be dual-era** so they can still reach the long tail of 2025 servers. The notebook reproduces every row with live processes.

### Feature lifecycle: Active, Deprecated, Removed
Separately from revisions, individual *features* (messages, capabilities, transports, schema types, normative behaviours) have a lifecycle defined by **SEP-2596**:

| Feature state | Meaning | Implementer expectation |
| --- | --- | --- |
| **Active** | Part of the Current revision. | Implement per its normative requirements. |
| **Deprecated** | Still in the spec, scheduled for removal; migration path documented. | New implementations **should not adopt** it; existing ones **should migrate** before the earliest removal. |
| **Removed** | Deleted from `draft`; absent from the next Current revision; still documented in the Final revision it last appeared in. | Implementations targeting that revision must not depend on it. |

Rules worth memorising:

- Deprecation needs a **SEP** stating the rationale (superseded; unfixable security/privacy/interop risk; negligible adoption vs maintenance cost; or other Core Maintainer reasons) and a **migration path** (any replacement must be Active in the same revision).
- The **minimum deprecation window is twelve months**, measured from the **release of the revision** that first marks the feature Deprecated — not from SEP approval. The feature's **earliest removal** is the first revision released as Current on or after the window elapses. Actual removal is a Core Maintainer decision and may come much later.
- **Expedited removal**: for an active security risk (published advisory or in-the-wild exploitation, no in-place fix), Core Maintainers may shorten the window — but never below **ninety days**.
- A Deprecated feature may be **restored** to Active by a superseding SEP; a later re-deprecation restarts the clock.
- Deprecation leaves marks: `@deprecated` in `schema.ts`, a notice in the prose, a "Deprecated" changelog entry, and a row in the **deprecated registry**.
- **Tier 1 SDKs** must mark the API deprecated with the language's native mechanism in their next release and should emit a runtime warning (Python: a `DeprecationWarning`). Removal from the spec does **not** force SDKs to drop a feature; that follows each SDK's own support policy.

### What changed: 2025-11-25 → 2026-07-28
**Major changes**

| # | Change | Old (2025-11-25) | New (2026-07-28) |
| --- | --- | --- | --- |
| 1 | Sessions removed (SEP-2567) | `Mcp-Session-Id` header; lists could vary per connection | No protocol sessions; list endpoints don't vary per connection; cross-call state uses **server-minted handles passed as tool arguments** |
| 2 | Stateless protocol (SEP-2575) | `initialize` / `notifications/initialized` handshake | Every request carries `io.modelcontextprotocol/protocolVersion` + `clientCapabilities` in `_meta`; clients SHOULD send `clientInfo`, servers SHOULD return `serverInfo` in each result's `_meta`; mismatch → `UnsupportedProtocolVersionError` |
| 3 | `server/discover` (SEP-2575) | Capabilities learned once from `initialize` | Servers MUST implement it; clients MAY call it first or use it as a stdio compatibility probe |
| 4 | `subscriptions/listen` (SEP-2575) | HTTP `GET` stream, `resources/subscribe` / `resources/unsubscribe` | One long-lived POST-response stream; opt in to `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`; ack + `subscriptionId` tagging. `notifications/progress` and `notifications/message` stay on their request's own stream |
| 5 | Removals (SEP-2575) | `ping`, `logging/setLevel`, `notifications/roots/list_changed` | Gone. Log level is per request via `io.modelcontextprotocol/logLevel` in `_meta`; servers MUST NOT emit `notifications/message` for requests without it |
| 6 | Tasks → extension (SEP-2663) | Experimental core tasks, blocking `tasks/result`, `tasks/list` | Extension `io.modelcontextprotocol/tasks`: poll with `tasks/get`, input via `tasks/update`, no `tasks/list`; servers may return task handles unsolicited |

| 8 | `resultType` everywhere (SEP-2322) | No such field | Required: `"complete"` or `"input_required"`; results from older servers without it MUST be treated as `"complete"` |
| 9 | No SSE resumability (SEP-2575) | `Last-Event-ID`, SSE event IDs, redelivery | A broken stream loses the in-flight request; the client MUST re-issue it with a **new request ID** |

**Deprecated** in this revision: Roots, Sampling, Logging (SEP-2577); HTTP+SSE reclassified; `includeContext` `"thisServer"`/`"allServers"` reclassified; Dynamic Client Registration in favour of Client ID Metadata Documents. **Other**: `schema.json` now types `minimum`/`maximum`/`default` as `number`. **Governance/process**: the feature lifecycle policy (SEP-2596) and a PR-based SEP workflow with files in `seps/` (SEP-1850).

> **Interview tip.** If asked "what changed in MCP recently?", lead with the *theme*, not the list: **MCP became stateless**. Sessions, the handshake, `ping`, SSE resumability and server-initiated requests all existed to maintain connection state; removing them lets any replica behind a load balancer serve any request. `server/discover`, per-request `_meta`, MRTR, `subscriptions/listen` and `ttlMs` caching are the pieces that replace what state used to do.

## Key points
- Versions are `YYYY-MM-DD` strings marking the **last backwards-incompatible change**; compatible updates don't bump them. Revisions are **Draft / Current / Final**; Current is `2026-07-28`.
- **No handshake**: each request carries `io.modelcontextprotocol/protocolVersion` in `_meta` (plus `MCP-Protocol-Version` on HTTP); servers accept or reject per request.
- Unsupported version → **`-32022` `UnsupportedProtocolVersionError`** with `data.supported` and `data.requested`; client picks a mutual version and retries.
- `server/discover` is **mandatory for servers, optional for clients**.
- Extensions negotiate via the `extensions` map in capabilities; if one side lacks it, revert to core behaviour or reject.
- Dual-era stdio clients probe with `server/discover` and fall back to `initialize` on **any non-modern error or timeout** — never keyed to one code; on HTTP they inspect the `400` body. Cache the era per server.
- Feature states **Active → Deprecated → Removed**; ≥ **12-month** window from the deprecating revision's release (≥ **90 days** for expedited security removals).
- Deprecated in 2026-07-28: **Roots, Sampling, Logging, Dynamic Client Registration**; already deprecated: HTTP+SSE, `includeContext` `thisServer`/`allServers`.
- Removed in 2026-07-28: **sessions, `initialize`, `ping`, `logging/setLevel`, `resources/subscribe`, SSE resumability, server-initiated requests, core tasks**.

## Pitches
### What changed in MCP 2026-07-28?
The headline is that MCP became stateless. In 2025 a client opened a session with an initialize handshake and the server remembered its version and capabilities. Now every request carries its protocol version and client capabilities in metadata, servers expose a server/discover call, and sessions, ping and resumable SSE streams are gone. Servers no longer send requests to clients; they return an input-required result and the client retries. Change notifications moved to subscriptions/listen, and Roots, Sampling and Logging were deprecated.

### How does MCP version negotiation work now?
There is no handshake. Each request declares its version in the underscore-meta field, and on HTTP also in a header. If the server doesn't support it, it returns error minus 32022 with the list of versions it does support, and the client retries with the best mutual one. A client can also call server/discover up front to learn the supported versions and capabilities in one go. For old servers, a dual-era client probes with discover and falls back to the initialize handshake if the reply isn't a recognisably modern error.

### How does MCP deprecate features?
Features move through Active, Deprecated and Removed. Deprecating something needs a SEP with a rationale and a migration path, and the feature then stays in the spec for at least twelve months, counted from the release of the revision that deprecated it — only ninety days if there's an active security exploit. A public registry lists everything on its way out. Tier 1 SDKs must mark the API deprecated and should warn at runtime, so in practice I see a deprecation warning in my code long before anything breaks.

## Interview
### Why did MCP remove the `initialize` handshake? What replaced each of its jobs?
The handshake created per-connection state: a negotiated version, both sides' capabilities and identities, held for a session. That made horizontal scaling awkward (sticky sessions, session stores) and complicated reconnection. In 2026-07-28 each job moved: **version** → `io.modelcontextprotocol/protocolVersion` in every request's `_meta`, rejected with `-32022` if unsupported; **client capabilities** → `io.modelcontextprotocol/clientCapabilities` on every request; **identity** → `clientInfo` on requests and `serverInfo` in results' `_meta`; **server capabilities and versions** → `server/discover`, which is cacheable via `ttlMs`/`cacheScope`. The result: any server instance can process any request on its own.

### A client gets error `-32022` from a server. What should it do — and what should it *not* do?
`-32022` is `UnsupportedProtocolVersionError`; `data.supported` lists the server's versions and `data.requested` echoes the one sent. The client **SHOULD** intersect `supported` with its own versions, pick the best mutual one and **retry** the request; if there is none, surface a clear error. It should **not** fall back to the legacy `initialize` handshake: a recognized modern error proves the server is modern. It also should not compare versions by naive string arithmetic for unknown values — use the set of versions it actually implements.

### You maintain a popular stdio MCP server used by both old and new clients. How do you migrate?
Make it **dual-era**: if the first message is `initialize`, serve legacy semantics for that process; if it carries modern `_meta`, serve statelessly. Implement `server/discover`, add `resultType`, `ttlMs`/`cacheScope`, and `serverInfo` in result `_meta`. Replace any server-initiated requests with MRTR (`InputRequiredResult` + retry) on the modern path. Stop relying on per-connection state — use explicit handles passed as tool arguments. Move logging to `stderr`. Keep legacy support until telemetry says old clients are gone; if you ever drop it, make the `initialize` error **name your supported versions**, since legacy clients cannot fall forward.

### How does a dual-era client decide whether a stdio server is modern or legacy? Why not just check for `-32601`?
It sends `server/discover` first with its preferred modern version. A `DiscoverResult` or a recognized modern error (like `-32022`) means modern. Any other error, or a timeout, means legacy → send `initialize`. Keying on `-32601` is explicitly forbidden: legacy servers answer pre-`initialize` requests with implementation-defined errors (`-32601`, `-32602`, `-32600`…) or not at all. The client should then **cache** the verdict for that server process. Even modern-only clients should probe, because some legacy servers would execute an era-ambiguous `tools/call` without complaint.

### Sampling is deprecated. Can I still use it? When will it disappear?
Yes — Deprecated means it is still part of the spec and fully functional; new implementations **should not adopt** it and existing ones **should migrate** (integrate directly with an LLM provider API). It was deprecated in `2026-07-28` by SEP-2577 with a twelve-month minimum window, so its **earliest removal** is the first revision released as Current on or after 2027-07-28 — and removal is a Core Maintainer decision that may come later. SDKs may keep supporting it beyond spec removal under their own policies. Contrast with `ping`, which 2026-07-28 **removed** outright.

### Gotcha: "A modern client can talk to any MCP server as long as it handles `-32022`." True?
No. `-32022` only helps against **modern** servers at a different version. Against a **legacy** server, a modern-only client fails: the server may return an arbitrary error, never answer, or — worse — process an era-ambiguous request like `tools/call` under legacy semantics. That is why the spec recommends probing with `server/discover` even for modern-only clients (deterministic failure), and why production clients should be **dual-era**, falling back to `initialize` on stdio or after inspecting a `400` body on HTTP.

## Glossary
- Protocol revision | 协议修订版 | A dated version (`YYYY-MM-DD`) of the spec marking the last backwards-incompatible change; Draft, Current or Final.
- Modern / legacy era | 新时代 / 旧时代协议 | Per-request-metadata versions (`2026-07-28`+) versus `initialize`-handshake versions (`2025-11-25` and earlier).
- Dual-era implementation | 双时代实现 | A client or server that supports both modern and legacy versions.
- `UnsupportedProtocolVersionError` | 不支持的协议版本错误 | Error `-32022` returned when a request's version is not implemented; `data.supported` lists alternatives.
- `server/discover` | `server/discover`（服务器发现） | Mandatory server RPC returning supported versions, capabilities and identity; optional for clients to call.
- Extension negotiation | 扩展协商 | Advertising optional extensions in the `extensions` map of capabilities, keyed by prefixed identifiers.
- Era probe | 时代探测 | A dual-era client's initial `server/discover` used to decide between modern requests and the legacy `initialize` fallback.
- Feature lifecycle | 特性生命周期 | The Active → Deprecated → Removed states a spec feature moves through under SEP-2596.
- Deprecation window | 弃用窗口期 | The minimum time (≥ 12 months, or ≥ 90 days if expedited) a feature stays Deprecated before it may be removed.
- SEP (Specification Enhancement Proposal) | 规范增强提案 | The formal proposal process required to change, deprecate or restore spec features.

## Notebook
### 1. Version strings and a negotiation function
Versions are an enumerated set. A client and a server each support some subset; the client wants the newest version both share. Order comes from an explicit registry, not from string comparison.

```python
import json

KNOWN_VERSIONS = ["2024-11-05", "2025-03-26", "2025-06-18", "2025-11-25", "2026-07-28"]  # oldest -> newest
MODERN = {"2026-07-28"}   # per-request _meta era; everything older uses the initialize handshake


def choose_version(client_supports, server_supports, known=KNOWN_VERSIONS):
    """Newest version both sides support, or None. Unknown strings are ignored, never 'newer'."""
    mutual = [v for v in known if v in client_supports and v in server_supports]
    return mutual[-1] if mutual else None


cases = {
    "both modern":               (["2026-07-28", "2025-11-25"], ["2026-07-28"]),
    "server still on 2025":      (["2026-07-28", "2025-11-25"], ["2025-06-18", "2025-11-25"]),
    "no overlap":                (["2026-07-28"], ["2025-03-26"]),
    "server claims 'zzz'":       (["2026-07-28"], ["zzz", "2026-07-28"]),
}
for label, (client, server) in cases.items():
    picked = choose_version(client, server)
    era = "-" if picked is None else ("modern" if picked in MODERN else "legacy handshake")
    print(f"{label:<22} -> {picked}  ({era})")
```

### 2. Three servers for the rest of the notebook
We need one server of each era. The SDK's `MCPServer` is **dual-era**. The other two are tiny hand-written JSON-RPC loops: a **legacy** server that only understands `initialize` (like any 2025 server that hasn't upgraded), and a **modern-only** server that rejects `initialize` with `-32022` naming its versions, as the spec recommends. A small **wiretap** script sits between client and server and logs every line in both directions.

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())

(workdir / "dual_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    server = MCPServer("weather", version="2.3.0")

    @server.tool()
    def weather_current(location: str) -> str:
        """Get current weather for a location."""
        return f"{location}: 20 degrees (dual-era SDK server)"

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

(workdir / "legacy_server.py").write_text(textwrap.dedent('''
    """A 2025-11-25-era server: initialize handshake or nothing."""
    import json, sys
    initialized = False
    def reply(id_, result=None, error=None):
        print(json.dumps({"jsonrpc": "2.0", "id": id_, **({"error": error} if error else {"result": result})}), flush=True)
    for line in sys.stdin:
        msg = json.loads(line); method, id_ = msg.get("method"), msg.get("id")
        if method == "initialize":
            reply(id_, {"protocolVersion": "2025-11-25", "capabilities": {"tools": {}},
                        "serverInfo": {"name": "old-weather", "version": "0.9.0"}})
        elif method == "notifications/initialized":
            initialized = True
        elif not initialized:
            reply(id_, error={"code": -32600, "message": "Server not initialized"})
        elif method == "tools/list":
            reply(id_, {"tools": [{"name": "weather_current", "description": "Current weather",
                                   "inputSchema": {"type": "object", "properties": {"location": {"type": "string"}}}}]})
        elif method == "tools/call":
            reply(id_, {"content": [{"type": "text", "text": "Sunny (legacy 2025 server)"}]})
        elif method == "ping":
            reply(id_, {})
        elif id_ is not None:
            reply(id_, error={"code": -32601, "message": f"Method not found: {method}"})
```

### 3. Per-request negotiation by hand: `-32022` and retry
A future client prefers a (hypothetical) newer revision `2027-03-01` and also speaks `2026-07-28`. It sends its request without any discovery, reads `data.supported` from the error, negotiates, and retries — exactly the flow in the versioning spec.

```python
CLIENT_SUPPORTS = ["2027-03-01", "2026-07-28"]   # newest first; 2027-03-01 is made up for the demo


def envelope(version):
    return {"io.modelcontextprotocol/protocolVersion": version,
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "future-client", "version": "1.0"}}


proc = subprocess.Popen([sys.executable, str(SERVERS["dual-era"])],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE, text=True)


def rpc(message):
    print(">>>", json.dumps(message)[:200])
    proc.stdin.write(json.dumps(message) + "\n"); proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    print("<<<", json.dumps(reply)[:300], "\n")
    return reply


def call_with_negotiation(request_id, method, params):
    version = CLIENT_SUPPORTS[0]
    for attempt in range(2):
        reply = rpc({"jsonrpc": "2.0", "id": request_id + attempt, "method": method,
                     "params": {**params, "_meta": envelope(version)}})
        error = reply.get("error")
        if not error or error["code"] != -32022:
            return version, reply
        mutual = [v for v in CLIENT_SUPPORTS if v in error["data"]["supported"]]
        if not mutual:
            raise RuntimeError(f"no common version: server supports {error['data']['supported']}")
        version = mutual[0]
        print(f"... server rejected {error['data']['requested']}, retrying with {version}\n")
    raise RuntimeError("negotiation did not converge")


version, reply = call_with_negotiation(1, "tools/call", {"name": "weather_current", "arguments": {"location": "Oslo"}})
print("negotiated:", version, "| result:", reply["result"]["content"][0]["text"])
proc.stdin.close()
exit_code = proc.wait(timeout=10)
```

Notice there was no handshake: the *same* `tools/call` was simply re-sent with a different `_meta` version and a new `id`.

### 4. The SDK's two connection modes, on the wire
`Client(..., mode="legacy")` forces the 2025 `initialize` handshake; the default `mode="auto"` probes with `server/discover` and falls back only if the reply is not modern evidence. Same dual-era server, two very different conversations.

```python
import os

from mcp import Client, StdioServerParameters


def tapped(server_key, log_name):
    log = workdir / log_name
    log.unlink(missing_ok=True)
    return log, StdioServerParameters(command=sys.executable, args=[str(workdir / "wiretap.py"), str(log), str(SERVERS[server_key])])


def print_wire(log, width=260):
    for line in log.read_text().splitlines():
        print(line[:width])


for mode in ["legacy", "auto"]:
    log, params = tapped("dual-era", f"wire_{mode}.log")
    async with Client(params, mode=mode) as client:
        result = await client.call_tool("weather_current", {"location": "Paris"})
        print(f"===== mode={mode!r}: negotiated {client.protocol_version}, "
              f"tools.listChanged={client.server_capabilities.tools.list_changed}")
    print_wire(log)
    print()
```

Read the two logs side by side: **legacy** sends `initialize`, then `notifications/initialized`, then bare requests with no `_meta`, and results lack `resultType`. **auto** sends `server/discover` first and every later request carries the full envelope; results carry `resultType`, `ttlMs`/`cacheScope` and `serverInfo`. (The SDK also issues a `tools/list` after `tools/call` to validate the tool's output schema — handy to know when reading logs.)

### 8. A migration linter for 2025-era traffic
Engineers inherit old code and logs. Encode the changelog and the deprecated registry as data, then scan the legacy wire log captured in section 4 (plus a few extra snippets) for anything removed or deprecated in 2026-07-28.

```python
RULES = [  # (needle, state, what to do instead)
```

### 9. When can a deprecated feature disappear?
The window is measured from the **release** of the deprecating revision; the earliest removal is the first revision released as Current on or after the window ends. The release dates below after 2026-07-28 are **invented** for the exercise.

```python
from datetime import date


def add_months(d, months):
    y, m = divmod(d.month - 1 + months, 12)
    return date(d.year + y, m + 1, min(d.day, 28))


def earliest_removal(deprecated_in, releases, months=12, days=None):
    """First release on/after the window ends. `days` models an expedited (security) window, min 90."""
    if days is not None:
        assert days >= 90, "expedited removal still needs at least ninety days"
        window_end = date.fromordinal(deprecated_in.toordinal() + days)
    else:
        assert months >= 12, "the standard window is at least twelve months"
        window_end = add_months(deprecated_in, months)
    return window_end, next((r for r in sorted(releases) if r >= window_end), None)


hypothetical_releases = [date(2026, 12, 15), date(2027, 6, 30), date(2027, 11, 18), date(2028, 5, 2)]
deprecated = date(2026, 7, 28)   # Roots, Sampling, Logging, DCR
for label, kwargs in [("standard 12 months", {}), ("SEP asks for 18 months", {"months": 18}),
                      ("expedited, 120 days", {"days": 120})]:
    end, release = earliest_removal(deprecated, hypothetical_releases, **kwargs)
    print(f"{label:<24} window ends {end} -> earliest removal in revision released {release}")
```

Note how the 12-month case lands on 2027-11-18, not 2027-07-28: removal only happens *in a release*, and the 2027-06-30 one came too early.
