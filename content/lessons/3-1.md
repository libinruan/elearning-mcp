## Summary
Tools are the primitive that lets a language model *act*: query a database, call an API, book a flight. A server advertises them with `tools/list` — each one a name, a description and a JSON Schema for its input (and optionally its output) — and the client invokes them with `tools/call`. This lesson walks the whole Tools page of the 2026-07-28 spec: the model-controlled interaction model and why a human must stay in the loop, the capability and its `listChanged` flag, naming rules, every field of a `Tool`, the five content types a result can carry, `structuredContent` validated by an `outputSchema`, the crucial split between protocol errors and `isError` results, explicit handles for stateful tools, and the security duties of both sides.

## Lesson
### Where tools sit among the three primitives
A server offers three building blocks, and the official "Understanding MCP servers" page frames each by **who controls it**:

| Primitive | What it is | Controlled by | Typical examples |
| --- | --- | --- | --- |
| **Tools** | Functions the LLM can actively call; may write to databases, call APIs, modify files | **Model** | search flights, send messages, create calendar events |
| **Resources** | Passive, read-only data sources used as context | **Application** | documents, knowledge bases, calendars |
| **Prompts** | Pre-built instruction templates | **User** | "plan a vacation", "summarise my meetings" |

Tools are the only primitive with *side effects*, which is why they get the most safety machinery. In the docs' travel example the model calls `searchFlights`, `createCalendarEvent` and `sendEmail` — the last two change the world, and the user should see and approve them.

### The interaction model: model-controlled, human-supervised
Tools are **model-controlled**: the LLM discovers them and decides to invoke them from context and the user's request. The protocol does not mandate any UI, but the spec adds a strong warning: for trust & safety there **SHOULD** always be a human in the loop who can deny an invocation. Applications SHOULD:

- make clear which tools are exposed to the model,
- show a clear visual indicator whenever a tool is invoked,
- present confirmation prompts for operations.

In practice hosts implement this with per-tool enable/disable toggles, approval dialogs, "always allow" settings for pre-approved safe operations, and activity logs of every call and result.

### Capability and discovery: `tools/list`
A server with tools **MUST** declare the capability (in its `server/discover` result):

```json
{"capabilities": {"tools": {"listChanged": true}}}
```

`listChanged` says the server will emit notifications when the set of tools changes. A server that declares `tools` **MUST** answer `tools/list` with the tools currently available to the requesting client. The set MAY be empty and MAY change over time, but **MUST NOT vary per connection or as a side effect of other requests** — sessions were removed in 2026-07-28, so there is no connection state to vary on. It **MAY** vary by the *authorization* on the request (e.g. only the tools the caller's scopes allow), because credentials are per-request input.

Servers **SHOULD** return tools in a **deterministic order** (new in 2026-07-28). Same set → same order means a client can cache the list, and — less obviously — the tool definitions a host puts at the top of an LLM prompt stay byte-identical, so the model provider's **prompt cache** keeps hitting. `tools/list` supports pagination (`cursor` / `nextCursor`) and caching (`ttlMs`, `cacheScope` — lesson 3.4):

```json
{"jsonrpc": "2.0", "id": 1, "result": {
  "resultType": "complete",
  "tools": [{"name": "get_weather", "title": "Weather Information Provider",
             "description": "Get current weather information for a location",
             "inputSchema": {"type": "object",
                             "properties": {"location": {"type": "string", "description": "City name or zip code"}},
                             "required": ["location"]}}],
  "nextCursor": "next-page-cursor", "ttlMs": 300000, "cacheScope": "public"}}
```

### Anatomy of a `Tool`
| Field | Required | Meaning |
| --- | --- | --- |
| `name` | yes | Unique identifier, used in `tools/call` |
| `title` | no | Human-readable display name |
| `description` | no (in practice essential) | What it does — this is what the model reads to decide |
| `inputSchema` | yes | JSON Schema for the arguments; **MUST** be a valid schema object with `"type": "object"`, never `null` |
| `outputSchema` | no | JSON Schema the `structuredContent` must conform to |
| `annotations` | no | `ToolAnnotations` behaviour hints |
| `icons` | no | Sized icons for UIs (`src`, `mimeType`, `sizes`) |
| `_meta` | no | Extension metadata |

Both schemas default to **JSON Schema 2020-12** when no `$schema` is given; a server may opt into another dialect (e.g. draft-07) explicitly. For a tool with no parameters the spec **recommends** `{"type": "object", "additionalProperties": false}` (accepts only `{}`); `{"type": "object"}` also works but accepts any object. In 2026-07-28 both schemas were loosened to allow *any* 2020-12 keywords, and `$ref` resolution rules were added that clients follow when validating.

Display-name precedence for a tool is `title`, then `annotations.title`, then `name`.

**`ToolAnnotations`** are hints about behaviour: `title`, `readOnlyHint` (default `false`), `destructiveHint` (default `true`, meaningful only when not read-only), `idempotentHint` (default `false`), `openWorldHint` (default `true` — interacts with external entities, like web search, versus a closed domain like a memory store). They let a host decide, say, to skip the confirmation for a read-only lookup. But:

> **Spec rule.** Clients **MUST** consider tool annotations untrusted unless they come from trusted servers, and should never make tool-use decisions based on annotations from untrusted servers.

Two more details. Properties in `inputSchema` may carry **`x-mcp-header`**, which mirrors a primitive argument into an `Mcp-Param-{name}` HTTP header so load balancers and WAFs can route without parsing the body (new in 2026-07-28; details in lesson 2.3; never mark secrets this way). And if you saw `execution.taskSupport` on tools in 2025-11-25 code: tasks left the core spec for the `io.modelcontextprotocol/tasks` extension, and the 2026-07-28 `Tool` schema has no `execution` field.

### Tool names
Names **SHOULD** be 1–128 characters, case-sensitive, using only `A-Z a-z 0-9 _ - .` — no spaces, commas or other special characters — and unique within a server. Valid examples: `getUser`, `DATA_EXPORT_v2`, `admin.tools.list`. Uniqueness is only per server: a host aggregating several servers will meet two `search` tools and **SHOULD** disambiguate, for example by prefixing a server identifier. Don't use `serverInfo.name` for that — it is not guaranteed unique.

### Invoking: `tools/call`
```json
{"jsonrpc": "2.0", "id": 2, "method": "tools/call",
 "params": {"name": "get_weather", "arguments": {"location": "New York"}}}
```
The result is a `CallToolResult`: `content` (a list of content blocks), optional `structuredContent`, optional `isError` (absent means `false`), plus `resultType: "complete"`. (Like every request in 2026-07-28 the real message also carries the `_meta` envelope; the spec examples omit it for brevity.)

A server MAY instead answer with `resultType: "input_required"` — an `InputRequiredResult` whose `inputRequests` ask the client for, e.g., an elicitation. The client then retries `tools/call` with a **new JSON-RPC id**, adding `inputResponses` and echoing `requestState`. This multi round-trip pattern replaced server-initiated requests; lesson 5.3 covers it.

### What a result can contain
**Unstructured** content goes in `content`, which may mix several blocks:

| `type` | Shape | Use |
| --- | --- | --- |
| `text` | `text` | The common case |
| `image` | base64 `data` + `mimeType` | Charts, screenshots |
| `audio` | base64 `data` + `mimeType` | Speech, recordings |
| `resource_link` | `uri`, `name`, optional `description`, `mimeType` | Point at a resource the client can fetch or subscribe to |
| `resource` | embedded `resource` with `uri`, `mimeType`, `text` or `blob` | Inline the resource contents |

Every content type accepts the same optional **annotations** as resources — `audience` (`"user"` / `"assistant"`), `priority` (0–1), `lastModified` — so an image can be marked "for the user's eyes" (`audience: ["user"]`) and kept out of the model's context. A `resource_link` returned by a tool is not guaranteed to appear in `resources/list`; servers that embed resources SHOULD implement the `resources` capability.

**Structured** content goes in `structuredContent` — any JSON value (object, array, string, number, boolean or null; widened from objects-only in 2026-07-28). If the tool declares an `outputSchema`, servers **MUST** return structured results that conform, and clients **SHOULD** validate them. For backward compatibility a tool returning structured content SHOULD also put the serialised JSON in a text block. Note the docs' clarification: `structuredContent` is *server-produced data*, unrelated to LLM "structured outputs".

Why both? The text block is for the model; `structuredContent` plus `outputSchema` is a typed contract for programs — a host can render a table, a code-mode agent can chain the value into the next call, and validation catches a server that drifted from its declared shape.

### Two kinds of errors
This is the most-asked tools question in interviews.

1. **Protocol errors** — standard JSON-RPC errors for problems with the request itself: unknown tool, a request that fails the `CallToolRequest` schema, server errors. Example: `{"code": -32602, "message": "Unknown tool: invalid_tool_name"}`.
2. **Tool execution errors** — a normal result with `isError: true` and an explanation in `content`: API failures, **input validation errors** (date in the wrong format, value out of range), business-logic errors.

```json
{"resultType": "complete", "isError": true,
 "content": [{"type": "text", "text": "Invalid departure date: must be in the future. Current date is 08/08/2025."}]}
```

The reason is the model. Clients **SHOULD** pass tool execution errors to the LLM so it can **self-correct and retry**; they MAY pass protocol errors too, but those are less likely to help. If a tool threw a JSON-RPC error for "date in the past", most hosts would surface a generic failure and the model would never learn what to change.

> **Pitfall.** The Python SDK's `MCPServer` reports even an *unknown tool name* as an `isError` result rather than `-32602`; malformed params (e.g. no `name`) do come back as `-32602`. Know the spec's split, and test what your SDK actually sends.

### List changed — now via `subscriptions/listen`
When its tool set changes, a server that declared `listChanged` **SHOULD** send `notifications/tools/list_changed` — but in 2026-07-28 only to clients that opened a **`subscriptions/listen`** stream with `toolsListChanged: true` (the old standalone HTTP GET stream is gone; lesson 3.4). The client then re-fetches `tools/list`.

### Stateful tools: explicit handles
With no protocol session, a server cannot tie one call to the next through connection state. The non-normative guidance: return an **explicit handle** from a creation tool (`create_basket` → `{"basket_id": "bsk_a1b2c3"}`) and accept it as an argument on later calls (`add_item(basket_id, sku)`). The model carries the handle forward. Design rules: a handle is a *name*, not a capability — re-check the caller's authorization on every call (for unauthenticated servers, mint it with real entropy such as UUIDv4 and bound its lifetime); keep it **opaque**; state the **lifetime** in the creation tool's description ("expires after 24 hours of inactivity"); and answer an expired or unknown handle with a **tool execution error** so the model can recover by creating a new one. Lesson 4.2 turns this into design practice.

### Security considerations
Servers **MUST** validate all inputs, implement access controls, rate-limit invocations and sanitise outputs. Clients **SHOULD** prompt for confirmation on sensitive operations, show tool inputs to the user before calling (to catch accidental or malicious exfiltration), validate results before passing them to the LLM, follow the `$ref` resolution rules when validating, implement timeouts, and log tool usage for audit.

## Key points
- Tools are **model-controlled**, but the spec says there SHOULD always be a **human in the loop** able to deny invocations.
- Declare `tools` (with optional `listChanged`); `tools/list` MUST NOT vary per connection but MAY vary by authorization, and SHOULD be in **deterministic order** for client and prompt caching.
- A `Tool` has `name` and `inputSchema` (required, an object schema, never `null`), plus `title`, `description`, `outputSchema`, `annotations`, `icons`, `_meta`. Schemas default to JSON Schema 2020-12.
- Names SHOULD be 1–128 chars of `A-Za-z0-9_-.`, case-sensitive, unique per server; multi-server hosts disambiguate by prefixing.
- Result content types: `text`, `image`, `audio`, `resource_link`, embedded `resource`; all accept `audience`/`priority`/`lastModified` annotations.
- With an `outputSchema`, servers MUST return conforming `structuredContent` (any JSON value) and clients SHOULD validate it; also include the JSON as text for compatibility.
- Unknown tool / malformed request → **JSON-RPC error**; API, validation and business failures → **`isError: true`** result the model can read and fix.
- `ToolAnnotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) are **untrusted hints** unless the server is trusted.
- Cross-call state uses **explicit opaque handles** passed as arguments; `list_changed` arrives only on a `subscriptions/listen` stream.

## Pitches
### How does a model actually use an MCP tool?
The host calls `tools/list` on each server and gets every tool's name, description and JSON Schema for its input. It hands those to the model as function definitions. When the model decides to use one, the host shows the call to the user if it needs approval, sends `tools/call` with the name and arguments, and feeds the returned content back to the model. So the model chooses, the host executes and supervises, and the server just runs the function and describes the result.

### Why does MCP distinguish isError results from protocol errors?
Because the reader of a tool error is usually the model, and the model can only fix what it can see. If my tool gets a date in the wrong format, I return a normal result with isError true and a message like "use YYYY-MM-DD"; the host passes it to the model, which retries correctly. A JSON-RPC error is for things the model can't fix — an unknown tool, a malformed request, a crashed server — and hosts typically turn it into a generic failure.

### What are tool annotations and can I rely on them?
Annotations are hints such as readOnlyHint, destructiveHint, idempotentHint and openWorldHint. They help a host design good UX — skip the confirmation dialog for a read-only lookup, warn loudly before a destructive delete. But they are self-reported by the server, so the spec says clients must treat them as untrusted unless the server itself is trusted. I use them to make approvals smoother for vetted servers, never as a security boundary for unknown ones.

## Interview
### Walk me through the fields of an MCP Tool definition.
`name` (required, unique per server, 1–128 chars of `A-Za-z0-9_-.`), optional `title` for display, `description` that the model reads to choose the tool, `inputSchema` (required, a JSON Schema object with `type: "object"`, default dialect 2020-12), optional `outputSchema` that `structuredContent` must conform to, optional `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`), optional `icons`, and `_meta`. Display precedence is `title` → `annotations.title` → `name`. A strong answer adds that the description and schema *are* the prompt the model sees, so they deserve the same care as any prompt.

### A tool receives `{"date": "31/02/2026"}`. How should it fail, and why?
As a **tool execution error**: a normal `CallToolResult` with `isError: true` and actionable text — "Invalid date 31/02/2026: use YYYY-MM-DD and a real calendar date." The spec lists input validation errors under execution errors precisely so the client SHOULD pass them to the LLM, which can self-correct and retry. A JSON-RPC `-32602` is reserved for problems with the request structure itself — unknown tool, params that don't match `CallToolRequest` — which the model is unlikely to fix.

### What is `structuredContent` and when do you add an `outputSchema`?
`structuredContent` is a JSON value (any type since 2026-07-28) carrying the tool's result for *programs*: UIs, code-mode agents, downstream pipelines. When you declare an `outputSchema`, the server MUST return conforming data and clients SHOULD validate it, giving you a typed contract and early detection of drift. Add one whenever a consumer will parse the result. Keep the serialised JSON in a text block too, for older clients and for the model. It has nothing to do with LLM "structured outputs".

### Your host connects to three servers that each expose `search`. What do you do?
Tool names are only unique per server, and the spec says aggregating clients SHOULD implement a disambiguation strategy, e.g. prefixing with a server identifier (`github__search`, `jira__search`) and mapping back when calling. Don't key it on `serverInfo.name` — it isn't guaranteed unique; use the host's own configuration id. Also keep each server's list in deterministic order so the combined tool block stays prompt-cache friendly.

### MCP has no sessions any more. How do you build a shopping-cart tool?
Use explicit handles: `create_basket` returns an opaque, high-entropy id (also in `structuredContent`), and every later tool takes `basket_id` as an argument; the server stores state under that key. Check the caller's authorization against the handle on every call, because a handle is a name, not a capability. Put the retention policy in the creation tool's description, and return an `isError` result for an expired handle so the model can create a new basket.

### Gotcha: can `tools/list` return different tools to different clients?
It can vary by the **authorization** presented on the request — for example, only the tools the token's scopes allow. It **MUST NOT** vary per connection or as a side effect of earlier requests ("call `enable_admin` to unlock more tools" is out). That rule follows from statelessness: any server instance must give the same answer to the same request. If you need per-user lists, mark the response `cacheScope: "private"`.

## Glossary
- Tool | 工具 | A server-exposed function, described by a name and JSON Schema, that the model can decide to invoke.
- Model-controlled | 模型控制 | Interaction model in which the LLM, not the user or app, decides when a tool is used.
- Human in the loop | 人在回路（人工监督） | A person who can see and deny tool invocations; the spec says there SHOULD always be one.
- inputSchema / outputSchema | 输入模式 / 输出模式 | JSON Schemas (default 2020-12) describing a tool's arguments and its structured result.
- structuredContent | 结构化内容 | A JSON value in a tool result meant for programs, validated against `outputSchema` when present.
- isError | 工具执行错误标志 | Flag on a `CallToolResult` marking a failure the model can read and use to self-correct.
- Protocol error | 协议错误 | A JSON-RPC error response for an unknown tool, malformed request or server failure.
- ToolAnnotations | 工具注解 | Untrusted behaviour hints such as `readOnlyHint` and `destructiveHint`.
- Resource link | 资源链接 | A `resource_link` content block pointing at a resource URI instead of inlining it.
- State handle | 状态句柄 | An opaque id returned by a tool and passed back on later calls to carry state without sessions.

## Notebook
### 1. A server with one tool per result type
`MCPServer` derives everything from the function: name, docstring → `description`, type hints → `inputSchema`, and (for typed returns) `outputSchema` + `structuredContent`. `title` and `annotations` are decorator arguments. We silence the SDK's server-side logging so the error demos below stay readable.

```python
import base64
import json
import logging
import struct
import zlib

from pydantic import BaseModel, Field

import mcp_types as types
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import Context, Image
from mcp.server.mcpserver.exceptions import ToolError

logging.getLogger("mcp").setLevel(logging.CRITICAL)


def show(model, limit=1500):
    """Print a pydantic protocol object exactly as it goes on the wire (minus serverInfo noise)."""
    data = model.model_dump(by_alias=True, exclude_none=True, mode="json")
    data.get("_meta", {}).pop("io.modelcontextprotocol/serverInfo", None)
    if not data.get("_meta"):
        data.pop("_meta", None)
    print(json.dumps(data, indent=2, ensure_ascii=False)[:limit])


def tiny_png() -> bytes:
    """A valid 1x1 red PNG, built by hand so the notebook needs no image library."""
    chunk = lambda kind, body: (struct.pack(">I", len(body)) + kind + body
                                + struct.pack(">I", zlib.crc32(kind + body) & 0xFFFFFFFF))
    return (b"\x89PNG\r\n\x1a\n" + chunk(b"IHDR", struct.pack(">IIBBBBB", 1, 1, 8, 2, 0, 0, 0))
            + chunk(b"IDAT", zlib.compress(b"\x00\xff\x00\x00")) + chunk(b"IEND", b""))


class Weather(BaseModel):
    temperature: float = Field(description="Temperature in celsius")
    conditions: str
    humidity: float = Field(description="Humidity percentage")


server = MCPServer("travel")


@server.tool()
def greet(name: str) -> str:
    """Say hello. Returns plain text."""
    return f"Hello, {name}!"


@server.tool(title="Weather Data Retriever",
             annotations=types.ToolAnnotations(readOnlyHint=True, openWorldHint=True))
def get_weather_data(location: str) -> Weather:
    """Get current weather data for a location (city name or zip code)."""
    return Weather(temperature=22.5, conditions="Partly cloudy", humidity=65)


@server.tool(annotations=types.ToolAnnotations(readOnlyHint=True))
def render_chart() -> list[types.ContentBlock]:
    """Render the forecast chart as an image meant for the user, plus a caption for the model."""
    return [
        types.ImageContent(type="image", data=base64.b64encode(tiny_png()).decode(), mime_type="image/png",
                           annotations=types.Annotations(audience=["user"], priority=0.9)),
        types.TextContent(type="text", text="Chart rendered: 7-day forecast, mostly sunny."),
    ]


@server.tool()
def find_itinerary(trip: str) -> list[types.ContentBlock]:
    """Return a link to the itinerary file and the packing list inline."""
    return [
        types.ResourceLink(type="resource_link", uri=f"trips://{trip}/itinerary.md", name="itinerary.md",
                           description="Full day-by-day plan", mime_type="text/markdown"),
        types.EmbeddedResource(type="resource", resource=types.TextResourceContents(
            uri=f"trips://{trip}/packing.txt", mime_type="text/plain", text="passport\nadapter\nsunscreen")),
    ]


@server.tool(annotations=types.ToolAnnotations(readOnlyHint=False, destructiveHint=True, idempotentHint=False))
def cancel_booking(booking_id: str) -> str:
    """Cancel a booking. Irreversible."""
    return f"Booking {booking_id} cancelled."


print("tools registered:", [t.name for t in await server.list_tools()])
```

### 2. Discovery: what the model will see
`tools/list` returns the definitions in registration order (deterministic). Look at the generated `inputSchema`, the `outputSchema` derived from the pydantic model, and the annotations. Also note `ttlMs` / `cacheScope` on the result (lesson 3.4).

```python
async with Client(server) as client:
    listing = await client.list_tools()
    print("capabilities.tools:", client.server_capabilities.tools)
    print("order:", [t.name for t in listing.tools], "| ttlMs:", listing.ttl_ms, "| cacheScope:", listing.cache_scope)
    show(next(t for t in listing.tools if t.name == "get_weather_data"), limit=2500)
```

Display-name precedence is `title` → `annotations.title` → `name`. A host would label the buttons like this:

```python
def display_name(tool: types.Tool) -> str:
    return tool.title or (tool.annotations.title if tool.annotations else None) or tool.name


async with Client(server) as client:
    for t in (await client.list_tools()).tools:
        a = t.annotations
        hints = a.model_dump(by_alias=True, exclude_none=True) if a else {}
        print(f"{display_name(t):<24} hints={hints}")
```

### 3. Call every tool and read the content blocks
Plain text, structured content (with its text mirror), an image annotated for the user, a resource link and an embedded resource.

```python
async with Client(server) as client:
    for name, args in [("greet", {"name": "Ada"}), ("get_weather_data", {"location": "Barcelona"}),
                       ("render_chart", {}), ("find_itinerary", {"trip": "bcn-2026"})]:
        result = await client.call_tool(name, args)
        print(f"--- tools/call {name}")
        show(result, limit=900)
```

For `get_weather_data` the SDK filled **both** `structuredContent` (for programs) and a text block with the same JSON (for the model and older clients) — exactly the spec's SHOULD. For `greet`, a `str` return is wrapped as `{"result": ...}` because a function return type always yields an object-shaped schema in this SDK.

### 4. Break it: a server that lies about its output
Clients SHOULD validate `structuredContent` against `outputSchema`. The SDK's client does this inside `call_tool`. Here we hand its validator a forged result that doesn't match the schema, to see what a buggy or malicious server would trigger.

```python
async with Client(server) as client:
    await client.list_tools()  # the client remembers each tool's outputSchema
    forged = types.CallToolResult(content=[types.TextContent(type="text", text="it's warm")],
                                  structured_content={"temperature": "warm", "conditions": "sunny", "humidity": 65})
    try:
        await client.session.validate_tool_result("get_weather_data", forged)
    except RuntimeError as exc:
        print("client rejected the result:\n", str(exc).splitlines()[0])
```

### 5. Two kinds of errors
Four failure modes. Watch which become `isError` results (visible to the model) and how much each message tells the model.

```python
@server.tool()
def book_flight(origin: str, destination: str, date: str) -> str:
    """Book a flight. date must be YYYY-MM-DD and in the future."""
    if not date[:4].isdigit() or date < "2026-07-28":
        raise ToolError(f"Invalid departure date {date!r}: must be YYYY-MM-DD and in the future.")
    return f"Booked {origin}->{destination} on {date}"


@server.tool()
def flaky_api() -> str:
    """Calls an upstream API that crashes."""
    raise ConnectionError("upstream 10.0.0.7:5432 refused connection (password=hunter2)")


async with Client(server) as client:
    cases = [("business error (ToolError)", "book_flight", {"origin": "NYC", "destination": "BCN", "date": "08/08/2025"}),
             ("unexpected exception", "flaky_api", {}),
             ("arguments fail inputSchema", "book_flight", {"origin": "NYC"}),
             ("unknown tool", "teleport", {})]
    for label, name, args in cases:
        r = await client.call_tool(name, args)
        print(f"{label:<28} isError={r.is_error} -> {r.content[0].text.splitlines()[0][:110]}")
```

Note two SDK behaviours. A `ToolError` message reaches the model (actionable), while an unexpected exception becomes a generic "Error executing tool flaky_api" — internal details such as hosts and passwords are **not** leaked, which is what "sanitize tool outputs" asks for. And this SDK reports an unknown tool as `isError` too, whereas the spec lists it as a protocol error.

### 6. Protocol errors on the wire
To see a real JSON-RPC error we go below the SDK: run the server as a stdio subprocess and send a `tools/call` that violates the `CallToolRequest` schema (no `name`).

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "weather_server.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    server = MCPServer("weather")

    @server.tool()
    def get_weather(location: str) -> str:
        """Get current weather information for a location."""
        return f"Current weather in {location}: 22C, partly cloudy"

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))
proc = subprocess.Popen([sys.executable, str(workdir / "weather_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)

    print("<<<", json.dumps(reply), "\n")
```

### 8. Stateful tools with explicit handles
No sessions, so state lives under an opaque handle that the model carries between calls. An unknown handle is an `isError` result that tells the model how to recover.

```python
import uuid

baskets: dict[str, list[str]] = {}
shop = MCPServer("shop")


class BasketRef(BaseModel):
    basket_id: str


@shop.tool()
def create_basket() -> BasketRef:
    """Create an empty basket and return its id. Baskets expire after 24 hours of inactivity."""
    basket_id = f"bsk_{uuid.uuid4().hex[:12]}"
    baskets[basket_id] = []
    return BasketRef(basket_id=basket_id)


@shop.tool()
def add_item(basket_id: str, sku: str) -> list[str]:
    """Add a product to an existing basket; returns the basket contents."""
    if basket_id not in baskets:
        raise ToolError(f"Unknown or expired basket {basket_id!r}. Call create_basket to start a new one.")
    baskets[basket_id].append(sku)
    return baskets[basket_id]


async with Client(shop) as client:
    handle = (await client.call_tool("create_basket", {})).structured_content["basket_id"]
    print("handle:", handle)
    print((await client.call_tool("add_item", {"basket_id": handle, "sku": "TENT-2P"})).structured_content)
    bad = await client.call_tool("add_item", {"basket_id": "bsk_000000000000", "sku": "STOVE"})
    print("isError:", bad.is_error, "->", bad.content[0].text)
```

### 9. Dynamic tools and `notifications/tools/list_changed`
A tool can change the tool set. In 2026-07-28 the client hears about it only if it opened a `subscriptions/listen` stream with `toolsListChanged` (lesson 3.4 goes deep). `MCPServer` does not notify automatically when you call `add_tool`; the tool publishes the event with `ctx.notify_tools_changed()`.

```python
@server.tool()
async def enable_hotels(ctx: Context) -> str:
    """Unlock hotel-booking tools for this deployment."""
    def search_hotels(city: str) -> list[str]:
        """Search hotels in a city."""
        return [f"Hotel Arts {city}", f"Casa {city}"]
    server.add_tool(search_hotels)
    await ctx.notify_tools_changed()
    return "hotel tools enabled"


async with Client(server) as client:
    before = [t.name for t in (await client.list_tools()).tools]
    async with client.listen(tools_list_changed=True) as sub:
        print("listening, honored filter:", sub.honored.model_dump(exclude_none=True, by_alias=True))
        await client.call_tool("enable_hotels", {})
        event = await anext(sub)
        print("event:", event)
        after = [t.name for t in (await client.list_tools()).tools]
    print("new tools:", sorted(set(after) - set(before)))
```

### 10. A host-side approval gate
The protocol leaves UX to the host, but the spec says a human SHOULD be able to deny calls and annotations are untrusted unless the server is. Here is a minimal policy: auto-approve read-only tools **only for trusted servers**, otherwise ask (simulated by a scripted "user").

```python
TRUSTED_SERVERS = {"travel"}


def needs_approval(server_name: str, tool: types.Tool) -> bool:
    hints = tool.annotations or types.ToolAnnotations()
    if server_name not in TRUSTED_SERVERS:
        return True                      # never trust hints from unknown servers
    return not hints.read_only_hint      # trusted + read-only -> no dialog


def scripted_user(tool_name: str, args: dict) -> bool:
    print(f"   [dialog] Allow {tool_name}({args})?", "-> DENY" if tool_name.startswith("cancel") else "-> allow")
    return not tool_name.startswith("cancel")


async def host_call(client, server_name, name, args):
    tool = next(t for t in (await client.list_tools()).tools if t.name == name)
    if needs_approval(server_name, tool) and not scripted_user(name, args):
        return f"{name}: denied by user (the model is told the call was refused)"
    text = (await client.call_tool(name, args)).content[0].text
    return f"{name}: " + " ".join(text.split())[:70]


async with Client(server) as client:
    for server_name, name, args in [("travel", "get_weather_data", {"location": "Rome"}),
                                    ("travel", "cancel_booking", {"booking_id": "B-42"}),
                                    ("random-server", "get_weather_data", {"location": "Rome"})]:
        print(f"{server_name}/{name}")
        print("  ", await host_call(client, server_name, name, args))
```
