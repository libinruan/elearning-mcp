## Summary
Under every SDK, MCP is just three kinds of JSON-RPC 2.0 messages: **requests**, **responses** and **notifications**. The 2026-07-28 revision adds a few rules on top of plain JSON-RPC: ids may never be `null`, every result carries a `resultType`, and every request carries an **envelope** in `params._meta`: protocol version, client capabilities and (optionally) client identity. This lesson covers the message shapes, the `_meta` key-naming rules and reserved keys (including OpenTelemetry trace context), the error-code allocation policy with the three MCP-defined codes `-32020`, `-32021` and `-32022`, how MCP uses JSON Schema, and the `icons` field. In the notebook you build a message validator and then provoke every error code from a real server.

## Lesson
### Three message kinds, one format
The spec says it plainly: *all messages between MCP clients and servers **MUST** follow the JSON-RPC 2.0 specification.* JSON-RPC has three kinds of message, and MCP adds a few rules to each.

| Kind | Shape | Who sends it in 2026-07-28 | Gets a reply? |
| --- | --- | --- | --- |
| **Request** | `jsonrpc`, `id`, `method`, `params?` | the **client** only | yes: exactly one response |
| **Response** | `jsonrpc`, `id`, and either `result` or `error` | the **server** only | no |
| **Notification** | `jsonrpc`, `method`, `params?`, **no `id`** | either side | never: the receiver **MUST NOT** respond |

The direction column is new. Earlier revisions let servers send their own requests (`sampling/createMessage`, `elicitation/create`, `roots/list`, `ping`). In 2026-07-28, **servers MUST NOT initiate JSON-RPC requests and clients do not send responses**. When a server needs something from the client, it returns a special result instead (see `resultType` below).

**Request rules.**
- A request **MUST** include a string or integer `id`.
- *Unlike base JSON-RPC*, the id **MUST NOT** be `null`.
- The id **MUST NOT** match the id of any other request the sender has issued that has not yet received a response. Ids only have to be unique among in-flight requests, which is what lets responses (and cancellations) be matched back to the right request.

```json
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "add", "arguments": {"a": 2, "b": 3},
            "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
                      "io.modelcontextprotocol/clientCapabilities": {}}}}
```

**Notification rules.** A notification **MUST NOT** include an `id`. Leaving out the id is what makes a message a notification. Examples are `notifications/progress`, `notifications/message` and `notifications/cancelled`.

### Responses and `resultType`
A **result response** **MUST** carry the same `id` as its request and a `result` object. New in 2026-07-28, the result **MUST** include a `resultType` string, so a client knows how to parse the rest:

| `resultType` | Meaning |
| --- | --- |
| `"complete"` | The request finished and `result` holds the final content. |
| `"input_required"` | The server needs more input (an elicitation, a sampling call, roots). `result` is an `InputRequiredResult` with `inputRequests`; the client retries the original request with `inputResponses`. This is the **Multi Round-Trip Request** pattern (lesson 5.3). |
| extension-defined | Extensions **MAY** add values, but only ones advertised through capabilities. |

Two rules matter for interoperability. A `resultType` the client does not recognise **MUST** be treated as invalid. A result with **no** `resultType` (from a server on an earlier revision) **MUST** be treated as `"complete"`.

```json
{"jsonrpc": "2.0", "id": 7,
 "result": {"resultType": "complete",
            "content": [{"type": "text", "text": "5"}], "structuredContent": {"result": 5},
            "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "calc", "version": "1.0.0"}}}}
```

An **error response** carries an `error` object with an integer `code`, a `message` (the schema says it **SHOULD** be one concise sentence) and an optional `data` of any type. It **MUST** carry the request's `id`, *except* when the id could not be read because the request was malformed. That is why `JSONRPCErrorResponse.id` is optional in the schema, and why a parse error goes out with `"id": null`.

### Three message patterns
The core protocol composes these messages into three patterns, and every transport carries all three:

1. **Request and response.** The server may send notifications scoped to the request (progress, log messages) before the response.
2. **Multi round-trip requests (MRTR).** The server answers `resultType: "input_required"`, and the client retries with the requested input.
3. **Subscribe and notify.** A `subscriptions/listen` request whose response is a long-lived stream of change notifications. Each notification is tagged with `io.modelcontextprotocol/subscriptionId`.

### The `_meta` envelope: per-request protocol fields
Because 2026-07-28 is stateless (lesson 2.2), there is no `initialize` handshake to remember a version or capabilities. **Every request carries them** in `params._meta`:

| Key | Type | Required | Purpose |
| --- | --- | --- | --- |
| `io.modelcontextprotocol/protocolVersion` | string | **Yes** | Protocol version for this request, e.g. `"2026-07-28"` |
| `io.modelcontextprotocol/clientCapabilities` | `ClientCapabilities` | **Yes** | What the client supports *for this request*; `{}` means no optional capabilities |
| `io.modelcontextprotocol/clientInfo` | `Implementation` | No (**SHOULD** send) | Client name and version |
| `io.modelcontextprotocol/logLevel` | `LoggingLevel` | No | Opt in to log notifications for this request (deprecated feature, lesson 2.4) |

> **Spec rule.** A request missing a required field is malformed. The server **MUST** reject it with `-32602` (Invalid params), and on HTTP the status **MUST** be `400 Bad Request`.

Servers **SHOULD** identify themselves in every result's `_meta` with `io.modelcontextprotocol/serverInfo`. Both `clientInfo` and `serverInfo` are **self-reported and unverified**. They are meant for display, logging and debugging. Implementations **SHOULD NOT** change behaviour based on them and **SHOULD NOT** use them for security decisions.

A server **MUST NOT** rely on a capability the client did not declare in this request. If it needs one (for example, a tool that must elicit a confirmation from a client that declared no `elicitation`), it **MUST** return `-32021` `MissingRequiredClientCapability` with `data.requiredCapabilities` listing what is missing. On HTTP that is also a `400`.

### `_meta` key naming and reserved keys
`_meta` is the one extension point that exists on every request, result and notification, so the spec gives its keys a format. A key is an optional **prefix** plus a **name**:

- **Prefix:** dot-separated labels followed by `/`. Each label starts with a letter and ends with a letter or digit, with letters, digits or hyphens in between. Use **reverse DNS** (`com.example/`, not `example.com/`).
- **Name:** unless empty, it starts and ends with an alphanumeric character and may contain `-`, `_`, `.` and alphanumerics in between.
- **Reserved:** any prefix whose **second label** is `modelcontextprotocol` or `mcp`. So `io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/` and `com.mcp.tools/` are reserved, but `com.example.mcp/` is not (its second label is `example`).

The keys reserved by the spec are: `progressToken`, the four per-request fields above, `io.modelcontextprotocol/subscriptionId` (on notifications from a `subscriptions/listen` stream), and `traceparent`, `tracestate` and `baggage`. Implementations **MUST NOT** make assumptions about values at reserved keys. Official extensions add more keys under `io.modelcontextprotocol/`, and third parties use their own vendor prefix.

**OpenTelemetry trace context.** `traceparent`, `tracestate` and `baggage` are an explicit exception to the prefix rule. They keep their bare W3C names for compatibility with existing tooling and the OpenTelemetry semantic conventions for MCP, and their values **MUST** follow W3C Trace Context and W3C Baggage. Propagating `traceparent` lets one distributed trace run from the host's agent loop through the MCP client and into the server's database call. This is also the recommended replacement for the deprecated protocol-level logging.

```json
"_meta": {"traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01",
          "io.modelcontextprotocol/protocolVersion": "2026-07-28",
          "io.modelcontextprotocol/clientCapabilities": {}}
```

### Error codes and the allocation policy
MCP reuses the standard JSON-RPC codes for general failures:

| Code | Name | Typical MCP cause |
| --- | --- | --- |
| `-32700` | Parse error | The body is not valid JSON |
| `-32600` | Invalid request | Not a valid request object (a batch, a posted response, a bad envelope) |
| `-32601` | Method not found | Unknown method, or one gated behind a capability the server did not advertise (HTTP: `404`) |
| `-32602` | Invalid params | Missing `_meta` fields, unknown tool or prompt, bad cursor, bad log level, resource not found |
| `-32603` | Internal error | Unexpected server condition |

JSON-RPC reserves `-32000` to `-32099` for implementation-defined server errors. In 2026-07-28, MCP **partitions** that range:

| Sub-range | Status | Rule |
| --- | --- | --- |
| `-32000` … `-32019` | legacy / implementation-defined | New codes **MUST NOT** be allocated here, new implementations **SHOULD NOT** use them, and receivers **MUST NOT** assume a meaning (except `-32002`). |
| `-32020` … `-32099` | **reserved for the MCP spec** | Only codes the spec defines may be emitted, and only with their specified meaning. |

The spec defines three codes:

| Code | Name | When | HTTP status |
| --- | --- | --- | --- |
| `-32020` | `HeaderMismatch` | Streamable HTTP headers (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, `Mcp-Param-*`) missing, malformed, or different from the body | `400` |
| `-32021` | `MissingRequiredClientCapability` | The request needs a client capability that was not declared; `data.requiredCapabilities` | `400` |
| `-32022` | `UnsupportedProtocolVersion` | The server does not serve the requested version; `data: {supported: [...], requested}` | `400` |

Codes from earlier revisions stay reserved and **MUST NOT** be emitted. `-32002` (resource not found in 2025-11-25 and earlier) became `-32602`, although clients **SHOULD** still accept `-32002` from old servers. `-32042` (URL elicitation required, 2025-11-25 only) is retired. These three codes were briefly `-32001`/`-32003`/`-32004` in drafts and were renumbered once the policy existed, so you may still see the old numbers in older code. Errors that are **purely local** (an SDK's own request timeout) have no spec code. Surface them so they cannot be mistaken for errors the peer sent. Codes for your own application **SHOULD** sit outside `-32768`…`-32000` entirely.

> **Pitfall.** A tool that fails is usually **not** a JSON-RPC error. Tool execution failures come back as a normal result with `isError: true`, so the model can read the message and retry. JSON-RPC errors are for protocol problems: bad envelope, unknown method, wrong version.

### How MCP uses JSON Schema
Tool `inputSchema`/`outputSchema` and elicitation forms are JSON Schema, with these rules:

- **Default dialect:** a schema with no `$schema` is **JSON Schema 2020-12**. A schema **MAY** declare another dialect (for example draft-07). Implementations **MUST** support 2020-12, **SHOULD** document any others, and **MUST** handle an unsupported dialect gracefully with an error.
- Schemas **MUST** be valid in their declared or default dialect. In 2026-07-28, `inputSchema` and `outputSchema` may use any 2020-12 keyword, and `structuredContent` may be any JSON value.
- **`$ref` resolution:** implementations **MUST NOT** automatically dereference a `$ref` that resolves to a **network URI**. An opt-in fetch mode **MUST** be off by default and **SHOULD** use a host allowlist (at minimum rejecting loopback, link-local and private addresses), timeouts, size limits and logging. A schema that fails because of an unresolved external `$ref` **SHOULD** be rejected, not treated as permissive. Otherwise a tool schema could turn into an SSRF probe.
- **Composition keywords** (`anyOf`, `oneOf`, `allOf`, `if`/`then`/`else`, `$defs`) **SHOULD** be bounded by a maximum depth, a cap on subschemas or a time budget, so that a malicious schema cannot be used to deny service to your validator.

### `icons`
`Implementation` (server or client info), `Tool`, `Prompt` and `Resource` may carry `icons`: an array of `{src, mimeType?, sizes?, theme?}`. `src` is an HTTPS URL or a `data:` URI, `sizes` looks like `["48x48"]` or `["any"]`, and `theme` is `"light"` or `"dark"`. Clients that render icons **MUST** support `image/png` and `image/jpeg` and **SHOULD** support `image/svg+xml` and `image/webp`. Icons are an attack surface, so consumers **MUST**:

- treat icon metadata and icon bytes as untrusted;
- accept only `https:` or `data:` URIs, rejecting `javascript:`, `file:`, `ftp:`, `ws:` and app schemes, as well as redirects to other origins;
- fetch icons without cookies or credentials;
- defend against oversized images and SVGs with embedded script;
- detect the real type from magic bytes, using a strict allowlist.

They should also check that icons come from the server's own origin.

## Key points
- MCP messages are JSON-RPC 2.0: **requests** (with `id`), **responses** (`result` or `error`, same `id`) and **notifications** (no `id`, never answered).
- In 2026-07-28 only **clients send requests**. Servers answer, optionally emit notifications scoped to the request, and ask for input through `resultType: "input_required"`.
- Request ids are strings or integers, **never `null`**, and unique among the sender's in-flight requests.
- Every result carries `resultType` (`"complete"`, `"input_required"` or an advertised extension value). If it is missing, treat it as `"complete"`.
- Every request carries `_meta` with **required** `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`. If they are missing, the answer is `-32602` (HTTP `400`). `clientInfo`/`serverInfo` are unverified.
- `_meta` keys are `prefix/name` in reverse DNS. Prefixes whose **second label** is `modelcontextprotocol` or `mcp` are reserved. `traceparent`/`tracestate`/`baggage` are the un-prefixed OpenTelemetry exception.
- `-32000…-32019` is the legacy implementation-defined range, and `-32020…-32099` belongs to the spec: **-32020 HeaderMismatch, -32021 MissingRequiredClientCapability, -32022 UnsupportedProtocolVersion**.
- Tool failures are `isError: true` results, not JSON-RPC errors. Resource-not-found moved from `-32002` to `-32602`.
- JSON Schema defaults to **2020-12**. Never auto-fetch network `$ref`s, and bound composition keywords. Icons are untrusted input: `https:`/`data:` only, fetched without credentials.

## Pitches
### What does an MCP message look like on the wire?
It's plain JSON-RPC 2.0. The client sends requests with a method, params and a non-null id. The server answers with a result or an error carrying that same id, and either side can send fire-and-forget notifications that have no id. What MCP adds is an envelope: every request carries its protocol version and client capabilities in `params._meta`, and every result carries a `resultType`, so the client knows whether it is final or whether the server needs more input.

### Walk me through MCP's error codes.
The first layer is the standard JSON-RPC codes: parse error, invalid request, method not found, invalid params and internal error. Missing envelope fields or an unknown tool give minus 32602. Then MCP splits the server-error range. Minus 32000 to minus 32019 is legacy, implementation-defined space. Minus 32020 upward is reserved for the spec, which defines header mismatch, missing required client capability and unsupported protocol version. Ordinary tool failures aren't protocol errors at all: they come back as results with `isError` true.

### Why does `_meta` have key-naming rules?
`_meta` is the extension point on every message, so without rules, vendors and the spec would collide. Keys look like a reverse-DNS prefix, a slash and a name. Any prefix whose second label is `modelcontextprotocol` or `mcp` is reserved for the protocol, so I'd put my own data under something like `com.acme/`. The one deliberate exception is OpenTelemetry's `traceparent`, `tracestate` and `baggage`, which keep their W3C names so standard tracing tooling works across the client-server hop.

## Interview
### What changes does MCP make to plain JSON-RPC 2.0?
- Request ids **must not be `null`**, and they must be unique among the sender's in-flight requests.
- Every result must carry **`resultType`**: `"complete"`, `"input_required"` (MRTR) or an extension value. An absent value means `"complete"` for backward compatibility.
- Every request carries a **per-request envelope** in `params._meta` (protocol version and client capabilities, plus client info as a SHOULD) instead of a handshake.
- **Direction is restricted**: servers never initiate requests and clients never send responses.
- **Batching is not used.** A Streamable HTTP POST body must be a single request or notification, and stdio frames one message per line.
- The server-error range has an **allocation policy** with spec-owned codes `-32020…-32099`.

### A request comes in without `io.modelcontextprotocol/clientCapabilities`. What should the server do, and why not just assume `{}`?
It must reject it with `-32602` Invalid params, plus `400 Bad Request` on HTTP. The spec calls a request missing any required field *malformed*. If the server guessed, it would be inferring state the client never stated, which is exactly what statelessness forbids. It would also hide client bugs. A client that genuinely supports nothing optional sends an explicit `{}`. The same logic gives `-32021`: if handling the request needs, say, elicitation and the client did not declare it, the server returns `MissingRequiredClientCapability` with `data.requiredCapabilities` rather than trying anyway.

### When is a failure a JSON-RPC error and when is it `isError: true`?
JSON-RPC errors are for problems the **protocol layer** detects: unparseable JSON, unknown method, malformed params or envelope, unsupported version, header mismatch, missing capability. The model usually cannot fix these, and they go to the client code. **Tool execution errors**, such as an API failure, a validation problem with the arguments' values or "no such customer", come back as a normal `CallToolResult` with `isError: true` and a readable message. The host feeds that to the model so it can self-correct. If you turn those into JSON-RPC errors, the model never sees them.

### You want to attach a tenant id and a trace to every MCP request. How?
Use `_meta`. Trace context goes in the reserved, un-prefixed `traceparent` (and optionally `tracestate`/`baggage`) using W3C formats. The server's OpenTelemetry instrumentation extracts it and parents its span under the client's. The tenant id goes under **my own reverse-DNS prefix**, e.g. `com.acme/tenant`, never under `io.modelcontextprotocol/` or `dev.mcp/`, which are reserved. Two caveats: `_meta` is client-asserted, so a tenant id there is not authorization (that comes from the auth layer); and on HTTP, if a gateway needs to route on a value, the value belongs in a tool parameter mirrored with `x-mcp-header` (lesson 2.3).

### Gotcha: a server returns error code `-32002`. What does it mean?
In 2026-07-28 it means nothing by itself. `-32000…-32019` is the legacy implementation-defined range, and receivers must not assume a meaning, **except** for `-32002`. That code was "resource not found" in 2025-11-25 and earlier, and clients **SHOULD** still accept it from old servers. Modern servers must not emit it: resource-not-found is now `-32602`. So the right reading is "an older server telling me the resource does not exist". Similarly, `-32042` (URL elicitation required) was 2025-11-25-only and is retired.

### Why does the spec forbid auto-dereferencing remote `$ref`s in tool schemas?
Tool schemas come from servers, which may be untrusted. If the client's validator followed `"$ref": "http://169.254.169.254/latest/meta-data"`, a malicious server could make the host fetch internal URLs (SSRF), leak that the schema was loaded, or hang the validator. So network `$ref` resolution is **off by default**. An opt-in mode should allowlist hosts, reject loopback, link-local and private ranges, and apply timeouts and size limits. Unresolvable refs make the schema invalid rather than "accept anything". For the same reason, composition keywords get depth and size budgets.

## Glossary
- JSON-RPC 2.0 | JSON-RPC 2.0 远程过程调用协议 | The lightweight request/response/notification message format all MCP messages use.
- Request | 请求 | A message with a method, params and a non-null string or integer id that expects exactly one response.
- Notification | 通知 | A one-way message without an id; the receiver must not reply.
- `resultType` | 结果类型（`resultType`） | Required field on every result that says how to parse it: `"complete"`, `"input_required"` or an extension value.
- `_meta` | 元数据字段（`_meta`） | The metadata object on requests, results and notifications that carries the per-request envelope, progress tokens, trace context and vendor data.
- Per-request envelope | 逐请求信封 | The required `io.modelcontextprotocol/protocolVersion` and `clientCapabilities` keys (plus optional `clientInfo`) in every request's `_meta`.
- Reserved prefix | 保留前缀 | A `_meta` key prefix whose second label is `modelcontextprotocol` or `mcp`, reserved for the protocol.
- `HeaderMismatch` (-32020) | 请求头不匹配错误 | Error returned when Streamable HTTP headers are missing, malformed or disagree with the request body.
- `MissingRequiredClientCapability` (-32021) | 缺少必需的客户端能力错误 | Error returned when a request needs a client capability the client did not declare.
- `UnsupportedProtocolVersion` (-32022) | 不支持的协议版本错误 | Error listing the server's supported versions when the requested version is not served.

### 1. A message classifier you can trust
Before talking to a server, encode the rules from the lesson as code. `inspect_message` classifies a decoded JSON object and lists every rule it breaks. We will reuse it on the server's real replies.

```python
import json


def show(obj, limit=900):
    text = json.dumps(obj, indent=2, ensure_ascii=False)
    print(text if len(text) <= limit else text[:limit] + "\n  ...")


REQUIRED_ENVELOPE = ("io.modelcontextprotocol/protocolVersion", "io.modelcontextprotocol/clientCapabilities")


def inspect_message(msg: dict) -> tuple[str, list[str]]:
    """Return (kind, problems) for one decoded MCP / JSON-RPC message."""
    problems = []
    if msg.get("jsonrpc") != "2.0":
        problems.append('jsonrpc must be exactly "2.0"')
    has_id = "id" in msg
    if "method" in msg:
        kind = "request" if has_id else "notification"
        if has_id:
            rid = msg["id"]
            if rid is None:
                problems.append("request id MUST NOT be null (MCP rule, stricter than JSON-RPC)")
            elif isinstance(rid, bool) or not isinstance(rid, (str, int)):
                problems.append("request id must be a string or an integer")
            meta = (msg.get("params") or {}).get("_meta") or {}
            missing = [k for k in REQUIRED_ENVELOPE if k not in meta]
            if missing:
                problems.append(f"request envelope is missing {missing} -> server answers -32602")
    elif "result" in msg or "error" in msg:
        kind = "response"
        if "result" in msg and "error" in msg:
            problems.append("a response carries result OR error, never both")
        if "result" in msg:
            if msg.get("id") is None:
                problems.append("a result response must echo the request id")
            if "resultType" not in msg["result"]:
                problems.append("result lacks resultType (a client treats it as 'complete')")
        if "error" in msg and not isinstance(msg["error"].get("code"), int):
            problems.append("error.code must be an integer")
    else:
        kind = "invalid"
        problems.append("neither method nor result/error present")
    return kind, problems


ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {},
            "io.modelcontextprotocol/clientInfo": {"name": "notebook", "version": "0.1"}}

samples = {
    "good request": {"jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {"_meta": ENVELOPE}},
    "null id": {"jsonrpc": "2.0", "id": None, "method": "tools/list", "params": {"_meta": ENVELOPE}},
    "no envelope": {"jsonrpc": "2.0", "id": "a", "method": "tools/list"},
    "notification": {"jsonrpc": "2.0", "method": "notifications/progress",
                     "params": {"progressToken": "t", "progress": 1}},
    "old-style result": {"jsonrpc": "2.0", "id": 1, "result": {"tools": []}},
    "error": {"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "Method not found"}},
}
for label, msg in samples.items():
    kind, problems = inspect_message(msg)
    print(f"{label:<17} -> {kind:<12} {problems or 'OK'}")
```

### 2. `_meta` key rules and the reserved prefixes
Implement the key grammar from the spec: an optional reverse-DNS prefix ending in `/`, then a name. A prefix is **reserved** when its *second* label is `modelcontextprotocol` or `mcp`.

```python
import re

LABEL = r"[A-Za-z](?:[A-Za-z0-9-]*[A-Za-z0-9])?"
NAME = r"(?:[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?)?"
KEY = re.compile(rf"^(?:(?P<prefix>{LABEL}(?:\.{LABEL})*)/)?(?P<name>{NAME})$")
OTEL_KEYS = {"traceparent", "tracestate", "baggage"}


def check_meta_key(key: str) -> str:
    m = KEY.match(key)
    if not m:
        return "INVALID"
    prefix = m.group("prefix")
    if prefix is None:
        return "OpenTelemetry exception (reserved, no prefix)" if key in OTEL_KEYS else "valid, unprefixed"
    labels = prefix.split(".")
    if len(labels) > 1 and labels[1] in ("modelcontextprotocol", "mcp"):
        return "RESERVED for MCP"
    return "valid, vendor prefix"


for key in ["io.modelcontextprotocol/protocolVersion", "dev.mcp/anything", "org.modelcontextprotocol.api/x",
            "com.mcp.tools/y", "com.example.mcp/tenant", "com.acme/tenant", "traceparent", "progressToken",
            "1bad.com/x", "com.acme/-name", "com.acme-/x"]:
    print(f"{key:<42} {check_meta_key(key)}")
```

Notice `com.example.mcp/tenant` is **not** reserved (its second label is `example`), while `com.mcp.tools/y` **is**.

### 3. Where does an error code come from?
Codify the allocation policy so you can read any code at a glance.

```python
MCP_DEFINED = {-32020: "HeaderMismatch", -32021: "MissingRequiredClientCapability",
               -32022: "UnsupportedProtocolVersion"}
JSONRPC_STANDARD = {-32700: "Parse error", -32600: "Invalid request", -32601: "Method not found",
                    -32602: "Invalid params", -32603: "Internal error"}


def explain_code(code: int) -> str:
    if code in JSONRPC_STANDARD:
        return f"JSON-RPC standard: {JSONRPC_STANDARD[code]}"
    if code in MCP_DEFINED:
        return f"MCP spec: {MCP_DEFINED[code]}"
    if -32019 <= code <= -32000:
        extra = " (old 'resource not found' - accept from legacy servers)" if code == -32002 else ""
        return "legacy implementation-defined range: assume nothing" + extra
    if -32099 <= code <= -32020:
        return "reserved for the MCP spec but undefined: a server MUST NOT emit it"
    if -32768 <= code <= -32000:
        return "JSON-RPC reserved range: do not use for app errors"
    return "application-defined (outside the JSON-RPC reserved range)"


for code in [-32700, -32602, -32020, -32021, -32022, -32002, -32001, -32042, -32050, -32500, -1, 4004]:
    print(f"{code:>7}  {explain_code(code)}")
```

### 4. Provoke every error from a real server over stdio
Now a real SDK server runs as a subprocess and we talk to it with raw JSON lines. One tool, `delete`, needs the user's confirmation. It declares that through a resolver that elicits, so the server needs the client's `elicitation` capability.

```python
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "lab_server.py").write_text(textwrap.dedent('''
    from typing import Annotated
    from pydantic import BaseModel
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Elicit, Resolve

    mcp = MCPServer("error-lab", version="1.0.0")

    @mcp.tool()
    def add(a: int, b: int) -> int:
        """Add two integers."""
        return a + b

    @mcp.tool()
    def divide(a: float, b: float) -> float:
        """Divide a by b."""
        if b == 0:
            raise ValueError("division by zero")
        return a / b

    class Confirm(BaseModel):
        ok: bool

    def ask(target: str):
        return Elicit(f"Really delete {target}?", Confirm)

    @mcp.tool()
    def delete(target: str, confirm: Annotated[Confirm, Resolve(ask)]) -> str:
        """Delete something after the user confirms."""
        return f"deleted {target}" if confirm.ok else "kept"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

proc = subprocess.Popen([sys.executable, str(workdir / "lab_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
inbox = queue.Queue()
threading.Thread(target=lambda: [inbox.put(line) for line in proc.stdout], daemon=True).start()


def send_raw(text: str, wait: float = 5.0):
    """Write one line to the server's stdin and return the next line it writes (or None)."""
    proc.stdin.write(text + "\n")
    proc.stdin.flush()
    try:
        return json.loads(inbox.get(timeout=wait))
    except queue.Empty:
        return None


def rpc(id_, method, params=None, *, meta=ENVELOPE):
    params = dict(params or {})
    if meta is not None:
        params["_meta"] = meta
    return send_raw(json.dumps({"jsonrpc": "2.0", "id": id_, "method": method, "params": params}))


reply = rpc(1, "server/discover")
show(reply)
print("classifier:", inspect_message(reply))
```

Now break things one at a time and run each reply through both helpers:

```python
def report(label, reply):
    if reply is None:
        print(f"{label:<34} -> (no reply)")
    elif "error" in reply:
        err = reply["error"]
        print(f"{label:<34} -> {err['code']} {explain_code(err['code'])}\n{'':<38}message: {err['message'][:90]}")
        if "data" in err:
            print(f"{'':<38}data: {json.dumps(err['data'])}")
    else:
        r = reply["result"]
        print(f"{label:<34} -> result resultType={r.get('resultType')!r} isError={r.get('isError')}")


report("unknown method", rpc(2, "tasks/list"))
report("missing _meta envelope", rpc(3, "tools/list", meta=None))
report("unsupported protocol version", rpc(4, "tools/list",
       meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": "1900-01-01"}))
report("needs undeclared elicitation", rpc(5, "tools/call", {"name": "delete", "arguments": {"target": "prod"}}))
report("tool raises (NOT a protocol error)", rpc(6, "tools/call", {"name": "divide", "arguments": {"a": 1, "b": 0}}))
```

Read the last two carefully. Calling `delete` without declaring `elicitation` gives **-32021**, and `data.requiredCapabilities` tells the client exactly what to add. A tool that raises is **not** a JSON-RPC error: it is a `complete` result with `isError: true`, which the host shows to the model.

What happens if the client *does* declare elicitation? The server can no longer send its own `elicitation/create` request (servers never initiate requests in 2026-07-28), so it answers with `resultType: "input_required"`:

```python
reply = rpc(7, "tools/call", {"name": "delete", "arguments": {"target": "prod"}},
            meta={**ENVELOPE, "io.modelcontextprotocol/clientCapabilities": {"elicitation": {}}})
result = reply["result"]
print("resultType:", result["resultType"])
show(result["inputRequests"])
print("requestState (opaque, echoed back on retry):", result["requestState"][:40], "...")
```

Lesson 5.3 finishes this round trip. For now the point is that `resultType` tells the client how to parse `result`.

Finally, malformed JSON-RPC. The spec says a parse error is answered with `id: null`, but this SDK's stdio server simply drops lines it cannot parse or that break the JSON-RPC shape. **Never rely on getting an answer to garbage.** Always use client-side timeouts.

```python
for label, line in [("not JSON at all", '{"jsonrpc": "2.0", "id": 8, "method": "tools/l'),
                    ("null id", json.dumps({"jsonrpc": "2.0", "id": None, "method": "tools/list",
                                            "params": {"_meta": ENVELOPE}})),
                    ("jsonrpc 1.0", json.dumps({"jsonrpc": "1.0", "id": 9, "method": "tools/list",
                                                "params": {"_meta": ENVELOPE}}))]:
    report(label, send_raw(line, wait=1.5))

report("server still healthy?", rpc(10, "tools/call", {"name": "add", "arguments": {"a": 2, "b": 40}}))
proc.stdin.close()
exit_code = proc.wait(timeout=10)   # closing stdin is the graceful shutdown signal
```

### 5. The same errors over Streamable HTTP, with status codes
On HTTP each error also gets an HTTP status: `400` for envelope, header and version problems and `404` for an unknown method. Here the server runs in a background thread on `127.0.0.1`.

### 6. `_meta` passthrough: trace context and vendor keys
`Client.call_tool(..., meta=...)` merges your keys into the envelope the SDK builds. This tool echoes what arrived so you can see a W3C `traceparent` and a vendor-prefixed tenant key travelling next to the protocol fields.

```python
from mcp import Client
from mcp.server.mcpserver import Context

echo = MCPServer("meta-echo")


@echo.tool()
def show_meta(ctx: Context) -> str:
    """Return the request's _meta exactly as the server received it."""
    return json.dumps(dict(ctx.request_context.meta or {}), indent=2, default=str)


async with Client(echo) as client:
    result = await client.call_tool("show_meta", {}, meta={
        "traceparent": "00-0af7651916cd43dd8448eb211c80319c-00f067aa0ba902b7-01",
        "com.acme/tenant": "tenant-42",
    })
    print(result.content[0].text)
    print("\nserverInfo in the result's _meta:", result.meta["io.modelcontextprotocol/serverInfo"])
```

The SDK filled in `protocolVersion`, `clientCapabilities` and `clientInfo` for you. Server-side, the SDK's OpenTelemetry middleware reads `traceparent` from this same `_meta` to parent its span.

    return "ok: fetch without credentials, then verify magic bytes"

            print(f"tool {tool.name}: {icon.src[:40]:<40} -> {icon_verdict(icon)}")
