## Summary
A **transport** is a binding. It decides how MCP messages are framed and delivered, how request metadata is carried, and how cancellation and termination are signalled. It never changes what the messages mean. This lesson covers the two standard bindings in 2026-07-28. **stdio** is newline-delimited JSON-RPC over a subprocess's stdin/stdout, with logging on stderr and shutdown by closing stdin. **Streamable HTTP** is one POST per message to a single endpoint, answered with JSON or a request-scoped SSE stream, with the method, name and selected tool parameters mirrored into validated headers. You will also learn the security rules (Origin validation, localhost binding), cancellation by closing the stream, what was removed (sessions, GET streams, resumability), backward compatibility, and custom transports.

## Lesson
### What a transport is, and isn't
The transports overview is precise: *protocol semantics are identical on every transport.* A binding defines four things:

1. **Framing and delivery.** How one JSON-RPC message is delimited and sent. Messages **MUST** be UTF-8.
2. **Request metadata.** Everything lives in the body's `_meta`. A binding **MAY** also mirror fields into envelope metadata such as HTTP headers. *The body remains the source of truth*, and a binding that mirrors defines how mismatches are rejected.
3. **Cancellation.** On stdio the client sends `notifications/cancelled`. On Streamable HTTP it closes the request's response stream.
4. **Termination.** How the connection or process ends.

Every binding **MUST** deliver client requests and notifications to the server, and server responses and notifications to the client. *No other message direction exists*: servers never send requests and clients never send responses.

### stdio: the local subprocess transport
The client launches the server as a subprocess and they talk over its standard streams:

- The server reads JSON-RPC from **stdin** and writes JSON-RPC to **stdout**.
- Each message is one JSON-RPC request, notification or response, **delimited by newlines**, and **MUST NOT contain embedded newlines**. Serialize compactly. A pretty-printed message breaks the framing.
- The server **MUST NOT** write anything to stdout that is not a valid MCP message. The client **MUST NOT** write anything else to stdin.
- The server **MAY** write UTF-8 to **stderr** for any logging. The client may capture, forward or ignore it, and **SHOULD NOT** assume stderr output means an error.

> **Pitfall.** A stray `print("debug")` in a stdio server goes to stdout and corrupts the stream. Log with `print(..., file=sys.stderr)` or a logger configured for stderr. This is the #1 bug in hand-written stdio servers.

All server messages share the single stdout channel. There are no per-request streams. The server writes responses (correlated by `id`), notifications for in-flight requests (`notifications/progress`, `notifications/message`), and notifications for an active `subscriptions/listen` request, which the client correlates through `io.modelcontextprotocol/subscriptionId` in `_meta`. The server **MUST NOT** write requests to stdout. Server-to-client needs travel inside `InputRequiredResult` replies (MRTR). Because responses carry ids, a client can **pipeline** several requests and match the answers as they arrive, in any order.

**Request metadata on stdio** is purely inline (`_meta` in the body). There is no header layer.

**Cancellation:** the client **MUST** send `notifications/cancelled` with the request's id. The server **SHOULD** stop work as soon as practical and **MUST NOT** send further messages for that request.

**Shutdown.** The client **SHOULD**:

1. close the server's stdin;
2. wait for the process to exit;
3. if it does not exit in reasonable time, force-terminate it (POSIX: `SIGTERM`, then `SIGKILL`; Windows: `TerminateProcess` or Job Objects).

Servers **SHOULD** exit promptly on EOF. *It is the primary graceful-shutdown signal and the only portable one.* A server **MAY** shut down by closing stdout and exiting. If the server dies unexpectedly, the client **SHOULD** restart it. In-flight requests are lost and can be retried (statelessness), and `subscriptions/listen` streams must be re-established.

**Lifetime:** clients **SHOULD NOT** tie the stdio process lifetime to a single task, thread or conversation (lesson 2.2). One process can serve interleaved, unrelated work.

### Streamable HTTP: one POST per message
For remote (and many local) servers, the server is an independent process that handles many clients. It exposes a **single MCP endpoint** path (for example `https://example.com/mcp`) that accepts **POST**.

**Sending.** Every client message is a **new HTTP POST** to the endpoint:

- The `Accept` header **MUST** list both `application/json` and `text/event-stream`.
- The body is **a single** JSON-RPC request or notification. Clients **MUST NOT** POST responses.
- The request metadata headers (below) are required on every POST.
- A **notification** that the server accepts gets `202 Accepted` with no body. If it cannot be accepted, the server returns an error status. (This revision defines no client-to-server notifications over HTTP. `notifications/cancelled` is stdio-only.)
- A **request** gets either `Content-Type: application/json` (one JSON object) or `Content-Type: text/event-stream` (an SSE stream). The server chooses per request, and **the client MUST support both**.

**Receiving an SSE response.** Before the final response, the server **MAY** send notifications, which **MUST** relate to the originating request: progress, log messages. It **MUST NOT** send independent requests on the stream. That was allowed in 2025-03-26 through 2025-11-25, and MRTR replaces it now. The final response **SHOULD** end the stream. When opening SSE, servers **SHOULD** send `X-Accel-Buffering: no`, so that proxies like nginx do not buffer events. Long-lived streams should get periodic SSE comment lines (`:`) as keep-alives, which clients must ignore.

```text
POST /mcp  tools/call (progressToken=7)          200 OK  Content-Type: text/event-stream
                                                  event: message
                                                  data: {"method":"notifications/progress",...}
                                                  event: message
                                                  data: {"jsonrpc":"2.0","id":1,"result":{...}}
                                                  (stream closes)
```

**Change notifications** (list changes, resource updates) do **not** ride on these per-request streams. The client opens a long-lived `subscriptions/listen` POST whose response stream carries only the types it opted into (lesson 3.4). Request-scoped `notifications/progress` and `notifications/message` never go on the listen stream.

### Request metadata headers
Streamable HTTP **mirrors body fields into headers** so that load balancers, gateways, WAFs and observability tools can route and inspect traffic without parsing JSON:

| Header | Source | Required for |
| --- | --- | --- |
| `MCP-Protocol-Version` | `_meta["io.modelcontextprotocol/protocolVersion"]` | every POST |
| `Mcp-Method` | `method` | all requests |
| `Mcp-Name` | `params.name` or `params.uri` | `tools/call`, `prompts/get`, `resources/read` |
| `Mcp-Param-{Name}` | a tool argument annotated with `x-mcp-header` | `tools/call`, when the value is present |

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: execute_sql
Mcp-Param-Region: us-west1
```

**Status codes tied to versions and methods.** An unsupported version gets `400` with `UnsupportedProtocolVersionError` (`-32022`). An unknown method gets `404` with `-32601`. The JSON-RPC body tells it apart from a legacy server's plain 404. A request with **no** `MCP-Protocol-Version` header **MAY** be treated as `2025-03-26` by a server that supports pre-2025-06-18 clients. Otherwise it is rejected per server validation.

**`x-mcp-header`.** A server **MAY** annotate a tool parameter in `inputSchema` with `"x-mcp-header": "Region"`. Clients **MUST** support this: they mirror the argument into `Mcp-Param-Region`. The constraints are: a non-empty, case-insensitively unique RFC 9110 token; only on `integer`, `string` or `boolean` properties (never `number`; integers within the JavaScript safe range); and only on properties *statically reachable* through a chain of `properties` keys (not through `items`, `anyOf`/`oneOf`/`allOf`/`not`, `if`/`then`/`else` or `$ref`). HTTP clients **MUST** drop a tool whose annotation breaks these rules from `tools/list`, and **SHOULD** log a warning.

**Value encoding.** Strings are sent as-is, integers in decimal, and booleans as `true`/`false`. A value that is not safe plain ASCII (non-ASCII, control characters, leading or trailing whitespace) or that already looks like the sentinel is sent as `=?base64?{base64 of UTF-8}?=`. The same applies to `Mcp-Name`. So `"Hello, 世界"` becomes `=?base64?SGVsbG8sIOS4lueVjA==?=`. Header *names* compare case-insensitively, while *values* such as method names are case-sensitive.

**Server validation.** A server that processes the body **MUST** reject the request with **`400 Bad Request` and `-32020` HeaderMismatch** when:

- a required standard header is missing;
- a header value differs from the body (after base64 decoding; integers **SHOULD** compare numerically, so `42.0` equals `42`);
- a value contains invalid characters;
- a body value for an annotated parameter has no matching `Mcp-Param-*` header.

The reason is security: if a load balancer routes on the header while the server executes the body, the two must never disagree. When a client gets `-32020` over `Mcp-Param-*`, it **SHOULD** re-fetch `tools/list` (the schema may have changed) and retry. Intermediaries just return an HTTP error. Intermediaries that enforce policy on mirrored headers **SHOULD** reject older or absent versions, which lack header-body validation, rather than trust them.

### Security for HTTP servers
The spec lists three requirements:

1. Servers **MUST validate the `Origin` header** on all incoming connections, to prevent **DNS rebinding**. If it is present and invalid, the server **MUST** answer `403 Forbidden`, optionally with an id-less JSON-RPC error body.
2. When running locally, servers **SHOULD bind only to `127.0.0.1`**, not `0.0.0.0`.
3. Servers **SHOULD** authenticate all connections (OAuth, module 6).

How DNS rebinding works: a page on `evil.example` makes its own hostname resolve to `127.0.0.1`. The browser now believes it is same-origin, so the page's JavaScript can POST to your local MCP server and call its tools. Checking `Origin` (and, as the Python SDK also does, `Host`) against an allowlist defeats this. The rebinding page's Origin and Host are still `evil.example`.

### Cancellation and the end of resumability
On Streamable HTTP, **closing the SSE response stream is the cancellation**. The server **MUST** treat a client disconnect as cancellation of that request, **SHOULD** stop work as soon as practical, and **MUST NOT** send further messages for it. Since every request has its own stream, the signal is unambiguous, so no `notifications/cancelled` is needed or expected.

The flip side: **resumable SSE via `Last-Event-ID` is not supported** in 2026-07-28. A broken response stream loses the in-flight request, and the client **MUST** re-issue it as a new request with a **new id**. If the work is long enough that this hurts, use the Tasks extension (lesson 7.1), not transport tricks.

### Backward compatibility
2026-07-28 changed Streamable HTTP: **no GET stream endpoint, no protocol-level sessions, no server-sent requests on SSE, no resumability**. Revisions 2025-03-26 through 2025-11-25 had `Mcp-Session-Id` (ended with `DELETE`), a standalone GET SSE stream, and `Last-Event-ID`. A server that supports only this revision **SHOULD**:

- answer **GET or DELETE** with `405 Method Not Allowed`;
- **ignore** `Mcp-Session-Id`, and neither mint nor echo session ids;
- **ignore** `Last-Event-ID`.

**Era detection over HTTP.** A dual-era client sends a modern request first. On `400` it inspects the body. A recognised modern JSON-RPC error (`-32022`, `-32021`, `-32020`) means the server is modern, so the client fixes the request. An empty or unrecognised body means legacy, so it falls back to `initialize`.

**The old HTTP+SSE transport (2024-11-05)** is **Deprecated** under the feature-lifecycle policy (deprecated since 2025-03-26). New implementations **SHOULD NOT** adopt it. A client that still supports it POSTs first. On `400`, `404` or `405` *without* a recognised modern error body, it issues a GET expecting an SSE stream whose first event is `endpoint`, and uses the old transport if that arrives. Servers can keep hosting the old SSE and POST endpoints next to the new MCP endpoint.

### Custom transports
Implementations **MAY** add transports over any bidirectional channel. They **MUST** preserve the JSON-RPC format, the message patterns and the per-request metadata model, and **SHOULD** document connection setup, framing and cancellation. Over a reliable byte stream (a Unix socket, TCP), they **SHOULD reuse stdio framing**, newline-delimited JSON-RPC. Only the process-lifecycle parts (launch, stderr, EOF shutdown, restart) need channel-specific equivalents.

## Key points
- A transport defines **framing, metadata carriage, cancellation and termination**, never semantics. Messages are UTF-8 JSON-RPC, and the body's `_meta` is the source of truth.
- **stdio:** one compact JSON message per line on stdin/stdout, with no embedded newlines and nothing else on stdout. **Logs go to stderr**, which is not an error signal.
- stdio shutdown: **close stdin → wait → SIGTERM/SIGKILL**. Servers exit on EOF. Cancellation is `notifications/cancelled`.
- **Streamable HTTP:** a single endpoint, **one POST per message**, `Accept: application/json, text/event-stream`. Notifications get `202`. Requests get JSON **or** a request-scoped SSE stream, and clients must handle both.
- Required headers: **`MCP-Protocol-Version`** on every POST, **`Mcp-Method`** on every request, and **`Mcp-Name`** for `tools/call`/`prompts/get`/`resources/read`. `x-mcp-header` parameters become **`Mcp-Param-{Name}`**, with `=?base64?…?=` for unsafe values.
- Header and body disagree, or a required header is missing → **`400` + `-32020` HeaderMismatch**. Unsupported version → `400` + `-32022`. Unknown method → `404` + `-32601`.
- Security: **validate `Origin`** (invalid → `403`) against DNS rebinding, **bind to 127.0.0.1** locally, and authenticate.
- HTTP cancellation = **closing the response stream**. **No resumability**: re-issue a broken request with a new id.
- 2026-07-28 removed **sessions, the GET stream and server-sent requests**. GET/DELETE get `405`, and `Mcp-Session-Id`/`Last-Event-ID` are ignored. The 2024-11-05 **HTTP+SSE transport is Deprecated**.

## Pitches
### stdio or Streamable HTTP, which would you choose?
It depends on where the server runs and who uses it. For a local tool that one user's host launches, like a filesystem or git server, I'd use stdio: the host spawns it as a subprocess, there's no network surface, credentials come from the environment, and shutdown is just closing stdin. For a shared or remote service I'd use Streamable HTTP: one endpoint, one POST per message, and responses as JSON or a request-scoped SSE stream. It's stateless, so it scales behind a normal load balancer with OAuth in front.

### Why does Streamable HTTP mirror the body into headers?
So infrastructure can make decisions without parsing JSON-RPC. A gateway can route on `Mcp-Method`, rate-limit on `Mcp-Name`, or pin a tenant's region with an `Mcp-Param-Region` header that the tool schema declares through `x-mcp-header`. Because the body stays the source of truth, the server must check that headers and body agree, and reject a mismatch with 400 and error minus 32020. Otherwise an attacker could get the gateway to route on one value while the server executes another.

### How do you secure a local HTTP MCP server?
Bind it to 127.0.0.1, never 0.0.0.0, so nothing on the network can reach it. Then validate the Origin header on every request and return 403 for unknown origins. That stops DNS rebinding, where a malicious web page points its own hostname at localhost and gets the browser to call my tools. Checking the Host header helps too. And I'd still put authentication in front, because other local processes and other users on the machine can reach localhost.

## Interview
### Your stdio server works in the Inspector but hangs or crashes in the host. What do you check first?
Check **stdout hygiene**. Anything other than newline-delimited JSON-RPC on stdout, such as a `print()`, a library banner or a progress bar, corrupts the stream, and the client either fails to parse it or waits forever for a response it can't frame. Move all logging to **stderr**. Next, check that messages are compact (no embedded newlines) and UTF-8. Then check lifecycle: does the server exit when stdin closes? If not, the host has to SIGTERM or SIGKILL it. Finally, remember that the client may treat stderr as informational only, so a server that "reports" errors only on stderr looks healthy from the protocol's point of view.

### Explain when a Streamable HTTP server answers with JSON and when with SSE.
The server chooses per request, and the client must accept both. A plain request with nothing to stream gets `application/json`. If the server wants to send notifications related to the request before the result, such as progress (only when the client sent a `progressToken`) or log messages (only when the client set a `logLevel`), it opens `text/event-stream`, sends those as SSE events, and ends with the response. It must not send independent requests on the stream. Server-to-client needs go in an `InputRequiredResult`. Long-lived change notifications use a separate `subscriptions/listen` POST. The Python SDK, for example, delays committing to SSE until the handler actually emits a notification, so quick calls get JSON.

### A request arrives with `Mcp-Name: get_weather` but the body calls `delete_repo`. What must the server do, and why does it matter?
Reject it with **HTTP 400 and JSON-RPC `-32020` HeaderMismatch**, without executing anything. Mirrored headers exist so that intermediaries can act on them: a WAF might allow `get_weather` and block `delete_repo`, or a router might send it to a read-only pool. If the server executed the body regardless, an attacker could smuggle a forbidden call past every header-based control. The same applies to `MCP-Protocol-Version`, `Mcp-Method`, and every `Mcp-Param-*` derived from `x-mcp-header`, compared after base64 decoding, with integers compared numerically.

### How is cancellation different on stdio and Streamable HTTP?
On **stdio** there is one shared channel and no per-request stream, so the client **must** send `notifications/cancelled` with the `requestId` (and optionally a `reason`). On **Streamable HTTP** each request has its own response stream, so **closing it is the cancellation**. The server must treat the disconnect as cancel, and no notification is expected. In both cases the server should stop work and free resources, must not send anything further for that request, and both sides must tolerate the race where the result was already on its way.

### What happens to an in-flight request if the SSE connection drops in 2026-07-28?
It is lost. Revision 2026-07-28 **removed SSE resumability** (`Last-Event-ID` and SSE event ids), and the server treats the disconnect as cancellation. The client **must re-issue** the request as a **new request with a new id**. That is safe to design for because the protocol is stateless, but it means non-idempotent tools need their own protection, such as idempotency keys in arguments or server-minted handles. Truly long-running work belongs in the Tasks extension, where the client polls a task handle instead of holding a stream open.

### Gotcha: an old client sends `GET /mcp` with an `Mcp-Session-Id`. How should a 2026-07-28-only server respond?
`GET` (and `DELETE`) to the MCP endpoint get **`405 Method Not Allowed`**. There is no standalone SSE stream any more. On a POST, `Mcp-Session-Id` is **ignored**: the server neither mints nor echoes session ids. `Last-Event-ID` is ignored too, since streams aren't resumable. If the old client also sends `initialize`, a modern-only server should reject it with an error that names its supported versions, because legacy clients cannot fall forward and that message may be all the user sees. A dual-era server could instead serve it with legacy semantics.

## Glossary
- Transport binding | 传输绑定 | The definition of how MCP messages are framed, delivered, cancelled and terminated over a channel, without changing their meaning.
- stdio transport | 标准输入输出传输 | The binding where a client launches the server as a subprocess and exchanges newline-delimited JSON-RPC over stdin/stdout.
- Streamable HTTP | 可流式 HTTP 传输 | The binding where each client message is an HTTP POST to one MCP endpoint, answered with JSON or a request-scoped SSE stream.
- Server-Sent Events (SSE) | 服务器发送事件 | A `text/event-stream` HTTP response format used to deliver request-related notifications followed by the final response.
- MCP endpoint | MCP 端点 | The single HTTP path (e.g. `/mcp`) that accepts POSTs for a Streamable HTTP server.
- `Mcp-Method` / `Mcp-Name` | `Mcp-Method`／`Mcp-Name` 请求头 | Required headers mirroring the JSON-RPC method and the tool/prompt name or resource URI.
- `x-mcp-header` | `x-mcp-header` 参数头注解 | A JSON Schema annotation that makes the client mirror a primitive tool argument into an `Mcp-Param-{Name}` header.
- DNS rebinding | DNS 重绑定攻击 | An attack where a web page makes its hostname resolve to localhost so the browser can call a local server; stopped by Origin/Host validation.
- Resumability (removed) | 可恢复性（已移除） | The 2025-era ability to resume an SSE stream with `Last-Event-ID`; in 2026-07-28 a broken stream means re-issuing the request.
- HTTP+SSE transport (deprecated) | HTTP+SSE 传输（已弃用） | The 2024-11-05 two-endpoint transport (GET SSE stream plus POST endpoint), deprecated in favour of Streamable HTTP.

### 1. stdio framing by hand: pipelining, stderr and a broken frame
A server that logs to **stderr** while it works. We pipeline two requests in a single write and watch the replies arrive **by id, out of order**, with stdout and stderr read separately.

```python
import json
import queue
import subprocess
import sys
import tempfile
import textwrap
import threading
import time
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "stdio_server.py").write_text(textwrap.dedent('''
    import sys
    import anyio
    from mcp.server import MCPServer
    from mcp.server.mcpserver import Context

    mcp = MCPServer("stdio-lab", log_level="ERROR")

    @mcp.tool()
    def add(a: int, b: int) -> int:
        """Add two integers."""
        return a + b

    @mcp.tool()
    async def slow(steps: int, ctx: Context) -> str:
        """Work for a while, reporting progress."""
        for i in range(steps):
            print(f"[server log] slow step {i + 1}/{steps}", file=sys.stderr, flush=True)   # stderr: fine
            await ctx.report_progress(i + 1, steps)
            await anyio.sleep(0.3)
        return "done"

    if __name__ == "__main__":
        mcp.run(transport="stdio")
'''))

ENVELOPE = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
            "io.modelcontextprotocol/clientCapabilities": {}}
proc = subprocess.Popen([sys.executable, str(workdir / "stdio_server.py")], stdin=subprocess.PIPE,
                        stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True)
stdout_q, stderr_q = queue.Queue(), queue.Queue()
threading.Thread(target=lambda: [stdout_q.put(l) for l in proc.stdout], daemon=True).start()
threading.Thread(target=lambda: [stderr_q.put(l) for l in proc.stderr], daemon=True).start()


def write_lines(*messages):
    data = "".join(json.dumps(m) + "\n" for m in messages)     # compact JSON, one per line
    proc.stdin.write(data)
    proc.stdin.flush()


def read_stdout(timeout=3.0):
    try:
        return json.loads(stdout_q.get(timeout=timeout))
    except queue.Empty:
        return None


write_lines(
    {"jsonrpc": "2.0", "id": "slow-1", "method": "tools/call",
     "params": {"name": "slow", "arguments": {"steps": 3}, "_meta": {**ENVELOPE, "progressToken": "p"}}},
    {"jsonrpc": "2.0", "id": "fast-2", "method": "tools/call",
     "params": {"name": "add", "arguments": {"a": 2, "b": 40}, "_meta": ENVELOPE}},
)
start = time.time()
for _ in range(5):
    msg = read_stdout(timeout=10)
    label = f"response id={msg['id']}" if "id" in msg else f"{msg['method']} {msg['params'].get('progress')}"
    print(f"stdout +{time.time() - start:.2f}s  {label}")
time.sleep(0.1)
while not stderr_q.empty():
    print("stderr          ", stderr_q.get().rstrip())
```

`fast-2` was written second but answered first. The client matches answers by `id`, not by order. Now break the framing: send the same request **pretty-printed** (embedded newlines).

```python
pretty = json.dumps({"jsonrpc": "2.0", "id": 3, "method": "tools/list", "params": {"_meta": ENVELOPE}}, indent=2)
print(f"pretty-printed message spans {pretty.count(chr(10)) + 1} lines")
proc.stdin.write(pretty + "\n")
proc.stdin.flush()
print("reply:", read_stdout(timeout=2))

write_lines({"jsonrpc": "2.0", "id": 4, "method": "tools/list", "params": {"_meta": ENVELOPE}})
print("compact reply has", len(read_stdout()["result"]["tools"]), "tools - the server survived, but request 3 was lost")
```

`json.dumps` without `indent` never emits a raw newline: newlines *inside* strings are escaped as `\n`, so arbitrary text is safe in one frame.

### 2. stdio cancellation and shutdown
Cancel a running request with `notifications/cancelled`, then shut down gracefully by closing stdin.

```python
write_lines({"jsonrpc": "2.0", "id": "long-5", "method": "tools/call",
             "params": {"name": "slow", "arguments": {"steps": 20}, "_meta": {**ENVELOPE, "progressToken": "q"}}})
print("first message:", read_stdout(timeout=10)["params"])
write_lines({"jsonrpc": "2.0", "method": "notifications/cancelled",
             "params": {"requestId": "long-5", "reason": "user pressed stop"}})
print("after cancel :", read_stdout(timeout=2), "<- no response is sent for a cancelled request")

t = time.time()
proc.stdin.close()                                   # step 1: close the input stream
code = proc.wait(timeout=5)                          # step 2: wait (step 3 would be terminate/kill)
print(f"server exited with code {code} {time.time() - t:.2f}s after EOF")
time.sleep(0.1)
log_lines = []
while not stderr_q.empty():
    log_lines.append(stderr_q.get().strip())
print("stderr shows the cancelled work stopped early:", [l for l in log_lines if "/20" in l])
```

### 3. Streamable HTTP: one endpoint, raw POSTs
Run an HTTP server on `127.0.0.1` in a thread. A small ASGI wrapper **records every request's headers** so we can see exactly what clients send. One tool declares an `x-mcp-header` parameter.

```python
import logging
import socket
from typing import Annotated

import anyio
import httpx
import uvicorn
from pydantic import Field
from mcp.server import MCPServer
from mcp.server.mcpserver import Context

web_server = MCPServer("http-lab")


@web_server.tool()
def run_sql(region: Annotated[str, Field(description="Region to run in", json_schema_extra={"x-mcp-header": "Region"})],
            query: str) -> str:
    """Run a (pretend) SQL query in a region."""
    return f"[{region}] {query} -> 42 rows"


@web_server.tool()
async def slow(steps: int, ctx: Context) -> str:
    """Work for a while, reporting progress."""
    try:
        for i in range(steps):
            await ctx.report_progress(i + 1, steps, f"step {i + 1}")
            await anyio.sleep(0.2)
    except BaseException as exc:            # cancellation arrives as an exception in the handler
        server_events.append(f"slow() interrupted by {type(exc).__name__}")
        raise
    return "done"


for noisy in ("httpx", "httpx2", "mcp", "uvicorn"):
    logging.getLogger(noisy).setLevel(logging.ERROR)

server_events, seen_headers = [], []
mcp_app = web_server.streamable_http_app()          # binds DNS-rebinding protection for 127.0.0.1


async def recorder(scope, receive, send):
    if scope["type"] == "http":
        seen_headers.append({"method": scope["method"],
                             **{k.decode(): v.decode() for k, v in scope["headers"] if k.startswith(b"mcp")}})
    await mcp_app(scope, receive, send)


sock = socket.socket()
sock.bind(("127.0.0.1", 0))
port = sock.getsockname()[1]
sock.close()
uv = uvicorn.Server(uvicorn.Config(recorder, host="127.0.0.1", port=port, log_level="warning", lifespan="on"))
threading.Thread(target=uv.run, daemon=True).start()
while not uv.started:
    time.sleep(0.05)
URL = f"http://127.0.0.1:{port}/mcp"
web = httpx.Client(trust_env=False, timeout=10)
HEADERS = {"Accept": "application/json, text/event-stream", "Content-Type": "application/json",
           "MCP-Protocol-Version": "2026-07-28"}


def tools_call(name, arguments, id_=1, meta=ENVELOPE):
    return {"jsonrpc": "2.0", "id": id_, "method": "tools/call",
            "params": {"name": name, "arguments": arguments, "_meta": meta}}


r = web.post(URL, json=tools_call("run_sql", {"region": "us-west1", "query": "select 1"}),
             headers={**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "run_sql", "Mcp-Param-Region": "us-west1"})
print(r.status_code, r.headers["content-type"])
print(json.dumps(r.json(), indent=2)[:600])
```

### 4. JSON or SSE? Let the request decide
The same `slow` tool is answered as JSON when nobody asked for progress, and as an SSE stream when the request carries a `progressToken`. This SDK only commits to SSE once the handler actually emits a notification.

```python
def parse_sse(text):
    return [json.loads(line[len("data: "):]) for line in text.splitlines() if line.startswith("data: ")]


h = {**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "slow"}
r = web.post(URL, json=tools_call("slow", {"steps": 2}), headers=h)
print("no progressToken  ->", r.status_code, r.headers["content-type"])

r = web.post(URL, json=tools_call("slow", {"steps": 3}, meta={**ENVELOPE, "progressToken": "tok-1"}), headers=h)
print("with progressToken->", r.status_code, r.headers["content-type"],
      "| X-Accel-Buffering:", r.headers.get("x-accel-buffering"))
for event in parse_sse(r.text):
    print("   SSE event:", event.get("method") or f"final response id={event['id']}",
          event.get("params", {}).get("message", ""))
```

### 5. Header validation: break every header
Each request below is wrong in exactly one way. All of them except the last two are rejected **before** any tool runs.

```python
good_body = tools_call("run_sql", {"region": "us-west1", "query": "select 1"})
base = {**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "run_sql", "Mcp-Param-Region": "us-west1"}
cases = {
    "all correct": base,
    "Mcp-Method lies": {**base, "Mcp-Method": "tools/list"},
    "Mcp-Name lies (WAF bypass attempt)": {**base, "Mcp-Name": "get_weather"},
    "Mcp-Name missing": {k: v for k, v in base.items() if k != "Mcp-Name"},
    "Mcp-Param-Region lies": {**base, "Mcp-Param-Region": "eu-west1"},
    "Mcp-Param-Region missing": {k: v for k, v in base.items() if k != "Mcp-Param-Region"},
    "Accept lacks text/event-stream": {**base, "Accept": "application/json"},
    "header NAMES are case-insensitive": {k.upper(): v for k, v in base.items()},
}
old_body = tools_call("run_sql", {"region": "us-west1", "query": "select 1"},
                      meta={**ENVELOPE, "io.modelcontextprotocol/protocolVersion": "2025-11-25"})
for label, headers in cases.items():
    r = web.post(URL, json=good_body, headers=headers)
    detail = r.json().get("error", {}) if r.headers.get("content-type", "").startswith("application/json") else {}
    print(f"{label:<36} HTTP {r.status_code}  {detail.get('code', '')} {detail.get('message', '')[:70]}")

r = web.post(URL, json=old_body, headers=base)          # header says 2026-07-28, body says 2025-11-25
print(f"{'body version != header':<36} HTTP {r.status_code}  {r.json()['error']['code']} {r.json()['error']['message'][:70]}")
```

The `MCP-Protocol-Version` check runs before the supported-version check, so a client that contradicts itself hears `-32020`, not `-32022`. One quirk: this dual-era SDK picks the *era* from the header, so a request whose **header** names an old version is handed to the legacy transport instead (you will see that in section 8).

Non-ASCII values travel in the base64 sentinel form. The SDK exposes the same encoder clients use:

```python
from mcp.shared.inbound import encode_header_value

for value in ["us-west1", "Zürich", " padded ", "=?base64?literal?="]:
    print(f"{value!r:<22} -> Mcp-Param-Region: {encode_header_value(value)}")

r = web.post(URL, json=tools_call("run_sql", {"region": "Zürich", "query": "select 1"}),
             headers={**base, "Mcp-Param-Region": encode_header_value("Zürich")})
print("\nencoded header accepted:", r.status_code, r.json()["result"]["content"][0]["text"])
```

### 6. Origin and Host checks against DNS rebinding
Because the app was built for host `127.0.0.1`, the SDK enabled DNS-rebinding protection with localhost-only allowlists. A page on `evil.example` that rebinds its name to 127.0.0.1 still sends its own `Origin` and `Host`:

```python
list_body = {"jsonrpc": "2.0", "id": 9, "method": "tools/list", "params": {"_meta": ENVELOPE}}
lh = {**HEADERS, "Mcp-Method": "tools/list"}
for label, extra in [("no Origin (non-browser client)", {}),
                     ("Origin http://localhost:5173", {"Origin": "http://localhost:5173"}),
                     ("Origin http://evil.example", {"Origin": "http://evil.example"}),
                     ("Host evil.example (rebinding)", {"Host": f"evil.example:{port}"})]:
    r = web.post(URL, json=list_body, headers={**lh, **extra})
    print(f"{label:<32} -> HTTP {r.status_code} {r.text[:40] if r.status_code != 200 else ''}")
```

### 7. Cancel by closing the stream
Start a long call that streams progress, read two events, then **close the connection**. No `notifications/cancelled` is sent: the disconnect itself is the signal.

```python
server_events.clear()
body = tools_call("slow", {"steps": 30}, meta={**ENVELOPE, "progressToken": "tok-2"})
with web.stream("POST", URL, json=body, headers={**HEADERS, "Mcp-Method": "tools/call", "Mcp-Name": "slow"}) as r:
    received = 0
    for line in r.iter_lines():
        if line.startswith("data: "):
            received += 1
            print("got:", json.loads(line[6:])["params"]["message"])
            if received == 2:
                break                    # leaving the block closes the response stream
time.sleep(0.5)
print("server side:", server_events)
```

### 8. Older clients and the high-level `Client`
How a 2026-07-28 server treats legacy traffic, then what the SDK `Client` sends on its own.

```python
print("GET  /mcp                ->", web.get(URL, headers=HEADERS).status_code, "(no standalone SSE stream any more)")
print("DELETE /mcp              ->", web.delete(URL, headers=HEADERS).status_code, "(no sessions to delete)")
note = {"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": 1}}
print("POST a notification      ->", web.post(URL, json=note, headers={**HEADERS, "Mcp-Method": "notifications/cancelled"}).status_code)
r = web.post(URL, json=list_body, headers={k: v for k, v in lh.items() if k != "MCP-Protocol-Version"})
print("POST without version hdr ->", r.status_code, r.json()["error"]["message"],
      "\n   (this SDK is dual-era: no header = an old client, so the legacy session transport answered)")
```

Finally, the real client. It discovers, sends `Mcp-Method`/`Mcp-Name`, and mirrors `x-mcp-header` arguments. If it does not know the schema yet, the server's `-32020` makes it re-list the tools and retry, exactly as the spec suggests.

```python
from mcp import Client

seen_headers.clear()


async def on_progress(progress, total, message):
    print(f"   progress {progress:.0f}/{total:.0f} {message}")


async with Client(URL) as client:
    print("negotiated:", client.protocol_version)
    print((await client.call_tool("run_sql", {"region": "Zürich", "query": "select 1"})).content[0].text)
    print((await client.call_tool("slow", {"steps": 2}, progress_callback=on_progress)).content[0].text)

print("\nwhat went over the wire:")
for h in seen_headers:
    print("  ", h)
uv.should_exit = True
```
