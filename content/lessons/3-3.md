## Summary
Prompts are the third server primitive and the only one controlled by the **user**: reusable, parameterised templates — "review this code", "plan a vacation" — that a person explicitly picks, typically as a **slash command**. A server lists them with `prompts/list`, and `prompts/get` renders one with the user's arguments into a list of `PromptMessage`s that can mix text, images, audio, resource links and embedded resources. Because filling in arguments by hand is error-prone, MCP pairs prompts (and resource templates) with **completion**: `completion/complete` returns up to 100 ranked suggestions for the argument being typed, aware of the arguments already chosen. This lesson covers both pages of the 2026-07-28 spec, their errors and security rules, and builds a working slash-command flow.

## Lesson
### Prompts are user-controlled
The spec defines prompts as structured messages and instructions for interacting with language models that clients can discover, retrieve and customise with arguments. They are **user-controlled**: exposed so that *the user* can explicitly select them. The spec adds a precise clarification: this "refers to who decides when the prompt is used, not who authors its content. Prompt content is defined by the server."

That makes prompts the server author's way to ship **expertise**: the best way to ask for a code review against *this* codebase's conventions, or a vacation-planning workflow that knows to check the calendar resource and call the weather tool. The docs describe them as "pre-built instruction templates that tell the model to work with specific tools and resources", and as a way to "showcase how to best use the MCP server".

| | Tools | Resources | Prompts |
| --- | --- | --- | --- |
| Who decides to use it | model | application | **user** |
| Typical trigger | the LLM emits a tool call | picker / auto-include | `/command`, menu, button |
| Output | result content | contents of a URI | messages to start or steer a conversation |

How a host surfaces them is up to it. Common patterns: **slash commands** (type `/` to see `/plan-vacation`), command palettes, dedicated buttons, context-menu suggestions. Good UIs make prompts easy to discover, describe clearly what each does, collect arguments with validation, and are transparent about the underlying template.

### Capability, listing and getting
```json
{"capabilities": {"prompts": {"listChanged": true}}}
```
A server with prompts **MUST** declare this capability in its `DiscoverResult`. The same list rules as tools and resources apply: `prompts/list` returns the prompts currently available to the requester, MUST NOT vary per connection or as a side effect of other requests, and MAY vary by authorization. It supports pagination and caching (`ttlMs`, `cacheScope`).

```json
{"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete",
  "prompts": [{"name": "code_review", "title": "Request Code Review",
               "description": "Asks the LLM to analyze code quality and suggest improvements",
               "arguments": [{"name": "code", "description": "The code to review", "required": true}]}],
  "ttlMs": 600000, "cacheScope": "public"}}
```

A `Prompt` has `name` (required), optional `title`, `description`, `icons`, `arguments` and `_meta`. Each `PromptArgument` has `name`, optional `title`, `description` and `required`. Note what is *missing*: there is no type field. On the wire, `prompts/get` arguments are a map of **string to string**:

```json
{"jsonrpc": "2.0", "id": 2, "method": "prompts/get",
 "params": {"name": "code_review", "arguments": {"code": "def hello():\n    print('world')"}}}
```
```json
{"jsonrpc": "2.0", "id": 2, "result": {"resultType": "complete", "description": "Code review prompt",
  "messages": [{"role": "user", "content": {"type": "text",
                "text": "Please review this Python code:\ndef hello():\n    print('world')"}}]}}
```

> **Pitfall.** The conceptual "Understanding MCP servers" page shows a `plan-vacation` prompt whose arguments carry `"type": "number"` and `"type": "array"`. That is illustrative; the normative schema's `PromptArgument` has no `type`, and argument values are strings. Parse numbers on the server and validate them.

`prompts/get` may also return an `InputRequiredResult` (multi round-trip): the server asks for more input — say, an elicitation — before it can resolve the prompt, and the client retries with `inputResponses` and `requestState` (lesson 5.3).

### `PromptMessage`: roles and content
`GetPromptResult` holds an optional `description` and `messages`, each a `PromptMessage` with:

- `role`: `"user"` or `"assistant"` — so a prompt can pre-seed a multi-turn exchange (few-shot examples, or an assistant turn that frames the task),
- `content`: one content block.

The content types are the same family as tool results:

| Type | Notes |
| --- | --- |
| `text` | the most common case |
| `image` | base64 `data` + valid `mimeType` (**MUST**) |
| `audio` | base64 `data` + valid `mimeType` (**MUST**) |
| `resource_link` | a URI the client can fetch, without inlining the contents |
| `resource` (embedded) | server-side content inlined; **MUST** include a valid URI, the MIME type, and either `text` or base64 `blob` |

All of them accept the optional `audience` / `priority` / `lastModified` annotations. **Embedded resources** are what makes prompts powerful: a `review_against_style_guide` prompt can pull the team's style guide and the file under review straight into the conversation, so the user picks one command and the model receives everything it needs.

There is no `system` role. A prompt shapes the *conversation*; the host still owns its own system prompt, and it decides how to translate `PromptMessage`s into its model provider's message format.

### List changes, errors and good practice
When the set of prompts changes, a server that declared `listChanged` SHOULD send `notifications/prompts/list_changed` — in 2026-07-28 only to clients that opened a `subscriptions/listen` stream with `promptsListChanged: true` (lesson 3.4).

Errors are standard JSON-RPC: servers SHOULD return **`-32602`** for an invalid prompt name and for missing required arguments, and **`-32603`** for internal errors. Implementation considerations: servers SHOULD validate prompt arguments before processing; clients SHOULD handle pagination for large prompt lists; both parties SHOULD respect capability negotiation. On security, implementations **MUST** carefully validate all prompt inputs and outputs to prevent injection attacks or unauthorised access to resources — a prompt that interpolates a user argument into instructions, or embeds a resource chosen by argument, is an injection and data-access surface.

### Completion: autocomplete for arguments
Prompt arguments and resource-template variables are free text, but valid values are often a closed or searchable set: languages, cities, airport codes, repository names. **Completion** gives an IDE-like experience: as the user types, the client asks the server for suggestions.

A server that supports it **MUST** declare:

```json
{"capabilities": {"completions": {}}}
```

The request names *what* is being completed with a reference, the argument and its current value:

```json
{"jsonrpc": "2.0", "id": 1, "method": "completion/complete",
 "params": {"ref": {"type": "ref/prompt", "name": "code_review"},
            "argument": {"name": "language", "value": "py"}}}
```
```json
{"jsonrpc": "2.0", "id": 1, "result": {"resultType": "complete",
  "completion": {"values": ["python", "pytorch", "pyside"], "total": 10, "hasMore": true}}}
```

| Reference type | Identifies | Example |
| --- | --- | --- |
| `ref/prompt` | a prompt by `name` | `{"type": "ref/prompt", "name": "code_review"}` |
| `ref/resource` | a resource URI or URI template by `uri` | `{"type": "ref/resource", "uri": "file:///{path}"}` |

For prompts or templates with **several arguments**, clients should send what is already resolved in `context.arguments`, so suggestions can depend on earlier choices:

```json
{"ref": {"type": "ref/prompt", "name": "code_review"},
 "argument": {"name": "framework", "value": "fla"},
 "context": {"arguments": {"language": "python"}}}
```
→ `{"completion": {"values": ["flask"], "total": 1, "hasMore": false}}`. With `language: "javascript"` the same prefix would never suggest Flask.

The result rules: `values` is ranked by relevance with **at most 100 items**; `total` (optional) is the number of matches, which may exceed what was sent; `hasMore` (optional) says more exist even if the exact total is unknown.

### Completion errors and practice
Errors: `-32601` when the capability isn't supported (method not found), `-32602` for an invalid prompt name or missing required arguments, `-32603` for internal errors. Servers SHOULD sort by relevance, use fuzzy matching where appropriate, **rate-limit** and validate inputs. Clients SHOULD **debounce** rapid requests (don't send one per keystroke), cache results where appropriate, and cope with missing or partial results. Implementations **MUST** validate inputs, rate-limit, control access to sensitive suggestions, and **prevent completion-based information disclosure** — autocomplete over customer names or private repositories is a data leak if it ignores the caller's authorization.

### Putting the three primitives together
The docs' multi-server travel example shows the intended choreography. The **user** invokes `/plan-vacation` with destination, dates, budget (completion helps pick "Barcelona"). The user selects **resources** — their June calendar, travel preferences, past trips — which the application attaches. The prompt's messages instruct the **model**, which calls **tools** — `searchFlights`, `checkWeather`, then, with approval, `bookHotel`, `createCalendarEvent`, `sendEmail`. Prompts supply intent and structure, resources supply context, tools supply action — each under its own controller.

## Key points
- Prompts are **user-controlled**: the user decides *when*; the server defines the *content*. Hosts usually surface them as slash commands.
- Declare `prompts` (`listChanged` optional); `prompts/list` (paginated, cacheable) and `prompts/get` (may return `input_required`).
- `PromptArgument` = `name`, `title?`, `description?`, `required?` — no type; `prompts/get` argument values are **strings**.
- `GetPromptResult.messages` is a list of `PromptMessage` with `role` `user`/`assistant` and one content block: text, image, audio, `resource_link` or embedded `resource`.
- Embedded resources MUST include a URI, MIME type and `text` or `blob`; they let one command bring the right context with it.
- Prompt errors: `-32602` for unknown prompt or missing required argument, `-32603` internal; validate inputs and outputs against injection.
- Completion needs the `completions` capability; `completion/complete` takes `ref` (`ref/prompt` or `ref/resource`), `argument {name, value}` and optional `context.arguments`.
- Results: `values` ranked, **max 100**, plus optional `total` and `hasMore`; clients debounce, servers rate-limit and prevent information disclosure.

## Pitches
### What are MCP prompts and why would a server offer them?
Prompts are reusable templates a user explicitly invokes, usually as a slash command. The user picks one and fills a few arguments; the server returns ready-made messages, possibly with embedded resources like a style guide or a file. That lets the server author package expertise — the right way to ask for a review or a migration plan with this server's tools — so users get consistent, high-quality workflows without writing the prompt themselves.

### How does argument completion work in MCP?
When a user fills in a prompt argument or a resource template variable, the client sends completion/complete with a reference to the prompt or template, the argument name and what has been typed so far, plus any arguments already chosen as context. The server answers with up to a hundred ranked suggestions, an optional total, and a hasMore flag. The client debounces keystrokes, and the server rate-limits and makes sure suggestions never reveal data the caller couldn't otherwise see.

### When should something be a prompt rather than a tool?
I ask who should decide to use it. If the model should be able to reach for it mid-conversation, it's a tool. If it's a workflow a person deliberately kicks off — review this pull request, write the release notes, plan a trip — it's a prompt, surfaced as a slash command. Prompts don't execute anything; they produce well-crafted messages, often with embedded resources, that steer the model to use the right tools. Many good servers ship both: tools for actions, prompts as guided entry points.

## Interview
### How do prompts differ from tools, if both can be "used" by the AI application?
The difference is the controller. A tool is **model-controlled**: the LLM decides mid-conversation to call it, and it may have side effects. A prompt is **user-controlled**: a person explicitly picks it, typically a slash command, and it produces *messages* that start or steer a conversation — it doesn't execute anything itself. The spec stresses that user-controlled refers to who decides when, not who writes the content: the server authors it. A prompt often *orchestrates* tools and resources by instructing the model to use them.

### What can a prompt return, and when would you embed a resource?
A list of `PromptMessage`s, each with role `user` or `assistant` and one content block: text, image, audio (base64 with a valid MIME type), a `resource_link`, or an embedded `resource` that MUST carry a URI, MIME type and `text` or `blob`. Embed when the content is small and certainly needed — the team's style guide inside `/review`, the failing test inside `/fix-test` — so the user gets full context with one command. Use a link when it's large or optional and let the host decide whether to fetch it.

### A client sends `prompts/get` without a required argument. What should happen?
The server SHOULD return a JSON-RPC error **`-32602` (Invalid params)**, the same code as for an unknown prompt name; `-32603` is for genuine internal failures. Ideally the message names the missing argument so the host can prompt the user for it. Gotcha: some SDKs collapse these to `-32603`; the Python `MCPServer` does, so to follow the spec you validate yourself and raise an `MCPError` with `INVALID_PARAMS`.

### Design completion for a `deploy` prompt with `environment` and `service` arguments.
Declare `completions`. For `environment`, return the environments the caller may deploy to, filtered by prefix. For `service`, use `context.arguments.environment` to list only services that exist there. Rank by relevance (exact prefix, then fuzzy, then recency), cap at 100 values, set `total` and `hasMore` honestly. **Authorize** every suggestion against the caller's token — completion must not leak service names the user can't see — and rate-limit. Client side, debounce keystrokes (~200 ms) and cache results per `(ref, argument, value, context)`.

### Gotcha: the docs show a prompt argument with `"type": "number"`. Can I declare typed prompt arguments?
Not in the protocol. That example comes from the conceptual "Understanding MCP servers" page; the normative `PromptArgument` has only `name`, `title`, `description` and `required`, and `prompts/get` sends `arguments` as a string-to-string map. Put the expected format in the `description`, offer completion for closed sets, and parse and validate on the server, returning `-32602` for bad values. If you need rich typed input, a tool with an `inputSchema` — or an elicitation form — is the better fit.

## Glossary
- Prompt | 提示模板 | A server-defined, parameterised message template that the user explicitly invokes.
- User-controlled | 用户控制 | Interaction model in which the user decides when a primitive is used.
- Slash command | 斜杠命令 | A UI pattern where typing `/` lists prompts the user can run.
- PromptArgument | 提示参数 | A named, optionally required, string-valued input to a prompt.
- PromptMessage | 提示消息 | One message of a rendered prompt, with a `user`/`assistant` role and a content block.
- Embedded resource | 嵌入式资源 | A content block that inlines a resource's URI, MIME type and text or blob.
- Completion | 参数补全 | Server-provided autocomplete suggestions for prompt and resource-template arguments.
- `ref/prompt` / `ref/resource` | 补全引用类型 | Reference types identifying the prompt or resource template being completed.
- Debounce | 防抖 | Delaying requests until the user pauses typing to avoid one request per keystroke.

## Notebook
### 1. A server with three kinds of prompts
`@server.prompt()` turns a function into a prompt: parameters become arguments (required when they have no default, described with `Field(description=...)`), the docstring becomes the description. The function can return a string (one user message) or a list of `UserMessage` / `AssistantMessage` and raw content blocks.

```python
import json
import logging
from typing import Annotated

from pydantic import Field

import mcp_types as types
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import AssistantMessage, UserMessage
from mcp.shared.exceptions import MCPError

logging.getLogger("mcp").setLevel(logging.CRITICAL)


def show(model, limit=1800):
    data = model.model_dump(by_alias=True, exclude_none=True, mode="json")
    data.pop("_meta", None)
    print(json.dumps(data, indent=2, ensure_ascii=False)[:limit])


STYLE_GUIDE = "1. Type hints everywhere.\n2. No bare except.\n3. Functions under 40 lines."

server = MCPServer("dev-workflows")


@server.resource("docs://style-guide", mime_type="text/markdown")
def style_guide() -> str:
    return STYLE_GUIDE


@server.prompt(title="Request Code Review")
def code_review(code: Annotated[str, Field(description="The code to review")],
                language: Annotated[str, Field(description="Programming language")] = "python") -> str:
    """Asks the LLM to analyze code quality and suggest improvements."""
    return f"Please review this {language} code:\n{code}"


@server.prompt(title="Plan a vacation")
def plan_vacation(destination: Annotated[str, Field(description="City or region")],
                  days: Annotated[int, Field(description="Trip length in days (whole number)")] = 7) -> list:
    """Guide the model through planning a trip, with a worked example of the expected format."""
    return [
        UserMessage("Plan a 2-day trip to Lisbon."),
        AssistantMessage("Day 1: Alfama + tram 28. Day 2: Belém + LX Factory. Budget: ~€180."),
        UserMessage(f"Great format. Now plan a {days}-day trip to {destination}. "
                    "Check my calendar resource and the weather tool before proposing dates."),
    ]


@server.prompt(title="Review against the style guide")
def review_with_guide(code: Annotated[str, Field(description="The code to review")]) -> list:
    """Review code against the team style guide, which is embedded in the conversation."""
    return [
        UserMessage(types.EmbeddedResource(type="resource", resource=types.TextResourceContents(
            uri="docs://style-guide", mime_type="text/markdown", text=STYLE_GUIDE))),
        UserMessage(f"Review this code strictly against the style guide above:\n{code}"),
    ]


print("prompts:", [p.name for p in await server.list_prompts()])
```

### 2. `prompts/list`: what a slash-command menu needs
Arguments carry `name`, `description` and `required` — but no type. A host renders this as `/code_review <code> [language]`.

```python
async with Client(server) as client:

    print()
    for p in listing.prompts:
        args = " ".join(f"<{a.name}>" if a.required else f"[{a.name}]" for a in p.arguments or [])

```

### 3. `prompts/get`: render with arguments
Arguments travel as strings; `MCPServer` converts `"5"` to `int` for `days` using the type hint. Look at the roles in the multi-message prompt and the embedded resource block.

```python
async with Client(server) as client:
    print("--- code_review")
    show(await client.get_prompt("code_review", {"code": "def hello():\n    print('world')"}))
    print("\n--- plan_vacation (days arrives as the string '5')")
    for m in (await client.get_prompt("plan_vacation", {"destination": "Barcelona", "days": "5"})).messages:
        print(f"{m.role:>9}: {m.content.text}")
    print("\n--- review_with_guide")
    show(await client.get_prompt("review_with_guide", {"code": "try:\n    run()\nexcept:\n    pass"}))
```

### 4. A host's slash-command handler
The host — not the protocol — turns `PromptMessage`s into its model's message format. Here: parse `/command key=value`, call `prompts/get`, and convert to Anthropic-style messages (embedded resources become tagged text; consecutive same-role messages are merged because many chat APIs require alternation).

```python
import shlex


def to_chat_messages(prompt_messages):
    chat = []
    for m in prompt_messages:
        c = m.content
        if c.type == "text":
            block = {"type": "text", "text": c.text}
        elif c.type == "resource":
            body = getattr(c.resource, "text", "<binary>")
            block = {"type": "text", "text": f"<resource uri='{c.resource.uri}'>\n{body}\n</resource>"}
        elif c.type == "image":
            block = {"type": "image", "source": {"type": "base64", "media_type": c.mime_type, "data": c.data}}
        else:
            block = {"type": "text", "text": f"[{c.type}]"}
        if chat and chat[-1]["role"] == m.role:
            chat[-1]["content"].append(block)
        else:
            chat.append({"role": m.role, "content": [block]})
    return chat


async def run_slash_command(client, line: str):
    name, *pairs = shlex.split(line.lstrip("/"))
    arguments = dict(pair.split("=", 1) for pair in pairs)
    result = await client.get_prompt(name, arguments)
    return to_chat_messages(result.messages)


async with Client(server) as client:
    messages = await run_slash_command(client, "/review_with_guide code='except: pass'")
print(json.dumps(messages, indent=2))
```

### 5. Break it: bad arguments and the error code
The spec says unknown prompt names and missing required arguments SHOULD be `-32602`. See what the SDK actually sends.

```python
async with Client(server) as client:
    for label, name, args in [("missing required arg", "code_review", {}),
                              ("unknown prompt", "deploy", {}),
                              ("non-numeric days", "plan_vacation", {"destination": "Rome", "days": "a week"})]:
        try:
            await client.get_prompt(name, args)
        except MCPError as err:
            print(f"{label:<22} -> code={err.code} message={err.message!r}")
```

All three come back as `-32603` "Internal server error" — an SDK gap, and unhelpful to a user filling in a form. Fix it in the handler: accept the raw string, validate, and raise `MCPError` with `INVALID_PARAMS`, which the SDK passes through unchanged.

```python
from mcp_types import INVALID_PARAMS


@server.prompt(title="Plan a vacation (validated)")
def plan_trip(destination: Annotated[str, Field(description="City or region")],
              days: Annotated[str, Field(description="Trip length in days, 1-30")] = "7") -> str:
    """Plan a trip; validates its arguments and reports problems as -32602."""
    if not days.isdigit() or not 1 <= int(days) <= 30:
        raise MCPError(INVALID_PARAMS, f"Argument 'days' must be a whole number from 1 to 30, got {days!r}",
                       data={"argument": "days"})
    return f"Plan a {int(days)}-day trip to {destination}."


async with Client(server) as client:
    try:
        await client.get_prompt("plan_trip", {"destination": "Rome", "days": "a week"})
    except MCPError as err:
        print("fixed:", err.code, err.message, err.data)
```

### 6. Completion for prompt arguments and template variables
One `@server.completion()` handler serves every `completion/complete` request; it receives the `ref`, the `argument` (`name`, `value`) and the `context` with already-resolved arguments. Registering it makes the server advertise the `completions` capability. We cap values at 100 and report `total` / `hasMore`.

```python
LANGUAGES = ["python", "pytorch", "pyside", "perl", "php", "javascript", "java", "go", "rust"]
FRAMEWORKS = {"python": ["flask", "fastapi", "django"], "javascript": ["express", "fastify", "next"]}
CITIES = ["Paris", "Park City", "Parma", "Barcelona", "Barbados", "Berlin"]


@server.resource("weather://forecast/{city}/{date}", mime_type="application/json")
def forecast(city: str, date: str) -> str:
    return json.dumps({"city": city, "date": date, "high_c": 27})


@server.prompt()
def scaffold(language: str, framework: str) -> str:
    """Scaffold a new web service."""
    return f"Create a {framework} service in {language}."


def ranked(options, prefix, limit=100):
    matches = [o for o in options if o.lower().startswith(prefix.lower())]
    return types.Completion(values=matches[:limit], total=len(matches), has_more=len(matches) > limit)


@server.completion()
async def complete(ref, argument, context):
    resolved = (context.arguments if context and context.arguments else {})
    if isinstance(ref, types.PromptReference):
        if argument.name == "language":
            return ranked(LANGUAGES, argument.value)
        if argument.name == "framework":
            return ranked(FRAMEWORKS.get(resolved.get("language", ""), []), argument.value)
    if isinstance(ref, types.ResourceTemplateReference) and ref.uri == "weather://forecast/{city}/{date}":
        if argument.name == "city":
            return ranked(CITIES, argument.value)
    return None   # no suggestions -> empty values


prompt_ref = types.PromptReference(type="ref/prompt", name="scaffold")
template_ref = types.ResourceTemplateReference(type="ref/resource", uri="weather://forecast/{city}/{date}")

async with Client(server) as client:
    print("completions capability declared:", client.server_capabilities.completions is not None)
    show(await client.complete(prompt_ref, {"name": "language", "value": "py"}))
    print("framework 'f' with language=python:", (await client.complete(
        prompt_ref, {"name": "framework", "value": "f"}, {"language": "python"})).completion.values)
    print("framework 'f' with language=javascript:", (await client.complete(
        prompt_ref, {"name": "framework", "value": "f"}, {"language": "javascript"})).completion.values)
    print("city 'Par' for the forecast template:", (await client.complete(
        template_ref, {"name": "city", "value": "Par"})).completion.values)
```

### 7. Completion on the wire, and a server without the capability
The raw `completion/complete` exchange over stdio, then the same request to a server that never registered a completion handler: `-32601` method not found, exactly as the spec lists.

```python
import subprocess
import sys
import tempfile
import textwrap
from pathlib import Path

workdir = Path(tempfile.mkdtemp())
(workdir / "complete_server.py").write_text(textwrap.dedent('''
    import sys
    import mcp_types as types
    from mcp.server import MCPServer
    server = MCPServer("completer")

    @server.prompt()
    def code_review(code: str, language: str) -> str:
        """Review code."""
        return f"Review this {language} code: {code}"

    if "--with-completion" in sys.argv:
        @server.completion()
        async def complete(ref, argument, context):
            langs = ["python", "pytorch", "pyside", "perl", "php"]
            hits = [l for l in langs if l.startswith(argument.value)]
            return types.Completion(values=hits[:3], total=len(hits), has_more=len(hits) > 3)

    if __name__ == "__main__":
        server.run(transport="stdio")
'''))

        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "by-hand", "version": "0.1"}}
request = {"jsonrpc": "2.0", "id": 1, "method": "completion/complete",

for flags in (["--with-completion"], []):

    proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    reply.get("result", {}).pop("_meta", None)
    print(f"server flags={flags}\n>>> {json.dumps({k: v for k, v in request['params'].items() if k != '_meta'})}")
    print("<<<", json.dumps(reply), "\n")
    proc.stdin.close()
    proc.wait(timeout=10)
```

### 8. Debouncing on the client
Clients SHOULD debounce. Simulate a user typing `b`, `ba`, `bar`, `barc` quickly, then pausing: only the last value is sent.

```python
import asyncio

sent = []


async def debounced_complete(client, ref, arg_name, keystrokes, delay=0.15):
    pending = None

    async def fire(value):
        await asyncio.sleep(delay)
        sent.append(value)
        return (await client.complete(ref, {"name": arg_name, "value": value})).completion.values

    for value, gap in keystrokes:
        if pending:
            pending.cancel()
        pending = asyncio.create_task(fire(value))
        await asyncio.sleep(gap)
    return await pending


async with Client(server) as client:
    typing = [("b", 0.03), ("ba", 0.03), ("bar", 0.03), ("barc", 0.0)]
    values = await debounced_complete(client, template_ref, "city", typing)
print("keystrokes:", [k for k, _ in typing], "| requests actually sent:", sent, "| suggestions:", values)
```
